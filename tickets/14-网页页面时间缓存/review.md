## 裁定（10-31，优先于 design.md 第 14 节）
1. **路线改为读回先行**：录制用仓库已跑通的 web-replay GPU 取帧（WebGPU 读回）+ FrameEncoder / 随包 ffmpeg.exe 管道，编码器沿用 video/hwaccel.ts 的多厂商探测（Windows NVENC，macOS hevc_videotoolbox，其余软编），一并覆盖 macOS。先实测 1080p/4K/8K 读回 + 编码吞吐；只有 8K 确实被读回卡住才另立原生纹理输入，本票不做原生纹理桥。
2. **色度**：实施第一步做探针：本机 FFmpeg 能否硬解 HEVC 4:4:4、4:2:0 能否过彩字画质门槛。能硬解 4:4:4 就用（管道送 yuv444p 也避开 NVENC 内部 BT.601 转换），否则 4:2:0；4:2:0 也过不了门槛就停下回报。
3. **采样网格带相位**：网格为 t = φ + n/F，相位 φ 进变体键，常见片段（src 任意秒数）也能命中。
4. **共享解码会话**：同一变体的所有段共用一个解码会话（段间无参考，接着喂下一段的包）；按实际参考帧数缩减表面。
5. **外来内容（安全底线 3）**：只有本会话已通过确认（含“仅这一次”的范围写清）的来源才能登记补录与预热；后台永不弹窗；缓存域供页仍按原网页文件夹的外来标记判断。
6. **确定性前提**：以 henjiWeb.seek 的确定性约定为前提；站外请求用全协议 webRequest 记录为不可缓存原因；系统字体进环境签名；不去“识别”时钟与随机。录制槽与实时页共用同一存储分区语义。
7. **只缓存可靠帧**：只录 html-in-canvas 快照路径且守护区校验通过的帧；unsettled、降级、设备丢失前后的帧不发布。
8. **显式精度参数**：渲染入口加显式精度参数，缺省精确；只有节目监视器上屏的播放、拖动、暂停，以及显式开启 useWebCache 的导出和自动预渲染放行有损缓存；离屏取帧消费方（颜色分析、OCR、敏感文字、跟踪、场景检测、定格、发到画布、收集输出、render_video_edit_preview 等）一律精确。
9. 采纳：先录 ≤1440p 预览档服务播放与拖动，最高档按暂停与导出需要再补。
10. 采纳：抢占时只停提交、保留页面与编码会话续录（显存紧张才释放，注意 .tmp 清理期）；导出精确取到的网格帧顺手写进缓存。
11. 采纳：跨实例协调用随进程退出自动释放的内核对象（命名互斥体或独占锁文件），不自建选主心跳。
12. 采纳：NVENC 等开会话失败当暂时资源不足，降级槽位，不记成“不支持”。
13. 采纳：缺帧时向前重跑本段，不往回 seek；守护区校验位置与回读开销写清。
14. 采纳：倍率离散档位 + 迟滞，只在跨档时调整。
15. 采纳：占位纹理同尺寸全局共用一张，不计入本帧必需硬预算；修尺寸语义。
16. 采纳：不复制网页文件夹，出文件时按批次清单哈希校验，不符作废本批。
17. 采纳：缓存实例给无限预算、由段族统一回收；SHA 在发布时算，读时只核尺寸；删掉引用者集合。
18. 采纳：多槽相邻段交叠一帧比对，不一致就该页面只允许单槽顺序录。
19. 采纳：旧预渲染缺 provenance 视为实时网页，可照常复用。

## 探针后的裁定（11-01）
- 4:2:0 即使无损也只有 24.31 dB / 0.8587（彩字色度丢失，提高码率救不回）→ **4:2:0 不用于网页缓存**。
- **缓存编码定为 HEVC 4:4:4 8 位无损（NVENC constqp 0）**，只在本机 4:4:4 硬件编码与硬件解码都探测通过的设备上启用；不通过的设备不建缓存，网页照旧走实时路径（行为与现在相同，不降画质）。macOS 本票不启用缓存（VideoToolbox 4:4:4 能力以后单独验证，Mac 由用户自测）。
- 读回改为 RGBA → GPU 着色器转平面 4:4:4（BT.709，范围与反变换配对、保证往返误差最小），不走现有 NV12/BT.601 reader。
- 先测 1440p 预览档与 4K 档的吞吐和每分钟体积；无损体积过大（1440p60 超过约 200 Mbps）时再试 qp 4–8 的近无损档，按 RGB PSNR ≥ 45 dB、SSIM ≥ 0.995 且人眼放大看彩字无色边判定。
- 门槛不变：45 dB / 0.995。

## 读回阶段后的裁定（11-01）
- 4:4:4 无损体积可接受：1440p 约 372 MB/分钟（≈50 Mbps）、4K 约 803 MB/分钟，画质 50 dB / SSIM 0.9995。后台补录 1440p 19.5 fps、4K 9.3 fps 可用。
- 阻塞是正式解码入口：D3D11VA 对 HEVC 4:4:4 回退软解。按顺序解决：① 先在本机枚举 D3D11 视频解码器档案，看驱动是否提供 HEVC RExt 4:4:4（Main444）GUID；有就把它登记进原生解码服务的档案表并核对 FFmpeg d3d11va 对 RExt 的支持，走现有共享纹理链；② 没有再做 NVDEC（CUDA）解码 + CUDA/D3D11 互操作写入共享纹理；两条都不通就停下回报，不接受软解。
- 之后继续缓存调度、读缓存与回退、精度参数、03 遗留、useWebCache 与真机验收。

## 接手后真机数据裁定（11-01）
轻页面上缓存读取（1080p 22 ms、4K 32 ms）比实时取帧（12.6 ms）慢。
1. 先查根因：HEVC 4:4:4 硬解本应几毫秒，22 ms 说明读路径有瓶颈（会话建立、拷贝或等待）。剖析并修，目标是轻页面上缓存读取不慢于实时取帧。
2. 再加自适应兜底（批准，属设计调整）：播放与拖动按每个页面实测的读取与实时耗时（滑动平均）择优，实时够快就不读缓存；导出按用户开关；精确消费方照旧。
3. 用重页面（复杂 DOM/动画/图表）再测一组，判断缓存的收益区间。
4. 导出行文案：标签“使用网页缓存”；悬停“网页画面取自已录好的缓存，导出更快；缓存缺失的部分实时渲染。”（无损且与可靠真值逐字节一致，不写“可能有细微差异”）。
剩余照旧：节目播放与来回拖动流畅度、冷页首播丢帧、导出整帧耗时、真实显存紧张、约 600 帧验收、4K 偶发补录失败查因、“精确导出取到的帧写进缓存”。
