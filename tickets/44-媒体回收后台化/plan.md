# 44 媒体回收后台化：实现范围

摘要 1：媒体回收从“卡在界面加载前 3 秒、从未跑完”改为“界面加载后在后台跑一轮”，只删上一次运行留下、且在本次启动那一刻没有任何持久引用的文件。
摘要 2：先让候选表停止膨胀（缓存搬出设置表、触发器只在旧行可能含路径时入队、迁移清存量），再做后台化；顺带落地 D5（调用记录保留期）与 D4（快照与自检不挡启动）。
摘要 3：分级 L2 且命中高风险路径（删除用户数据、持久格式迁移、主进程生命周期）；每步提交前做独立审查；设计见同目录 design.md，冲突时以本文件为准。

## 目标

1. 候选表不再因设置改写、助手调用状态改写而增长；存量从 15,655 行 / 约 105 MB 降到约 1,700 行 / 约 5 MB，数据库压缩后回到约 55 MB。
2. 启动不再等回收：“应用界面加载完成”（`window.renderer.load_completed`）提前约 3 秒。
3. 回收能真正跑完：正常启动后日志出现 `media_recycle.background.completed`，无人引用的受管文件进入“最近删除”和系统回收站。
4. 宁可不删、不能错删：任何一项前提不成立，本次运行整轮放弃，候选原样保留到下次。

## 不做

- 不恢复渲染层实时引用上报（t192 已删除的那条链路）。
- 不给“仍被引用的候选”加删除出口（理由见 design.md 第 6 节）。
- 不改退出回收的 3 秒预算与判定条件。
- 不处理音频任务大结果改存文件（D5 第 3 条）、迁移前备份文件的保留策略。

## 依赖与顺序

| 步骤 | 内容 | 依赖 | 持久格式迁移 |
|---|---|---|---|
| S1 | 两类缓存搬出设置表 | 无 | 无 |
| S2 | 触发器加入队条件、清存量、清缓存旧行、启动压缩 | S1 | SQLite 账本 26 → 27，新增黄金样本 |
| S3a | 后台回收实现（未接线） | S2 | 无 |
| S3b | 接线、移除启动阻塞、门禁 | S3a；D2 单实例锁先合入 | 无 |
| S4 | 助手调用记录终态保留期 | S2 | 无 |
| S5 | 每日快照改在线备份并后置、保留策略、大库自检后置 | S2（体积先降下来） | 无 |

S4、S5 与 S3 互不依赖，可并行；S3b 是唯一会让应用第一次真正删除文件的提交。

## 完成标准

- S1：打开含代码素材的剪辑工程后，`settings` 表不再出现 `cache.video-edit.*` 的新行；参数面板与性能提示行为不变。
- S2：隔离库里 1 万次设置改写、助手调用状态改写后候选表行数不变；真实资料目录副本迁移后候选约 1,700 行，压缩后数据库约 55 MB；`npm run check:persistence-compat` 通过。
- S3a：design.md 第 10 节列出的用例全部存在且改前会失败；`npm run check:media-recycle` 通过。
- S3b：演练模式（`HENJI_MEDIA_RECYCLE_DRY_RUN=1`）在真实资料目录跑一轮，把“将回收清单”交用户过目后再去掉演练开关；日志出现 `media_recycle.background.completed`；`window.renderer.load_completed` 距进程启动的时间比改前少约 3 秒；`test:reality -- --suite restart` 的回收场景通过。
- S4：超过保留期的终态记录被清理，当天记录、带付费预留的记录、待核对记录原样保留；查询已清理的操作返回明确的“已过保留期”说明。
- S5：有快照与没有快照的启动，`window.renderer.load_completed` 时间基本一致；损坏库仍能被发现并从快照恢复。
- 每步：改动文件的精确 vitest、`tsc`（`tsconfig.json` 与 `tsconfig.electron.json`）、相关门禁通过；独立审查的重要问题全部处理。

## 需要调度者拍板

1. 助手调用记录按 30 天保留，当前一条也删不掉（最老的记录 26 天），这张表会稳定在 35–40 MB。要让数据库明显变小需要改成 7 或 14 天，或者另行瘦身 `record_json`。
2. D2（单实例锁）是否排在 S3b 之前。建议是：回收真正开始删文件之后，第二个窗口实例的未保存引用就不再有“回收反正跑不完”这层意外保护。
3. S3b 首次在真实资料目录启用前，是否先跑演练模式并让用户看一遍清单。建议要。
