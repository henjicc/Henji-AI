# 排查：主链路的助手可用性（2026-11-13，只读）

> 范围：录屏 → 音频编辑后台录音 → 转写、本地粗剪、助手二次优化、校对 → 送进剪辑、AI 参与剪辑 → 导出。
> 方法：读能力声明（`src/core/application-control/domains/**`）、实体与属性登记（`*Fields.ts`、`*Reflection.ts`）、处理函数、助手技能文档（`resources/assistant-skills/**`），对照 `tickets/46-正式使用链路/`、`tickets/45-全局性能/` 的 result 文件与代码里的真实行为。
> 没有改代码、没有碰 git、没有启动应用、没有跑 assistant:cli 或付费调用。跑过一次 `npm run check:application-control-coverage`：15 项全过（只说明已登记的路径完整，不代表下面这些缺口不存在）。

## 总评

**录屏、转写、剪辑、导出这几步助手都能发起和读回；整条链在两处断开，另有两处说明会把助手带错：** 一是音频编辑录音完全做不了，界面重载后读到的录音状态也可能是错的；二是本地粗剪交给助手的待确认线索读不到关键字段，技能文档和回执让助手去筛的 `kind=retake` 根本没有登记成属性；三是音频编辑的算法操作（去重念、快速处理、呼吸声等）助手没有办法单步撤销，只能整份还原；四是两份技能文档仍写着“口播后续剪切不更新剪辑字幕”，和 11-13 改过后的行为相反。

## 二、缺口清单

### A. 助手完全做不了

**A1 音频编辑录音的开始、暂停、停止、恢复都没有对助手开放**（已知缺口，已核实）
- 证据：`src/core/audioCapture/contracts.ts:83` 的 `AUDIO_CAPTURE_CONTROL_EXCLUSION`；`src/features/application-control/audioCaptureDomain.ts` 的 `registerCapabilities() {}` 为空；`audio-edit-workbench/SKILL.md` 里没有录音这一步。
- 排除理由已经过时：它写的是“避免无作品归属、无结果撤销的后台录音”，但 10-23 起录音已经绑定作品和位置（`AudioCapturePlacement`：projectId、起止帧、revision、spliceId），停止后由 `restoreAudioEditTake` 拼进作品，算一步撤销；11-13 起切工作区、界面重载也不停。
- 业务实现已经有了，不用新写：`prepareAudioEditTake(projectId, start, end)`（`src/features/audioEdit/application/audioEditSpliceService.ts:42`）→ `getAudioCaptureSession().start(placement)` / `togglePause()` / `stop()` / `recoverTake()` / `recover()`（`src/features/audioCapture/captureSession.ts`）；新建录音草稿用 `createAudioEditRecording()` 背后的 `createAudioEditDraft(null)`，但助手调用时不应该切页面。
- 建议修法：录音是有设备副作用的会话生命周期，写不成属性；按 `start_screen_recording` 的先例补一组语义能力（这一点和“专用能力只留给算法型操作”的字面说法有出入，请用户定）：
  - `start_audio_edit_recording`：documentRef 可选（不给就新建录音草稿，不切页面）、positionSeconds、replaceUntilSeconds；返回会话状态。
  - `pause_audio_edit_recording` / `resume_audio_edit_recording`。
  - `stop_audio_edit_recording`：拼回作品并保存，回读作品时长作为成功证据。
  - `recover_audio_edit_recording`：恢复中断的录音或待恢复文件。
  - 安全语义：不付费、不执行外来代码；放弃录音时文件进回收区（现有 `trashFile`）。
  - 录屏开着麦克风时，开始录音会被拒（`RECORDING_ACTIVE`，`electron/main/services/audio-capture/service.ts:225`），这条要写进说明。
  - 同步修改 `AUDIO_CAPTURE_CONTROL_EXCLUSION`、`audio_capture.settings` 的实体描述、`insert_audio_edit_file` 描述里的“录音设备控制不在此能力内”，以及 `audio-edit-workbench` 技能。
- 拿不准：`create_document` 新建、还没有素材的口播能不能直接进 `prepareAudioEditTake`。`loadAudioEditProject` 遇到无素材文档会拒绝（见 `registerAudioEditCapabilityHandlers.ts:68` 的注释），可能要像界面那样先建录音草稿。
- 工作量：中，约 1 天（声明加处理器、结果测试、技能文档），要真机录音验收。
- 涉及文件：`src/core/application-control/domains/` 下新建或扩展 audioCapture 的能力声明、`src/features/application-control/audioCaptureDomain.ts`、**`src/core/audioCapture/contracts.ts`（正被别人改）**、**`src/features/audioCapture/*`（captureTestFixture.ts 正被别人改；captureSession.ts、captureApplicationService.ts 本身没在改，但在同一目录）**、`resources/assistant-skills/audio-edit-workbench/SKILL.md`。建议等录音那批改动提交后再做。

**A2 录音状态读回不可靠，也不全**（属于“读不回”，和 A1 一起修）
- 证据：`src/features/audioCapture/captureApplicationService.ts:10` 的 `readAudioCaptureSession()` 只读渲染层的 `session` 单例。界面重载后，这个会话要等标题栏指示每 5 秒问一次 `active()` 才会建立（result-录音 第一节第 3 条）；在那之前读到的是 `phase: 'idle'`，可后台其实还在录。
- 读不到的事实：录到哪份作品（placement.projectId）、中断原因（会话里有 error）、待恢复文件（`pendingFiles`）、健康计数（溢出、丢帧、写盘峰值）。
- 建议修法：`recording` 属性改为先问主进程 `active()`（重载后也是真实状态），再合并会话里的 placement、error、notice；另加只读 `pending_files`（文件名、时长、所属作品）。属性在 `audioCaptureFields.ts` 里登记，并同步 `audioCaptureDomain.ts` 的 schemaDocuments。
- 工作量：小，半天。
- 涉及文件：`src/features/application-control/audioCaptureFields.ts`、`audioCaptureDomain.ts`、`src/features/audioCapture/captureApplicationService.ts`；**平台接口 `src/platform/contracts/audioCapture.ts` 正被别人改**。

**A3 音频编辑的算法操作助手没法单步撤销**
- 证据：`audioEditApplicationCapabilities.ts:50` 只有 `insert_audio_edit_file`、`repair_audio_edit_region` 标了 `supportsUndo`；没有 `undo_audio_edit` 这类能力（剪辑有 `undo_video_edit`，画布有 `undo_canvas_change`）。`undo_application_changes` 只认 `change_application_entities` 返回的 undoRef。`audioEditStoreLedger.ts:32` 把界面的 `undo`/`redo` 记成“绑定到全部可写属性”，账面上算覆盖了，实际上助手撤不掉 `quick_process_audio_edit`、`clean_audio_edit_retakes`、`process_audio_edit_breaths`、`compress_audio_edit_silence`、`clean_audio_edit_fillers`、`format_audio_edit_subtitles`、`detect_audio_edit_mouth_clicks`、`match_audio_edit_loudness` 这一步。可这些能力的描述和回执都写着“一步撤销”“可整批撤销”。
- 影响：助手跑完快速处理发现不对，只能用 `reset_audio_edit` 整份还原（连用户手改的也一起没了），或者逐条手写回去。
- 建议修法：照 `undo_video_edit` / `redo_video_edit` 补 `undo_audio_edit` / `redo_audio_edit`（documentRef），复用音频编辑现有的 500 步历史；账本里的 `undo`/`redo` 改为绑定这两个能力。另一个办法是让这些能力回执带 undoRef，改动面更大，不推荐。
- 工作量：小到中，半天到 1 天。
- 涉及文件：`src/core/application-control/domains/audioEdit/audioEditApplicationCapabilities.ts`、`src/features/audioEdit/application/registerAudioEditCapabilityHandlers.ts`、`audioEditStoreLedger.ts`。这几个文件目前没人在改。

### B. 能做，但读不回，或说明会让它用错

**B1 待确认线索读不到关键字段，技能和回执却让助手按这些字段筛**（重要，正卡在“助手二次优化”这一步）
- 证据：`src/features/audioEdit/application/audioEditFields.ts:124-135`，`audio_edit.suggestion` 只登记了 document_id、title、detail、current_state、status 五项。数据里明明有的 `kind`、`confidence`、`startFrame`、`endFrame`、`blockIds`（`src/core/audioEdit/types.ts:59`）都没登记。
- 会让它用错的地方：
  - `registerAudioEditCapabilityHandlers.ts:26` 的回执写“读 audio_edit.suggestion（kind=retake、status=pending）……把对应词块 included 设为 false”，可 kind 和词块都读不到。
  - `clean_audio_edit_retakes` 的描述同上。
  - `audio-edit-workbench/SKILL.md:17,23` 写“kind=retake 带置信度与接缝说明”。
  - 结果是助手按 `where kind=retake` 筛会报属性不存在，或者只能对着截断的标题去全文里找位置。
  - `设计-口播粗剪算法.md` 8.1 节把“词块、起止帧”记为“有，不用补”，这个前提也不成立。
- 建议修法：在 `audioEditFields.ts` 给 suggestion 加只读属性 `kind`（枚举）、`confidence`（枚举）、`start_frame`、`end_frame`、`sample_rate`、`block_ids`。都是通用读，不加工具。设计文档 8.1 要加的 removed_text、options、reason、audience 等可以一起补；先把已有字段登记上，二次优化就能开工。
- 工作量：小，2–3 小时（字段加结果测试）。
- 涉及文件：`src/features/audioEdit/application/audioEditFields.ts`（没人在改）；**`src/core/audioEdit/retakes.ts`、`retakeSelfCheck.ts` 正被别人改**（线索的生成方，加 8.1 的新字段时要和那边协调）。

**B2 转写的说明不足以让助手用对**
- 证据：`audioEditApplicationCapabilities.ts:43`，描述只有“可能计费；参考稿仅辅助内容对齐”。
- 缺的内容：
  - 会一直等到转写完（timeout 10 分钟；写操作超时后只是不再等，转写本身不取消，见 `applicationHostBridge.ts:238-249`），超时后用 `query_audio_edit_tasks` 查。
  - 长录音要选能处理长音频的模型。
  - `modelId` 从哪取：`transcription.default_model` 设置项有可选模型清单（`generalSettingDefinitions.ts:46`），但它的说明只写了“录制讲解使用”，口播转写是否也用这个默认值，我没核实。
  - 已有转写不会再识别（skill 里写了，能力描述没写）。
- 两条文案会误导助手：
  - `electron/main/services/audio-edit/task-store.ts:177`：中断任务的 errorMessage 是“上次处理已中断。转写不会自动重新提交。”，而实际上只要回执是未计费，就可以重新调 `transcribe_audio_edit`。
  - `src/core/audioEdit/asrCatalog.ts:77`：超上传上限的提示只说“请在设置里换用百炼 Fun-ASR”，没给模型 ID，也没说可以直接传 `modelId`。
- `query_audio_edit_tasks` 的输出里没有“能不能重新提交 / 是否已计费”，只能从错误文字猜（`asr.ts:21,39,118` 三种拒绝各一句话）。
- 建议修法：补能力描述和 `modelId` 的 describe；中断文案改成“上次转写中断，没有计费，可以重新转写”（已计费或结果未知的另写一句）；任务输出加 `resubmittable`、`billing` 两个可选字段，从 `timestampedAsrNeverSubmitted` 派生。
- 工作量：小，半天。
- 涉及文件：`audioEditApplicationCapabilities.ts`、`electron/main/services/audio-edit/task-store.ts`、`asr.ts`、`src/core/audioEdit/asrCatalog.ts`（这几个已由 7dd36054f 提交，目前没人在改）。

**B3 录屏省略参数时的默认值跟用户习惯不一致，读回也缺长录关键事实**
- 证据：`recordingCapabilities.ts:19-22`，宽高默认 1920×1080、帧率默认 30、tracks 默认 `{ systemAudio: false }`。处理器（`screenRecording/application/applicationDomain.ts:106`）只有编码参数取自 `loadRecordingSetup()`，分辨率和帧率用的是输入值。用户平时录 4K60，助手省略这几个参数就会录成 1080P30、没有声音。说明里也没写这些默认值，助手读不到用户保存的录制设置（10-23 台账记过“录屏视频设置尚无独立属性注册”）。
- 读不回的事实：`recordingReflection.ts:61-65` 的 details 没填 schema 里已经有的 `warnings`、`error`。中断原因、`missing-data` 空档、丢帧和重复帧、编码续录次数、拼好的声音条数（result-录屏 第七节的 `recording.capture.summary`）只进了日志，助手只能猜。
- 建议修法：省略宽高、帧率、tracks 时取用户保存的录制设置；描述写明默认值，并写明“音频编辑正在录音时不要开麦克风”。另加只读实体 `screen_recording.setup`（分辨率、帧率、画质、编码、默认设备），用通用属性读写。details 里填 warnings、error 和收尾汇总的关键计数。
- 工作量：中，约 1 天。
- 涉及文件：`src/core/application-control/domains/screenRecording/recordingCapabilities.ts`、`src/features/screenRecording/application/recordingReflection.ts`、`applicationDomain.ts`（这几个没人在改）；汇总数据来自 **`electron/main/services/screen-recording/capture/service.ts`（正被别人改）**，要等它提交。

**B4 `render_cache.rendering.paused` 在数据里有，schema 和说明里没有**
- 证据：`videoEditRenderCache.ts:200,429` 返回 `paused`（例如“正在录屏，录完后继续渲染”），可 `videoEditFields.ts:156` 的 schema 是 `rendering: { done, total, auto }.strict()`，属性说明也没提。读回时会不会因为 strict 校验失败，我没核实（registry 只对写入做形状校验，读路径看起来不校验）。
- 自动预渲染不跑的原因（窗口隐藏、系统有输入、有占显卡的任务，result-W6-B 第 4、6 条）只进了日志，助手读不到；对正式使用影响小。
- 建议：schema 和说明补上 `paused`。小，1 小时。
- 涉及文件：`src/features/videoEdit/application/videoEditFields.ts`。

**B5 录屏的 stop、import、recover 只等 60 秒**（拿不准，需要实测）
- `recordingCapabilities.ts:29` 对所有录屏操作统一用 `timeoutMs: 60000`。两小时的录制停止时要拼两路长 WAV、补齐分片，如果开始时指定了剪辑目标还要导入，可能超过 60 秒。写操作超时后不会取消，但助手会收到“读取已取消或等待超时，请重新查询”，容易以为失败了再停一次。
- 建议：stop、recover、import 改成按长任务处理（加长 timeout，或返回 submitted 再读 phase），并在描述里写“超时后读 session 的 phase”。
- 工作量：小；先在长录测试（待办 4r）里看实际耗时再定。

### C. 说明过时

## 三、助手驱动的整链路走查脚本（草案）

前提：先 `electron:bundle`，用 `electron:prod` 和真实资料目录；或用隔离资料目录加真实麦克风。A1 修好之前，第 2 步只能人工点开始和停止，其余由助手做。外部 MCP 写入都带 operationId。

| # | 做什么（能力，按顺序） | 读回什么来判定成功 | 付费 |
|---|---|---|---|
| 0 | `get_current_application_context`；用 `list_application_entities` 列 `screen_recording.source`，读 `audio_capture.settings`（devices、effective） | 拿到目标窗口的 sourceRef；录音设备可用、notice 为空 | 否 |
| 1a | `start_screen_recording`：sourceRef，宽高 3840×2160，fps 60，`tracks.systemAudio=true`，**不开麦克风**（避开第 2 步的独占录音），给 projectId，destination 可先省略 | 返回 sessionRef；隔几秒读 `screen_recording.session.phase=recording`、elapsed_ms 在涨 | 否 |
| 1b | 录制中：`mark_screen_recording` 打标记；`read_screen_recording_events(markersOnly)` | 标记条数对得上；事件数在涨 | 否 |
| 1c | （压力项）录制中重载界面，再读 session | phase 仍为 recording，elapsed_ms 连续 | 否 |
| 1d | `stop_screen_recording` | phase=stopped；details.media 里有画面分片和拼好的声音（`*-joined-*.wav`）；超时就再读 phase，不要重发 stop | 否 |
| 2a | 音频编辑录音：A1 之前由人点开始；A1 之后用 `start_audio_edit_recording`（不给 documentRef，新建草稿） | 读 `audio_capture.settings.recording`：phase=recording、durationSeconds 在涨（修好 A2 后还能读到所属作品） | 否 |
| 2b | 录音中切工作区、重载界面，再读 recording | 修好 A2 后：phase 仍为 recording、时长连续；现在重载后最多约 5 秒会读到 idle，属已知缺口 | 否 |

| 5a | 读待确认线索：`list_application_entities` 列 `audio_edit.suggestion`，按 document_id 和 status=pending 筛（B1 修好后再加 kind=retake，并读 block_ids 与起止帧） | 数量与第 4 步回执一致 | 否 |
| 5b | 逐条裁决：写 `transcript_block.included` 或 `audio_edit.cut`，再把线索 status 写成 applied 或 dismissed | 每次 `change_application_entities` 都 verified；`current_state` 变成 removed 或 dismissed | 否 |
| 5c | 再跑一次 `clean_audio_edit_retakes` 做自检 | 待确认数下降或归零 | 否 |
