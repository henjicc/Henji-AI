## 结论（一页）

**推荐：现在不换工具，在 FFmpeg 命令行上做两处小改（路线 A）；“Rust 采集进程内嵌 libav”（路线 B）作为开工后的独立工程，先做 macOS。** 没有哪个开源录屏核心能直接拿来当库或独立进程用（路线 C）。

理由：

1. **继续时 1.6 秒没画面、暂停一次多一个文件，在命令行里就能消掉。** FFmpeg 命令行运行中可以从 stdin 收 `c` 命令，转给滤镜（`ffmpeg.c` 的 `check_keyboard_interaction`）；`setpts` 的 `expr` 是运行时参数（`setpts.c` 的 `process_command`，选项带 `AV_OPT_FLAG_RUNTIME_PARAM`），表达式里有 `T_CHANGE`（命令生效后第一帧的时刻）。暂停时把时间戳改成远在过去的值，CFR 同步会把这些帧丢掉（`video_sync_process` 中 `delta < -1.1` 时 `nb_frames = 0`）；继续时改回 `PTS - 偏移`，偏移在命令生效的那一帧算出来。这样进程不停、文件不换、继续即时有画面，编码器全程不重建。我们打包的构建还带 `zmq` 滤镜（`--enable-libzmq`），可以作为 stdin 之外的备用控制通道。要先做 1 天的验证（见“最小的一步”）。
2. **磁盘多一份，根子不在 FFmpeg 命令行，而在录制文档的模型上。** 现在的模型是“一片 = 一个文件 = 会话时钟上连续的一段”，理解、打码、导演、成片等十来处读取方都按这个假设读原分片（见 `result-录屏合成一个视频.md` 风险第一条）。不管画面由谁录，只要“一次录制一个文件、文件里跳过了暂停”，分片就得能表达“在文件里从第几秒起”。所以 A、B 都要先过这一关：分片加文件内偏移，读取方统一走一个换算入口，持久格式升版。
3. **路线 B 的真正收益是另外三样，不是暂停：** 每帧精确的系统时刻（WGC `SystemRelativeTime`，与事件同一个 QPC 时钟，现在只能按 `now − out_time` 估第一帧）；收尾与崩溃由我们自己的进程掌控（不再发 `q`、超时强杀）；macOS 能做到无光标原生采集（现在 macOS 只有 Chromium 兼容路径，光标总是烧进画面，靠光标的自动推近和重绘光标在 macOS 上都受限）。这些都值得做，但不急，也不该和今天刚验收通过的 Windows 链路同时动。
4. **路线 C 没有现成核心可直接用。** Cap 的录制管线（AGPLv3）和它自己的工程格式、actor 框架绑得很紧；它的 Studio 模式在暂停时也是停管线、另起一段（`studio_recording.rs` 的 `Pause` 调 `stop_pipeline`），和我们现在一样。能单独借的只有 MIT 的 `scap-direct3d`、`scap-screencapturekit`，但它们没发到 crates.io，依赖 Cap 的 `cap-timestamp`（AGPL）和 workspace-hack。OBS 的结论不变。
5. **路线 D 只适合当兼容回退。** 它依赖界面进程（界面重载就录不下去，`service.ts` 的 `ownerLost`），光标按现有实现总是烧进画面，时间戳要经 IPC 往返校准。

**时机**：A 的两步现在做（不换工具，改动集中在 `gfxcapture.ts`、采集清单与读取方）；B 等主链路稳定后作为独立工程立项，macOS 先行，Windows 视 A 的验证结果与精度需求再定。

**最小的一步**：先花约 1 天做命令行验证，只改实验用的命令、不进代码库：`gfxcapture=…,setpts@p=PTS` 接现有编码参数，录制中经 stdin 发 `c setpts@p -1 expr <丢帧表达式>` 与 `c setpts@p -1 expr PTS-(T_CHANGE-<已出帧数>/60)/TB`，检查四件事：命令能否送达只有源的滤镜图、暂停期间是否一帧不漏、继续后的帧距是否恒定、NVENC/QSV/AMF 是否都不报错。通过后按这个顺序做：
1. 采集清单的分片加“文件内起点”（新增字段，含义变化，按 persistence.md 升版并写迁移），读取方统一走一个换算入口。
2. `gfxcapture.ts` 的暂停与继续改成发命令、不结束进程，同一个文件里记多个逻辑分片。只有暂停、没有编码器重启的录制不再需要合并，直接导入，磁盘不多占，继续时没有空档。
3. 编码器中途重启的少数情况仍按现在的合并做。合并成功后可以把分片改指合并文件、删掉原分片（第 1 步做完后这一步就安全了）。

## 现状（读代码确认）

- **输入**：FFmpeg 的 `gfxcapture` 源滤镜（Windows.Graphics.Capture），`hwnd=` 或 `hmonitor=` 由 `source.ts` 用 PowerShell 调 `MonitorFromPoint` 取得。参数带 `capture_cursor=0|1`、`capture_border=1`、`max_framerate`、`width/height`、`resize_mode=scale_aspect`，区域用 `crop_*`。输出 `AV_PIX_FMT_D3D11` 纹理，硬件编码时直接进编码器；软件编码时 `hwdownload,format=bgra,format=yuv420p`。
- **编码器**（`hwaccel.ts` 的 `recordingEncoderProfile`）：`h264/hevc_nvenc`（p4、ll、vbr/cbr、`-cq 26`、lookahead 4 补关键帧）、`_qsv`（veryfast）、`_amf`（speed）、`_videotoolbox`（只在 Chromium 以外的路径上会用到，但 macOS 现在不走 gfxcapture），软件 `libx264/libx265 superfast zerolatency`。`-bf 0`，GOP 30 帧，`-r fps -fps_mode cfr`。
- **封装**：`-movflags +frag_keyframe+empty_moov+default_base_moof -flush_packets 1`，每个关键帧一个分片。
- **进程**：`process.ts` 用一个固定的 Node 监督进程（`ELECTRON_RUN_AS_NODE`）包住 FFmpeg，父进程 stdin EOF 时转发 `q`，3 秒后强杀；`gfxcapture.ts` 的 `end()` 发 `q`，5 秒后 `taskkill /T /F`。
- **暂停与继续**：`pause()` 即 `end(true)` 结束进程并按 `-progress` 的时长封口；`resume()` 即 `start()`，重新开进程、`openSpan` 开新文件 `screen-00000N.mp4`。
- **每帧时刻**：FFmpeg 的 `gfxcapture` 把 `SystemRelativeTime`（QPC，100 ns）作为 PTS，但在 `output_frame` 里减掉第一帧（`frame->pts -= ctx->first_pts`），绝对时刻没有输出。我们只能按 `-progress` 每 0.25 秒报的 `out_time_us`，取 `now − out_time` 的最小值估第一帧的会话时刻（`span.monoUs`）。之后各帧按 CFR 线性推算。
- **兼容路径**（`chromium.ts`）：`getDisplayMedia` → `MediaStreamTrackProcessor` → WebCodecs（mediabunny）→ 分片 MP4 → IPC 写盘，每块 `datasync`。暂停同样是封口加新片。光标总是烧进画面（`service.ts` 中 `cursorEmbedded: backend === 'chromium' || …`）。macOS 只能走这条。
- **可复用的家底**：`native/video-decoder` 已经是一个链接 FFmpeg 9.0 共享库（`ffmpeg-sys-next =9.0.0`）、自建 D3D11VA 设备（`platform/windows/d3d11va.rs`）的 Rust 常驻进程，`windows =0.62.2`。打包的运行时目录里已有 `avfilter-12.dll`。

## 路线 A：保持 FFmpeg 命令行，只改用法

### A1. 运行中控制：哪些办法可行

| 办法 | 源码依据 | 结论 |
|---|---|---|
| stdin `c`/`C` 命令 | `ffmpeg.c` 的 `check_keyboard_interaction`：读到 `c` 后读一整行 `<目标> <时间> <命令> <参数>`，交给 `fg_send_command`。Windows 下 stdin 是管道时走 `PeekNamedPipe`（`read_key`），我们经监督进程转发的匿名管道正属于这种。命令经调度器的控制队列送进滤镜线程（`sch_filter_command` → `send_to_filter(…, nb_inputs, …)`）。只有源、没有输入的滤镜图，每轮会非阻塞地取一次控制队列（`sch_filter_receive` 中 `*in_idx == fg->nb_inputs` 分支），所以 gfxcapture 这种图也能收到。 | **可行**，需实测。延迟：按键每 100 ms 才查一次（`cur_time - last_time >= 100000`），命令行其余部分随即读完。 |
| `zmq` 滤镜 | 打包构建 `--enable-libzmq`，`-filters` 列出 `zmq V->V`。每帧收一次消息，延迟不超过一帧。 | **可行，作备用**。主进程要说 ZMTP（加 `zeromq` 原生模块，或手写一个很小的 REQ 客户端）。 |
| `sendcmd` | 只能按预先写好的时间表发命令，不能临时触发。 | 不适用。 |
| `select` 运行时改表达式 | `f_select.c` 的选项不带运行时标志，也没有 `process_command`。 | **不行**。 |
| `gfxcapture` 自身暂停 | `vsrc_gfxcapture.c` 的选项表没有运行时参数，滤镜没有 `process_command`。 | **不行**。 |
| `setpts` 运行时改表达式 | `setpts.c`：`expr` 带 `R`（运行时）标志，`process_command` 解析新表达式并把 `T_CHANGE` 置为 NaN，下一帧填成该帧时刻。可用变量有 `PTS`、`T`、`TB`、`N`、`PREV_OUTPTS`、`T_CHANGE`、`RTCTIME` 等。 | **可行，是关键**。 |

### A2. 用 `setpts` 在同一进程里暂停（推荐的小改）

滤镜链：`gfxcapture=…,setpts@p=PTS`，其余参数不变（`setpts` 是只改元数据的滤镜，`AVFILTER_FLAG_METADATA_ONLY`，D3D11 帧直接透过）。

- **暂停**：`c setpts@p -1 expr -1e18`。读 `video_sync_process`：CFR 模式下 `delta = sync_ipts - next_pts + duration`，远小于 −1.1 时 `nb_frames = 0`，帧被丢掉，丢帧计数照常累计（`-progress` 的 `drop_frames` 会涨，统计时要扣掉暂停期间的部分）。
  - 不能用“时间戳冻结在上一帧”（`PREV_OUTPTS`）。按同一段代码推算，CFR 下同时间戳的帧前一两帧会被当成正常帧顺延输出，暂停时会漏出画面。
- **继续**：`c setpts@p -1 expr PTS-(T_CHANGE-<已输出时长>)/TB`。“已输出时长”取暂停期间 `-progress` 已稳定的 `frame=` 计数除以帧率（暂停期间计数不再变，等两次报告相同再允许继续，或在继续时取最后一次的值；暂停短于 0.25 秒时要等下一次报告）。命令生效的那一帧正好接在上一帧之后，CFR 同步把不到 0.6 帧的误差截掉（`delta0 < 0 && delta > 0` 的裁剪分支）。
- **结果**：一个进程、一个文件，暂停期间不写盘、不编码，继续即时有画面（只差命令送达的 ≤100 ms，或用 zmq 时 ≤1 帧）。WGC 和编码器全程不重建。
- **与事件时钟对齐**：文件里的时间 = 会话时间扣掉暂停，正是 `recordingUs` 的定义，所以剪辑侧“一个素材、一个 `recordingStartUs`”的模型（合并文件现在就是这样导入的）原样适用。真实剪掉的长度可以用两个独立量核对：“继续时刻 − 暂停时刻”，以及继续后 `now − out_time` 最小值的跳变量。两者相差就是命令送达的延迟，可以据此把事件时钟的暂停区间对齐到画面（`alignRecordingPauses` 的思路不变，容差会小很多）。
- **精度**：与现在一样，由 `now − out_time` 的估计决定，没有逐帧绝对时刻。现有 250 ms 容差是估算值，实际误差未实测。
- **崩溃后可读**：与现在相同。分片 MP4 每个关键帧一个分片，崩溃最多丢最后一片（约 0.5 秒）。叠加 `hybrid_fragmented` 的建议（见对照 OBS 第 4 项）照样成立。
- **工作量**：验证 1 天；实现 3–4 天（`gfxcapture.ts` 的暂停/继续分支与边界计算、清单里同一文件的多个逻辑分片、恢复与统计）；加上分片模型改造（见下）。
- **风险**：中。`c` 命令是官方的交互功能，但很少被程序化使用。命令行解析用 `%255[^\n]` 读参数，表达式要控制在 255 字节以内。命令回执打在 stderr（`Command reply for stream …`），需要解析以确认生效。QSV、AMF 下编码器对时间戳跳变的反应未实测。

### A3. 分片、HLS、追加写、concat 协议

- `-f segment` / `hls -hls_segment_type fmp4`：只是把一个进程的输出切成多个文件，帮不了暂停，文件反而更多。`hls_flags append_list` 能让新进程续写同一个播放列表，但剪辑与读取方都不吃 m3u8。**不采用。**
- `concat:` 协议只用于读，把字节首尾相接；两个分片 MP4 接起来会有两个 moov，不是合法文件。**不适用于写。**
- **“新进程追加到同一个分片 MP4”**：mp4 封装器有 `fragment_index`、`frag_discont`、`skip_trailer`（`-h muxer=mp4` 可见），加上 `-output_ts_offset`，可以让第二个进程输出到管道。主进程丢掉它的 `ftyp/moov`，只把 `moof/mdat` 追加到第一个文件尾部。这样不复制就能保持单文件，前提是两次的编码参数与 extradata 一致。它解决不了 1.6 秒空档，只适合编码器意外重启后续录这种少见情况，而且和 `hybrid_fragmented`（结束时改写成普通 MP4）互相冲突。**优先级低，暂不做。**
- **“拼完直接用拼好的文件、删掉分片”**：最省事的做法是采集清单的分片加 `fileStartUs`（在文件里从哪一刻开始；省略为 0），合并成功并核对时长后，把各分片改指合并文件、填好起点，再删原分片。前提是所有读取方都经同一个“会话时刻 → (文件, 文件内时刻)”换算入口；`src/core/screenRecording/combine.ts` 里已有合并文件与会话时钟的换算，可以收口到这里。这改变了分片的已有含义，按 persistence.md 要升最低可读版本，写迁移和黄金样本。A2 也要用这个模型（同一文件里的多个逻辑分片），所以**这一步是 A2 的前置，也是 B 的前置**。工作量 3–5 天，主要花在逐个读取方的核对上。

## 路线 B：自己的 Rust 采集进程 + FFmpeg 库（或平台编码器）

### B1. Windows 采集的三种拿法

| 拿法 | 依据 | 每帧时刻 | 光标 / 边框 | 维护与许可 |
|---|---|---|---|---|
| **进程内调用 libavfilter 的 `gfxcapture`** | 滤镜带 `AVFILTER_FLAG_HWDEVICE`；没给设备时自建 D3D11VA 设备（`ff_gfxcapture_init` 中 `av_hwdevice_ctx_create(…D3D11VA…)`），也可以传入我们自己的设备（`Using provided hw_device_ctx`）。我们已打包 `avfilter-12.dll`，`video-decoder` 已有 D3D11VA 设备代码。 | 只有相对第一帧的 PTS（同样减了 `first_pts`）。但在进程内可以在 buffersink 取帧时读 QPC，取 `qpc_now − pts` 的最小值，误差约等于“合成到取帧”的延迟（推测 1–3 ms，未实测），比现在经编码、管道和 0.25 秒报告周期的估计准得多。 | 与现在完全相同（同一份代码，参数原样传）。 | GPL（随 FFmpeg），与现有构建一致。WGC 行为与今天验收的完全一样，**风险最小**。 |
| **`windows-capture` crate** | 2.0.1（2026-08-08），MIT，累计下载约 275 万；依赖 `windows 0.62.2`，与我们锁定的版本相同。`Frame::timestamp()` 直接返回 `SystemRelativeTime`；`as_raw_texture()` 给 `ID3D11Texture2D`；`CursorCaptureSettings::WithoutCursor`、`DrawBorderSettings`、`MinimumUpdateIntervalSettings`、`DirtyRegionSettings`。它自带的编码器走 WinRT `MediaTranscoder`（`SetHardwareAccelerationEnabled(true)`），只能输出普通 MP4、参数控制少、不能分片，**只用它的采集，不用它的编码器**。 | **逐帧精确 QPC**，与 `hrtime` 同一个时钟。 | 可选。 | MIT，活跃。 |
| Cap 的 `scap-direct3d` | MIT（`LICENSE`：`scap-*` 系列为 MIT）；逐帧取 `SystemRelativeTime` 包成 `PerformanceCounterTimestamp`，可设光标与边框。 | 精确。 | 可选。 | **没发到 crates.io**，依赖 `cap-timestamp`（不在 MIT 系列，按 AGPL）、`cap-d3d-adapter` 和 workspace-hack，需要摘出来自己维护。 |
| `scap`（helmerapp） | 0.0.8，最后更新 2025-08。 | — | — | 版本早、更新慢，**不选**。 |
| `crabgrab` | 0.4.0，最后更新 2024-06，近期下载 561。 | — | — | 基本停更，**不选**。 |
| `xcap` | Apache-2.0，活跃，但以截图为主，视频录制是实验功能。 | — | — | **不选**。 |

### B2. 编码与封装

- **D3D11 纹理直送硬件编码器（零拷贝）是可行的**，FFmpeg 命令行今天就是这么做的：`gfxcapture` 输出 `AV_PIX_FMT_D3D11` 帧，直接进 `h264_nvenc`、`h264_amf`。在进程内用 `ffmpeg-sys-next 9.0`（或 `ffmpeg-next 9.1` 安全封装；WTFPL）建 `hw_frames_ctx`，与解码服务的 D3D11VA 写法相同。
  - QSV 通常要 NV12，可能需要 `hwmap=derive_device=qsv` 或 D3D11 视频处理器转格式。现在的命令行路径在 QSV 上具体怎么协商的，未核实。
  - 用 `windows-capture` 时，它的纹理来自它自己的设备，要么让编码器用同一个设备，要么跨设备共享纹理（解码服务已有 NT 句柄共享纹理的代码）。
- **Cap 的做法作参照**：Windows 上用 WGC 纹理 → Media Foundation 硬件 H.264 MFT（`cap_enc_mediafoundation::H264Encoder::new_with_scaled_output`，`video_processor.rs` 做缩放与转格式）→ 用 FFmpeg 封装成分片 MP4（`cap_mediafoundation_ffmpeg::set_fragmented_mp4_options`），失败时回退 libx264（`win.rs`）。它不用 NVENC 专有接口，靠 MF 覆盖三家显卡。这部分 crate 是 AGPL。
- **暂停**：停止送帧，继续时从时间戳里减掉累计暂停，天然单文件。这与 Cap Instant 模式的 `SharedPauseState::adjust`（`core.rs`）、OBS 的 `pause.ts_offset`、Aperture 的 `timeOffset` 是同一种做法。
- **停止与崩溃**：`av_write_trailer` 由我们自己的停止命令触发，不需要 `q` 和强杀；崩溃时分片 MP4 最多丢最后一片，`hybrid_fragmented` 由封装选项开启。编码器出错（驱动重置）时，可以在进程内只重建编码器、采集不停。若改用 `avc3`/`hev1` 采样项（参数集放在码流里），重建后还能接着写同一个文件；这一点未实测。
- **4K60 性能**：采集和编码路径与现在相同（GPU 纹理到 GPU 编码），省掉了 FFmpeg 命令行的滤镜线程和管道，CPU 只会更低。需要按现有长录方法实测。

### B3. macOS

- 现在 macOS 只有 Chromium 兼容路径，光标烧进画面。
- 原生做法：ScreenCaptureKit（`SCStreamConfiguration.showsCursor = false`，可以按显示器、窗口、应用过滤，`sourceRect` 取区域）→ VideoToolbox 或 `AVAssetWriter`（设 `movieFragmentInterval` 后崩溃可恢复）。
- Rust 绑定：`screencapturekit` 11.1.2（MIT/Apache，2026-11-02，下载约 345 万）、`objc2-screen-capture-kit`（Zlib/Apache/MIT）。
- 参照实现：Aperture（MIT，Swift，`Aperture.swift`：`SCStream` + `AVAssetWriter`，`pause()` 置标志、`timeOffset` 扣暂停，单文件）；Cap 的 `scap-screencapturekit`（MIT）与 `enc-avfoundation`（AGPL）。
- 时刻：`CMSampleBuffer` 的 PTS 用主机时钟（`mach_absolute_time`），libuv 在 macOS 上的 `hrtime` 用的也是它，可以直接对齐（由文档推断，未实测）。
- macOS 上我们没有 FFmpeg 共享库（`ffmpeg-loader.ts` 在非 Windows 平台不定位 FFmpeg 构建目录，命令行来自 `ffmpeg-ffprobe-static`），所以 macOS 应该直接用 `AVAssetWriter`，不引入 libav。和 Windows 共用的只有进程协议、清单与恢复模型，采集和编码各写一套。

### B4. 工作量与风险

- **Windows**（进程内 gfxcapture 或 windows-capture，加 libav 编码与封装，加进程协议、恢复与统计，加打包）：10–15 人天。最大的风险是原生进程里的 GPU 资源生命周期（设备丢失、显示器热插拔、窗口关闭），以及 QSV/AMF 的格式协商。
- **macOS**（ScreenCaptureKit + AVAssetWriter，加权限流程）：10–15 人天，风险在权限与多显示器缩放。
- **对现有实现的冲击**：大。要替换 `gfxcapture.ts` 与 `process.ts`，`service.ts` 的后端选择、恢复、统计、编码回退和续录逻辑都要重接，今天的长录、强杀、界面重载验收要全部重跑。分片模型改造（A3 最后一条）是前置。

## 路线 C：现成的开源录屏核心

| 项目 | 采集与编码 | 暂停 | 能否当库或独立进程直接集成 | 许可 |
|---|---|---|---|---|
| **Cap**（2.5 万星，今天仍在提交） | Windows：WGC（`scap-direct3d`）→ MF 硬件 H.264 → FFmpeg 封装分片 MP4，可回退 libx264；macOS：ScreenCaptureKit → AVFoundation。封装可放独立进程（`cap-muxer`）。 | **Studio 模式每次暂停停管线、另起一段**（`studio_recording.rs` 的 `Pause` → `stop_pipeline`，`next_index: index + 1`），由编辑器按多段处理，和我们现在一样；**Instant 模式**用 `SharedPauseState` 扣暂停，单文件。 | **不能直接用。** `cap-recording` 依赖 Cap 自己 fork 的 `ffmpeg-next`、`cpal`、`cidre`（git rev），用 kameo actor 组织，产出 Cap 自己的工程格式；只用库要大量剥离。 | `scap-*`、`cap-camera*` 为 MIT，其余 AGPLv3（`LICENSE`）。 |

## 路线 D：Electron / Chromium 自带采集

- **现状**：`getDisplayMedia({ video: { frameRate } })` → `MediaStreamTrackProcessor`（`maxBufferSize: 1`）→ WebCodecs 硬件或软件编码（mediabunny，`latencyMode: 'realtime'`）→ 分片 MP4，经 IPC 每块写盘并 `datasync`。
- **局限**：
  - 依赖界面进程，界面重载或崩溃就按失败收尾（`ownerLost`）。
  - 光标：我们的实现按“总是烧进画面”处理。Chromium 对 `cursor: 'never'` 的支持历史上不完整，现状未核实（参考 [W3C 讨论](https://lists.w3.org/Archives/Public/public-webrtc-logs/2019Apr/0012.html)、[WebRTC 提交](https://webrtc.googlesource.com/src/+/3f2a3b19e3de1531fed98a6d8295f89a79f6d969)、[Openscreen PR](https://github.com/getopenscreen/openscreen/pull/157)、[MDN cursor](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackSettings/cursor)）。
  - 时间戳：`VideoFrame.timestamp` 经 `CaptureFrameClock` 用一次 IPC 往返校准到主进程时钟，误差是往返时间的一半。
  - 4K60：有缩放或裁剪时每帧走 `OffscreenCanvas.drawImage`，有额外拷贝；实际能稳定到多少帧未实测。Windows 上 Chromium 现在默认用 WGC 采屏（[Windows Latest](https://windowslatest.com/2025/04/19/microsoft-fixes-chromes-washed-out-dull-hdr-colours-on-windows-11-24h2)）。
- **暂停**：可以很便宜地改成单文件。暂停时不 `finalize` mux，继续时把累计暂停从 `time` 里扣掉，约 0.5–1 天。macOS 在路线 B 之前只有这条路，这个小改值得顺手做。
- **定位**：保留为兼容回退与 macOS 的过渡方案，不作为主路径。

- 命令行路径在 QSV 上，D3D11 BGRA 帧怎样协商成编码器需要的格式：未核实。进程内实现要先确认这一点。
- 用 `avc3`/`hev1` 让编码器重建后接着写同一个文件：未实测。
- 进程内取帧时读 QPC 能把首帧估计误差压到多小（文中 1–3 ms 是推测）。
- Chromium 现在对 `cursor: 'never'` 的支持程度：查了 W3C、WebRTC、MDN 与一个 Electron 项目的 PR，没有找到确定结论。
- 屏幕录制文档的读取方确切有多少处要改：只引用了结果文档的“十来处”。按 `.spans` 和 `.monoUs` 粗搜命中的文件较多，大多与录屏无关，没有逐个核对。
- screenpipe 与 Screenity 的许可和采集细节：没有细查，它们不是录屏核心。
