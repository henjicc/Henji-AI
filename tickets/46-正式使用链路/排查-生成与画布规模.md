# 排查：生成与画布在极端规模下的表现

**一句话总评**：按现在的用量（历史 18 条、最大画布 15 个节点）完全不会卡；真正先撞墙的不是列表渲染（生成历史已虚拟化、画布内存撤销是结构共享），而是几条“每次都全量重做”的后台路径——启动时每条画布生成记录都整份重读一次画布、每次任务变化都把全部历史缩略图重查一遍、每次保存都把撤销记录展开成 24 份整画布写盘、拖动时各节点选择器全量扫连线。修掉这几条（大多是小改）后，生成上限可到约 1 万条，画布约 2000 个节点；再往上要分页加载历史、画布按视口降级节点内容，属于大改。

用户现有数据（11-13 只读查询 `E:\文档\HenjiAI\.system\henji.db` 与作品目录）：历史 18 条，其中 9 条是画布生成记录（50%）；已完成的生成回执 127 条里 112 条“未交接”（88%）；画布共 4 份，最大一份 15 个节点、57KB。

基准（都不依赖应用，放在 `tickets/46-正式使用链路/证据/规模/`）：
- `history-sqlite-bench.cjs`：照抄 history 表、索引、FTS、结果交接触发器，在系统临时目录建库测查询与写入，跑完删除。运行：`ELECTRON_RUN_AS_NODE=1 node_modules/electron/dist/electron.exe tickets/46-正式使用链路/证据/规模/history-sqlite-bench.cjs 1000 10000 50000`（`UNRELEASED_PCT=88` 模拟用户真实回执比例）。
- `canvas-scale.bench.test.ts` + `vitest.scale.config.ts`：直接调用正式的画布文档换算、zod 校验、位置编解码、xyflow 变更与命中函数。运行：`npx vitest run --config tickets/46-正式使用链路/证据/规模/vitest.scale.config.ts tickets/46-正式使用链路/证据/规模/canvas-scale.bench.test.ts`。
- 本机 Node（Electron 42 内置 Node 24），单线程，数字是量级，不是真机帧率。

### 拿不准、未列为问题

- 历史加载完成时 `replaceGenerationTasks` 对每条任务 `JSON.stringify` 一次并通知一次监听者（`generationTaskProjection.ts:17-35`，`visibleGenerationTaskCommand.ts:97-108`），1 万条就是 1 万次 `bumpScope('generation')`；助手正好在等任务时，`waitForGenerationCompletion.ts:50` 每次通知都会查一次。量级没测。
- 原有问题（不是规模问题）：历史缩略图按文件名生成缓存路径（`historyThumbnail.ts:62-70`），不同目录里同名的图片会共用一张缩略图，显示成别的图。生成结果文件名通常唯一，导入的结果可能撞名。

## 四、已确认没问题的点

- 生成历史列表是虚拟化的（`useVirtualTaskList.ts`，overscan 4），卡片有 memo；进度走独立 store，不重建任务数组（`useTaskState.ts:197-201`）；`setTasks` 用 Set 判断变化，O(n)（`useTaskState.ts:183-190`）。
- SQLite 按 ID 取、计数、少见词全文检索在 5 万条下仍是 0.2ms、3ms、1ms；删 1000 条约 100ms。
- 切换模型与历史规模无关。
- 画布内存撤销是结构共享，取快照约 0ms、还原 <1ms@5000；撤销上限 50 步只做淘汰。
- 拖动每帧的 store 变更与 xyflow 节点同步 1.1ms@5000；框选命中 0.1ms@5000；文档图校验线性。
- 连线组件、主端口连接标记、上游媒体收集都已走按引用缓存的索引（`connectionIndex.ts`、`graphMediaResolver.ts:15-55`）。
- 上一轮已做的不再重复：宿主上下文拖动节流、续查扫描只看 data 变化、微缩略图改主进程生成并落盘、参数行视频缩略图不挂 video、拖动中只在松手时标脏（`canvasProjectInstances.ts:178-186`）。

## 五、真实窗口验证与造数据

**必须真机才能确认的**：生成——启动到历史完整出现的时间（G1、G4 的 IPC 实际单价）、生成期间缩略图重查对主进程的占用（G2）、滚动帧率；画布——几百到几千节点的打开到首帧、平移缩放帧率、拖动跟手、内存与 GPU 进程显存（C5），以及 C3、C4 模拟值在真实组件上的系数。

**数据隔离**：只用隔离资料目录启动。`npm run ui:tour` 默认 `--profile temporary`，会传 `isolateUserData`（`uiInspection.cjs:339-349`），数据写在临时目录、用户的 `E:\文档\HenjiAI` 不受影响；隔离后 userData 不同，单实例锁也不会和正在运行的开发版冲突。**不要直接用** `npm run electron:canvas-stress` 和 `npm run electron:pan-bench`：两者启动时都没开隔离（`electron-phase4-canvas-stress.cjs:38-40`，`electron-canvas-pan-bench.cjs:306`），夹具画布会写进真实作品目录并登记进索引，pan-bench 还要从真实目录读名为 TEST 的画布。真机前先 `npm run electron:bundle`。

**生成历史造数据**：现成场景 `GENERATION_BENCH=1 GENERATION_BENCH_COUNTS=1000,10000 GENERATION_BENCH_IMAGE=<一张真实图片> npm run ui:tour -- --only generation-history-performance`（`uiInspectionGenerationPerformance.cjs`），经 `generationHistory.insertMany` 在隔离库里造记录、重载后测加载与滚动。但它有三处会让结论偏乐观，验证前要先补：
1. 所有记录指向**同一张图**，`historyMediaResolver` 与缩略图重查都按路径去重，实际只发几次 IPC——要改成每条记录一份独立文件（先在隔离目录里复制 N 份小图）。旧证据“1 万条加载 606ms、滚动 p95 16.8ms”就是在这种条件下得到的。
2. params 只有 `{ aspect_ratio }`，真实记录 600–1400 字节，要按真实形状填。
3. 没有画布生成记录，测不到 G1；要先造一份画布，再让一部分记录带 `__canvasGeneration: { projectId, nodeId, version: 2 }` 指向它。规模上限写死 1 万（`:13`），测 5 万要放开。

**画布造数据**：在隔离实例里经 `window.henjiNative.testFixtures.createCanvas({ id, name, nodes, edges, viewport })`（`canvasDocumentFixture.cjs:40-42`）一次写入整份画布；节点与连线按本次基准 `makeGraph` 的比例生成，图片路径指向隔离目录里复制好的真实图片（每个节点一份，避免全部命中同一解码缓存）。档位 500 / 1000 / 2000 / 5000，每档测：打开到首帧（`canvas.document.bind.completed` 的 durationMs 加首个 rAF）；按 pan-bench 的做法连续单向扫掠平移与缩放；框选并拖动 20 个节点 3 秒的长任务与帧间隔；松手后日志里 `documents.save.completed` 的 durationMs、bytes 和会话状态文件大小；渲染进程堆与 GPU 进程内存。素材组场景（C4）另造 20 个素材组各 20 个成员。
