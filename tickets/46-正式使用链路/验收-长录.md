## 五、脚本问题（`scripts/recording-soak.cjs` 等，均已修）

1. **光标对齐抽查只在主屏移动光标**：`os.moveCursor` 固定在主屏 40%/60% 处移动，录制只记被录区域内的光标（`src/core/captureLog/coordinates.ts` 的 `capturePoint` 区域外返回 null），录副屏时这项必然失败。改成在被录显示器里移动，按虚拟桌面归一化（`MOUSEEVENTF_VIRTUALDESK`）。修好后 8 次抽查全部对上。
2. **运动源摆错位置并盖住主屏**：ffplay（SDL）感知 DPI，`-left/-top/-x/-y` 是物理像素，脚本按 DIP 给。在 150% 缩放下，窗口落在物理 x=2560–5120，盖住主屏右三分之一，副屏只露出左上角。原来的“画面在动”检查只看整帧，所以照样判通过。修法：用感知 DPI 的系统查询拿到被录显示器的物理矩形再摆放；画面检查另外要求右下四分之一也在动。修好后抽帧确认铺满。
3. **墙钟起点包含开始调用的耗时**：录音从调用前算起，把约 2.4 秒的开始耗时算成“少录”，3 秒容差会掩盖真实丢失。改为按开始回执的 `durationSeconds`（录屏用首个快照的 `elapsedMs`）推算真正开录的时刻。改完后录音 60 分钟差 0.07 秒，录屏 30 分钟差 0.46 秒。
4. **系统声时长比较口径不对**：系统声比画面早约 1.2 秒开录，停止时又晚收尾，冒烟里差 3.1 秒，只是勉强落在 3.18 秒容差内。改为核对“覆盖整段画面”：起点不晚于画面起点、终点不早于画面起点加录制时长，各留 1 秒；汇总时长允许比录制长 10 秒以内。
5. **没修、只记录**：主进程加压无效。并发全文日志查询让 ping 最长只到 4–18 ms，四场都是如此，所以“主进程卡顿时录制不断”这项实际没测到。需要应用提供只在自动化模式开放的“让主进程忙 N 毫秒”钩子（脚本的已知缺口第 1 条）。`powercfg /requests` 没有管理员权限，没取证。

脚本自带的纯逻辑测试（`node --test scripts/lib/recordingSoak.test.cjs`，9 项）通过。

## 六、产品缺陷

### 已修

1. **对外宿主注册被硬上限拒绝，所有 MCP 能力不可用（阻断）**
   - 现象：正式构建启动后 `mcp.status().ready` 一直是 false，外部连接调用全部拿到“应用正在连接”。开发版是同一份代码，同样受影响。
   - 日志：`mcp.host.register.failed`（frontend，01:55:48 与 01:58:01）ZodError `too_big maximum 256 path ["tools"]`。
   - 根因：`src/core/application-control/localHostContracts.ts` 的 `localHostRegistrationSchema` 写死了 `tools.max(256)`、`domains.max(32)`、`entities.max(128)`。能力数量最近已超过 256 个（最近几个提交又加了录音开始、停止、暂停、恢复等能力），注册在渲染端和主进程两侧都被拒。这也违反 AGENTS.md 的“容量不设硬上限”。
   - 修法：去掉这三处上限，只是删掉一个校验上限，不改 IPC 形状、不改持久格式。这个缺陷不修整个验收无法进行，而且根因只有一处，所以我直接修了。重新 bundle 后宿主立即 ready。没有测试依赖这些上限。
   - **请安排审查**：严格说这算触碰了 IPC 校验 schema，超出了“不涉及 IPC”的授权边界。

### 未修（只报告）

2. **录屏的麦克风在界面重载时断约 2.5 秒**
   - 证据：30 分钟长录第 810 秒重载，空档 2.53 秒；两次冒烟分别是 2.71 秒和 2.56 秒。麦克风都被拆成两条。
   - 日志：`recording.host.detached` 后 0.1 秒出现 `audio_capture.recording.summary`，说明麦克风原生会话随界面结束；接回后另开一段。
   - 原因：录屏的麦克风分段仍由界面写（`result-录屏.md` 第 263 行、`result-录音.md` 第 48 行已有记录）。系统声挪进原生进程后已经不断，麦克风还没挪。音频编辑录音则不受影响，60 分钟全程连续。
   - 影响：做正式视频时，录屏中途界面一旦重载，就会丢 2–3 秒口播。
   - 建议：把录屏麦克风按系统声的方式交给主进程驱动原生会话（工作量中等，涉及 IPC 与轨道记录），需要你安排。
3. **`logging.bridge.event_rejected`：导航日志无法写入**
   - 现象：`navigation.surface.open.start/.completed` 两条日志每次都被拒，原因是 “An object could not be cloned”。长录里切回音频编辑时稳定出现。
   - 原因：`registerToolboxCapabilityHandlers.ts:28`、`navigation/application/applicationDomain.ts:48`、`registerCanvasCapabilityHandlers.ts:178` 把整个能力上下文 `context` 当作 `correlation` 传给 `openApplicationSurface`；`surfaceNavigationService.ts:68/89` 把它展开进日志上下文，里面有不可结构化克隆的字段。
   - 影响：与录制无关，只是这两条日志丢失。应只传 `requestId` 等可序列化字段。
4. **写盘峰值偏高（观察）**
   - 4K60 录屏与声音写在同一块盘（E:）时，系统声写盘峰值 1084 ms、麦克风 931 ms（02:30:38 同时出现）；录音 60 分钟峰值 632 ms。
   - 全程丢帧 0，说明缓冲兜住了。但“写盘慢到多少会开始丢”这次没测到边界，长时间 4K60 加慢盘时值得留意。
5. **小观察，未判定为缺陷**：清理时把作品移进回收区后，音频编辑里仍开着那份已删除的作品，直到手动返回。是否需要在删除时关闭编辑器，可以另行确认。
