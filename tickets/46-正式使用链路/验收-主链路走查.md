## 二、问题清单

### 挡路（3 条，均已修，待审查）

**Q1 读不到口播任务状态**
- 现象：`query_audio_edit_tasks` 返回 `APPLICATION_OUTPUT_CONTRACT … tasks.0.errorMessage: Invalid input`。只要有一条成功的任务就必现，所以助手读不到转写或处理的进度，也读不到能否重新转写。
- 根因：`electron/main/services/audio-edit/task-store.ts:171/177` 的 SQLite 行类型写成 `error_message?: string`，实际成功的任务是 `null`，原样传给声明为 `string().optional()` 的输出契约（正是 AGENTS 里“`field?: T` 不允许 null”那条）。
- 修法：行类型改成 `string | null`，输出时 `?? undefined`。重启后读回正常。

**Q2 快速处理必失败（界面与助手都会）**
- 现象：`quick_process_audio_edit` 报“任务引用与当前口播不匹配”，执行状态 not_executed。界面上的“快速处理”按钮调用的是同一个 `quickProcessAudioEdit`。
- 根因：`compressAudioEditSilence` 在一次操作里两次调用主进程停顿分析：去重念用 `energy:{}`，压缩停顿用 `energy:{levels:true}`，传的是同一个 requestId。主进程 `runAudioEditTask`（`task-store.ts:186`）规定同一请求号只认一份输入摘要，第二次就会被拒。单独的去重念、呼吸处理只调用一次，所以不受影响。
- 修法：`audioEditApplicationService.ts` 里去重念那次分析改用派生请求号 `${requestId}:retakes`；`cancelAudioEditTask` 取消父请求时连带取消 `父请求号:` 开头的子任务，取消照常有效。真实应用复跑通过。回归：`audioEditQuickProcess.test.ts` 的替身按主进程规则拒绝“同号不同输入”，旧代码会失败（已验证红→绿）。

**Q15 口播改动后剪辑永远不更新**
- 现象：口播送进剪辑后，回音频编辑删一句，`audioLinkNotices` 一直是“音频更新未完成，仍使用上次声音，稍后自动重试”。日志里每次都是 `音频正在更新，将在保存后重试`，重试 4 次全失败。只有重启应用，等两个计数重新对齐后才会更新。
- 根因：`src/features/videoEdit/application/videoEditAudioLinks.ts:45`（今天的 db0b6ff8a 引入）拿口播实例的 `document.revision`（内存编辑计数，每次编辑 +1）去比文件版本 `meta.revision`（每次保存 +1）。一次保存合并多次编辑（助手的一次事务、快速处理、拖动都会这样）之后，这两个数就永远对不上。
- 修法：改为比较 `persistedRevision`（文件版本），并要求没有未保存修改（`!dirty`）。回归测试“一次保存合并了多次编辑时照常刷新”：旧代码失败，新代码通过。**这项修复没进运行产物**（见零节），需要在 bundle 后的真实窗口里再验一次。
- 同类排查：`audioEditRegions.ts` 的频谱用 `rememberSavedRevision` 显式换算两种版本号，是对的；`videoEditAudioLinks.ts:211` 比较的是渲染版本和文件版本，同一口径，也是对的。

### 影响效率（按影响大小排）

- **Q21 一次录屏的所有片段共用一个链接组**（`src/features/screenRecording/application/recordingVideoImport.ts:42`：整次导入只生成一个 linkId）。录屏一旦暂停就会分成多段，之后裁剪或调速其中一段，其他段跟着变，回执也不提。剪辑时容易误改；内置助手这次自己察觉了（用 linked=false）。建议按时间跨度给每段画面和对应的声音各配一个链接组。
- **Q24 两个进程编辑同一份文档时，后保存的一方静默覆盖**：内置助手（CLI 进程）切开多机位、给录屏前段加速后写回了文件；应用里开着同一份剪辑，下一次保存时检测到冲突（期望版本 22、实际 25），`documentSession.ts:470` 自动选“覆盖”，0.5 秒后写盘，CLI 的修改就没了。磁盘旧版本按设计由 `repository.ts:327 preserveFile` 备份，但应用和助手回执都没有提示，助手的回执还是 verified。日常只用应用内侧栏时不会碰到；用 CLI、外部同步盘或多实例时会丢改动而不自知。至少应在回执与界面上说明“覆盖了别处的修改，旧版本在哪”。
- **Q12 口播成品没法由助手导出**：`export_audio_edit` 的 destination 只有 quick 和 preset 两种，用户都没配置时直接拒绝；剪辑导出省略 destination 时默认放进项目的“导出”文件夹。建议口播也默认放进项目的“导出”文件夹。
- **Q13 录屏导入的 sequenceId 不认组合 id**：读回和创建得到的都是 `文档:序列`，传进去却报“录制期间目标序列已移除”（`recordingVideoImport.ts:21`），而且 executionState=unknown，recovery 写“执行结果没能确认”。实际上什么都没执行，报错还把助手引到错误方向。`start_screen_recording` 的 destination 也是同一个字段。
- **Q8 外部会话缓存了旧的工具清单与输出 schema**：本会话（Claude Code）开局时缓存的 mcp 工具缺 `start_audio_edit_recording`、`undo_audio_edit` 等，`list_projects` 也因为旧输出 schema 校验失败。新连接正常。应用更新后外部助手要重连；可以考虑由服务端发 `tools/list_changed`。
- **Q16 插入音频**：`positionSeconds` 按原素材时间算，说明只写“作品的 positionSeconds 秒处”，助手看到的是剪后时间，会插错位置；插入段的字幕是占位“（需要重新转写）”，`transcribe_audio_edit` 又规定已有转写的口播不再识别，所以插入段没有办法补转写，占位文字会进字幕。
- **Q14 `place_video_edit_creative_result` 的 result.documentRef.kind 必须写 `documents.document`**，其他口播能力都是 `audio_edit.document`；传错时报“收到字符串”，看不出错在哪。
- **Q22 导出查询不给文件路径**：只有 assetRef。内置助手是从别处推断出路径的，外部助手要再查资产。
- **Q25 无窗口命令行取不到视频帧，导出也会在第 0 帧失败**（待办 4t3 已知）：内置助手第 3 次导出把它说成“当前会话 GPU 异常”，建议重启应用或更新显卡驱动，还把这个错误结论写进了项目的 `制作进度.md`。失败原因里应该写清“无窗口模式不支持合成视频帧”。另外 CLI 进程会自己启动空闲预渲染，并因为硬件编码不可用而失败（13:07、13:08 各一次）。
