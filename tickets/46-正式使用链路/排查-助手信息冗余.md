# 排查：传给助手的信息有哪些是多余的（4u）

> 2026-11-13，只排查与度量，没有改代码。证据来自三处：① 用真实通道同一套序列化函数离线导出的工具定义、契约、实体描述和模型结构（`buildApplicationToolCatalog`、`buildApplicationContract`、`applicationReflectionHandlers.describeEntities`、`projectApplicationToolResult`、`searchGenerationModelCatalog`、`getGenerationModelSchema`、`prepareGenerationTask`），脚本在 [证据/payload-audit/](证据/payload-audit/)；② 11-12 真实日志 `E:\文档\HenjiAI\.system\logs\henji-2026-11-12.log` 里 7 次内置助手运行、65 次模型请求的 `model_requested` / `model_completed` / `usage_summary` / `tool_executed`（DeepSeek `deepseek-flash`）；③ 本会话 MCP 实际下发给 Claude Code 的工具定义。MCP 实机抽样没做成：这次排查期间 `get_current_application_context` 通了一次，之后 `list_projects`、`describe_application_entities` 一直返回 `APPLICATION_NOT_READY`，所以真实读取结果改用日志里的 `tool_executed.resultText`（每条最多 4000 字）。
>
> **token 估算法**：离线体积用 tiktoken `o200k_base` 计（下文写“o200k”）。它不是 DeepSeek 的分词器。用真实日志校准过一次：同一会话从 8 个工具涨到 109 个工具，请求体多出 338,521 字节，DeepSeek 实际输入多出 105,284 token，约 3.2 字节/token；同一批工具用 o200k 计约 3.75 字节/token。所以**工具 JSON 的 DeepSeek 实数大约是 o200k 的 1.2 倍**。中文为主的文本，o200k 和 DeepSeek 大致都在 1.3–1.6 字/token。仓库的 `estimateContextTokens` 是保守估算，偏高 1.5–2 倍，只用于预算，不用于这里的结论。

## 一句话总评

模型参数那一块之前已经瘦得差不多了。**现在真正烧 token 的是工具定义**：内置助手一旦按领域加载工具（例如 `video_edit` 一次 90 个），每次请求就固定多出约 10.5 万 token，而且整个会话都不卸载。真实会话里**工具定义占全部输入 token 的 82–86%**，工具结果只占一成左右。

## 冗余清单

“缓存影响”一栏：**前缀**指系统提示词和工具定义，改一次会让所有用户的缓存各失效一次，之后长期省；**每轮**指工具结果和宿主上下文，越短越好，不影响前缀。

### 甲、每次请求都付的固定开销

**甲1 按领域加载会把整个领域的工具一次带上，并且整个会话保留**（收益最大）

- 位置：`electron/main/services/embedded-agent/toolDisclosure.ts:31-37`（loader 的说明把“领域”列为一种加载方式），`:71`（`domains.includes(domainOf(name))` 会选中该领域的全部工具），`:21-29` 与 `:58-61`（已加载的名单从会话分支恢复，同一界面下一直生效）。
- 现状：`video_edit` 90 个工具，o200k 85.9k，真实 DeepSeek 约 10.5 万 token/次。真实会话 e0039f96 人在生成页，只是只读查结构，第 2 轮就从 21 个工具涨到 111 个；下一条消息 5a36b3db 首轮就是 111 个，7 次请求每次 12.6–14 万 token。
- 多余内容：只读查询其实只用到 `list/read_application_entity`，这两个本来就在基础工具里。e0039f96 和 9ed3b90f 真正调用过的领域工具只有 `observe_video_edit_frame`、`open_document`、`undo_application_changes` 3 个。
- 建议：loader 去掉按领域整体激活，改为 `domains` 只返回该领域的工具名和一句用途（目录式），实际加载必须点名 `names`；或者给领域加载设个小上限，并把全量名单放进返回文字里。加载的工具不跨用户消息保留，或者只保留本会话实际调用过的工具。
- 预计节省：剪辑类会话每次请求从约 11–14 万降到 2–3 万 token，会话总输入少 75–85%。
- 缓存：工具集变小、变化少，对缓存是净利好。与 4t 协调两点：新加载的工具追加在列表末尾，不要按名字插进中间（`toolDisclosure.ts:50` 现在按名字排序）；真实日志 9ed3b90f 第 26 次请求加了 6 个工具，那次有 27,823 token 没命中缓存。
- 风险：助手可能不知道该点哪个名字。所以领域目录要返回名字和一句用途，`load_application_tools` 的说明要改成先看目录再点名。
- 涉及文件：`toolDisclosure.ts`（4t 没改它）、`toolDisclosureProfiles.ts`；`piEngine.test.ts` **正被 4t 改**，要协调。

**甲2 每个工具 schema 里的通用信封与噪音**（两条通道同源，一次改全受益）

- 涉及文件：`resultProjection.ts`。注意 `boundedTransactionResult` 是回执唯一出口，改投影时不要碰它。

### 丙、偶发的

**丙1 生成准备的输出（用户点名的“模型参数”，之前的精简漏了它）**

- 位置：`src/features/generation/application/generationPreparationService.ts:593-616`、`registerGenerationCapabilityHandlers.ts:285-288`；`resultProjection.ts:93` 的 `modelMetadata` 只处理 `search_models` 和 `get_model_schema`。
- 现状（离线，300 字提示词）：Kling 4.0 751 token、GPT Image 2.6 794、MiniMax Speech 768。
- 多余内容：
  - `options` 原样回显整段 `prompt`，长度随提示词增长，最长 32k 字符。
  - `options` 带全部默认值和界面专用状态，例如 MiniMax 的 `minimaxVoiceClonePanel`（`lastPreviewAudioUrl`、`lastPreviewAudioFilePath`、`cloneAudioFileName` 等 15 个界面字段）；GPT Image 在 output=image 时仍带 `FrameCount`、`FrameDuration`、`SvgModel` 这些被联动隐藏的参数。
  - `selectionEvidence` 全是回显：`selectedModelId`、`providerId`、`canonicalModelId`、`tags`，以及空的 `qualitativeDescription`、`schemaValidated:true`、`availableInRegistry:true`。
  - `priceEstimate` 有浮点噪音（`1.1749999999999998`、`7.954749999999998`），`comparisonNote` 每次都是同一句，`comparableCnyExchangeRate` 也每次都带。
- 建议：prepare 输出只给 `prepared`、`canSubmit`、`message`、`adjustedParams`、与默认值不同的 `options`（不含 prompt）、`mediaLimits`、`priceEstimate`（金额四舍五入，去掉固定说明）；`selectionEvidence` 只留 `standing` 和 `standingReason`。`resolve_generation_model` 和 `prepare_canvas_node_generation` 一并核对，这次没有离线展开它们的输出。
- 预计节省：−50–70%，提示词越长越多。
- 风险：中等。`submit` 是否依赖模型从 prepare 结果里抄完整 options 要先查。如果 `create_visible_generation_task` 需要完整 options，就让宿主按 `inputSignature` 记住，不让模型抄。
- 涉及文件：上述两个文件，没人在改。

**丙2 `search_models` 与 `get_model_schema` 的残余**（已经精简过，剩下的不多）

- `search_models`：每条都带 `selectionEvidence:{"compatible":true}`（15 token × 32 条）和 `canonicalModelId`。`priceEstimate.description` 在 `generationPreparationService.ts:251` 被截到 80 字，句子会断在中间（例如“Klein 每”），**可能误导估价**，宁可去掉也不要半句。整页约 5–5.7k token。
- `get_model_schema`：164 个模型中位 496 token，最大 1,187（apimart-midjourney）。残余是 `schemaVersion`、浮点噪音、固定的 `comparisonNote`；`inputLimits.rules[].when` 用的是内部表达式 `falKling40Mode === "reference-to-video"`，能看懂，但可以换成“模式=参考生视频时”。
- 预计节省：−10–15%。优先级低。

**丙3 技能主文件超过入口预算**

- `skills.test.ts:93/125` 的 6,144 字节入口预算只对 `video-edit-workbench` 和 `image-edit-workbench` 断言。现在 `三维镜头构图/SKILL.md` 18,168 字节（o200k 5.5k），`audio-edit-workbench/SKILL.md` 10,515 字节，`video-edit-code-creation/SKILL.md` 10,226 字节。技能是按需加载的，但一读就会留在整段历史里。
- `domainProfiles.camera_stage.guidance`（`toolDisclosureProfiles.ts:38-41`）和三维技能主文件讲的是同一套做法：加载 camera_stage 时 guidance 先进上下文，接着又要读技能。
- 建议：三个超标的主文件把细节拆进 references；预算断言扩到所有准入技能。**`audio-edit-workbench` 正被 4s1 改**，等它合入后再拆。
- 预计节省：每次加载该技能少 2–4k。

**丙4 MCP 专有**

- `toMcpResult` 的 `content.text` 与 `structuredContent` 完全相同（`mcp/resultProjection.ts:14-15`）。规范允许这样做，但会让“两份都给模型”的客户端付双倍。可以考虑在有 outputSchema 时让 text 只放摘要；先核实主要客户端怎么消费。
- outputSchema 257k 只占传输，不确定有没有客户端交给模型，优先级低。

**丙5 宿主上下文**（不大，只留观察）

- 每轮固定带一句 `read:` 指引和 `truncated:false`、`selectionCounts`，约 60 token。
- 剪辑里的 `currentStyle.summary` 是整份风格说明书。相同时 `compactStableText` 会替换成“与前文相同”，不同时全文发送。说明书可能有数千字，这次没有实测样本。
- `availableCapabilities`（全部能力 ID）在完整快照里有，但 `buildEmbeddedPromptContext` 没把它交给 Pi，这是对的。

### 两条通道是否同源

工具目录（`buildApplicationToolCatalog`）、结果投影（`projectApplicationToolResult`，经 `applicationToolDispatcher.ts:100`）、实体描述都是同源的，**没发现一边精简了另一边没跟上**。差异只有这几处：MCP 多 outputSchema、多一份 text 镜像、instructions 里带记忆快照；Pi 多 `load_application_tools` 和 `read_assistant_context`，记忆按请求召回。所以甲2、乙1–乙5、丙1 都是一次改两边同时受益；甲1、甲3 只影响内置助手。外部不按需加载的客户端吃的是全目录 179k，甲2 对它们最直接。

### 其他发现（不属于冗余，单独记）

- 离线导出时，实体 `font` 的 json schemaRef 解析失败（`SCHEMA_NOT_FOUND`），连带 `describe_application_entities(domains=["video_edit"])` 整域失败。可能只是离线没有注册字体 schema，**要在实机确认**；如果实机也这样，就是“注册了但走不通”的那一类缺陷。
