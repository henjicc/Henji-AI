# 代码与参数风格一致性

目标：在不违背 API 文档的前提下，尽量保持 Henji-AI 现有模型风格统一。

## 1) 现有模型的新版本（优先强一致）

- 先选同家族旧版本作为主参考（同 provider、同模态）。
- 能复用就复用：参数命名、参数顺序、默认值语义、mode 切换结构、request 组织方式。
- 仅在 API 变更处做“最小差异改动”，不要顺手重写整套风格。
- 需要改名/改顺序时，在确认清单里写明“为什么必须改”。

## 2) 全新模型（保持项目级一致）

- 参数命名遵循当前仓库习惯：`{provider}{Model}{Field}`。
- 参数排序遵循 `param-order-patterns.md`，优先和同模态模型一致。
- 请求构建结构保持现有模式：先归一化输入，再条件映射字段，最后返回 requestData。
- 复用已有工具函数与共享文案 helper（如 `sharedFieldText`、媒体 source helper）。

## 3) 与 API 文档冲突时

- API 契约优先于风格。
- 允许“局部风格不一致”，但只限必要字段。
- 在确认清单中输出“差异项”：
  - 字段名差异
  - 默认值差异
  - 请求结构差异

## 4) 落地前快速自检

- 同家族模型并排对比：`meta`、`params`、`endpoints`、`request` 四段结构是否同形。
- 是否出现无必要的命名风格漂移。
- 是否因为追求统一而错误映射了 API 字段（禁止）。
