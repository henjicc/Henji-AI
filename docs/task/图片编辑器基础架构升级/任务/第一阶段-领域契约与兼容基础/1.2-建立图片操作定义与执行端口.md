# 1.2 建立图片操作定义与执行端口

## 任务状态

- 状态：待验证
- 所属阶段：第一阶段（领域契约与兼容基础）
- 前置任务：1.1
- 关联任务：2.1、2.3、3.2、3.3
- 是否可以并行：否

## 任务目标

建立不依赖图片编辑器 UI、画布节点或 Electron 实现的图片操作定义、注册和执行端口。用现有标注/几何能力证明契约，让后续发光、调色或画布独立节点可共享参数、校验和执行语义，无需复制代码。

## 当前情况

- `src/features/canvas/tools/types.ts` 的 `CanvasToolPlugin` 同时定义标签、图标、编辑器种类、支持节点、初始参数和执行，但直接依赖 `CanvasNode/NodeToolType`。
- `ToolOptions` 只允许字符串/数字/布尔值，当前通过把 `ImageMarkDoc` JSON 放入字符串规避复合类型。
- `builtInTools.ts` 定义“编辑”和“切割”两个画布工具；`registry.ts` 有注册表雏形，但数据源仍是固定数组。
- `CanvasToolProcessor.process()` 按 `NODE_TOOL_TYPES` 分支，没有执行 handler 注册。
- 智能助手的 `imageEditOperationSchema` 是现有可运行时校验基础，但它属于助手协议，不应继续成为编辑器领域的唯一定义。
- 现有标注导出发生在渲染层 Canvas；`electron/main/services/image/ops.ts` 已有 Sharp 图像服务，但本次尚无需求驱动的新效果执行器。

## 实施方案

将“操作数据定义”、“编辑器面板注册”、“画布宿主适配”和“具体执行器”分开。核心定义至少提供稳定 ID、参数 schema、默认值、可用阶段/顺序和输出类型；执行端口按操作 ID 分发到当前兼容渲染器或未来 Electron 后端。

本任务不创建黑柔/白柔/灰光定义，不注册新画布节点，不新增无实际执行内容的 IPC。

## 执行步骤

1. 基于 1.1 的 V2 文档，列出操作定义必需字段，区分核心参数、编辑器展示元数据、画布宿主元数据和执行 handler。
2. 建立宿主无关的操作定义、注册查询、重复 ID 检查、参数解析/默认值和显式输出类型。
3. 建立执行端口与 handler 注册，使调用方提交 `{ operationId, params, source }` 类似稳定请求，不需知道实际执行在渲染层还是主进程。
4. 将现有标注文档/几何操作作为首批定义或兼容适配器，用现有 `exportMarkedImage()` 验证执行端口，保持像素结果不变。
5. 为未来画布工具/节点定义最小适配输入，仅描述如何复用操作 schema 与执行，不引入 `CanvasNodeDefinition` 到核心目录。
6. 添加单测，覆盖注册、重复 ID、默认参数、非法参数、未知操作、执行分发和标注兼容输出。
7. 把最终契约、执行目标和未来主进程边界写入实施方案，供 2.3、3.2、3.3 直接消费。

## 验收标准

- [ ] 核心操作定义不导入 React、`CanvasNode`、Electron 主进程或具体 UI 组件。
- [ ] 注册表对重复 ID、未知操作和非法参数有确定错误行为与测试。
- [ ] 现有标注/几何能力通过新执行端口可达，对外导出结果和日志语义不变。
- [ ] 画布适配契约只引用核心能力，核心定义不反向依赖画布。
- [ ] 没有创建空发光工具、空 IPC、空 Electron 服务或新画布效果节点。
- [ ] 定向测试、TypeScript、ESLint 通过，任务总览和执行记录已同步。
