# T2 交接：代码效果作者源码的类型检查

来源：`docs/task/代码效果与渲染改进/以后再做.md` 第 12 条（作者源码的类型）。按建议做了前者：提供作者接口的 `.d.ts`，试渲染前后台跑类型检查，把错误按“文件:行:列”报给助手。没有做“规范改写成 JS”。

## 1. 方案与选型

### 怎么检查

- **检查器**：TypeScript 自带的 LanguageService（项目已依赖 `typescript` 5.9.3，编译 Worker 里本来就在用它解析源码位置）。TS Playground、Monaco 的 TS Worker 都是这条路。看过 `@typescript/vfs`：只是给浏览器拼虚拟文件系统的薄封装，这里要自定义模块解析（与打包器同一套 `resolveAuthorProjectImport`，含 `@组件/` 映射），再加一层依赖没有收益，而且本任务不能装依赖，所以直接实现 LanguageServiceHost。
- **为什么用常驻 LanguageService，而不是每次 `ts.createProgram`**：标准库约 1.2MB 文本，解析加绑定是冷启动的主要开销（约 0.3 秒）。LanguageService 留着已解析的标准库和没变的作者文件，之后每次只重查变化的文件。实测热检查只要十几毫秒，见第 3 节。
- **让作者不写注解也能查**：作者源码通常是 `export default { draw(ctx, time, params) {...} }`，参数没有类型。检查器只在内存里把入口的默认导出改写成 `__henjiAuthorModule({...})`。这是一个带 `const` 泛型的声明函数：`ctx`、`time`、`info`、图层与 `pose` 由此得到上下文类型；`params` 的键名和取值形状从 `params` 声明推断（number→number、color 默认值是十六进制时为 string、写成数组时为 RGBA 元组、point→{x,y}、其余为 any）。插入点记在表里，报错位置换回原文行列。默认导出写成 `const effect = {...}; export default effect` 或 `export { effect as default }` 时，改写变量初值。
- **推断失败时退回宽类型**：没写 `params`，或模块对象另有错误时，键名一律按 any 处理。否则 TS 会把真正的错误（比如 `nmae` 拼错）挤成一条误导性的“params 不能赋给 readonly []”。有测试锁住这一点。
- **只报“能确定是错”的问题**：`strict` 关闭，`noImplicitAny`、`strictNullChecks`、`noImplicitThis` 都关；`strictBindCallApply`、`strictFunctionTypes` 开。标准库用 `esnext` 加 `webworker` 系列，不给 DOM，因为作者代码运行在剪辑渲染 Worker 里。WebGPU 类型用 `@webgpu/types`。`.wgsl`、`.glsl` 导入按字符串处理，`http(s)://` 外链按 any 处理。忽略 TS2556（`ctx.moveTo(...point)` 这类把数组展开成定长参数的写法，运行时照常工作）。
- **误报基线**：技能文档里全部 21 段完整 ts 源码零报错，已固化为测试。仓库里另外 49 段内嵌作者源码也跑过（一次性原型脚本，未入库）。除测试夹具本身读了未声明参数 `p.amount`（属真问题），以及多文件夹具缺少兄弟文件以外，没有误报。

### 放在哪一层、何时触发

- **线程**：复用现有的源码检查 Worker 脚本 `videoEditCodeCompiler.worker.ts`，新增 `author.typecheck` 消息，但另起一个 Worker 实例专门做类型检查（`VideoEditAuthorTypeChecker`）。比较过三种做法：
  - 放进打包所用的同一实例：类型检查是同步的，冷启动约 0.3 秒，会挡住打包请求，还可能触发打包的 5 秒超时。
  - 另写一个 Worker 文件：Vite 会给它再打一份约 9.5MB 的 TypeScript。
  - 放主进程或 utility process：要新开 IPC，违反“禁止为新功能另建通道”，而且创建流程本来就在渲染层。

  选定的做法是同一份 Worker 代码起第二个实例，产物里不多一份 TypeScript，打包与类型检查互不排队。检查实例常驻，空闲 120 秒后结束以释放内存；单次请求 20 秒超时就结束线程；取消只放弃这次结果，线程保留热状态。
- **触发**：只在助手（以及外部 MCP、经公共入口的 UI 调用）创建 `video_edit.code_material` 或 `video_edit.code_version` 时触发，即执行器传入 `typeReports` 收集器的路径。模板套用、代码资产导入、界面“新建代码素材”对话框、界面源码编辑器的候选路径都不检查，不额外起线程。**打开工程、播放、导出都不经过类型检查**，以前能渲染的工程不受任何影响。
- **与打包、试渲染并行**：拿到钉住的组件后立即开始检查，不进入渲染关键路径；提交（`editVideoProject`）之后再收结果，最多再等 8 秒。等不到或线程出错时如实记为“类型检查未完成（原因），本次没有类型结论”，不让已提交的修改变成失败。

### 错误怎样到达助手

走现有的同一条路，不另建通道：
- **创建成功**：执行器 `withAuthoringHints` 里，与“参数化体检”和性能回报并列，按素材追加一条 `observation` 证据。`fact` 形如“类型检查发现 N 处问题（不阻止创建，画面照常试渲染；按位置修正后提交新源码版本）：- main.ts:12:9 TS2551 Property 'fillStlye' does not exist on type 'OffscreenCanvasRenderingContext2D'. Did you mean 'fillStyle'?”，最多列 6 条，总长不超过 1000 字。`data` 给出结构化的 file、line、column、endLine、endColumn、code、message，最多 20 条。没问题时写“类型检查通过：main.ts。”。JS 未开检查时不出证据。
- **加载或试渲染失败**：`withVideoEditCodeTypeContext` 把类型问题附在原错误信息后面（“类型检查同时发现 N 处问题，可能就是原因：…”，最多 5 条）。错误类、`CodeMaterialError` 的 code 和 `sourceSpan` 都不变，界面源码编辑器的跳转照旧可用。取消、`SYNTAX`、`SOURCE_LIMIT` 原样抛出：取消不是源码问题，后两者打包器已给出准确位置。
- TS 信息保留英文原文加错误码。模型最熟这套措辞，也不必另打包约 300KB 的中文诊断表。长链只保留首行（哪里不匹配）和末行（根因，例如缺少 bounds）。

### 阻断还是警告：警告

理由：
1. 运行时才是作者接口的真相。声明再准，也有它覆盖不到的写法（宿主接受任意长度的 bounds 数组、Chromium 新于 TS 标准库的 API、作者粘贴进来的无类型第三方代码）。如果阻断，误报会卡住本来能正确渲染的源码，助手只能学会加 `any` 绕过，检查反而失去信用。
2. 错误本身可操作：每条都带 文件:行:列 加错误码加 TS 的“Did you mean”。成功时它出现在证据里，告诉助手按位置修正后提交新版本；失败时它就在错误信息里，作为最可能的原因。
3. 检查是并行的，不拖慢创建；“不阻止”写进了证据文本和技能文档，助手只凭结果与说明就知道该怎么做。
4. 与 FrameFlow 方案第 7 阶段“apply 时可选类型检查”一致。

### JS 入口：默认不查，`// @ts-check` 开启

- 内置六套风格的样片都是 JS（`index.js`），JS-only 素材也不经 esbuild 直接交给浏览器。默认检查会给存量 JS 带来一批 checkJs 特有的噪声，例如对象字面量方法里的 `this` 按上下文类型推断。
- 助手单文件 `source` 的默认入口就是 `main.ts`，主路径已经覆盖。
- JS 作者可在文件开头写 `// @ts-check` 获得同样的检查（含上下文类型）；任何文件开头写 `// @ts-nocheck` 关闭检查。这两条都是 TS 标准写法，技能文档已说明。

### 作者接口声明与宿主契约的一致性

- 声明文件是 `resources/video-edit-author/author-api.d.ts`。它不进应用自己的 TS 工程和 eslint，原因有两个：一是它引用的 WebGPU 全局类型在应用工程里没有，二是作者参数值必须用 `any`，而项目禁止新增裸 `any`。源码检查 Worker 以 `?raw` 方式打包这份文本，它不随安装包作为单独文件发行。
- 检查器另外给出全局类型别名 `AuthorModule`、`AuthorLayer`、`AuthorPose`、`AuthorRect`、`AuthorFrameInfo`、`AuthorParams`、`AuthorAssets`、`AuthorGpuInputs`，作者在拆出去的工厂函数上标注时不用导入。
- `videoEditAuthorApiContract.test.ts` 用正式 tsconfig 编译一段只含类型断言的文件，逐项核对：
  - 宿主类型（`videoEditAuthorModule.ts`）与声明的字段集合相同（宿主自用的 `sourceSpan` 除外）；
  - 宿主传给 draw、layers、WebGL、WebGPU 入口的实参满足作者看到的参数类型；
  - 作者按声明写出的模块与图层被宿主接受（只放宽 bounds 和 clip 为 `number[]`）；
  - 真实的 `GPUTexture` 满足宿主的最小 GPU 结构；宿主设备类型的每个成员都是 `GPUDevice` 的成员。

  做过断牙验证：删掉声明里 `AuthorPose.blur`、把 `motionBlur` 改名后，两条断言失败；恢复后通过。
- 只做“核对”，没有改宿主 `videoEditAuthorModule.ts`（只读约束）。若以后想反过来由同一份声明派生宿主类型，需要先解决 WebGPU 类型在应用工程里不可见的问题。

## 6. 风险与遗留

- **声明精度**：`params` 取值推断只覆盖确定的类型，其余为 any。color 按默认值形状区分字符串和数组，与宿主 `authorParameterValues` 一致。若宿主改变参数值形状，需要同步 `author-api.d.ts`（一致性测试不覆盖参数取值映射，只覆盖结构字段）。
- **报错位置**：`layers()` 返回的图层不合规时，TS 把错误报在 `layers` 方法名上，不是具体图层对象；末行会写明根因（缺 bounds、pose 字段名不对）。这是 TS 对对象字面量方法的固有行为。
- **工厂函数**：在没有上下文类型的位置写 `{ blurShape: "lens" }` 这类字面量联合时，可能被拓宽成 string 而报错。作者可用全局 `AuthorLayer` 标注返回类型。这类情况在技能样例里没有出现。
- **JS 默认不查**：风格样片与 JS 素材得不到这层检查，需要时加 `// @ts-check`。
