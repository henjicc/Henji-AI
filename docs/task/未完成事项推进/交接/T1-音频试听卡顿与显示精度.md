> 来源：`docs/task/音频编辑完善/待处理问题.md` 第 3、5 条。2026-10-27，子代理 T1。
> 没有运行真实应用；结论来自读代码，加上能在改前代码上复现、改后通过的单元测试。行号“改前”指 HEAD `1b5e829d5`。

## 1. 结论

### 问题 3：删除、静音之后马上播放会卡一下（已修，根因已确证）

试听本来就由渲染层的 `AudioEditSpliceRenderer` 实时拼接，不是等成品分块；文档里“若是在等成品分块”这一支不成立。卡顿的原因是：剪切后已经读出的声音被全部丢掉，播放从冷缓存开始。

- **根因**：`src/features/audioEdit/preview/useAudioEditPreview.ts:74-76`（改前）里的 `planKey` 包含 `activeSpans`，所以任何一次删除或静音都会 `new PreviewChunkCache(...)`。一秒块缓存和“已保存”标记都挂在这个实例上（`previewChunkCache.ts:8-9`，改前），于是：
  1. 播放头附近已经读出的每一秒都要重新经 IPC 向主进程要。主进程每块都要走一遍 `requireAudioEditProject`，再走 `prepareAudioEditRenderSource`（整份作品 schema 校验、逐级检查缓存文件），最后起一次 ffmpeg 解码 1 秒（`electron/main/services/audio-edit/preview.ts:8-23`）。
  2. 新实例取第一块前还要 `flushAudioEditProject` 保存一次。保存后文件修改时间变了，主进程会重新读取、解析整份文档（`project-store.ts:36-56`）。
  3. 删除和静音根本不改变声音本身，上面这些都是重复劳动。依据：剪辑区间不进剪后声音的缓存键（`render.ts:59-64`）；静音是 `cuts.mode='mute'`，落到片段上只是 `muted` 标记（`timeline.ts:73-77`）。
- **放大因素**：`src/core/audioEdit/spliceCrossfade.ts:90、107`（改前）在渲染片段的任意一段之前，都先 `await` 这个片段首尾两个拼接点的判断，而判断要读拼接点两侧各 20 ms 的声音。剪完从拼接点开始播时，第一段还得等**下一个**拼接点（可能在几十秒外）两侧的块读回来。
- **为什么是“卡一下”而不是“晚一点开始”**：worklet 只要队列里有数据就出声（`public/audio-edit-preview-worklet.js` 的增益目标只看 queuedFrames）。`togglePlayback` 也是先发 `playing`，再等填充（`useAudioEditPreview.ts:303、317`，改前）。第一段只到下一个整秒边界，可能很短；后面的块在冷缓存下一块一块串行地取，跟不上就会饿死，淡出后再淡入，听起来就是开头卡一下。缓冲追上以后就正常了。
- **修法**：一秒块按“声音”单独缓存（作品 + 素材 + 原始/剪后 + 处理配方），删除和静音只换拼接表，继续用已经读出的声音，也不再先保存一次；拼接点的判断只在这一段碰得到首尾淡化范围时才等，结尾那个拼接点的判断在后台提前开始。拼接输出逐样本不变，导出共用同一渲染器。

### 问题 5：加了十段图形均衡器、改几次后波形与频谱精度下降，撤销又恢复（频谱部分已修，根因已确证；波形另修了一处同类缺陷，“精度下降”本身未确证）

文档里的“时段图形均衡器”应为“十段图形均衡器”（`graphic_eq`）。它排在去口水音、呼吸这类整段处理项之前时，属于效果链中“整段处理的那一段”，每改一次参数声音配方就变一次（`src/core/audioEdit/effects.ts:100-105`、`regions.ts:46-49`）。

**频谱根因（已确证）：两个“作品版本”不是同一个数，却被直接拿来比较。**

- 显示端的目标版本：`AudioWaveWorkspace.tsx:201-203` 用 `project.revision`，是内存实例的版本，**每改一次加一**（`audioEditProjectInstances.ts:338` 的 commitEdit；撤销、重做在 :371 也加一）。
- 宿主给块和整段进度标的版本：`electron/main/services/audio-edit/spectral-pyramid.ts:154` 用从文件读出的 `project.revision`（`project-store.ts:51` → `documentContent.ts:62` 取的是文件外壳的 revision），**每保存一次加一**（`electron/main/services/documents/repository.ts:274`）。
- 自动保存会把 800 ms 内的修改合成一次写入（`src/features/documents/documentSession.ts:52`）。拖均衡器滑块这类连续修改，内存版本加好几次，文件版本只加一次，于是内存版本越跑越靠前。
- 出现差距以后再改一次声音，目标版本就是当时的内存版本，比宿主之后能回的任何文件版本都大：
  - `useAudioEditSpectral.ts:137`（改前）把新声音的每一块都当成过期，悄悄丢掉；`finally` 里又立刻重发（:148-150），形成一个持续的整块 IPC 循环，每块约 5 MB。
  - 整段计算的进度也在 :82 被丢掉。
  - 新块进不了 store，显示一直停在改声音之前那份 store（:212-216 的 held）。放大或平移到新位置后，只剩旧 store 里有的粗层，这就是“精度下降”。
- “撤销又恢复”的两种情况：撤销到没有整段处理项的状态时进入原始模式，版本恒为 0，立刻恢复；撤销回之前看过的声音时，旧 store 里正好有当时视野的细层块，看起来也恢复了。
- 之后如果零散的修改又各自保存了足够多次，文件版本追上目标版本，也会自己恢复。所以表现是“改过几次以后”，而且时有时无。
- 其他拿宿主版本做比较的地方（`audioEditApplicationService.ts:83、137`，`audioEditSpliceService.ts:38`）用的都是 `persistedRevision`，是对的；比错的只有频谱这一处。
- **修法**：在频谱唯一的取块入口 `audioEditRegions.ts` 里，记下“保存屏障完成时的文件版本 → 保存前的内存版本”。宿主回来的块和整段进度，先把文件版本换算成内存版本再交给调度器。这份记录按实例保存，重新打开后作废。另外，调度器收到过期结果时改为隔 600 ms 再取，并记 debug 日志 `audio_edit.spectral.tile_stale`，不再连续重发。

**波形：修了一处同类缺陷（已确证）**

- `AudioWaveWorkspace.tsx:164`（改前）在 150 ms 后直接调 IPC `audioEdit:editedSource`，没有先保存。主进程按文件里的作品来渲染（`electron/main/ipc/audio.ts:50-53`）。如果 800 ms 的自动保存还没写，拿回来的就是上一份声音的路径，还会被 `rememberEditedSource` 记在这次声音的名下。结果是直到下次改声音之前，显示的都是旧声音的波形。
- 平时常常被试听那边恰好先保存了一次而掩盖住，属于时序竞态。
- **修法**：新增 `getAudioEditEditedSource`，先保存，再请求。

**波形“精度下降”本身：没有在代码里找到长期变粗的确定原因，没有改行为。**

已核对的内容：

- 多级峰值是一次返回整份所有层级（`electron/main/services/audio/ops.ts:444-460`），不存在“先给粗层”的中间状态。
- 新声音的波形读出之前，界面沿用上一份（`AudioWaveWorkspace.tsx:174-178`）。读出后如果已经放大到采样级，还要再回读原始采样（`useWaveformDetail`）。回读要在全局 2 路的重任务门限里排队（`electron/main/services/media-import/concurrency.ts:1`），排队期间画的是第 0 级峰值。这会暂时变粗，属于正常的过渡。
- 风险点：`src/services/waveform/waveformDataService.ts` 的 `acquireWaveformDetail` 回读失败后，会把这个窗口标成 `failed`，同一窗口以后不再重试；只要平移不出这个窗口，就一直是粗的。我没找到确定的失败触发条件，按要求没有改。已有日志 `services.waveform` 的 warn“精细波形回读失败，保留多级峰值显示”可以确认是否发生过。

**文档里另外两个猜测的核对**

- “每份 256 MB 的块缓存挤掉了细层”：`SpectralTileStore.set` 淘汰时会跳过当前需要（pin）的块（`src/core/audio/spectralTiles.ts:48`），可见范围和预取范围内的细层块不会被挤掉。未发现问题。
- “频谱块失败三次就不再重试”：这个机制确实存在（`useAudioEditSpectral.ts:47、117`），但修复前新声音的块是被当成过期丢掉的，不计入失败次数，和这次的症状无关。可能造成连续失败的路径见第 6 节，未确证。

## 4. 需要用户在开发版里确认的操作

问题 3（试听）：

1. 打开一份做过修复、效果或区间音量的口播（剪后模式），在编辑器里播一段后暂停。
2. 在刚听过的位置拖一个时间选区，按 Delete（另试一次按 M 静音），马上按空格。听开头还卡不卡。
3. 在效果链里加“基本声音”这类实时效果后，重复第 2 步。
4. 选区放在完全没听过、也没拖动擦洗过的远处，删除后马上播放。第一次可能要稍等一下才出声（冷缓存），但出声后不应马上断一下；如果还会断，告诉主控，见第 6 节。

问题 5（显示）：

1. 用有去口水音或呼吸处理的口播，在效果链里把“图形均衡器（10 段）”放到这些整段处理项之前。
2. 显示选“都显示”，放大到频谱能看到细节，连续拖几次均衡器滑块，然后放大、平移到新的位置。
3. 看：
   - 频谱应在新声音处理完、细层算完后（几秒内）变清晰，不再一直停在粗一层；
   - 波形应是改过的声音，比如把 31 Hz 拉到最高，波形幅度应跟着变；

   - `npm run logs:query` 查 `audio_edit.spectral.tile_stale`（debug 级），正常时不应持续出现；

## 6. 风险、遗留与范围外发现

1. **换声音后频谱会空一下**：新 store 收到第一块就整体切过去（`useAudioEditSpectral.ts:212-216`），而第一块常常是整段计算刚开始、还是 0 列的总览块，可见区域会空白一下，直到可见范围的细层块算完（每块几十到几百毫秒）。这是暂时现象，没有改。如果用户仍然觉得“闪一下、变粗一下”，建议改成：新 store 缺块的位置逐块回落到上一份声音的块。改的时候要注意控制旧 store 的保留时长和内存（每份最多 256 MB）。
2. **改声音后，旧声音的整段频谱计算不会取消**：`spectral-pyramid.ts:47-99` 的后台任务没有“观察者都离开就取消”的机制，原生端的整段计算又是串行的（`native/audio-worker/src/spectral_server.rs` 的 background 锁）。连续改几次后，最新声音的整段计算排在最后。另外 `spectralWorker.request` 默认 120 s 超时（`spectral-worker-client.ts:73`），从发出就开始计时，排队时间也算在内，排久了会以 AUDIO_WORKER_TIMEOUT 失败，然后从头再算。这影响视野超过约 3 分钟时用的粗层（level ≥ 3）。没确证和这次的症状有关，没有改。建议先查日志 `audio_edit.spectral.failed` / `completed` 的错误和 elapsedMs；确认后再给后台任务加“无人关注即取消”，并把整段计算的超时改成按进度续期。
3. **取消细层块可能导致整个频谱进程被结束**：原生端在前台锁上排队的请求，要等前面的块算完才回执；主进程的取消宽限期只有 2 s（`spectral-worker-client.ts:86`），一过就结束整个频谱进程，所有在途的块一起失败，各记一次失败。连续失败三次后，这一块在当前调度器里不再重试（`useAudioEditSpectral.ts:117`）。快速连续改均衡器时有可能触发，未确证。判断方法：`audio_edit.spectral.tile_failed` 的消息是“频谱进程取消超时”或“音频频谱进程已退出”。如果确认，需要改 Rust：`spectral_server.rs` 在拿 foreground 锁之前，以及拿到之后，先检查 cancelled，已取消就立即回执。我不能编译原生程序，所以没有改。
4. **冷缓存下的试听**：删除点附近从没播放或擦洗过时，仍要逐块经 IPC 和 ffmpeg 读取；如果第一段很短，理论上仍可能饿一下。如果用户还反馈卡，可以加两样：读当前块时顺带预取时间线上的下一块；起播前至少缓冲约 0.25 秒再出声。这次没做，因为会改变现有缓存命中次数的断言和 worklet 的起播语义，而已确证的根因已经修了。
5. **频谱版本换算**依赖“取块前先保存”这个屏障，这是现有入口本来就有的。将来如果有别的代码绕过 `audioEditSpectralClient` 直接调 `getPlatform().audioEdit.spectralTile`，版本就不会被换算，需要走这个入口。
6. `docs/task/音频编辑完善/待处理问题.md` 第 3、5 条的状态需要主控更新（我不能改 `docs/task/**`）。
