# 界面巡检与打磨：实施方案

[返回总览](00-任务总览.md) · [重要记录](重要记录.md)

## 一、背景

《界面重设计与主题引擎》计划把主要页面按“石墨”设计系统落地了，但用户实际使用后仍发现细节问题（2026-10-04：模式参数不在第一位、生成底栏换行、选中项与高亮看不清），而且仍有不少老旧页面、弹窗和状态没被新界面覆盖。这类问题靠组件级检查和现有门禁发现不了，需要**真实操作软件、截图、逐张目视**才能发现。

本计划是长期计划：先定规范和操作工具，再按区域循环“操作 → 截图 → 发现 → 修复 → 复验”，最后把反复出现的问题沉淀成自动检查。用户反馈的那三类问题由界面计划的 4.3 修复，本计划从 4.3 之后的界面开始巡检。

## 二、界面审查规范（每张截图按这张表看）

规范本体以 skill `henji-ui-surface` 与 `docs/rules/frontend-ui.md` 为准，这里只列巡检时逐张核对的维度。1.1 会把这张表写进 skill 的参考文件，作为所有 Agent 改界面和验收时的统一清单。

| 维度 | 判据（任一不满足即记为问题） |
|---|---|
| 骨架 | 窗口顶到内容区最多两条带（命令带 + 从属带）；不套卡片；同一视图横向 padding 一致 |
| 单行与收纳 | 工具条、底栏、命令带在 960 与 1440 下都不折行；放不下的按优先级收进“更多”浮层，而不是挤成两行 |
| 顺序 | 决定其余参数含义的选择（渠道、模式、版本）排第一；主动作在最右或约定位置；同类页面顺序一致 |
| 状态可辨 | 选中、悬停、聚焦、按下、禁用一眼可辨且互不同色；选中用强调色指示（界面计划重要记录 012）；悬停或选中的容器里，行内控件仍与容器底可区分 |
| 文字 | 常见中文选项与标签不截断；必须截断时有完整提示；不竖排折行；数字与单位不分行 |
| 对比度 | 像素审计通过（正文 ≥ 4.5，大字与图标 ≥ 3）；四个预设下都可读 |
| 一致性 | 同类控件同一个组件、同一尺寸档；返回入口按三种形态；同一动作在不同页面图标与文案一致 |
| 动作层级 | 一个表面只有一个强调色实底主动作；同组动作同档；破坏性动作静息静默 |
| 信息准入 | 不展示内部 ID、版本、哈希、缓存/管线状态；技术限制写成用户能判断的后果 |
| 三态 | 空、加载、错误走 `UiEmpty` / `UiLoading` / `UiError`，且每个数据区都能看到这三态 |
| 图标 | 只用 lucide 或确属图形的 SVG，禁止 emoji 与符号字符 |
| 尺寸与缩放 | 1440×900 与 960×640 都可用；界面缩放、长文本、多数据（长列表、很多参数、很长文件名）下不溢出、不重叠 |
| 交互反馈 | 点击、拖动、打开浮层都有可见反馈；浮层不被裁切，位置贴近触发点；嵌套浮层内的操作不关闭父浮层 |
| 性能观感 | 打开、切换、滚动没有可见卡顿或闪烁；首帧不出现无样式或错位的中间态 |

问题分级：

- **P0**：不可用，或有数据风险（点不到、关不掉、操作丢数据、崩溃）。
- **P1**：看不清、点错、错位、折行、截断、顺序错、状态不可辨、对比度不达标。
- **P2**：一致性与细节（间距不齐、同类不同样、文案不统一）。

P0、P1 在本轮修复；P2 同区域顺手修，跨区域的统一处理记入第三阶段。

## 三、操作规范（用代码操作软件）

1. **实例**：只用自动化测试实例（共享启动器，已静音），放副屏（`HENJI_DEV_DISPLAY_POINT=2561,1`，显示器变化时重新核对）。不操作、不静音、不结束用户自己的开发实例；结束后只关本次启动的测试进程树。
2. **数据**：默认临时资料目录 + 仓库夹具。要看真实模型列表或供应商配置时用 `--profile real`，只读，不带 `--allow-writes`。**不触发真实付费生成**：需要“生成中 / 已完成 / 失败”这类状态时用夹具或场景内的模拟结果。确需真实付费调用时先问主控，由主控按用户授权判断。
3. **进入页面**：用已登记的开发导航参数、正式应用能力或界面点击，不猜 ID、不建无关工程。入口缺失就记为问题或补开发导航参数，不绕路。
4. **定位与动作**：按可访问名称与角色定位元素，不写死坐标；每步之后等待稳定（动画结束、字体与图片加载完、浮层定位完成）再截图。
5. **截图**：用正式截屏，不在窗口缩放下用 CDP 裁剪（3.7 已踩过错位）。每个区域至少石墨、深海、胶片、纸白 × 1440×900，再加石墨 × 960×640；关键交互态都要截：静息、悬停、聚焦、浮层打开、选中、拖动中、空、加载、错误、长文本、多数据。
6. **目视**：Agent 必须打开每张截图，按第二节逐项看，并配合像素对比度审计。DOM 断言通过不等于视觉通过；不能只看自动报告就下结论。
7. **记录**：问题写进对应区域任务的“问题台账”表：编号、级别、页面/状态、截图路径、现象、违反的判据、根因、修复提交、复验截图。截图放 `.ui-tour/` 或 `.ui-patrol/` 下（不进仓库），台账里写相对路径。
8. **修复**：按根因改共享组件、令牌或模型展示补丁，并在同类实现里排查同源问题；不在调用点打补丁。修完用同一套步骤复跑、重新截图对比。有回归价值的路径固化为 `ui:tour` / Reality 场景。
9. **收尾**：关闭测试实例；临时脚本、截图、日志不进提交；按项目规则精确提交并推送。

## 四、单轮巡检流程

```
选区域 → 读盘点清单里该区域的页面与状态
→ 写/复用探针步骤（进入 → 各交互态 → 截图）
→ 四预设 + 960 跑一遍 → 逐张目视 + 对比度审计
→ 填问题台账（分级）→ 按根因修复 + 同源排查 + 精确测试
→ electron:bundle → 同一探针复跑 → 复验截图目视
→ 有价值的固化为场景 → 提交推送 → 更新总览
```

一轮结束的标准：该区域台账里 P0、P1 全部修复并复验，P2 已处理或已登记到第三阶段。

## 五、阶段划分

| 阶段 | 内容 |
|---|---|
| 第一阶段：规范与工具 | 1.1 把第二、三节落进 skill 与测试规则，建脚本化探针工具；1.2 全量盘点界面清单与新界面覆盖情况 |
| 第二阶段：分区巡检与修复 | 按盘点结果分区循环巡检；先查用户最常用的区域（生成、画布），再查老旧页面 |
| 第三阶段：检查固化 | 把反复出现、可以判定的问题（条带数量、折行、截断、同色层级、选中可辨）做成自动检查进门禁 |

第二阶段的任务可按 1.2 的盘点结果增减或拆分；新发现但不属于已有区域的问题，记入最接近的区域任务或新增任务。

## 六、执行规则

- 沿用两个计划共用的主控规则：只在 `main` 工作；每个任务独立验证后用 `git add -- <文件>` 精确提交并推送；`packages/ai-sdk` 的换行符改动不属于本计划，不提交也不还原。
- 写代码的子 Agent 最多两个；`electron:bundle`、Electron、Reality 全局串行；界面重设计计划未完成的任务优先。
- 子 Agent 不得执行 `git add` / `git mv` / `git commit`，由主控提交。
- 每个修复最多两轮返工，仍不达标标记阻塞并写明原因。
- 改界面先读 skill `henji-ui-surface` 与 `docs/rules/frontend-ui.md`；收尾按 `docs/rules/testing.md` 选验证。
- 本计划不改业务逻辑、数据结构与 IPC，除非问题根因就在那里（例如入口缺失、状态不刷新），并在执行记录说明。
