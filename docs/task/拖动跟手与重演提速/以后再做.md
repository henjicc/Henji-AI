## 优先级 2

### 4. 拖动时主线程的界面重绘

开发版每次指针事件约有 9 毫秒花在 React 重绘上：工具栏、菜单、文字覆盖层每帧都重绘。

- 先用 `electron:prod` 看正式构建里还剩多少。
- 再对只关心播放头的组件做选择性订阅。

### 5. “先加速后减速”拖动不稳定

第二轮两次实测的 90 分位分别是 42 和 61 毫秒，是唯一超过 50 毫秒的场景。要先查清超时出在哪一段：发请求、Worker 排队、解码还是呈现。

### 7. 擦洗音频的遗留

- 新引擎（提交 `e1709c879`）还等用户试听确认。开发版要整页重载（Ctrl+R）才会加载新的音频处理器。
- 慢速拖动按设计是断续的，原速片段之间留空，这样不变调。**2026-11-02 用户试听：快速拖动干脆、不变调，认可；但慢速拖动“放一下断一下”不行，要像 PR、AE：只要拖动没停，再慢也是连续的、不变调的慢速播放（变速不变调，按拖动速度连续时间伸缩），停下才静音。** 这是下一步要做的。
- 第一次混音冷启动约 0.5 秒。
- 系统输出延迟约 60 毫秒。

### 8. 网页重演的遗留

- 显卡共享纹理是 Electron 的实验接口，Mac 上没验证过，按设计应自动退回 CPU 画面。
- 虚拟时钟管不到：Worker、`requestIdleCallback`、视频/GIF、没写 smooth 的平滑滚动，仍走真实时钟，个别异步解码处可能差几帧。
- 页面加载阶段页面时间是停着的，应用会比录制时更早显示出来（约 30 毫秒对 153 毫秒）。
- 左上角帧标记被顶层弹窗盖住时，退回取最新画面，并给出警告。
- 待核实：跑 `npx vitest run electron/main/services/web-replay` 时，当天应用日志里出现了同一时刻的 `web_replay.replay.failed` / `capture_fallback`。测试可能写进了真实日志目录。

### 9. 4K60 长 GOP 素材拖动的精确帧更新率（2026-11-02 实测）

- Reality `video-edit-4k60-scrub`（4K60 H.264、GOP 120、B 帧）单独运行：精确画面更新冷倒拖 2.8 次/秒、正拖 4.0、快速正拖 8.4、热倒拖 11.3，场景门槛 27（快速 58）。解码 p95 约 0.4–0.5 秒，硬件解码占用持续约 98%：每一步都从前一关键帧往后解几十帧，已到硬件上限，不是退化。
- 场景只数 `data-presented-frame` 变化，近似画面（常驻关键帧）不计入；手感上先出近似画面，跟手程度要另外看。
- 要达到门槛需要新策略，例如：正向拖动复用顺序解码器连续往前解、倒拖用解码后的倒序帧缓存、拖动时按指针速度选择只追关键帧；或调整场景口径把近似画面计入并单独约束精确帧追上的时间。属于拖动手感设计，等用户定方向。
