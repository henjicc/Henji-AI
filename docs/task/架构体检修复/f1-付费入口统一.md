## 根因与实现

原 `applicationPaidRequest` 对没有助手调用上下文的 UI 返回 undefined；普通生成又仅在模型声明专用确认时申请授权，导致 UI 与助手不共用费用事实。现在 UI 经既有 `applicationControl.complete/uiPaidApproval` 通道，交给同一个主进程策略、operationStore 和 paidReservations；origin.actor 为 user，界面表示“你”。

复用 ask/auto/bypass、单次/每日额度、按真实项目与类别的授权。新增内部 UI 操作标识只用于账本，不新增公共 Agent 工具。无真实项目归属的工具箱/聊天/提示词优化不伪造项目。生成估价复用正式 createPriceEstimate，包含受控隐藏工具模型；不重复运行请求准备与媒体上传。

统一生命周期为 prepare → approve（需要时）→ start → complete；确认拒绝/等待取消为 not_executed，不调用模型、不占额度。已派发后失败保留 unknown，不能冒充退款。嵌套调用和批次通过本次信号复用授权，避免重复预留；助手沿原可信作用域与异步生成回执，不创建 UI 副账本。

所有费用确认由 GlobalAlertDialog 展示。auto 通过后沿现有 NotificationContext 轻提示一次“已按自动同意规则执行，预计 ¥x”；未知价格保留“按模型实际计费”。删除字幕任务、标题、双语字幕、扩图与两宿主录音转写的私有费用确认。讲解外发原有审批保留，专用 Modal 改为统一弹窗。

## 应用能力覆盖与设计自查

覆盖分级：本次为现有业务能力的授权基础设施修复；不新增用户数据实体或专用 MCP 工具。原算法能力和通用实体读写不变，内部 UI 审批枚举不属于对外目录；UI、Pi、外部 AI 继续共用正式领域入口与策略。

1. 助手只凭名称和说明能否用对？能，原识别/翻译/标题/生成等正式语义入口不变，可信上下文带入原有审批和项目归属，不要求模型拼内部 UI 标识。
2. 能否 AI 先做、人只确认？能，预检和估价先完成，规则额度内自动执行，需确认时统一展示费用与单次/项目同意；确认前不发付费请求。
3. 产物能否直接流进其他工作区？能，继续落入原字幕、标题、媒体、画布与讲解候选服务，保留原保存、稳定引用和撤销流程，没有新增中间产物格式。

成熟方案选型：复用项目已有 Zod schema、Zustand 弹窗队列、GlobalAlertDialog、NotificationContext、operationStore 与付费策略。现有实现已覆盖所需能力，无需引入第三方审批库或另建账本/通知/IPC。
