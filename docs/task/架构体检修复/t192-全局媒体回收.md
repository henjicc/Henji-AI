## 最终回收时机与判定

- **启动**：数据库初始化后，在任何主窗口、文档会话、MCP/助手服务启动前，等待本轮扫描与删除结束；随后才创建渲染窗口。CLI/模型验证模式不回收，以免与桌面会话并行。
- **运行中**：历史、预设、素材等业务记录删除/替换只通过 SQLite 事务 outbox 写候选；上传、编辑状态、缩略图和租约释放只入队。已删除旧的定时器、删除后去抖和 live 心跳/IPC/owner census，不存在运行中物理回收入口。
- **退出**：复用既有 closeApplication 保存守卫及 window:confirmClose。主进程记录窗口必须经过保存确认并真正关闭；未保存窗口、强制销毁或关闭失败都不能回收。will-quit 后等待既有服务清理全部成功，才执行回收。退出回收最多等 **3 秒**，超时发出 AbortSignal 并继续退出；候选留到下次启动。已提交给操作系统的单次 unlink 无法撤销，取消后不再发起后续删除。
- **保守判定**：应用创建凭证、当前受管根、realpath 后的路径及文件身份都吻合，且所有引用提供者成功并无人引用才删除。读失败、未知媒体协议、提供者超时、持久数据变化、文件替换都保留。按文件判断：同一历史记录里仍被引用的输入不会阻止无引用输出释放；派生文件仍受主文件保护。
- **提交账本交接**：generation_submissions 增加内部 media_released 字段。完成结果落入历史时，由同事务触发器持久记录交接；文档发布/保存确认时，以及静止窗口读取文档时，也记录交接。未完成或尚未交给持久 owner 的提交仍持有引用。已经交接的完成回执继续用于幂等，但不再持有媒体引用，删除历史不会使其重新生效。
- **回收站**：当前仓库没有应用内回收站或永久删除接口，正式文档/项目入口实际调用 shell.trashItem。按本轮决定不追踪操作系统回收站，已移除上一轮系统回收站永久快照。没有新增应用内回收站产品功能；未来若加入，应把其持久快照注册为提供者，永久删除快照后释放引用。

## 受管范围与排除清单

只有 writer 显式登记过创建身份的文件可回收；目录位置本身不代表删除权。

| 实际目录来源 | 可回收内容 |
|---|---|
| getUserFolderDir('generated') | 当前作品根“生成结果”/Generated，不含项目自己的生成结果目录 |
| getUserFolderDir('uploads') | 当前作品根“上传素材”/Uploads 的托管副本 |
| getProgramStoreDir('thumbnails') | Thumbnails，含 540 子目录及素材缩略图 |
| getProgramDataDir()/EditStates | 已解除历史持有关系的编辑状态文件 |

| 排除范围 | 理由及删除边界 |
|---|---|
| ImageEditorV3 CAS | 有独立不可变资源引用、租约与 GC；本回收器不登记或删除其文件 |
| AudioEdit/录音会话内部缓存 | 由文档、任务或录音会话管理，可重建；保留其生命周期 |
| ContentDiskCache（代理、缩略帧、波形等） | 内容身份、缓存预算及过期规则由现有缓存服务维护 |
| DocumentStore 文档封面/会话缓存 | 由文档生命周期清理；回收器只读取持久会话里的媒体引用，不删除缓存本身 |
| 外部导入原件、项目作品/素材、导出目录及普通用户文件 | 不属于应用受管根，不获得回收器删除权 |
| 没有创建凭证的既存文件或已被其他内容替换的文件 | 不按文件名推断所有权，保守保留 |

CAS、AudioEdit、ContentDiskCache、文档封面/会话的删除入口统一使用缓存边界检查：真实路径不能位于受管根内，递归目标不能包含受管根；junction 别名也受保护。通用 fs 删除同样防止路径别名绕过。check:media-recycle 覆盖这些入口及桌面启动时的边界接线。

## 引用提供者清单

1. SQLite 注册表：history、presets、assets、generation_submissions（只保留尚未交接或未完成引用）、pending_task_results、camera_stage_render_tasks、audio_edit_tasks、settings、application_invocations、application_observations。注册同时生成删除/替换 outbox；未知带媒体路径/JSON 字段的存储在运行时与原生测试中拒绝回收。
2. 文档：DOCUMENT_KINDS 全部已登记类型，用户根、外部登记位置、索引里的文档与项目包；JSON 文档、图片包和嵌套包均在 Worker 扫描。普通作品目录只扫描正式文档扩展名，避免把任意 JSON 文件误当文档。
3. 已保存会话：DocumentStore/session-state（含画布持久撤销/重做历史）、ImageEditorV3/documents 工作副本。EditStates 仅扫描仍有 history 持有者的文件，孤立编辑状态不能反过来永久保住被删历史的结果。
4. 脱离索引的位置：从列表忘记的外部项目/缺失文档仍登记扫描根；离线或不可读时保守失败。
5. 主进程租约：生成媒体租约、上传图片租约和正在取得租约的路径。成功生成遗留的进程内租约可能使退出轮保留；下次启动没有这些进程内租约，仍按持久引用重新判定。

不再有 renderer-live-and-undo 提供者。未持久的临时状态只存在于运行期，该阶段没有删除权；可恢复的撤销引用从已保存的会话文件读取。

## 选型、规模与设计自查

- 复用现有 better-sqlite3/SQLite 事务与触发器，不引入仅覆盖局部引用计数的库；跨 SQL、文档包、会话文件的引用必须由正式存储提供者作证。SQLite 版本按总管理者决定维持 **21**，未增加外部契约版本或目录指纹。
- 复用 Node Worker、现有 yauzl、正式文档保存屏障和退出清理流程；不增加依赖或并行运行时。Worker 每文件/ZIP 条目应答，SQL 128 行分页让出事件循环；没有产品数量上限。退出 3 秒是生命周期技术预算，超时只保留，不忽略引用。
- 原生测试验证真实 SQLite 与磁盘/Worker 链路；尚未取得大规模工程内存和耗时数据。单个大 JSON/嵌套 ZIP 仍在 Worker 整份解析。
- **助手只凭名称和说明能否用对？** 能。公共“删除记录/文档”的调用不变，UI 与助手继续走同一领域存储；回收为内部维护，不新增工具、设置或算法能力。
- **能否 AI 先做、人只确认？** 候选入队、完整引用判定、失败保留及下次静止窗口重试均自动完成，不要求用户逐文件操作。
- **产物能否直接流进其他工作区？** 能。沿用原媒体 URL 和共享路径；已持久文档、持久撤销历史、预设、素材等任一 owner 的引用都会保护对应文件。
