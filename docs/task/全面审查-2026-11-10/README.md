## 建议的推进顺序

1. **D1 → D4 → D5** 一起做。它们是同一个根因链：设置表和调用记录的每次改写都往回收队列里塞一条候选，回收又只能在启动和退出各 3 秒的窗口里跑，永远清不完，数据库因此变大，自检和快照跟着变慢。先修 D1，D4、D5 的症状会消掉大半。
2. **E1**：先让 CI 变绿（一处间距门禁、11 个测试文件），再定一条“红了当天修”的规矩。CI 红着的时候，上面那批数据层改动没有保护。
3. **D2、D3**：都是小改动，风险低，收益明确。
4. **E2**：首屏脚本瘦身，直接改善每次启动。
5. **A1、A2**：回到 2.0 交付主线，按缺口清单的顺序做。
6. **U1** 以及 P2、P3 各项，穿插着做。

## 做得好的（不用再花力气）

- **Electron 隔离**：所有窗口都是 `contextIsolation: true`、`sandbox: true`、`nodeIntegration: false`；导航与新窗口都有拦截；IPC 统一经 `registerIpcHandler` 解析入参并脱敏错误。
- **架构门禁**：依赖图零循环、零禁用边；死代码基线里未使用文件和依赖都是 0；裸 `any` 全仓只有 1 处；`TODO/FIXME` 只有 6 处。
- **数据保护的意识**：数据库有逐版本迁移、升级前备份、每日快照和损坏自动恢复；持久格式有契约和黄金样本。
- **渲染层兜底**：未捕获异常与未处理拒绝都落日志；根错误边界能显示原因并重试。
- **测试规模**：2286 个测试文件，CI 分片并记录成本历史。
