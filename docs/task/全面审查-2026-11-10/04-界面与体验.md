<a id="u1"></a>
## U1（P1）工作区没有各自的错误边界

### 现象

错误边界只有这几处：根（[main.tsx:95](../../../src/main.tsx)）、图片编辑器、镜头参考、全景查看器。生成、画布、工具箱、剪辑四个工作区在 [TabContainer.tsx](../../../src/components/TabContainer.tsx) 里只包了 `Suspense`，没有错误边界；助手侧栏、设置弹窗、素材库浮层也没有。

日志里 13 次 `app.ui.crashed` 全部是在根上接住的：生成页的一个任务卡片渲染出错，整个应用（包括正在剪的片子、正在跑的助手对话）都被换成一张错误页。这 13 次都发生在开发过程中，但机制对正式版一样成立。

### 影响

任何一个工作区里的渲染错误，都会让用户看不到其他工作区。点“重新加载界面”会重新挂载整棵树，没保存的界面状态（滚动位置、展开的面板、输入到一半的内容）全丢。

### 建议做法

1. 在 `TabContainer` 里给每个工作区各包一层 `UiErrorBoundary`，错误页只占这个工作区的区域，标题栏和工作区切换照常可用。
2. 助手侧栏、设置弹窗、素材库浮层、剪辑的各个停靠面板同样各包一层。面板出错时只有这个面板显示错误和“重试”。
3. 用 `resetKeys` 绑定当前文档 ID：切换到另一份文档时自动重置错误状态。
4. 画布节点：单个节点渲染出错时只把这个节点显示成“无法显示”，不影响其他节点。镜头参考已经对单个模型这么做了（`CharacterErrorBoundary`），照着做。

### 注意事项

- 只用现有的 `UiErrorBoundary`，不要再写新的错误边界类。镜头参考里那两个自己写的（`CharacterErrorBoundary`、`TreeErrorBoundary`）有机会时也换成它。
- 错误边界接不住事件处理函数和异步代码里的错，那些仍然走全局兜底，这是正常的。
- 错误页的文案现在是写死的中文，和 U2 一起处理。

<a id="u2"></a>
## U2（P2）英文界面是半成品

### 现象

`src/i18n/locales` 下有 `zh-CN`（3984 条）和 `en-US`（3986 条）两套词条，185 个文件用了翻译函数。但扫描界面代码后发现，293 个界面文件里还有约 3063 行直接写死的中文（不含注释、日志和抛出的错误），按目录分布：

| 目录 | 写死的中文行数 |
|---|---|
| `src/features/videoEdit` | 1399 |
| `src/features/cameraStage` | 308 |
| `src/features/audioEdit` | 246 |
| `src/features/imageEdit` | 158 |
| `src/components/params` | 150 |
| `src/features/logs` | 108 |
| 其余 | 约 700 |

主进程里的原生对话框文案（数据库恢复提示等）也是写死的中文。

所以切到英文后，生成页和设置基本是英文，剪辑、镜头参考、音频编辑基本是中文。

### 需要用户先定方向

这是产品决定，两条路：

- **A. 2.0 只做中文**：把语言切换入口收起来（或标注“预览”），英文词条留着不删。成本最低，也最诚实。
- **B. 2.0 要有可用的英文**：需要把这三千多行都接进词条，工作量大，而且之后每个新界面都要守这条规矩，需要加门禁。

建议选 A，等产品在国内站稳、有明确的海外用户需求时再做 B。理由：目标用户画像目前是中文创作者；三千行文案的翻译质量需要人看，不适合现在分散精力。

### 如果选 B

1. 加一条静态检查：界面文件里不允许出现写死的中文字符串，存量按文件记进基线，只减不增。
2. 按工作区分批迁移，剪辑最后做（量最大、变化最快）。
3. 助手能力的名称和说明是给模型看的，保持中文，不在这次范围里。

<a id="u3"></a>
## U3（P2）密钥解密失败时用户看不到原因

### 现象

11-09 19:47:57 到 19:48:18 之间，正式构建运行时 `keystore.decrypt.failed` 连续出现 33 次（供应商 `apimart`），同时外部连接的凭据也报“暂时无法解密”7 次。[keystore.ts:188](../../../electron/main/services/keystore.ts) 的处理是：记一条警告，然后“按未配置处理”。

### 影响

- 用户看到的是“这个供应商没有配置密钥”，会以为密钥丢了而重新输入。原因其实是系统加密服务解不开（常见情况：用不同的用户数据目录启动、系统账户或系统加密密钥发生变化）。
- 每次读取都重新尝试解密并记日志，21 秒 33 条。

本次没有查清这一次具体为什么解不开（当时刚启动正式构建，随后界面加载也失败了一次，可能是同一个启动异常的连带现象）。**需复核。**

### 建议做法

1. 区分“没有保存过”和“保存过但解不开”两种状态，后者在供应商设置里明确显示“已保存的密钥在这台电脑上无法读取，请重新填写”，而不是显示成空。
2. 同一个密钥解密失败后，在本次运行内记住结果，不再反复尝试和记日志；用户重新保存后清除。
3. 排查 19:47 这次的原因：对比开发版、正式构建、命令行三种启动方式下的用户数据目录是否一致（系统加密依赖用户数据目录里的状态文件）。

### 注意事项

- 这是密钥相关改动，碰的是安全五条底线的第一条。日志和界面都不能出现密钥明文或密文片段。
- 不要在解密失败时自动删除已保存的密文：换回原来的环境后它可能又能解开。

<a id="u4"></a>
## U4（P2）缺全局入口：命令面板、任务中心、统一快捷键

三件事都是“专业软件下限”里常见、现在没有的。它们和 AI 原生的方向一致：应用已经有两百个左右登记好名称和说明的能力，这些入口大部分可以从登记表自动生成，不用逐个手写。

### 命令面板

全仓没有命令面板或全局搜索。应用有四个工作区、十几个工具、上百个操作，新用户找功能只能逐层点。

建议：一个全局快捷键唤起的面板，数据来源就是能力登记表（名称、说明、所属工作区）加上设置搜索索引（`settingsSearchIndex.ts` 已有）、最近文档、素材。选中后走和助手、界面按钮相同的那条执行路径。这也顺带验证了“助手只凭名称和说明就能用对”：人搜不到的操作，名字多半也起得不好。

### 任务中心

生成、导出、代理文件、转写、本地模型下载、三维渲染、网页重演，各有各的进度显示，分散在各自的工作区里。切到别的工作区就看不到进度，也没有一个地方能看“现在后台在跑什么、哪些失败了”。

建议：标题栏放一个任务指示，点开是统一的任务列表，显示进行中和最近完成或失败的长任务，能取消、能跳到对应位置。数据来源是各域已有的任务表（`generation_submissions`、`audio_edit_tasks`、`camera_stage_render_tasks` 等）。助手那边也能用同一份数据回答“现在在跑什么”。

### 统一快捷键

可自定义的快捷键只有剪辑和屏幕录制有；其他地方是 53 处直接监听键盘事件加 126 处组件上的按键处理，没有统一登记。后果是：没有总的快捷键一览、不同工作区可能冲突、用户不能改。

建议：建一个快捷键登记表（标识、默认键位、生效范围、对应的能力），剪辑现有的自定义快捷键迁进来作为第一个使用者，其他工作区逐步迁移。命令面板里顺带显示每个命令的快捷键。

### 注意事项

- 三件事都是新界面，按 `henji-ui-surface` 做；先和用户确认要不要做、做到什么程度（[product-goal.md](../../rules/product-goal.md) 的“做不做”判断）。
- 命令面板和任务中心都不要另起一套数据，否则就违反了“同功能多份实现”。
- 优先级建议：任务中心 > 命令面板 > 快捷键。任务中心解决的是现在就存在的“看不到进度”的问题。

## 其他观察（没有单独编号）

- **“最近删除”占用**：`recent-deleted` 目录 833 MB、639 条记录。有保留期和过期清理，机制没问题；建议在设置的存储分区里显示它占了多少、提供“立即清空”，让用户知道空间去哪了。
- **解析不了的字体文件**：字体扫描每次都报同样 5 个解析失败的字体文件。可以记住失败的文件（按路径和修改时间），下次跳过。
