# 08 执行编排：谁来做、先后顺序、在哪做

返回[总表](README.md)。

这份文件回答三件事：每个任务用什么模型和思考强度；哪些能同时做、哪些必须排队；哪些要开独立工作区（worktree）。总调度的工作方式（派活模板、回报格式、审查与合并流程）沿用已有约定，这里不重复。

## 一、模型怎么选

依据是 Anthropic 2026-11-09 的文章 [Which Claude model should you build with?](https://claude.dev/blog/which-claude-model-should-you-build-with)，结合本项目的约束（思考强度只用 medium / high / xhigh；界面与审美不交给 Codex；Codex 目前暂停使用）。

### 四档模型各自干什么

| 模型 | 文章里的定位 | 在本项目里用来做 |
|---|---|---|
| **Haiku** | 量大、便宜、结果一眼能验的活 | 找文件、读日志、跑一个命令并摘出结论、列清单。不改代码 |
| **Sonnet** | 范围清楚、有明确规格的日常工作；重复性的调查、审查、起草 | 照清单做的机械改动（删未使用代码、改名、补词条）、单文件小修复、规格写死的小功能、文档整理、轻量审查 |
| **Opus** | 复杂编码的日常主力；拿不准时的默认起点；看图和操作界面 | 大多数缺陷修复与功能、需要判断的重构、所有界面与视觉工作（含逐张看截图）、独立审查 |
| **Fable** | 最难的技术项目：大型重构与迁移、架构规划、带多个子代理 | 总调度本身；涉及删用户数据或跨模块的方案设计；Opus 用 high 做过一轮仍不行的问题 |

### 六条选型规则

1. **默认从 Opus medium 起步。** 不确定用什么就用它。
2. **有清楚的规格不等于可以用 Sonnet。** 迁移、性能优化、碰持久格式的活，即使步骤写得很清楚，也用 Opus。Sonnet 只接“做错了一眼能看出来”的活。
3. **不够用时按这个顺序加码：先给它自己验证的手段，再加思考强度，最后才换更大的模型。** 给执行者一条能跑的检查命令（类型检查、某个测试、一条日志查询），通常比加强度更有效也更便宜。换到更大的模型时，思考强度从比原来低一档开始。
4. **Opus 到 high 还不行，就换 Fable medium，不要上 xhigh。** 文章给的数据：强度过了 high 之后，再加一档的花费和直接换大模型差不多，而大模型的结果更好。xhigh 只留给审查高风险方案这一种场合。
5. **小模型只放在出错代价低的地方，改代码和做判断留给主模型。** 小模型读错搜索结果，会让主模型打开错的文件，反而更费。所以 Haiku 只负责“找”和“读”，结论要带上文件路径和行号供复核。
6. **贵的模型上下文要干净。** 主会话只留决定和结论；大段阅读（长日志、几百个文件的清单、整份规则文档）交给便宜的子代理读完带回摘要。模型越大，这一条越要紧，因为长上下文每一轮都要重新计费。

### 什么时候值得开多个子代理

文章的结论和已有约定一致：

- **值得**：互不依赖、每块都够大、结果能独立检查。文章里的例子是一个大模型带 25 个 Sonnet 并行查缺陷，花费少三分之一而结果相当。
- **不值得**：一条依赖链上的步骤；一个上下文装得下的工作。这时候拆分和合并的开销比省下的多。
- 本项目的上限维持不变：同时实现的最多 3 个（确有需要可到 4–5 个），调研和只读任务不计入。

### 自动能验的活，先便宜后贵

文章里一个实用做法：结果能自动检验的批量工作，全部先用低配置跑，只把没通过的拿高配置重跑，总体更便宜、通过率还更高。本项目里适用的是 R2、R3（删未使用代码，类型检查就是验收）和 E1（修测试）：先 Sonnet medium 全做一遍，类型检查或测试不过的那几处再交给 Opus。

审查一栏：**独立审查** = 提交前派一个全新上下文的 Opus high 只看改动和规则；标 xhigh 的是高风险方案。

## 三、先后顺序

分四批。批与批之间串行；批内写在同一行的是一条线上依次做，不同行之间可以同时进行。

### 第零批：清场（全部在主工作区，一个接一个，不并行）

```
E1 修绿 CI  →  R1 R4 R5 E6 删除类小项  →  R2 R3 全仓清理并收紧门禁
```

为什么必须最先、必须串行：

- CI 不绿，后面所有改动都没有保护。
- R2、R3 要改几百个文件，和任何并行任务都会冲突。趁还没有 worktree 分出去的时候一次做完，之后拉出的每个 worktree 都基于清理后的代码。
- 这一批没有需要设计的东西，用 Sonnet 为主，是最便宜的一批。

这一批进行的同时，可以让 Fable 写 **D1 的设计文档**（只写文档，不碰代码，不算并行实现）。

### 第一批：数据层、启动、报错样式（三条线并行）

```
线 A（worktree A）：D1 实现 → D5 → D4 → D2
线 B（worktree B）：D3 → E2
线 D（worktree D）：V1 → V2 → V4 V5 V7
```

- 线 A 四个任务都碰数据库打开、迁移和主进程入口，是公共底座，只能排成一条线。每个任务单独提交、单独合并，不攒到最后。
- 线 B 两个任务互不相干，放一条线是为了控制并行数。D3 碰持久格式，E2 碰构建配置，都不和线 A 重叠。
- 线 D 是界面线。V2 改公共组件 `UiError`，之后的 V4、V5、V7 才能用上新样式，所以排在后面。
- **线 B 的 E2 和线 D 的 V5 都会碰剪辑目录**，但文件不重叠（一个是代码素材审查，一个是时间线片段绘制）。合并时后合的那个先把 `main` 合进自己的分支再验证。

合并顺序：谁先验收通过谁先合，一次合一个；每合一个在 `main` 上跑类型检查和受影响的测试。

### 第二批：助手与全局视觉（主工作区的两个独占任务 + 两条并行线）

```
主工作区（依次）：A2 → V3 V6（字体与聚焦描边，公共令牌）→ V9 逐屏复查
线 C（worktree C）：A1 方案 → A1 各项能力依次实现 → A1 真实验收
线 E（worktree）：R6 → V8
```

- A2 改的是所有写入共用的执行引擎，V3、V6 改的是全局令牌和字体。这两类都是公共底座，放主工作区依次做，做的时候不合并其他界面分支。
- V9（逐屏复查）必须排在 V2、V3、V6 之后：公共组件和字体定了再看，不然看出来的问题一半会被后面的改动覆盖。它也依赖线 E 的 R6（巡检场景能跑通）。
- A1 是这一批里最大的一块，自己占一条线。它依赖 A2：验证逻辑不修好，真实验收时助手会被假失败带偏。所以 A1 的实现可以和 A2 同时开始，但 A1 的真实验收要等 A2 合并后做。

### 第三批：其余完善（三条线并行，随时可以插队做）

```
线 F：P1 → P2 → P3
线 G：D6 → U3 → R7
线 H：U1 → U2 → E4
V9 产出的逐屏问题：按“公共组件 → 令牌 → 单个界面”分批，每批一条线
```

### 收尾（独占）

```
E3 工具链升级（合并时不得有其他分支在等）→ E5 发布演练
```

E3 改依赖和锁文件，是最典型的公共底座：可以在 worktree 里先做完，但合并前后都要跑完整构建，这段时间不合其他东西。E5 放最后，对着最终的代码打包。

## 四、worktree 的用法

**开 worktree 的条件**（都满足才开）：和其他正在做的任务同时进行；改动的文件范围事先说得清；不碰下面列的公共底座。

**不开、直接在主工作区串行做的**：

- 公共底座：类型总入口、数据库结构与迁移、全局样式与设计令牌（`index.css`、`tailwind.config.js`、`styleTokens.ts`）、字体、依赖与锁文件、构建配置、所有写入共用的执行引擎。
- 全仓范围的机械改动（R2、R3）。
- 只读的调查和复查（V9、A1 验收、E5）。

表里线 A 的任务虽然碰数据库和迁移，仍放在 worktree 里，是因为第一批期间主工作区没有别的任务在动这些文件，而且它要和线 B、线 D 并行；条件是**线 A 存续期间，其他任何线都不许加数据库迁移**。需要加迁移的任务（目前没有）排到线 A 合并之后。

**每个 worktree 的固定动作：**

1. 从 `main` 的最新提交拉出。子代理自动创建的 worktree 基准可能是旧提交，brief 第一步写明先对齐到 `main`。
2. 执行者只在自己的 worktree 里改，只改 brief 列出的范围。
3. 需要真实窗口验证的，同一时间只允许一个 worktree 启动应用；类型检查这类重活各线错开跑，CPU 至少留 10%。
4. 验收通过后合回 `main`（压成一个提交），在 `main` 上跑检查，然后推送。
5. 合并后立刻清理：先扫描并断开 worktree 里指向主仓库的联接点（`node_modules` 等），确认为零，再删目录和本地、远端分支。

## 五、每个任务的 brief 里要带的验证手段

对应选型规则第 3 条。执行者手里有一条能自己跑的检查，比多给一档思考强度有用。

| 任务 | 给执行者的检查 |
|---|---|
| E1 | 失败的那 11 个测试文件逐个 `npx vitest run <文件>`；`npm run check:ui-design` |
| R2 R3 | 两个工程的 `tsc --noEmit`；`npm run check:dead-code` 报告的数量归零 |
| D1 | 隔离资料目录里改写设置 1 万次后候选表行数不变；真实资料目录副本迁移后候选数与库体积；启动日志出现 `media_recycle.sweep.completed` |
| D2 | 连续启动两次只有一个窗口；数据目录只读时出现错误提示并退出 |
| D3 | 旧版本黄金样本打开两次，第二次日志里没有 `persistence.backup.start` |
| D4 | 有快照与无快照的启动，“进程启动到界面加载完成”的耗时对比 |
| E2 | 首屏脚本里搜不到 `checkSourceElement`；`electron:prod` 启动耗时前后各量三次 |
| A2 | `assistant:cli` 对画布生成节点写 `generation_config`，返回成功且读回值一致 |
| V1–V7 | `ui:tour --steps` 截指定状态，执行者自己逐张看；改公共组件的加石墨与纸白两套主题 |
| P1 | 一天日志里 `fonts.scan.start` 的次数与触发原因分布 |

验证命令的范围按 [testing.md](../../rules/testing.md) 裁剪：只跑直接覆盖改动的测试加类型检查，不跑全量。
