## D1（P0）媒体回收从来跑不完

> **2026-11-10 更正**：实现以 [tickets/44-媒体回收后台化/design.md](../../../tickets/44-媒体回收后台化/design.md) 为准，那份设计逐条核对过代码。本节有几处写错了：
> - 22 次回收全部卡在“读取引用”这一步，清扫一次都没真正开始；退出时的回收没有任何记录。
> - 库里路径有三种写法并存，按“受管根目录前缀”判断会漏。按不漏判的条件，存量能清掉约 89% 的行、95% 的体积，不是 99%。
> - 文档保存或删除不会重新产生候选，所以“建议做法”第 5 步（给仍被引用的候选一个出口）不做。
> - 迁移前的数据库备份不是自动的，要显式声明才有。

### 现象

- 两天日志里回收启动了 22 次，**全部被推迟，删除的文件数都是 0**（`media_recycle.sweep.deferred` 17 次、`media_recycle.references.deferred` 5 次，没有一次完成）。
- 候选表 `media_recycle_candidates` 有 15,655 行，占 104.6 MB，是整个数据库（166 MB）的六成多。
- 每次带窗口启动，主进程都在回收上等满 3 秒才开始加载界面。

### 原因

三件事叠在一起：

1. **候选产生得太多**。[schema.ts:80-86](../../../electron/main/services/media-recycle/schema.ts) 给每张登记过的表建了触发器，行被更新或删除时把旧行整份存进候选表。候选按来源统计：

   | 来源表 | 候选行数 | 占用 |
   |---|---|---|
   | `settings` | 1,394 | 70.6 MB |
   | `application_invocations` | 6,569 | 15.3 MB |
   | `application_observations` | 5,791 | 13.5 MB |
   | 其余 5 个来源 | 1,901 | 1.6 MB |

   `settings` 里真正的设置只有十来条，其余是缓存：`cache.video-edit.code-metadata.v1:*` 1291 条（每条 19.5 KB）和 `cache.video-edit.render-performance.shown`（127 KB，经常改写）。这些缓存每改写一次就产生一条候选，而它们根本不含媒体路径。助手调用记录同理：一次调用会改写状态好几次，每次都留一条候选。

2. **回收只能在两个 3 秒窗口里跑**。[lifecycle.ts:25-38](../../../electron/main/services/media-recycle/lifecycle.ts) 启动时限 3 秒，退出时限 3 秒。日志显示光是“读取持久媒体引用”就要 2.3 秒（例：22:04:20.673 开始，22:04:23.026 才进入清扫），留给清扫的不到 1 秒，然后超时。

3. **仍被引用的候选不会离开队列**。[store.ts:22](../../../electron/main/services/media-recycle/store.ts) 对还在用的候选做的是“挪到队尾”，不是删除。所以队列只增不减。

### 影响

- 回收功能实际上不工作：该清的生成结果、上传副本、缩略图一直留在磁盘上。
- 数据库越来越大，带慢启动自检和每日快照（见 D4）。
- 每次启动固定多等 3 秒，且这 3 秒没有任何产出。

### 建议做法

按顺序做，每一步都能单独验证：

1. **缓存搬出设置表**（同时解决 D5 的一半）。代码素材参数缓存与渲染性能提示记录改存到不挂回收触发器的地方：新建一张 `cache_entries` 表，或者写成程序目录下的缓存文件。这是可重建数据，旧条目直接丢弃即可，不需要迁移内容。
2. **触发器只在可能含媒体路径时才记候选**。给触发器加 `WHEN` 条件：旧行里出现了受管媒体根目录的位置前缀才入队。`application_invocations`、`application_observations` 多数状态改写不涉及媒体，会被直接挡掉。
3. **清掉存量**。写一条迁移：删除不含任何受管媒体路径的候选。预计能去掉 99% 以上的存量。迁移前系统会自动备份数据库，这一步符合现有机制。
4. **回收改成窗口显示之后在后台跑**，不再卡在界面加载之前。引用普查的结果在同一次运行内可以复用（[store.ts](../../../electron/main/services/media-recycle/store.ts) 已有按连接缓存的“休眠”集合），分片执行，每片之间让出事件循环；不设 3 秒总时限，改成“用户开始操作文档时暂停”。
5. **仍被引用的候选给一个出口**：同一批路径如果已经确认被某份文档长期引用，就删掉候选；以后文档真的不再引用时，文档自己的删除或改写会重新产生候选。这一条要仔细核对会不会漏回收，拿不准就先不做，前四步已经足够让队列收敛。

### 注意事项

- 回收设计得很保守是有意的：宁可不删，不能错删。第 4 步把回收挪到后台后，必须保证“未保存的文档引用”不会被当成无引用。现在靠的是“启动时没有打开的窗口”这个前提（见 `MediaRecycleLifecycle.opened` 的检查），挪到后台就没有这个前提了，需要改成读取打开中的文档的实时引用，或者只在没有任何文档打开时推进。**这一点是整个改动里最容易出事故的地方，先写设计再动手。**
- `check:media-recycle` 门禁和 [t192-全局媒体回收](../架构体检修复/t192-全局媒体回收.md) 记录了当初的取舍，动手前先读。
- 第 3 步的判断条件要和触发器的 `WHEN` 条件用同一份实现，避免两边不一致。

### 怎么验证

- 新建隔离资料目录，造 1 万条设置改写，确认候选表不增长。
- 用真实资料目录的副本跑迁移，核对候选从 1.5 万降到几十条，数据库执行 `VACUUM` 后体积回到几十 MB。
- 启动日志里出现 `media_recycle.sweep.completed`，且“界面加载完成”的时间点提前约 3 秒。

## D2（P0）单实例、全局异常兜底、启动失败提示

### 现象

1. 全仓没有 `requestSingleInstanceLock`。双击两次图标会起两个完整的应用，共用同一个数据库和同一批文档。
2. 主进程没有注册 `uncaughtException` / `unhandledRejection`。主进程里漏掉的异常不会进应用日志；未捕获异常时 Electron 弹的是英文原生报错框。
3. [index.ts:137](../../../electron/main/index.ts) 的 `app.whenReady().then(async () => { ... })` 没有 `catch`。里面只对“数据库版本太新”这一种错误弹了提示，其他启动错误（数据目录没权限、磁盘满、迁移失败）会变成一个没人接的拒绝：**进程活着，没有窗口，没有任何提示。**

### 为什么排 P0

10-21 真实资料目录出过一次数据库损坏（主文件和日志文件不同步，目录里还留着 `henji.db.backup-20261021-malformed`）。[db-recovery.ts:8-9](../../../electron/main/services/db-recovery.ts) 的注释写明“起因未能确认”。多个进程同时操作同一份数据是这类损坏最常见的来源之一：SQLite 本身支持多进程，但启动时的自检失败恢复会把数据库文件改名换掉（`restoreDatabaseFromSnapshot`），另一个实例正开着它时后果不可预料；启动回收、迁移也都假设只有自己一个。

这不是说已经确认损坏是双开造成的，而是：原因不明的情况下，先把最常见的那扇门关上。

### 建议做法

1. **单实例锁**：带窗口的正常启动先 `app.requestSingleInstanceLock()`，拿不到就退出；第一个实例收到 `second-instance` 时把主窗口显示并聚焦。
   - 助手命令行（`assistant:cli`）和 `--verify-model` 是有意与主应用并存的（日志里外部连接接线员有 `standby` 状态），**不参与这把锁**。
   - 自动化隔离运行（`HENJI_ISOLATED_APP_DATA`）用的是另一份数据目录，Electron 的锁按用户数据目录区分，天然不冲突；改完跑一次 Reality 确认。
   - 开发版和正式构建目前共用真实资料目录。要不要互斥由用户决定；建议互斥，因为它们的数据库迁移版本可能不同（日志里已经出现“这份助手模型配置由更新版本的痕迹AI创建”的报错）。
2. **命令行模式不做破坏性恢复**：命令行启动时如果数据库自检失败，只报错退出，不执行“隔离损坏文件并换上快照”，这件事留给带窗口的主实例。
3. **主进程全局兜底**：注册 `process.on('uncaughtException')` 与 `process.on('unhandledRejection')`，写进现有日志（域名建议 `main.errors`，和渲染层的 `app.errors` 对应）。不要吞掉后继续跑业务：记录之后，未捕获异常按现在的行为处理即可。
4. **启动失败要看得见**：给 `whenReady` 链加 `catch`，记录日志，用 `dialog.showErrorBox` 显示中文原因和日志目录位置，然后 `app.exit(1)`。

### 注意事项

- 单实例锁要放在 `app.whenReady()` 之前、数据库打开之前。
- macOS 上从访达再次打开应用走的是 `activate`，不是 `second-instance`，两条路都要测。
- 第 4 步的提示文案用用户能看懂的话，不要直接贴堆栈；堆栈进日志。

### 怎么验证

- 连续启动两次：第二次不出现新窗口，第一个窗口被带到前台。
- 把数据目录设成只读后启动：出现错误提示框，进程退出，日志里有记录。
- 主应用开着时跑 `npm run assistant:cli -- --goal "列出项目"`，两边都正常。

## D3（P1）旧版本文件每次读取都重做“升级前备份”

### 现象

两天日志里 `persistence.backup.start` 出现 1894 次：

| 格式 | 次数 |
|---|---|
| 项目文件 `project.json` 第 2 版 → 第 3 版 | 1436 |
| 音频工程 `.hjaud` 第 6 版 → 第 7 版 | 404 |
| 音频工程第 3 版 → 第 7 版 | 48 |
| 助手模型配置第 1 版 → 第 2 版 | 6 |

其中同一个文件 `D:\视频制作\2026-10-23_元宝搜索\project.json` 被备份了 1396 次。

### 原因

读取旧版本文件时，[stored-file.ts:16-21](../../../electron/main/services/persistence/stored-file.ts) 先调 [backupBeforePersistenceUpgrade](../../../electron/main/services/persistence/file-upgrade.ts)，然后在内存里升级内容返回，**升级结果不写回磁盘**。所以文件一直是旧版本，下次读取再来一遍。

备份本身是按内容寻址的，不会堆出一堆重复文件，但每次都要：把原文件整份复制到临时文件 → 算一遍哈希 → 发现目标已存在 → 再把已有备份读一遍算哈希比对 → 删临时文件。项目文件很小无所谓；音频工程和图片文档包走同一条路，文件大了每次读取都是双倍的磁盘读写。

### 建议做法

二选一，推荐第一种：

1. **升级成功后写回**。读到旧版本并升级成功后，把新版本内容原子写回原文件（写临时文件再改名），之后的读取就是当前版本，不再触发备份。只读位置（权限不足、只读介质）写回失败时退回现在的行为并记一条日志。
2. **先查再备份**。备份前先流式计算原文件哈希，目标备份已存在就直接返回，不复制。这样仍然每次读都要升级，但省掉一半读写。

### 注意事项

- 写回会改变“打开旧文件不改动它”的行为。旧版本应用打不开新格式是预期的（persistence.md 规定新版本可读旧格式，没有要求反过来），但要确认备份文件确实已经落盘再写回。
- 文档有跨进程锁（`DocumentStore`），写回必须在持锁的路径里做。索引扫描这类只读路径不要写回，只在真正打开文档时写回。
- 项目文件 1436 次里大部分来自启动时的文档索引扫描和助手读取，方案 2 对这部分同样有效；两种方案可以都做。

### 怎么验证

- 打开一份第 6 版音频工程后关闭，再次打开，日志里不再出现 `persistence.backup.start`。
- 黄金样本测试继续通过。

## D4（P1）数据库日常开销随体积上涨

### 现象

- **启动自检**：[db-recovery.ts:31](../../../electron/main/services/db-recovery.ts) 的注释写着“几 MB 的库只需几毫秒”。现在数据库是 166 MB，对最新快照实测 `quick_check` 用了 2.37 秒（冷读）。启动日志里从进程起来到 IPC 注册完，13 次带窗口启动在 1.1–2.5 秒之间。
- **每日快照**：`VACUUM INTO` 在主进程同步执行。有快照的那次启动（19:07），这一段是 5.09 秒，比平时多 3 秒以上。
- **快照占用**：保留 7 份，每份约 160 MB，共 1.1 GB；加上迁移前备份，`backups/` 目录 1.2 GB。
- ~~没有设置 `busy_timeout`~~（更正：better-sqlite3 默认就会等 5 秒，这一条不成立）。

### 建议做法

1. 先做 D1、D5。数据库回到几十 MB 以内，这一条的问题会自动缩小一个数量级。
2. 快照挪到窗口显示之后执行，用 better-sqlite3 的在线备份接口（`backup()`，异步、分页进行，不长时间占住主进程），不要在启动路径上同步 `VACUUM INTO`。
3. 启动自检保留，但数据库超过一定体积时把完整自检放到后台，启动时只做打开和版本检查。损坏的典型表现（打不开、迁移报错）本来就会在打开阶段暴露。
4. （已取消：默认已有 5 秒等待。）
5. 快照保留策略改成按体积封顶，或“最近 3 天每天一份 + 更早的每周一份”。

### 注意事项

- 第 3 步是在“启动快”和“尽早发现损坏”之间取舍。10-21 出过真实损坏，不建议去掉自检，只是别让它挡在窗口前面。后台自检发现问题时要能提示用户重启恢复。
- 在线备份期间数据库照常可写，备份的是开始时刻的一致状态，这是这个接口的保证，不需要额外加锁。

### 怎么验证

- 启动日志里“进程启动 → 界面加载完成”的时间在有快照和没有快照的日子里基本一致。
- 手动破坏一份数据库副本，确认仍能被发现并从快照恢复。

## D5（P2）设置表当缓存用，调用记录永久保留

### 现象

- `settings` 表 1302 行里 1291 行是 `cache.video-edit.code-metadata.v1:*`，没有淘汰机制，代码素材每改一个版本就多一条。
- `application_invocations` 2922 行、33 MB，一个月攒下来的。[operationStore.ts:117](../../../electron/main/services/application-runtime/operationStore.ts) 的注释写明“助手事实与在途请求永久保留”，只清理界面发起的付费收据。
- `audio_edit_tasks` 380 行、9.9 MB，单条结果最大 0.95 MB。

### 建议做法

1. 缓存搬出设置表（见 D1 第 1 步），并加上限：按最近使用时间保留最近若干条或若干 MB。
2. 助手调用记录设保留期：终态记录保留 14 天，超期删除（原定 30 天，但按 30 天这张表会稳定在 35–40 MB，且现有最老记录才 26 天）。撤销引用、付费账本、在途恢复真正需要的那部分先确认清楚再定范围。
3. 音频任务的大结果改存文件，表里只留路径；或同样设保留期。

### 注意事项

- 第 2 步改变了“永久保留”的既有决定，属于行为变化，先和用户确认保留多久。付费账本的每日额度统计（`generationSpendSince`）依赖这张表，清理条件不能碰当天的记录。
- 助手的撤销引用（`undoRef`）如果指向已清理的记录，要返回明确的“已过期”，不能报内部错误。

## D6（P2）画布文档里存了程序目录的缩略图路径

### 现象

日志里 `documents.content.program_references` 警告两天出现 17 次，例：画布文档 `f21fcef6-…` 里保存着 `C:\Users\…\AppData\Local\com.henji.ai\Henji-AI\Thumbnails\16f3….webp`。应用自己的警告文案已经说明后果：“换位置或拷给别人后会失效”。

### 建议做法

1. 找到是哪条路径把缩略图的程序目录地址写进了节点数据（从这份文档里该节点的类型入手查写入方）。缩略图是可重建的派生物，文档里应该只存原始媒体的引用，缩略图由原始媒体现算。
2. 读取时对已有文档做一次修正：遇到程序目录缩略图路径就丢弃该字段，按原始媒体重新生成。
3. 现在只是警告。等写入方修掉后，把这条检查升级成保存前的断言，防止再出现。

### 注意事项

- 这是落盘内容的变化，按 [persistence.md](../../rules/persistence.md) 判断是否需要升格式版本。只删一个可选的派生字段，一般不需要提高最低可读版本。
- 修之前先确认这 17 次是同一份文档反复读取，还是多份文档都有，决定影响面。
