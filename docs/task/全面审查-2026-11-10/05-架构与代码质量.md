## P1（P2）字体目录两天扫描 617 次

### 现象

`fonts.scan.start` 两天出现 617 次。每次扫描读 1756 个字体，耗时约 0.6 秒（例：22:04:20.548 开始，22:04:21.141 完成），并且每次都报出同样 5 个解析失败的文件。

[service.ts](../../../electron/main/services/fonts/service.ts) 对字体目录做了文件监听，有变动就标记为“需要重扫”。扫描次数这么多，说明要么监听被频繁触发（系统字体目录本身常有无关的文件变动），要么每次界面重新加载都触发了一次完整扫描。开发版界面重载很频繁，正式版会少很多，但机制一样。**具体是哪种需要看一下调用方，本次没有查到底。**

### 建议做法

1. 先在日志里给扫描加上触发原因（首次、监听到变动、界面请求），跑一天看分布。
2. 监听回调里只对字体扩展名的文件变动做标记，并做防抖（比如 2 秒内的多次变动合并成一次）。
3. 目录内容没变（文件名、大小、修改时间的清单一致）时直接用上次的结果。目录下已有 `catalog-cache.json`，确认它在重扫时有没有被用上。
4. 解析失败的字体按路径和修改时间记住，下次跳过。

### 注意事项

- 扫描在 Worker 里（`worker.ts`），不卡主进程，所以这是资源浪费问题，不是卡顿问题，优先级不高。

## P2（P2）日志噪声与没有语义的事件名

### 现象

- 两天日志共约 4.3 万条、24 MB。其中 `application.capability.execute.start/completed` 各约 1.07 万条、`mcp.read.start/completed` 各约 1.06 万条，这四种加起来就占了一半，全部是 `info` 级别。
- `info.event` 1291 条、`error.event` 3 条、`warn.event` 1 条：这些是调用方没有给事件名时的兜底（[logger.ts:155](../../../src/core/logging/logger.ts)、[push.ts:39](../../../electron/main/services/logging/push.ts)），按事件名查日志时查不到它们。
- 视频解码的 FFmpeg 输出 320 条全部记成警告（`video_decoder.native.ffmpeg.log`），真正的警告被淹没。
- 部分失败日志缺原因，见 [03 的 A2](03-助手与产品.md#a2)。

### 建议做法

1. 高频的成对日志降级：只读能力的 `start` 降到 `debug`；`completed` 只在耗时超过阈值或失败时记 `info`。写入类能力保持现状。
2. 找出 1291 条没有事件名的调用方（按 `domain` 分组统计一下就能定位），补上事件名；然后把“缺事件名”做成开发检查模式下的警告。
3. FFmpeg 的输出按它自己的级别映射，普通信息记 `debug`。

### 注意事项

- 降级前确认 `logs:query --chain` 按运行链路查问题时不依赖这些 `start` 条目；依赖的话保留链路上的关键一条。
- 助手的运行追踪（`application_model_traces`）是另一套，不受影响。

## P3（P2）吞掉错误的写法 533 处

### 现象

形如 `.catch(() => {})`、`.catch(() => undefined)` 的写法全仓 533 处（不含测试），分布：

| 位置 | 处数 |
|---|---|
| `src/features/videoEdit/engine` | 91 |
| `electron/main/services/image-editor-v3` | 59 |
| `electron/main/services/documents` | 53 |
| `src/features/videoEdit/application` | 41 |
| `electron/main/services/web-source` | 31 |
| `electron/main/services/web-replay` | 22 |
| 其余 | 236 |

其中很多是合理的（清理临时文件、关闭已经关闭的句柄、取消后不关心结果）。问题在于合理的和不合理的写法一样，读代码时分不出来；而文档服务、图片编辑后端这些涉及用户数据的地方，吞掉一个写入或改名的失败可能意味着静默丢数据。AGENTS.md 也明确写了“禁止吞错”。

### 建议做法

1. 提供两个有名字的小工具替代匿名吞错，让意图写在名字里：
   - “尽力清理”：失败只记 `debug` 日志。用于删临时文件、关句柄。
   - “忽略取消”：只吞取消类错误，其他照常抛出。
2. 按风险分批替换，先做 `electron/main/services/documents`（53 处）和 `image-editor-v3`（59 处）：逐处判断是清理、取消，还是其实应该上报。
3. 加一条 lint 规则禁止新增空的 `.catch`，存量记基线，只减不增。

### 注意事项

- 这是逐处判断的活，不能批量替换。每一处都要看被吞的那个操作失败了意味着什么。
- 剪辑引擎那 91 处多数在渲染热路径上，换成带日志的版本时注意不要每帧打日志。

## P4（P3）存量命名与文件体积

### 现象

- 死代码基线里记着 3112 处命名问题，1842 处在图片编辑（`ImageEditorV3`、`withImageEditDocumentInstanceV3`、`image-editor-v3` 等）。AGENTS.md 规定命名不带迭代版本号，旧方案早已删除，“V3”现在只是历史痕迹。
- 最大的源文件：`videoEditRenderer.ts` 2866 行，其后是 `videoEditService.ts` 1362 行、`web-source/page.ts` 1336 行、`videoEditNativeFrameSource.ts` 1278 行、`videoEditThreeSpace.ts` 1256 行、`VideoEditPreview.tsx` 1186 行。

### 建议做法

- 命名：按既有规则“改到哪个文件就清到哪个文件”，不专门做全量改名。唯一建议集中做的是 IPC 通道名和落盘目录名之外的**导出符号**，等图片编辑下一次有较大改动时顺带做一批。落盘目录 `ImageEditorV3` 和持久格式里的名字不要动。
- 大文件：不按行数拆。`videoEditRenderer.ts` 下次要改时先看它是不是同时承担了“调度、资源管理、合成”几种职责，是的话按职责拆；只是长而内聚就不动。

## P5（P3）零散小项

逐条都很小，碰到相关文件时顺手处理：

1. **硬件解码探测疑似每次启动都重跑**。有按显卡和驱动版本的指纹缓存（`hardware-capabilities.ts`），但两天里探测日志出现在十几次启动中，每次都因为 AV1 4:4:4 样片解不出来而记 2 条警告和一批 FFmpeg 输出。先确认缓存为什么没命中（可能是开发版与正式构建交替运行导致指纹或版本号不同）。“这种格式本机不支持”是探测的正常结论，不应记成警告。
2. **`as unknown as` 271 处**、**`.find(...)!` 221 处**：都是绕过类型检查的写法。不需要专项清理；新代码避免，改到时修。
3. **`electron/main/index.ts` 里的小瑕疵**：命令行模式退出前有一个只含一个元素的 `Promise.race`（原意应该是“等 5 秒”），直接写成等待即可。
4. **`pending_task_results` 表不清理**：104 行、体积很小，注释说明是有意保留用于恢复。可以给已经确认保存进历史的记录设个保留期，不急。
5. **`web-source/page.ts:601`** 的导航拦截里 `new URL(url)` 对非法地址会抛错；包一层，解析失败就直接拦掉。
6. **开发版与正式构建共用真实资料目录**：日志里出现过“这份助手模型配置由更新版本的痕迹AI创建，请升级后再打开”（提示词优化按钮加载配置失败 3 次），原因是开发版先把配置升到了新版本，之后运行的旧正式构建读不了。对最终用户没有影响，但对日常开发是个坑。可以让开发版默认用独立的资料目录，需要真实数据时再显式指定；这会改变现在“开发版用真实数据”的习惯，由用户决定。
