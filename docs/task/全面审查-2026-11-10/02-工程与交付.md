## E1（P0）CI 连续两天红

### 现象

`gh run list` 最近 60 次“Build Henji-AI”：失败 42 次，取消 16 次，成功 2 次。11-09 全天 26 次有结果的运行全部失败。

最近一次（11-09 22:02 UTC）失败的作业：

- **代码检查**：`check:ui-design` 报 1 个问题——`src/features/canvas/nodes/VideoNode.tsx:236` 用了不在间距档位里的 `pt-9`。
- **普通单元测试 1/3、2/3、3/3** 全部失败，涉及 11 个测试文件：
  - `src/App.developmentGallery.test.tsx`
  - `src/features/devGallery/uiGalleryCoverage.test.ts`
  - `src/components/ui/layout.test.tsx`
  - `src/components/ui/motionIntegration.test.tsx`
  - `src/components/ui/motionConsumers.test.ts`
  - `src/workspaces/GenerationWorkspace/application/visibleGenerationTaskCommand.test.ts`
  - `src/features/canvas/application/generationNodeExecutor.test.ts`
  - `src/features/canvas/application/canvasGenerationTaskService.test.ts`
  - `src/features/developer/sdkModelInventory.test.ts`
  - `src/features/application-control/mcpIntegration.test.ts`
  - `electron/main/services/mcp/skills.test.ts`
- 质量门禁因此不通过，安装包构建被跳过。

其余作业（原生 SQLite、WebGPU 像素、大图导出、原生录音、视频解码）是绿的。

### 为什么排 P0

现在的做法是每次提交直接推送、不等 CI。这本身没问题，但前提是有人在红的时候去看。连续两天红意味着：这两天里任何新引入的失败都被原有的红盖住了，门禁形同虚设。同一时期的开发日志里也能看到没有被拦住的问题：能力说明超过 1000 字导致应用宿主初始化失败（9 次）、引用了未定义的常量导致界面整体崩溃（多次）。

### 建议做法

1. 先修到绿。间距那一处是一行改动；11 个测试文件按 [testing.md](../../rules/testing.md) 的原则逐个判断——测试在保护真实行为就修代码，测试只是抄了清单或钉死了合法变化就改或删测试。从文件名看，生成任务、画布执行那几条大概率对应最近的生成与画布改动（参考素材合并、自动缩放、连线吸附），界面样张覆盖那几条大概率是新增组件没有登记进样张。**这是推测，以实际失败信息为准。**
2. 定一条规矩并写进 AGENTS.md：推送后 CI 红了，下一次开工先修 CI，再做别的。不需要挂着会话等 CI，只需要开工时看一眼 `gh run list --limit 1`。
3. 给“应用能力注册”补一个快速检查：所有内置能力的说明长度、结构校验在单元测试里跑一遍。现在是运行到界面里才抛错，把整个应用带崩。

### 注意事项

- 不要为了变绿而跳过或删除测试；也不要因为测试“碍事”就放宽门禁阈值。
- CI 日志里还有两条和失败无关的警告，顺手处理：Node 20 的 Action 已弃用（`actions/checkout@v4`、`actions/setup-node@v4` 升到新版本）；子模块警告见 E6。

## E2（P1）启动包里带着 TypeScript 编译器，且没有压缩

### 现象

`out/renderer/assets` 里启动必经的两个脚本：`index-*.js` 4.6 MB、`App-*.js` 16.6 MB（377,730 行）。

- `App` 这个包里有完整的 TypeScript 编译器（能搜到 `checkSourceElement`、`Diagnostics.This_syntax_is_not_allowed_when_erasableSyntaxOnly_is_enabled` 这些编译器内部符号）。来源是这些文件顶部的静态导入 `import ts from 'typescript'`：
  - `src/core/videoEdit/codeEffectReview.ts`
  - `src/core/videoEdit/codeTrackReview.ts`
  - `src/core/videoEdit/codeMaterial/` 下的 `componentValidation.ts`、`fileEdits.ts`、`projectClosure.ts`、`textCoverage.ts`、`textFonts.ts`
  - `src/features/videoEdit/application/videoEditReview.ts`
  - `src/features/videoEdit/engine/videoEditAuthorBundle.ts`

  这些模块被助手能力注册一路静态引用到了首屏。结果是：用户哪怕只是打开应用生成一张图，也要先解析一遍 TypeScript 编译器。
- 产物没有压缩：带完整缩进、换行和 1350 行注释。`electron.vite.config.ts` 和打包脚本里都没有 `minify` 设置。整个 `out/renderer` 117 MB，安装包按 `out/**` 原样收进去。

### 影响

每次启动多解析十几 MB 脚本，占内存；安装包偏大（10-03 的安装包 230 MB）。本机日志里的“界面加载”时间全是开发版的数字（30–50 秒，那是开发服务器的开销），**正式构建的实际启动耗时这次没有测到，动手前先用 `electron:prod` 量一个基线。**

### 建议做法

1. 把上面这些文件里对 `typescript` 的使用改成用到时再加载：函数内 `const ts = await import('typescript')`，或者把整段审查逻辑移进已有的 `videoEditCodeCompiler` Worker（那个 Worker 本来就带着编译器，12 MB）。后者更干净：主线程完全不碰编译器，审查也不会卡界面。
2. 在依赖图门禁的“首屏”检查里加一条：首屏包不得包含 `typescript`、`three` 这类大库。现在的门禁有 `firstScreen` 一项，但没拦住这个。
3. 渲染层正式构建打开压缩。`build.minify` 用 esbuild；如果有代码依赖函数名或 `Function.prototype.toString`（作者代码运行时、Worker 序列化之类），先用 `keepNames` 保住名字，再逐步收紧。
4. 首屏脚本瘦身后，把“首屏包体积”记进性能工作流，超过阈值就报。

### 注意事项

- 第 1 步会把同步函数变成异步，调用链上的签名要跟着改。优先选“移进 Worker”，对调用方来说本来就是异步的。
- 第 3 步开压缩后必须跑一遍真实窗口的冒烟（`electron:smoke`）和代码素材渲染，压缩最容易弄坏的就是按名字找东西的代码。
- 这条和 2026-10-26 的决定（开发版行为贴近正式版）不冲突：压缩只影响正式构建。

### 怎么验证

- `App-*.js` 里搜不到 `checkSourceElement`。
- `electron:prod` 启动到界面可用的时间，改动前后各量三次对比。

## E3（P2）工具链版本落后

### 现象

| 依赖 | 当前 | 说明 |
|---|---|---|
| Vite | 4.5.14 | 已停止维护的大版本 |
| ESLint | 8.57.1 | 已停止维护 |
| Vitest | 1.6.1 | 落后多个大版本 |
| React | 18.3.1 | 可用，不急 |
| Tailwind CSS | 3.4.18 | 可用，不急 |
| Electron | 44.9.3 | 新 |
| TypeScript | 5.9.3 | 新 |

CI 用 `npm ci --force` 安装，说明依赖之间有被强行忽略的版本冲突。

### 建议做法

1. 先查 `npm ci`（不带 `--force`）报什么冲突，逐个解决，去掉 `--force`。
2. Vitest 与 Vite 一起升：测试有 2286 个文件，升级后单测速度通常有明显改善，对“别跑太多测试、别吃满 CPU”的诉求有直接帮助。
3. ESLint 升到 9 需要改成扁平配置，独立做一次。
4. React 19、Tailwind 4 改动面大，没有明确收益前不动。

### 注意事项

- electron-vite 3.1 对 Vite 版本有要求，升 Vite 前先确认它支持的范围，可能要一起升。
- 这类升级不涉及功能，适合单独一组提交，升完跑一次完整的 `electron:build` 和冒烟。属于 L3 级验证，后台跑。
- 项目里有 4 个补丁（`patches/`），升级相关包时要确认补丁还能打上，尤其是 `@xyflow/react`。

## E4（P2）规则文档过大、与实际不符

### 现象

- `docs/rules/assistant-status.md` 293 KB。AGENTS.md 规定“智能助手的任何改动”动手前必读它，但这个体积一次读不完，实际执行时只能读一部分，等于规则无法遵守。
- `docs/rules/testing.md` 40 KB，同样偏大。
- `docs/task/代码效果与渲染改进/以后再做.md` 77 KB、`制作进度.md` 50 KB，“压缩后先读它”的成本越来越高。
- AGENTS.md 写“Electron 42”，实际安装的是 44.9.3。
- AGENTS.md 本身 38 KB，每次会话都要全部加载。

### 建议做法

1. `assistant-status.md` 拆成“当前状态总表”（控制在 20 KB 内，只放通/不通与欠账）加“历史记录”分文件。必读的只是总表。
2. 进度类文档定期归档：已完成的条目移到 `归档/` 下按月存放，主文件只留未完成和最近两周的。
3. AGENTS.md 里的版本号改成“以 package.json 为准”，不写死数字；带日期的决定记录超过一个月且已成为常态的，改写成普通规则，去掉日期和来历。
4. 给规则文件设体积上限（比如 30 KB），加进 `check:skill-sync` 同类的轻量检查里。

### 注意事项

- 拆分时不要改规则的内容，只动结构；拆完用搜索确认其他文档里指向它的锚点链接没有断。

## E5（P2）发布链路一个多月没有演练

### 现象

`release/` 里最新的安装包是 10-03 生成的 `henji-ai-setup-2.0.0-beta.1.exe`。之后主分支有一千多个提交，包括原生录音、原生视频解码、网页录制重演等带原生二进制的改动。CI 的安装包构建作业只在打标签或手动触发时运行，而且前置的质量门禁现在是红的（E1），所以这段时间没有任何一次完整打包。

### 影响

离正式版越近才发现打包问题，代价越大。原生依赖（ASIO 录音、FFmpeg、ONNX、koffi、uiohook）在 `asarUnpack` 和按平台过滤的清单里都有手写条目，新增依赖漏登记的话只有装出来跑才会暴露。macOS arm64 的包更是只能靠 CI 出。

### 建议做法

1. E1 修绿后，手动触发一次带 `build_installer` 的工作流，Windows 和 macOS 各出一个包。
2. Windows 包在本机装一遍，跑 `electron:smoke`，再手动过一遍：录音、导入一个视频进剪辑、导出、生成一张图。
3. 之后每周或每个里程碑固定出一次包，不等到发版。
4. 把安装包体积记下来做趋势。

### 注意事项

- 不签名是已定的决定，不在这里重提。
- macOS 包按已有约定由用户在真机上自测。

## E6（P3）仓库卫生

### 现象

- `tickets/` 下有 4.2 GB 没有被 Git 跟踪、也没有被忽略的验收证据（`.rgba`、`.half` 原始像素文件等），`git status` 列出 246 条未跟踪项。一次 `git add tickets/某目录` 就可能把几百 MB 提交进去。
- `docs/` 目录 4.0 GB。
- `docs/others/gegl`、`docs/others/gimp` 是两条子模块记录，但仓库里没有 `.gitmodules`。CI 每次清理都报 `fatal: No url found for submodule path 'docs/others/gegl'`；别人带 `--recursive` 克隆会失败。
- 根目录有 `nul`（Windows 下命令重定向写错留下的）、`tmp-electron-dev.*.log`（6 月的）。都已被忽略，不影响提交，但可以删。

### 建议做法

1. `.gitignore` 加上 `tickets/**/evidence*/` 以及 `*.rgba`、`*.half`。证据文件验收完就删，或挪到仓库外。
2. 两条子模块记录：只是参考源码的话，`git rm --cached docs/others/gegl docs/others/gimp` 去掉记录，把目录加进忽略。
3. 删除根目录的 `nul` 和两个临时日志。
4. 看一下 `docs/` 里 4 GB 是什么：如果是参考视频和截图，同样考虑挪到仓库外或加忽略。

### 注意事项

- 删 `nul` 在 Windows 上要用 `\\?\D:\VibeCode\Henji-AI\nul` 这种路径，或在 Git Bash 里 `rm nul`，资源管理器删不掉。
- 第 2 步之前确认这两个目录里没有本地改动需要保留。
