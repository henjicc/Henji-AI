# 运镜控制简易模式 · 重要记录

## 记录 001：简易模式核心形态 = 镜头卡（场景快照）模型

- 日期：2026-07-10
- 状态：已确定
- 背景：现有 AE 式关键帧时间轴对非专业用户门槛过高，需要"快速随手出片"的创作模式。调研了 PowerPoint Morph / Figma Smart Animate / Keynote Magic Move（两状态+自动补间）与 Unity Cinemachine（程序化运镜行为）。
- 最终决定：简易模式的时间轴是一排"镜头卡"，每卡 = 全场景可动画状态快照 + 停留时长 + 到下一卡的过渡时长；过渡由编译器差异检测后自动生成；卡片数据编译为现有 StageTrack 关键帧，播放/导出链路复用。附带三项增强：每卡停留时长（hold）、每对象错峰延迟（delay）、摄像机运镜行为预设（替代纯位置插值）。
- 选择原因："两状态自动补间"是被亿级用户验证的小白范式；编译式架构让现有采样/播放/导出引擎零改动；运镜预设解决环绕等两点插值做不出来的镜头，也消除环绕方向/角度歧义。
- 影响任务：全部。

## 记录 002：角色动作随时间切换的机制

- 日期：2026-07-10
- 状态：已确定
- 背景：`StageCharacterMotion` 是对象属性、不可打关键帧；自动走跑要求过渡期间临时播放走/跑 clip、到达后恢复，需要"motion 随时间变化"的新机制。
- 最终决定：采用方案 A。`StageSceneAnimation` 增加 `motionSchedule` 旁路时间表；每项记录角色、起止时间、过渡动作和到位后的目标卡动作。`CharacterModel` 按 currentTime 解析动作并继续用 `AnimationMixer.setTime` 确定性 seek；位置与朝向仍走既有关键帧轨道，不新增 motion 轨道类型。
- 选择原因：保持 `keyframeEngine`、专业时间轴和属性注册表不感知离散动作类型，改动面最小；时间表跟随 animation 一起持久化、播放和导出 seek，同一时间解析结果确定；`afterMotion` 明确表达“到达后恢复目标卡 motion”，避免依赖当前 store 对象的偶然状态。3.2 烘焙时需保留时间表，或在专业模式支持离散动作轨道后再显式转换。
- 影响任务：1.4、2.1（schedule 存放）、3.2（烘焙时 schedule 的归宿）。

## 记录 003：环绕（orbit）预设的终点语义

- 日期：2026-07-10
- 状态：已确定
- 背景：环绕预设"角度驱动"（转多少度由参数定）与"两卡机位驱动"（终点=下一卡机位）存在冲突：用户在 B 卡摆的摄像机位置和环绕几何落点可能不一致。
- 最终决定：选了非 direct 运镜预设后，本段过渡摄像机终点由编译时的几何计算决定，直接覆盖/忽略 B 卡快照里摆放的机位；不做"UI 选中运镜后自动把 B 卡机位吸附到落点"这类交互层同步方案（一期不做）。该决定统一应用到全部 5 种非 direct 预设（orbit/dollyIn/dollyOut/truck/crane），不仅是 orbit。
- 选择原因：几何驱动是运镜预设存在的意义——环绕/横移这类效果本来就无法靠"随便摆两个机位再插值"做出正确弧线/平移，如果终点还要看 B 卡机位，预设参数（degrees/offset/height 等）会变得没有意义或与机位产生冲突歧义；同时几何覆盖已经保证渲染结果正确，是否在 UI 上同步显示/提示落点是 2.3 的呈现问题，不影响编译层的正确性与一致性。不选"自动吸附机位"方案是因为那会让简易模式再引入一层"卡片数据被静默改写"的心智负担，一期先用最简单、最可预测的"几何为唯一权威来源"规则。
- 影响任务：1.3（已按此定稿实现，编译集成测试已覆盖）、2.3（细节层 UI 需要提示用户"启用运镜预设后终点由预设参数决定，与本卡摆放位置无关"）。

## 记录 004：镜头卡缩略图一期不做真实截图

- 日期：2026-07-10
- 状态：已确定
- 背景：卡片带真实场景缩略图最直观，但需要离屏捕获（依赖 captureRef，且每次自动记录都要重截）、存储与失效管理，成本不小。
- 最终决定：一期卡片显示序号+名称+时长，不做真实截图缩略图；二期再评估（可复用 `export/cameraStageScreenshot.ts` 的捕获链路）。
- 选择原因：不阻塞核心闭环；自动记录高频写卡时重复截图有性能风险。
- 影响任务：2.2。

## 记录 006：效果器为采样层确定性叠加，不产生关键帧

- 日期：2026-07-10
- 状态：已确定（具体叠加落点 3.1 执行时定稿并回填此记录）
- 背景：手持晃动等程序化效果若编译成密集关键帧会导致轨道爆炸且烘焙后不可维护；实时随机数会造成导出与播放不一致。
- 最终决定：效果器是挂在摄像机对象上的持久化参数（kind/enabled/intensity/frequency），偏移由 time 的纯函数（正弦叠加/hash 噪声）在采样/渲染层计算叠加，覆盖播放、scrub、导出三条路径；偏移不写入工程存档的 transform。一期仅摄像机（handheld/breathing），数据结构按任意对象可挂设计。
- 选择原因：确定性保证导出一致；不污染关键帧数据；专业模式可直接复用同一能力。
- 影响任务：1.1（字段）、3.1（实装）。

## 记录 007：模式与数据关系 = 工程锁定 + 单向烘焙

- 日期：2026-07-10
- 状态：已确定
- 背景：简易（shots 派生 animation）与专业（直接编辑 animation）两套权威数据不能双向同步——专业模式改了关键帧无法可靠还原回卡片。
- 最终决定：工程创建时定模式（默认简易）；简易可单向烘焙为专业（清 shots、固化 animation、清撤销历史），不可逆；专业不能转简易；v10 及以下旧工程一律视为专业。选中卡片时场景改动**自动记录**进卡（不设"更新片段"按钮），靠撤销兜底。
- 选择原因：数据单一权威来源最稳；保住"简易起稿、专业精修"路径；自动记录贴合"快速随手做"的定位。
- 影响任务：1.1、2.1、2.4、3.2。
