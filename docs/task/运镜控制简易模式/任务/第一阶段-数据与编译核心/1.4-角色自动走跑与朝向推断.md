# 1.4 角色自动走跑与朝向推断

## 任务状态

- 状态：已完成
- 所属阶段：第一阶段-数据与编译核心
- 前置任务：1.2
- 关联任务：2.3（细节层可覆盖推断结果）、重要记录 002（动作时间表机制）
- 是否可以并行：可与 1.3 并行

## 任务目标

两张相邻镜头卡之间角色位置发生位移时，编译器自动产出：① 朝向关键帧（面朝移动方向，到达后转回目标卡朝向）；② 一份"动作时间表"（过渡期间按位移速度播放 走路/慢跑/冲刺 循环动作，到达后恢复目标卡的 motion），并打通播放端消费该时间表。用户在细节层可用 `motionOverride` 覆盖（UI 在 2.3，本任务保证数据通路）。

## 当前情况

- 角色动作 `StageCharacterMotion`（`domain/characterMotion.ts`）：`{ mode:'pose' } | { mode:'clip', clipName, speed }`，是**对象属性，不可打关键帧**。内置动作含 `Walk_Loop`（走路）、`Jog_Fwd_Loop`（慢跑）、`Sprint_Loop`（冲刺）、`Idle_Loop`（待机）。
- 动作播放端：`scene/CharacterModel.tsx`（188 行）按对象的 motion 字段驱动 GLB AnimationMixer——**执行本任务前必须先读该文件确认 clip 切换/速度机制**。
- 朝向是普通的 `transform.rotation.y` scalar 轨道，编译器（1.2）已能写。
- **关键设计缺口（重要记录 002，状态待确认）**：motion 随时间切换目前没有任何机制。两个候选：
  - 方案 A（推荐）：编译器额外输出 `motionSchedule: Array<{ objectId, from, to, motion }>`，作为编译产物的旁路数据存 store（非轨道）；`CharacterModel` / `StagePlaybackDriver` 播放和 scrub 时按 currentTime 查表决定生效 motion。不动关键帧引擎。
  - 方案 B：把 motion 变成可动画属性（step 插值的新轨道类型）。改动面大（animatableProps/keyframeEngine/时间轴 UI 都要认识新类型），且烘焙到专业模式后轨道语义怪异。
  - 本任务执行时先与用户确认或按方案 A 落地并更新重要记录 002 为"已确定"。
- 速度→动作映射需要阈值：位移距离/过渡时长 = 平均速度（米/秒）。阈值定为常量并写注释（初值建议：<0.1 不触发；0.1~1.8 走路；1.8~4 慢跑；>4 冲刺），数值执行时可调。

## 实施方案

新建 `domain/characterTransitionInference.ts`（纯函数）：

- `inferCharacterTransition(fromState, toState, transitionDuration)` → `{ facingYawKeyframes, motion: StageCharacterMotion | null }`：
  - 位移向量水平分量 → 目标朝向 yaw（`Math.atan2`，角度制，与现有 rotation 存储一致）；注意选最短旋转路径（±180° 归一）。
  - 平均速度 → 按阈值选 Walk/Jog/Sprint clip；clip 的 speed 参数可按速度比例微调（一期固定 1.0 即可，注明）。
  - 朝向关键帧时序：过渡开始后短暂转身（如前 15% 时间转到移动朝向）→ 保持 → 结尾 15% 转到目标卡朝向。
- `shotCompiler.ts` 接入：角色对象位移超阈值且无 `motionOverride` 时应用推断；有 override 用 override；产出 motionSchedule 旁路数据（编译器返回类型扩展为 `{ animation, motionSchedule }`，1.2 的调用方同步适配）。
- 播放端消费（按重要记录 002 定稿方案）：`CharacterModel.tsx` 读当前时间对应的 schedule 条目；scrub 路径（`playbackSampling.ts`）同样生效。
