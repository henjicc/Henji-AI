# 重要决定

> 仅记录会影响整体方向或多个任务的决定。普通实现细节不在此记录。

## 决定 001：迁移动机定位为「跨平台一致性」而非「单机性能」
- 日期：2026-06-26
- 状态：已确定
- 背景：用户希望迁移 Electron 以支撑画布模式的高性能/复杂操作与跨设备一致性。技术核查发现：Tauri 在 Windows 上使用 WebView2（内核即 Chromium），与 Electron 打包的 Chromium 同源；画布栈（`@xyflow/react` + `konva`）为纯 Web 技术，渲染性能取决于引擎而非外壳。
- 最终决定：迁移的核心收益定位为 **跨平台/跨设备一致性 + 锁定较新 Chromium 能力（WebGPU/OffscreenCanvas/Worker）**，而非「换壳提升性能」。Windows 单机性能预期持平。
- 选择原因：避免用错误预期驱动迁移；macOS 的 WKWebView 与 Windows 的 WebView2 引擎差异是真实痛点，Electron 的统一 Chromium 可解决。
- 影响任务：全局；尤其 4.1（性能验收以「不劣化 + 跨平台一致」为基线，而非「显著提速」）。

## 决定 002：Rust 后端迁移策略 —— 全量 Node/TS 重写
- 日期：2026-06-26
- 状态：**已确定**（用户拍板：做就做全面迁移，不用 sidecar）
- 背景：`src-tauri/src` 约 9354 行 Rust，覆盖 ai_runtime（含 boa_engine JS DSL、进度学习、4 家 provider、上传）、llm_runtime（genai 流式）、image_commands（image/imageproc 图像处理）、SQLite、keyring、zip。
- 最终决定：**全量 Node/TS 重写（方案 B），彻底移除 Rust 与 `src-tauri/`，不保留任何 sidecar 二进制。** 后端能力全部落到 Electron 主进程（Node + TS）。
- 库映射见 `技术调研-Electron-2026.md` 第 8 节：`rusqlite→better-sqlite3`、`keyring→safeStorage`、`reqwest→undici/fetch`、`image/imageproc/ab_glyph→sharp + @napi-rs/canvas`、`zip→archiver/yauzl`、`genai→undici 流式 + IPC`、`boa_engine→Node 原生/node:vm`。
- 选择原因：用户要求一次性彻底迁移、语言统一（全 TS）、调试简单、单进程、长期维护成本最低；避免「双语言 + 进程管理 + 二进制打包」的长期负担。boa_engine 的 JS DSL 在 Node 下原生支持，是重写的有利点。
- 已知风险（须在对应任务重点把控）：
  - 图像处理像素级一致性（水印/分镜文字渲染，原用 imageproc/ab_glyph）—— 任务 3.7 重点回归。
  - `progress_learning`（921 行进度学习）逻辑较重，需逐函数对齐 —— 任务 3.5。
  - 重写工作量最大、回归面最广，因此第三阶段按域拆分、逐域验收。
- 影响任务：3.5（AI Runtime）、3.6（LLM 流式）、3.7（图片处理）全部按 Node 重写实施；4.3 直接删除 `src-tauri/`。

## 决定 003：引入平台抽象层（PAL）作为迁移基座
- 日期：2026-06-26
- 状态：已确定
- 背景：渲染层约 54 个文件、118 处直接 `invoke` / 依赖 `@tauri-apps/*`，散落各层。直接替换风险高且不可回滚。
- 最终决定：新增 `src/platform/*`，定义与外壳无关的能力接口；提供 Tauri 适配器（现状）与 Electron 适配器（新增）。渲染层与 `commands/` 只依赖 PAL，启动时按环境装配适配器。
- 选择原因：契合项目既有解耦哲学（关注点分离、禁止跨层导入）；支持双壳共存、逐命令灰度、随时回滚。
- 影响任务：1.3（接口设计）、2.4（渲染层接入）、第三阶段全部（各域按 PAL 接口实现 Electron 适配）。

## 决定 004：用户数据目录与数据库保持兼容、不搬家
- 日期：2026-06-26
- 状态：待确认
- 背景：现状数据库位于 `appLocalDataDir()/Henji-AI/henji.db`，媒体在同目录 `Media/`，密钥经 keyring 存系统凭据库。Electron 默认数据目录可能不同。
- 最终决定（拟）：Electron 侧将数据目录显式指向与 Tauri 一致的路径，复用同一 `henji.db` 与 `Media/`，避免用户升级后历史「消失」。密钥因存储后端不同（keyring vs safeStorage）无法自动互通，提供首启迁移引导。
- 选择原因：保护既有用户数据，降低迁移摩擦。
- 影响任务：3.1（数据层）、3.2（密钥）、3.4（媒体协议）、4.1（验收需含「老数据可读」）。
- 待确认：Tauri `com.henji.ai` 标识符对应目录与 Electron `app.getPath('appData')` 的精确映射关系。

## 决定 005：构建工具链 = electron-vite + electron-builder
- 日期：2026-06-26
- 状态：待确认（推荐）
- 背景：2026 年 React+TS+Vite 的 Electron 新项目，electron-vite DX 最佳；Electron Forge 为官方端到端工具但其 Vite 支持仍 experimental（Forge v7.5.0+），可能有破坏性变更。
- 最终决定（拟）：**开发/构建用 electron-vite，打包/分发/自动更新用 electron-builder。** 兼顾 DX 与成熟的分发能力，规避 Forge Vite 实验性风险。
- 选择原因：本项目已是 Vite 4 + React + TS，electron-vite 接入最自然；electron-builder 的多平台打包与 electron-updater 生态成熟。
- 影响任务：2.1（工程骨架）、4.2（打包与更新）。

## 决定 006：自动更新通道
- 日期：2026-06-26
- 状态：待确认（推荐）
- 背景：现状仅「GitHub Release API 轮询 + 手动下载」（`src/services/updateChecker.ts`）。本仓库为公开 GitHub + Apache-2.0。
- 备选：（A）`update.electronjs.org` + `update-electron-app`（开源免费、接入最简）；（B）`electron-updater` + GitHub Releases（可控、支持灰度/多通道）。
- 最终决定（拟）：与决定 005 一致，采用 **electron-updater + GitHub Releases** 实现真正的增量自动更新；如需零成本可退回 A。
- 影响任务：4.2。

## 决定 007：数据库用 better-sqlite3（不用 node:sqlite）
- 日期：2026-06-26
- 状态：已确定
- 背景：`node:sqlite`（Node 22.5+ 内置）2026 仍为实验性、不建议生产；better-sqlite3 已支持 Electron 42 预编译。
- 最终决定：用 **better-sqlite3**（同步 API，与现有 `DatabaseService` 风格契合），复用同一 `henji.db` 与表结构，配 `@electron/rebuild`。
- 选择原因：生产级稳定 + 平滑兼容旧数据。
- 影响任务：3.1。
- 注意：原生模块需重建；保持项目路径无空格（当前 `D:\VibeCode\Henji-AI` 安全）。

## 决定 008：跟随 Electron 大版本升级的常态机制
- 日期：2026-06-26
- 状态：已确定
- 背景：Electron 仅支持最新 3 个大版本，约每 8 周一个大版本。
- 最终决定：迁移目标锁定实施时的当前大版本（≥42），并建立「每隔数月跟随升级一次」的维护惯例，避免脱离支持窗口、丢失安全更新。
- 选择原因：统一且较新的 Chromium 正是本次迁移核心收益，需靠持续升级维持。
- 影响任务：4.2、4.3（文档需写入升级惯例）。
