# 3.6 LLM 流式 Runtime 迁移（全量 Node 重写）

## 任务状态
- 状态：待验证
- 所属阶段：第三阶段-功能迁移
- 前置任务：1.2、2.3、3.2
- 关联任务：4.1
- 是否可以并行：可与 3.5 并行（不同子系统）

## 任务目标
将 Rust `llm_runtime`（LLM 对话/流式）全量重写为 Node/TS，等价覆盖 `llm_chat_stream`、`llm_cancel_task` 及 `llm_*` key 命令；保证**流式增量输出**与**中途取消**在 Electron IPC 上正确工作。

## 当前情况
- Rust 现状：`llm_runtime/commands.rs`(526 行，6 命令)、`ppio.rs`(236 行)、`types.rs`(221 行)，用 `genai` crate 做流式对话。
- 命令：`llm_set/remove/get_provider_api_key`、`llm_get_provider_key_status`、`llm_chat_stream`、`llm_cancel_task`。
- 前端契约：`src/commands/llmRuntime.ts`（7 处 invoke）；消费方含 `services/llm/llmDiscoveryService.ts`。
- **关键点（1.2 已核实）**：现状用 Tauri `Channel<LlmStreamEventDto>` 推流，事件枚举**已确认**为 `Token(String) | ReasoningToken(String) | Done(LlmTraceDto) | Error(String)`（`llm_runtime/types.rs:190`，`LlmTraceDto` 含 providerId/modelId/startedAtMs/elapsedMs/inputChars/outputChars）。取消是**协作式**（`task_registry` 的 `Set<String>`，在 `ppio::stream_chat`/`stream_genai_chat` 内部循环检查，不是硬中断）。

## 实施方案
主进程用 Node `fetch` 对接 LLM 提供商（PPIO 等）的流式接口（SSE/chunked），将增量经 2.3 的流式通道回传渲染层；事件类型直接照搬 Rust 判别联合：`Token(String) | ReasoningToken(String) | Done(LlmTraceDto) | Error(String)`。取消用模块级 `Set<string>`（协作式，对齐现状）**叠加** `AbortController`（中断流式请求，比现状更快生效，是增强而非偷工减料）。key 命令复用 3.2 的 safeStorage。

## 执行步骤
1. 主进程实现 `electron/main/services/llm/`：provider 客户端（流式解析）、任务注册表（`Set<string>` + `Map<taskId, AbortController>`）、错误归一。
2. 定义流式事件 TS 类型（对齐上方判别联合），实现 `llm:chatStream`：建立流式请求 → 逐分片经 `webContents.send` 回传 → 循环中检查取消标记 → 结束发 `done`/`error` 终止帧。
3. 实现 `llm:cancel`：标记 `Set` + 调用对应 `AbortController.abort()`。
4. key 命令（set/remove/get/status）走 3.2 keystore（llm 命名空间）。
5. PAL `llmRuntime` 契约 Electron 适配；`commands/llmRuntime.ts` 改走 PAL，流式回调签名与现状对齐。
6. 端到端：发起对话流式输出逐字到达、可中途取消、错误正确终止；`llmDiscoveryService` 模型发现可用。
