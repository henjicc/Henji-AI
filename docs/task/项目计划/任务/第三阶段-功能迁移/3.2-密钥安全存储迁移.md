# 3.2 密钥安全存储迁移

## 任务状态
- 状态：已完成
- 所属阶段：第三阶段-功能迁移
- 前置任务：2.3
- 关联任务：3.5、3.6、4.1
- 是否可以并行：可与 3.1/3.3/3.4 并行

## 任务目标
用 Electron `safeStorage` 在主进程实现 API Key 的安全存储，等价覆盖现状的 `ai_*`/`llm_*` provider key 命令；并提供「从 Tauri keyring 迁移」的引导，避免用户已配置的密钥丢失（决定 004）。

## 当前情况
- 现状：Rust `ai_runtime/key_store.rs` + `llm_runtime` 用 `keyring` crate 写系统凭据库。
- 命令面：`ai_set/remove/get_provider_api_key`、`ai_get_provider_key_status`；`llm_set/remove/get_provider_api_key`、`llm_get_provider_key_status`。
- 注意：另有 `src/core/providers/base/utils.ts` 中 `getApiKey/setApiKey` 走 `localStorage`（疑似旧/兜底逻辑，迁移时需核对是否仍在用）。
- 跨外壳风险：keyring（系统凭据库）与 safeStorage（应用加密文件）后端不同，**密钥不会自动互通**。

## 实施方案
主进程用 `safeStorage.encryptString/decryptString` 把密钥加密后存到用户数据目录下的密钥文件（或并入数据库 settings 表的加密字段）；经 IPC 暴露 set/remove/get/status。首启时若检测到 Tauri keyring 中的旧密钥不可读，则提示用户重新填写或提供一次性导入入口。

## 执行步骤
1. 主进程实现 `electron/main/services/keystore.ts`：`safeStorage` 加密存储，键名对齐现状 provider id 约定。
2. 暴露 IPC：`keystore:set/remove/get/status`，覆盖 ai 与 llm 两套 provider。
3. PAL `keystore` 契约的 Electron 适配落地；`commands/aiRuntime`、`commands/llmRuntime` 的 key 相关函数改走 PAL。
4. 核对并清理 `core/providers/base/utils.ts` 的 localStorage 兜底（确认是否废弃）。
5. 设计迁移引导：首启检测无密钥时，提示「请重新填写 API Key」；可选提供从环境/文件一次性导入。
6. 验证 set→status→get→remove 全链路，并确认密钥不出现在日志/trace 中（安全）。
