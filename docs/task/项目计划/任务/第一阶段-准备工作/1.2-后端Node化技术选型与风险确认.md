## 任务目标
确认全量 Node 重写所需的库选型、关键协议（流式/取消）与高风险点的应对方案，输出一份「后端能力 → Node 实现路径」对照表，使 3.5/3.6/3.7 可直接照此实施。

## 当前情况
- 重写库映射初稿见 `记录/技术调研-Electron-2026.md` 第 8 节。
- 高风险域：
  - `image_commands`（image/imageproc/ab_glyph/png）→ sharp + @napi-rs/canvas，**水印/分镜文字渲染存在像素级一致性风险**。
  - `ai_runtime/progress_learning.rs`（921 行进度学习）→ 逻辑较重，需逐函数对齐。
  - `ai_runtime/request_builder_dsl.rs` + `js_runtime.rs`（boa_engine 执行 JS DSL）→ Node 原生执行 JS，反而简化，但需确认 DSL 沙箱与 API 表面一致。
  - 流式（`llm_chat_stream`）与取消（`ai_cancel_task`/`llm_cancel_task`）→ 需确定 IPC 上的流式与中断协议。

## 实施方案
逐域确认实现路径与验证手段，落到「可直接编码」的粒度；对像素一致性等风险给出验证基线（如保留若干 Rust 输出样张做对比）。

## 执行步骤
1. 确认各域目标库与版本：better-sqlite3、safeStorage、undici、sharp、@napi-rs/canvas、archiver/yauzl。
2. 设计流式协议：`llm_chat_stream` 用 `ipcRenderer` 事件分片或 `MessagePort`；取消用 `AbortController` + 任务注册表（对齐原 `task_registry.rs`）。
3. 确认 JS DSL 在 Node 下的执行方式（`node:vm` 沙箱 vs 直接执行）与可用 API 表面，确保与 `request_builder_dsl` 语义一致。
4. 为图像处理定义像素一致性验证基线：用现有 Rust 命令产出 N 张水印/分镜样张存档，作为 3.7 的对比基准。
5. 复核进度学习算法（`progress_learning.rs`）的输入输出与持久化（`progress-seeds.json`），明确 Node 移植边界。
6. 输出「后端能力 → Node 实现路径」对照表，回填本任务执行记录，并补充到 3.5/3.6/3.7 的实施方案。
