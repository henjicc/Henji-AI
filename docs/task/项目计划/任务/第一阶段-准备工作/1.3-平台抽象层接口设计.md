# 1.3 平台抽象层（PAL）接口设计

## 任务状态
- 状态：已完成
- 所属阶段：第一阶段-准备工作
- 前置任务：1.1
- 关联任务：2.4、第三阶段全部
- 是否可以并行：可与 1.2、1.4 并行

## 任务目标
设计 `src/platform/*` 平台抽象层的能力接口（仅类型与契约，不含实现），使渲染层彻底与外壳解耦：同一组接口在 Tauri 下走 `invoke`、在 Electron 下走 `window.henjiNative.*`。本任务只产出**接口定义 + 适配器装配骨架**，不迁移业务调用（那是 2.4）。

## 当前情况
- 渲染层约 54 个文件、118 处直接依赖 `@tauri-apps/*`（见 1.1 清单），散落在 `commands/`、`services/`、`utils/save/`、`hooks/` 等。
- 环境判定现状：`src/utils/save/environment.ts::isDesktop()` 检测 `window.__TAURI__`。
- 能力域可归为：AI Runtime、LLM Runtime、数据库、密钥、文件系统、对话框、外部链接、媒体/路径、剪贴板、原生拖拽、项目包、日志、窗口控制、ModelScope。

## 实施方案
按能力域定义接口（每域一个 `*.ts`），用一个 `PlatformRuntime` 聚合接口；提供 `runtime.ts` 在启动时探测环境并装配适配器。接口签名尽量对齐现有 `commands/*` 的对外签名，降低 2.4 改造成本。

实际落地结构（与原计划的差异：`fs`/`dialog`/`shell`/`paths`/`http` 合并为单个 `system` 契约，因为它们同属 3.3「系统基础能力迁移」一个任务，拆成 5 个文件反而碎片化；`image`/`dragDrop` 单列为独立契约，因为它们分别对应 3.7/3.8 两个独立任务）：
```text
src/platform/
├── index.ts            # 对外统一导出
├── runtime.ts          # 环境探测 + 适配器装配（getPlatform()，惰性单例）
├── types.ts            # 公共类型（ShellKind、PlatformNotImplementedError）
├── contracts/          # 12 个能力域接口：aiRuntime/llmRuntime/db/keystore/system/media/image/clipboard/dragDrop/projectPackage/window/logging
└── adapters/
    ├── tauri/          # 现状实现（包裹 invoke / @tauri-apps，逐函数对照 1.1 命令清单搬运，未改逻辑）
    └── electron/       # 骨架实现（每个方法抛 PlatformNotImplementedError，待第三阶段逐项点亮）
```

## 执行步骤
1. 依据 1.1 清单，按能力域归并出接口清单与方法签名（输入/输出类型沿用现有 DTO，如 `AiGenerateRequestDto`）。
2. 定义 `contracts/*.ts`：每域一个 interface，标注平台差异（媒体协议、拖拽限制、密钥不互通等）。
3. 定义 `runtime.ts`：`detectShell(): 'tauri' | 'electron'` + `getPlatform(): PlatformRuntime`，惰性装配适配器。
4. 搭建 `adapters/tauri/`：将现有 `invoke` 调用包成接口实现（此步只搬运、不改逻辑）。
5. 搭建 `adapters/electron/` 骨架：方法先抛 `NotImplemented`，待第三阶段逐项点亮。
6. 不改动任何业务调用点（保持现网可运行）；编译通过即可。
