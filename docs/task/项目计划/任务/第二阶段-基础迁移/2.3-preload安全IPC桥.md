# 2.3 preload 安全 IPC 桥

## 任务状态
- 状态：待开始
- 所属阶段：第二阶段-基础迁移
- 前置任务：2.1
- 关联任务：2.4、第三阶段全部
- 是否可以并行：否（第三阶段所有功能迁移的承载层）

## 任务目标
建立安全的 preload IPC 桥：经 `contextBridge` 暴露窄而具名的 `window.henjiNative.*` 白名单 API，主进程侧建立统一的 `ipcMain` handler 注册与输入校验框架。本任务搭**框架与约定**，具体能力 handler 由第三阶段各任务填充。

## 当前情况
- 现状全部能力走 Tauri `invoke('命令名', args)`，约 42 个命令。
- Electron 安全基线（2026 调研）：IPC 即安全边界，必须逐条校验；`contextBridge` 禁止暴露裸 `ipcRenderer`。

## 实施方案
设计「按域分组」的 IPC 通道命名（如 `ai:generate`、`db:select`、`media:read`），preload 仅暴露分域方法对象；主进程提供 handler 注册器，统一做参数校验、错误规范化（对齐原 `ai_runtime/errors.rs` 风格）与日志。preload 暴露的 API 形状与 PAL 的 Electron 适配器契约一致。

## 执行步骤
1. 约定 IPC 通道命名规范（`<域>:<动作>`）与请求/响应/错误的统一信封格式。
2. preload 用 `contextBridge.exposeInMainWorld('henjiNative', { ai, llm, db, keystore, fs, dialog, media, clipboard, drag, projectPackage, logging, window, modelscope })`，每域仅挂白名单方法。
3. 主进程实现 handler 注册器：集中注册、参数校验、错误规范化、可选 trace 日志。
4. 设计**流式与取消**通道：流式（`llm:chatStream`）用 `ipcRenderer.on(事件)` 接分片或 `MessagePort`；取消用单独通道传 taskId（对齐原 `*_cancel_task`）。
5. 提供 TS 类型声明（`window.henjiNative` 的全局类型），供渲染层与 PAL electron 适配器引用。
6. 用 1~2 个示例命令（如 `ping` 或 `db:select`）端到端验证通路，其余 handler 留给第三阶段。

## 涉及文件
### 新增
- `electron/preload/index.ts`：`henjiNative` 白名单暴露。
- `electron/preload/api.d.ts`（或 `src/platform/native.d.ts`）：`window.henjiNative` 全局类型。
- `electron/main/ipc/registry.ts`：handler 注册器 + 校验 + 错误规范化。
- `electron/main/ipc/stream.ts`：流式/取消通道工具。
### 修改
- `electron/main/index.ts`：启动时注册 IPC。
- `src/platform/adapters/electron/*`：示例命令打通（其余待第三阶段）。
### 可能废弃
- 无。

## 验收标准
- [ ] `contextIsolation:true`、`sandbox:true` 下 `window.henjiNative` 可用且仅含白名单方法。
- [ ] 未暴露裸 `ipcRenderer`；主进程对入参做校验。
- [ ] 流式与取消通道有可用样例（事件分片 + AbortController）。
- [ ] 错误信封统一，渲染层可区分错误类型。
- [ ] 示例命令端到端跑通；类型声明可被渲染层引用。
