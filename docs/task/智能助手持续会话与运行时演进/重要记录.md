# 重要记录 —— 智能助手持续会话与运行时演进

## 记录 001：本轮采用增量演进，不替换安全执行平面

- 日期：2026-07-30
- 状态：已确定
- 背景：现有项目已经具备唯一 `AgentRunner`、Utility Process、工具网关、审批、PAL、宿主命令、检查点和日志体系。
- 最终决定：保留现有执行平面，以 repository、projector、compactor、queue、wait coordinator 和 Provider adapter 等协作模块补齐结构性能力，不引入第二套 Agent Loop。
- 选择原因：当前主要缺口是会话与控制平面，不是底层业务工具或安全框架缺失；增量演进能降低未知副作用和回归风险。
- 影响任务：全部任务

## 记录 002：SQLite 追加式会话事实是持续会话的唯一持久源

- 日期：2026-07-30
- 状态：已确定
- 背景：当前已使用 SQLite 保存 thread、run、event、message、artifact 和 checkpoint；Pi 的 JSONL 适合其 CLI 产品，但不适合作为本项目新的平行事实源。
- 最终决定：新增会话能力继续使用 SQLite 追加 migration；旧表和旧数据保留。JSONL 仅可用于日志、诊断或导出，不作为主会话存储。
- 选择原因：复用现有事务、索引、迁移、所有权和 Electron 主进程边界，避免同一会话出现两个事实源。
- 影响任务：1.1、1.3、2.1、2.2、2.3、3.1、3.2、4.2

## 记录 003：实时事件、会话事实和运行检查点分层

- 日期：2026-07-30
- 状态：已确定
- 背景：当前所有 `ModelDelta` 都作为 AgentEvent 持久化，既产生写放大，也让 UI 流、会话历史和恢复状态职责混合。
- 最终决定：实时 delta 允许合并和有界保留；完整用户/助手消息、压缩和队列变化进入会话事实；预算、副作用、等待条件和安全保存点进入检查点。三者通过稳定 ID/sequence 关联。
- 选择原因：不同数据的保留周期、重放语义和一致性要求不同，分层后才能可靠重连和控制数据库规模。
- 影响任务：1.1、2.1、2.2、2.3、3.1、3.2、4.2

## 记录 004：确定性工作摘要与语义摘要并存

- 日期：2026-07-30
- 状态：已确定
- 背景：现有 `AgentWorkingSummary` 能保存 revision、Artifact、审批和恢复事实，但难以概括长对话中的用户意图；单独依赖 LLM 摘要又可能伪造已执行动作。
- 最终决定：确定性摘要继续作为安全和副作用事实；summarizer 只概括意图、决定、约束和未解决问题，并标记来源与信任级别。语义摘要不得覆盖工具证据。
- 选择原因：同时获得长会话可用性和可验证的恢复安全。
- 影响任务：2.1、2.2、2.3、3.2、4.1、4.2

## 记录 005：第一轮持续会话保持线性

- 日期：2026-07-30
- 状态：已确定
- 背景：Pi 的追加式会话树和分支摘要有价值，但 Henji 当前首先需要解决同一 thread 跨 run 的基本多轮连续性。
- 最终决定：首轮只实现线性 transcript、稳定 sequence、分页和当前 head；存储可预留父条目字段，但不实现分支、回到历史节点或树形 UI。
- 选择原因：先验证核心投影、压缩和恢复语义，避免会话 UI 与数据迁移范围失控。
- 影响任务：2.1、2.2、3.1、4.2

## 记录 006：不照搬 Pi 的高权限扩展和安全模型

- 日期：2026-07-30
- 状态：已确定
- 背景：Pi 默认继承宿主用户的本地权限，扩展可直接加载 TypeScript；Henji 是面向普通用户的桌面应用，已有更严格的风险和数据边界。
- 最终决定：不新增通用 Shell、任意文件/网络工具或任意 TypeScript 扩展。内部能力模块必须有来源、版本、冲突诊断和生命周期，但执行仍通过现有网关与 IPC 白名单。
- 选择原因：持续会话会放大权限错误的影响，安全边界必须比参考项目更严格。
- 影响任务：1.2、1.3、2.3、3.2、4.2

## 记录 008：`assistant_decides` 的 R1 自动执行范围

- 日期：2026-07-30
- 状态：已确定
- 背景：当前 UI 将该模式描述为“安全读取自动执行”，网关实际上自动执行全部 R1，其中可能包含低风险持久写操作。
- 最终决定：`assistant_decides` 自动执行 R0，以及非破坏、只读的 R1/R2；所有 R1 及以上写操作都需要审批。`ask` 自动执行安全读取，对全部 R2/R3 及非只读 R1 请求审批；`full_access` 自动执行 R0～R2，R3 仍审批。数据级别优先于模式：C2 始终逐次审批，C3 与 R4 永远禁止。界面文案与这三套规则同步。
- 选择原因：需要在操作流畅性和用户预期之间做产品决策，代码不能自行假设。
- 影响任务：1.2、3.1、4.2

## 记录 009：运行中消息的默认语义

- 日期：2026-07-30
- 状态：已确定
- 背景：持续会话需要区分“补充当前任务”“任务结束后继续”和“回答当前澄清”，三类消息的消费时机不同。
- 最终决定：等待澄清时，发送默认绑定为“回答当前问题”；其他 busy 状态默认作为“补充当前任务”，只在下一安全保存点消费；界面同时提供“任务结束后继续”的显式入口。用户未显式选择时不自动把补充消息转换为后续任务。
- 选择原因：默认行为会直接影响用户对发送按钮的理解和运行时队列语义。
- 影响任务：2.3、3.1、4.2

## 记录 010：异步生成终态后的续接方式与费用

- 日期：2026-07-30
- 状态：已确定
- 背景：生成任务可能持续很久，不能依赖 Utility Process 一直存活；终态后继续调用模型还会产生新的费用和预算消耗。
- 最终决定：等待条件持久化后释放活动 Runner；终态通过关联子 run 续接，同一 thread 内以 `parentRunId` 关联源 run，不复活旧 Runner。子 run 继承源 run 的工作摘要、副作用证据和剩余预算，只允许对明确登记的 wait 自动调用模型一次；预算不足时只追加终态事实并等待用户。默认等待 60 分钟，工具可配置但硬上限 24 小时；超时不自动取消已提交生成。
- 选择原因：需要同时兼顾可恢复性、run 语义、费用透明和防重复执行。
- 影响任务：2.3、3.2、4.1、4.2

## 记录 011：首轮原生 Provider 的范围

- 日期：2026-07-30
- 状态：已确定
- 背景：当前 Agent 模型统一走 OpenAI-compatible；协议分层可以先通过 Faux Provider 和兼容契约验证，也可以同时落地 Anthropic、Gemini 或 Responses 等原生协议。
- 最终决定：首轮只完成 Provider/API/Model 契约、结构化错误、动态凭据和 Faux Provider，不新增原生 Provider。后续出现明确模型需求时，再通过独立模型适配任务实现对应原生协议。
- 选择原因：避免为了抽象制造没有使用方的适配代码，同时给未来非兼容协议留出正确边界。
- 影响任务：4.1、4.2

## 记录 014：审批绑定和权限审计采用数据优先、默认闭锁

- 日期：2026-07-30
- 状态：已确定
- 背景：审批模式只表达用户对交互频率的偏好，不能覆盖敏感数据、工具误分级、异步预览漂移或审计不可用等安全边界。
- 最终决定：审批绑定同时覆盖参数、预览、目标、数据级别、目的地、可逆性、permission、工具版本和 revision；C2 每次访问都需要新审批并显示目的地，C3 拒绝进入 Agent 上下文，R0 破坏性工具定义直接拒绝。批准凭证只允许在原 TTL 与审计完成后 30 秒组成的有界窗口内开始消费，过期事实按审批 ID 恰好一次记录；授权审计结束后、首次真实执行前必须重新校验宿主 revision，取消或失败终局必须等待待审批对象清理。写操作、开放世界、R2+、C2/C3 和工作流委托的审计失败默认阻断；只有封闭世界的 R0/R1、C0/C1 只读工具允许带结构化告警降级。
- 选择原因：显式意图和 `full_access` 不能等价于无限授权；持续会话会扩大一次错误审批或缺失审计的影响，需要可复查且不可漂移的单次授权证据。
- 影响任务：1.2、1.3、2.3、3.1、3.2、4.1、4.2

## 记录 015：动态能力只在轮次边界激活，Artifact 默认同 run 所有权

- 日期：2026-07-30
- 状态：已确定
- 背景：注册表工具数量已经超过单轮模型 schema 的合理体积；Artifact 又可能包含敏感内容，若在请求中途改变工具集合或仅凭同 thread 放宽读取，会造成模型契约漂移和跨运行数据越权。
- 最终决定：能力搜索始终作为常驻控制面，活动工具在每次模型请求前按注册表元数据、route、最近 observation、发现结果和宿主上下文冻结；单轮最多 8 项且 schema 最多 48 KiB，模型输出中的 dynamic 或未披露调用一律拒绝。Artifact 正文每页最多 4 KiB，只允许稳定 cursor 和明确顶层字段；默认必须同时匹配 runId 与 threadId，C2 每页逐次审批，C3 禁止。未来关联子 run 读取源 run 产物时，必须增加绑定 `parentRunId` 的显式委托事实，不能退化为同 thread 任意读取。
- 选择原因：把“能力能否发现”与“本轮是否披露”分开，同时让分页读取保持低于二次 offload 阈值，并为异步子 run 保留可审计、最小授权的扩展点。
- 影响任务：1.3、2.2、2.3、3.2、4.2

## 记录 016：会话事实 schema 与投影入口固定

- 日期：2026-07-30
- 状态：已确定
- 背景：2.2、2.3 和 3.1 需要共享稳定的会话条目、sequence、head 和预留状态种类，不能分别再建消息事实源。
- 最终决定：`src/core/assistant/session.ts` 是会话共享契约；SQLite `agent_session_entries` 是追加式事实表；`AgentSessionStore` 统一负责幂等追加、分页、thread 摘要和 Runner 历史投影。第一轮只消费 `user_message/assistant_message`，`compaction/queued_message/external_wait/run_reference` 作为同表版本化 kind 由后续任务启用；旧 `agent_messages` 保留并在 migration 中稳定回填。
- 选择原因：同一条 sequence 轴可把 transcript、压缩、队列与等待事实关联起来，同时保持 Runner 只消费经过 projector 选择的模型消息，不把内部事件直接伪装成对话。
- 影响任务：2.1、2.2、2.3、3.1、3.2、4.2

## 记录 017：语义摘要与确定性事实并存

- 日期：2026-07-30
- 状态：已确定
- 背景：持续会话需要压缩用户意图和长期约束，但 LLM summarizer 不能成为工具执行、revision、审批或副作用完成的证据源。
- 最终决定：`AgentWorkingSummary` 继续保存可验证的运行事实；`agent-semantic-summary/v1` 只保存用户意图、长期约束、已确认决定、开放问题和上下文说明，投影时显式标记为不可信历史。有效摘要作为追加式 compaction entry 保存且不删原始消息；摘要失败回退确定性压缩，overflow 只允许重试一次。
- 选择原因：把会话可读性与安全证据分开，既支持长会话，又不让概率摘要伪造已执行事实或放大恶意工具文本。
- 影响任务：2.2、2.3、3.1、3.2、4.1、4.2
