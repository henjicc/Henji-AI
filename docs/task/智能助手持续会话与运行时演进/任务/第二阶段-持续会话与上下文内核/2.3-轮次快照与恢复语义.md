# 2.3 轮次快照与恢复语义

## 任务状态

- 状态：待开始
- 所属阶段：第二阶段 · 持续会话与上下文内核
- 前置任务：1.1、1.2、2.1
- 关联任务：2.2、3.1、3.2、4.1、4.2
- 是否可以并行：是，可与 2.2 并行做设计和故障测试；共享字段冻结后再集成

## 任务目标

为每个模型 turn 建立不可变快照和显式安全保存点，统一模型、工具、会话 head、宿主 revision、上下文版本和运行中变化的生效时机。完成后，在模型请求中、工具执行后或保存点后发生崩溃，系统都能明确恢复、等待用户或安全失败，不会重复未知写操作；终局后运行资源和监听器能可靠释放。

## 当前情况

- `runner.ts` 每轮会重新读取宿主快照、工具集合和记忆，但这些值只是局部变量，没有版本化 `TurnSnapshot` 或持久引用。
- 主模型/路由/摘要模型在 Runner 构造时选定；用户运行中调整模型、工具或设置何时生效没有统一规则。
- 当前 checkpoint 保存 `AgentRunState` 与 `AgentWorkingSummary`，Utility 崩溃会将活动 run 转为 `recovery_required`，未知副作用不会自动重放，这一安全原则可复用。
- `pause()` 只改变状态并在 Runner 的显式等待点生效，模型/工具内部取消和“下一安全点暂停”的产品语义没有统一记录。
- `electron/main/agent-utility.ts` 将 Runner 保存在 `runners` Map，终局回调只 post message，没有删除 Runner；main runtime 的 `runs` 也保留 live record，长期使用可能累积资源。
- 当前没有 `save_point` / `settled` 事件，持久化监听完成和“可以开始下一轮”的边界依赖隐含调用顺序。

## 实施方案

引入版本化 `TurnSnapshot`，至少包含 run/turn、session head sequence、projection/compaction version、模型引用与 API 协议、活动工具名/版本/schema digest、宿主 scope revision、相关 Artifact/资源引用、请求选项和创建时间；快照不保存 API key 或不必要的完整敏感正文。

在以下边界创建保存点：会话/当前 turn 输入已持久化且即将调用模型；工具调用结果、审批事实和副作用摘要已全部耐久且即将进入下一模型 turn；进入用户澄清或外部等待前。运行中新增消息、工具发现、模型设置和资源刷新写入 pending change，只在下一个快照消费。

定义恢复矩阵：模型请求前可从快照重试；只读工具失败可按策略重试；写工具已发出但结果未知时先查询验证或进入 `recovery_required`；保存点后可从下一 turn 继续。新增 `settled` 语义，保证终局事件、持久化和监听器完成后再释放 utility/main 的 Runner、RPC、listener 和内存事件，仅保留持久快照。

## 执行步骤

1. 列出模型请求、审批等待、工具开始/完成、暂停、取消、澄清、外部等待和终局的状态迁移，定义每个位置的安全恢复动作。
2. 定义 `TurnSnapshot`、pending change、save point 和 settled 共享 schema；明确版本升级和旧 checkpoint 无快照时的 `recovery_required` 行为。
3. 在 2.1 SessionRepository 与现有 checkpoint 之间建立原子/可恢复写入顺序，记录 session head 与 save point 的一致性。
4. 修改 Runner，使一轮内只读取快照值；下一轮开始前合并宿主 revision、动态工具、消息队列、记忆和配置变化。
5. 把暂停定义为“当前不可中断单元结束后的安全暂停”，取消继续使用 AbortSignal；界面和事件明确两者差异。
6. 在模型请求前、模型已返回未执行工具、只读工具中、写工具已发出未回执、工具结果已持久和保存点后注入崩溃，验证恢复矩阵。
7. 增加 settled 清理：等待终局持久化/监听器完成，再从 utility runners、manager active set、main live map 和订阅表移除可释放资源；历史查询改走持久层。
8. 验证旧 checkpoint、版本不匹配、重复 save point、重连、暂停/恢复/取消和 100 次短 run 的资源上限。
9. 更新任务执行记录、总览和 3.1/3.2 可用的状态字段，创建独立提交。

### 可能废弃

- 每轮通过散落局部变量隐式决定配置生效时机的方式，在快照接管后废弃。
- 终局后永久保留 utility Runner/live record 的行为在持久查询切换完成后废弃。

## 特殊风险与回退要求

- 快照绝不保存 API key、Authorization header、完整 cookie 或不必要的 C2/C3 正文。
- 未知写副作用只能查询验证或等待用户，不能因为存在 save point 就自动重放。
- 新 checkpoint 版本无法解析时继续沿用现有 fail-closed `recovery_required`，禁止猜测恢复。

## 验收标准

- [ ] 每个模型 turn 有不可变快照，包含 session head、模型/协议、工具版本摘要、宿主 revision 和上下文版本，但不含凭据。
- [ ] 运行中模型、工具、消息和资源变化只在下一个保存点后的快照生效，不污染当前请求。
- [ ] 六类故障注入位置都有自动化恢复断言；写操作结果未知时绝不自动重放。
- [ ] save point 与会话 head/checkpoint 一致，重复回调不会创建冲突状态。
- [ ] pause、cancel、waiting_user/waiting_external 预留语义和 UI 描述一致。
- [ ] 终局持久化和监听器完成后 Runner、RPC、订阅与 live map 被释放；100 次短 run 不持续增长。
- [ ] 旧 checkpoint 仍可查看；不可安全升级的活动 run 明确进入 `recovery_required`。
- [ ] 相关状态机、Runner、持久化、Utility 和 UI 测试通过。
- [ ] 本任务执行记录和任务总览已同步更新，并创建独立 Git 提交。
