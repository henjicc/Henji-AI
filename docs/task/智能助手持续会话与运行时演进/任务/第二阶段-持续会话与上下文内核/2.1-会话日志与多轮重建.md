# 2.1 会话日志与多轮重建

## 任务状态

- 状态：待开始
- 所属阶段：第二阶段 · 持续会话与上下文内核
- 前置任务：1.1
- 关联任务：2.2、2.3、3.1、4.2
- 是否可以并行：是，可与 1.2、1.3、4.1 并行；会话 schema 冻结后再与 2.2/2.3 集成

## 任务目标

把当前仅用于 run 分组的 `threadId` 升级为真正的持久会话：用户消息、最终助手消息和必要的产品状态以追加式条目保存；同一 thread 的后续 run 能从有效历史重建上下文；应用重启后 UI 能按顺序分页显示完整 transcript；新 thread 与旧 thread 严格隔离。

## 当前情况

- `electron/main/services/agent-runtime/persistence/migrations.ts` 已有 `agent_threads`、`agent_runs` 和 `agent_messages`。`agent_messages` 只有 role/content/runId/createdAt，没有稳定 thread sequence、条目类型、投影状态或压缩条目。
- `AgentPersistenceStore.createRun()` 只写入本次用户 goal；`appendTerminalMessage()` 只在 run 终局写入最终 assistant 文本，没有按 thread 加载消息的公开方法。
- `AgentRunner` 的 `conversation` 在构造时始终为空，新 run 不读取相同 thread 的历史。
- `runtime.ts` 使用 `activeByThread` 防止同一 thread 同时运行多个 run，但 `threadId` 没有承担 transcript 事实源职责。
- `src/features/assistant/store/assistantUiStore.ts` 只在本地持久化当前 `threadId`；“新对话”创建 UUID，历史界面主要展示 run 列表和单 run snapshot。
- `src/platform/contracts/assistant.ts` 只有 `listRuns()`，没有 list threads、读取 transcript、分页或追加运行中用户消息的契约。
- 旧计划中的“会话恢复”已覆盖单 run checkpoint 与工作摘要，不等于本任务的跨 run transcript；旧实现需要保留。

## 实施方案

采用追加 migration 建立版本化会话条目事实源。优先方案是新增 `agent_session_entries`，包含稳定 `entry_id`、`thread_id`、单调 `sequence`、可选 `run_id/turn`、`kind`、版本化 `payload_json`、状态、创建时间和预留的 `parent_entry_id`；第一轮始终线性写入，不实现分支 UI。旧 `agent_messages` 保留，迁移/读取层把它作为 legacy 消息投影，禁止破坏性搬迁。

会话 repository 提供 thread 列表、head、按 cursor 分页、追加条目和幂等写入。新 run 启动前读取同一 thread 的有效 transcript，并通过独立 projector 生成初始 Agent 消息；2.2 完成前可先使用“旧摘要 + 最近完整消息”的兼容投影，不在本任务内提前实现语义压缩。

UI 从“当前 run 的事件卡片”扩展为“当前 thread 的连续消息 + 当前 run 的执行详情”。运行历史仍可查看，但不再被当作聊天记录。本任务只实现继续工作必需的 thread 列表、选择和新建；删除/归档不纳入本轮，如用户新增明确需求再单独建立任务。

## 执行步骤

1. 定义会话条目类型与职责：用户消息、最终助手消息、运行引用、压缩、队列/等待状态预留；明确哪些 AgentEvent 不进入 transcript。
2. 设计并测试 additive migration、thread sequence 分配、事务边界、幂等键和旧 `agent_messages` 兼容读取；不删除旧表。
3. 实现 SessionRepository：创建/更新 thread、追加条目、读取 head、按 cursor 分页、列出 thread 摘要，并保证同 thread 顺序稳定。
4. 扩展 main runtime：创建 run 时在同一事务或可恢复顺序中追加用户条目；终局时追加完整 assistant 条目；重复终局回调不重复写入。
5. 在启动 Runner 前读取当前 thread 投影并传入 utility；`conversation` 不再只从空数组开始。工具证据仍由工作摘要和 observation 负责，避免把原始内部事件全部注入模型。
6. 扩展共享 schema、IPC、preload、PAL 和命令，提供 list threads、get transcript/cursor；所有读取继续校验窗口所有权和字段上限。
7. 改造助手历史和对话 reducer，使同一 thread 的多次 run 消息按 sequence 展示；当前 run 的工具/审批/进度作为消息之间的执行投影，不复制成聊天正文。
8. 覆盖旧数据库迁移、三轮追问、应用重启、新 thread 隔离、重复回调、分页边界、中文/媒体引用和已失败 run 测试。
9. 更新本任务记录、总览和后续任务的实际 schema 路径，创建独立提交。

## 数据迁移与回退要求

- migration 必须可在空库、仅旧表、含失败/中断 run 和已有新表四种状态重复验证。
- 旧消息可按 `created_at + message_id` 形成稳定兼容顺序，但不能伪造精确 turn；无法确认的字段标明 legacy。
- 新会话投影发生问题时可回退为当前单 run 上下文；已追加条目不删除，待修复后可重新投影。

## 验收标准

- [ ] 同一 thread 连续三次 run，第三次能使用前两次明确的用户约束与最终回答。
- [ ] 应用重启后 transcript 顺序、内容和当前 head 一致；分页无重复、无跳项。
- [ ] 新建 thread 后不注入旧 thread 的消息、摘要、Artifact 或队列状态。
- [ ] 同一个 run 的用户消息和终局 assistant 消息在重复回调/重连下只写一次。
- [ ] 旧数据库无需删除或手工转换即可读取历史 run 和 legacy 消息。
- [ ] UI 同时区分连续聊天消息与单 run 的工具、审批和执行详情，不把内部事件原文伪装成 assistant 消息。
- [ ] 会话 API 经过 PAL/preload 白名单，renderer 不直接访问 SQLite。
- [ ] 相关 migration、repository、runtime、UI 测试与类型/lint 检查通过。
- [ ] 本任务执行记录和任务总览已同步更新，并创建独立 Git 提交。
