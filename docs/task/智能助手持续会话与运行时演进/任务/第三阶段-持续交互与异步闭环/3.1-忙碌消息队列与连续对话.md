# 3.1 忙碌消息队列与连续对话

## 任务状态

- 状态：待开始
- 所属阶段：第三阶段 · 持续交互与异步闭环
- 前置任务：2.1、2.3
- 关联任务：2.2、3.2、4.2
- 是否可以并行：是，可与 3.2 并行；双方必须共用保存点、等待状态和队列契约

## 任务目标

让用户在助手忙碌时仍能发送消息，并明确区分“回答当前澄清”“补充当前任务”和“任务结束后继续”。消息需要持久化、可见、可取消且只消费一次；正在发送的模型请求和正在执行的工具不被中途篡改，新消息只在 2.3 定义的安全保存点生效。

## 当前情况

- `src/features/assistant/conversation/AssistantComposer.tsx` 在 `disabled` 或 `submitting` 时禁止输入和发送，busy placeholder 为“当前任务结束后可继续提问”。
- `AssistantConversation.tsx` 根据 active run 是否终局计算 `busy`，busy 时 `pendingGoal` 不会启动新 run。
- `electron/main/services/agent-runtime/runtime.ts` 对同一 thread 的活动 run 直接返回 `thread_busy`，没有追加消息入口。
- `src/platform/contracts/assistant.ts` 目前只有 start、pause、resume、cancel 和 approval，没有 enqueue/respond clarification/next turn API。
- Runner 已发布 `ClarificationRequired` 事件并能以文本询问用户，但用户回答会启动另一 run，无法绑定原问题和原预算。
- 当前 pause/cancel、审批和工作摘要已有稳定 run/tool/approval ID，可用于队列所有权和一次性消费。
- 2.1 提供追加式会话条目，2.3 提供 TurnSnapshot/save point，是本任务必须复用的事实和消费边界。

## 实施方案

定义三种用户语义，但 UI 使用中文产品词而非内部术语：

- **回答当前问题**：绑定 `waitId/clarificationId`，只在 `waiting_user` 状态接受并恢复原执行；
- **补充当前任务**：相当于 steering，写入当前 run 的 pending queue，在下一保存点、下一次模型调用前消费；
- **任务结束后继续**：相当于 follow-up/next-turn，当前 run 自然结束后在同一 thread 开始关联的下一执行。

所有消息先追加到会话事实并获得 entryId，再进入持久队列；状态为已接收、待处理、已消费、已取消或失败。默认语义见 `重要记录.md` 记录 009，未确认前先实现显式 mode，不把默认写死在深层代码。

当前任务补充在取消/失败前尚未消费时标记取消，不静默转成新任务；“任务结束后继续”默认保留到下一执行，除非用户显式取消。切换 thread 不改变消息所有权，UI 只显示对应 thread 队列。

## 执行步骤

1. 按记录 009 实现 clarification、current-task、after-task 三种 mode、状态机、TTL/上限、取消与 run 终局行为。
2. 在会话 schema 上新增队列条目/引用，保证 append message 与 enqueue 的幂等顺序；同一 clientMessageId 重试不会重复入队。
3. 扩展 runtime、Utility protocol 和 Runner：接收队列变更，但只在 save point 创建下一 TurnSnapshot 时消费；正在运行的模型/工具输入保持不变。
4. 增加 `waiting_user` 或等价明确状态，ClarificationRequired 携带稳定 waitId、问题和允许回答范围；回答只能消费一次。
5. 支持 after-task：当前 run settled 后创建关联续接执行或在同一会话开启下一 turn，继承会话事实但不重放前 run 工具。
6. 改造 Composer：busy 时保持可编辑，提供清晰的发送目标；等待澄清时优先显示“回答当前问题”，其余状态显示“补充当前任务/任务结束后继续”。
7. 在 transcript 中展示消息状态和归属；消费后不重复显示为新用户消息，取消/失败有可理解原因。
8. 覆盖模型流式中、只读工具中、审批等待、暂停、取消、崩溃、thread 切换、重复点击、多个 pending 消息和恢复后消费顺序。
9. 运行 runtime、会话、状态机、UI reducer/组件和 Utility smoke，记录结果并独立提交。

## 特殊风险与回退要求

- 消息不得直接修改正在执行工具的参数；需要改变写操作时只能在下一快照重新规划，并重新经过审批与 revision 校验。
- 客户端乐观状态不是事实源；重连后以 SQLite queue 状态为准。
- 队列超限或无法恢复时明确失败，不允许静默丢弃或无限积压。
