# 3.2 生成任务等待与事件唤醒

## 任务状态

- 状态：已完成
- 所属阶段：第三阶段 · 持续交互与异步闭环
- 前置任务：1.3、2.3
- 关联任务：2.1、2.2、3.1、4.1、4.2
- 是否可以并行：是，可与 3.1 并行；状态与队列契约必须共用

## 任务目标

把“创建生成任务后立即结束”升级为可持久等待、跨重启唤醒和继续验证的异步闭环。Agent 提交付费生成后记录 taskId、目标终态、超时和会话归属，释放活跃模型循环；任务进入 success/error/cancelled/timeout 时只唤醒一次，先查询权威状态，再继续结果验证或恢复，不重复提交生成。

## 当前情况

- `src/workspaces/GenerationWorkspace/application/visibleGenerationTaskCommand.ts` 在创建 pending 任务后调用 `emitVisibleGenerationTaskChange()`；`onStart` 与 queued 更新只修改 task 状态，当前代码片段没有向 Agent 发布耐久终态事件。
- 内置工具 `create_visible_generation_task` 返回 `{ taskId, status: submitted }`，`get_generation_task` 能查询状态。
- `runner/result-verifier.ts` 明确要求 pending/queued/generating 时不要在同一 run 立即轮询，并允许如实告诉用户“已提交”，因此当前 run 通常结束。
- Agent run status 没有 `waiting_external`，checkpoint 也没有外部等待条件。
- `npm run assistant:cli -- --await-generation` 已有 CLI 外层等待能力，但它依赖同一隐藏宿主读取结果，不是通用 Agent 会话恢复或业务事件协议。
- 生成任务可能继续运行于助手面板关闭、renderer 重载或应用重启之后；等待事实不能依赖 AssistantConversation 组件存活。
- 可继续复用：稳定 taskId、生成任务状态查询、任务队列、现有日志、2.3 save point、3.1 持久消息队列和工具结果验证。

## 实施方案

在生成任务权威状态层增加稳定状态事件出口，覆盖 pending、queued、generating、success、error、cancelled；助手只订阅该业务事件，不复制生成执行逻辑。若权威任务状态当前仍位于 renderer，应通过现有应用服务/host bridge 将版本化状态事件交给 main 持久协调器，不能由某个助手组件临时监听。

新增持久 wait record：waitId、threadId、sourceRunId、taskId、目标终态、创建/超时、lastObservedStatus、savePoint、resumePolicy、consumedAt 和错误。进入等待前必须持久化工具已提交证据与 save point，再释放 Utility 活动 Runner。

终态事件使用 taskId + 状态版本/时间做幂等去重。唤醒后先调用 `get_generation_task` 或等价权威查询，确认状态和结果引用，再恢复同一会话的后续推理。采用原 run 复活还是关联子 run 见 `重要记录.md` 记录 010；两种方案都必须保持一次性唤醒、累计费用可见和未知副作用不重放。

## 执行步骤

1. 盘点生成任务从创建、排队、执行、轮询到终局的所有状态写入点，确定唯一权威版本与可稳定发布的业务事件位置。
2. 按记录 010 实现关联子 run、剩余预算继承、一次自动模型续接、60 分钟默认超时和 24 小时硬上限。
3. 定义 generation status event 和 wait record schema，增加 additive migration、唯一约束、索引和过期扫描；同一 sourceRunId/taskId 只能存在一个活动等待。
4. 在生成任务每次真实状态变化时发布事件；main coordinator 持久化 last status，并对终态执行幂等 claim，不能依赖助手 UI 挂载。
5. Runner 创建任务后，在保存点记录 `waiting_external` 或等价状态、工具证据和 continuation payload，然后 settled 释放资源。
6. 终态唤醒时重建会话/快照，先查询任务；success 注入稳定资产/任务引用并验证，error 注入恢复约束，cancelled/timeout 给出明确结果。
7. 接入 3.1：等待期间允许补充要求、安排后续和取消等待；取消等待是否同时取消生成任务必须由用户明确选择。
8. 覆盖状态乱序、重复事件、应用重启、renderer 重载、Utility 崩溃、终态先于 wait commit、超时后迟到成功和手动取消竞态。
9. 使用脚本化/本地任务完成测试和一次真实 Provider 手动验收，核对付费调用次数、唤醒次数和最终日志链。
10. 更新执行记录、总览和重要决定，创建独立提交。

- CLI 独立等待逻辑若能无损迁移到共享 coordinator，则保留薄适配并废弃重复状态判断。

## 特殊风险与回退要求

- 终态唤醒可能产生额外模型费用，必须遵守确认后的 resumePolicy、预算和用户可见说明。
- 任何恢复路径都不得再次调用 `create_visible_generation_task`，除非用户明确发起新任务。
- 等待协调器失败不影响已提交的生成任务本身；恢复后通过 taskId 重新对账。

## 验收标准

- [x] 生成任务所有真实状态变化有稳定业务事件，助手面板关闭或重建不影响事件持久化。
- [x] wait record 在应用重启后仍可恢复，包含 taskId、目标终态、超时、save point 和一次性消费状态。
- [x] success/error/cancelled/timeout 每种终态只唤醒一次，重复、乱序和迟到事件不会重复模型调用。
- [x] 唤醒后的第一步是权威查询和结果验证；任何路径都不重复提交原生成任务。
- [x] 等待期间的补充消息、取消等待和“是否同时取消生成”遵守 3.1 队列与用户选择。
- [x] 续接产生的 token/费用与原任务关联可见，预算和确认策略符合记录 010 的最终决定。
- [x] CLI `--await-generation` 与正式助手对同一任务状态解释一致，没有两套终态规则。
- [x] 故障注入、重启、状态竞态和自动化有记录；真实 Provider 手动验收按统一决定并入 4.2。
- [x] 本任务执行记录和任务总览已同步更新，并创建独立 Git 提交。
