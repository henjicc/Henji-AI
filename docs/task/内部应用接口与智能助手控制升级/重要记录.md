# 重要记录

## 记录 001：本次只建设内部应用接口

- 日期：2026-08-01
- 状态：已确定
- 背景：未来可能有其他本地软件调用痕迹 AI，但当前首要消费者是内置智能助手。
- 最终决定：本次建立与调用方和传输方式无关的内部 Application API；不实现 MCP、HTTP、WebSocket、本地端口或外部 SDK，只保留未来适配边界。
- 选择原因：先把业务能力、schema、事务和安全边界做正确，避免过早承担外部协议、鉴权和兼容成本。
- 影响任务：1.1、2.1、2.2、2.3、7.1。

## 记录 002：反射属性与语义操作分层

- 日期：2026-08-01
- 状态：已确定
- 背景：现有能力几乎全部是零散动作，无法完整暴露可调整参数；如果只提供通用属性 Patch，又会丢失领域语义和安全约束。
- 最终决定：新增实体/属性反射注册表描述可控状态，继续使用 `ApplicationCapabilityDefinition` 描述语义操作；两者通过稳定实体类型、属性路径和影响声明关联。
- 选择原因：既能覆盖大量参数，又能保留“环绕”“生成”“导入”等高层业务动作。
- 影响任务：1.1、2.1、2.2、2.3、4.1、4.3、5.1 至 5.4。

## 记录 003：禁止任意代码和任意 Store 修改

- 日期：2026-08-01
- 状态：已确定
- 背景：Blender MCP 通过任意 Python 获得了很强的控制力，但这会绕过权限、schema、撤销和数据不变量。
- 最终决定：只允许注册表声明的实体字段和正式语义操作；不提供任意 JavaScript、Python、Store Patch、IPC 或文件系统执行能力。
- 选择原因：保持桌面应用的数据安全、可验证性和可撤销性。
- 影响任务：1.1、2.1、2.3、7.1。

## 记录 004：智能助手是第一个消费者但不是架构所有者

- 日期：2026-08-01
- 状态：已确定
- 背景：当前大量能力以 assistant 或 agent 命名并直接围绕工具调用组织，未来 UI 或其他本地调用方难以复用。
- 最终决定：领域应用服务和内部控制面不得依赖 Agent 运行时；智能助手通过独立适配层消费。UI 的持久业务动作也逐步复用相同领域服务。
- 选择原因：避免为每个调用方重新适配业务能力，同时不让模型协议侵入领域层。
- 影响任务：1.1、2.1 至 2.3、4.1、5.1 至 5.4。

## 记录 005：先以三维运镜建立纵向样板

- 日期：2026-08-01
- 状态：已确定
- 背景：3D 失败案例同时暴露了状态读取、对象复用、空间布局、完整参数、语义动作、Surface 和视觉验证问题。
- 最终决定：内部接口内核完成后，先迁移 3D 并跑通完整闭环，再批量迁移其他领域。
- 选择原因：3D 是复杂度足够高且证据明确的代表场景，能尽早验证通用架构是否真的成立。
- 影响任务：4.1 至 4.4、5.1 至 5.4。

## 记录 006：视觉观察的首批覆盖范围

- 日期：2026-08-01
- 状态：已确定
- 背景：结构化数据无法完全判断 3D 构图、物体遮挡和最终视觉质量，但为所有界面建设截图观察会显著扩大范围。
- 最终决定：覆盖全部已注册 Surface、生成结果和媒体实体。优先使用领域原生预览，其他 Surface 使用经过敏感区域遮罩的应用内区域截图；模型可按任务需要自主申请观察。
- 选择原因：智能助手需要在不同组合任务中判断真实视觉结果，不能把观察能力限制在 3D 特例。
- 影响任务：4.4、5.1 至 5.4、6.2、6.5、7.1、7.2。

## 记录 008：旧能力 ID 和历史运行的兼容期限

- 日期：2026-08-01
- 状态：已确定
- 背景：迁移期间可以用薄适配器保留旧能力 ID，但长期并存会导致工具重复、模型误选和维护成本上升；历史运行可能保存旧调用记录。
- 最终决定：当前处于开发阶段，不保留跨阶段旧能力兼容。单个领域迁移期间可使用薄适配器，但任务完成前必须删除旧能力 ID 与旧执行入口。历史记录只读展示，不恢复或重放旧调用。
- 选择原因：彻底消除重复能力和双实现，比为尚无正式用户的旧调用维持长期兼容更重要。
- 影响任务：1.1、1.2、5.1 至 5.4、7.1、7.2。

## 记录 010：增加可选多模态观察模型角色

- 日期：2026-08-01
- 状态：已确定
- 背景：主要助手模型可能擅长工具调用但不支持某种媒体输入，如果完全依赖 primary，会让视觉观察与主模型选择强绑定。
- 最终决定：Agent profile 增加可选 `observer` 模型角色。primary 支持目标模态时直接观察；否则由支持该模态的 observer 产生带来源证据的结构化描述；两者均不支持时禁用该观察并说明如何配置。
- 选择原因：既严格遵守模型真实模态能力，又允许文本主模型与多模态观察模型组合工作。
- 影响任务：6.3、6.4、6.5、7.2。

## 记录 011：观察范围与截图权限边界

- 日期：2026-08-01
- 状态：已确定
- 背景：模型需要自主观察实际界面，但任意全屏截图可能包含其他应用、密钥、本地路径和无关隐私。
- 最终决定：模型可自主申请观察，但只能通过正式观察能力捕获 Henji-AI 已注册 Surface 或稳定媒体引用；截图前遮罩敏感区域，禁止操作系统全屏和其他应用窗口。观察请求、范围和脱敏结果进入既有审计日志。
- 选择原因：满足通用视觉闭环，同时把权限限定在用户交给当前应用管理的内容内。
- 影响任务：2.1、2.2、4.4、5.1、6.5、7.1、7.2。

## 记录 012：代表性复杂任务的效率验收阈值

- 日期：2026-08-01
- 状态：已确定
- 背景：失败基线运行 `ba36b4cf-67d0-4650-9333-abb8ad4a576a` 进行了约 15 次能力搜索、32 次工具调用、32 轮，并累计约 75.5 万 Token，最终仍由用户取消。
- 最终决定：对同一代表性 3D 组合请求，在需求和目录 revision 不变时只允许 1 次批量能力发现；总工具调用不超过 12 次、模型步骤不超过 12 轮、累计输入 Token 不超过 25 万；相同执行指纹最多进行 1 次有新证据的恢复尝试。
- 选择原因：阈值足以容纳观察、导航、计划、分组执行和验证，同时能明确阻止旧式搜索与工具循环。
- 影响任务：3.2、3.3、7.2。
