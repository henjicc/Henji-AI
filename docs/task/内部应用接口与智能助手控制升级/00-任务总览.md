# 内部应用接口与智能助手控制升级

## 任务目标

当前智能助手能够调用 86 项应用能力，但能力主要以零散动作工具暴露，缺少统一的实体、属性、约束、状态读取、事务和验证协议。这导致复杂组合任务中出现重复搜索、先写后读、重复创建已有对象、参数不可发现、界面切换过晚和无法可靠判断完成等问题。

本任务要建立一套与调用方和传输方式无关的内部应用接口：由正式领域服务提供业务语义，由反射注册表描述可读写状态，由事务执行层负责计划、提交、撤销和验证；智能助手成为第一个完整消费者，现有界面逐步复用同一业务入口。同时补齐全 Surface 视觉观察、生成结果识别和助手图片/视频/音频附件输入，并依据当前配置模型的真实多模态能力动态开放。未来可以在这套内部接口之外增加本地外部适配器，但本次不实现 MCP、HTTP、Socket、插件协议或远程控制服务。

## 重要说明

- `ApplicationCapabilityDefinition` 继续作为动作能力的唯一元数据源；新增反射层描述“有什么实体和属性可读写”，两者职责分离但通过稳定标识关联。
- 禁止提供任意 JavaScript、任意 Store Patch、任意 IPC 或类似 Blender MCP 的任意 Python 执行入口。
- 领域模型是数据真相，正式应用服务是业务写入入口；UI 和智能助手不得各自维护同一套持久业务逻辑。
- 现有项目文件、设置值和用户内容默认保持兼容；旧能力 ID 不长期保留，同一领域迁移完成即删除旧执行入口。历史运行只保留只读展示，不支持重新执行旧能力调用。
- 所有已注册 Surface 都必须提供视觉观察；优先使用领域预览或媒体原件，其次使用经过敏感区域遮罩的应用内 Surface 截图，不开放操作系统全屏任意截图。
- `LlmCapabilities.image/video/audio` 及现有模型设置勾选项是助手多模态能力的唯一配置来源；不在提示词、组件或模型 ID 分支中重复判断。
- 当前已有的智能助手基础、持续会话和智能化升级计划仍然有效。本计划只接管应用控制架构、复杂任务编排及相关体验，不重复实现已经完成的运行时能力。
- 每个代码任务独立提交；开始任务前必须先处理工作区中不属于本计划的存量改动。
