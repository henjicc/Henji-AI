# 4.1 提取三维正式应用服务与完整控制描述

## 任务状态

- 状态：待开始
- 所属阶段：第四阶段 · 三维运镜端到端样板
- 前置任务：2.1
- 关联任务：4.2、4.3、4.4
- 是否可以并行：可以；可与 3.1 并行，完成后 4.2 和 4.3 可并行

## 任务目标

把 3D 场景的持久业务读写从助手专用能力和 UI Store 调用中提取到正式应用服务，并为项目、场景、对象、摄像机、镜头、轨迹和关键帧建立完整反射描述，作为其他领域迁移的首个样板。

## 当前情况

- `src/features/cameraStage/domain/` 已有场景、镜头、动画、空间路径和相机预设等完整领域代码，可继续复用。
- 新建工程的默认摄像机和镜头定义已存在于场景默认值/Store 初始化中。
- `cameraStageApplicationCapabilities.ts` 达 441 行，包含约 12 项手写动作；其 Patch 类型与 `sceneTypes.ts`、`shotTypes.ts` 不一致。
- `src/features/assistant/hostActions.ts` 也承载 3D 宿主操作，文件接近 500 行。

## 实施方案

新增 3D application service，统一负责读取、创建、更新、删除和领域不变量；UI 与助手能力都委托该服务。属性描述尽量由领域 schema 和可动画属性清单生成，只有权限、语义别名和动态可编辑性需要补充元数据。

## 执行步骤

1. 盘点 UI、Store、project service、hostActions 和 3D 能力中的所有持久写入入口，标出重复逻辑。
2. 建立 3D 应用服务接口，覆盖项目、场景对象、摄像机、镜头、轨迹和关键帧的查询与写入。
3. 把默认对象、名称唯一性、引用有效性、时间范围和关键帧约束收口到应用服务。
4. 从 `sceneTypes.ts`、`shotTypes.ts`、`animatableProps.ts` 等生成或登记完整属性定义、单位、范围、枚举和关系。
5. 将现有能力改为薄适配器，不再自行过滤 `Record<string, unknown>` 或直接改 Store。
6. 让现有 UI 持久操作逐步调用相同服务；拖拽预览等高频临时态仍保留本地。
7. 增加服务与反射覆盖测试，确认默认场景和旧项目读取不变。
8. 更新迁移矩阵、任务记录并独立提交。

## 涉及内容

### 新增文件

- `src/features/cameraStage/application/`：3D 正式应用服务、领域提供者和反射定义。
- 对应 application service 与反射测试。

### 修改文件

- `src/core/assistant/capabilities/cameraStageApplicationCapabilities.ts`：收敛为语义操作定义和薄适配。
- `src/features/assistant/hostActions.ts`：移出 3D 持久业务逻辑并控制文件体积。
- `src/features/cameraStage/domain/sceneTypes.ts`、`shotTypes.ts`、`animatableProps.ts`：仅补足可复用 schema 或元数据，不引入 assistant 依赖。
- 3D Store/UI 调用点：改为通过应用服务提交持久变更。

### 可能废弃

- 3D 助手专用安全 Patch 和重复 Store 写入函数：在 UI 与能力都切换后删除。
