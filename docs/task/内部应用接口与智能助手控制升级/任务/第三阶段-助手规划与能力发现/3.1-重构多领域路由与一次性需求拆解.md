# 3.1 重构多领域路由与一次性需求拆解

## 任务状态

- 状态：待开始
- 所属阶段：第三阶段 · 助手规划与能力发现
- 前置任务：1.1
- 关联任务：3.2、3.3、4.4
- 是否可以并行：可以；可与 2.1 开始后的内核实现并行，但 3.2 集成前需等待 2.2

## 任务目标

让 Router 把一次用户请求解析为多个有顺序和依赖的任务 Facet，而不是只返回一个领域标签；同时识别目标 Surface、必须先观察的实体、可并行步骤、预期结果和停止条件，为后续一次性能力激活提供完整输入。

## 当前情况

- `electron/main/services/agent-runtime/context/router.ts` 当前以单一 `AgentIntent` / `AgentToolDomain` 决策为主。
- 代表性 3D 请求只被识别为 `canvas`，没有同时识别 `camera_stage` 和 `navigation`。
- `prompt-layers.ts` 主要靠文字限制重复搜索，不能替代结构化任务分解。
- 既有计划、持久运行和 working summary 可以承载更丰富任务图，无需重写 runner。

## 实施方案

扩展路由结果为有版本的任务 Facet 集合。每个 Facet 声明领域、目标、所需观察、能力类别、目标 Surface、依赖、可并行性、完成条件和置信度。确定性规则负责明显领域和安全边界，模型分类器补充开放语义；二者输出同一 schema。

## 执行步骤

1. 定义多 Facet 路由 schema、依赖边和 Surface 提示，不破坏现有 intent 的兼容读取。
2. 扩展确定性规则，使包含项目创建、3D 场景、运镜和界面打开的组合请求能同时识别多个领域。
3. 调整模型路由提示与解析器，要求给出目标实体、观察需求、完成条件和不确定项，而非直接猜工具名。
4. 生成可持久化的初始任务图，并与现有工作计划/summary 事件关联。
5. 为单领域、跨领域、无操作问答、歧义请求和不支持请求增加路由测试。
6. 确保路由失败有保守回退，不默认激活全部能力。
7. 更新任务记录并独立提交。

## 涉及内容

### 新增文件

- `electron/main/services/agent-runtime/context/` 下的 Facet schema 或路由辅助模块，按现有目录职责命名。
- 对应多领域路由测试与回归样例。

### 修改文件

- `electron/main/services/agent-runtime/context/router.ts`：输出多 Facet 决策并控制文件体积。
- `electron/main/services/agent-runtime/context/prompt-layers.ts`：使用结构化任务图替代仅靠提示词限制。
- `src/core/assistant/runtimeContracts.ts` 或相关共享契约：增加可持久化任务图类型。
- `electron/main/services/agent-runtime/evaluation/regression-cases.test.ts`：加入组合需求样例。

### 可能废弃

- 只表达单领域的旧路由字段：迁移期保留只读兼容，删除条件在 1.1 中确定。

## 验收标准

- [ ] 代表性复杂请求能同时得到 3D、导航和必要的项目/画布 Facet。
- [ ] 每个 Facet 有依赖、观察需求、目标 Surface 和完成条件。
- [ ] 路由结果可持久化、恢复并写入现有结构化日志。
- [ ] 歧义或不支持请求不会通过“激活所有工具”掩盖问题。
- [ ] 单领域和非操作型问答行为不回退。
- [ ] 对应 Electron lint、TypeScript、路由和评测测试通过。
- [ ] 任务总览已同步，任务有独立提交。
