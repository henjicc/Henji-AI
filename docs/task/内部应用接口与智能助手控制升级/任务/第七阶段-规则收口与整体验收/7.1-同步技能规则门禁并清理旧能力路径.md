# 7.1 同步技能规则门禁并清理旧能力路径

## 任务状态

- 状态：已完成
- 所属阶段：第七阶段 · 规则收口与整体验收
- 前置任务：5.1、5.2、5.3、5.4、6.1、6.2、6.3、6.4、6.5
- 关联任务：7.2
- 是否可以并行：否；需要所有领域迁移结论稳定

## 任务目标

把新内部应用接口固化为项目唯一开发方式：同步 Codex/Claude 项目技能和规则，扩展能力覆盖门禁，移除已完成迁移的重复能力、旧适配和 assistant 专用业务路径，确保以后新增参数或功能能自动进入统一控制面。

## 当前情况

- `.codex/skills/henji-application-capability/` 与 `.claude/skills/henji-application-capability/` 两份技能要求同步维护。
- `docs/rules/assistant-capability.md` 仍以当前 Application Capability/Surface 注册方式为主。
- `scripts/check-assistant-capabilities.cjs` 尚未覆盖所有实体属性、操作影响、唯一业务入口和未来暴露元数据。
- 迁移期间会保留旧能力薄适配；若不在本阶段清理，将继续增加模型误选和维护成本。

## 实施方案

以 1.2 迁移矩阵为删除清单，以全领域测试为前提逐项移除旧入口。更新规则和两个项目技能，明确新增功能必须同时登记领域服务、反射/操作、Surface/权限、验证和覆盖清单。门禁从“能力有没有注册”升级为“公共控制面是否完整且没有重复来源”。

## 执行步骤

1. 对照迁移矩阵确认所有“迁移/合并/删除”项的测试、同任务删除条件和历史只读展示条件已满足。
2. 删除旧能力薄层、旧 ID、重复 schema、`agentCanvas*` 等已无消费者的专用业务路径，不保留跨阶段兼容执行入口。
3. 扩展检查脚本，验证实体/属性/操作唯一 ID、schemaRef、影响声明、Surface、观察提供者、权限、撤销、验证和领域覆盖。
4. 增加禁止任意 Store Patch、任意脚本执行、重复业务入口和跨层导入的静态门禁。
5. 更新 `docs/rules/assistant-capability.md` 与架构规则中的内部 Application API 边界。
6. 同步修改 Codex 和 Claude 的 `henji-application-capability` 技能及必要 references，保持主技能精简。
7. 更新能力 manifest/seeds 生成方式和 CI 命令，确保未来新增功能、Surface 观察或模型模态门禁漏登记时失败。
8. 运行相关静态检查和回归测试，更新重要记录、任务记录并独立提交。
