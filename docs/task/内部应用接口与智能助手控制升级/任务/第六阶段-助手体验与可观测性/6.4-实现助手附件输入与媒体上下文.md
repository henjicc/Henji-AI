# 6.4 实现助手附件输入与媒体上下文

## 任务状态

- 状态：已完成
- 所属阶段：第六阶段 · 助手体验与可观测性
- 前置任务：6.3
- 关联任务：5.3、5.4、6.1、6.5、7.2
- 是否可以并行：可以；可与第五阶段中不修改助手消息契约的任务并行

## 任务目标

允许用户在助手输入区添加图片、视频和音频附件，使附件能够安全导入、预览、持久化、恢复并按模型能力进入上下文；不支持的模态在发送前给出明确反馈，不能丢失附件或把裸本地路径发给模型。

## 当前情况

- `AssistantComposer.tsx` 当前提交的是文本目标，`useAgentRun.ts` 和运行启动契约没有完整附件参数。
- `LlmChatMessage` 已定义图片、视频和音频内容片段，底层有继续扩展的类型基础。
- 素材库、媒体协议、上传和生成链路已有图片/视频/音频处理能力，但助手尚未复用这些正式入口。
- 媒体字符串可能是裸路径、`henji-media://`、HTTP、data 或 blob；不同消费方要求不同，不能在消息层随意转换。
- 运行持久化、恢复和 Artifact 已存在，本任务不得另建附件数据库或文件通道。

## 实施方案

为助手消息新增稳定附件引用和元数据，文件导入复用素材/媒体持久化服务。Composer 展示可删除、可预览的附件队列；提交前依据 6.3 选择 primary 或 observer 路径并检查数量、类型、大小与时长。持久会话保存引用和安全元数据，发送到模型时才在 provider 边界转换为所需内容片段。

## 执行步骤

1. 定义助手附件 schema：稳定 mediaRef、模态、MIME、大小、时长/尺寸、显示名、数据等级和生命周期，不保存裸路径。
2. 扩展 run 启动、用户消息、事件、持久化、恢复和工作摘要契约，使附件与文本一起保持顺序和引用完整性。
3. 在 `AssistantComposer.tsx` 增加附件选择、拖入/粘贴、预览、移除和提交状态，复用现有 UI primitives、媒体导入和上传入口。
4. 依据模型能力和 provider 约束，在发送前校验图片/视频/音频类型、数量、大小、时长和编码；不支持时保留草稿并给出切换模型建议。
5. 在模型请求构建边界把 mediaRef 解析为可接受的 URL、data 或音频数据；UI 显示和主进程文件读取分别遵守 `media-url.md`。
6. 让 primary 支持时接收原始媒体；只配置 observer 时先生成带来源引用的观察结果，再把结果交给 primary，UI 明确显示这一过程。
7. 为附件持久化失败、源文件丢失、模型切换、用户取消、恢复会话和超限建立结构化错误及恢复路径。
8. 增加附件 reducer、消息序列化、媒体转换、模态门禁和恢复测试；准备用户拖拽/粘贴/预览手动验收步骤。
9. 更新任务记录并独立提交。
