## 一、当前项目现状

### 1.1 技术栈与约束

- Electron 42 / React 18 / Vite 4 + electron-vite / TypeScript / SQLite（better-sqlite3）/ i18next
- 包管理器 npm，根 `package.json` 为 `"type": "module"`、`"private": true`、无 `workspaces` 字段
- 路径别名 `@/` → `src/`，**只配在 `electron.vite.config.ts` 的 renderer 块**，main 与 preload 块没有
- `electron.vite.config.ts` 的 main 块 `rollupOptions.external` 只有 `['better-sqlite3', 'ffmpeg-ffprobe-static']`，其余全部打包进 `out/main`
- `electron-builder.yml` 的 `files` 只收 `out/**` 与 `package.json`；`asarUnpack` 用的是 `node_modules/<原生模块>/**` 的根路径

上述两条决定了一件事：**SDK 作为 workspace 包会被 electron-vite 打包进 `out/`，不进 `node_modules`，因此不影响 `asarUnpack` 的原生模块路径。** 这是选择 monorepo 而非 submodule 的实证依据之一。

### 1.2 生成模型链路现状

```
src/models/**/*.model.ts (99 个)
    │  defineModel() 注册到 src/core/ModelRegistry（渲染层，供 UI 使用）
    │
    └─ scripts/generate-model-manifest.cjs (702 行)
           用 typescript 编译器 API 解析源码 + vm 求值常量
           把 request.builder 序列化成字符串
                  ↓
       resources/model-manifest.json (254 KB)
                  ↓
       electron/main/services/ai-runtime/manifest.ts 读取
                  ↓
       request-builder-dsl.ts → js-runtime.ts 用 node:vm 执行 builder 字符串
                  ↓
       providers/<供应商>.ts 发请求与轮询
```

主进程**完全没有** import 过 `src/models`。序列化链路存在的唯一原因是 `@` 别名不可用（`scripts/check-main-imports.cjs` 的注释对此有完整说明）。

该链路的自述债务：

| 位置 | 内容 |
|---|---|
| `scripts/generate-model-manifest.cjs` `KNOWN_ENDPOINT_CONSTANTS` | 跨文件 import 的端点常量解析不到，镜像一份，注释写明「否则 manifest 与源码静默分叉」 |
| `scripts/generate-model-manifest.cjs` `CUSTOM_BUILDER_OVERRIDES` | 4 个模型的 builder 手抄成字符串：`fal-ai-bytedance-seedream-v4`、`fal-ai-bytedance-seedream-v4.5`、`kie-seedream-4.0`、`kie-seedream-4.5` |
| `electron/main/services/ai-runtime/js-runtime.ts` | JS_PRELUDE 里重实现了 `src/models/modelscope/utils.ts` 的等价函数，注释已标注 |

## 三、总体解决思路

### 3.1 三条切分线

1. **运行环境 ↔ 供应商逻辑**：供应商逻辑写成纯 TypeScript，网络、凭据、文件、日志全部通过接口注入。
2. **模型元数据 ↔ 展示元数据**：SDK 拥有「模型是什么」（id、供应商、端点、请求构建、轮询、参数结构、价格算法、输入限制），痕迹AI 拥有「模型长什么样」（i18n 文案、面板分组、联动、图标）。切分口径见 [重要记录.md](重要记录.md) 记录 003。
3. **两类模型 ↔ 公共抽象**：生成模型与 LLM 各自保留协议差异，但共用凭据、网络、错误、追踪与媒体上传。

### 3.2 迁移策略：逐层搬迁，每步可运行

采用「先建包 → 由内向外逐层搬 → 每搬一层立刻回接 → 最后删旧」的方式，禁止一次性大搬家。

顺序依据是依赖方向：零依赖的纯逻辑先走，带宿主依赖的后走，序列化链路最后删。每个任务完成后痕迹AI 必须能正常运行并通过对应测试。

### 3.3 关键技术决定

- **builder 不再序列化**：SDK 内 builder 是直接 import 的普通函数，主进程直接调用。删除 `js-runtime.ts` 的 `node:vm` 执行、`generate-model-manifest.cjs` 的编译器解析、以及由此产生的全部手抄副本。这同时解决 UXP 无 `vm`、CSP 可能禁用 `new Function` 的问题。
- **模型清单用显式导入**：`catalog/index.ts` 显式 import 全部模型并导出数组，由脚本生成、纳入版本控制。`import.meta.glob` 只在痕迹AI 渲染层的展示层残留（若仍需要）。
- **不做声明式配置语言**：现有 `request-builder-dsl.ts`（184 行）够用。理由见 [重要记录.md](重要记录.md) 记录 007。
- **模型类型开放**：`ModelType` 从 `'image' | 'video' | 'audio'` 闭合联合改为可扩展（见记录 005），为语音识别等新类型预留。

### 3.4 UXP / Tauri 运行时约束（任务 1.1 结论摘要）

任务 1.1 完成了 8 项运行时能力验证（UXP 侧为官方文档调研，Tauri 侧为真实工程验证：`cargo check` 编译通过 + 直接阅读本机 `npm install` 落地的 `@tauri-apps/plugin-http@2.5.9` 真实源码），完整的逐项结论与依据见 [1.1-运行时约束验证.md](任务/第一阶段-可行性验证与基础设施/1.1-运行时约束验证.md) 执行记录。结论未推翻本文件任何架构假设，但产出以下需要后续任务遵守的具体约束：

- **构建产物形态**：UXP 没有运行时 Node 模块解析器，npm 依赖必须在构建期由 webpack/parcel 等打包进最终产物；SDK 的 `dist/` 必须是标准 ESM/CJS，能被主流打包器静态分析，不能依赖运行时动态 `import()`/`require()` 解析 `node_modules`。这条直接约束任务 1.2 的包骨架与构建配置。
- **CSP 默认禁用动态求值**：UXP 官方权限字段 `allowCodeGenerationFromStrings` 默认 `false`，需显式声明才能用 `eval`/`new Function`；即使声明启用，UXP 也没有 `node:vm`（UXP 相比 CEP "has lost Node.js support"）。这双重确认了[重要记录.md](重要记录.md)记录 002 的决定。
- **网络权限通配符**：UXP `manifest.json` 的 `requiredPermissions.network.domains` 支持子域名通配符（如 `https://*.adobe.com`）及 `"domains": "all"`；Tauri capability 的 URL allow-list 同样支持 glob（如 `https://*.apimart.ai/*`，已实测 `cargo check` 通过）。新增供应商域名在两个平台都无需绕过白名单机制，但仍需要在各自 manifest/capability 里显式登记，即新增供应商无论如何都要发版（呼应记录 007）。
- **凭据存储定位**：UXP `SecureStorage` 官方定位是"更像缓存而非持久存储"，key 不加密、value 加密，且建议数据可在丢失后重新生成——`CredentialStore` 接口（任务 2.1）设计时不能假设凭据一定还在。
- **base64 能力**：UXP 没有 `btoa`/`atob`，但有 `TextEncoder`/`Uint8Array`，需要在运行时接口层或上传层（任务 2.1/2.4）提供一个纯 JS 的 base64 polyfill。
- **残留风险（非阻塞，需后续实测）**：UXP 端 SSE/流式响应的稳定性缺乏权威依据（Tauri 端已有较强的包源码级证据），任务 4.2 启动前需要用真实 Photoshop + UXP Developer Tool 环境复核；UXP `imaging.getPixels()`/`getData()` 在 Grayscale/LAB/CMYK 模式下有社区报告的历史问题，任务 2.4 设计 UXP 版 `MediaReader` 时需要单独验证。

## 六、新旧实现兼容方式

### 6.1 迁移期的双轨原则

第二至第四阶段每个任务采用「移动而非复制」：

1. 文件迁入 `packages/ai-sdk/src/`，原位置**直接删除**，不留转发文件。
2. 原引用方改为从包导入。
3. 测试文件一并移动，只改 import 路径，**不改断言**。

**禁止**保留 `export * from '@henjicc/ai-sdk/...'` 这类兼容转发层。理由：同功能多份入口是本项目明确禁止的（`AGENTS.md` 全局禁止事项），且转发层会掩盖迁移遗漏。

### 6.2 `model-manifest.json` 的处置

任务 3.3 删除生成器后，`resources/model-manifest.json` 与 `electron-builder.yml` 的对应 `extraResources` 条目一并删除。是否保留一份供外部消费的目录快照，见 [重要记录.md](重要记录.md) 记录 008（待确认）。

### 6.3 数据与接口兼容要求

- **IPC 通道签名不变**：`ai:generate`、`ai:continuePolling`、`llm:chatStream`、`llm:modelStep` 等通道的 payload 与返回结构在第二至第四阶段不得改变。渲染层不应感知到迁移。
- **模型 ID 与别名不变**：99 个模型的 `meta.id`、`canonicalModelId`、`aliases` 全部保持原值。用户的历史记录、画布项目、预设都按这些 ID 存储，改动会导致存量数据失配。
- **参数 ID 不变**：`params[].id`（如 `kieGrokImagineVideoResolution`）是持久化字段名，迁移过程中不得重命名。
- **SQLite 表结构不变**：进度样本、待取结果、LLM 配置的表结构不在本次范围内。

| 删除 manifest 后主进程打包体积或启动时间变化 | 桌面端启动变慢 | 任务 3.3 记录删除前后 `out/main` 体积与冷启动耗时 |

| 参数 ID 或模型 ID 在迁移中被改写 | 存量项目数据失配 | 任务 3.2 用脚本对比迁移前后的 ID 全集，必须完全一致 |

**回退原则**：每个任务一次独立提交，回退即 `git revert` 该提交。禁止把多个任务混进一次提交。若某任务需要多次提交才能完成，最后必须 squash 成一次。

## 八、全局开发约束

1. 遵守 `AGENTS.md` 与 `docs/rules/` 全部既有规则，本任务不豁免任何一条。
