# 4.3 统一两类模型的公共抽象

## 任务状态

- 状态：已完成
- 所属阶段：第四阶段 大语言模型迁移
- 前置任务：4.2、3.3
- 关联任务：5.1、5.2
- 是否可以并行：否

## 任务目标

生成模型与大语言模型两条链路都进入 SDK 后，把它们各自实现的重复层——凭据、网络、错误分类、追踪、取消——收敛成单一实现，消除 SDK 内部的同功能多份实现。

## 当前情况

两条链路迁移完成后，SDK 内会同时存在以下重复：

| 能力 | 生成模型侧 | LLM 侧 | 现状 |
|---|---|---|---|
| 凭据 | `CredentialStore.get('generation', id)` | `CredentialStore.get('llm', id)` | 接口已统一（2.1），但主进程是两个独立 keystore 函数 |
| 网络 | `providers/provider-fetch.ts` 的 `fetchProvider`（含 `retryPreconnectOnce`） | `llm/streaming.ts` 自己发请求 | **两份实现** |
| 错误 | `runtime/errors.ts` 的 `AiRuntimeError` + 错误码 | `llm/sdk/provider-error.ts`(222 行) 自成一套 | **两份实现** |
| 重试 | `provider-fetch.ts` 的预连接重试 + `polling.ts` 的连续失败容忍 | `llm/sdk/retry-policy.ts`(80 行) | **两份实现** |
| 取消 | `runtime/task-registry.ts` | `llm/task-registry.ts`(21 行) | **两份实现，逻辑近乎相同** |
| 追踪 | `electron/.../trace.ts`（留主进程） | `llm/sdk/trace.ts`（按 4.2 决定） | 待 4.2 结论 |
| 媒体上传 | `upload/preprocess.ts` | 直接复用生成模型侧（已统一） | ✅ 已统一 |

**注意**：`AGENTS.md` 全局禁止事项明确禁止「同功能多份实现」。上表中标为「两份实现」的 4 项，若不在本任务收敛，就是把外部的重复搬进了 SDK 内部。

## 实施方案

**收敛原则：保留语义更强的一方，另一方作为它的特化，而不是取最小公倍数。**

具体判断：

- **取消**：两份 `task-registry` 逻辑几乎相同（内存 Set + AbortController Map），直接合并为一份，用命名空间区分生成任务与 LLM 任务。
- **网络**：`fetchProvider` 的 `retryPreconnectOnce` 语义（只对未建立连接的错误重试，避免重放计费请求）对 LLM 同样成立且更重要（LLM 按 token 计费）。以 `fetchProvider` 为基础，LLM 侧的流式需求作为它的一个选项。
- **错误**：`provider-error.ts`(222 行) 的分类比 `AiRuntimeError` 细（区分鉴权、余额、限流、上下文超长、内容过滤等）。**以 LLM 侧为基础**扩展出统一错误模型，生成模型侧的错误码映射进去。这是本任务改动最大的部分。
- **重试**：`retry-policy.ts` 与 `polling.ts` 的连续失败容忍解决的是不同问题（前者是单次请求重试，后者是轮询查询失败容忍），**不强行合并**，但要共用同一套「什么错误值得重试」的判断。

**不统一的部分要写清理由**：生成模型的「创建任务 + 轮询」与 LLM 的「流式响应」是本质不同的协议，不应强行统一成一个 `execute`。

## 执行步骤

1. 合并两个 `task-registry`：保留 `runtime/task-registry.ts`，增加命名空间参数；删除 `llm/task-registry.ts`；更新两侧调用点。
2. 统一错误模型：
   - 在 `runtime/errors.ts` 中以 `provider-error.ts` 的分类为基础扩展错误码集合
   - 生成模型现有错误码（`empty_result`、`provider_task_failed`、`provider_task_unreachable`、`invalid_route`、`cancelled`、`api_key_missing` 等）映射进统一集合，**原有错误码字符串保持不变**（渲染层与日志可能依赖）
   - 删除 `llm/sdk/provider-error.ts`，逻辑并入 `runtime/errors.ts`（若超过 400 行则拆成 `errors.ts` + `error-classify.ts`）
3. 统一网络层：LLM 的流式请求改为经 `provider-fetch.ts`（按 4.2 结论，若 `Transport` 已为流式扩展则复用该路径）。
4. 统一重试判断：抽出 `shouldRetry(error)` 单一实现，`retry-policy.ts` 与 `polling.ts` 共用。
5. 统一追踪：按 4.2 的 trace 归属决定，把生成模型侧的 trace 构建（当前在 `electron/.../trace.ts`）与 LLM 侧对齐到同一个 `Tracer` 接口。
6. 检查 `CredentialStore` 的 scope 机制是否够用；主进程 `sdk-runtime.ts` 的实现应把 `getAiProviderApiKey` 与 `getLlmProviderApiKey` 收在一个实现里。
7. 在 `packages/ai-sdk/README.md` 记录「哪些层是统一的、哪些层刻意保持分离及原因」。
8. 全量回归两条链路。
