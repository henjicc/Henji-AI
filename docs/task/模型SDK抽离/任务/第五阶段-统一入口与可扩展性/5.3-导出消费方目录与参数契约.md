## 任务目标

让 SDK 对外导出足以让消费方**自动生成参数表单**的目录契约。这是「新项目接入一个模型的边际代码为 0 行」这一目标能否兑现的关键——若消费方拿不到参数结构，就还得回去翻文档。

## 当前情况

### 问题的由来

原 `resources/model-manifest.json` 的 `ModelManifestItem` 只有：

```
modelId / aliases / aliasParamDefaults / aliasParamMappings / providerId
modelType / polling / progress / progressLearning / endpoints / request / runtimeConstraints
```

**没有 `params`**。它是「纯执行用」的清单，参数 schema 全留在渲染层供 UI 使用。任务 3.1 定义的 `ModelRuntimeDefinition` 已按 [重要记录.md](../../重要记录.md) 记录 003 把 `params` 的取值契约纳入 SDK，本任务把它整理成对外契约并验证够用。

### 参数结构的组成

`src/core/types/ParamDef.ts`（708 行）包含多种参数类型。执行本任务前需要先枚举清楚 SDK 侧 `RuntimeParamDef` 实际覆盖了哪些 `type`（dropdown / number / text / slider / switch / 复合面板等），以及哪些是纯展示结构不该导出。

### 消费方的实际需要

一个消费方要自动生成表单，需要知道：参数 ID、控件类型、默认值、可选值集合、数值范围与步长、显示顺序、条件显隐（某参数在什么条件下才出现）、以及「哪些参数是媒体输入」（媒体不能用文本框，见 `AGENTS.md` 全局禁止事项）。

价格计算 `pricing.calculator` 是函数，消费方直接调用即可，不需要额外契约。

## 实施方案

导出两层：

1. **类型层**：`ModelRuntimeDefinition` 及其 `params` 结构，消费方用 TypeScript 直接消费，有完整类型提示。
2. **数据快照层**（可选）：若 [重要记录.md](../../重要记录.md) 记录 008 确认需要非 TypeScript 消费方，提供一个由目录序列化产出的 JSON。**若无此需求则不做**。

同时提供几个便利查询函数，避免每个消费方都自己写一遍：按类型/供应商/标签筛选、取默认值集合、判断参数是否为媒体输入。

**验证方式是关键**：不能靠「看着够用」，必须真的写一个通用表单渲染器（放在 6.3 的示例里）跑一遍，才能证明契约完整。

## 执行步骤

1. 枚举 `RuntimeParamDef` 实际覆盖的全部 `type`，列成表写进 `packages/ai-sdk/README.md`，每种类型说明消费方应渲染成什么控件。
2. 确认条件显隐结构（`ConditionTypes.ts` 相关）已完整进入 SDK 侧；若 3.1 遗漏则补上。
3. 确认媒体输入参数可被识别：消费方需要能判断「这个参数是图片输入」，从而渲染上传按钮而非输入框。检查 `inputLimits` 与 `runtimeConstraints.mediaFields` 是否够表达。
4. 实现便利查询函数并挂到 `client.catalog`：
   - `listByType(type)` / `listByProvider(id)` / `listByTag(tag)`
   - `getDefaultValues(modelId)`：返回全部参数默认值
   - `getParams(modelId)`：返回 `RuntimeParamDef[]`
   - `estimatePrice(modelId, params)`：包装 `pricing.calculator`
5. 处理 [重要记录.md](../../重要记录.md) 记录 008：确认是否需要 JSON 快照。需要则实现生成脚本并接入构建；不需要则把记录 008 状态改为「已确定：不做」。
6. 写一份「参数类型 → 控件」的对照表进 README。
7. 用一个最小表单渲染器验证契约完整（可先写在 `packages/ai-sdk/examples/` 里，6.3 再完善）：选 5 个参数结构差异最大的模型，确认全部能渲染。
