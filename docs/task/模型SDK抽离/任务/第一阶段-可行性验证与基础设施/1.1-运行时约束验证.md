# 1.1 运行时约束验证

## 任务状态

- 状态：已完成
- 所属阶段：第一阶段 可行性验证与基础设施
- 前置任务：无
- 关联任务：1.2（骨架设计依赖本任务结论）、3.3（删除 VM 执行的可行性依据）
- 是否可以并行：否（本任务是整个计划的前置闸门）

## 任务目标

在投入任何迁移工作之前，用最小成本验证「纯 TypeScript 的供应商适配层能在 Photoshop UXP 与 Tauri 中运行」这一架构前提是否成立，并产出一份明确的运行时能力清单。若 UXP 侧不成立，整个方案需要重新设计而不是继续往下做。

本任务**不写正式代码**，产出物是一份验证结论文档 + 一次性的验证脚本（验证完即可丢弃）。

## 当前情况

- 痕迹AI 当前的执行链路依赖 `node:vm`（`electron/main/services/ai-runtime/js-runtime.ts`，171 行）执行序列化后的 builder 字符串。UXP 无 `node:vm`，且插件 CSP 很可能禁用 `eval` / `new Function`。这是最可能推翻方案的一点。
- UXP 要求所有访问的域名写入插件 `manifest.json` 的网络权限；Tauri HTTP 插件要求配置允许访问的 URL。当前项目访问的域名至少包括：`https://api.kie.ai`、`https://api.apimart.ai`、`https://api.apib.ai`、`https://api.aiuxu.com`、`https://api.aishuch.com`（`apimart-endpoints.ts`）、`https://grsaiapi.com`、`https://grsai.dakka.com.cn`（`grsai-endpoints.ts`），以及 fal / ppio / modelscope / bailian / volcengine 的域名（分散在各自的 `providers/*.ts`）。
- 现有 `providers/kie.ts`（123 行）是最典型的「创建任务 + 轮询 + 复杂结果解析」链路，适合作为验证样本。
- 用户的 Tauri 项目与 Photoshop UXP 插件项目是否已经存在，**待确认**。若尚未创建，本任务用最小空白工程验证。

## 实施方案

用 `providers/kie.ts` 的逻辑做一个 100 行以内的独立 spike，分别在 UXP 与 Tauri 环境里跑通「创建任务 → 轮询 → 拿到结果 URL」，重点验证的不是业务正确性，而是**运行时能力边界**。

验证清单固定为下面 8 项，逐项记录「支持 / 不支持 / 有条件支持」。

## 执行步骤

1. 在 `packages/` 之外的临时目录（或 scratchpad）创建 spike 工程，不进入本仓库版本控制。
2. 编写一个不依赖任何 Node API 的最小 KIE 客户端：`POST https://api.kie.ai/api/v1/jobs/createTask` → 取 `data.taskId` → 轮询 `GET /api/v1/jobs/recordInfo?taskId=` → 解析 `data.resultJson`。逻辑照抄 `electron/main/services/ai-runtime/providers/kie.ts`。
3. 在 **Photoshop UXP** 中逐项验证：
   - `fetch` 是否可用、是否支持 `AbortSignal`
   - `manifest.json` 网络权限的配置方式与通配符支持程度
   - CSP 是否禁用 `eval` / `new Function`
   - 打包后是否能加载 npm 依赖（确认必须在构建期打包、不能运行时从 `node_modules` 解析）
   - `TextEncoder` / `Uint8Array` / `btoa` 或等价的 base64 能力是否可用（上传层需要，见任务 2.4）
   - 从 Photoshop 文档导出图层字节的 API 与耗时（`MediaReader` 实现的成本评估）
   - SecureStorage 的可用性与限制
   - SSE / 流式响应的可行性（LLM 侧需要，见任务 4.2）
4. 在 **Tauri** 中验证同样 8 项，其中网络走 `@tauri-apps/plugin-http` 的 `fetch`，注意确认它对流式响应与 `AbortSignal` 的支持程度。
5. 记录每一项的结论、限制与规避方式。
6. 把结论写入本文件的「执行记录」，并把影响架构的结论回填到 [01-实施方案.md](../../01-实施方案.md) 第三节与 [重要记录.md](../../重要记录.md)。
7. 若 UXP 的 CSP 禁用动态求值（预期如此），确认 [重要记录.md](../../重要记录.md) 记录 002 的决定仍然正确；若发现 UXP 连普通 `fetch` 或 npm 打包都不可行，**立即停止后续任务**并向用户报告，方案需重新设计。

  | # | 验证项 | UXP 结论 | 依据 | Tauri 结论 | 依据 |
  |---|---|---|---|---|---|
  | 1 | `fetch` 可用性 + `AbortSignal` | **支持**。`fetch` 全局可用；`AbortController` 有独立官方文档页（`Global Members/HTML DOM/AbortController`） | 文档调研 | **支持**（强证据）。`@tauri-apps/plugin-http@2.5.9` 真实源码 `fetch()` 完整处理 `init.signal`：请求前检查 `signal.aborted`，请求中监听 `abort` 事件调用 Rust 端 `plugin:http\|fetch_cancel` 释放连接，body 读取阶段 abort 也会调用 `fetch_cancel_body` | 包源码实读（本机 `npm install` 落地版本），非端到端实测 |
  | 2 | `manifest.json`/capability 网络权限通配符支持程度 | **支持**。官方 manifest v5 指南示例出现 `https://*.adobe.com` 这类子域名通配符，也可设 `"domains": "all"`；但 `requiredPermissions.webview.domains`（跳转外部页面用的白名单）**不支持**通配符——这是网络请求权限与 webview 跳转权限的两套白名单，我们只用前者 | 文档调研 | **支持**。官方插件源码注释给出示例 `{"url": "https://*.tauri.app"}`；本次在 spike 的 `capabilities/default.json` 写入 `"https://*.apimart.ai/*"` 并通过 `cargo check`（`tauri-build` 会在编译期校验 capability schema） | 文档 + 真实编译验证 |
  | 3 | CSP 是否禁用 `eval`/`new Function` | **默认禁用**。官方权限字段 `allowCodeGenerationFromStrings`，默认值 `false`，需显式在 manifest 声明才能用 `eval()`/`new Function()`/内联事件处理器。即使声明启用，UXP 本身**没有 Node.js 运行时**（官方原话：UXP 相比 CEP "has lost Node.js support"），因此 `node:vm` 在 UXP 上不存在，与 CSP 设置无关——「序列化 + VM 执行」路线在 UXP 上双重不可行 | 文档调研 | 不适用/非阻塞项。Tauri 前端是标准 webview，`eval` 存在与否是产品自己的选择，架构已决定不用 | — |
  | 4 | 打包后能否加载 npm 依赖（构建期 vs 运行时） | **有条件支持**：必须用 webpack/parcel 等在构建期把依赖打进最终产物，UXP **没有运行时 Node 模块解析器**，不能像 Node.js 那样运行时 `require()` 任意 `node_modules` 包（官方社区原话：仍可 `import npm modules`，但"there is no mixed-context anymore, nor default packages such as fs, path"） | 文档调研 | **支持**，同样是构建期打包（前端默认 Vite，Rust 端 crate 是 Cargo 编译期静态链接），已用 `cargo check` 实测确认可编译链接 | 真实编译验证 |
  | 5 | `TextEncoder`/`Uint8Array`/`btoa` 或等价 base64 能力 | **有条件支持**：`TextEncoder`/`TextDecoder`/`Uint8Array` 官方文档确认可用（fs 模块示例代码直接用 `new TextEncoder().encode(data)`）；但 `btoa`/`atob` **不在** UXP 全局对象里（社区多次反馈 "atob is not defined"），需要基于 `Uint8Array` 手写一个纯 JS 的 base64 encode/decode（标准写法，体积小，无第三方依赖，不构成实质阻碍） | 文档调研 + 社区证据 | **支持**。webview 内核是标准 Chromium/WebKit/WebView2，`TextEncoder`/`btoa` 都是原生浏览器 API | 常识性确认，未单独实测 |
  | 6 | 从 Photoshop 文档导出图层字节的 API 与耗时 | **支持**，通过 `photoshop.imaging.getPixels()` 取 `PhotoshopImageData`，再 `.imageData.getData()` 取底层字节；社区实测约 1000×1000 像素 1 秒左右量级。已知坑（均为社区/issue 追踪证据，未见官方修复公告）：Grayscale/LAB 模式下 `getPixels()` 通道数处理有历史 bug（AdobeDocs/uxp-photoshop#501）；CMYK 模式下 `imageData.getData()` 曾有崩溃报告。这条只影响任务 2.4 的 `MediaReader` 里 Photoshop 专属实现，不影响 SDK 核心可移植性 | 文档调研 + 社区证据，**非实测**（无 Photoshop 环境） | 不适用（Tauri 不跑在 Photoshop 里，无图层概念） | — |
  | 7 | SecureStorage 可用性与限制 | **支持，但有明确限制**：`require('uxp').storage.secureStorage`，键值对，value 加密存储，但 **key 本身不加密**；官方明确定位为"更像缓存而非持久存储"，建议数据要能在丢失后从插件内重新生成——**不能把它当唯一的凭据持久层**，需要有丢失后的重新登录/重新配置路径 | 文档调研 | **有条件支持**：Tauri 官方生态里 `tauri-plugin-store` 是明文 JSON（不加密），真正加密的凭据存储要用 `tauri-plugin-stronghold` 或社区 keyring 插件，本次未实测，只是文档层面确认存在对应方案 | 文档调研，未实测 |
  | 8 | SSE / 流式响应可行性 | **有条件支持，证据不完整**：UXP 全局 `Streams`（`ReadableStream`/`WritableStream`/`TransformStream`）有独立官方文档页，具备流式读取的基础能力，`fetch` 的 `Response.body` 理论上可以是流；但**未找到官方文档或社区案例明确验证** UXP 对 `text/event-stream`（长连接、持续 chunked 推送）这类 SSE 场景的稳定性，标记为残留风险，需要任务 4.2（LLM 执行层迁移）之前用真实 Photoshop 环境复测 | 文档调研，**证据不完整** | **支持**（强证据）。`@tauri-apps/plugin-http` 真实源码里 `Response.body` 是 `ReadableStream`，通过 IPC `fetch_read_body` **逐 chunk** 拉取直到收到"结束标志字节"，是标准分块流式实现，SSE 场景（本质是持续 chunked 响应）应当可用 | 包源码实读，未做端到端真实 SSE 服务器联调 |
