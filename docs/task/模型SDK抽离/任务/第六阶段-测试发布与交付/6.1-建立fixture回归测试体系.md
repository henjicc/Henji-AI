## 任务目标

为 8 个供应商建立基于真实响应快照的回归测试，覆盖「请求构建」与「响应解析」两个纯函数环节。这是敢于改动 SDK 的前提，也是任务 3.2 迁移 99 个模型时唯一能发现静默请求体差异的手段。

## 当前情况

### 已有测试的性质

| 测试 | 数量 | 覆盖什么 |
|---|---|---|
| `packages/ai-sdk/tests/providers/*.test.ts`（2.3 迁移） | 25 用例 | 适配器行为，含 mock 响应 |
| `packages/ai-sdk/tests/catalog/model-adaptation-*.test.ts`（3.2 迁移） | 89 用例 | **请求体断言**，按模型验证 builder 输出 |
| `polling.test.ts`(5)、`media-fields.test.ts`(17)、`upload*.test.ts`(11) | 33 用例 | 协议与上传层 |

`model-adaptation-*.test.ts` 这批（kie 22、apimart 29、fal 6、grsai 8、ppio 5、modelscope 10、official-images 6）已经是事实上的请求体回归测试，**本任务不是从零开始，而是把它们体系化并补齐响应解析侧**。

### 缺口

1. **响应解析侧覆盖不足**：`kie.ts` 的 `extractUrls` 要处理 `data.resultJson` 这个 JSON-in-JSON、5 个指针、深度遍历 `resultObject`——这是最容易出错的地方，但只有 `kie.test.ts` 4 个用例。
2. **没有真实响应快照**：现有 mock 是手写的简化结构，不是供应商实际返回的完整 payload。真实响应里的意外字段、空数组、错误分支都没覆盖。
3. **没有统一的 fixture 组织方式**：新增供应商时不知道该补哪些快照。

### 现成的采集途径

项目已有日志链路可以拿到真实 payload：`runtime.ts` 记录 `generation.runtime.request_json` 与 `generation.runtime.response_json` 事件，`npm run logs:query -- --chain <runId>` 可按链路查询。这是采集 fixture 的最低成本路径，**不需要额外付费重跑**（历史日志里已有）。

## 实施方案

fixture 按「供应商 / 场景」组织，每个场景一个 JSON 文件，包含 `request`（期望的请求体）与 `response`（真实响应）两部分。测试对 fixture 做两个方向的断言：

- 正向：给定 params → 构建出的请求体等于 `request`
- 反向：给定 `response` → 解析出的结果 URL 等于 `expected`

**采集来源必须是真实日志**，禁止手写「看起来对」的响应结构——手写的 fixture 只能证明代码符合作者的想象。

**脱敏是硬性要求**：日志里的 API Key、用户 prompt、结果 URL 中的签名参数必须替换。项目已有 `sanitizeJsonValue`（`electron/main/services/logging`），采集脚本应复用其规则。

## 执行步骤

1. 设计 fixture 目录结构与文件格式，写进 `packages/ai-sdk/tests/fixtures/README.md`：
   ```
   fixtures/<供应商>/<场景>.json
   { "modelId": "...", "params": {...}, "expectedRequest": {...},
     "response": {...}, "expectedUrls": [...] }
   ```
2. 写采集脚本 `scripts/collect-provider-fixtures.cjs`：从日志库按 `event` 提取 `generation.runtime.request_json` 与 `generation.runtime.response_json` 配对，脱敏后写成 fixture 草稿。
3. 为 8 个供应商各采集至少 3 个场景，**必须包含**：
   - 一个成功的创建任务响应
   - 一个成功的轮询完成响应（含结果 URL）
   - 一个失败响应（供应商报错）
4. KIE 额外补齐结果解析的边界场景：`resultJson` 为 JSON 字符串、结果在 `resultObject` 深层、多结果 URL、首尾帧字段（`firstFrameUrl` / `lastFrameUrl`）。
5. ApiMart 与 GRSAI 补多域名切换场景的 fixture。
6. 写 fixture 驱动的测试 `packages/ai-sdk/tests/fixtures.test.ts`：遍历全部 fixture 做正反双向断言。
7. 在 `packages/ai-sdk/tests/fixtures/README.md` 写清「新增供应商时必须补哪些 fixture」，并把这条加进 `docs/rules/model-adaptation.md` 的适配流程。
8. 确认 fixture 中不含任何密钥、真实用户 prompt 或带签名的可访问 URL。
