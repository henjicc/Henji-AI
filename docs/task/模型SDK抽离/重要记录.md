# 重要记录：模型 SDK 抽离

> 只记录会影响整个计划或多个任务的重要决定。普通实现细节写在各自任务文件的执行记录里。

## 记录 001：SDK 放在本仓库 monorepo 子包，不使用 submodule

- 日期：2026-08-27
- 状态：已确定
- 背景：候选方案有三个——独立 Git 仓库、Git submodule、npm workspaces 子包。用户最初倾向独立仓库，担心「放在项目里以后拆不出来」。
- 最终决定：使用 npm workspaces，SDK 位于 `packages/ai-sdk/`，是本仓库内的普通目录，不是独立 Git 仓库。
- 选择原因：
  1. 需要拆分时 `git subtree split --prefix=packages/ai-sdk` 可随时生成带完整历史的独立仓库，「可拆分」这个属性无需提前付费获得。
  2. submodule 对单人维护是净负担：detached HEAD、易忘记 push、clone 需 `--recursive`、两侧联动改动无法用一次提交说清。
  3. 痕迹AI 仍在高频新增模型，monorepo 让本地开发保持「改文件即生效」的零摩擦；独立仓库会变成「改 SDK → 发版 → 升依赖 → 验证」。
  4. 实证：`electron-builder.yml` 的 `files` 只收 `out/**`，SDK 会被 electron-vite 打包进 `out/`，不进 `node_modules`，因此不影响 `asarUnpack` 里 better-sqlite3 / sharp 等原生模块的根路径。
- 影响任务：1.2、6.2

## 记录 002：builder 从「序列化 + VM 执行」改为直接函数调用

- 日期：2026-08-27
- 状态：已确定
- 背景：当前 `scripts/generate-model-manifest.cjs`（702 行）用 TypeScript 编译器 API 解析模型源码、把 `request.builder` 序列化成字符串写进 `resources/model-manifest.json`，主进程再用 `node:vm` 执行。该设计存在的唯一原因是 `@` 别名只配在 renderer 块，主进程 import 不到 `src/models`（见 `scripts/check-main-imports.cjs` 注释）。
- 最终决定：SDK 内 builder 是直接 import 的普通函数；主进程从包里 import 并直接调用。删除 `generate-model-manifest.cjs`、`js-runtime.ts`、`manifest.ts` 以及 `resources/model-manifest.json`。
- 选择原因：
  1. SDK 是独立包、内部不用 `@` 别名，主进程 import 它与 import 任何 npm 包无异，序列化的理由消失，且不违反 `AGENTS.md` 规则 4 的跨层导入禁令。
  2. 还清既有债务：`CUSTOM_BUILDER_OVERRIDES` 里 4 个模型的 builder 手抄副本、`KNOWN_ENDPOINT_CONSTANTS` 镜像常量、`js-runtime.ts` JS_PRELUDE 里 `src/models/modelscope/utils.ts` 的影子实现，全部随之消失。生成器注释自述该链路会「与源码静默分叉」。
  3. UXP 没有 `node:vm`，且 CSP 很可能禁用 `eval` / `new Function`，序列化路线在 UXP 上不可行。
- 影响任务：1.1、3.2、3.3、6.4

## 记录 003：模型定义的归属切分口径

- 日期：2026-08-27
- 状态：已确定
- 背景：`*.model.ts` 目前混合了运行时契约与界面展示契约。需要确定哪些字段进 SDK、哪些留痕迹AI。
- 最终决定：**SDK 拥有「模型是什么」，痕迹AI 拥有「模型长什么样」。**

  | 字段 | 归属 |
  |---|---|
  | `meta.id` / `canonicalModelId` / `provider` / `type` / `tags` / `aliases` / `polling` | SDK |
  | `endpoints` / `request` / `runtimeConstraints` | SDK |
  | `inputLimits` / `pricing`（含 `calculator` 函数） | SDK |
  | `params[]` 的 `id` / `type` / `default` / `options[].value` / `min` / `max` / `step` / `order` / 条件显隐 | SDK |
  | `progress` / `progressLearning` 的配置数据 | SDK（消费与落库仍在主进程） |
  | `meta.name` / `meta.description` / `meta.i18nScope` / `params[].name` / `options[].label` | 痕迹AI |
  | `linkages` / 面板分区与分组 / `panelWidth` / 图标 | 痕迹AI |

- 选择原因：`params[].id` 与取值范围同时是界面契约和 builder 的输入契约，切成两半就必须手工同步——那正是 `KNOWN_ENDPOINT_CONSTANTS` 已经踩过的坑。i18n 与面板布局是真正的产品资产，与模型能力无关，留在应用侧。
- 影响任务：3.1、3.2、3.4、5.3

### 澄清补充（任务 3.1 落地后回填，原表格保留不改）

任务 3.1 手工拆分 3 个代表性模型（`grok-imagine-video` 简单样本、`minimax-speech` 复杂样本、`apimart-midjourney` 带 `linkages`+`paramPresentation` 样本）后，发现原表格没有覆盖到的几类字段，口径如下：

1. **`params[].role`（渠道/模式角色）与 `params[].socketType`（画布插槽类型覆盖）划给痕迹AI**，不是 SDK。两者都不参与请求构建：`role` 只影响面板里参数的排序位置（`modelParamConventionValidator` 校验的是产品摆放约定），`socketType` 只影响画布连线颜色与兼容性判断（消费方全在 `src/features/canvas/**`）。这条是原表格「条件显隐」之外遗漏的两个 `ParamDef` 字段，补记以免 3.2 误判成运行时字段。
2. **`composite` 类型参数（`panel`/`config` 两个字段）整体划给痕迹AI**，不是像 dropdown 那样只切 `options[].value`。原因：`composite` 参数没有结构化的取值枚举——它绑定哪个特殊面板组件（音色选择器/复合布局/自定义面板）、面板内部怎么配置（音色列表、子组件标签、数值范围）完全是"怎么交互、长什么样"；请求构建器自始至终只读这个参数的当前值（一段不透明 JSON），从不关心它是用哪种面板选出来的。全仓库 99 个模型里只有 1 个（`minimax-speech`）用到 `composite` 类型，风险面很小。SDK 侧 `RuntimeCompositeParamDef` 因此只剩 `id`/`order`/`default`/`api*` 这层壳。
3. **`resolution`/`aspect-ratio` 两种参数类型比照 dropdown 处理**：`presets[].value`/`options[].value` 留 SDK，`label`（`resolution` 是 I18nText，`aspect-ratio` 历史遗留是纯字符串）与 `icon` 留痕迹AI。这是原表格「`options[].value`」条目的自然延伸，原表格只字面提到了 dropdown/radio 的 `options`，3.2 迁移这两种类型时按同一口径处理，不是新决定。
4. **`params[].apiField`/`apiTransform`/`apiMapping`/`transferKey` 明确划给 SDK**：都是请求字段映射/跨模型参数迁移的运行时行为，原表格没有逐字列出（只写了笼统的"取值契约"），这里补充确认。
5. **顶层 `requirements`（生成前置条件）整体留 SDK**，原表格未提及这个字段。`GenerationRequirement.message.title`/`message.message` 历史上一直是纯字符串、不是 `I18nText`（既有产品资产的已知缺口，3.1 如实保留，不顺手"修正"），因此整段 `requirements` 结构不依赖 `I18nText` 类型，可以完整放进 `ModelRuntimeDefinition` 而不违反"SDK 不碰 I18nText"的边界。同理 `Linkage` 类型内的 `reason?: string`（调试/禁用原因说明）虽然是纯字符串，但 `linkages` 整体已经因为 `trigger`/`effect`/`condition` 这些展示编排语义划给痕迹AI，不受此例影响。
6. **`ModelTag` 在 SDK 侧简化为 `type ModelTag = string`**，不搬运应用侧 `KnownModelTag` 的完整字面量清单（`src/core/types/ModelTags.ts` 那份连同中文描述表 `TAG_DESCRIPTIONS` 是标签管理 UI 用的产品资产）。SDK 只需要知道"这是一串标签字符串"，枚举校验留在应用侧或未来的标签注册表（任务 5.1/5.2 可能涉及）。
7. `packages/ai-sdk/src/types/model.ts` 里的 `ProgressConfig`/`ProgressLearningConfig`/`ProgressLearningSegment` 与既有 `types/runtime.ts`（任务 2.2 迁入的序列化 manifest DSL 类型）同名冲突，已重命名为 `ModelProgressConfig`/`ModelProgressLearningConfig`/`ModelProgressLearningSegment`——两者概念不同（`model.ts` 是保留真函数的源码契约，`runtime.ts` 是去函数化后的可序列化清单格式），3.2/3.3/3.4 迁移时注意不要用错名字。

## 记录 004：大语言模型纳入本次范围

- 日期：2026-08-27
- 状态：已确定
- 背景：初步建议是第一版 SDK 只做异步任务式生成模型，不碰 LLM——理由是 OpenAI 兼容协议已被 Vercel AI SDK 解决，自建收益低。用户明确要求 LLM 一并纳入，且要求为将来的语音识别等新模型类型预留扩展。
- 最终决定：LLM 纳入范围，作为独立的第四阶段。但**保留原有的架构差异，不强行与生成模型统一成一套模型定义**。
- 选择原因与约束：
  1. LLM 供应商是**用户在设置页自建**的，不是代码里的固定枚举；`providerPresets.ts` 只提供 7 个预设起点。生成模型的「99 个写死的模型定义」模式不适用。
  2. LLM 走统一 `openai-compatible` 协议，差异集中在 `providerProtocol.ts` 的认证头与请求体 quirks 表；生成模型则是每家一套私有 REST + 轮询。
  3. 两者真正值得统一的是**凭据、网络、错误、追踪与媒体上传**这四层（`electron/main/services/llm/runtime.ts` 已经在复用 `ai-runtime/upload.ts` 的 `preprocessRequestBody`），而不是模型定义本身。
  4. `src/core/llm/` 已经几乎可移植（运行时只依赖 `zod`），迁移成本远低于生成模型侧。
- 影响任务：4.1、4.2、4.3、5.1、5.2

## 记录 005：模型类型与供应商注册改为可扩展

- 日期：2026-08-27
- 状态：已确定
- 背景：当前 `src/core/types/ModelDefinition.ts:22` 是 `export type ModelType = 'image' | 'video' | 'audio'`，闭合联合。用户明确提出未来会增加语音识别等新类型。`ProviderId` 已经是 `'ppio' | 'fal' | 'kie' | 'modelscope' | string`（开放但字面量提示不全）。
- 最终决定：`ModelType = BuiltinModelType | (string & {})`，`BuiltinModelType` 保留 `image` / `video` / `audio`；`ProviderId = BuiltinProviderId | (string & {})`，内置值补齐 APIMart、Bailian、Volcengine、PPIO、KIE、ModelScope、Fal、Grsai 八个。`registerProvider` 同 id 重复注册抛 `provider_already_registered`、不覆盖旧值；`unregisterProvider` 返回是否真实删除；`listProviders` 返回隔离快照。8 个内置 provider 仍随模块初始化。
- 选择原因：闭合联合意味着每加一种模态都要改核心类型并牵动全部消费方；对一个要被多个项目消费的 SDK，这会强制所有下游同步升级。注册制则允许消费方在不改 SDK 的前提下扩展。
- `outputKind` 结论：本次不新增。逐份检索包内 80 份生成模型资料与 9 份 LLM 资料，没有 ASR、语音识别、转写或 speech-to-text 模型；唯一音频模型 MiniMax Speech 是语音合成/声音克隆，输出仍是音频。等第一个非媒体输出模型真实接入时，再按其响应和宿主消费需求设计，禁止为假想需求过度设计。
- 边界：`ModelType` 描述模型产出分类；上传预处理的 `MediaKind` 描述请求字段媒体种类，两者保持独立，未合并。
- 影响任务：5.1、5.2、5.3

### 任务 8.1 澄清补充（原决定的历史背景保留）

用户现已明确提出真实的 ASR 与 OCR 扩展方向，因此“暂无真实需求所以不增加输出契约”的前提不再成立。

## 记录 006：SDK 包名与分发渠道

- 日期：2026-08-27
- 状态：**已确定并完成首次发布**
- 背景：npm 不支持把 Git 仓库的子目录作为依赖安装，因此 monorepo 里的 `packages/ai-sdk` 需要选定分发方式。
- 最终决定：包名为 `@henjicc/ai-sdk`，从 `0.1.0` 起只发布到私有 GitHub Packages（`https://npm.pkg.github.com`），不同时维护 subtree 镜像或公开 npm。消费方用具备 `read:packages` 与对应仓库权限的 token 配置项目级 `.npmrc`。

- 发布证据：2026-08-27 已真实发布 `@henjicc/ai-sdk@0.1.0`，GitHub Packages version id `1177711681`，包可见性为 private、关联仓库为 `henjicc/Henji-AI`。仓库外干净目录从 registry 安装后，TypeScript 导入 `createAIClient` 与无网络探针均通过。
- 影响任务：1.2（package.json 的 name 字段）、6.2、6.3

## 记录 007：不做远程目录热更新，不做声明式配置语言

- 日期：2026-08-27
- 状态：已确定
- 背景：前期调研资料建议了两项增强——远程模型目录热更新、以及把供应商适配写成 YAML/JSON 声明式配置。
- 最终决定：两项都**不做**，本次任务范围内不引入。
- 选择原因：
  1. **远程目录**：需要配套版本协商、回滚、签名、最低 SDK 版本校验，工作量不低于 SDK 本体，而收益只是「少发一次版」。且 UXP 的 manifest 网络白名单与 Tauri HTTP 插件的 URL 许可都要求域名在打包期固定，新增供应商无论如何都要发版。等发版频率真正构成困扰时再单独立项。
  2. **声明式配置**：真实响应结构比文档脏得多。以 `providers/kie.ts` 的 `extractUrls` 为例，它要先从 `data.resultJson` 取出一个 JSON **字符串**、`JSON.parse` 一层，再从 `/resultUrls`、`/images`、`/videos`、`/firstFrameUrl`、`/lastFrameUrl` 五个指针取值，取不到还要对 `resultObject` 做深度遍历。写成 YAML 只会退化成一门半吊子脚本语言。现有 `request-builder-dsl.ts`（184 行）覆盖度已经够用，协议复用用函数式模板（`createAndPoll({ createFn, pollFn, extractFn })`）表达即可。
- 影响任务：全部（作为范围约束）

## 记录 008：model-manifest.json 是否保留为对外快照

- 日期：2026-08-27
- 状态：已确定（不做 JSON 快照）
- 背景：任务 3.3 会删除 `resources/model-manifest.json` 的生成链路。但该文件（254 KB）本身是一份结构化的模型目录快照，对不使用 TypeScript 的消费方可能有价值。
- 候选方案：
  1. 彻底删除，消费方一律通过 SDK 的 TypeScript 导出访问目录。
  2. 保留一个由 SDK 目录生成的 JSON 快照产物（内容与来源都变了：从「解析源码」变成「运行时序列化已加载的目录」），作为 SDK 的构建产物之一发布。
- 最终决定：选方案 1，彻底删除旧 manifest，SDK 不发布 JSON catalog 快照。已知的两类外部宿主都不构成“非 TypeScript/JavaScript 消费方”：Tauri 前端可以在构建期打包 ESM，UXP 同样通过 webpack/Parcel 等构建期打包 ESM/CJS。
- 选择原因：真实 99 catalog 包含 endpoint selector、request builder、pricing calculator、visible/inputLimits 函数等不可无损 JSON 化的行为契约。若只序列化数据子集，它会成为比 ESM/CJS 目录更弱且需单独版本协商的第二份真相，当前没有真实需求支撑这个成本。
- 未来重开条件：只有出现明确的非 JavaScript/TypeScript 消费方时，才另行设计带 schema/version 的可序列化投影；不得把运行时函数丢失后的普通 `JSON.stringify(catalog)` 当成可用契约。
- 影响任务：3.3、5.3、6.2

## 记录 010：任务 1.1 运行时验证——确认记录 002，并新增两条运行时约束

- 日期：2026-08-27
- 状态：已确定
- 背景：任务 1.1 对「纯 TypeScript 供应商适配层能在 UXP / Tauri 中运行」这一架构前提做了 8 项运行时能力验证。UXP 侧因本机无 Photoshop/UXP Developer Tool，采用官方文档调研；Tauri 侧用本机真实 Rust/npm 工具链完成了 `cargo check` 编译验证与真实已安装包（`@tauri-apps/plugin-http@2.5.9`）源码阅读。完整 8 项结论见 [1.1-运行时约束验证.md](任务/第一阶段-可行性验证与基础设施/1.1-运行时约束验证.md) 执行记录。
- 最终决定：
  1. **确认记录 002**：UXP 的 CSP 默认通过 `allowCodeGenerationFromStrings`（默认 `false`）禁用 `eval`/`new Function`，且 UXP 本身没有 `node:vm`（官方原话：UXP 相比 CEP "has lost Node.js support"）。「序列化 + VM 执行」路线在 UXP 上双重不可行，builder 改为直接函数调用的决定不需要调整。
  2. **新增约束一**：UXP 没有运行时 Node 模块解析器，npm 依赖必须在构建期打包进最终产物（webpack/parcel 等），不能运行时动态 `require()`/`import()` 解析 `node_modules`。这要求 `packages/ai-sdk` 的 `dist/` 产物必须是标准 ESM/CJS，能被主流打包器静态分析打包。
  3. **新增约束二**：UXP `SecureStorage` 官方定位是"更像缓存而非持久存储"（key 不加密，建议数据可在丢失后重新生成），任务 2.1 设计 `CredentialStore` 接口时不能假设凭据一定还在，需要支持"取不到时重新获取"的语义。
- 选择原因：这两条约束都来自官方文档的明确措辞，不是推测；且都不构成对现有方案的推翻——1.2 的包产物形态本来就该是标准 ESM/CJS，2.1 的接口本来就该做异步容错处理，只是任务 1.1 把这两点从"应该这样做"变成了"必须这样做，否则 UXP 上会出问题"的硬约束。

## 记录 011：任务 1.2 骨架落地——构建工具选 tsup，`exports` 用 development 条件避免本仓库日常开发先构建

- 日期：2026-08-27
- 状态：已确定
- 背景：任务 1.2 需要给 `packages/ai-sdk` 定下 `build` 脚本与 `package.json` `exports` 结构，这个决定会被 1.3 之后所有往 SDK 里写代码的任务直接沿用，改起来成本不低，值得单独记一笔。
- 最终决定：
  1. **构建工具用 tsup，不用裸 tsc。** 任务 1.1 已确认 SDK 产物必须是主流打包器能静态分析的标准 ESM/CJS（记录 010 新增约束一）。裸 tsc 单次调用只能输出一种 module 格式，双格式（ESM+CJS）需要两份 tsconfig 手工拼接 `exports`；tsup 基于 esbuild，一次调用按 entry 表同时产出 ESM、CJS 与类型声明，且天然支持多入口，与 `exports` 的 5 个入口（`.`/`./providers`/`./catalog`/`./llm`/`./runtime`）一一对应。配置见 `packages/ai-sdk/tsup.config.ts`。
  2. **每个 exports 子路径的条件顺序固定为 `development → types → import → require → default`，`development` 指向 `src/`，其余指向 `dist/`。** 实测确认 Vite 4.4.5（本仓库锁定版本）的 exports 解析会按 `isProduction` 自动把 `development`/`production` 加入候选条件集，且按对象里子路径条件的书写顺序取第一个命中项——这意味着 `electron:dev`（渲染层与主进程的 Vite/Rollup 构建）在开发模式下无需先执行 `npm run build -w packages/ai-sdk` 就能直接解析到源码，改完即生效；生产构建与 tsc classic 解析（`tsconfig.electron.json` 用的 `moduleResolution: "node"` 完全不认 `exports`，只读顶层 `main`/`types` 字段）则落到 `dist/`。
  3. **`dist/` 不提交进 git**，复用仓库根 `.gitignore` 已有的 `dist/` 忽略规则。这意味着任何需要 tsc classic 解析该包（主进程 `tsconfig.electron.json`）或需要生产打包产物的场景，前置条件是 `dist/` 已经被构建过；1.2 阶段没有真实代码引用 SDK，因此还没有把 `npm run build -w packages/ai-sdk` 接入 `electron:build`，留给第一个让主进程真正 `import` SDK 内容的任务去接线。
- 选择原因：这套设计把「本仓库日常开发零摩擦」（不用为了改一行 SDK 代码就跑一次构建）和「产物必须是可被外部打包器静态分析的标准 ESM/CJS」（UXP 约束）同时满足，且没有在两者之间做取舍——前者靠 bundler 感知 `development` 条件，后者靠 `dist/` 一直保持标准形态。

## 记录 012：tsc classic 解析不认 `exports` 子路径——electron 主进程侧统一从包根导入，`electron:build` 接入 SDK 构建

- 日期：2026-08-27
- 状态：已确定
- 背景：任务 2.1 首次让 `electron/main/services/ai-runtime/` 下的代码真正 `import` `packages/ai-sdk` 的非占位内容（5 个运行时接口 + `task-registry`）。记录 011 已经预判了 `tsconfig.electron.json` 的 `moduleResolution: "node"`（TS 经典 / Node10 解析）"完全不认 `exports`，只读顶层 `main`/`types` 字段"，但当时未实测到"子路径导入会直接报错"这个具体后果。任务 2.1 用一个临时测试文件实测确认：
  ```

  // error TS2307: Cannot find module '@henjicc/ai-sdk/runtime' or its corresponding type declarations.
  //   There are types at '.../dist/runtime/index.d.ts', but this result could not be
  //   resolved under your current 'moduleResolution' setting.
  ```

  而 `import { SDK_PLACEHOLDER } from '@henjicc/ai-sdk'`（包根）在同一 tsconfig 下能正常解析（读 `package.json` 顶层 `main`/`types` 指向 `dist/index.cjs`/`dist/index.d.ts`）。
- 最终决定：
  1. **electron 主进程侧（受 `tsconfig.electron.json` 约束的代码，即 `electron/**` 与 `electron.vite.config.ts`）需要引用 SDK 内容时，一律从包根 `@henjicc/ai-sdk` 导入，禁止使用 `@henjicc/ai-sdk/providers`、`@henjicc/ai-sdk/runtime` 等子路径。** Vite/Rollup（渲染层构建、`electron-vite build`）与 vitest 都能正确解析 `exports` 子路径，不受此约束——只有 tsc classic 这一条解析路径有问题。
  2. **`packages/ai-sdk/src/index.ts`（包根入口）需要把新增的子目录内容一并重新导出**（本次是 `export * from './runtime'`），否则包根解析不到该内容，电主进程侧永远拿不到。后续任务往 `providers/`、`catalog/`、`llm/` 等子目录添加真实内容、且 electron 主进程需要消费时，需要同步更新根 `index.ts`（或在该任务里明确记录"暂不需要主进程消费，因此不导出"的理由）。
  3. **`npm run build -w packages/ai-sdk` 已接入 `electron:build`**（插在 `check:assistant-capabilities` 之后、`tsc -p tsconfig.electron.json` 之前），不再要求每个后续任务各自记得手动构建一次 `dist/`。日常 `electron:dev` 不受影响，仍然靠 `development` exports 条件直接读 `src/`（记录 011），不需要这一步。
- 选择原因：
  1. 「包根统一导入」是影响最小的修复——不需要改 `tsconfig.electron.json` 的 `moduleResolution`（改成 `bundler`/`node16` 会牵动整个主进程的模块解析行为，风险和验证成本远超收益，且与该 tsconfig 现有的 `module: "CommonJS"` 搭配不自然），也不需要放弃 `exports` 的多入口设计（渲染层与其他消费方仍然受益于子路径按需导入）。
  2. 把 SDK 构建接入 `electron:build` 而不是让每个任务自行决定，是因为「手动跑一次 tsup」这种约定极易在多任务、多协作者场景下被遗忘，遗忘后的失败模式是 `tsc -p tsconfig.electron.json` 读到过期的 `dist/`（类型声明缺失新增导出），报错信息与"忘记构建"这个根因不直接相关，排查成本高；一次性接线成本很低（tsup 对当前体量的包耗时以毫秒计）。
- 影响任务：2.2、2.3、2.4、4.1、4.2（凡是 electron 主进程侧需要 `import` SDK 内容的后续任务，都要遵守「包根导入」这条约束）

## 记录 016：任务 3.3——主进程直连 catalog 的索引、异步与智能比例兼容边界

- 日期：2026-08-27
- 状态：已确定
- 背景：删除 manifest/VM 后，主进程首次直接消费 99 个真实模型对象。除了复现原 `ModelManifestStore` 的 alias 覆盖顺序，还必须处理 Fal Seedream v4/v4.5 的异步 builder，以及宿主媒体预处理与 SDK builder 之间的智能比例传递。
- 最终决定：
  1. SDK 提供 `createModelIndex(catalog)`，索引规则固定为：canonical ID 始终覆盖同名 alias；alias 不覆盖已有 canonical ID；多个模型声明同名 alias 时首个获胜；后出现的 canonical ID 可覆盖早先同名 alias。`catalogIndex` 与 4 组单测作为后续统一入口的真相源。
  2. `buildRequest(params, model)` 对 endpoint selector 与 request builder 都统一 `await`，同步模型自动兼容；主进程生成和续轮询两条路径不得绕开这个入口。
  3. Fal Seedream v4/v4.5 的“智能比例”在浏览器环境可读取图片尺寸，但 Electron 主进程 Node 环境没有全局 `Image`。宿主媒体预处理已计算的首图比例继续通过内部参数 `__firstImageRatio` 传入，真实 builder 必须优先消费它，再把浏览器 `Image` 解码仅作为缺少 hint 时的 fallback；KIE Seedream 4.0/4.5 保持同一 hint 契约。
  4. 原 `CUSTOM_BUILDER_OVERRIDES` 四模型没有真实付费生成授权，不得以假网络结果冒充 E2E。当前证据固定为真实 catalog selector/builder + runtime normalizer 的路由和请求体契约测试；6.4 获得明确授权后再补供应商网络 E2E，并在报告中继续区分两类证据。
- 选择原因：索引规则直接决定旧工程 ID 是否能恢复；统一 await 是 SDK 已声明异步返回后的必要调用契约；`__firstImageRatio` 是跨浏览器/Node 宿主都可移植的纯数据边界，避免 SDK 依赖 DOM 解码能力；替代证据边界必须如实保留。
- 影响任务：4.3、5.1、5.2、6.2、6.4。

## 记录 017：任务 4.3——公共基础设施统一，协议生命周期与宿主追踪刻意不统一

- 日期：2026-08-27
- 状态：已确定
- 背景：生成模型与 LLM 执行层都进入 SDK 后，需要消除凭据、网络、错误、重试、取消与追踪接口的重复；同时必须遵守记录 014，不得借“统一”把助手 trace/capability-smoke/scripted-model-step 迁入 SDK，也不能把创建+轮询与流式/模型步压成一个错误的执行协议。
- 最终决定：
  1. **task registry 只有一份，但任务身份必须带命名空间。** `runtime/task-registry.ts` 用 `generation`/`llm` + taskId 组成内部 key；两类任务即使 taskId 相同也不会互相取消。5.2 的统一客户端若暴露 `cancel`，必须显式接受或可靠推导命名空间，不得恢复成裸 taskId 的全局取消。
  2. **错误 schema、分类器与重试判断各保留一份，策略生命周期不合并。** `runtime/errors.ts` 保留生成侧 `AiRuntimeError` 与既有错误码字符串，同时承载 LLM 的 `[provider_error]` 序列化模型；`runtime/error-classify.ts` 提供鉴权、余额、额度、限流、上下文、内容过滤、取消等细分类及唯一 `shouldRetry(error, mode)`。`safe-preconnect` 仅允许可证明尚未建连的错误重试；`request` 服务于模型步；`poll-query` 服务于状态查询连续失败容忍。共同分类不代表共同重试次数或生命周期。
  3. **网络统一到 `Transport + fetchProvider`。** 原生 SSE 与 Vercel AI SDK 模型步均经该入口；模型步的 `createModelStepLanguageModel` 追加可选第 4 个 `Transport` 参数，保留前三参数兼容。未注入时只为现有 Electron 直接调用保留全局 fetch 适配，但仍经过 `fetchProvider`，不另写网络失败判断。该改动只增加“安全预连接一次”能力，没有扩大为任意响应失败重放。
  4. **`CredentialStore` 与 `Tracer` 统一的是宿主接口，不是宿主业务。** 复核确认 4.2 后 Electron 已是单一 `CredentialStore.get(scope, providerId)` 实现，无需再合并 keystore 函数。SDK 只用 `RuntimeContext.tracer` 报告 `generation.generate`、`generation.continue-polling`、`llm.chat`、`llm.model-step` 通用 span；生成 trace builder、助手结构化 trace、capability-smoke、scripted-model-step 继续留痕迹AI，严格沿用记录 014。
  5. **创建+轮询与 SSE/模型步刻意保持分离。** 生成任务有服务端 taskId、长时轮询、进度与查询连续失败容忍；LLM 以 token/tool call 流式输出或完成单个模型步。二者终止条件、结果形状和可安全重试边界不同。第五阶段只能统一消费入口与运行时注入，不能合并协议生命周期。
- 选择原因：公共抽象的价值是让身份、错误、安全重试、网络与追踪注入只有一个真相源；协议差异和宿主观测格式本身不是重复实现。强行合并会丢失取消隔离、轮询语义或助手可移植性边界，并可能重放计费请求。
- 影响任务：5.1（扩展供应商时复用公共错误/网络入口，不另建同功能实现）、5.2（统一客户端按能力分组，取消必须保留命名空间，宿主 trace/落盘/IPC 留主进程）、5.3、6.2、6.3、6.4。

## 记录 018：任务 5.2——统一入口的宿主边界、取消身份与自定义 provider 生命周期

- 日期：2026-08-27
- 状态：已确定
- 背景：`createAIClient` 需要同时服务生成、LLM、目录与供应商扩展，但不能借统一入口改变参数持久化、把痕迹AI 业务带进 SDK，或让一个 client 的自定义 provider 永久污染另一个 client。
- 最终决定：
  1. **统一的是消费入口与可移植编排，不是宿主业务。** SDK 负责模型/alias 解析、builder、request normalize、媒体预处理、provider 执行与 LLM 执行；文件落盘及 `filePath`、应用结构化日志/trace、进度学习、pending result、IPC DTO/事件继续留宿主。生成参数保持既有扁平字段；助手 trace、capability-smoke、scripted-model-step 的记录 014/017 边界不变。
  2. **取消公共 API 固定为 `cancel({ namespace, taskId })`。** 不能按 5.2 原草案暴露裸 requestId；生成与 LLM 同名任务必须经 4.3 registry 的命名空间隔离。生成创建阶段以请求 ID 登记，续轮询阶段以供应商服务端 taskId 登记，内部日志 requestId 不参与轮询取消身份。
  3. **自定义模型索引是 client 私有的，自定义 provider 仍复用 5.1 的唯一进程级 registry。** client 记录自己成功注册的 provider；构造中途失败回滚本次已注册项，`dispose()` 幂等且只注销自身项，同 ID 并发注册明确报 `provider_already_registered` 而不覆盖。不同 ID 的 client 可并行、互不注销；但 provider 在所属 client 存活期对同进程其他 client 可见，这是“唯一 registry”架构的显式语义，不宣称 per-client 隔离。外部消费方注册自定义 provider 后必须调用 `dispose()`。
- 选择原因：这组边界既保留 Electron 的 IPC/日志/落盘契约，也让 SDK 在 Tauri/UXP 等宿主只依赖 RuntimeContext；显式命名空间避免恢复 4.3 已修复的交叉取消；拒绝暗中覆盖全局 provider 可避免并发 client 行为依赖创建顺序。
- 影响任务：5.3（公开目录与类型需要以 client 私有模型索引为准）、6.2（发布文档说明进程级 provider registry 生命周期）、6.3（最小示例必须展示命名空间取消与 `dispose()`）、6.4（真实网络 E2E 仍需单独授权）。

- 验证边界：ASR/OCR 当前是纯 fixture，只证明扩展机制，不代表真实供应商适配。按需 bundle 以模块图而非仅体积
  判定隔离，覆盖 bare、单 KIE Z-Image、KIE provider pack 与 LLM-only；真实发布留给 8.2 的 `0.1.5`。
- 影响任务：8.2（Fal 工具沿用完整 pack/provider-scoped 策略并统一发布）、8.3（Henji-AI 按需消费）、
  Photoshop UXP 集成（只选所需 pack，不导入包根/全量 generation）。

## 记录 024：任务 8.2——工具模型与默认生成目录采用独立分发边界

- 日期：2026-08-28
- 状态：已确定
- 背景：Photoshop 插件有 3 个 Fal 图像消除工具；它们底层仍是异步图片任务，但产品语义、输入契约与默认生成模型不同。
- 最终决定：
  1. 三项工具使用真实 `ModelRuntimeDefinition` 和 Fal adapter，但模型文件位于默认 catalog 外；`generation` 与普通 Fal provider pack 继续严格保持 99 / 31，不靠 UI 过滤隐藏工具。
  2. 对外提供单模型 `tool-models/fal/*` 与聚合 `tool-packs/fal-image-edit-tools`。完整 pack 自带 Fal adapter、媒体预处理与 CDN 上传；聚合包只是 3 项模型的技术分发集合，不是宿主必须理解的“擦除能力包”。
  3. 不公开具体 `image-erase` CapabilityModule，也不包装第二次 generation create/poll。三项执行直接使用 `createModularGenerationClient`。跨生成、LLM、ASR/OCR 的选择统一使用 `ModelCapabilityProfile`：从真实 model tags/input limits/runtime fields、LLM catalog input 与扩展 descriptor 派生 provider/output/operation/input/output/features/tags。
  4. Flux 固定 `dilate_pixels=10`，Bria 固定用户绘制遮罩的 `mask_type=manual`，Finegrain 只暴露官方三档 mode；按项目约定不暴露 `output_format` 和 seed。
- 选择原因：分发 pack 决定静态依赖图，能力画像只筛选已导入候选；分开两层既避免“运行时过滤等于 tree-shake”的误导，也让所有模型类型共享同一筛选 taxonomy，同时保留各自执行内核。
- 影响任务：8.3、Photoshop UXP SDK 集成与后续工具/ASR/OCR 能力包。
