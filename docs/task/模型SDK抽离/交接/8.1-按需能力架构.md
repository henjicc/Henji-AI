# 8.1 交接：按需模型与开放能力架构

## 结论

`@henjicc/ai-sdk` 已从“全量生成目录只能在创建后过滤”改为可真正按需装配：兼容入口 `@henjicc/ai-sdk/generation` 仍默认提供 99 个模型；新入口 `@henjicc/ai-sdk/generation/core` 不静态导入任何内置模型或供应商，宿主只会带入显式选择的完整 model pack/provider pack。SDK 同时增加独立于媒体 `ModelType` 的开放能力模块协议，ASR、OCR 等新能力不需要修改 core 的联合类型或 switch。

本任务没有发布新包、没有真实外网请求，源码版本保持 `0.1.4`。8.2 增加 Fal 工具后统一升版并发布 `0.1.5`。

## 公共 API 与选择方式

### 生成能力

- `createModularGenerationClient({ runtime, packs, models, providers })`：bare 模块化入口；零 pack 时目录为零模型。
- `GenerationPack`：完整执行单元，包含 `models` 与 `providers`。
- 同一供应商的多个单模型 pack 可直接组合；等价的 provider 执行/上传注册会自动复用为一个，冲突实现仍拒绝覆盖。
- `GenerationClientProviderRegistration`：包含 provider adapter，可选 provider-scoped `preprocess` 与 `testConnection`。
- `createGenerationClient({ runtime, ... })`：原兼容入口，默认 99 模型与 8 个内置供应商，传入的 model/provider 仍按原语义追加。
- `createAIClient({ runtime })`：原根客户端行为不变；显式传 `generation: { mode: 'modular', packs }` 时才切到选择性目录，chat 继续可用。

发布子路径：

- `@henjicc/ai-sdk/generation/core`
- `@henjicc/ai-sdk/models/<provider>/<model>`：单模型模块同时导出低层 `model`、`provider` 与完整 `pack`。普通宿主应传 `pack`；单独 `model` 只适合自行管理适配器/上传的高级场景。
- `@henjicc/ai-sdk/provider-packs/<provider>`：该供应商全部模型的完整 pack。
- `@henjicc/ai-sdk/provider-adapters/<provider>`：只需要供应商执行/预处理注册时使用。
- `@henjicc/ai-sdk/llm`：LLM-only 宿主继续只导入该入口，不进入 generation/catalog/provider 静态图。

99 个单模型 pack、8 个 provider adapter、8 个 provider pack 都由 `scripts/generate-catalog-index.cjs` 从唯一的 `catalog/**/*.model.ts` 自动生成。生成器重跑前后 hash 一致；`check-modular-bundles.cjs` 同时校验 99/99、8/8、8/8，新增/删除模型但漏导出会直接失败。

### 完整 pack 的上传自描述

完整 pack 不是只含 schema。每个 pack 都带执行所需的 model definition、provider adapter、provider-scoped media preprocessor/uploader，并统一使用创建客户端时传入的 `RuntimeContext`。上传遍历、读取与 source 识别收敛在共享 `upload/preprocess-core.ts`，KIE、Fal、API Mart、PPIO 等差异由独立 provider strategy 组合，没有复制生成轮询或请求执行内核。

KIE fixture 只导入 `@henjicc/ai-sdk/models/kie/gpt-image-2` 的一个完整 pack，验证了：

1. `uxp://`/`managed://` 媒体引用交给 `runtime.media.read`；
2. 调 KIE 文件上传；
3. 创建生成任务；
4. 轮询并返回结果。

脚本 transport 精确收到 3 次请求，未导入任何隐藏上传模块。首次 fixture 暴露 `uxp://` 会被误判为远程 URL、导致跳过 `MediaReader` 的边界；已在公共媒体字段识别中将 `uxp://` 与 `managed://` 定义为宿主管理引用，并由相关 26 项测试覆盖。

## 开放能力模块

`@henjicc/ai-sdk/capabilities` 导出：

- 开放字符串 `CapabilityKind` 与 `CapabilityContentKind`；内置提示包含 `media-generation`、`chat` 及 text/structured-data/image/audio/video/pdf，但允许任意非空新字符串。
- `CapabilityContract`：分别描述输入/输出内容类型，可表达 ASR 的 audio→text、OCR 的 image/pdf→text/structured-data。
- 泛型 `CapabilityModule<TInput, TOutput>` 与类型化 `CapabilityHandle<TInput, TOutput>`。
- `createCapabilityClient({ runtime, modules? })`，提供 `register`、`list`、`get`、`execute`、`cancel`、`unregister`、`dispose`。
- 每次执行获得完整 `RuntimeContext`、稳定 `requestId` 与 `AbortSignal`；统一记录 start/completed/failed 日志和 tracer span，非 SDK 错误归一化为 `AiRuntimeError`。
- `generationCapabilityDescriptor`、`chatCapabilityDescriptor` 仅作为发现适配层，不重写稳定的生成轮询或 LLM 流式执行内核。

两个纯 fixture 模块证明 core 无需修改：

- `speech-recognition`：audio→text，验证发现、类型化执行、外部取消、注销和 dispose。
- `ocr`：image/pdf→text+structured-data，验证发现、执行、错误归一化与注销。

它们不是实际供应商适配，不发真实请求，也不得对外宣称 SDK 已接入真实 ASR/OCR 模型。

这更新了 5.1 的“暂无真实 ASR，所以不加 outputKind”记录：现有媒体生成 `ModelType` 兼容不变；新需求由独立 capability input/output contract 表达，不把 OCR/ASR 硬塞进 image/video/audio 生成类型。

## Bundle 与断牙证据

所有门禁同时构建 IIFE/ESM，关闭 tree-shaking 审计真实静态模块图，并禁止 Node builtin、require、eval、`new Function` 等风险全局。生命周期 `networkCalls=0`。

| 场景 | IIFE bytes | ESM bytes | 模块数 | 静态图断言 |
|---|---:|---:|---:|---|
| bare 0 模型 | 15,907 | 15,451 | 15 | 无内置 model/provider，目录严格为 0 |
| 单 KIE Z-Image 完整 pack | 38,851 | 38,462 | 32 | 只有 `kie/z-image` 与 KIE provider |
| KIE provider pack | 106,844 | 106,448 | 61 | 只有 KIE 的 27 个模型与 KIE provider |
| LLM-only | 785,006 | 784,843 | 201 | 无 generation、生成 model、生成 provider |

断牙实测：

- 临时从 `generation/core` 导出全量 catalog，bare 门禁立即变红并列出 99 个越界模型；精确恢复后转绿。
- 临时从 `llm/index` 导出 generation，LLM-only 门禁立即变红并列出 generation、99 模型与 8 provider；精确恢复后转绿。

相对导入图审计只发现未改动的既有 `llm/modelCatalog.ts ↔ llm/modelCatalogEntries.ts` 环；本次新增 core、packs、capabilities 与 provider-scoped upload 模块没有形成新环。最大新增公共实现 `generation/core.ts` 为 472 行，符合 400～500 行可接受区间；没有新增超过 500 行文件。

## 给 8.2、8.3 与 UXP 的输入

### 8.2

1. 新增 Fal 工具模型/能力时应复用现有 Fal provider-scoped preprocessor/adapter；如工具不是 image/video/audio generation，优先作为独立 capability module，不要往 `ModelType` 加假类型。
2. 每个新增 catalog model 会由 generator 自动产生单模型完整 pack，并进入 Fal provider pack；必须跑 exports 完整性与四类 bundle 门禁。
3. 统一升版到 `0.1.5` 后再发布；不要改写已发布的 `0.1.4` 状态。

### 8.3（Henji-AI 本体）

1. 当前应用仍使用默认 99 模型兼容入口，本任务没有切换应用消费。
2. 若应用要选择性装配，使用 `createAIClient({ generation: { mode: 'modular', packs } })`，不要先导入全 catalog 再过滤。
3. 应用现有生成/LLM 行为已通过全仓与 Electron 回归；切换时继续保持应用层只做选择，模型协议、上传与轮询仍在 SDK。

### UXP/Photoshop

1. 只导入插件需要的完整单模型 pack，例如 `@henjicc/ai-sdk/models/kie/z-image`，或需要同供应商全部模型时导入 provider pack；不要使用全量 `generation` 再隐藏 UI。
2. UXP 只实现自己的 `RuntimeContext`（Transport、CredentialStore、MediaReader、Logger/Tracer）；`uxp://`/`managed://` 引用会交给宿主 MediaReader，pack 自己负责 provider 上传。
3. 低层 `model` 导出不保证可独立执行；普通插件消费完整 `pack`。
4. 本任务只做脚本 fixture 与 Electron 真实宿主回归，没有真实 UXP 网络 E2E；UXP 安装包验证继续由后续任务完成。

## 8.2 方向修订（2026-08-28）

8.1 的“完整 pack 决定静态分发、开放 CapabilityModule 承载 ASR/OCR 等独立执行协议”继续成立；
8.2 进一步明确：**能力筛选 taxonomy 与代码分发 pack 是两层**。Fal 图片消除模型底层仍符合 generation
协议，因此不再为它们增加具体 `image-erase` CapabilityModule，也不包装第二份 create/poll；它们以默认
99 之外的单模型 pack 与 `tool-packs/fal-image-edit-tools` 技术集合分发，直接由
`createModularGenerationClient` 执行。

跨 generation、LLM、ASR/OCR 的选择改用统一 `ModelCapabilityProfile`，画像从已导入候选的真实
tags/inputLimits/runtimeConstraints、LLM input/capabilities 和扩展 descriptor 派生。运行时 search 只过滤
已导入候选，不会自动缩小 bundle；真正 tree-shake 仍由宿主显式 import 单模型/provider/collection pack。
该修订不改变 8.1 已提交实现，只为 8.2 及后续消费方补充更精确的使用边界。
