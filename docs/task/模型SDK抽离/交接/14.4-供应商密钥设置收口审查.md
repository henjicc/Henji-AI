# 14.4 供应商密钥设置收口审查

更新时间：2026-08-28

## 审查结论

独立审查 `918e582e` 与 `24704703` 后，14.2 的事务主链路和 14.3 的界面方向正确，但发现三类需要在收口前修复的边界：内置供应商身份可被降级后永久删除、嵌套扩展配置可夹带明文凭据、渲染层仍保留可绕过高层事务的通用/LLM 低层密钥写入口。上述问题均已做底层修复并补断牙测试。

最终契约如下：

- 既有 builtin 必须保持原 preset 与 `lifecycle: builtin`，只能禁用或重置；非 builtin 也不能自行提升为 builtin。
- provider/model 的任意嵌套扩展字段都会递归检查明文凭据名；`apiKey`、`client_secret`、`password`、`token` 等必须通过 credential mutation，不得进入配置或 journal。
- renderer 侧已移除通用 `keystore:*` 以及 `llm:set/removeProviderApiKey`；LLM 凭据写入只允许经过 `llm:providerSettings:commit/delete` 原子事务。生成模型自己的 `ai:*ProviderApiKey` 领域入口保持不变。
- 设置页的供应商启用、API 地址和推理能力更新也改走高层事务，不再用普通整份配置保存绕过事务。
- `ApiKeyInput` 继续是生产界面唯一密钥输入，hint/error 通过稳定 id 与 `aria-describedby` 关联，显隐按钮带 `aria-pressed`，输入右侧留有内嵌按钮空间。
- 内置身份拒绝会明确提示使用“禁用”或“重置供应商”，而不是泛化失败文案。

## 事务与安全审查

- `credentialId` 是所有 LLM 凭据事实坐标；providerId 仅为供应商坐标。BigModel cn/global 等 profile 的独立 credential slot 不被本次修改合并。
- commit/delete 在主进程串行执行，先写不含明文的 journal，再写 credential 与 config；失败恢复 credential snapshot 和旧配置，启动时可恢复未完成事务。
- 删除前仍检查内置生命周期、Prompt/Agent 引用以及共享 `credentialId`；内置拒删、共享凭据保留、独占 LLM 凭据随 custom provider 删除，PPIO 生成侧 fallback 不受影响。
- journal 只保存旧配置与已加密凭据快照；新增递归检查保证扩展对象也不能把明文 secret 混进 provider/model 配置。
- API Key 管理地址继续由 SDK 契约限制为不含账号密码、长度不超过 2048 的绝对 HTTP(S) URL；打开外链仍走 `useExternalLink` → PAL → 主进程，不使用 `window.open`。
- 全盘生产输入扫描确认：`type="password"` 只存在于 `ApiKeyInput`；生产消费者只有全局密钥页、LLM 设置/管理弹窗和 Onboarding。业务 TSX 未发现绕开 primitives 的原生密钥输入。
