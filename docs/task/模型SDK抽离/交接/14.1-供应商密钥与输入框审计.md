# 14.1 供应商密钥与输入框审计交接

日期：2026-08-28

范围：只读审计供应商管理、API Key 输入、配置持久化、凭据槽、日志与助手观察边界；目视核对用户提供的三张截图。本任务不修改运行代码，不执行真实网络或付费请求。

## 一、结论

这不是只把眼睛按钮挪进输入框的局部样式任务。当前有一个可复用的密钥输入组件，但供应商配置与密钥仍是两条彼此不知道成败的写入链：

- 所有生产密钥输入已经汇聚到 `src/components/Settings/components/ApiKeyInput.tsx`，不应再建 `PasswordInput`、`SecretInput` 等平行组件。
- `ApiKeyInput` 的眼睛按钮当前是输入框外侧独立描边按钮，和用户图 2 一致；目标应改为图 3 的输入框内右侧无框动作。
- “新建供应商”只保存 `LlmProviderConfig` 与推荐模型，不采集 API Key。
- 供应商配置写入 `llm-config.json`，密钥另走 Electron keystore；创建、删除均没有跨两者的事务或补偿回滚。
- 删除供应商只删除 config/providers 与 models，不删除 `llm:<credentialId>`，会留下孤儿密钥；失败时也不会恢复已经写入的另一侧。
- UI 读写密钥使用 `providerId`，但 SDK 已明确把 `credentialId` 作为独立凭据坐标。继续混用会破坏区域/租户隔离。
- LLM 预设与 BigModel endpoint profile 已经有官方 `apiKeyUrl`，但配置类型没有记录“预设还是自定义”，界面也没有消费该 URL；自定义供应商没有可保存的密钥管理 URL。
- `LlmConfigService` 每次归一化都会补回内置供应商和模型，所以当前对派欧云/DeepSeek点“删除”并不是真删除；按钮语义与持久化事实不一致。

根本方案是：先建立明确的供应商来源与凭据坐标契约，再由一个宿主事务入口统一提交“供应商配置 + 独立凭据”，最后复用现有 `ApiKeyInput` 完成界面收口。不能让弹窗自己依次调用“保存配置”和“保存密钥”。

## 三、现有实现与缺口

### 3.1 密钥输入唯一入口

生产代码没有第二个 password 控件，三类调用方都复用 `ApiKeyInput`：

| 调用面 | 文件 | 数量/范围 | 当前持久化 |
|---|---|---|---|
| 全局生成供应商密钥 | `src/components/Settings/tabs/ApiKeysTab.tsx` | `API_KEY_PROVIDERS` 的 8 家供应商 | `ai:<providerId>` |
| LLM 供应商展开区 | `src/components/Settings/sections/LlmSettingsSection.tsx` | 动态供应商 | `llm:<providerId>`，尚未按 `credentialId` |
| 首次引导 | `src/features/onboarding/components/OnboardingModal.tsx` | 派欧云、Fal、APIMart、KIE | `ai:<providerId>` |

`ApiKeyInput.tsx` 目前用 `flex + gap` 并排渲染 `UiInput` 与 `UiButton`。后续只改这个唯一入口即可同步三类界面；不要新增通用 `UiPasswordInput`，也不需要扩展原生 input 实现。

### 3.2 供应商来源与官方链接

- `packages/ai-sdk/src/llm/providerPresets.ts` 的每个 `LlmProviderPreset` 已有 `apiKeyUrl`。
- `packages/ai-sdk/src/llm/bigmodel/profiles.ts` 的中国大陆/Global profile 各有独立 `apiKeyUrl` 与 `defaultCredentialId`。
- `createProviderFromPreset()` 只生成运行配置，没有保留“来自哪个预设”的身份；弹窗重开时靠 `providerId` 猜预设。
- 只靠 `providerId` 猜来源不可靠：用户自定义供应商可能使用与预设相同的名称/ID，区域化实例也不能只靠 ID 推断。
- 全局生成供应商已有 `src/core/config/providers.ts` 的 `ProviderLink[]` 和现有外链入口，不需另建链接表。

建议把以下可移植的设置契约加入 SDK，而不是在 UI 写供应商 ID 分支：

```ts
type LlmProviderSetup =
  | { kind: 'preset'; presetId: string }
  | { kind: 'custom'; apiKeyManagementUrl?: string }

interface LlmProviderConfig {
  // 既有字段……
  setup?: LlmProviderSetup // undefined 只用于一次性归一化旧配置
}
```

并提供纯函数 `resolveLlmProviderApiKeyUrl(provider)`：

1. endpoint profile 的官方 URL 优先；
2. `setup.kind === 'preset'` 时从唯一 preset 目录解析；
3. `setup.kind === 'custom'` 时使用用户填写且校验过的 HTTP/HTTPS URL；
4. 没有 URL 就返回 `null`，界面不显示空入口。

`createProviderFromPreset()` 与内置默认供应商必须写入 `setup.kind='preset'`；自定义供应商明确写 `setup.kind='custom'`。旧配置只在归一化时迁移一次，保存后不再靠 `providerId` 猜。

### 3.3 凭据坐标

SDK 的 `LlmProviderConfig`、模型配置和 endpoint identity 已有 `credentialId`，运行时也按它向 `RuntimeContext.credentials` 取密钥；设置界面却仍把 `providerId` 传给 `llmGet/Set/RemoveProviderApiKey`。

目标不变量：

- 所有 LLM 设置读写先用 SDK identity resolver 得到 `credentialId`，再访问 `llm:<credentialId>`。
- 新建自定义供应商生成稳定且唯一的 `providerId`，并显式令 `credentialId=providerId`；以后只改显示名称不迁移凭据槽。
- BigModel 中国大陆与 Global 继续使用不同 credentialId，禁止互相回退。
- 派欧云允许读取 `ai:ppio` 作为既有产品级 fallback，但新建自定义供应商绝不继承这一特例。
- 删除供应商时只删除它独占的 LLM 凭据槽；若仍有其他供应商引用同一 `credentialId`，保留密钥并返回“仍被引用”的结果。

现有 IPC 参数虽然名为 `providerId`，实质已能存任意合法槽 ID。为避免继续混淆，后续契约应把 LLM 路径的参数/返回字段改名为 `credentialId`；生成供应商的 `ai:<providerId>` 契约保持不变。

### 3.4 创建、删除与回滚

当前创建顺序只有 config，没有 key；当前删除顺序只有 config/models，没有 key。`useApiKeys` 与 `useLlmSettings` 还各自复制了一套 450ms 防抖保存，组件卸载会清掉尚未执行的 timer，存在“输入后立即关闭设置，界面看似已改但实际没落盘”的窗口。

需要一个唯一的供应商设置事务，不允许由 `LlmProviderDialog` 拼调用顺序：

```text
弹窗草稿（provider + tri-state credential mutation）
  → commands / PAL
  → Electron llm provider settings transaction
  → llm-config.json + keystore(llm:<credentialId>)
  → 成功后返回脱敏结果并刷新界面真相源
```

凭据变更必须是三态，而不是用空字符串猜语义：

- `unchanged`：编辑供应商但不碰已有密钥；
- `set`：写入新密钥；
- `remove`：用户明确清空已有密钥。

推荐新增一个领域级 IPC（例如 `llm:commitProviderSettings` / `llm:deleteProviderSettings`），而不是再加一组低级 Key CRUD。主进程在同一串行临界区内：

1. 读取并保存旧配置及目标凭据的加密快照；
2. 校验 provider/setup/URL/credentialId 与依赖关系；
3. 原子写配置文件并执行凭据变更；
4. 任一步失败，恢复旧配置与旧加密条目；
5. 返回 `providerId`、`credentialId`、`configured`、`rollbackStatus` 等非敏感结果。

因此结论是：**需要改 Electron / preload / IPC**。理由不是缺少单个 set/remove 方法，而是跨配置文件与 keystore 的事务必须由拥有两种资源的宿主统一负责；渲染层补偿无法覆盖窗口退出、进程崩溃与并发保存。

现有 keystore 的 `read → 整文件 write` 也不是原子替换。实现事务时应同时把 keystore 与 `llm-config.json` 改为同目录临时文件 + fsync/rename 的原子更新，并用进程内互斥锁串行化；恢复快照只处理加密 ciphertext，任何日志、返回值、测试快照都不能包含明文 key。

删除计划还必须先检查模型、Prompt Profile、Agent Profile 对供应商的引用。不能只删 providers/models 后留下悬空引用；应由纯函数输出删除影响，存在主模型等强引用时阻止并列明要先切换的配置，普通模型记录可在同一事务删除。

`normalizeLlmConfig()` 的默认播种也要收口：默认供应商/模型只在“没有配置文件”的首次创建时播种，不能在每次归一化时复活用户已经删除的记录。

## 四、目标界面

### 4.1 管理供应商弹窗

右栏按以下顺序组成一个扁平表单，不新增卡片：

1. “供应商预设”标签 + 下拉；
2. 仅自定义模式显示“供应商名称”；
3. “接口类型”；
4. “API 地址”；
5. “API 密钥”，右侧可显示“获取/管理 API Key”外链；
6. 仅自定义模式显示可选“密钥管理地址”；
7. “启用供应商”；
8. 已存在且允许删除时，在底部 `UiGroup divided` 中单独一行显示删除按钮。

删除“当前编辑”内嵌面、预设推荐模型段落和预设说明段落。推荐模型仍由 `createModelsFromPreset()` 在保存时自动补缺，但不作为常驻解释重复显示。

字段标签使用现有 `UiFormRow` / `ApiKeyInput label`，输入仍使用 `UiInput`。自定义名称条件来自 `setup.kind`，不得写 `if (providerId === ...)`。

### 4.2 API Key 输入

只改现有 `ApiKeyInput`：

- 外层负责标签、可选管理链接和 hint；
- 输入区使用 `relative`；
- `UiInput` 增加右内边距；
- 眼睛使用 `UiIconButton appearance="color-only"` 或等价无框档，绝对定位到输入框右侧；
- `label` 与 input 用稳定 `id/htmlFor` 关联；
- `aria-label/title` 随“显示/隐藏”切换；
- 密钥显示为明文时，在输入节点或同尺寸包装层条件性添加 `data-observation-sensitive`；password 圆点态不额外扩大遮罩范围；
- 切换供应商、关闭弹窗或保存成功后恢复隐藏态。

内置/预设供应商通过 resolver 得到官方 URL 后显示“获取/管理 API Key”；自定义供应商使用用户配置 URL；`null` 时不渲染链接。外链继续走 `useExternalLink` → PAL → 主进程 `openExternalUrl()`，沿用 HTTP/HTTPS 协议校验，禁止业务组件直接调用 Electron shell。

## 五、日志与敏感数据边界

- 渲染层与主进程已有按 `apiKey/api_key/authorization/token/secret/password` 字段名脱敏的统一 sanitizer，但新事务不能依赖“最后会脱敏”而把 key 放入日志对象。
- 事务日志只记录 `start/completed/failed`、操作类型、providerId、credentialId、是否配置、受影响模型数、rollbackStatus；不记录明文、Authorization、输入草稿或 keystore ciphertext。
- 错误消息不能拼入 key。失败测试使用明显 sentinel，并同时扫描结构化日志和错误文本。
- 密钥明文不得写入 `llm-config.json`、localStorage、Zustand 持久化或助手 Effect/evidence。
- 显示明文只发生在用户当前可见输入框；关闭/切换后清理 React state。助手的 `security.provider_keys` 与 `llm.configuration` 继续只返回“是否配置”，不返回值。

## 七、测试计划

### 7.1 纯契约与事务

- preset/custom 来源归一化；旧配置只迁移一次。
- 内置 preset、BigModel CN/Global、自定义 URL、无 URL 的 resolver 精确测试。
- 自定义 provider 的 providerId/credentialId 稳定且独占；显示名变化不迁槽。
- 创建成功同时落 config 与 key；key 失败时 config 未变化；config 失败时旧 key 恢复。
- 删除成功清理 provider/models 与独占 key；共享 credential 不删；PPIO fallback 不删 `ai:ppio`。
- 删除被 Agent/Profile 强引用时拒绝且无写入。
- 配置/keystore 原子写失败、恢复失败、并发提交与进程重启 journal 恢复。

### 7.2 UI 与可访问性

- `ApiKeyInput` 初始为 password，眼睛在同一相对输入容器内且无独立边框；切换后 aria 文案、图标和 type 一致。
- 明文态有 `data-observation-sensitive`，隐藏态只显示圆点。
- 所有三类生产密钥入口仍引用同一个 `ApiKeyInput`，不出现第二个业务 password 实现。
- 自定义模式显示供应商名称、API Key、可选管理 URL；预设模式隐藏名称和自定义 URL。
- 内置供应商显示正确官方入口；自定义无 URL 不显示入口。
- “当前编辑”、推荐模型和重复说明不存在；所有字段有上置标签；删除动作独立一行并二次确认。
- 保存失败保持弹窗与草稿，显示可行动错误；保存成功才关闭/重置。

### 7.3 安全、日志与正式验证

- sentinel key 不出现在 `llm-config.json`、日志、错误、Effect、截图证据或测试快照。
- 主/渲染日志 sanitizer 回归，事务日志只含稳定非敏感坐标。
- 精确 Vitest：SDK resolver、config planner、keystore、IPC contract、ApiKeyInput、ProviderDialog、surface observation。
- 因涉及公共类型、持久化、IPC 和 preload，按 L2 执行两个 TypeScript 工程、变更文件 ESLint、`check:main-imports`、`check:surface`、`check:colors`、`check:icons` 与 `electron:build`。
- 构建后运行正式 Electron 设置场景，覆盖 960×640 与常用宽屏；自动点击预设/自定义、明文切换、保存失败、删除确认并生成截图，Agent 逐张目视。使用临时 profile 和 fake credential backend，不接真实供应商。

## 八、建议拆分

1. **14.2：供应商 setup/credential 契约与删除 planner**
   先在 SDK/纯领域层建立 preset/custom、管理 URL resolver、credentialId 与删除影响契约，补精确测试；不改 UI。
2. **14.3：宿主 provider+credential 事务**
   实现主进程串行事务、原子写、回滚、IPC/preload/PAL/command 与日志安全测试；不做界面重排。
3. **14.4：统一密钥输入与供应商弹窗 UI**
   只改现有 `ApiKeyInput`，完成内嵌眼睛、字段标签、官方入口、自定义 URL、删除独立行和视觉场景；不再新增密码组件。
4. **14.5：全链路收口**
   跑 L2/构建/正式 Electron UI 场景与断牙，确认三类密钥入口、事务回滚、观察遮罩、日志脱敏和无真实网络；若 SDK 公共契约需要发布，先在 Henji-AI 完整验证再发布，并按消费者清单只同步实际受影响宿主。

## 九、助手能力与遗留风险

### 助手台账

无需更新 `docs/rules/assistant-status.md`：

- `settings.api_keys`、`settings.llm` Surface 已登记；
- `security.provider_keys` 与 `llm.configuration` 已明确为受保护只读设置；
- 本方案不扩大助手读取/写入密钥的能力，不改变任何域的“通/不通”，也不增加欠账清单。

后续若改动 Surface ID 或 protected setting 契约，才需要运行 `check:assistant-capabilities` 并重新判断台账；仅调整同一 Surface 内布局无需改台账。

### 风险

- 旧配置没有来源字段，首次迁移需要区分真实 preset 与同名 custom；无法无歧义判断的记录应按 custom 保守处理，不能静默套官方 preset。
- 真正跨两个文件的崩溃一致性需要主进程 journal/原子恢复；只在 renderer 写 try/catch 补偿不够。
- 删除供应商的依赖引用必须先定产品语义；默认应阻止删除仍被 Agent/Profile 使用的供应商，不能自动悄悄改主模型。
- `safeStorage` 保护本机静态密文，但 renderer 为支持“显示”仍会短暂持有明文；应缩短生命周期、默认隐藏、关闭即清理，不能宣称它防得住同账户已控制进程。
- `LlmSettingsSection.tsx` 与 `LlmConfigService.ts` 已分别 428/448 行，实施时必须拆职责，不能把事务和迁移继续塞回原文件。
