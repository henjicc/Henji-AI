## 首败、停止与修复

1. 首轮 Fal 4.0 create 返回 HTTP 200 与明确 taskId，但 SDK 0.1.2 优先保存 `request_id`、按 catalog alias 重建 status route，20 次同 task poll 均得到 HTTP 405/空 JSON，终态 `provider_task_unreachable`。当即停止所有后续付费 create，Fal 4.5 未执行，也没有重发 Fal 4.0。
2. 根因修复：Fal create 同时返回 `status_url`/`request_id` 时优先保存完整 `status_url`；从完整 URL 提取纯 request id 写入 metadata，禁止完整 status URL 被媒体 URL 收集器误收。
3. 第一次离线回归真实失败两处：fixture 仍期待旧 request id；完整 status URL 被结果 URL 收集。修正 fixture 与 request id 规范化后，3 文件 85/85 通过。
4. 只有在用户给出新的“授权收口”后才再次联网；Fal 4.0 completed 后才创建 Fal 4.5。

上述首败和第一次离线失败未被后续通过删除或稀释。
