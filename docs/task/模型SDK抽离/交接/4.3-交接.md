## 统一 / 刻意不统一

| 能力 | 处理 | 最终边界与理由 |
|---|---|---|
| CredentialStore | 统一 | 单一 `get(scope, providerId)`；scope 隔离密钥空间，宿主决定持久化方式 |
| task registry | 统一 | 单一实现；命名空间避免两类同名 taskId 互相取消 |
| 错误 schema/分类 | 统一 | 生成错误码与 LLM `[provider_error]` 协议共存；分类器只有一份 |
| 网络入口 | 统一 | 两类执行经宿主 `Transport`，需预连接保护的请求经 `fetchProvider` |
| shouldRetry | 统一判断 | 唯一函数按 mode 返回分类结论；不合并重试次数与生命周期 |
| Tracer | 统一接口 | SDK 只报告通用 span，宿主决定观测系统 |
| 创建+轮询 vs SSE/模型步 | 刻意不统一 | 服务端 taskId、长轮询、进度、查询容错与 token/tool-call 流的终止条件和结果形状不同 |
| 轮询连续失败 vs 模型步请求重试 | 刻意不统一 | 前者保护长任务状态查询，后者发生在单个未完成模型步；共享分类但不能共享次数/状态机 |
| 助手 trace | 刻意不统一 | 带 router/turn/context-window 等助手业务语义，属于宿主观测格式 |
| capability-smoke | 刻意不统一 | 请求/结果 schema 仍属于痕迹AI应用边界，迁 SDK 会违反可移植性约束 |
| scripted-model-step | 刻意不统一 | 痕迹AI助手测试替身，不是 SDK 产品能力 |

## 兼容性证据

- 生成错误码：本任务没有修改生成侧 `new AiRuntimeError(code, ...)` 调用点的 code 字符串。当前扫描仍包含 `cancelled`、`api_key_missing`、`invalid_route`、`provider_not_found`、`empty_result`、`provider_task_failed`、`provider_task_unreachable`、`provider_network_error`、`provider_http_error`、`invalid_json`、`invalid_response`、`unknown_provider`、`unsupported_provider`、上传与媒体类既有 code。
- LLM 错误：原 `[provider_error]${JSON}` 序列化 marker、严格 schema、`ProviderModelStepError.details` 与解析函数保持；16 个 provider error 测试覆盖 authentication/billing/quota/rate-limit/context-overflow/content-filter/cancel/network 等分类。
- 取消：registry 测试证明同 taskId 的 generation 与 llm 控制器互不影响；chat/model-step 测试证明 `AbortSignal` 传入 Transport 并归一为取消语义。
- 网络：原生 SSE 契约测试证明请求经过注入 Transport；Vercel 模型步契约测试用真实 OpenAI-compatible SSE 响应形状证明也经过注入 Transport。
- 错误 Key 替代证据：假 Transport 返回 401，得到 authentication 分类、用户可读消息且不重试；未向外网发送错误凭据。
- IPC/宿主边界：未改渲染层通道契约；应用专属 trace/capability-smoke/scripted-model-step 未迁移。
- 断言语义：既有断言未为“换绿”而改写；只增加新行为的契约断言并同步命名空间调用签名。

## 遗留风险

- `createModelStepLanguageModel` 为保留 `electron/main/agent-utility.ts` 既有三参数直接调用，未注入 Transport 时仍用 `globalThis.fetch` 组成兼容 Transport；它仍经过 `fetchProvider`，但 UXP/Tauri 等新消费方必须从 `runModelStep` 或显式第 4 参数注入宿主 Transport。
- 模型步既有 `maxRetries` 允许在一个模型步未形成结果时重试，这是 4.2 前既有行为；4.3 只统一判断，没有扩大次数。后续若要重新评估 token 计费边界，必须单独立项，不应混入 5.2 入口包装。
- `@fal-ai/client` 仍靠 npm workspace 提升解析、未写入 SDK 自己的 dependency，是 2.4 留给 6.2 的发布风险；4.3 未处理也未扩大。
- 真实供应商的取消响应与错误 body 形状仍需 6.4 在获得授权后补 E2E；当前证据是精确契约测试。

## 给 5.2 的输入

1. `createAIClient` 应按 `generate` / `continuePolling` / `chat.stream` / `chat.modelStep` 分组包装，不能合并成单个生命周期 `execute()`。
