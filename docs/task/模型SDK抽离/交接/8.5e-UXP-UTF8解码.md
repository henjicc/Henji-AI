# 8.5e UXP UTF-8 解码交接

## 结论

- 已发布 `@henjicc/ai-sdk@0.1.8`。Photoshop 27.5 / UXP 9.2 即使没有全局
  `TextEncoder` / `TextDecoder`，`@henjicc/ai-sdk/llm/streaming` 仍可增量读取 SSE。
- 修复位于 SDK 唯一原生 SSE 实现内部；宿主不需要、也不应注入全局 polyfill，旧包根与
  `llm` 兼容入口继续复用同一份 `streaming.ts`。
- reasoning、text、usage、finish reason、`[DONE]`、Abort/cancel、
  `RuntimeContext.transport` 契约均未改变。

## 根因与修复

真实 Photoshop smoke 返回 `TextEncoder=false`、`TextDecoder=false`。`0.1.7` 的
`packages/ai-sdk/src/llm/streaming.ts` 直接执行 `new TextDecoder()`，因此网络响应进入 SSE
读取前就失败；原门禁向 VM 注入了 Node 的 `TextDecoder`，产生了假绿。

`0.1.8` 新增 `src/llm/utf8-stream-decoder.ts`，实现不依赖 Node/DOM 全局的增量 UTF-8 解码：

- 中文与 emoji 可在任意字节位置跨 chunk；
- 非法 continuation、过长编码、UTF-16 代理区与大于 U+10FFFF 的序列按标准替换字符处理；
- 流式截断尾段暂存，最终 flush 只输出一个替换字符；
- 不修改宿主全局，不引入 Buffer、process、Node builtin 或额外依赖。

UXP 门禁不再向 VM 提供 `TextEncoder` / `TextDecoder`，并显式禁止 bundle 出现直接
`new TextDecoder`。fixture 自带的 UTF-8 编码只用于 Node 门禁数据准备，不进入发布 bundle。
