# 8.3 Henji-AI 本体显式选择交接

## 结论

Henji-AI 已从 SDK 根客户端的隐式默认 99 模型切换为显式 modular 装配。应用唯一选择层位于
`src/core/modelCatalog/applicationModelProfile.ts`，直接组合已发布 `@henjicc/ai-sdk@0.1.5` 的 8 个
provider pack：volcengine、bailian、grsai、ppio、modelscope、apimart、kie、fal。

应用生产客户端、渲染层模型注册和主进程进度估时现在消费同一选择层；没有先导入全量 catalog 再过滤，
没有复制 client、provider、上传、轮询或取消内核，也没有把默认目录之外的 3 个 Fal 消除工具放进普通生成页。
SDK/package 源码、版本和已发布产物均未修改，本任务没有发布包或发送真实外网请求。

## 应用 profile 与边界

- `HENJI_GENERATION_PROVIDER_PACKS`：8 个公开 provider pack 的显式组合。
- `assertHenjiGenerationSelection()`：启动期门禁，要求 8 个预期 provider、99 个条目且 99 个 ID 唯一；漏 pack
  会在 client、目录或 UI 启动前明确失败，不会静默缩成残缺目录。
- `HENJI_GENERATION_MODELS`：只从 pack 内真实 models 展开，不维护第二份模型 ID 清单。
- `getHenjiGenerationModel()`：复用 SDK `createModelIndex`，保留真实 ID 与 alias 的既有解析语义，供进度估时使用。
- `createHenjiAIClient(runtime)`：固定调用
  `createAIClient({ runtime, generation: { mode: 'modular', packs } })`；chat/LLM 仍来自同一根 client。
- Electron 经典 `moduleResolution: node` 不理解 package exports，因此只在 `electron/types/` 增加
  `provider-packs/*` 的类型安全声明适配；实际运行仍解析 npm package 的公开 exports。renderer TypeScript、
  Electron TypeScript、`check:main-imports` 和真实 electron-vite build 均已证明该路径合法，没有相对导入 SDK 内部源码。

当前 provider pack 模型数保持：volcengine 2、bailian 2、grsai 4、ppio 6、modelscope 7、apimart 20、
kie 27、fal 31，合计 99。测试按 ID 集合与兼容 catalog 做 99/99 parity，不把兼容 catalog 用作生产选择源。

## 统一 capability discovery

`henjiModelCapabilityDiscovery` 使用同一组已选 generation packs 与 SDK 的真实
`LLM_MODEL_CATALOG_ENTRIES` 建立应用查询；`searchHenjiModelCapabilities(query)` 直接接受 SDK 标准
`ModelCapabilityQuery`，支持 provider、output、operation、input、features、tags 组合，不改变现有 UI/ModelRegistry 协议。
模型 tags、input limits、runtime media fields 与 LLM input/capabilities 仍是唯一真相，没有第二份手写能力表。

当前查询实测计数：

| 查询 | 命中数 |
|---|---:|
| generation / LLM 总画像 | 99 / 14 |
| 图片生成 / 图片编辑 | 49 / 40 |
| 视频生成 / 文生视频 / 图生视频 | 49 / 46 / 49 |
| 参考生视频 / 视频编辑 | 23 / 5 |
| 音频生成 | 1 |
| chat 文本 / 图片 / 视频 / 音频输入 | 14 / 9 / 9 / 1 |
| chat 同时接受 text+image+video+audio | 1 |
| 默认 `features=erase` | 0 |

单独用 `@henjicc/ai-sdk/tool-packs/fal-image-edit-tools` 建立测试 discovery 时，Fal + image-edit + erase
精确返回 3；这证明 optional pack 只有宿主显式选择后才出现。

## 消费方改动

- `electron/main/services/ai-runtime/sdk-runtime.ts`：生产 `sdkAIClient` 改由 `createHenjiAIClient` 创建。
- `electron/main/services/ai-runtime/progress.ts`：估时与样本记录从应用选择索引查模型，含 alias 兼容。
- `src/core/loaders/modelLoader.ts`：presentation 合成与 ModelRegistry 注册从 `HENJI_GENERATION_MODELS` 读取，结果仍为 99。
- `src/core/index.ts`：导出应用 profile 与 discovery 适配，供未来功能筛选消费。

未修改 TSX、UI 结构、展示补丁、模型 schema、助手提示词或助手能力登记。ModelRegistry、普通生成页、画布、
设置与助手看到的 generation 范围仍为原 99，真实 LLM 目录范围仍为 14；因此没有改变助手“通/不通”或新增欠账，
不更新 `assistant-status.md`。

- `electron:build` 通过，其中 SDK 可移植性、默认 99、全部 modular bundle、助手能力 4+152 项门禁均通过。
- `electron:smoke` 通过：providerStatusCount=8、pageErrors=[]、consoleErrors=[]。
- `test:reality -- --suite integration` 通过：9 文件、35 项助手真实运行时集成测试。
- diff whitespace、敏感信息、跨层 import 与文件体积审计通过；新增生产文件 109 行，无新增裸 `any` 或循环依赖。

本任务没有 UI 改动，因此没有运行 UI tour/UI audit；没有网络协议或密钥行为变化，因此没有真实付费/外网测试。

## 给 Photoshop UXP 的输入

1. UXP 应按产品功能显式导入所需的单模型 pack、provider pack 或 Fal 工具 pack，不要从全量 generation 隐藏 UI。
2. 运行时筛选统一使用 `createModelCapabilityDiscovery` 的 provider/output/operation/input/features 条件；pack 决定静态分发，
   discovery 只筛选已经导入的候选，两者不能互相替代。
3. 若插件只需要 Fal 消除，选择 `tool-packs/fal-image-edit-tools`；不要把 3 个工具并回普通生成目录。
4. Photoshop 宿主继续只实现自己的 RuntimeContext、MediaReader 与 UI 映射，执行、上传、轮询、取消由 SDK client/pack 负责。
