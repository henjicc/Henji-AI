# 8.5a UXP LLM 流式入口交接

## 结论

- 已发布 `@henjicc/ai-sdk@0.1.7`，UXP 请使用窄入口 `@henjicc/ai-sdk/llm/streaming`，不要从 `@henjicc/ai-sdk/llm` 引入原生 chat stream。
- 窄入口复用原有 `chat.ts` / `streaming.ts` 唯一实现；旧 `llm` 和包根入口保持兼容。
- 静态依赖图不经过 `llm/index`、`modelStep`、Zod、Vercel `ai` 或 `@ai-sdk/*`，也不含 JIT / Node 填充。
- 未发起任何真实 LLM 或付费请求；流式与取消验证全部使用注入的 `RuntimeContext.transport` 脚本 fixture。

## 给 UXP 消费方的公开契约

```ts
import {
  cancelLlmChatTask,
  runLlmChatStream,
  type LlmStreamEventDto,
} from '@henjicc/ai-sdk/llm/streaming'
```

公开 value exports：

- `runLlmChatStream`
- `cancelLlmChatTask`
- `resolveLlmTaskId`
- `normalizeLlmChatError`
- `ProviderModelStepError`
- `parseModelProviderError`
- `serializeModelProviderError`

必要类型已从同一入口导出，包括 `LlmStreamEventDto`、`LlmChatRequestDto`、`LlmChatStreamOutcome`、`LlmUsageDto`、`RuntimeContext`、`Transport` 及 provider error 类型。

## 实现边界

- `chat.ts` 改为直接依赖 leaf modules，避免经过 runtime/upload barrel 将 Zod 拉入 UXP 图。
- provider error 的运行时 class / parse / serialize 抽到零 Zod 的 `provider-error-core.ts`；`errors.ts` 仍保留 Zod schema 并重导出同一实现。
- LLM provider protocol 的运行时函数抽到零 Zod 的 `providerProtocolCore.ts`；`providerProtocol.ts` 仍保留 schema 和兼容导出。
- native SSE 保留跨 chunk UTF-8 解码、reasoning/text event、usage、`finish_reason`、`[DONE]`、provider HTTP error 及 Abort/cancel 归一化。
- 所有网络调用必须走 `RuntimeContext.transport`，窄入口没有 global `fetch`。
