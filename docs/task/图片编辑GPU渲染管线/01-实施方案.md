# 图片编辑 GPU 渲染管线实施方案

## 当前项目和相关功能现状

- `src/core/imageEdit/v3/` 已有稳定文档、图层树、RenderPlan、CPU 分块执行器、颜色契约、撤销和资源预算。
- `src/features/imageEdit/v3/execution/` 当前以 CPU RenderPlan 合成预览/视口瓦片，部分模糊、扩散、辉光可临时进入 vGPU，最终经 ImageBitmap、Canvas2D 图集或 DOM 代理展示。
- 普通多栅格层拖动已有 DOM 代理快路径，但复杂图层仍在高频交互中触发 CPU 合成；多个预览优先级仍可能复制 Worker 与资源。
- vGPU `0.3.1` 已在仓库使用。官方契约确认：一次 `init()` 产生共享设备的 Context；昂贵资源应常驻，`Frame` 可多 Pass 单次提交，Target 支持 `rgba16float`/`r8unorm` 与测试回读，热路径禁止逐帧 readback。

## 最终目标与总体方案

保留现有业务真相，只替换渲染执行与呈现：每个打开的编辑会话创建一个 GPU Scene Worker、一个设备和一个 vGPU Context，将文档投影为项目自有的 retained 2D RenderGraph。资源首次出现或内容版本变化时上传；拖动只更新瞬态矩阵并请求合并帧；权威文档只在手势提交时更新一次。

场景协议固定包含 `initialize`、`sync-scene`、`upload-tiles`、`update-transform`、`update-viewport`、`render`、`export`、`dispose`；事件包含 `ready`、`tiles-needed`、`frame-ready`、`export-tile`、`device-lost`、`failed`。`sceneGeneration`、`cameraSequence`、`interactionSequence` 独立校验，旧帧不得覆盖新状态。

## 技术策略

- GPU Scene 通过既有 `ImageEditWebGpuDeviceManager` 获取受管 `GPUDevice`，再使用 vGPU `initFromDevice(device)` 建立会话 Context；原生设备由设备管理器持有，vGPU 只释放自身包装资源。1.2 的生产客户端默认不发出 `render`，待 2.1 具备基础栅格合成后再启用，不改变现有可见输出。
- 源纹理以 `resourceRef + mip + tile + contentVersion` 去重；显存预算默认 256 MiB，LRU 不得淘汰当前视口目标 mip、交互层和最后稳定帧。
- 颜色中间目标使用线性预乘 Alpha `rgba16float`，蒙版使用 `r8unorm`；固定混合可直接表达的模式走 attachment blend，需要读取背景的模式走离屏 Target 和 ping-pong。
- 创建一次并复用 Context、Target、Draw/Effect、uniform/storage buffer；预热目标签名 Pipeline。静态工作可使用 Bundle，动态矩阵只做 in-place `set()`。
- 第一阶段继续输出 ImageBitmap 复用现有展示；完成色彩和设备恢复后切换 OffscreenCanvas/WebGPU Surface，实现预览零回读。
- GPU 丢失或失败时保留最后稳定帧并立即切 CPU；恢复后按最新权威快照重建一次，不向正式界面展示后端细节。

## 兼容与非任务范围

- 不改变 `ImageEditDocumentV3`、节点数据、项目包、撤销历史、实时保存和助手能力。
- 解码、ICC 读取与最终编码继续由现有主进程服务承担；GPU 接管渲染和颜色运算。
- 不新增 PixiJS、CanvasKit、Skia 或第二套图层模型；不改 SDK、模型与供应商适配；迁移期间不升级 vGPU。

## 阶段关系

1. 基准和 Scene 基础设施先串行完成。
2. 基础栅格合成完成后，实时交互接入；完整图层语义与大图色彩可以并行。
3. 画笔/效果与直接呈现可在各自前置完成后并行。
4. GPU 导出依赖完整效果和大图色彩；最终切换依赖直接呈现与导出共同完成。

## 风险控制与回退

- 以 1.1 CPU golden 为像素真值，同输入同时跑 CPU/GPU 比较；原通用目标为线性误差不超过 `1e-4`、8-bit 最大 1 LSB。2.1 按既定 `rgba16float` 中间目标实测存在逐层半精度量化，基础 normal/opacity/transform 门槛经记录 006 调整为线性误差不超过 `1.1e-3` 且 8-bit 仍不超过 1 LSB；后续若引入全精度路径，仍以 `1e-4` 为目标。
- 每个阶段保留 CPU 自动回退和结构化后端诊断，只有相应 Reality 与 golden 通过才扩大 GPU 默认范围。
- `target.read()`/`readFloats()` 只用于测试、诊断和导出，禁止进入实时帧循环。
- 设备恢复、资源销毁、过期序列和预算淘汰必须有精确测试；任务按独立提交回退。

## 全局开发约束

- 新文件优先不超过 400 行，不新增裸 `any`，复用统一日志入口。
- 高频交互状态不进入 React 大状态、持久化或历史快照。
- 每个任务开始前同步总览状态，结束后填执行记录、交接文件、精确验证、独立提交并推送。

## 最终验收条件

- 真实 KIE 五层连续拖动 event-to-present p95 ≤ 16.7 ms、p99 ≤ 33.4 ms，且至少比 1.1 基线提升 3 倍。
- 100 次 pointermove 不改变 revision、不编译 RenderPlan、不执行 CPU region、不重复上传、不回读；pointerup 只提交一次。
- 完整图层、HDR、8192 大图、设备丢失、节点预览、单层/整图导出及项目包往返通过精确测试和双尺寸 Electron Reality。
- 当前全部可渲染文档和既有导出格式默认走 GPU，CPU 只在设备或运行失败时接管。
