# 重要记录

## 记录 001：采用 vGPU 加项目自有 retained 2D 场景

- 日期：2026-09-04
- 状态：已确定
- 背景：vGPU 已提供 Context、Target、Frame、Effect/Draw、Bundle、uniform 与读回能力，但没有 PSD 式图层树语义。
- 最终决定：使用 vGPU 作为 WebGPU 工具层，图层树、RenderGraph、失效和缓存由项目实现；必要 shader 下探 WGSL。
- 选择原因：最大化复用现有 vGPU 与 RenderPlan，同时避免引入第二套框架和业务模型。
- 影响任务：1.2～5.2

## 记录 002：CPU 管线在迁移期和故障时保持可用

- 日期：2026-09-04
- 状态：已确定
- 背景：WebGPU 可用性、设备丢失和复杂语义迁移都需要安全边界。
- 最终决定：运行时固定按 WebGPU Surface → GPU ImageBitmap → CPU/Canvas2D 选择，失败自动回退且不向正式界面展示内部后端。

- 影响任务：1.2、2.2、4.2、5.2

## 记录 003：以确定性 CPU 输出作为 GPU 迁移像素真值

- 日期：2026-09-04
- 状态：已确定
- 背景：GPU 合成、色彩与分块导出必须有跨实现的稳定比较基准。
- 最终决定：固定五层、16 层、复杂蒙版、Rec.2020 PQ HDR 和 8192 大图场景；CPU RenderPlan 输出指纹和误差比较器作为后续 GPU golden 入口。

## 记录 005：GPU Scene 使用受管原生设备并渐进启用生产渲染

- 日期：2026-09-04
- 状态：已确定
- 背景：项目已有 WebGPU 设备管理器和丢失冷却策略；vGPU 官方 `initFromDevice(device)` 支持包装外部设备，且包装释放不应销毁由外部持有的原生设备。
- 最终决定：每个编辑会话只由 `ImageEditWebGpuDeviceManager` 持有一个设备，vGPU Context 通过 `initFromDevice` 绑定该设备；1.2 只建立生命周期和协议，生产 `render` 在 2.1 基础合成可用前保持关闭。
- 选择原因：避免两套设备生命周期和资源复制，同时保证基础设施落地不会提前改变现有 CPU 可见输出。
- 影响任务：1.2、2.1、2.2、4.2

## 记录 006：基础 FP16 合成采用 1.1e-3 线性误差门槛

- 日期：2026-09-04
- 状态：已确定
- 背景：原计划同时要求中间颜色目标固定为线性预乘 `rgba16float`，又要求 normal/opacity/transform 的线性误差不超过 `1e-4`。2.1 以相同输入比较 CPU Float32 与真实 WebGPU 后，五层最大误差为 `0.00103194`，16 层为 `0.00103605`，8-bit 编码差异均不超过 1 LSB；误差表现符合逐层 FP16 attachment blend 的量化，而不是纹理重传或 shader 顺序错误。
- 最终决定：基础 `rgba16float` 合成的线性误差门槛调整为不超过 `1.1e-3`，同时保留 8-bit 最大 1 LSB 的硬门槛；不得把原 `1e-4` 静默标记为通过。需要 `1e-4` 的后续场景必须使用经设备能力验证的更高精度路径或重新评估中间格式。
- 选择原因：vGPU 官方格式矩阵确认 `rgba16float` 是默认可渲染、可线性过滤的 HDR 中间格式；`rgba32float` 默认不可线性过滤，而 WebGPU 的 32-bit 浮点 blending 还受可选 `float32-blendable` 能力约束。继续使用计划指定的广泛兼容 `rgba16float`，并以实测上界加约 6% 余量设为 `1.1e-3`，比假定所有设备支持 Float32 blending 更可控。
- 影响任务：2.1、3.1、4.1、5.1、5.2

## 记录 007：交互序列与稳定帧交接保持后端无关

- 日期：2026-09-04
- 状态：已确定
- 背景：高频 pointer event 的时间戳不保证跨手势、合成事件或相同时间戳时严格单调；同时 2.2 使用 GPU ImageBitmap，4.2 将切换直接 WebGPU Surface，不能让手势和权威提交依赖具体呈现后端。
- 最终决定：每个编辑会话使用本地严格单调 interaction sequence，transient update、clear、权威 scene 接管与过期帧丢弃共享同一门控；过期 ImageBitmap 必须先关闭。GPU 帧先完整写入 staging，再原子替换安全表面和前表面；任何失败保留最后稳定帧并自动回退。呈现后端可在 ImageBitmap 与直接 Surface 间替换，但不得改变该序列、提交和回退契约。
- 选择原因：避免时钟语义造成旧帧覆盖新手势，确保 GPU/CPU 切换无黑屏，并让 3.1、4.1 扩展内容语义时不重新发明交互协议。
- 影响任务：2.2、3.1、4.1、4.2、5.2

## 记录 008：3.1 RenderGraph 固定以线性预乘颜色保存节点结果

- 日期：2026-09-04
- 状态：已确定
- 背景：CPU RenderPlan 允许调整节点在 perceptual-working 域执行，但组、混合与后续节点仍需共享一种可缓存的 GPU 输出契约；同时源纹理解码若先写入 FP16，会在第一次正式合成前额外引入一次半精度往返。
- 最终决定：RenderGraph 的可缓存节点输出统一为线性预乘 RGBA；合成与调整中间目标使用 `rgba16float`，源解码缓存使用只经 `textureLoad` 读取的 `rgba32float`。curves/HSL 在 shader 内进入 perceptual-working，按 CPU 顺序完成调整、蒙版、混合和透明度后再转回线性；曝光与温度/色调保持线性。曲线 LUT 使用 `r32float` 与 `textureLoad`，不依赖 Float32 filtering 或 blending。
- 选择原因：保持跨节点单一颜色/alpha 合同，并避免源缓存额外 FP16 量化；实测恢复记录 006 的五层 `0.00103194`、16 层 `0.00103605` 上界，全部模式与调整层的 8-bit 量化 100% 通道不超过 1 LSB。
- 影响任务：3.1、3.2、4.1、5.1

## 记录 009：直接呈现以单 canvas 所有权和稳定双表面为边界

- 日期：2026-09-04
- 状态：已确定
- 背景：可见 canvas 只能转移一次 OffscreenCanvas 所有权；vGPU Surface 使用瞬态 swapchain，设备丢失后旧 Surface/Frame 不可继续提交，同时 2.2 的稳定 Canvas2D 帧必须在新后端首帧成功前持续可见。
- 最终决定：每个编辑会话只保留唯一 GPU Scene Worker/device/vGPU Context；固定 React canvas 节点并只在所有权边界执行一次 `transferControlToOffscreen()`。正常帧直接从现有线性预乘 `rgba16float` output 呈现到 vGPU Surface，选择顺序固定为 Surface → GPU ImageBitmap → CPU/Canvas2D/DOM。Surface 首帧通过 scene、camera、interaction、surface generation 与物理 DPR 尺寸门控后才原子接管；失败和 device lost 立即保留稳定帧并回退。每个稳定 GPU 帧之间最多自动恢复一次，恢复前销毁旧 registry/compositor/context/Surface，只同步最新权威 snapshot 与缺失纹理。
- 选择原因：保证正常交互路径每帧零 ImageBitmap、零 Canvas2D staging、零 GPU 回读，同时杜绝重复 transfer、旧帧覆盖、黑屏和连续设备失败的重试风暴。
- 影响任务：4.2、5.2
