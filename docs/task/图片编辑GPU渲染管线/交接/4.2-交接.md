# 4.2 实现 GPU 直接呈现与设备恢复交接

## 完成边界

- 复用唯一 GPU Scene Worker、`ImageEditWebGpuDeviceManager`、vGPU Context、3.1 RenderGraph、4.1 atlas/色彩/总预算，以及 2.2 稳定帧；没有新增业务图层模型、第二套 Worker/device/context 或导出职责。
- 可见预览 canvas 使用固定 React 节点，只转移一次 OffscreenCanvas 所有权。Worker 内用 vGPU `surface(gpu, canvas, { autoResize: false, size, alphaMode: 'premultiplied', colorSpace: 'srgb' })`，从现有 `rgba16float` output 直接 present。
- 降级顺序固定为 Surface → GPU ImageBitmap → CPU/Canvas2D/DOM。Surface 正常帧不创建或转移 ImageBitmap、不请求 Canvas2D context、不做 GPU readback；ImageBitmap 只在 Surface 初始化或提交失败后惰性创建。
- 直接首帧 ready 前稳定 Canvas2D/DOM 继续显示；通过 generation 与物理尺寸门控后才原子显示 GPU canvas。任何初始化失败、提交失败或 device lost 都先保留最后稳定帧，再进入后备。

## 状态机与门控

1. 主线程固定 canvas → 单次 `transferControlToOffscreen()` → 递增 `surfaceGeneration` 并携 transferable 发送给唯一 Worker。
2. Worker 复用现有 device/context/compositor，Surface 手动 resize；render 必须同时匹配 `sceneGeneration`、`cameraSequence`、`interactionSequence`、`surfaceGeneration`。
3. direct frame 只有在 `frame.done`、`gpu.settled` 与提交前后的当前性检查全部通过后才发布 `surface-frame-ready`；过期任务以 superseded 结束，不得错误进入 ImageBitmap fallback。
4. 主线程还核对 Surface generation、CSS→DPR 物理宽高；首帧成功后才把 GPU canvas 设为 visible。回退回调先恢复稳定 CPU 表面，再隐藏 GPU canvas。
5. 高频 camera/interaction 留在 session/ref/Worker 协议，不用 React state 驱动每帧。

## 设备丢失与恢复

- device lost 立即停止接受旧 frame，清空 registry（逐项 destroy GPU texture）、invalidate 并 dispose 旧 compositor/context/Surface，发布 `device-lost` 与精确的 `tiles-needed`。
- 恢复只读取当前 session 的最新 scene、layout、transient transform、Surface generation 和受保护资源键；只 acquire 一次新设备、sync 最新 snapshot 一次、reattach Surface 一次，并仅重传缺失纹理。
- `ImageEditorGpuSceneRecoveryV3` 在两个稳定 GPU 帧之间只允许一次自动恢复。新设备在首个有效帧前再次丢失时停在 CPU fallback，不进行第三次 acquire，避免重试风暴。
- vGPU wrapper dispose 只负责 Context/Surface/管线资源，原生设备所有权继续由既有 device manager 持有。

## 关键入口

- `imageEditorDirectPresentationSurfaceV3.ts`：固定 DOM canvas 的唯一 OffscreenCanvas 转移与 Surface generation。
- `imageEditorGpuDirectPresentationV3.ts`：Surface 直接 present、手动 resize、过期帧取消和惰性 ImageBitmap fallback。
- `imageEditorGpuSceneProtocolV3.ts` / `imageEditorGpuSceneFrameEventsV3.ts`：attach、direct-ready、四类序列与无 bitmap transfer 的帧交接。
- `imageEditorGpuSceneRuntimeV3.ts` / `imageEditorGpuSceneRecoveryV3.ts`：设备状态、资源销毁、最新 snapshot 单次恢复和风暴抑制。
- `imageEditorPresentationSurfaceV3.ts` / `imageEditorRenderSessionGpuBridgeV3.ts`：双表面原子切换、稳定帧回退与正式日志。
- `uiInspectionSceneCatalogGpuRaster.cjs`：8192 direct 计数、真实 device destroy 成功/失败和初始化失败 Reality 注入。

- 精确 Vitest：11 文件 58/58；其中 Runtime 8/8。正常 direct 单测确认 `transferToImageBitmap=0`、Canvas2D context=0、GPU readback Target=0；Surface 失败才生成 ImageBitmap。
- Runtime 恢复单测：旧 context dispose=1、旧 compositor dispose=1、旧 texture destroy=1；device acquire 总计=2、最新 scene sync=1、Surface reattach=1。第二次丢失发生在恢复首帧验证前时 acquire 仍为 2。
- `node --test scripts/lib/uiInspection.test.cjs`：20/20；本任务 ESLint、`tsc -p tsconfig.json --noEmit`、`tsc -p tsconfig.electron.json --noEmit`、`git diff --check` 均通过。
- `verify:changed` L2 精确阶段 11 文件 52/52；其 `vitest related` 对未配同名测试的任一 TS 源在当前 worktree/node_modules symlink 下均报 Rollup `PARSE_ERROR pos:7/37`。精确测试、ESLint、双 tsc、bundle 和 Reality 已独立覆盖，未把 related 误报记为通过。
- Electron Reality，1440×900 与 960×640：
  - 8192 Surface 初帧均为 `surface=1 / ImageBitmap=0 / readback=0`；交互后 1440 为 `surface=3 / bitmap=0 / readback=0 / atlas=84,542,720 B`，960 为 `surface=16 / bitmap=0 / readback=0 / atlas=50,725,632 B`。
  - complex graph 各完成 100/100 次拖动。1440：`p50=5.8 / p95=6.4 / p99=8.6 ms`；960：`p50=4.2 / p95=5.0 / p99=7.2 ms`。CPU task、upload、readback、PreviewOverride、revision 增量均为 0。

  - 初始化失败场景在新会话首次 `initialize` 请求中注入，发生于 `deviceManager.acquire()`、vGPU Context 和任何 Surface frame 之前。两档均实测 `initialize start=1 / failed=1 / completed=0 / acquire=0 / Surface frame=0 / hidden Surface ready=0`；CPU coverage>0，复制图层触发保存且平移继续。

## 限制与后续合并点

- 3.2 继续拥有画笔、标注和效果内容语义；合并时只让其 RenderGraph 输出流入现有 compositor，不得接管 canvas、另建 Worker/device/context 或恢复状态机。
- 5.2 可复用 direct/bitmap/CPU 选择、四类序列、首帧原子切换、资源清理和有界恢复作为总集成门禁。
- 5.1 导出仍从文档/CPU 导出链读取，不得从 Surface 或 atlas 回读。
- UI Inspection 仅通过 preload 暴露只读 `runtimeInfo.uiInspectionActive` 与 `uiInspectionGpuInitializationFailure` 布尔值；后者只在唯一初始化失败场景启动 Electron 时由进程环境设置，并直接进入首次 Worker initialize。隐藏 device-lost 诊断事件只在 inspection active 时监听；没有暴露任意命令、参数或测试秘密，正式界面没有内部状态。
- 主任务集成时更新 `00-任务总览.md` 的 4.2 状态与完成计数；本分支刻意不改总览，以降低与并行 3.2 冲突。
