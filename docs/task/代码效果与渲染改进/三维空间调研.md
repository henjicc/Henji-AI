# 三维空间统一方案：设计调研报告

调研日期：2026-10-29。只读调研，没有改代码。npm 版本与许可证是当天 `npm view` 的结果，three 源码核对的是 r186 的 `WebGPUBackend.js`。

---

## 0. 结论先行

1. **技术栈**：真三维内容统一用 three.js r186（`three/webgpu` 的 WebGPURenderer 加 TSL 后期）。它直接跑在剪辑渲染 Worker 里，共用合成器的 GPUDevice。作者库已经内置了 three 0.186.1，可以直接复用。界面不再依赖 R3F 和 drei。其余几个库按需引入：camera-controls 管视口导航，three-mesh-bvh 管拾取，glTF Transform 管模型导入优化。pmndrs postprocessing、Theatre.js、Babylon.js、Spark 都不采用，原因见第 1 节。
2. **统一方案的核心取舍，需要你拍板**：
   - 2.5D 卡片就是剪辑片段本身。片段加“三维图层”开关，加 z、X/Y 旋转；序列里加摄像机片段。卡片继续由现有合成器画。合成器里已经有角点贴合用的透视（单应）矩阵管线，运动模糊与镜头虚化也都已有，补上三维投影即可。
   - 真三维内容（几何体、角色、模型、灯光、环境）组成一份三维场景（SpaceScene），由 three 在同一个 GPUDevice 上渲染成一层，按深度插进卡片之间，用的是同一台摄像机。
   - 两者共用一套三维词汇：变换、摄像机镜头、灯光、环境、动画曲线，统一放在 `src/core/space/`。
   - 这和你说的“一份场景格式装下一切，卡片也是场景节点”不完全一样，差别与代价见 2.1。
3. **第一个原型**：在剪辑 Worker 里，用作者代码的 `createWebGPU(device)` 入口跑 three WebGPURenderer。它共用合成器 device，通过 `setXRRenderTargetTextures` 直接渲染进合成器给的目标纹理，做到零拷贝。对照组是现有的 WebGL 画布加 `copyExternalImageToTexture` 路线。比较 1080p 和 4K 下的单帧耗时 p50/p95/最大值、首次出现时的着色器卡顿（`compileAsync` 前后对比）、乱序重复渲染是否逐字节一致，以及颜色和预乘是否正确。这个原型不改宿主、不改格式，4–6 个工作日。
4. **阶段**：
   - P0 原型；
   - P1 剪辑里的 2.5D（片段三维化、摄像机、景深、运动模糊、“拉开景深层次”算法）；
   - P2 节目监视器里原地编辑三维；
   - P3 SpaceScene 渲染器与剪辑里的三维对象片段；
   - P4 镜头参考迁到同一引擎，去掉 R3F；
   - P5 按需：模型导入、HDR、高斯泼溅、阴影。
   - 总量粗估 14–20 周（单人等效，不含 P5）。

## 1. 成熟开源调研

### 1.1 本地现状（核对代码得出）

**剪辑渲染管线**
- 合成器是裸 WebGPU，跑在剪辑 Worker 里（`src/features/videoEdit/engine/videoEditGpuCompositor.ts`）。设备由 `ImageEditWebGpuDeviceManager` 申请，申请时只带 limits；诊断模式下另加 `timestamp-query`。
- 片段图层的顶点着色器已经支持角点贴合的透视矩阵（`videoEditGpuShaders.ts` 的 `warp0..2`，矩阵来自 `videoEditCornerPinMatrix`）。所以卡片要的透视投影，现成管线就能画。
- 运动模糊是快门内多次采样位姿再做曝光平均：片段侧在 `core/videoEdit/motionBlur.ts`，180° 快门，最多 16 个样本；作者图层侧在 `videoEditCodeMotion.ts`，单次 pass 最多 64 个样本。
- 作者图层已有 `blurShape:'lens'` 的镜头虚化（`VideoEditAuthorGpu.lens`）。
- 位姿目前都是二维：片段是 x/y/scale/rotation/anchor，作者图层是 6 元仿射矩阵。

**作者代码入口**
- 作者代码可以用 `createWebGPU(device)` 拿到合成器的同一个 device，并通过 `draw(target, …)` 写目标纹理（`videoEditAuthorModule.ts`）。
- WebGL 入口每帧要用 `copyExternalImageToTexture` 把整帧拷进来（`videoEditAuthorRuntime.ts` 第 216 行）。

**内置库**
- 作者库已内置 `three@0.186.1`，包含 `three/webgpu`、`three/tsl`，以及只收能离线、能在 Worker 里跑的 addons（`src/core/videoEdit/codeMaterial/authorLibraries.ts`）。
- 应用本身的 three 还是 0.169，配 R3F 8.18、drei 9、React 18。

**已有实测**（`docs/task/原生代码素材与智能剪辑/重要记录.md` 第 343 行与第 718 行）
- 共享宿主 GPUDevice 的 WebGPURenderer 在 Worker 里能跑。r178 下 30 帧热 p95 为 14.8 ms，WebGL 为 16.1 ms。
- 但当时是用 Canvas drawImage 消费三维画面，并不是零拷贝。
- three WebGL 的物体第一次出现时会同步编译着色器，把同在 GPU 进程里的 WebGPU 合成一起卡住，约 0.9 s。

**镜头参考**
- 由 `src/features/cameraStage`（195 个文件）实现：R3F 加 WebGL，`.hjstg` 文档 kindVersion 1。
- 对象有三类：primitive、character、camera。动画的唯一真相源是状态关键帧，播放时再编译成属性轨。
- 渲染方式有彩色、深度、线稿、法线、剪影五种。
- 出视频走隐藏窗口逐帧截图再编码。
- 用到的 drei 很少：Grid、Html、Line、OrbitControls、PerspectiveCamera、useGLTF。自写的 ShaderMaterial 只有两处（`stageStyleRenderer.ts`、`StageGround.tsx`）。

**和用户口味直接相关的取舍**
- **景深**：three 的 `dof()` 依据深度缓冲做，适合不透明网格。半透明卡片不写深度，会出光晕。所以卡片走逐层镜头虚化，网格层走 `dof()`。两边用同一个弥散圆公式，见 2.3。
- **运动模糊**：三维层用快门内子帧累积，和现有取样数规则一致：每约 4 像素一个样本，预览减半，导出用满。速度缓冲版的 `motionBlur` 节点只在预览吃紧时作为备选。
- **色调映射**：卡片（图文、视频、代码画面）不做色调映射，保持显示参考色，文字颜色不漂。网格默认用 Khronos PBR Neutral，它不像 AgX 那样压饱和，更适合中性黑白灰和扁平质感。AgX 留作照片级选项。
- **抗锯齿**：用 MSAA 4×，或 SMAA。不用 TAA，因为它依赖历史帧，跳帧取帧时结果不确定。

## 2. 统一方案

### 2.1 核心取舍：卡片是片段，三维对象是场景（需要你决定）

| | **方案 B（推荐）：片段三维化 + 三维对象场景** | 方案 A：一切都是 SpaceScene 节点，全部由 three 渲染 |
|---|---|---|
| 卡片的来源 | 就是剪辑片段：视频、图片、文字、图形、代码、嵌套序列 | 场景里的卡片节点，引用素材或片段 |
| 卡片能用的功能 | 片段已有的全部能力原样可用：效果、调色、遮罩、跟踪、关键帧、修剪、淡化、文字栅格档位 | 每张卡先由合成器渲染成独立纹理，再交给 three；效果链走两遍，每张卡多一份显存 |
| 渲染 | 合成器的透视层管线，几乎全是现成代码 | three 渲染全部 |
| 景深 | 正对镜头的卡片逐层虚化是精确的，和 AE Classic 3D 一致 | 深度缓冲景深，透明卡片边缘会出光晕 |
| 穿插与光影 | 卡片之间不穿插；三维对象层按深度插在卡片之间（Element 3D 式） | 支持穿插，卡片可以受光、投影 |
| 工作量与风险 | 小。P1 就能交付你要的观感 | 大。等于把剪辑合成重做一遍 |

**推荐 B 的理由**：你的口味是扁平、分层、有景深、有错位，卡片之间不需要穿插，AE 的 Classic 3D 就是这种做法。留一个口子：以后有需要时，单张卡片可以“参与三维光照/穿插”，通过 ExternalTexture 把同一张纹理放进 three 层渲染。只在需要时启用，不必一开始就承担方案 A 的成本。

“一份格式”在 B 里的落点：
- 一套三维词汇：`Transform3D`、`SpaceCamera`（焦距、画幅、光圈、对焦距离或对焦目标、快门角与相位）、`SpaceLight`、`SpaceEnvironment`、动画曲线。动画曲线**直接用剪辑的关键帧 schema**，贝塞尔与缓动都已有。
- 这套词汇由两处使用：剪辑序列（片段卡片与摄像机片段），以及 SpaceScene（`.hjstg` 内容；剪辑内嵌的场景用同一个 schema）。
- 渲染器只有一个实现，跑在一个地方：剪辑渲染 Worker。

### 2.2 数据模型

**`src/core/space/`**：纯数据、zod schema，主进程与渲染层共用。
- `Transform3D`：位置、旋转（角度）、缩放、锚点。
- `SpaceCamera`：
  - 焦距 mm，画幅宽 mm 默认 36。
  - `fStop`。
  - `focus`：`{distance}` 或 `{target: 引用}`。
  - `shutter: {angle, phase}`，缺省跟随序列开关。
  - 2.5D 默认用 80mm 左右的长焦，因为长焦加大的 z 间距才有温和的错位、不畸变，具体值和你一起试定。
- `SpaceLight`、`SpaceEnvironment`：默认中性灰背景，用 RoomEnvironment 式的中性棚光。

**剪辑侧**（`.hjvid` 升版本）：
- 片段：
  - 新增 `threeD?: true`；
  - 动画键新增 `z`、`rotationX`、`rotationY`，旧的 `rotation` 就是绕 Z 轴旋转；
  - 新增 `anchorZ`。
  - 采用 AE 的约定：z=0 平面在默认摄像机下与画面一一对应。所以打开三维开关、z 还是 0 时画面不变，和 AE 一样“开了三维开关画面不跳”。
- 新片段类型 `camera`：放在轨道上，有入出点，镜头参数可以加关键帧。最上层有效的摄像机生效，与 AE 相同。
- 新素材类型 `space`：引用 `document.spaces[]` 里的内嵌 SpaceScene。内嵌的内容自带 `contentVersion`，复用 `.hjstg` 的迁移链。片段可选“使用序列摄像机”（缺省）或“使用场景自带摄像机”。
- 序列级：沿用现有运动模糊总开关，新增景深总开关。

**SpaceScene**（`.hjstg` 内容；剪辑内嵌用同一 schema）：
- 节点：`primitive`、`character`、`model`、`imagePlane`（布景里的参考照片面片）、`light`、`camera`、`group`。
- `group` 可以标记“单独成层”，这样卡片可以插在两组网格之间。
- 动画：
  - 第一步保留状态关键帧作为真相源。
  - P4 改为属性轨作为真相源；状态关键帧降级为“状态卡”编辑视图，由同一份编译器写入属性轨；运镜预设参数作为曲线段的生成信息保存，可以再次编辑。
- **部件不能整块出现**：
  - `visible` 的切换一律编译成不透明度渐变，缺省 8–12 帧，具体时长和你确认；
  - 只有显式选“硬切”才不渐变；
  - 剪辑的运动复核（`query_video_edit_review`）加“突然出现”检查。
  - 网格半透明时先做一遍深度预渲染再混合，避免自身重叠处发灰。

**作者代码（读写）**：
- **读**：作者接口升到 v7。
  - 新参数类型 `space` 和 `info.space`，提供当前摄像机矩阵、节点求值结果，以及 `project(ref)` 把三维点投到画面。用途举例：标签跟着三维点走。
  - `AuthorPose` 新增 `z`、`rotationX`、`rotationY`。代码片段被三维化时，它的图层按序列摄像机投影，相当于 AE 的“折叠变换”。这一项放到 P2。
- **用同一渲染器画**：新增自家冻结库 `henji-space@1.0.0`（参照 henji-layout 的做法）。作者在 `createWebGPU` 里调用 `createSpaceRenderer(device)` 渲染某个 SpaceScene，并可以叠加自己的 three 对象。three 只有一份实例。
- **写**：运行时代码只读不写，因为要保持确定性。写入一律走应用能力，也就是助手或界面，见 2.5。

### 2.3 渲染

**卡片（合成器）**
- 每帧对三维片段做三步：
  1. 求出模型矩阵 × 摄像机视图投影，得到 3×3 单应矩阵，写进现有的 `warp` 通道；
  2. 按视深从远到近排序，深度相同时按轨道顺序；
  3. 相机平面后方的部分交给硬件在齐次空间裁掉。顶点输出用 z=0、w>0，原型要核对 w<0 时是否正确裁剪。
- **景深**：按摄像机参数算弥散圆，正对镜头的卡片 CoC 为常数，复用现有的 lens 虚化。倾斜卡片先取中心 CoC，以后再做逐像素 CoC，从预滤波金字塔取样。
- **运动模糊**：把现有片段的快门采样扩展到三维键，加上摄像机自身的运动。摄像机一动，所有三维卡片都应该模糊。曝光平均的着色器已经能处理多个矩阵样本。
- **文字清晰**：栅格按投影后的屏幕尺寸选 2^k 档，规则同 `authorRasterScale`；停稳不抖，延续现有的复核规则。

**三维对象（three，同一个 device）**
- 每个 `space` 片段（或每个“单独成层”的组）在 Worker 里有一个 `SpaceRenderer` 实例，管理方式参照 `authorRuntimes` 表。
- 一个无框架的同步器按节点 id 把 SpaceScene 增量同步成 three 对象，只做增、改、删。
- 输出：
  - 首选：经 `setXRRenderTargetTextures` 直接渲染进合成器给的层纹理；
  - 备选：RT 加 GPU 内拷贝。
- 景深用 `dof()`，参数与卡片的 CoC 由同一摄像机换算。
- 运动模糊：子帧累积，样本数规则与卡片相同，预览封顶。
- 预热：进入片段前对未来要出现的物体先 `compileAsync`，接在现有 `warmAuthor` 预热后面。这对应已经记录的“物体首次出现卡 0.9 s”。
- 颜色：
  - 内部用 HalfFloat；
  - 输出 pass 转成合成器的工作空间，即预乘、Rec.709 gamma 2.4 显示参考。
  - three 默认按 sRGB 编码，差别要在原型里核对。
- 显存：三维层的 RT 与 MSAA 缓冲计入 `videoEditGpuBudget`。
- 设备：合成器申请 device 时，按适配器实际支持情况追加 three 用得到的可选特性：`float32-filterable`、`rg11b10ufloat-renderable`、`shader-f16`、`texture-compression-bc`/`astc`。现有 `optionalFeatures` 参数已经支持这样做。

**确定性约定**
- 时间只来自帧时间，禁用 TSL 内置的挂钟 `time` 节点，改用宿主 uniform。
- 随机数沿用现有的播种包装。
- 不用 TAA，不用跨帧累积。
- 模型动画用 `mixer.setTime`。
- 交付前做乱序重复取帧的逐字节检查。

### 2.4 编辑界面

**剪辑里原地编辑（主路线）**
- 序列里有三维片段时，节目监视器多一个“三维视图”切换：当前摄像机视图，或自定义 / 顶 / 侧视图，对标 AE 的 Active Camera 与 Custom View。
- 自定义视图就是用另一台临时摄像机渲染同一个合成，看到的和导出的一致。
- 操纵手柄画在主线程的二维覆盖层上，沿用 `CodeElementEditOverlay` 的做法：Worker 回传摄像机矩阵，覆盖层负责投影坐标轴与旋转环。不需要在主线程再放一份 three。
- 拾取：卡片用解析几何直接算；三维对象交给 Worker 用 three-mesh-bvh 做射线查询。
- 自定义视图导航用 camera-controls 的阻尼，手感有分量。
- 摄像机路径画在覆盖层上，可以拖动控制点。
- 关键帧就在剪辑时间线和曲线编辑器里编辑。
- 打开内嵌的 `space` 片段时，在原地进入它的场景，像 AE 进入预合成，面包屑可以返回。

**独立的“三维空间”工作区**（由镜头参考演进）
- 用户可见名称从“镜头参考”改为“三维空间”。扩展名 `.hjstg` 不变，所以不涉及改后缀。
- P4 起，视口用同一个引擎渲染：宿主在后台建一个只含这个 space 片段的单片段序列，交给剪辑渲染 Worker 画。
- 出图、出视频、出控制图（深度、法线、线稿、剪影改用 TSL 的 MRT 实现）直接走剪辑的导出编码，不再用隐藏窗口逐帧截图。
- 这样“镜头参考出视频”和“剪辑导出”是同一条路，速度和确定性都更好。
- 角色姿势、状态卡、运镜预设等面板保留。

### 2.5 迁移（持久格式向后兼容）

**`.hjstg`**
- **v2**（P3，新增对象类型与镜头字段）：
  - 对象 `type` 枚举新增几种，旧程序会拒绝，所以 `kindMinReaderVersion` 提到 2；
  - 1→2 的迁移是纯函数：对象原样保留，摄像机按视野角 `fov` 换算出等效焦距，缺省 `fStop` 等于“不虚化”；
  - 加黄金样本 v2，v1 样本升级后要求取景不变。
- **v3**（P4，属性轨成为真相源）：
  - 2→3 用现有 `compileStateKeyframesToAnimation` 编译出属性轨；
  - 状态关键帧的名称、过渡预设、错峰、空间路径、运镜参数作为曲线段元数据保留，保证可以再编辑；
  - 验收：所有 v1、v2 样本逐帧采样，与迁移前的位姿误差在浮点精度以内。

**`.hjvid`**：新增 `spaces[]`、片段三维键、`camera` 与 `space` 两种类型。新类型属于联合分支变更，所以要提高 `minReaderVersion`。补黄金样本，并通过 `check:persistence-compat`。

**作者接口**：`code-author-api` 升到 7。宿主按版本保持旧代码原有行为。

已有的镜头参考渲染结果（画布节点、`camera_stage.render_task` 引用）不受影响。

### 2.6 助手能力（通用实体为主，算法能力只留少数）

**通用读改增删**，只需注册实体与属性：
- `video_edit.clip`：新增 `three_d`、`z`、`rotation_x`、`rotation_y`、`anchor_z`，以及对应的动画键。
- `video_edit.camera`（摄像机片段）：`focal_length`、`f_stop`、`focus_distance`、`focus_target`（引用；写入它就等于“对焦到某个片段”，不需要专门能力）、`shutter_angle`。
- `space.scene`、`space.node`、`space.camera`、`space.light`：
  - 引用里带容器，即 `.hjstg` 文档或剪辑的内嵌场景，同一份实体定义服务两种宿主；
  - 现有 `camera_stage.*` 在 P4 改名为 `space.*`，同步更新技能文档与测试。
- 意图语义的派生属性：
  - `frame_rect`：在当前摄像机画面中所占的矩形，按画面比例，可写；
  - `depth_from_focus`。
  - 助手不必用米或像素思考。

**专用算法能力**，只保留无法用属性写入表达的：
1. `arrange_video_edit_depth`：拉开景深层次。给选中的片段分配深度，同时按比例反向缩放，让当前画面构图完全不变；只有摄像机运动时才出现错位。这是最贴合你口味、也最适合让 AI 先做的一步。
2. `apply_space_camera_move`：由现有 `apply_camera_stage_camera_move` 泛化，作用对象是摄像机片段或场景摄像机。预设有环绕、推拉、横移、升降。缺省缓动“有分量、平移中段不急”。
3. `place_space_object`：沿用现有的布置与碰撞算法。
4. `render_space_output`：沿用现有渲染任务，内部改走导出管线；可以出图、出视频、出控制图。
5. 观察与核对：沿用 `observe_camera_stage_scene`、`verify_camera_stage_scene`，剪辑侧用 `observe_video_edit_frame` 逐帧读回。

## 3. 第一个原型：验证最大风险

**风险排序**：
1. three 和合成器共用 device 时的性能、着色器卡顿、颜色与预乘、错误处理；
2. 卡片透视、景深、运动模糊的观感和耗时；
3. 跳帧取帧的确定性。

**原型 1（P0 主体，4–6 个工作日，不改宿主与格式）**

做法是写一个作者代码效果，`import { WebGPURenderer } from 'three/webgpu'`，`createWebGPU(device)` 拿到合成器的 device。

场景：
- `resources/camera-stage/UAL1_Standard.glb` 角色，播放一段动作，用 `mixer.setTime` 驱动；
- 6 个几何体；
- 中性环境；
- Neutral 色调映射；
- `dof()`；
- MSAA 4×。

对比 4 条路线：
- a. 现有的 WebGL OffscreenCanvas 加 `copyExternalImageToTexture`；
- b. 共享 device，渲染到 RT，再 GPU 内 `copyTextureToTexture` 到 target；
- c. 共享 device，用 `setXRRenderTargetTextures` 直接渲染进 target；
- d. 在 c 的基础上做 8 个子帧的运动模糊累积。

测量：
- 分辨率 1080p 与 4K，每组 120 帧；
- 记录 CPU 提交耗时与 GPU 时间戳（诊断会话已经会申请 `timestamp-query`）的 p50 / p95 / 最大值；
- 物体首次出现时，开不开 `compileAsync` 预热，各卡多久；
- 乱序跳到第 37 帧渲染两次，结果是否逐字节一致；
- 与 Frameflow 或 AE 渲染的同一画面，用人眼对比颜色和预乘边缘。

达标判据：
- c 不慢于 b，b 不慢于 a；
- 4K 下 c 的 p95 在 8 ms 以内，给解码与合成留出 60fps 的余量；
- 预热后首次出现不超过 1 帧；
- 重复取帧逐字节一致；
- 颜色人眼看不出差别；
- 合成器的 error scope 与设备丢失恢复不受影响。

没过怎么办：
- c 不可用：用 b，代价只是一次 GPU 内拷贝。
- 颜色有偏差：在输出 pass 里自己写编码，不用 three 的输出变换。

**原型 2（2–3 天，紧接着做）**

- 在工作树里把片段的透视层接上摄像机投影。
- 场景：30 张文字与图片卡片分布在不同深度，摄像机做推拉加横移；逐卡做镜头虚化，16 个样本的运动模糊。
- 用 Frameflow 让 AE 的 Classic 3D 渲染同一构图作为对照。
- 达标：人眼与 AE 一致，对焦处文字停稳不抖，4K p95 在 10 ms 以内。

合计 P0–P4 约 14–20 周（单人等效），依据是对照现有代码量和已有实测的粗估，原型结果出来后再修正。

**直接复用开源**：
- three r186：渲染器、TSL 后期、glTF、蒙皮动画、RoomEnvironment、ExternalTexture、高斯泼溅；
- camera-controls；
- three-mesh-bvh；
- glTF Transform。

**必须自己写**，原因都是这些部分没有现成方案、又和本项目自身的结构绑定：
- 片段卡片的透视投影：只是扩展现有的角点贴合管线，引入第三方反而更重；
- 逐卡 CoC 与摄像机运动采样：要和现有快门规则、文字栅格档位保持一致；
- 场景同步器：Worker 里没有 React，只做 id 级增删改，很小；
- 持久格式与迁移：硬要求，开源库替代不了；
- 应用能力与 `arrange_video_edit_depth` 这类算法：属于产品的 AI 原生层；
- 二维覆盖层手柄：沿用现有覆盖层，避免主线程再装一份 three。
