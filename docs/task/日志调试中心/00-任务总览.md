# 日志调试中心 - 任务总览

## 任务目标

当前项目已有结构化日志内核（`src/core/logging`）和一个埋在测试模式面板里的日志查看器（`UnifiedLogViewer`），但存在三个核心问题：LLM 成功响应内容完全没有被记录；主进程日志绕道前端再落盘，链路脆弱且不符合前后端职责分离；查看器不是正式页面，历史日志无法回看。随着功能增多，控制台日志混乱、覆盖度靠自觉，调试体验差。

本任务的最终结果：主进程成为日志中枢（采集、落盘、查询都在后端）；大语言模型与生成模型的真实请求/响应完整可查（含捕获开关）；有一个与主界面风格一致的**独立日志窗口**（开发/测试模式经按钮或快捷键打开，可与主窗口同时使用，打包给最终用户不可见），支持按类型/级别/请求链路过滤、JSON 折叠、错误一键复制；AI 编程工具无需人工复制粘贴即可通过固定路径的 JSONL 文件和查询脚本读取日志；新功能接入日志有明确规范，不需要逐个适配。

**属于本任务**：日志数据层重构（主进程中枢、LLM 响应捕获、捕获开关）、独立日志窗口、历史回读、AI 访问约定与查询脚本、日志接入规范。
**不属于本任务**：MCP server 形式的日志接口（见重要记录 003）、日志上报/远程收集、对既有各业务模块逐一补日志埋点（规范建立后随日常开发逐步覆盖）、旧 Tauri 日志兼容。

## 重要说明

- 日志链路横跨五层：渲染层 `src/core/logging` → `src/commands/logging.ts` → `src/platform` → `electron/preload/index.ts` → `electron/main/ipc/logging.ts` + `electron/main/services/logging.ts`。凡是改日志事件结构或新增 IPC 的任务，五层必须同一任务内一次改齐。
- API key 等敏感字段在任何捕获模式下都必须保持打码（`isSensitiveKey` 逻辑，1.2 起统一收在 `electron/main/services/logging/sanitize.ts`），"完整捕获"只放开截断，不放开脱敏。这是不可协商的约束。
- 涉及 Electron 主进程的改动需要重启 `npm run electron:dev`；仅渲染层改动热更新即可。每次改完按项目约定明确告知用户。
- 日志页面的 UI 交互（点击过滤、复制按钮等）验证交给用户手动测试，任务文件写清操作步骤和验证点。
- 每个任务完成后按项目回归检查约定执行快速检查（`npm run lint`、`npx tsc -p tsconfig.electron.json --noEmit` 等），`electron:build` 仅在必要时执行。
