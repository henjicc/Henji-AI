# 3.2 日志接入规范与覆盖治理

## 任务状态

- 状态：已完成（自动化检查通过；主进程日志可见性待用户重启后人工验证）
- 所属阶段：第三阶段-AI友好与治理
- 前置任务：1.1（主进程 logger 存在后规范才完整）
- 关联任务：2.1（事件美化字典的兜底策略）
- 是否可以并行：可与第二阶段全部任务并行

## 任务目标

回答用户"以后开发新东西日志要不要再适配"的问题：建立成文的 domain/event 命名约定与接入方式，使新功能只要按规范调 `createLogger`（前端）或 `createMainLogger`（主进程）即自动进入落盘、页面、查询脚本整个体系，不需要任何逐案适配；并对现有明显缺日志的关键链路做一次盘点补漏（盘点为主，大规模补埋点不在本任务范围）。

## 当前情况

- domain 是自由字符串，现状风格不一：`core.services.GenerationService`、`commands.llmRuntime`、`workspaces.GenerationWorkspace`、`ai_runtime` 等混用路径式与模块式命名，无书面约定。
- event 命名事实上遵循 `模块.动作.阶段`（如 `generation.generate.start` / `llm_runtime.chat_stream.request_json`），但同样无文档。
- 页面事件美化依赖手工字典（2.1 后位于 `src/features/logs/eventDisplay.ts`），未登记的事件靠 `getDomainHint` 兜底——兜底已存在，所以"新事件必须登记字典"不应成为硬要求，只是可选美化。
- 哪些模块完全没有日志覆盖，目前没有盘点过（待执行时确认）。

## 实施方案

1. 成文规范（写入 CLAUDE.md"日志系统"小节，与 3.1 的内容合并组织）：
   - domain 命名：按代码分层前缀（如 `commands.*`、`core.services.*`、`features.canvas.*`、主进程 `main.ai_runtime`、`main.llm` 等），执行时结合现状定稿并列出对照表。
   - event 命名：`模块.动作.阶段`，阶段枚举建议 `start / progress / completed / failed / request_json / response_json`。
   - 级别使用约定：error（用户可感知的失败）/ warn（可自愈异常）/ info（关键业务节点）/ debug（排查细节）/ trace（高频细节）。
   - 接入方式：前端 `createLogger(domain)`、主进程 `createMainLogger(domain)`，一段最小示例。
   - 明确"美化字典是可选项"：未登记事件在页面按兜底样式正常显示，不阻塞。
2. 覆盖盘点：扫一遍主要链路（生成、LLM、上传、画布持久化、项目包、更新器、数据库），列出"无任何日志"的模块清单，写入本任务执行记录；对其中排查价值最高的 1-2 处顺手补上关键节点日志（超出的记为后续日常开发事项，不扩大本任务）。
3. 存量 domain 是否统一重命名：**不做**批量重命名（会破坏历史日志可查性），只规范增量；现状对照表中标注"存量保持"。

## 执行步骤

1. 梳理现有全部 `createLogger(` 调用点，汇总现存 domain 清单（`grep createLogger` 即可）。
2. 结合清单定稿命名约定与对照表，写入 CLAUDE.md（与 3.1 小节合并，总篇幅控制住，细则可放本计划目录内的附录文件）。
3. 盘点主要链路日志覆盖情况，产出缺失清单（记入执行记录）。
4. 为清单中最有排查价值的 1-2 处补关键日志（如确认为空缺）。
5. 回归检查：`npm run lint`；若动了主进程则加 `npx tsc -p tsconfig.electron.json --noEmit`。
