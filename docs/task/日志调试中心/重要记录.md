# 日志调试中心 - 重要记录

## 记录 001：日志页面入口形式

- 日期：2026-07-10
- 状态：已确定
- 背景：日志页面需要一个入口，候选有三：浏览器链接、第四个 Tab、独立 Electron 窗口。浏览器链接被否：浏览器页面拿不到 preload 桥（`window.henjiNative`），实时日志与历史查询都走 IPC，支持浏览器访问需主进程常驻本地 HTTP 服务并另做一套 HTTP/SSE 数据通道，与记录 003"文件即接口、不起服务"方向冲突，成本不成比例。Tab 的问题：无法"一边操作软件一边看日志"。
- 最终决定：做**独立 Electron 窗口**（单例 `BrowserWindow`，加载同一渲染层产物、经 URL 参数切换为日志壳，preload 桥直接可用）。启动方式：测试模式/开发者模式下的按钮入口 + 快捷键（建议 `Ctrl+Shift+L`，仅开发/测试模式注册）。打包给最终用户时无按钮、不注册快捷键，窗口不可达。不做浏览器链接、不加 Tab。
- 选择原因：独立窗口满足"同时用软件、同时看日志"的核心场景（可拖到第二块屏），且复用 PAL 桥零新增数据通道；成本仅比 Tab 略高（用户拍板）。
- 影响任务：2.1、2.2、2.3

## 记录 002：完整捕获模式下多模态数据的处理

- 日期：2026-07-10
- 状态：已确定
- 背景："完整捕获"模式放开长文本截断后，请求体中的图片/音频 base64、data URI 若也记原文，单条日志可能很大，会拖慢写入、膨胀文件并卡住页面渲染。
- 最终决定：完整捕获模式下**图片**（`data:image/*` 前缀可识别的）base64 原文保留；**音频/视频**以及无法识别类型的超长裸 base64 仍按现有"头尾摘要 + 长度标注"处理。标准模式一切维持现有截断策略。整体膨胀风险由记录 005 的保留时长 + 总大小上限兜底。
- 选择原因：图片是排查生成请求最常需要还原的载荷，体积可接受；音频/视频体积过大且排查时很少需要原文（用户拍板）。
- 影响任务：1.3

## 记录 003：AI 访问方式采用"文件即接口"，不做 MCP server

- 日期：2026-07-10
- 状态：已确定
- 背景：用户希望 AI 编程工具能自助读取日志，提出 MCP 或某种脚本接口的设想。日志已是固定路径的结构化 JSONL 文件，AI 工具自带文件读取能力，MCP/HTTP 服务对单机桌面应用属于过度设计且引入常驻进程负担。
- 最终决定：JSONL 文件 + `scripts/query-logs.cjs` 查询脚本 + CLAUDE.md 路径/用法约定，即为 AI 访问接口；不做 MCP server。若后续确有跨机器/多工具共享需求，另立计划。
- 选择原因：零额外运行时成本、零新依赖，AI 与人共用同一套查询方式，最稳。
- 影响任务：3.1、任务范围界定

## 记录 004：测试模式面板内嵌日志查看器的去留

- 日期：2026-07-10
- 状态：已确定
- 背景：`UnifiedLogViewer` 目前嵌在 `TestModePanel.tsx` 与 `TestModeParamsDisplay.tsx` 中。日志窗口上线后，同一功能存在两份入口违反"禁止同功能多份实现"约束。
- 最终决定：日志窗口上线时（2.1）直接删除旧查看器组件及其在测试面板中的挂载，测试面板中与旧查看器相关的选项/控件一并清理，不保留轻量视图；日志查看入口统一为日志窗口（测试面板处保留一个"打开日志窗口"按钮）（用户拍板）。
- 选择原因：没有必要维护两份入口；测试模式面板回归"测试参数"职责。
- 影响任务：2.1

## 记录 005：日志保留策略（时长 + 总大小双上限）

- 日期：2026-07-10
- 状态：已确定
- 背景：日志文件当前无限累积；完整捕获模式（含图片 base64 原文，见记录 002）下文件可能较大，需要自动清理策略。用户明确不希望日志整体庞大。
- 最终决定：双上限清理，常量集中定义：① 保留 1 天——启动时删除早于 1 天的日志文件；② 日志目录总大小上限（默认 256MB）——超限时从最旧文件删起，当天文件超限则截断保护由 1.3 的单条保险丝兜底。
- 选择原因：用户拍板"按 1 天"；仅时间上限不够，完整捕获 + 图片原文可能单日就把体积撑大，所以叠加总大小上限。
- 影响任务：1.1、2.3（历史回读实际只覆盖最近 1 天，价值收敛为"重启/刷新后找回当天日志"）
