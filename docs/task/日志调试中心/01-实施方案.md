# 日志调试中心 - 实施方案

## 现状盘点（2026-07-10 勘察结论）

### 已有能力

- **前端结构化日志内核** `src/core/logging/`（types / config / store / bridge / logger / sanitize / index）：
  - 每条日志是结构化 `LogEvent`：`level`（trace/debug/info/warn/error）、`domain`（自由字符串，如 `core.services.GenerationService`）、`event`（如 `generation.generate.start`）、`requestId`、`taskId`、`modelId`、`providerId`、`context`、`error`、`source`（frontend/backend）。
  - 内存环形缓冲 400 条（`store.ts`），支持 `subscribeLogEvents` 订阅。
  - `bridge.ts` 每 450ms / 60 条批量把前端日志经 `src/commands/logging.ts` → preload `logFrontendEvents` → IPC `logging:frontendEvents` 送到主进程。
  - 配置 `config.ts`：DEV 默认 debug 级别，`persistToFile` 默认 true，测试模式（localStorage `henji_test_mode`）下生产也开 debug。
- **主进程落盘** `electron/main/services/logging.ts`：按天写 JSONL 到 `%LOCALAPPDATA%\com.henji.ai\Henji-AI\logs\frontend-YYYY-MM-DD.log`，每行一个 JSON 对象（LogEvent + `source: 'frontend'`）。
- **日志查看器** `src/components/debug/UnifiedLogViewer.tsx`：已实现级别过滤、关键词搜索、事件美化（`EVENT_DISPLAY_MAP` 手工字典 + 兜底）、清空。仅挂载在 `src/components/TestModePanel.tsx` 和 `src/components/TestModeParamsDisplay.tsx` 里，不是独立页面。
- **AI 生成链路 trace** `electron/main/services/ai-runtime/trace.ts`：捕获生成请求体/响应体，含脱敏（api_key/token/secret 等 key 打码为 `***`）与截断（长字符串 1200+240 字符、base64 摘要、data URI 摘要、深度限制 12）。
- **请求预览事件**：主进程通过 `webContents.send` 推送两类预览到渲染层，渲染层在 `logger.ts` 的 `initLoggerConfig()` 中监听并转成日志事件：
  - `henji://llm-runtime-request-preview`（`electron/main/services/llm/runtime.ts` 约 36 行）→ `llm_runtime.chat_stream.request_json`
  - 生成链路预览 → `generation.runtime.request_json`

### 核心问题

1. **LLM 成功响应内容不落任何日志**。`electron/main/services/llm/streaming.ts` 的 `streamOpenAiCompatibleChat` 返回聚合结果 `LlmStreamOutput{ output, reasoningOutput }`（`runtime.ts` 约 45-51 行拿到），但只用于统计字符数；只有失败时前端 `src/commands/llmRuntime.ts` 才记日志。
2. **主进程日志绕道前端**：主进程发生的事（请求预览等）先推给渲染层，由渲染层 logger 记录后再桥接回主进程落盘。前端崩溃或未就绪时日志链断裂；主进程自身没有直接写日志的能力（全目录无 console.log，也无自有 logger）。
3. **无历史回读**：内存缓冲仅 400 条、刷新即丢；查看器不能读文件里的历史日志；日志文件无轮转清理。
4. **"真实原始"与截断策略冲突**：`trace.ts` 固定截断，无法按需查看完整请求/响应体。
5. **覆盖度靠自觉**：domain/event 命名无书面约定，`EVENT_DISPLAY_MAP` 手工维护，新功能接入日志无 SOP。

## 最终目标

1. 主进程是日志中枢：前端桥接事件、主进程自身事件、AI 生成 trace、LLM 请求/响应统一进主进程日志服务，直接写 JSONL 文件（按天分文件 + 自动清理），并实时推送给渲染层日志页面。
2. LLM 与生成模型的真实请求/响应完整可查，"完整捕获"开关控制是否截断（脱敏永远保留）。
3. 独立日志窗口：单例 `BrowserWindow`，与主窗口同时使用（一边操作软件一边看日志），与主界面同风格（复用 `Ui*` primitives），支持来源/domain/级别/关键词过滤、requestId 链路聚合视图、JSON 折叠、错误一键复制（Markdown/JSON）、历史日志回读、暂停/恢复捕获。入口仅开发/测试模式可见，打包给最终用户不可达。
4. AI 编程工具通过固定路径 JSONL 文件 + 查询脚本自助读日志，路径与用法写入 CLAUDE.md。
5. 日志接入规范成文：新功能只要 `createLogger(domain)` + 遵守命名约定即自动进入整个体系。

## 总体思路

**先修数据层，再做窗口，最后治理。** 窗口做得再好，想看的数据不存在也没用，所以第一阶段全部投入主进程数据层；第二阶段把 `UnifiedLogViewer` 升级迁移为独立日志窗口（升级而非重写，其过滤/美化逻辑可复用，旧组件随后删除）；第三阶段沉淀 AI 访问方式和规范。

### 关键技术决策

- **主进程日志服务扩展而非重建**：在 `electron/main/services/logging.ts` 基础上扩展（或拆分为 `logging/` 目录），新增主进程侧 `createMainLogger(domain)`、统一 `appendLogEvents(source, events)` 入口、按天轮转与保留清理、实时推送（`webContents.send('henji://log-event', ...)`）。文件命名从 `frontend-YYYY-MM-DD.log` 过渡为统一 `henji-YYYY-MM-DD.log`（每行含 `source` 字段区分来源）。
- **LLM 响应捕获点**：`electron/main/services/llm/runtime.ts` 中 `streamOpenAiCompatibleChat` 返回后（约 45-51 行），把聚合后的 `output` / `reasoningOutput` / 耗时 / 字符数作为 `llm_runtime.chat_stream.response_json` 事件直接写入主进程日志（不再绕前端）。请求侧 `request_json` 同样改为主进程直接记录（渲染层预览推送保留给测试模式面板即时显示，或由日志实时推送替代——由 1.2 执行时确认）。
- **捕获开关是运行时配置而非仅前端状态**：开关状态存在 `settingsStore`（渲染层 UI），经 IPC 同步到主进程内存配置，影响 `trace.ts` 与 LLM 捕获的截断行为。默认"标准模式"（现有截断策略），打开"完整捕获"后长字符串不截断且图片 `data:image/*` 保留原文；音频/视频与无法识别类型的裸 base64 任何模式下都保持摘要（重要记录 002）。
- **日志页面 = 独立 Electron 窗口**（重要记录 001）：主进程单例管理第二个 `BrowserWindow`，加载与主窗口相同的渲染产物 + `?view=logs` 参数，渲染层入口按参数分流渲染日志壳；preload 桥直接可用，不需要 HTTP 服务或第二套数据通道。入口为测试模式面板按钮 + 快捷键 `Ctrl+Shift+L`，两者仅在开发模式或测试模式下可用。UI 实现落在 `src/features/logs/`（对齐 features 目录惯例）。主进程日志推送需广播到所有窗口。
- **AI 访问 = 文件即接口**：不做 MCP/HTTP 服务。JSONL 文件路径固定、结构化、含 requestId 可关联，AI 工具用自身文件读取能力即可消费；补一个 `scripts/query-logs.cjs`（对齐 scripts 目录 .cjs 惯例）支持按日期/requestId/domain/level 过滤，人和 AI 共用。

## 阶段划分与关系

- **第一阶段-日志数据层**：1.1 主进程中枢（地基，其余全部依赖）→ 1.2 LLM 捕获（用 1.1 的主进程 logger）→ 1.3 捕获开关（控制 1.2 和 trace.ts 的截断行为）。
- **第二阶段-日志窗口**：2.1 窗口骨架 + 查看器迁移升级（依赖 1.1 的实时推送通道；含旧查看器删除）→ 2.2 链路视图与错误复制 → 2.3 历史回读（依赖 1.1 的文件查询 IPC）。2.2 与 2.3 可并行。
- **第三阶段-AI友好与治理**：3.1 查询脚本 + CLAUDE.md 约定（依赖 1.1 文件 schema 稳定，可与第二阶段并行）；3.2 接入规范成文（可与第二阶段并行）。

## 兼容要求

- 现有 `createLogger(domain)` 前端调用方（全仓多处）**签名不变**，业务代码零改动。
- `LogEvent` 结构只增不改：新增字段可选，已有字段语义不变，保证旧日志文件仍可被查询脚本解析。
- 测试模式面板（`TestModePanel`）在 2.1 完成前保持现状可用；2.1 时删除其内嵌查看器与相关选项，换为"打开日志窗口"按钮（重要记录 004），面板其余测试功能不受影响。
- `logging:frontendEvents` IPC 通道保留（前端桥接仍走它），主进程内部改为汇入统一日志服务。

## 风险控制

- **日志自身不能拖垮应用**：落盘全部异步批量；实时推送渲染层要限流（如按批推送）；完整捕获模式下单条事件体积可能很大（含图片 base64 原文），写入前做单条上限保护（超限强制截断并标注）；整体体积由"保留 1 天 + 目录总大小上限"双重兜底（重要记录 005）。
- **敏感信息**：脱敏逻辑（`isSensitiveKey`）在任何模式下生效；日志文件在用户本机 LOCALAPPDATA，不随项目包导出。
- **回退原则**：每个任务独立提交；数据层任务若出问题，回退单个提交即可恢复原有日志链路（前端桥接落盘路径始终保留）。

## 全局开发约束

- 遵守 CLAUDE.md 全部既有约束：`Ui*` primitives 单点落地、颜色 token、禁止新增裸 any、文件 ≤400 行优先、五层链路一次改齐、日志采集/持久化/查询属后端职责。
- 日志页面不直接 import Electron 主进程代码，一律经 `src/commands/*` + `src/platform/*`。
- 新增 IPC 通道在 preload 白名单显式声明，维持 `contextIsolation: true`。

## 最终验收条件

- 触发一次 LLM 对话后，日志窗口和 JSONL 文件中都能看到该次请求的完整请求体与聚合响应体，requestId 可关联。
- 打开完整捕获开关后，超长 prompt 不再被截断（api_key 仍为 `***`）。
- 前端未启动（或崩溃）时主进程事件依然落盘。
- 日志窗口可与主窗口同时使用，按来源/级别/domain/关键词过滤，可回看当天历史日志，错误可一键复制；打包产物中普通用户无法打开日志窗口。
- 在无历史对话的新 AI 会话中，仅凭 CLAUDE.md 的日志说明即可定位日志文件并用查询脚本取出某次请求的完整链路。
- `npm run lint`、`npx tsc -p tsconfig.electron.json --noEmit`、`npm run electron:smoke` 通过。
