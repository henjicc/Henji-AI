# 重要记录

## 记录 001：引入 `gap` 档位，不把真实缺口塞进 `excluded`

- 日期：2026-08-06
- 状态：已确定
- 背景：账本最初设计四档绑定（property / collection / capability / excluded）。建三维账本时发现 21 个动作既不是「已覆盖」也不是「有意不开放」，而是**确实还没做**。硬要求归入四档，只会逼人给真实缺口编一个假的排除理由。
- 最终决定：加第五档 `gap`，必须写 `plannedPhase` 与 `reason`，理由按与 `excluded` 相同的标准校验（≥12 字、不含推给将来的措辞）。汇总门禁盯住 `GAP_BASELINE` 总数不许涨。
- 选择原因：账本的价值在于「诚实」。区分「还没做」和「有意不做」是它存在的全部意义，混在一起就退化成一张豁免表。棘轮保证新缺口进不来，只能往下走。
- 影响任务：全部补齐类任务（第二、三、五、六阶段）都要在完成时调小 `GAP_BASELINE`。

## 记录 002：姿态关节直接写入遇上已有关键帧的语义

- 日期：2026-08-06
- 状态：**待确认**
- 背景：`camera_stage.object.animatable.*` 共 63 条属性（含 15 个姿态关节 × 3 轴）目前全部 `readOnly`，理由是「逐分量动画值通过关键帧实体或领域语义操作修改」。助手因此只能建关键帧，不能直接摆姿势。直接放开会出现两条互相覆盖的路径：助手写了静态值，而该轨道上有关键帧 → 播放头一动，采样器立刻把值覆盖回插值结果。用户看到的是「助手说改好了，值自己跳回去了」，**比「改不了」更糟**。
- 候选方案：
  - A：轨道上有关键帧就拒绝写入，提示改用关键帧。简单，但助手体验差。
  - B：无条件写静态值，关键帧照旧优先。会产生上述幽灵行为，**否决**。
  - C：轨道无关键帧 → 写静态值；轨道有关键帧 → 等价于在当前播放时间点写/建一个关键帧。
- 倾向决定：**方案 C**。它与界面上人拖手柄时的自动打点（`updateTransform` 的 `autoKeyPaths` 参数）语义完全一致，用户心智模型统一，且已有机制可直接复用。
- 选择原因：这个决策必须在写代码前定下来并写进属性描述，否则实现完再改语义要动数据。
- 影响任务：2.4。
- 待确认点：方案 C 会让「改姿势」在有动画时自动产生关键帧。这符合界面行为，但如果用户认为助手不该自动打点，需要改回方案 A。

## 记录 003：受保护设置只松绑两项，其余五项保持只读

- 日期：2026-08-06
- 状态：已确定
- 背景：`src/features/settings/application-control/protectedSettingDefinitions.ts` 有 7 项 `writable: false`。用户认为「总是以安全为理由去限制它，实际真不用那么担心」。
- 最终决定：
  - **松绑**：`models.visibility`、`updates.configuration`。两者 `sensitive: false`，纯保守限制，没有任何安全理由。
  - **保持只读**：`security.provider_keys`、`llm.configuration`（密钥明文）、`storage.data_path`、`storage.download_paths`、`downloads.quick_path`（必须走系统文件选择器）。
- 选择原因：后五项不是「顾虑」，是**渲染层技术上做不到**——OS 对话框不在渲染进程里，助手没有办法代替用户点。同时要把只读理由从含糊的安全表述改写成这个事实，并补一句助手可用 `open_application_surface` 把用户带到那一屏。
- 影响任务：4.4。
- 实现注意：`listApplicationSettingDefinitions()` 目前**只返回 general + interface**，protected 七项只出现在 `listApplicationSettingIds()` 里——它们根本没注册成反射属性。松绑不是改一个 flag，而是要写成带 `schema` / `read` / `write` 的正规 `ApplicationSettingDefinition`。

## 记录 004：补集合写入的同时必须删掉功能重复的专用能力

- 日期：2026-08-06
- 状态：已确定
- 背景：`AGENTS.md` 明令「禁止为设值/增删记录手写专用能力」。给镜头卡补 `collectionWrite` 后，`add_camera_stage_shot` 就成了同功能第二条路。
- 最终决定：补 `collectionWrite` 的**同一次提交**必须删掉对应专用能力。三维涉及 `add_camera_stage_shot`、`delete_camera_stage_object`。
- 选择原因：不删就是双轨，`applicationControlCoverage.test.ts` 的迁移唯一性断言也会红。本项目此前已因双轨吃过多次亏（同一语义两条路径，其中一条被遗忘）。
- 例外：`place_camera_stage_object` **保留**。它里面含碰撞检测与落地算法（`cameraStagePlacementExecutor.ts`），属于真正的算法型操作。切分口径是「创建对象走通用动词，带碰撞检测的摆放留作算法能力」。
- 影响任务：2.1、2.2。
- 待确认点（2.2 已解决，见下）：`captureIntoSelectedShot`（把当前对象状态记录进选中镜头卡）是简易模式的核心动作。助手侧已有 `updateObjectAcrossShots` 的建模语义写入（改动同步进所有卡），两者语义不同。需确认助手是否真的需要「只记录到某一张卡」这个入口，还是建模语义已经够用。

### 2.2 最终结论（已确定，2026-08-07）

用户明确选择开放该入口。技术依据：`compileShotsToAnimation`（`shotCompiler.ts`）是纯单向编译——`animation.tracks` 完全由 `shots[].objectStates` 差异推导而来；简易模式下 `shots` 数组任何一次变更（新建/删除/挪时间点）都会触发 `compile()` 重新生成整份 `animation`，会把此前通过 `camera_stage.keyframe` 集合写入直接落在 `animation.tracks` 上的编辑**整体覆盖丢弃**。也就是说在简易模式下，关键帧集合写入不是"逐卡捕获"的等效替代——它只在 shots 数组此后不再变化的前提下才稳定，属于脆弱路径，不能作为分支 A 的依据。

补的入口是 `camera_stage.shot.capture_object_refs`（`cameraStageTimelineFields.ts` 的 SHOT_FIELDS 里手写的一条字段）：写入时把列出的对象/摄像机当前的实时状态记录进**指定的**镜头卡（不依赖选中态，直接按稳定引用寻址 shotId），只覆盖列出的对象、只落在这一张卡上，不触碰这张卡的其余对象、不触碰其他镜头卡——因此不会重新打开 `modelingWrite.test.ts` 守住的那个已修问题（新对象在其余卡上停留默认状态、播放时插值）。回归测试见 `cameraStageShotCapture.test.ts`。

`captureIntoSelectedShot` 账本条目绑定到这条属性（`kind: 'property'`），不是字面调用该 store 方法——账本校验的是"助手有没有等效能力"，不是"是否调用了同一行代码"，这与 `reorderShot` 绑到 `time` 属性是同一个先例。

## 记录 005：门禁的领域清点存在 `src/stores/` 盲区

- 日期：2026-08-06
- 状态：已确定
- 背景：`scripts/check-assistant-capabilities.cjs` 新加的领域清点只遍历 `src/features/*`。而 `canvasStore`、`projectStore`、`settingsStore`、`themeStore`、`navigationStore`、`uiStore` 六个 store 全在 `src/stores/`，完全不在扫描范围内。canvas 过关是因为 `src/features/canvas/` 里有 Reflection 和账本，与 store 在哪无关——**是侥幸，不是覆盖**。
- 最终决定：把清点改成以 **store 文件**为单位而不是以 feature 目录为单位：扫描 `src/stores/*.ts` 与 `src/features/*/store/*.ts`，每个 store 必须能对应到一份账本，或在白名单里登记原因。
- 选择原因：现在的清点回答的是「这个目录接没接助手」，而真正要回答的是「这个 store 的每个动作助手能不能做」。后者才是用户的目标。
- 影响任务：4.1（必须先做，否则 4.2 / 4.3 建的账没有门禁盯着）。

## 记录 006：统一字段定义只做「一处声明、四处派生」，不做代码生成

- 日期：2026-08-06
- 状态：已确定
- 背景：四处登记是缺口再生的根因。收敛方式有多种：代码生成（脚本产出四个文件）、运行时反射魔法（从 store 自动推导）、或一个普通函数返回四元组。
- 最终决定：**普通函数**。一条声明返回 `{ descriptor, read, write, ledgerEntry }`，四个消费方各取所需。不生成文件，不做运行时推导。
- 选择原因：代码生成引入构建步骤和「生成产物要不要进 git」的问题；运行时推导让跳转定义、断点调试全部失效，出问题时排查成本极高。普通函数保持可读、可跳转、可断点，收益（4 处 → 1 处）已经拿到了。
- 影响任务：1.1、1.2、1.3。
- 边界：账本条目仍需人写一句「这在界面上是哪个动作」的映射，因为 store 动作名与属性 id 是两条不同的轴，无法自动对上。统一定义只是让这句话和另外三处写在一起。
