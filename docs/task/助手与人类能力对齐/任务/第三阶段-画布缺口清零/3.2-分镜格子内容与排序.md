## 当前情况

### 缺口的成因：两侧都没有入口

分镜数据存在两个地方，但两边都不可写：

| 位置 | 现状 |
|---|---|
| `canvas.node` 的节点内部数据 | 分镜格子（frames）是 `storyboardNode` 类型节点 `data` 里的一个数组。`canvas.node` 只注册了 `display_name` 与 `position` 两条可写属性，**格子内容不在其中** |
| `storyboard.card` 实体 | 整个 `storyboard` 领域标着 `writeExclusion: '分镜是画布工程的只读摘要投影，写入请用 canvas.* 的通用动词。'`（`src/features/canvas/application/storyboardReflection.ts`） |

`storyboard` 的排除理由**指向了 `canvas.*`，但 `canvas.node` 那边并没有对应的写入路径**——两边互相指，形成闭环。这是本次盘点发现的一个真实设计漏洞。

### store 侧

- `updateStoryboardFrame(nodeId, frameId, data, options)`：改某个格子的内容
- `reorderStoryboardFrame(nodeId, draggedFrameId, targetFrameId)`：拖拽调整顺序

都在 `src/stores/canvasStore.ts`（约 1318 / 1377 行）。

### 相关既有能力

`update_canvas_node`（`src/core/assistant/capabilities/canvasMutationApplicationCapabilities.ts`）——执行时确认它的输入 schema 能不能表达「改某个格子」。若能，这一项可能只是没接上，而不是缺路径。

`list_storyboard_projects` / `get_storyboard_project`（只读）在 `toolboxApplicationCapabilities.ts`。

## 实施方案

先判断走哪条路，两个候选：

### 候选 A：在 `canvas.node` 上补格子属性

给 `storyboardNode` 类型的节点补一条可写属性（如 `canvas.node.storyboard_frames`，值类型 `json` 带 schemaRef）。

优点：与 `storyboard` 的排除理由一致（写入走 `canvas.*`），闭环解开。
缺点：`canvas.node` 的属性对所有节点类型共享，加一条只对 `storyboardNode` 有意义的属性，需要在可写性判定里按节点类型区分。

### 候选 B：把 `storyboard.card` 改为可写

给 `storyboard.card` 注册可写属性并配执行器，收窄 `storyboard` 的 `writeExclusion`。

优点：语义更直接，「改分镜格子」就是改 card。
缺点：与现有「分镜是只读投影」的设计取向相反，要重新论证；且 card 的稳定引用与 canvas.node 的关系需要理清。

**执行时必须先读代码判断，把结论和理由写进执行记录，不要凭直觉选。**

关键判断依据：分镜格子是否有独立于画布节点的身份？若 card 只是 node.data 的一个视图，候选 A 更正；若 card 有自己的生命周期，候选 B 更正。

## 执行记录

### 2026-08-09

**候选选择：A（在 `canvas.node` 上补格子属性），理由是代码事实，不是猜测**：

1. 读 `updateStoryboardFrame`/`reorderStoryboardFrame`（`canvasStore.ts`）确认格子（`StoryboardFrameItem[]`）整段存在 `storyboardSplit` 节点的 `data.frames` 里，两个 store 动作都是直接 `.map()` 该数组——格子**没有独立于画布节点的存储**，`reorderStoryboardFrame` 内部的实现也证实了这点：把移动后每张格子的 `order` 重新赋值为数组下标，这与直接对每张格子写 `order` 字段是同一件事。
2. 读 `storyboardReflection.ts` 确认 `storyboard.card` 实体的 `provider` 数据来源是 `getStoryboardProject()` 对**画布节点摘要**（`nodeSummary`）的投影——一个 `storyboard.card` 对应一个画布节点（任意类型），根本不深入到 `storyboardSplit` 节点内部的 `frames` 数组。也就是说候选 B（把 `storyboard.card` 改可写）在结构上**够不到**格子数据，不是"设计取向相反需要重新论证"的问题，是从数据模型上就走不通。候选 A 因此是唯一可行的路。
3. 读 `update_canvas_node` 输入 schema 确认它**不能**表达"改某个格子"：`updateCanvasNode()` 无条件调用 `extractCanvasNodeData(node.type, input.data)`，而 `nodeControlRegistry.ts` 的 `nodeControlConfigs` 数组里根本没有注册 `CANVAS_NODE_TYPES.storyboardSplit`——对这个节点类型调用会直接抛 `当前闭环不支持节点类型：storyboardSplit`，不是"没接上"而是这条路径整个不通向这个节点类型。（但这不影响本任务：新属性走的是 `NODE_FIELDS` 的独立写入表，不经过 `extractCanvasNodeData`，所以没有改动 `nodeControlRegistry.ts`。）

**闭环验证**：`storyboard` 领域此前的 `writeExclusion` 理由写"写入请用 canvas.* 的通用动词"，但 `canvas.node` 那边压根没有对应的写入路径——两边互相指、都指向空处，是本次盘点确认的真实设计漏洞。补上 `canvas.node.storyboard_frames` 后，理由文字已更新为指向这条具体属性 id，闭环解开。

**内容与排序合并成一条属性**：`canvas.node.storyboard_frames`（`kind: 'json'`），数组元素 `{id, note, order}`，按 id 定点更新——只需要传要改的字段，不需要重发整个数组。排序**不单独**走 `store.reorderStoryboardFrame()`：它是一次拖拽换两个位置的手势 API（入参是"拖了谁、放到谁的位置"），跟"整批格子各自要什么 order"的输入形状不匹配；而 `reorderStoryboardFrame` 内部本质就是给每张卡重新赋 `order` 值，所以直接对每张卡写 `order` 字段是同一件事，还更直接，两个 store 动作因此共用同一条账本绑定。

**执行方式**：写入不能用 `canvas.node.data` 的通用合并表达（合并会用传入的 `frames` 整体替换掉其余格子），所以没有复用 `applyCanvasNodePropertyPatches`，新增独立的 `applyStoryboardFramePatches()`，在 `canvasMutationExecutor.ts` 里作为 `applyAtomic` 的第二步单独提交（第一步是原有的 display_name/position 合并）。两步共用同一个执行器的撤销机制（`before`/`after` 快照 + fingerprint 校验），不需要第二套撤销逻辑。

**实施**：
- `canvasMutationService.ts`：`CanvasNodePropertyPatch` 加 `storyboardFrames?`；新增 `applyStoryboardFramePatches()`（校验节点类型、校验 id 存在、按 id 调 `store.updateStoryboardFrame`）。
- `canvasFields.ts`：`NODE_FIELDS` 加 `storyboard_frames` 字段（读：非 storyboardSplit 节点返回空数组；写：zod 校验后存进 `patch.storyboardFrames`）；`canvasDescriptor()` 加了可选 `description` 参数（原先硬编码，这条属性的语义需要单独说明）。
- `canvasMutationExecutor.ts`：`applyAtomic` 在 `applyCanvasNodePropertyPatches` 之后追加逐节点的 `applyStoryboardFramePatches` 调用。
- `storyboardReflection.ts`：`writeExclusion.reason` 更新为指向具体属性 id。
- `canvasStoreLedger.ts`：删掉 `updateStoryboardFrame`/`reorderStoryboardFrame` 两条手写 gap（现由 `fieldLedgerEntries(NODE_FIELDS)` 自动派生，与 `updateNodePosition` 共用同一次 spread）。
- `storeActionCoverage.test.ts`：`GAP_BASELINE` 2 → 0。
- `canvasReflection.test.ts`：既有的属性清单断言更新（多了一条 `canvas.node.storyboard_frames`）。

**测试**：`canvasReflection.test.ts` 新增 3 用例——按 id 定点更新 note/order 并整体撤销、格子 id 不存在时整批拒绝、对非分镜节点写入被拒绝。撤销断言踩了一个真实的归一化差异（`setCanvasData` 会给格子补 `aspectRatio`/`previewImageUrl` 默认值，裸 `setState` 不会），改用同一条 `setCanvasData` 路径建立比对基准后解决，不是生产代码的问题。
