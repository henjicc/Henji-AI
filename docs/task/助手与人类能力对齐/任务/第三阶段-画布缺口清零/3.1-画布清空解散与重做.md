# 3.1 画布清空解散与重做

## 任务状态

- 状态：待开始
- 所属阶段：第三阶段 · 画布缺口清零
- 前置任务：1.3
- 关联任务：3.2
- 是否可以并行：可与第二、四、五、六阶段并行

## 任务目标

补齐画布三项缺口：`clearCanvas`（清空整张画布）、`ungroupNode`（解散分组）、`redo`（重做）。

`GAP_BASELINE` 降 3。

## 当前情况

### 三项缺口的具体情况

| 动作 | store 位置 | 助手侧现状 |
|---|---|---|
| `clearCanvas` | `src/stores/canvasStore.ts` | 界面上是一个按钮（`CanvasToolbar.tsx`）。助手只能逐个引用删除，节点多时受 `maxItemsPerChange: 50` 限制 |
| `ungroupNode` | 同上 | 有 `group_canvas_nodes` 专用能力，**没有对应的解散**。成对能力只注册了一半 |
| `redo` | 同上 | 有 `undo_canvas_change` 专用能力，**没有重做**。助手撤销过头之后无法回退自己的撤销 |

### 已有的可复用件

- `canvas.node` 与 `canvas.edge` 都已声明 `collectionWrite: { creatable: true, removable: true }`，`maxItemsPerChange: 50`。
- `CanvasCollectionExecutor`（`src/features/canvas/application/canvasCollectionExecutor.ts`）已注册两次（node + edge）。
- `undo_canvas_change` 与 `group_canvas_nodes` 定义在 `src/core/assistant/capabilities/canvasMutationApplicationCapabilities.ts`。

### 三项的形态判断（执行时确认）

- **`clearCanvas`**：本质是「删掉这个工程下的全部节点与连线」。优先做法是让集合删除支持「按父实体整体清空」，而不是新增 `clear_canvas` 能力。若 50 条上限成为障碍，考虑给清空场景单独放宽。
- **`ungroupNode`**：分组在画布里是一个 `groupNode` 类型的节点。解散 = 删掉这个 group 节点并把子节点释放出来。判断它能否表达成 `remove_items`（删 group 节点，释放行为由 store 的 `ungroupNode` 承担），能则不新增能力。
- **`redo`**：与 `undo_canvas_change` 成对。撤销做成了专用能力（因为它操作的是历史栈，不是实体状态），重做同理。这一项**大概率需要新增一个专用能力** `redo_canvas_change`——执行时书面回答「为什么不能表达成属性写入」（答案是：历史栈不是实体）。

## 实施方案

按上面的判断逐项处理，优先级顺序：`redo`（最简单，照抄 undo）→ `ungroupNode` → `clearCanvas`（形态需要设计）。

三项可以在同一次提交里完成，因为它们都在画布同一层、互不依赖。

## 执行步骤

1. 读 `src/stores/canvasStore.ts` 的 `clearCanvas`、`ungroupNode`、`redo` 实现，确认副作用（历史记录、选中态、持久化）。
2. 读 `src/core/assistant/capabilities/canvasMutationApplicationCapabilities.ts` 里 `undo_canvas_change` 的完整定义，作为 `redo` 的模板。
3. 读 `src/features/canvas/application/canvasCollectionExecutor.ts`，确认 `remove` 分支的目标解析方式，判断能否支持「整体清空」与「删 group 节点」。
4. **实现 `redo`**：照 `undo_canvas_change` 的形态新增 `redo_canvas_change`，注册进 `builtinApplicationCapabilityRegistry.ts`，实现处理器。执行记录里写明「历史栈不是实体，因此这里确实需要专用能力」。
5. **实现 `ungroupNode`**：判断能否走 `remove_items` 删 group 节点；能则只需在集合执行器里让删除 group 节点时调用 store 的 `ungroupNode` 而不是 `deleteNode`，不能则新增能力并说明理由。
6. **实现 `clearCanvas`**：设计「按父实体整体清空」的表达方式，评估 `maxItemsPerChange: 50` 是否构成障碍，结论写进执行记录。
7. 更新 `src/features/canvas/application/canvasStoreLedger.ts`：三条 gap 改绑定。
8. `GAP_BASELINE` 降 3。
9. 扩展 `src/features/canvas/application/canvasCollectionExecutor.test.ts` 或新建测试：
   - 清空后节点与连线都为空，且可撤销
   - 解散分组后子节点仍在、group 节点消失
   - 重做能恢复被撤销的改动
10. 运行 `npx tsc --noEmit && npm run lint && npm run check:assistant-capabilities`。
11. 运行 `npx vitest run src/features/canvas src/features/assistant/applicationCapabilities src/core/assistant`。
12. **实机验证交给用户**（涉及画布交互）：让助手把画布清空，确认节点全没了、Ctrl+Z 能撤回；让助手解散一个分组，确认子节点还在。
