# 3.1 画布清空解散与重做

## 任务状态

- 状态：已完成
- 所属阶段：第三阶段 · 画布缺口清零
- 前置任务：1.3
- 关联任务：3.2
- 是否可以并行：可与第二、四、五、六阶段并行

## 任务目标

补齐画布三项缺口：`clearCanvas`（清空整张画布）、`ungroupNode`（解散分组）、`redo`（重做）。

`GAP_BASELINE` 降 3。

## 当前情况

### 三项缺口的具体情况

| 动作 | store 位置 | 助手侧现状 |
|---|---|---|
| `clearCanvas` | `src/stores/canvasStore.ts` | 界面上是一个按钮（`CanvasToolbar.tsx`）。助手只能逐个引用删除，节点多时受 `maxItemsPerChange: 50` 限制 |
| `ungroupNode` | 同上 | 有 `group_canvas_nodes` 专用能力，**没有对应的解散**。成对能力只注册了一半 |
| `redo` | 同上 | 有 `undo_canvas_change` 专用能力，**没有重做**。助手撤销过头之后无法回退自己的撤销 |

### 已有的可复用件

- `canvas.node` 与 `canvas.edge` 都已声明 `collectionWrite: { creatable: true, removable: true }`，`maxItemsPerChange: 50`。
- `CanvasCollectionExecutor`（`src/features/canvas/application/canvasCollectionExecutor.ts`）已注册两次（node + edge）。
- `undo_canvas_change` 与 `group_canvas_nodes` 定义在 `src/core/assistant/capabilities/canvasMutationApplicationCapabilities.ts`。

### 三项的形态判断（执行时确认）

- **`clearCanvas`**：本质是「删掉这个工程下的全部节点与连线」。优先做法是让集合删除支持「按父实体整体清空」，而不是新增 `clear_canvas` 能力。若 50 条上限成为障碍，考虑给清空场景单独放宽。
- **`ungroupNode`**：分组在画布里是一个 `groupNode` 类型的节点。解散 = 删掉这个 group 节点并把子节点释放出来。判断它能否表达成 `remove_items`（删 group 节点，释放行为由 store 的 `ungroupNode` 承担），能则不新增能力。
- **`redo`**：与 `undo_canvas_change` 成对。撤销做成了专用能力（因为它操作的是历史栈，不是实体状态），重做同理。这一项**大概率需要新增一个专用能力** `redo_canvas_change`——执行时书面回答「为什么不能表达成属性写入」（答案是：历史栈不是实体）。

## 实施方案

按上面的判断逐项处理，优先级顺序：`redo`（最简单，照抄 undo）→ `ungroupNode` → `clearCanvas`（形态需要设计）。

三项可以在同一次提交里完成，因为它们都在画布同一层、互不依赖。

## 执行记录

### 2026-08-08

**三项的形态判断，均与任务文档最初的倾向不同**（任务文档倾向 clearCanvas/ungroupNode 走集合写入、只有 redo 新增能力；实际执行下来三项全部新增了能力）：

**`redoCanvasChange`**：照抄 `undo_canvas_change` 的先例，最简单。但读 `undoCanvasChange()` 实现发现它比预想复杂——不是直接调 `store.undo()`，而是先校验 `undoRef` 对应的 `historyDepth` 与当前 `history.past.length` 一致（防止撤销一条已经被其他改动覆盖的旧记录）。redo 是否需要同样的 token 校验？读 `canvasStore.ts` 确认：**每一个正向编辑动作都显式 `future: []`**（新增/改属性/删除等，逐个搜索确认），也就是说 `history.future` 只可能在 `undo()` 之后短暂非空，任何后续的新编辑都会把它清空——不存在"重做一个已经过期的操作"这种歧义场景。因此 redo **不需要** undoRef/historyDepth 那套安全校验，输入只要 `{projectId}`，`store.redo()` 返回 false 本身就是天然的安全网。`redoCanvasChange()` 因此比 `undoCanvasChange()` 简单得多，不是对称照抄。

**`ungroupCanvasNode`**：任务文档设想"判断能否表达成 remove_items 删 group 节点，能则只需在集合执行器里让删除 group 节点时调用 store 的 ungroupNode 而不是 deleteNode"。读 `store.deleteNodes()` 实现发现这个设想不成立：`deleteNodes` 对节点的删除语义早就是**级联删除**（`collectNodeIdsWithDescendants` 收集整棵子树），也就是说当前 `remove_items` 删除 group 节点这件事本身已经有明确语义——连同子节点一起删掉——解散分组要求子节点**保留**，与现有语义直接冲突，不是"复用同一个入口但换一种内部实现"能解决的，两种语义共用一个 `remove_items` 会产生歧义（模型无法从"删除这个节点"的意图判断出到底要不要带走子节点）。因此解散分组走独立的 `ungroup_canvas_node` 能力。

**`clearCanvas`**：任务文档倾向"让集合删除支持按父实体整体清空"。评估后放弃：要表达成 `remove_items`，助手需要先 `observe`/`list_application_entities` 枚举全部节点与连线引用（多一次往返），再受 `canvas.node`/`canvas.edge` 的 `maxItemsPerChange: 50` 限制分批提交——节点数超过 50 就至少要拆两批，且节点与连线是两个不同实体类型，删除顺序还有讲究（先删边还是先删点）。这些复杂度只是为了表达一个界面上单按钮触发的原子动作。改为直接照 `undo_canvas_change`/`group_canvas_nodes` 的先例：工程级整体状态操作走专用能力。`maxItemsPerChange: 50` 因此对清空场景**没有影响**——`clear_canvas` 走的是 `store.clearCanvas()` 整体重置，不经过集合写入的逐条上限。

**三者的共同理由**：都不是"设置一个值"或"对集合做增删"，而是**工程级整体状态操作**（重做作用于历史栈、解散改变节点树结构且与现有删除语义冲突、清空是整体重置不是逐条删除），与项目里已有的 `undo_canvas_change`/`group_canvas_nodes` 是同一类操作，遵循同一个先例。
