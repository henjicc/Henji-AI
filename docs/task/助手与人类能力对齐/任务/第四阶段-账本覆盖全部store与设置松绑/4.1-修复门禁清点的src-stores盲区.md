# 4.1 修复门禁清点的 src-stores 盲区

## 任务状态

- 状态：已完成
- 所属阶段：第四阶段 · 账本覆盖全部 store 与设置松绑
- 前置任务：无
- 关联任务：4.2、4.3（它们建的账要靠这道门禁盯着）
- 是否可以并行：可与第一、二、三、五、六阶段并行

## 任务目标

把领域清点从「按 feature 目录」改成「按 store 文件」，让 `src/stores/` 下的 6 个 store 进入扫描范围。

**这一项必须先于 4.2 / 4.3**，否则后面建的账没有门禁盯着，等于白建。

### 现有的白名单机制

`ASSISTANT_BLIND_FEATURES` 目前以 **feature 名**为 key（`imageMark` / `imageEdit` / `generation` / `logs` / `navigation` / `project` / `assistant` / `settings` / `toolbox`）。改成按 store 之后，key 要改成 store 文件路径或 store 名。

## 实施方案

改造清点逻辑：

1. 扫描 `src/stores/*.ts` 与 `src/features/*/store/*.ts`，得到全部 store 文件。
2. 扫描全部 `*StoreLedger.ts`，读出每个账本声明的 `storeId`。
3. 要求每个 store 文件都能对应到一个账本，或在白名单里登记原因。
4. 白名单 key 改为 store 文件的相对路径（明确、不歧义）。

**对应关系怎么建立**：账本里的 `storeId` 是个自由字符串（如 `'cameraStage'`），与文件名不一定一致。执行时有两个选择：
- 要求 `storeId` 等于 store 文件的 basename（去掉 `.ts`），强约束、简单
- 在账本里加一个 `storePath` 字段显式指明

建议前者（改 3 个现有账本的 `storeId` 即可），执行时评估。

### 白名单初始内容

改造后必然有 15 个 store 未建账，全部先进白名单并写明归属任务（4.2 / 4.3），随任务完成逐条删除。**白名单是一张会缩短的清单。**

## 执行步骤

1. 读 `scripts/check-assistant-capabilities.cjs` 现有的领域清点段落（在「属性写入执行器必须表驱动」注释之前）。
2. 实测全部 18 个 store 的动作数，补全上表中「待确认」的三项，结果写进执行记录。
3. 决定 store ↔ 账本的对应方式（`storeId` = basename，或加 `storePath` 字段），理由写进执行记录。
4. 若选 basename 方案，调整三个现有账本的 `storeId`：`cameraStage` → `cameraStageStore`，`canvas` → `canvasStore`，`assets` → `assetLibraryStore`（或反过来调整比对逻辑）。
5. 改造清点逻辑：按 store 文件遍历，比对账本，未覆盖则查白名单。
6. 把 `ASSISTANT_BLIND_FEATURES` 改名为 `ASSISTANT_BLIND_STORES`，key 改为 store 文件相对路径，填入 15 个未建账 store，每条写明归属任务编号。
7. **保留** feature 级的 Reflection 检查（imageMark / generation 那种全域失明是 feature 级的问题，与 store 级正交），两套检查并存。
8. **断牙验证**：从白名单里删掉 `src/stores/themeStore.ts` 一条，确认门禁报「store 未建账且未登记原因：src/stores/themeStore.ts」。跑完恢复。
9. **反向断牙**：临时把某个已建账 store 的账本文件改名，确认门禁报它未覆盖（证明比对逻辑真的在工作，不是永远查白名单）。跑完恢复。
10. 运行 `node scripts/check-assistant-capabilities.cjs`，确认通过。
11. 运行 `npm run check:assistant-capabilities` 全链。
12. 更新 `docs/rules/assistant-capability.md` 的「界面动作覆盖」一节：把「每个带 store 的 feature 必须有账本」改为「每个 store 必须有账本或登记原因」。
13. 同步两侧 skill（`.codex/` 与 `.claude/` 的 `henji-application-capability/SKILL.md`）。

## 执行记录

**清点逻辑改为按内容识别，不按目录 glob。** 任务文档设计的方案是扫描 `src/stores/*.ts` 与
`src/features/*/store/*.ts` 两个固定目录。实测跑了一个临时脚本枚举全部 `create<...>(` 调用点，
发现第 19 个 store：`src/services/largeUploadPolicy.ts` 里的 `useLargeUploadPromptStore`（大文件
询问弹窗队列，`enqueue`/`settleCurrent` 两个动作）——它既不在 `src/stores/` 也不在任何
`*/store/` 目录下，任何基于目录约定的扫描方案都会漏掉它，而这正是 4.1 本身要修的那类盲区。
于是没有照搬文档的目录扫描方案，改为按**内容**识别：文件同时满足"导入 `zustand`"与"调用
`create<`"就算一个 store，与文件放在哪个目录无关。18 → 19 是这次复核的直接产物，不是估算误差。
