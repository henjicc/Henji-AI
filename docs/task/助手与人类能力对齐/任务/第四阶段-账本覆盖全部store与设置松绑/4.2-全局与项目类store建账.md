## 任务目标

给 5 个全局/项目类 store 建账：`projectStore`（10 动作）、`settingsStore`（31）、`navigationStore`（2）、`uiStore`（2）、`themeStore`（2）。

共 47 个动作要逐条归类（4.1 复核时发现任务文档原写的 61 与实际代码不符，`projectStore`/
`navigationStore`/`uiStore` 三项数字对不上，已按运行时枚举订正，详见 4.1 执行记录）。归类过程
本身就是盘点这几块的人机差集——**预期会盘出新的 gap，这是正常的**，把它们如实登记并调高
`GAP_BASELINE`，然后在本任务或后续任务里烧掉。

### 已知的判断要点

**`projectStore`**：20 个动作里有一部分是持久化回填（`hydrate`、`saveCurrentProjectViewport`、`cancelPendingViewportPersist`），属于 `internal`；核心 CRUD 已被专用能力覆盖。执行时逐条对照。

**`settingsStore`**：31 个动作大多是 `setXxx` 形式，对应 `settings.registry` 的属性写入。**要特别注意**：`listApplicationSettingDefinitions()` 只返回 general + interface，protected 7 项没注册（见 4.4）。所以 `settingsStore` 里对应 protected 的那几个动作暂时是 gap，等 4.4 完成后再改绑定。

**`themeStore`**：`setTheme` / `toggleTheme` 对应明暗主题。确认它是否已经被 `settings.registry` 的某条属性覆盖——若是则绑 property，若否则是 gap。

**`navigationStore` / `uiStore`**：动作少，主要是 surface 打开关闭，大概率已被 `open/close_application_surface` 覆盖，绑 `capability`。

### 建账的形态

照 `src/features/cameraStage/application/cameraStageStoreLedger.ts` 的范式：

```ts
type State = ReturnType<typeof useXxxStore.getState>
type ActionName = { [K in keyof State]-?: State[K] extends (...args: never[]) => unknown ? K : never }[keyof State]
export const XXX_STORE_LEDGER: ApplicationStoreActionLedger<ActionName> = { storeId, title, entries: { ... } }
```

`Record<ActionName, …>` 提供编译期完整性检查——漏一条 `tsc` 就报。

### 账本放哪

`src/stores/` 下的 store 没有对应的 feature 目录。放置约定需要确定：
- 放到最相关的 feature 的 `application/` 下（如 `projectStore` → `src/features/project/application/`）
- 或新建 `src/stores/ledgers/` 目录

执行时决定并写进执行记录，同时确认 4.1 的清点逻辑能找到它们。

## 实施方案

一个 store 一次提交，五次提交。每次：枚举动作 → 逐条归类 → 建账 → 门禁绿 → 白名单删这一条。

归类时对每个动作问三个问题（来自 `01-实施方案.md` 的取舍原则）：

1. 这个值会写进工程文件 / settings 吗？会 → 必须开放
2. 它决定生成结果或导出内容吗？决定 → 必须开放
3. 关掉应用重开会恢复默认吗？会 → 大概率是视图态

## 执行步骤

1. 确定账本文件放置约定，写进执行记录，并确认 4.1 的清点能找到。
2. 对每个 store：
   a. 用运行时枚举拿到确切的动作名清单（写一个临时测试 `console.log(Object.keys(state).filter(k => typeof state[k] === 'function'))`，跑完删除）。
   b. 逐条归类为 `property` / `collection` / `capability` / `excluded` / `gap`。
   c. 建账本文件，`Record<ActionName>` 保证完整性。
   d. 在 `storeActionCoverage.test.ts` 的 `LEDGERS` 数组里注册。
   e. 从 4.1 的白名单里删掉这一条。
   f. 跑 `npx tsc --noEmit && npm run check:assistant-capabilities`。
   g. 单独提交。
3. 五个 store 全部建完后，统计新增的 gap 数量，更新 `GAP_BASELINE` 与总览的分布说明。
4. **`settingsStore` 里对应 protected 设置的动作**：先登记为 gap，理由指向任务 4.4。4.4 完成后回来改绑定。
5. 运行 `npm run check:assistant-capabilities` 与 `npx vitest run src/features/assistant/applicationCapabilities`。
