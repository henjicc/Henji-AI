## 任务目标

给 5 个全局/项目类 store 建账：`projectStore`（10 动作）、`settingsStore`（31）、`navigationStore`（2）、`uiStore`（2）、`themeStore`（2）。

共 47 个动作要逐条归类（4.1 复核时发现任务文档原写的 61 与实际代码不符，`projectStore`/
`navigationStore`/`uiStore` 三项数字对不上，已按运行时枚举订正，详见 4.1 执行记录）。归类过程
本身就是盘点这几块的人机差集——**预期会盘出新的 gap，这是正常的**，把它们如实登记并调高
`GAP_BASELINE`，然后在本任务或后续任务里烧掉。

### 已知的判断要点

**`projectStore`**：20 个动作里有一部分是持久化回填（`hydrate`、`saveCurrentProjectViewport`、`cancelPendingViewportPersist`），属于 `internal`；核心 CRUD 已被专用能力覆盖。执行时逐条对照。

**`settingsStore`**：31 个动作大多是 `setXxx` 形式，对应 `settings.registry` 的属性写入。**要特别注意**：`listApplicationSettingDefinitions()` 只返回 general + interface，protected 7 项没注册（见 4.4）。所以 `settingsStore` 里对应 protected 的那几个动作暂时是 gap，等 4.4 完成后再改绑定。

**`themeStore`**：`setTheme` / `toggleTheme` 对应明暗主题。确认它是否已经被 `settings.registry` 的某条属性覆盖——若是则绑 property，若否则是 gap。

**`navigationStore` / `uiStore`**：动作少，主要是 surface 打开关闭，大概率已被 `open/close_application_surface` 覆盖，绑 `capability`。

### 建账的形态

照 `src/features/cameraStage/application/cameraStageStoreLedger.ts` 的范式：

```ts
type State = ReturnType<typeof useXxxStore.getState>
type ActionName = { [K in keyof State]-?: State[K] extends (...args: never[]) => unknown ? K : never }[keyof State]
export const XXX_STORE_LEDGER: ApplicationStoreActionLedger<ActionName> = { storeId, title, entries: { ... } }
```

`Record<ActionName, …>` 提供编译期完整性检查——漏一条 `tsc` 就报。

### 账本放哪

`src/stores/` 下的 store 没有对应的 feature 目录。放置约定需要确定：
- 放到最相关的 feature 的 `application/` 下（如 `projectStore` → `src/features/project/application/`）
- 或新建 `src/stores/ledgers/` 目录

执行时决定并写进执行记录，同时确认 4.1 的清点逻辑能找到它们。

## 实施方案

一个 store 一次提交，五次提交。每次：枚举动作 → 逐条归类 → 建账 → 门禁绿 → 白名单删这一条。

归类时对每个动作问三个问题（来自 `01-实施方案.md` 的取舍原则）：

1. 这个值会写进工程文件 / settings 吗？会 → 必须开放
2. 它决定生成结果或导出内容吗？决定 → 必须开放
3. 关掉应用重开会恢复默认吗？会 → 大概率是视图态

## 执行步骤

1. 确定账本文件放置约定，写进执行记录，并确认 4.1 的清点能找到。
2. 对每个 store：
   a. 用运行时枚举拿到确切的动作名清单（写一个临时测试 `console.log(Object.keys(state).filter(k => typeof state[k] === 'function'))`，跑完删除）。
   b. 逐条归类为 `property` / `collection` / `capability` / `excluded` / `gap`。
   c. 建账本文件，`Record<ActionName>` 保证完整性。
   d. 在 `storeActionCoverage.test.ts` 的 `LEDGERS` 数组里注册。
   e. 从 4.1 的白名单里删掉这一条。
   f. 跑 `npx tsc --noEmit && npm run check:assistant-capabilities`。
   g. 单独提交。
3. 五个 store 全部建完后，统计新增的 gap 数量，更新 `GAP_BASELINE` 与总览的分布说明。
4. **`settingsStore` 里对应 protected 设置的动作**：先登记为 gap，理由指向任务 4.4。4.4 完成后回来改绑定。
5. 运行 `npm run check:assistant-capabilities` 与 `npx vitest run src/features/assistant/applicationCapabilities`。

## 执行记录

**账本放置约定**：不新开 `src/stores/ledgers/`，而是放进语义最贴近的既有 feature 目录，与
`canvasStoreLedger.ts`/`cameraStageStoreLedger.ts`/`assetStoreLedger.ts` 的先例一致：
- `projectStoreLedger.ts` → `src/features/canvas/application/`——`projectStore` 是
  `canvas.project` 实体的唯一数据源，`canvasProjectService.ts`/`canvasProjectMutationExecutor.ts`
  早就在这个目录操作它，`src/features/project/` 本身只有两个 UI 组件、没有应用层，不必为此单独开目录。
- `navigationStoreLedger.ts` → `src/features/navigation/application/`（已有 `surfaceNavigationService.ts` 在同目录）。
- `uiStoreLedger.ts`/`themeStoreLedger.ts`/`settingsStoreLedger.ts` → `src/features/settings/application-control/`
  （与既有的 `settingsReflection.ts`/`settingsMutationExecutor.ts` 同目录；`uiStore` 只管设置面板
  开关，`themeStore` 是主题相关的死代码，两者都归到设置领域最合适）。

4.1 的门禁按内容识别 store、按 `storeId`（= 文件 basename）比对账本，与账本放在哪个目录完全无关，
所以这个放置决定不影响门禁能否找到它们——已用 `node scripts/check-assistant-capabilities.cjs`
验证。

**实施顺序与提交次数**：5 个 store 实际分 3 次提交，不是文档建议的 5 次——`navigationStore`/
`uiStore`/`themeStore` 各只有 2 个动作，且改动都集中在同两个共享文件（`LEDGERS` 数组、
白名单），拆三次提交只会把同一批 diff 打碎，收益不大于合并的可读性代价，在提交信息里已说明这个偏离并给出理由。

**动作数订正**（详见 4.1 的订正记录）：`projectStore` 实为 10（非文档原写的 20）、
`navigationStore` 实为 2（非 4）、`uiStore` 实为 2（非 4）；`settingsStore`（31）与本任务描述一致。
共 47 个动作，不是文档最初估的 61 个。

**projectStore（10 动作，零新增 gap）**：`createProject`/`deleteProject`/`renameProject`/
`openProject`/`closeProject` 绑到既有的 `create`/`delete`/`rename`/`open`/`close_canvas_project`
五个能力（读 `canvasProjectService.ts`/`canvasApplicationService.ts` 确认调用链）。
`hydrate`/`getCurrentProject`/`saveCurrentProject`/`cancelPendingViewportPersist` 归为
`internal`——都是别的动作内部调用的前置/落盘/清理步骤，不是独立用户入口。
`saveCurrentProjectViewport` 归为 `view_state`——这是本任务里唯一一处需要权衡三问取舍原则的
地方：视口坐标确实写进工程文件（viewportJson），按"会写进工程文件吗"这条单独看应该开放；但它
是纯导航态（画布平移缩放到哪个位置），不影响节点/连线内容，也不参与生成或导出产物，助手没有
"控制用户正在看哪里"的需求，判断为 `view_state` 更合理。

**navigationStore/uiStore/themeStore（各 2 动作，零新增 gap）**：`setActiveWorkspace`/
`setActiveToolId` 绑到 `switch_workspace`/`select_toolbox_tool`（真正的入口是
`switchWorkspace()`/`selectToolboxTool()` 包装函数，store setter 是内部实现）。
`openSettings`/`closeSettings` 绑到 `open`/`close_application_surface`（`surfaceNavigationService.ts`
唯一调用方）。**核对 `themeStore` 时发现它是死代码**——除自身定义文件外，全仓库没有任何组件或
服务引用它（已用 grep 确认），界面真正的明暗/色调/强调色设置由 `settingsStore` 承载并注册进
`settings.registry`。两个动作先如实登记为 `excluded/internal` 并注明死代码事实，不在建账任务
里顺手删文件；已经开了一张独立的清理任务卡片（`task_b40a2077`）交给用户决定。

**settingsStore（31 动作，新增 2 个 gap）**：29 项直接绑到 `settings.registry` 里已注册的
`general.*`/`interface.*`/`canvas.*`/`generation.*`/`storyboard.*`/`diagnostics.*`/`assets.*`
属性（逐条核对 `generalSettingDefinitions.ts`/`interfaceSettingDefinitions.ts` 的 `write` 函数
确认调用哪个 store setter）。`setThemeColor`/`setThemeColors`/`resetThemeColors` 三个都绑到
全部 9 个 `interface.theme_color_*` 属性（`THEME_COLOR_TOKENS` 常量），因为它们能写任意一个或
多个 token。`setImageViewerInfoPanelCollapsed` 归为 `view_state`——面板是否存在已经由
`generation.viewer_info` 覆盖，这里只是查看时 Tab 键切换的折叠态。`setProviderKeyStatus` 归为
`derived`、`setProviderKeyStatuses` 归为 `internal`——密钥配置状态是 `aiSetProviderApiKey`/
`aiRemoveProviderApiKey`（IPC 命令）真正写入密钥后同步的派生标志位，密钥输入本身是凭据类操作，
助手不能代为完成（系统规则明确禁止代填密钥）。

新增的 2 个 gap 都对应 protected 设置，按本任务文档已经写明的分工登记，交给 4.4 统一处理：
`setProviderApiKey`（对应 `security.provider_keys`）、`setDownloadPresetPaths`（对应
`storage.download_paths`）。核对时**额外发现这两个 store 方法在全仓库里除自身定义外也找不到
调用方**——真正的密钥写入走 `aiSetProviderApiKey` 这个 IPC 命令（`useApiKeys.ts` 调用它之后只
调用 `setProviderKeyStatus` 同步布尔态，从不调用 `setProviderApiKey`）；`downloadPresetPaths`
字段只被读取（`canvasDownloadService.ts`），至今没有任何 Settings UI 组件提供设置入口。这个
发现没有改变归类结果——仍然登记为 `gap` 而不是自行判定为 `excluded`，因为 4.4 要统一审视全部
7 项 protected 设置的最终归宿（松绑 2 项、改写其余 5 项理由），这两条的死代码事实已经写进
gap 理由里，供 4.4 执行时参考。
