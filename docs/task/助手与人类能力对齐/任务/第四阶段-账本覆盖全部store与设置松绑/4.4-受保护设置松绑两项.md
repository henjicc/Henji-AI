# 4.4 受保护设置松绑两项

## 任务状态

- 状态：已完成
- 所属阶段：第四阶段 · 账本覆盖全部 store 与设置松绑
- 前置任务：4.2
- 关联任务：无
- 是否可以并行：否（依赖 4.2 的 `settingsStore` 账本，其中 protected 相关动作登记为 gap）

## 任务目标

放开两项**没有任何安全理由**的受保护设置：`models.visibility`（模型显示范围）、`updates.configuration`（软件更新）。

同时把其余 5 项的只读理由从含糊的安全表述改写成技术事实。

决策依据见 `重要记录.md` 记录 003（状态：已确定）。

## 当前情况

### 7 项受保护设置

`src/features/settings/application-control/protectedSettingDefinitions.ts`，全部 `writable: false`：

| id | sensitive | 判断 |
|---|---|---|
| `models.visibility` | **false** | **纯保守限制，无安全理由 → 放开** |
| `updates.configuration` | **false** | **纯保守限制，无安全理由 → 放开** |
| `security.provider_keys` | true | 密钥明文 → 保持只读 |
| `llm.configuration` | true | 含密钥 → 保持只读 |
| `storage.data_path` | true | 必须走系统文件选择器 → 保持只读 |
| `storage.download_paths` | true | 同上 → 保持只读 |
| `downloads.quick_path` | true | 同上 → 保持只读 |

### 关键实现事实（不要想当然）

`src/features/settings/application-control/settingsApplicationService.ts` 第 208 行附近：

```ts
export function listApplicationSettingDefinitions(): ApplicationSettingDefinition[] {
  return [...definitions]        // 只有 general + interface
}

export function listApplicationSettingIds(): string[] {
  return [...definitions.map(d => d.id), ...Object.keys(PROTECTED_APPLICATION_SETTING_DEFINITIONS)]
}
```

**protected 七项根本没注册成反射属性**，只出现在 id 列表里（供助手搜索定位）。

所以松绑**不是改一个 `writable` flag**，而是要把这两项写成带 `schema` / `read` / `write` 的正规 `ApplicationSettingDefinition`，并进入 `definitions`。

### 后五项的只读理由要改写

现在的描述文字带着「安全」的味道，但真实原因是**技术上做不到**：

- 密钥两项：明文密钥不能进模型上下文（这条确实是安全，保留表述）
- 路径三项：**OS 文件对话框不在渲染进程里**，助手没有办法代替用户点。这不是顾虑，是能力边界。

理由里要补一句：助手可用 `open_application_surface` 把用户带到对应设置分区，让用户自己点。

### `SettingsMutationExecutor` 的可写判定

`src/features/settings/application-control/settingsMutationExecutor.ts`：

```ts
get writableProperties(): ReadonlySet<string> {
  return new Set(listApplicationSettingDefinitions().filter(d => !d.sensitive).map(d => d.id))
}
```

两项松绑后会自动进入这个集合（它们 `sensitive: false`），**无需改执行器**。但要确认 `apply` 里的 `definitions.get(...)` 也能找到它们。

## 实施方案

1. 把 `models.visibility` 与 `updates.configuration` 从 `PROTECTED_APPLICATION_SETTING_DEFINITIONS` 移出，写成正规定义放进合适的定义文件（`generalSettingDefinitions.ts` 放更新配置；模型显示范围可能需要新建一个定义文件）。
2. 每项需要补：`schema`（zod）、`read()`、`write()`。read/write 要接**正式设置服务**，不能直接改 store（门禁禁止能力层 `setState`）。
3. 改写其余 5 项的 `description`，把理由说成技术事实并指明 `open_application_surface` 的替代路径。
4. 更新 4.2 建的 `settingsStore` 账本：对应这两项的动作从 gap 改为 property 绑定；`GAP_BASELINE` 相应降低。

### 模型显示范围的形态问题

「模型显示范围」是一个集合（哪些模型可见/收藏），不是一个标量。它能不能表达成单条设置属性？执行时判断：
- 若是「一组模型 id 的列表」→ 用 `ref_list` 或 `json` 值类型
- 若结构复杂 → 考虑注册成独立实体而不是设置项

结论写进执行记录。

## 执行记录

**关键发现：任务文档"两个 gap 对应这两项松绑设置"的假设不成立。** 读 4.2 建的
`settingsStoreLedger.ts` 发现，那 2 个 gap（`setProviderApiKey`/`setDownloadPresetPaths`）
分别对应 `security.provider_keys` 与 `storage.download_paths`——都是决定**保持只读**的那 5 项，
不是本任务要松绑的 `models.visibility`/`updates.configuration`。后两项从来就不是
`useSettingsStore` 的 store 动作（`models.visibility` 的真实数据在 `src/config/providers.ts`
的三个 localStorage 函数里，`updates.configuration` 在 `src/utils/updateConfig.ts` 里，都不经过
任何 zustand store），所以它们从建账那天起就不在 `GAP_BASELINE` 的统计范围内。**结论：
本任务不修改 `settingsStoreLedger.ts`，`GAP_BASELINE` 保持 8 不变**，验收标准第 7 条据此调整
措辞（核对清楚，而不是强行找一个能"降低"的数字）。

**`updates.configuration` 拆成两条标量设置**：`SettingValue` 类型是 `string | number | boolean`
的联合（`types.ts`），本注册表里目前没有任何一条设置是组合对象——包括 `downloadPresetPaths`
这种数组字段也只留在 protected 占位符里没有真正注册。`UpdateConfig` 有 4 个字段：`enabled`/
`frequency` 是用户与助手会独立调整的两个维度，写成 `updates.enabled`（boolean）与
`updates.check_frequency`（enum: startup/daily/weekly/never）两条 `storeSetting()`，读写接
`utils/updateConfig.ts` 现成的 `getUpdateConfig`/`setUpdateEnabled`/`setUpdateFrequency`；
`lastCheckTime` 是每次检查后自动写回的派生态，`ignoredVersions` 是通过"忽略此版本"按钮增长
的列表，两者都不是"配置"，且后者是数组、装不进 `SettingValue`，都不在本次松绑范围内。

**`models.visibility` 形态判断：结构复杂，注册成独立实体，不是设置属性。** 读
`src/config/providers.ts` 发现它其实是三个独立的 localStorage 集合——`hidden_providers`
（供应商级批量隐藏）、`hidden_types`（媒体类型级批量隐藏）、`hidden_models`（单个模型，
`${providerId}-${modelId}` 复合 key）——不是一个标量，也不是单一扁平列表，装不进
`SettingValue`，`ref_list` 也不贴切（它不是对一种实体的引用集合，是三种不同粒度的隐藏规则）。
按任务文档给出的"结构复杂 → 注册成独立实体"路径处理：`generation.model` 实体本来就已经注册
（`generationReflection.ts`），只是整体 `writeExclusion`（"模型目录由 src/models/** 静态定义
生成，不是用户数据"）。给它加一条新的可写属性 `generation.model.hidden`（boolean），只管
"这个模型自己是否被单独加入 hidden_models"，不处理供应商级/媒体类型级的批量隐藏——理由：
批量隐藏是一次操作影响一整批模型，语义上更接近"配置一条规则"而不是"改一个模型的属性"，
勉强塞进单模型的 `hidden` 字段语义会拧巴；而验收标准要验证的"隐藏某个模型"，per-model
`hidden` 已经完整覆盖。供应商级/类型级批量隐藏仍只能在设置页操作，记为已知的范围外能力，
不在本任务里扩展。

**generation.model 从整体 writeExclusion 迁移到统一字段定义**：新建
`generationModelFields.ts`，把原本硬编码在 `generationReflection.ts` 里的 5 条只读属性
（`provider_id`/`media_type`/`name`/`tags`/`parameter_schema_ref`）连同新的 `hidden` 一起
改写成 `ApplicationFieldDefinition[]`，`generationReflection.ts` 用 `fieldDescriptors`/
`fieldReadValues` 消费；新建 `generationModelMutationExecutor.ts`（`fieldWriterTable` 派生
可写属性集合，只有 `hidden` 一条）。这是本任务里唯一需要新建执行器的地方——task/result 两支
维持原样的整体 `writeExclusion`。

**revision 计算的连带修复**：读代码发现 `generation.model` 的读取路径此前一直用静态
`revision: 1` 占位（当时整支只读，没有写入所以从不校验）。现在 `hidden` 会变，若不修，
mutation 的 `expectedRevisions` 校验会用静态值和真实的可变状态对不上——写实现时先撞上了这个
坑（`REVISION_CONFLICT`），确认后在 `generationModelFields.ts` 加了 `modelsRevision` 计数器，
监听 Settings 面板写入模型可见性时已经在发的同一个 `modelVisibilityChanged` window 事件
（不新开广播通道），`generationReflection.ts` 的 `listEntities`/`readEntity` 都改用这个计数器。

**其余 5 项协议只读设置改写理由**：`security.provider_keys`/`llm.configuration` 强调"明文
密钥进模型上下文有泄露风险"；`storage.download_paths`/`storage.data_path`/
`downloads.quick_path` 强调"OS 文件选择器由系统弹出，不在渲染进程里，助手没有办法代替用户
点选"；每条都补一句用 `open_application_surface` 把用户带到对应分区。
