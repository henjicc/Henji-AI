## 当前情况

### 为什么这 11 个大概率是排除项

它们的共同特征：状态不进工程文件、不影响生成或导出的产物、关掉应用重开会恢复默认。这三条正是 `01-实施方案.md` 的取舍原则。

但有两处要特别小心：

**`generationHistoryFilterStore`（8 个动作）**：筛选条件不进持久化，但助手要查历史时**是不是真的不需要动它**？助手侧有 `list_generation_history` 能带条件查询——执行时确认它的输入 schema 覆盖了界面上全部 7 个筛选维度（关键词、供应商、模型、媒体类型、时间预设、起止日期）。**若覆盖不全，缺的那几维就是 gap，不是视图态。**`resetFilters` 是第 8 个动作，把前 7 项一次清空，按同样的取舍原则单独判断。

**`assistantUiStore`**：助手自己的面板状态。让助手改自己的面板位置/大小是否合理？`setApprovalMode`（审批模式）**明确不能给助手改**——那是用户对助手的授权开关，助手改它等于自我提权。这一条必须是 `user_only`，理由要写清楚。

### 排除 ≠ 不可见（重要）

`excluded` 表达的是**不可写**，不是**不可见**。视图态助手仍然要读得到——它得知道用户现在在看什么、开着哪个面板，这对多轮协作是必需的。

账本的 `excluded` 只管写入。若发现某个视图态助手**读**不到而应该读得到，那是另一类问题，记进执行记录（可能需要进 `contextProjection` 或 surface observation），不在本任务范围内改。

## 实施方案

与 4.2 相同的范式与流程。11 个 store 动作总数不大，可以按领域分 3 次提交：

1. 三维三个视图态 store（`cameraStageTool` / `Viewport` / `Session`）
2. 图片编辑两个 + 助手 + 弹窗两个（`imageEditorUi` / `imageEditorHandoff` / `assistantUi` / `alertDialog` / `largeUploadPolicy`）
3. 生成三个（`canvasGenerationProgress` / `generationTaskProgress` / `generationHistoryFilter`）

## 执行步骤

1. 对每个 store 运行时枚举动作名（临时测试打印，跑完删除）。
2. **先做 `generationHistoryFilterStore` 的覆盖核对**：读 `src/core/assistant/capabilities/builtinApplicationCapabilities.ts` 里 `list_generation_history` 的输入 schema，逐条对照界面上的 7 个筛选维度（`setKeyword` / `setProviderId` / `setModelId` / `setMediaType` / `setTimePreset` / `setStartDate` / `setEndDate`）。覆盖不全的维度登记为 gap。结论写进执行记录。
3. **确认 `assistantUiStore.setApprovalMode` 的处理**：登记为 `excluded('user_only')`，理由写明「审批模式是用户对助手的授权开关，助手改它等于自我提权」。
4. 逐个 store 建账，按 4.2 的相同范式（`Record<ActionName>` + `LEDGERS` 注册 + 白名单删条）。
5. 每建完一组跑 `npx tsc --noEmit && npm run check:assistant-capabilities`，单独提交。
6. 11 个全部完成后：
   - 确认 4.1 的白名单里 store 相关条目**全部清空**
   - 统计新增 gap，更新 `GAP_BASELINE` 与总览分布说明
7. 记录「视图态助手读不到但应该读得到」的发现（若有），供后续任务参考——**本任务不改**。
8. 运行 `npm run check:assistant-capabilities` 与 `npx vitest run src/features/assistant/applicationCapabilities`。

**生成三个 store（10 动作，6 个新 gap）**：`canvasGenerationProgressStore`/
`generationTaskProgressStore`（各 3 动作）都归 `derived`——生成进度是轮询回调实时写回的投影，
拆成独立 store 是为了避免高频写入触发整表/整画布重渲染（见两个文件头注释）。
`generationHistoryFilterStore`（8 动作）是本任务唯一有实质缺口的地方：核对
`list_generation_history` 的 `inputSchema`（`builtinApplicationCapabilities.ts`）发现只有
`mediaType`/`status`/`limit` 三个参数，界面上 7 个筛选维度只有 `mediaType` 能等价达成
（绑到 `capability: list_generation_history`）。`keyword`（关键词）、`providerId`（供应商）、
`modelId`（模型）、`timePreset`/`startDate`/`endDate`（时间范围）这 6 项助手完全没有对应查询
入口——按任务文档的明确要求，这不是视图态，如实登记为 6 个新 `gap`，理由写明需要扩展该能力的
`inputSchema` 才能补上，`plannedPhase` 标为"待排期"（不属于本 20 项任务清单里已规划的任何一
项）。`resetFilters` 只清空这 7 个筛选框的本地界面状态，不对应任何持久化的"当前查询条件"——
助手每次调用 `list_generation_history` 都是无状态的一次性查询，没有"重置"的对应物，归为
`view_state` 而非 `gap`。

**"视图态读不到但应该读得到"的发现**：本任务范围内没有发现这类问题——排查的 11 个 store 里，

读取路径（`observe_camera_stage_scene`、`get_canvas_node`、`list_generation_history` 等），
不需要额外读取这些本地 UI 状态本身。
