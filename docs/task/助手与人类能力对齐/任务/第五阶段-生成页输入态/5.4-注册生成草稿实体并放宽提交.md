# 5.4 注册生成草稿实体并放宽提交

## 任务状态

- 状态：实现完成；验证推迟到全部任务完成后统一进行（用户 2026-08-09 明确指示，见 5.3 补充说明）
- 所属阶段：第五阶段 · 生成页输入态
- 前置任务：5.3、1.3
- 关联任务：无
- 是否可以并行：否

## 任务目标

把 5.3 的生成草稿注册成反射实体 `generation.draft`，让助手能**像人一样逐步搭建生成输入**（写提示词 → 选模型 → 调参数 → 上传媒体 → 提交），而不是只能一次性提交。

同时给 `generationDraftStore` 建账，把 `generation` 从 `ASSISTANT_BLIND_FEATURES` 白名单里删除。

**零新增工具**：走通用动词写属性，提交复用现有的 `create_visible_generation_task`。

## 当前情况

### 5.3 完成后的状态

`src/features/generation/store/generationDraftStore.ts` 持有 `GenerationDraft`，参数联动已接入 reducer。生成页通过薄适配层消费。

### generation 领域现有的三个实体全是只读

`src/features/generation/application/generationReflection.ts`：

| 实体 | writeExclusion |
|---|---|
| `generation.model` | 「模型目录由 src/models/** 的静态定义生成，不是用户数据。」 |
| `generation.task` | 「生成任务与结果由生成链路创建和维护；发起任务属算法型操作，用 create_visible_generation_task。」 |
| `generation.result` | 同上 |

**这三条排除理由是对的，一个字都不要改。** 本任务新增的是**第四个实体** `generation.draft`——它是「用户正在搭建的输入」，与「已提交的任务」是两回事。

### 现有提交能力

- `prepare_generation_task`：准备任务（不提交）
- `create_visible_generation_task`：创建可见的生成任务

定义在 `src/core/assistant/capabilities/generationApplicationCapabilities.ts`。

它们目前要求把全部输入作为参数一次传入。放宽后：**不传参数时用当前 draft**。

### 统一字段定义就位（1.3）

本任务的属性注册要用 1.3 的统一字段定义，一处声明派生四样，不要退回四处登记。

## 实施方案

### 1. 注册 `generation.draft` 实体

单例实体（一个应用只有一份草稿；若 5.3 选了方案乙的多实例分片，则 ref id 为 scopeId）。

属性按 draft 字段映射，注意值类型选择：

| draft 字段 | 属性值类型 | 备注 |
|---|---|---|
| `promptDocument` | `string` 或 `json` | 提示词文档结构复杂，可能需要暴露成纯文本 + 单独的媒体绑定属性。**执行时判断** |
| `selectedProvider` / `selectedModel` | `ref` 指向 `generation.model` | 复用现有模型实体 |
| 上传的图/视/音 | `ref_list` 指向 `asset` 或 `string` 列表 | **执行时判断**：上传的是本地路径还是素材引用 |
| 视频裁剪起止 | `number` | 直接映射 |
| 模型筛选四项 | `string` / `enum` | 视图态还是真状态？**按取舍原则判断** |

**判断要点**：模型筛选（`modelFilterProvider` / `modelFilterType` / `modelFilterFunction` / `favoriteModels`）只影响用户在选择器里看到哪些模型，不影响生成结果。按取舍原则大概率是 `view_state`，但 `favoriteModels`（收藏）会持久化——它可能属于设置而不是草稿。执行时逐条判断。

### 2. 写入执行器

`GenerationDraftMutationExecutor`，写入表复用 5.1 的 `applyGenerationDraftPatch` 与 5.2 的 `reconcileGenerationParams`。**不重写任何 reducer 逻辑。**

### 3. 放宽提交

`prepare_generation_task` / `create_visible_generation_task` 的输入 schema 里，把必填输入改为可选；缺省时从 `generationDraftStore` 读当前 draft。

**注意**：这是放宽而不是改变，现有调用方式必须继续工作。

### 4. 建账

新建生成草稿 store 的账本，从白名单删 `generation`。

## 执行记录

**关键澄清：模型参数不在 `generation.draft` 范围内，验收标准第 4 条"调参数"要按此重新理解。**
读代码确认 `GenerationDraft`（5.1 已定稿的 18 项字段清单）本来就不包含模型参数——参数由
`useModelParams`/`useModelState` 单独管理，且这是**组件局部 React 状态**（`useState` 加
`modelId` 参数化），不是任何全局可寻址的 store，`MediaGenerator/index.tsx` 之外没有任何代码
能读到"用户当前在参数面板里填了什么"。这意味着"助手调参数"这件事在草稿层面无法表达为
"读写 generation.draft 的某个字段"——它本来就不是草稿的一部分。5.2 已经把
`reconcileGenerationParams` 接进了 `useModelParams.setParam`（提交 `24a2206`，测试见
`useModelParams.test.tsx`），这就是"参数写入触发联动修正"这条验收标准要证明的事，本任务
不需要为此新增测试。助手若要指定参数，走 `create_visible_generation_task` 现有的 `params`
参数（本来就是可选的，未改动）——这与"不传参数时用当前 draft"是两件事："不传"指的是
`modelId`/`prompt`/`mediaType`/`params` 这四个顶层参数各自独立地在省略时从草稿取默认值，
不是把模型参数也塞进草稿。

**18 个字段的归类结论**（详见 `generationDraftFields.ts` 顶部注释，这里摘要）：

| draft 字段 | 归类 | 说明 |
|---|---|---|
| `promptDocument` | 折叠为可写属性 `prompt_text`（字符串） | 复用 `setLegacyInput` 的解析逻辑，不暴露 `PromptDocumentV1` 原始 json——旧版纯文本带 `@图N` 内联引用，助手写起来更简单，且是已经完整存在、测试过的路径 |
| `selectedProvider` | 不单独暴露 | 由 `selected_model` 反查得出，两者从来都是成对写入 |
| `selectedModel` | 折叠为可写属性 `selected_model`（ref → generation.model） | 写入时用 `registry.getModel(id)` 反查 provider |
| `uploadedPromptImages` + `uploadedFilePaths` | 折叠为可写属性 `uploaded_images`（url 数组） | 复用 `reconcileMediaGeneratorPromptImages` 保留 resourceId |
| `uploadedVideos` + `uploadedVideoFilePaths` | 折叠为可写属性 `uploaded_videos` | 同一数组同时写两个原字段 |
| `uploadedAudios` + `uploadedAudioFilePaths` | 折叠为可写属性 `uploaded_audios` | 同上 |
| `uploadedVideoFiles`（浏览器 File 对象数组） | 不暴露 | 不可序列化，且与 `uploadedVideoFilePaths` 信息冗余 |
| `fileOrder` | 不暴露（view_state） | 只是上传托盘的展示排列，不改变各类型内部的语义顺序 |
| `uploadedVideoDuration` | 只读 | 视频真实时长是上传文件本身的元数据，助手不能凭空声明一个不匹配文件的时长 |
| `uploadedVideoTrimStart`/`uploadedVideoTrimEnd` | 可写属性 `uploaded_video_trim_start`/`uploaded_video_trim_end` | 直接映射，影响提交内容 |
| `modelFilterProvider`/`modelFilterType`/`modelFilterFunction` | 不暴露（view_state） | 只影响模型选择器 UI 里看到哪些模型，不影响生成结果；助手搜模型走 `search_models` 自己的筛选参数 |
| `favoriteModels` | 不暴露（view_state，非设置） | 不影响生成结果，是个人收藏偏好；这个 store 没有持久化（不带 zustand persist），实际行为和其他草稿字段一样是会话级状态，语义上更接近设置而非草稿内容，但由于没有真的持久化，暂不移到设置域，记为已知范围外 |

7 条可写属性 + 1 条只读属性，共 8 条属性注册在 `generation.draft` 上。

**账本设计**：`generationDraftStore` 只有 6 个动作（`patch`/`patchField`/`patchUploadedImages`/
`setLegacyInput`/`loadPromptCarrier`/`reset`），不是 18 个——账本 account 的是 store 自己的
方法，跟 4.2/4.3 建的其它账本同一个口径。`patchField` 是通用单字段写入原语，一个动作对应
5 条已注册属性（`selected_model`/`uploaded_videos`/`uploaded_audios`/两个 trim），这是
"等价能力"先例的延续（2.2 的 `reorderShot` 绑到 `time` 属性是同一类判断）。`patch` 与 `reset`
在界面上都没有对应的按钮触发（`patch` 是 5.4 新写的执行器专用批量提交原语，`reset` 是 5.3
建 store 时提供的工具方法，未接进任何 UI），归为 `excluded/internal`。零新增 gap，
`GAP_BASELINE` 不变（仍为 8）。

**电路问题**：`generationDraftFields.ts` 最初直接 `import { GENERATION_ENTITY_TYPES } from
'./generationReflection'` 来引用 `generation.model` 的实体 kind 字符串，而 `generationReflection.ts`
反过来要 `import { GENERATION_DRAFT_FIELDS } from './generationDraftFields'` 来注册
`generation.draft` 实体——两边循环 import，导致 `generationDraftFields.ts` 顶层的
`GENERATION_DRAFT_FIELDS` 数组字面量在模块求值阶段构造时读到还没初始化完的
`GENERATION_ENTITY_TYPES`（报 `Cannot read properties of undefined (reading 'model')`）。
改成在 `generationDraftFields.ts` 里直接写字面量常量 `'generation.model'`（不 import），
解开循环——`generation.model` 是稳定的实体 id 字符串，直接写字面量不会真的产生耦合问题。

**provider 实现选择**：`generation.draft` 是单例实体，结构上与 `model`/`task`/`result` 三支的
"目录型多实例"完全不同（不能列表分页、不需要按 id 搜索）。没有塞进已有的
`GenerationReflectionProvider`（那样只会把已经按 entityType 分支的 ternary 再拉长一路，参考
4.4 时就已经在这个类里踩过一次），单独写了 `GenerationDraftReflectionProvider`，与
`settingsReflection.ts` 的 `SettingsReflectionProvider`（单例 `settings.registry`）是同一类写法。

**revision 机制**：`generationDraftStore` 新增 `revision: number` 字段，每次 draft 真的变化
（不是引用相等的空 patch）就 `+1`，与 4.4 给 `generation.model` 加 `modelsRevision` 计数器
是同一类修复——反射层的 `readEntity`/`listEntities` 与 mutation 执行器的
`resultingRevisions`/`expectedRevisions` 都读这同一个计数器，保证乐观并发校验真的有意义。

**放宽提交**：`prepare_generation_task`/`create_visible_generation_task` 的 `modelId`/
`prompt`/`mediaType` 全部改成可选，新写的 `resolveGenerationInput()`（
`registerGenerationCapabilityHandlers.ts`）逐项判断——省略 `modelId` 用
`draft.selectedModel`；省略 `prompt` 用草稿提示词的旧版文本序列化（与 `prompt_text` 属性的
读取逻辑一致）；省略 `mediaType` 从解析出的 `modelId` 反查 `registry.getModel(...)?.meta.type`；
**`params` 只在整体省略时才用草稿的已上传媒体路径兜底，一旦显式传入就原样使用、不与草稿
合并**——这是保证"传参数时仍按传入值走"这条兼容性要求成立的关键：老代码一直显式传四项，
新的默认值分支永远不会命中它们，不会有任何行为变化。

**断牙验证**：临时注释掉 `generationDraftFields.ts` 里 `selected_model` 字段的 `writer`
（只留 `read`），`storeActionCoverage.test.ts` 的"账上写的助手入口真的存在，而且真的写得了"
断言报 `patchField → generation.draft.selected_model（没有任何执行器能写这些属性）`，
符合预期；恢复后测试变绿。
