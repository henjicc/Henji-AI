# 5.4 注册生成草稿实体并放宽提交

## 任务状态

- 状态：待开始
- 所属阶段：第五阶段 · 生成页输入态
- 前置任务：5.3、1.3
- 关联任务：无
- 是否可以并行：否

## 任务目标

把 5.3 的生成草稿注册成反射实体 `generation.draft`，让助手能**像人一样逐步搭建生成输入**（写提示词 → 选模型 → 调参数 → 上传媒体 → 提交），而不是只能一次性提交。

同时给 `generationDraftStore` 建账，把 `generation` 从 `ASSISTANT_BLIND_FEATURES` 白名单里删除。

**零新增工具**：走通用动词写属性，提交复用现有的 `create_visible_generation_task`。

## 当前情况

### 5.3 完成后的状态

`src/features/generation/store/generationDraftStore.ts` 持有 `GenerationDraft`，参数联动已接入 reducer。生成页通过薄适配层消费。

### generation 领域现有的三个实体全是只读

`src/features/generation/application/generationReflection.ts`：

| 实体 | writeExclusion |
|---|---|
| `generation.model` | 「模型目录由 src/models/** 的静态定义生成，不是用户数据。」 |
| `generation.task` | 「生成任务与结果由生成链路创建和维护；发起任务属算法型操作，用 create_visible_generation_task。」 |
| `generation.result` | 同上 |

**这三条排除理由是对的，一个字都不要改。** 本任务新增的是**第四个实体** `generation.draft`——它是「用户正在搭建的输入」，与「已提交的任务」是两回事。

### 现有提交能力

- `prepare_generation_task`：准备任务（不提交）
- `create_visible_generation_task`：创建可见的生成任务

定义在 `src/core/assistant/capabilities/generationApplicationCapabilities.ts`。

它们目前要求把全部输入作为参数一次传入。放宽后：**不传参数时用当前 draft**。

### 统一字段定义就位（1.3）

本任务的属性注册要用 1.3 的统一字段定义，一处声明派生四样，不要退回四处登记。

## 实施方案

### 1. 注册 `generation.draft` 实体

单例实体（一个应用只有一份草稿；若 5.3 选了方案乙的多实例分片，则 ref id 为 scopeId）。

属性按 draft 字段映射，注意值类型选择：

| draft 字段 | 属性值类型 | 备注 |
|---|---|---|
| `promptDocument` | `string` 或 `json` | 提示词文档结构复杂，可能需要暴露成纯文本 + 单独的媒体绑定属性。**执行时判断** |
| `selectedProvider` / `selectedModel` | `ref` 指向 `generation.model` | 复用现有模型实体 |
| 上传的图/视/音 | `ref_list` 指向 `asset` 或 `string` 列表 | **执行时判断**：上传的是本地路径还是素材引用 |
| 视频裁剪起止 | `number` | 直接映射 |
| 模型筛选四项 | `string` / `enum` | 视图态还是真状态？**按取舍原则判断** |

**判断要点**：模型筛选（`modelFilterProvider` / `modelFilterType` / `modelFilterFunction` / `favoriteModels`）只影响用户在选择器里看到哪些模型，不影响生成结果。按取舍原则大概率是 `view_state`，但 `favoriteModels`（收藏）会持久化——它可能属于设置而不是草稿。执行时逐条判断。

### 2. 写入执行器

`GenerationDraftMutationExecutor`，写入表复用 5.1 的 `applyGenerationDraftPatch` 与 5.2 的 `reconcileGenerationParams`。**不重写任何 reducer 逻辑。**

### 3. 放宽提交

`prepare_generation_task` / `create_visible_generation_task` 的输入 schema 里，把必填输入改为可选；缺省时从 `generationDraftStore` 读当前 draft。

**注意**：这是放宽而不是改变，现有调用方式必须继续工作。

### 4. 建账

新建生成草稿 store 的账本，从白名单删 `generation`。

## 执行步骤

1. 读 5.3 产出的 `generationDraftStore.ts`，确认 draft 的最终字段结构。
2. **逐条判断 18 个字段的归类**：哪些是可写属性、哪些是视图态、哪些属于设置。结论表写进执行记录。特别处理：
   - `promptDocument` 的暴露形态（纯文本 vs json）
   - 上传媒体的引用形态（本地路径 vs 素材引用）
   - `favoriteModels` 的归属（草稿 vs 设置）
3. 用 1.3 的统一字段定义新建 `src/features/generation/application/generationDraftFields.ts`。
4. 在 `generationReflection.ts` 注册 `generation.draft` 实体（**不动现有三个实体的 writeExclusion**）。
5. 新建 `GenerationDraftMutationExecutor`，写入表由 Fields 派生；在 `applicationControlRegistry.ts` 注册。
6. 放宽 `prepare_generation_task` / `create_visible_generation_task`：输入改可选，缺省读 draft。
7. 新建 `src/features/generation/application/generationDraftStoreLedger.ts`，注册进 `storeActionCoverage.test.ts` 的 `LEDGERS`。
8. 从 `scripts/check-assistant-capabilities.cjs` 的白名单删 `generation`。
9. 新建测试：
   - 助手写提示词、换模型、调参数，draft 真的变了
   - 参数写入触发联动修正（写一个非法组合，确认被拉回合法值）
   - 不传参数调用 `create_visible_generation_task`，用的是当前 draft
   - 传参数调用仍按传入的参数走（兼容性）
10. **断牙验证**：把写入表里的 `selectedModel` 一条删掉，确认 `storeActionCoverage` 报对应 store 动作没有绑定。跑完恢复。
11. 运行 `npx tsc --noEmit && npm run lint && npm run check:colors && npm run check:assistant-capabilities`。
12. 运行 `npx electron-vite build`（动到 core 与能力定义）。
13. 运行 `npm test` 全量。
14. **实机验证交给用户**：对助手说「把提示词改成 X，模型换成 Y，把尺寸调成 Z，然后生成」，确认它逐步改完并成功提交，且生成页上能看到这些改动。
