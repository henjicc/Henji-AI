# 5.2 参数联动提纯为纯函数

## 任务状态

- 状态：已完成（等待用户实机验证反馈）
- 所属阶段：第五阶段 · 生成页输入态
- 前置任务：5.1
- 关联任务：5.3
- 是否可以并行：否

## 任务目标

把模型参数的**联动逻辑**（某个参数的可选项随另一个参数变化）从 React 层提取成纯函数。

**这一步是整个第五阶段最容易出错、也最不能跳过的一步。** 不做它，5.3 完成后助手走 store 写入会**绕过联动**——用户看到界面上显示着一个非法的参数组合，而界面不提示任何错误。

## 当前情况

### 联动现在在哪

`src/components/MediaGenerator/state/useModelState.ts` 暴露：

- `setParam` / `setParams` / `resetParam` / `resetParams`
- `validateParam`
- **`getFilteredOptions`** ← 联动的核心

它把参数状态委托给 `useModelParams(modelId)`（执行时定位确切文件）。

### 联动是什么

模型 schema（`src/models/**.model.ts`）里，某些参数的可选值依赖其他参数的当前值。例如某个视频模型选了特定分辨率后，可用的时长选项会变。`getFilteredOptions` 就是算这个的。

### 为什么它必须先提纯

链路对比：

```
人在界面上改参数
  → setParam → React state → 重渲染 → getFilteredOptions 重算 → 界面显示合法选项

助手走 store 写入（5.3 之后）
  → 直接改 draft.params → ？？？
```

如果 `getFilteredOptions` 留在 React 层，助手这条路径**根本不经过它**。助手可以写入一个 schema 上非法的组合，界面照常显示，直到提交时才在供应商那边报错——或者更糟，供应商接受了但生成结果不对。

### 相关文件

- `src/components/MediaGenerator/state/useModelState.ts`
- `useModelParams` 的实现文件（执行时定位）
- `src/models/**.model.ts`：参数 schema 定义
- 参数 schema 的类型契约（执行时定位，可能在 `src/core/models/` 或 `src/models/types.ts`）

## 实施方案

新建 `src/features/generation/domain/generationParams.ts`，提供纯函数：

```ts
export function resolveGenerationParamOptions(
  schema: ModelParameterSchema,
  currentParams: Record<string, unknown>,
): Record<string, ParamOption[]>

export function validateGenerationParams(
  schema: ModelParameterSchema,
  params: Record<string, unknown>,
): { valid: boolean; issues: Array<{ paramId: string; reason: string }> }

/** 参数变更后把因联动而非法的其他参数拉回合法值 */
export function reconcileGenerationParams(
  schema: ModelParameterSchema,
  params: Record<string, unknown>,
): Record<string, unknown>
```

`useModelState` / `useModelParams` 内部改为调用这些纯函数，对外 API 不变。

**`reconcileGenerationParams` 是关键**：5.3 之后，store 的 params reducer 要在每次写入后跑它，这样助手和人走同一条联动路径。本任务只提供函数，5.3 负责接进 reducer。

### 快照测试策略

联动逻辑没有现成测试，风险高。提取前后必须证明等价：

1. 挑**联动最复杂的 2–3 个模型**（执行时从 `src/models/` 里找参数依赖最多的）。
2. 提取**前**，用现有 React 实现跑一遍全组合（或有代表性的组合），把 `getFilteredOptions` 的输出存成快照。
3. 提取**后**，用纯函数跑同样输入，比对快照完全一致。

快照测试可以在提取完成后保留为回归测试。

## 执行记录

**关键发现：联动逻辑早就是纯函数，本任务不是"从 React 里挖出来"。** 读
`src/hooks/useModelParams.ts` 发现它只是一层薄封装：真正的联动算法在
`src/core/linkage/LinkageEngine.ts`（`execute`/`getFilteredOptions`/`getFilteredRange`/
`isParamDisabled`/`isParamHidden`，纯类，不 import React），参数默认值提取与校验在
`src/hooks/utils/defaultExtractor.ts`（`extractDefaults`/`validateParamValue`），嵌套路径
读写在 `src/hooks/utils/paramUtils.ts`——三个文件全都没有 React 依赖，也早就是可以脱离
Hook 独立调用的纯逻辑。任务文档"执行时定位确切文件"的调研本身没问题，但它假设的前提
（联动逻辑困在 React 层）不成立。本任务因此不是重写算法，而是给这些已存在的纯函数搭一层
`src/features/generation/domain/generationParams.ts` 的稳定入口，并把 `useModelParams.ts`
改成调用这层入口而不是直接 `new LinkageEngine(...)`——这样 5.3/5.4 的 store 写入路径与
`useModelParams` 共用同一个调用点，不会出现"两处各自实现一遍联动"的分叉。

**签名与任务文档的出入**：文档给的三个函数签名只有 `schema` 参数，没有 `linkages`。但
`LinkageEngine` 的联动规则（`linkages`）与参数定义（`schema`）是模型定义里两个独立字段
（`registry.getSchema(id)` vs. `registry.getModel(id).linkages`），算法离不开 `linkages`。
三个函数的签名都补上了 `linkages: Linkage[]` 参数，不是可选项。`reconcileGenerationParams`
额外加了一个可选的 `changedKeys` 参数：明确知道触发源时（如 `setParam(key, value)`）精确
传入，省略时对 `params` 里出现过的每个 key 各跑一遍 `LinkageEngine.execute`（对没有匹配任何
规则的 key 是无操作，多跑不会有副作用）——这是留给 5.3 之后"整体状态可能来自任意来源、不
知道具体触发源"的场景兜底用的。

**挑选的模型与联动关系**（按 `linkages` 数组里 `trigger` 条目数实测排序，前三）：
- `ppio-kling-o1`（5 条，全部 `autoSwitch`）：图生视频模式（`ppioKlingO1Mode`）与画幅比
  （`ppioKlingO1AspectRatio`）互相联动——上传 2 张图自动切到首尾帧模式，切模式时画幅比在
  `smart` 与 `16:9` 之间自动切换，条件函数依赖 `countUploadedImages`/`hasUploadedVideo`
  这类跨三个媒体键名统一判断"是否已上传"的共享工具（`src/models/shared/mediaPresence.ts`）。
- `ppio-vidu-q3`（4 条：2 条 `autoSwitch` + 2 条 `hide`）：模式随图片数量自动切换（2 张图→
  首尾帧，减到 ≤1 张→切回文生视频/图生视频）；另外 2 条 `hide` 联动只影响可见性，不改参数
  值，不在 `reconcile` 覆盖范围内（`hide`/`disable`/`filterRange` 三种效果都不通过
  `execute()` 修改 params，而是分别在渲染时/`isParamHidden`/`isParamDisabled`/
  `getFilteredRange` 里单独查询——这三个函数不在本任务的三个签名之内，记为已知范围外，
  真要用时可以照 `resolveGenerationParamOptions` 的样式加）。
- `ppio-seedance-v1.5-pro`（3 条：2 条 `autoSwitch` + 1 条 `filterOptions`）：上传图片时
  画幅比自动切到 `adaptive`；`filterOptions` 联动会把 `adaptive` 选项挪到列表最前面（不是
  "从无到有"——`adaptive` 本来就是 schema 里 7 个基础选项之一，第一次核对这一点时测试断言
  写错了，实测确认后改成校验选项顺序而不是"选项是否存在"）。

**验证策略：没有采用"提取前后快照比对"，改成对照真实模型 schema 的行为断言测试，理由见下。**
`useModelParams.ts` 改前的 `getFilteredOptions`/`setParam` 本来就是直接调用
`LinkageEngine` 的薄封装——本任务没有重写算法，只是换了个调用入口，所以"提取前 vs.
提取后"实际上是同一段 `LinkageEngine` 代码对自己求快照，除了确认"没有手滑改错参数顺序"
之外提供不了额外的正确性信心。改用 `loadRealModelsIntoRegistry()` 把仓库里**真实**的
生产模型定义（连同它们的 `linkages`）装进注册表，对上面三个模型的代表性参数组合写具体的
行为断言（例如"上传 2 张图后模式变成 start-end-frame"），而不是把某次运行的输出原样存成
快照——这样测试会跟着模型 schema 一起演进：以后谁改了这三个模型的联动规则，测试会用具体
错在哪条断言告诉你，而不是一句"快照不匹配"，且不会诱使人在没看懂原因的情况下直接用
`--update` 覆盖快照。8 个用例覆盖 `autoSwitch`（含"删光图片后归位"这类条件反向的分支）、
`filterOptions`、`validateGenerationParams` 的非法值检测、`changedKeys` 省略与精确指定的
等价性、无联动模型的直通行为。

**`useModelParams.ts` 的改动**：删掉 `useMemo` 建的 `linkageEngine`（不再需要，
`generationParams.ts` 内部按需 `new LinkageEngine`），改成 `const linkages =
useMemo(() => model?.linkages ?? [], [model])`；`setParam` 内联动执行改调用
`reconcileGenerationParams(schema, newParams, linkages, [key])`；`getFilteredOptions`
改成先 `useMemo` 一次性算出全部 dropdown/radio 参数的选项表（`resolveGenerationParamOptions`），
按 `paramId` 查表返回——原来的"没有联动引擎时手写 fallback 逻辑"整段删掉了，因为
`LinkageEngine.getFilteredOptions` 在 `linkages` 为空数组时本来就会原样返回
`schema` 里的 `options`，两条分支在结果上完全等价，保留 fallback 只是重复代码。
