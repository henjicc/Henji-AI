# 5.3 生成草稿 store 化

## 任务状态

- 状态：实现完成，等待用户实机验证后正式标记完成（任务文档明确要求"用户确认无异常后才能标记完成"）
- 所属阶段：第五阶段 · 生成页输入态
- 前置任务：5.2
- 关联任务：5.4
- 是否可以并行：否

## 任务目标

把 5.1 抽出的 `GenerationDraft` 从 React 局部态搬到 Zustand store，`useUIState` 退化成薄适配层，**对外 API 仍然一字不改**。

**这是第五阶段唯一有真实回归风险的一步**（局部态 → 全局态，多实例语义变了）。前后两步都是纯提取，只有这一步改变了状态的生命周期。

## 当前情况

### 5.1 完成后的状态

`useUIState` 内部已是单个 `useState<GenerationDraft>`，对外 18 组 `xxx` / `setXxx`。4 个消费方零改动。

### 5.2 完成后的状态

参数联动已是纯函数（`resolveGenerationParamOptions` / `validateGenerationParams` / `reconcileGenerationParams`）。

### 多实例语义（必须先确认）

`useUIState` 是 hook，理论上每次调用都是独立实例。改成全局 store 后**全应用只有一份**。

已知的挂载情况：
- `src/workspaces/GenerationWorkspace.tsx` 挂载 `MediaGenerator`
- `src/features/canvas/params/NodeModelParamsControls.tsx` 也引用了 MediaGenerator 相关组件

**执行时必须确认**：画布节点里的参数控件是否共用 `useUIState`？若共用，改成全局 store 会让画布节点和生成页**互相串状态**——这是本任务最大的风险点。

若确认共用，方案要调整：store 按实例 key 分片（如 `draftsByScope`），而不是单一全局 draft。

## 实施方案

### 前提确认后二选一

**方案 甲（单实例确认无误）**：

```ts
// src/features/generation/store/generationDraftStore.ts
export const useGenerationDraftStore = create<{
  draft: GenerationDraft
  patch: (patch: Partial<GenerationDraft>) => void
  reset: () => void
}>(...)
```

`useUIState` 退化成：

```ts
const draft = useGenerationDraftStore(s => s.draft)
const patch = useGenerationDraftStore(s => s.patch)
const setSelectedModel = useCallback((v) => patch({ selectedModel: v }), [patch])
// …18 组，对外签名不变
```

**方案 乙（存在多实例）**：store 里存 `Record<scopeId, GenerationDraft>`，`useUIState(scopeId)` 取对应分片。对外 API 仍不变（多一个可选参数，默认值兼容现有调用）。

### 参数联动接进 reducer

store 的 params 写入路径要调用 5.2 的 `reconcileGenerationParams`，这样**助手和人走同一条联动路径**——这是 5.2 存在的全部意义。

### 选择器粒度

Zustand 的选择器要精确到字段（`s => s.draft.selectedModel`），不要整个 draft，否则任何字段变化都会让所有消费组件重渲染。生成页组件多，这会影响输入流畅度。

## 执行记录

**多实例情况确认（决定选方案甲）**：`grep -rn "useUIState(" src` 显示全仓库只有一处调用——
`src/components/MediaGenerator/index.tsx`。读 `src/features/canvas/params/
NodeModelParamsControls.tsx` 确认它不调用 `useUIState`/`useModelState`，只用画布自己的
`useNodeModelParams`（另一个独立 hook，管理画布节点自己的参数，与生成页的 `GenerationDraft`
完全无关）；它引入的 `ParameterPanel`（`MediaGenerator/components/ParameterPanel.tsx`）也
确认不调用 `useUIState`/`useModelState`。`<MediaGenerator>` 组件本身也只在
`GenerationWorkspace.tsx` 一处被渲染。**结论：`useUIState` 的 `GenerationDraft` 不存在多实例
场景，走方案甲（单一全局 draft，不按 scope 分片）。**

**"参数写入路径接 reconcileGenerationParams" 的归属澄清**：任务文档这条要求写在 5.3 里，但
`GenerationDraft`（5.1 的范围：`promptDocument`/`selectedProvider`/`selectedModel`/上传/
筛选，共 18 项）本来就**不包含**模型参数（`params`）——模型参数由 `useModelParams`/
`useModelState` 单独管理，是完全独立的一份状态。任务文档"涉及内容"一节自己也留了活口
（"若参数不在 draft 里则调整归属"）。核实后确认：`useModelParams.setParam` 已经在 5.2 里
接上了 `reconcileGenerationParams(schema, newParams, linkages, [key])`（提交 `24a2206`），
与 `GenerationDraft` 是否 store 化无关，本任务不需要为此再改 `useModelState.ts`。

**方案甲实现**：新建 `src/features/generation/store/generationDraftStore.ts`
（`useGenerationDraftStore`），`draft` 字段是唯一状态源，`patch`/`patchField`/
`patchUploadedImages`/`setLegacyInput`/`loadPromptCarrier`/`reset` 六个 action：
- `patchField` 复刻 5.1 的 `usePatchedDraftField` 语义（完整支持直接值/更新函数两种调用
  形式，新旧值引用相等时不产生新 draft），只是把 `setDraft` 换成 zustand 的 `set()`——
  `set()` 的更新函数天然读到的就是最新 state，不存在 React 闭包过期的问题，反而比
  5.1 版本更简单。
- `patchUploadedImages`/`setLegacyInput`/`loadPromptCarrier` 原样从 `useUIState.ts` 搬进
  store，内部逻辑逐字保留（继续调用既有的 `reconcileMediaGeneratorPromptImages`/
  `createMediaGeneratorPromptReferences`/`resolveMediaGeneratorPromptCarrier`，未重写）。

`useUIState.ts` 退化为薄适配层：18 个字段全部用 `useGenerationDraftStore(state =>
state.draft.xxx)` 精确到字段的选择器订阅（不是 `state => state.draft` 整体订阅），
setter 通过 `usePatchedField(key)` 包一层 `useCallback` 调用 `store.patchField`。4 个派生
`useMemo`（`uploadedImages`/`promptReferences`/`input`/`promptMediaBindings`）保留在
`useUIState.ts` 里，依赖数组不变（继续依赖具体字段，不依赖整个 draft）。对外 18 组
`xxx`/`setXxx` 的类型签名与调用方式逐一核对与 5.1 完全一致——`npx tsc --noEmit` 通过即是
"4 个消费方零改动"的证据。

**已识别但风险可控的行为差异（初始化时机）**：5.1 版本里 `createEmptyGenerationDraft` 通过
`useState(factory)` 的惰性初始化，在 `MediaGenerator` 组件**首次渲染时**才执行（此时模型
注册表大概率已经加载完）。store 化后 `createEmptyGenerationDraft()` 在
`generationDraftStore.ts` 模块被首次 import 时就执行一次——如果这个时间点早于模型注册表
填充完成，算出来的默认 `selectedProvider`/`selectedModel` 会是空字符串。**这不会导致用户
能感知到的问题**：`useUIState.ts` 里那个自动纠正的 `useEffect`（"供应商列表变化时选中项
失效就回落到第一个可用模型"）本来就会在模型加载完成后把空字符串纠正成第一个可用模型——
这条 effect 5.1/5.3 都没有改动过，行为兜底路径没变，只是触发它的初始条件从"几乎不可能"
变成"理论上可能，但同一个 effect 兜住了"。这一点值得在实机验证时留意：**打开生成页时
默认模型是否正确选中**，若发现空白或未选中，说明这个时机差异触发了，需要回来加固
（比如把 store 的初始 draft 建立延后到 hook 内的 `useEffect`）。
