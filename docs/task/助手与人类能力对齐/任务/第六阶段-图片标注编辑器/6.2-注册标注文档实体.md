# 6.2 注册标注文档实体

## 任务状态

- 状态：实现完成；实机验证推迟到全部任务完成后统一进行（用户已明确指示，见 6.1 同款备注）
- 所属阶段：第六阶段 · 图片标注编辑器（本任务完成后，第六阶段与全部 20 项任务实现均完成）
- 前置任务：6.1、1.3
- 关联任务：无
- 是否可以并行：否

## 任务目标

把 6.1 提升出来的标注文档注册成反射实体，让助手能读到当前编辑的标注、能增删改标注、能裁剪旋转、能导出。

**把 `imageMark` 从 `ASSISTANT_BLIND_FEATURES` 白名单里删除**——这是全项目最后一个全域失明的领域。

配合 6.1，本任务完成后白名单里应当只剩下有正当理由的条目（如 `logs`），距离「白名单清空」的最终验收只差那几条的重新评估。

## 当前情况

### 6.1 完成后的状态

- `src/features/imageMark/domain/markDocument.ts`：文档类型与纯函数 reducer
- `src/features/imageMark/store/markDocumentStore.ts`：按 sessionId 分片
- 三个宿主零改动，共用同一份领域层

6.1 的执行记录里应当已经写清楚：**标注是否为带 id 的数组、裁剪旋转的归属**。本任务的实体设计直接依赖这个结论。

### 已有的相邻领域：image_edit

`src/features/imageEdit/application/imageEditReflection.ts` 注册了三个实体，全部只读：

```
image_edit.session / image_edit.document / image_edit.layer
writeExclusion: '图片编辑预览是不可变快照，改动请用完整 operations 列表生成新预览。'
```

**注意区分**：`imageEdit` 是扩散类图片编辑（生成式），`imageMark` 是标注/打码/裁剪（几何类）。两者是不同的东西，不要混。imageEdit 的「不可变快照」理由对它自己成立，**不适用于 imageMark**——标注文档是可变的用户数据。

### 现有的相关能力

- `open_image_editor_with_source`：把某张图交给编辑器打开
- `create_image_edit_preview` / `create_image_edit_preview_from_ref` / `commit_image_edit`：这些是 imageEdit 的，不是 imageMark

所以 imageMark 侧只有「打开」这一个入口，打开之后助手什么都做不了。

## 实施方案

### 实体设计（依据 6.1 的结论）

预期形态（**执行时按 6.1 的实际结论调整**）：

| 实体 | 说明 | collectionWrite |
|---|---|---|
| `image_mark.document` | 一次编辑会话的标注文档（单例 per session） | 无 |
| `image_mark.annotation` | 单条标注（画笔/矩形/箭头/文字/打码） | **creatable + removable** |

`image_mark.document` 的属性：源图引用、尺寸、裁剪矩形、旋转/镜像状态、标注引用列表。
`image_mark.annotation` 的属性：类型（只读，创建后不可变）、几何（位置/尺寸/路径）、样式（颜色/粗细）、文字内容。

**若 6.1 的结论是「标注不是带 id 的数组」**，则集合写入无从谈起，需要改设计——那种情况下要在执行记录里说明，并考虑把整份标注表达成一条 `json` 属性（次优，但比全域失明好）。

### 属性注册用统一定义

用 1.3 的统一字段定义，一处声明派生四样。

### 导出

`render/exportMarkedImage.ts` 是把标注渲染合成到图片上。这**确实是算法型操作**（涉及 Canvas 渲染与编码），如果要给助手开放，是本计划里少数该新增专用能力的地方之一。执行时判断是否需要，需要则书面回答「为什么不能表达成属性写入」。

### 建账

新建 `markDocumentStore` 的账本（6.1 产出的 store），并把 6.1 里提到的编辑器 hook 层动作也归类。

## 执行记录

### 与任务文档设想不符之处（承接 6.1 的纠偏）

任务文档假设 6.1 产出 `src/features/imageMark/domain/markDocument.ts` 与
`src/features/imageMark/store/markDocumentStore.ts`。6.1 的实际结论是：状态统一收在
`src/features/imageEdit/store/imageEditSessionStore.ts`（按 sessionId 分片），三宿主经
`ImageEditor.tsx` 共用。本任务按 6.1 的真实产出设计，**不是**按本文件最初的预期形态：

- 反射与执行器仍新建在 `src/features/imageMark/application/` 下（符合"标注编辑器对助手
  可见"这件事该由 imageMark 这个 feature 目录体现），但读写的 store 是 imageEdit 那边的
  `imageEditSessionStore`。
- 新建的 `imageMarkStoreLedger.ts` 里 `storeId: 'imageEditSessionStore'`——账本文件位置与
  它登记的 store 文件位置不必一致，`check-assistant-capabilities.cjs` 的 store 级检查按
  `storeId` 字符串匹配 store 文件 basename，与账本文件放哪个目录无关；放在 imageMark 下
  是为了让同一脚本的**feature 级**检查（要求 `src/features/imageMark/` 下同时有
  `*Reflection.ts` 与 `*StoreLedger.ts`）通过。

### 文档形态结论（依据 6.1）

- `ImageMarkDoc`（V1 视图）：`items: MarkItem[]`（每项带 `id`）、`orientation`、`crop`
  都是文档级属性，与 6.1 执行记录一致。
- 底层真实存储是 V2 的 `ImageEditDocument.operations`；反射层一律通过
  `imageEditDocumentToMarkDoc`/`replaceMarkDocInImageEditDocument` 读写 V1 视图，不直接
  碰 V2 的 operations 数组。

### 实体设计（与任务文档预期形态的偏差）

| 实体 | 与预期的差异 |
|---|---|
| `image_mark.document` | 无差异：会话态单例，属性为 `orientation_rotate`（enum）/`orientation_mirrored`（boolean）/`crop_rect`（json，nullable）。**未暴露"源图引用/尺寸"**——`sourceImageUrl` 是 `ImageEditor.tsx` 的 React prop，不在 6.1 的 `imageEditSessionStore` 里，塞进去要么扩大 6.1 已提交的 store 形状，要么另开一条追踪链路，均超出本任务范围；且源图 URL 本身通常能从画布节点/生成历史的媒体属性另行读到，不是这个实体独有信息。 |
| `image_mark.annotation` | 预期是"类型（只读）+ 几何 + 样式（颜色/粗细）+ 文字"四组属性。实际收成两条：`type`（只读 enum，创建后不可变）与 `data`（json，装除 id/type 外的全部字段）。7 种标注类型（rect/ellipse/arrow/pen/text/number/mosaic）形状差异很大，拆成十几条各自 nullable 的属性只会让大多数类型上一半属性永远是 null；折成一条 json 与 `generation.draft.uploaded_images` 是同一个先例。写入校验直接复用既有的 `sanitizeMarkItem`（`@/core/imageEdit/markCodec.ts`），未新写一套逐字段校验。 |

### 稳定引用格式

- `image_mark.document` 的 id 就是 sessionId。
- `image_mark.annotation` 的 id 是 `sessionId:annotationId`，与 `camera_stage.shot` 的
  `projectId:shotId` 同一惯例。

### commitDocument 的账本分类说明

`imageEditSessionStore.commitDocument` 是文档级属性写入（旋转/镜像/裁剪）与标注集合写入
（新建/删除标注）共用的同一条"整份文档提交"原语。账本里把它归到 `image_mark.document` 的
三条属性（`kind:'property'`）；`image_mark.annotation` 的集合写入覆盖由它自己的
`collectionWrite` 声明 + `ImageMarkAnnotationCollectionExecutor` 独立审计
（`collectionCoverage.test.ts`），不要求账本同时给出 `kind:'collection'` 绑定——账本的作用
是证明"这个 store 动作存在某条助手可达路径"，不是穷举它服务的全部语义，与 2.2 记录里
`reorderShot` 绑到 `time` 属性同一先例。

### undo/redo：新增两个专用能力而非记成 gap

`imageEditSessionStore` 的 `undo`/`redo` 是按 sessionId 分片的完整撤销/重做栈，对应编辑器
工具栏的撤销/重做按钮，是真实的人类能力。与其记成 `gap` 推给以后，直接照抄 canvas 领域已有
的 `undo_canvas_change`/`redo_canvas_change` 先例（`canvasApplicationService.ts` 里两者也是
直接调 `useCanvasStore.getState().undo()/redo()`，机制完全一致），新增
`undo_image_mark_change`/`redo_image_mark_change` 两个语义能力，比 canvas 那套更简单——不需要
`undoRef`/`historyDepth` 校验，`imageEditSessionStore` 的 `undo()`/`redo()` 本身就是纯 LIFO
栈，越界返回 `null`。**GAP_BASELINE 保持 8，未上调。**
