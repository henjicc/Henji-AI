# 6.1 标注编辑器领域层提升

## 任务目标

把 imageMark（图片标注编辑器）的文档态从 React hook 局部态提升为可寻址的 store，为 6.2 的实体注册铺路。

这是第五阶段（生成页）的缩小版，走同样的路子，但成本更低——`domain/` 下已经有分离好的纯逻辑。

## 当前情况

### imageMark 是全项目唯一的全域失明领域

`src/features/imageMark/` 下**没有** Reflection、没有 capability、没有 executor。助手完全看不见这个编辑器，也动不了它。

它在 `scripts/check-assistant-capabilities.cjs` 的 `ASSISTANT_BLIND_FEATURES` 白名单里，理由写的是「期 5：文档态全在 React hook 局部态里，要先提升成 store」。

### 它是什么

工具箱里的「图片编辑」工具（surface id `tool.image_edit`，toolId `imageMark`），也在画布内以 Viewer 形态出现。功能：标注、打码、裁剪、旋转镜像、文字。

### 目录结构（已经分层不错）

```
src/features/imageMark/
  domain/     codec.ts, geometry.ts, types.ts   ← 纯逻辑已分离，可直接复用
  editor/     markEditorContextValue.ts, useMarkController.ts, useMarkHistory.ts,
              useMarkPointer.ts, useMarkTextEditing.ts, useMarkCropOrientation.ts
  render/     exportMarkedImage.ts
  standalone/ viewer/
```

### 人类能做的操作

来自 `src/features/imageMark/editor/markEditorContextValue.ts`：

| 动作 | 说明 |
|---|---|
| `selectTool(tool)` | 切换标注工具（画笔/矩形/箭头/文字/打码等） |
| `onStylePatch` | 改样式（颜色、粗细） |
| `onCropRatioChange` / `onCropReset` | 裁剪比例 |
| `onOrientation(op)` | 旋转 / 镜像 |
| `history` | 撤销重做（`useMarkHistory`） |
| 指针交互 | 绘制、拖拽（`useMarkPointer`） |
| 文字编辑 | `useMarkTextEditing` |
| 导出 | `render/exportMarkedImage.ts` |

**执行时要确认「文档」的确切形态**：标注对象是一个数组吗？每个标注有 id 吗？这决定 6.2 能不能把标注注册成可增删的集合实体。

### 记忆中的相关约束

项目里有一条既有约定：快速标记 / 裁剪统一到 `features/imageMark`，三个宿主（工具箱、画布 Viewer、独立窗口）共用，**禁止平行实现**。本任务的提升不能破坏这个共用关系——三个宿主必须继续用同一份领域层。

## 实施方案

按 5.1 → 5.3 的同样路子，但合并成一个任务（规模更小）：

1. **抽纯领域层**：`src/features/imageMark/domain/markDocument.ts`（若 `types.ts` 已经有文档类型则扩展它，不新建重复类型）。提供 `MarkDocument` 类型 + 纯函数 reducer（加标注、改标注、删标注、改样式、裁剪、旋转、撤销重做）。
2. **store 化**：`src/features/imageMark/store/markDocumentStore.ts`。**必须支持多实例**——三个宿主可能同时存在（画布里开着 Viewer，工具箱里也开着编辑器）。按 sessionId 分片。
3. **hook 退化为适配层**：`useMarkController` / `useMarkHistory` 内部改为读写 store，**对外 API 一字不改**，三个宿主零改动。

### 多实例是硬要求

与生成页不同，imageMark **明确会有多实例**（画布 Viewer + 工具箱 + 独立窗口）。store 从一开始就要按 sessionId 分片，不能先做单实例再改。

## 执行记录

### 与任务文档设想不符的架构现实（先纠偏，再实施）

任务文档写作时假设：`useMarkController`/`useMarkHistory` 自己持有文档局部态，标注文档的类型定义要在 `imageMark/domain/` 下新建/扩展 `markDocument.ts`，store 要新建在 `imageMark/store/markDocumentStore.ts`。

实读代码后发现这个假设已经过期——项目里存在一套任务文档未提及的 **V2 统一图片编辑器架构**，在本任务系列开始前就已经把三个宿主统一了：

- `src/features/imageMark/editor/useMarkController.ts`、`useMarkHistory.ts` **不持有状态**，`doc`/`setDoc`/`history` 全部通过参数传入（`MarkEditorDocumentController`）。它们本来就是薄适配层，不需要"退化"，因为它们从来没有变胖过。
- 真正持有状态的是 `src/features/imageEdit/editor/useImageEditorSession.ts`（任务文档完全没提到这个文件）。它内部用 `useState<ImageEditDocument>` + `undoStack`/`redoStack` 数组，通过 `session.markController`（实现 `MarkEditorDocumentController`）注入给 `MarkEditor.tsx`。
- 三个宿主（`src/features/canvas/ui/tool-editors/EditToolEditor.tsx`、`src/features/imageMark/viewer/ViewerMarkEditor.tsx`、`src/features/imageMark/standalone/ImageMarkTool.tsx`）**没有一个直接用 `<MarkEditor>`**，全部渲染 `<ImageEditor>`（`src/features/imageEdit/editor/ImageEditor.tsx`），由它统一调用 `useImageEditorSession` 并把 `markController` 传下去。`MarkEditor.tsx` 自己的 `documentController` 缺省时的本地 `useState` 兜底分支（`localDoc`/`setLocalDoc`/`localHistory`）因此对三个真实宿主都是死代码。
- 领域逻辑早就是纯函数，且已经不在 `ImageMarkDoc`（V1，`{version:1, items: MarkItem[], orientation, crop}`）这一层，而是在更新的 `ImageEditDocument`（V2，`{version:2, operations: ImageEditOperation[]}`）里，`@/core/imageEdit/document.ts` 提供 `imageEditDocumentToMarkDoc`/`replaceMarkDocInImageEditDocument`/`upsertImageEditOperation` 等纯函数做两层之间的桥接，全部不 import React。

**结论：真正要做的"领域层提升"，对象是 `useImageEditorSession.ts` 里的组件级 `useState`，不是 `useMarkController`/`useMarkHistory`。** 因此没有新建 `imageMark/domain/markDocument.ts`（领域逻辑已存在且已纯，扩展它没有实际内容可加），也没有新建 `imageMark/store/markDocumentStore.ts`；而是新建了 `src/features/imageEdit/store/imageEditSessionStore.ts`，把 `useImageEditorSession.ts` 改造成读写这个 store 的薄适配层。这不违反"三宿主共用同一份领域层"的约定——三宿主本来就都走 `useImageEditorSession`，改动点只在这个 hook 内部换了状态持有方式，对外形状不变（仅新增 `sessionId` 一个字段，纯增量）。

### 文档形态结论（供 6.2 使用）

- 对外契约层是 `ImageMarkDoc`（V1 视图）：`{ version: 1, items: MarkItem[], orientation, crop }`。`MarkItem` 的每个变体（画笔/矩形/箭头/文字/打码等）都带 `id: string` 字段，是带 id 的标注对象数组——6.2 可以把 `items` 注册成可增删的集合实体。
- 裁剪（`crop`）与旋转（`orientation`）是文档级属性，不是"变换列表"里的一项，各自独立存在于 `ImageMarkDoc` 上。
- 但底层真实存储是 `ImageEditDocument`（V2）：`{ version: 2, operations: ImageEditOperation[] }`，标注/裁剪/旋转在 V2 里各自是一条 `operation`（`image.annotations`/`image.crop`/`image.orientation`），`imageEditDocumentToMarkDoc()` 把它们拼回 V1 视图供 `MarkEditor` 消费。6.2 注册实体时，读写应该走 V1（`ImageMarkDoc`）这个更贴近人类操作语义的视图，而不是直接操作 V2 的 `operations` 数组。

### 实施内容

1. 新建 `src/features/imageEdit/store/imageEditSessionStore.ts`：zustand store，`sessions: Record<sessionId, {document, undoStack, redoStack}>`，提供 `ensureSession`（幂等）/`disposeSession`/`pushHistorySnapshot`/`commitDocument`/`updateDocumentWithoutHistory`/`undo`/`redo`。reducer 全部委托给已经是纯函数的 `@/core/imageEdit/document.ts`，store 只管"谁持有当前 document"。
2. 重写 `src/features/imageEdit/editor/useImageEditorSession.ts` 为薄适配层：首帧渲染期间（非 `useEffect`）用 `sessionIdRef` 幂等建会话，避免"先渲染出空文档再补上初始文档"的闪烁；卸载时 `disposeSession`。对外返回形状仅新增 `sessionId` 字段，唯一消费方 `ImageEditor.tsx` 未解构该字段，零改动。
3. 修复过程中发现并修的一个真实 bug（不是任务目标，是重构副作用）：最初用 `useRef` 镜像 store 里的 document（照抄原 `useState` 版本的写法），但同一个事件处理函数里连续多次调用 `updateOperation`（柔光滑杆事务式更新）之间没有重渲染，`ref` 只在渲染期间同步，第二次调用会读到陈旧值。改为 `currentDocument()`（`useCallback`，每次调用都 `getState()` 读 store 现值）后，被既有测试 `'把连续柔光滑块更新合并为一条文档历史记录'` 验证为真实回归修复（改前该测试红）。连带把 ~8 个依赖 `currentDocument` 的 `useCallback` 补齐依赖数组。
4. 新建 `imageEditSessionStore.test.ts`（5 个用例）：两个 sessionId 互不影响、撤销/重做栈互不影响、`disposeSession` 只清指定会话、`ensureSession` 幂等（不覆盖已提交内容）、redo 隔离。
5. 在既有 `useImageEditorSession.test.tsx` 追加第 4 个用例：两个独立 `renderHook()` 实例（模拟同时开两个宿主），互相隔离——一个改扩散参数不影响另一个，一个提交裁剪不影响另一个的裁剪。
