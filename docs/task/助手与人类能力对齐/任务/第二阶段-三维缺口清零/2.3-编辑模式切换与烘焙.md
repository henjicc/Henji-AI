# 2.3 编辑模式切换与烘焙

## 任务状态

- 状态：已完成
- 所属阶段：第二阶段 · 三维缺口清零
- 前置任务：1.3
- 关联任务：2.4（专业模式是精细动画的前提）
- 是否可以并行：可与 2.1 / 2.4 / 2.5 并行

## 任务目标

让助手能在简易模式与专业模式之间切换，并能执行烘焙。

烧掉 2 项 gap：`setEditorMode`、`bakeToProMode`。`GAP_BASELINE` 降 2。

**这一项的实际价值可能高于表面**：用户提过「我们在用户界面上做了一些简化，所以有些操作在视图下面做不了」。专业模式才有完整的关键帧编辑，这条挡住了助手做精细动画。

## 当前情况

### 缺口现状

`camera_stage.project.editor_mode` 属性标着：

```
readOnly: '编辑模式只能通过正式烘焙操作切换。'
```

位置：`src/features/cameraStage/application/cameraStageReflection.ts` 的 `propertiesByEntity[ENTITY_TYPES.project]`（约 119 行）。

**这句理由只对「简易 → 专业」成立。** 烘焙（`bakeToProMode`）把镜头卡状态编译成关键帧轨道，是有损且不可逆的；但「专业 → 简易」和同模式内切换没有这个约束。现在一句话把三种情况一起挡住了。

### store 侧

- `setEditorMode(mode)`：直接切换模式
- `bakeToProMode()`：把简易模式的镜头卡烘焙成专业模式的关键帧轨道

两者都在 `src/features/cameraStage/store/cameraStageStore.ts`。**执行时必须先读懂 `bakeToProMode` 的实现**，确认：
- 烘焙是否真的不可逆（烘焙后原镜头卡数据是否丢失）
- `setEditorMode` 直接切到 `pro` 而不烘焙会发生什么（是否等价于丢掉所有简易模式内容）

这两个问题的答案决定了本任务的设计。**不要假设，去读代码。**

### 风险等级

烘焙若确实不可逆，属于 `AGENTS.md` 说的需要审批的操作。项目已有风险分级（R0–R4）与审批机制，`ApplicationCapabilityDefinition` 有 `risk` 字段，引擎在 `commit` 处按 `requiresApproval` 拦截。

## 实施方案

分两件事处理，因为它们的可逆性不同：

### 1. `editor_mode` 属性放开（可逆的那部分）

把属性从整体只读改为可写，但在写入执行器里对**不可逆方向**做额外处理：

- 若目标模式与当前相同 → 空操作
- 若「专业 → 简易」→ 直接切（确认是否有损；若有损同样要审批）
- 若「简易 → 专业」→ 这一跳等价于烘焙，见下

### 2. 烘焙（不可逆的那部分）

若确认不可逆，注册为带审批的语义操作能力，`risk` 设为 `R2` 或更高、`destructive: true`、`supportsUndo` 按实际情况填。

**注意**：这是本计划里少数几个「确实该新增专用能力」的地方之一——烘焙是一次数据形态转换（卡状态 → 关键帧轨道），不是设值。在执行记录里书面记下这个理由。

若读代码后发现烘焙**可逆**（原数据保留），则不需要专用能力，直接作为 `editor_mode` 的一次属性写入即可，`GAP_BASELINE` 同样降 2。

## 执行记录

### 2026-08-08

**读代码后推翻了任务文档自己的假设**（执行步骤 1-2）：

任务文档写道"专业→简易与同模式内切换没有约束"。读 `shotSlice.ts` 的 `setEditorMode` 发现这个假设不成立：

```ts
setEditorMode: (editorMode) => set((state) => {
  if (state.editorMode === 'pro' && editorMode === 'simple') return {}   // 专业→简易被直接拒绝
  if (editorMode === state.editorMode && !(editorMode === 'simple' && state.shots.length === 0)) return {}
  ...
})
```

- **专业→简易**：被 store 第一行直接拒绝（空操作），应用从未支持这个方向，不是"没有约束"而是"根本不存在这个功能"。`shotSlice.test.ts` 421-439 行的既有测试也验证了这一点（`baked.setEditorMode('simple')` 后 `editorMode` 仍是 `'pro'`）。
- **同模式内切换**：多数情况下是空操作；唯一的例外是"模式为 simple 且 shots 为空"时会新建一张默认镜头卡——这只在全新工程上发生。
- **`setEditorMode` 的唯一真实调用点**：`cameraStageProjectService.ts` 的 `createNewProject()`，对着刚 `newScene()` 清空的空场景设置初始模式，创建工程后立即保存。全项目搜索确认没有任何 UI 组件直接调用它——`EditorModeBadge.tsx`（编辑模式切换的唯一界面入口）只调用 `bakeCurrentProjectToPro()`，从未调用 `setEditorMode`。
- **烘焙可逆性**：`bakeCurrentProjectToPro()`（`cameraStageProjectService.ts`）确认不可逆——烘焙后 `shots: []`，原镜头卡结构（每卡的名称/停留/过渡/连续性等）永久丢失，只保留编译出的关键帧轨道；同时清空撤销历史 (`clearCameraStageHistory()`)。界面 `EditorModeBadge.tsx` 的确认弹窗原文："此操作不可逆。当前镜头卡会固化为专业时间轴上的关键帧，之后无法再以镜头卡方式编辑""转换后将立即保存工程，并清空撤销历史。"

**结论**：不存在任务文档设想的"可逆方向"。`editor_mode` 维持整体只读，但把理由从"只能通过正式烘焙操作切换"（暗示专业→简易只是"未开放"）改写为准确描述——只能在新建工程时选定，或经烘焙单向切换；应用本身不支持已有内容从专业改回简易。`setEditorMode` 因此不需要开放成属性写入：它已完全被 `create_camera_stage_project`（新建工程时选 `mode`）覆盖，直接开放反而会绕开烘焙的编译清理步骤、在"专业"模式下留下过期的 `shots` 数据，重新制造静默不一致。

**烘焙注册为专用能力**（`bake_camera_stage_to_pro`，`risk: 'R2'`, `destructive: true`, `supportsUndo: false`）——书面回答"为什么不能表达成属性写入"：烘焙不是"把 editor_mode 设成 pro"这个值本身，而是一次数据形态转换（镜头卡结构 → 关键帧轨道 + 清空撤销历史），转换过程本身需要 `bakeCurrentProjectToPro()` 里的编译、清理、持久化步骤，无法压缩成一次属性 set；且不可逆操作按 `AGENTS.md`/`cameraStageControl('delete', ...)` 的既有模式需要走 `confirmation_required` 审批路径，这正是 `delete_camera_stage_object`/`delete_camera_stage_project` 已经在用的机制，复用而非新造。

**实施**：
- `cameraStageApplicationService.ts` 新增 `bakeToProMode(projectId)`：`ensureProjectLoaded` 定位工程后，已是专业模式则返回 `already_pro`（安全空操作，不抛错），否则委托给已有的 `bakeCurrentProjectToPro()`（与界面 `EditorModeBadge` 同一份实现，未重写），按 `status: 'baked'` 返回烘焙前镜头卡数与烘焙后关键帧轨道数。
- `cameraStageProjectApplicationCapabilities.ts` 新增 `bake_camera_stage_to_pro` 定义（`cameraStageControl('delete', ...)` 触发审批），`cameraStageCapabilityAdapter.ts` 加 `bakeCameraStageToPro` 适配函数，`registerToolboxCapabilityHandlers.ts` 注册处理器。
- `cameraStageReflection.ts`：`editor_mode` 的 `readOnly` 理由改写为准确描述。
- `cameraStageStoreLedger.ts`：`setEditorMode` 改绑 `excluded/internal`（已被 `create_camera_stage_project` 覆盖）；`bakeToProMode` 改绑 `capability: bake_camera_stage_to_pro`。
