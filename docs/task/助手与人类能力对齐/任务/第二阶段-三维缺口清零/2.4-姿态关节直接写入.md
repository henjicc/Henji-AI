## 任务目标

让助手能直接摆角色姿势（改关节角度）与套用姿势预设，而不是只能建关键帧。

烧掉 2 项 gap：`updatePoseJoint`、`applyPosePreset`。`GAP_BASELINE` 降 2。

**前置决策见 `重要记录.md` 记录 002，状态为「待确认」。倾向方案 C。执行前若用户未表态，按方案 C 执行并在执行记录里注明。**

## 当前情况

### 缺口现状

`camera_stage.object.animatable.*` 共 63 条属性（transform 三组 × 三轴 = 9，color 1，姿态关节 15 × 3 轴 = 45，camera 侧另有 8 条），**全部标着**：

```
readOnly: '逐分量动画值通过关键帧实体或领域语义操作修改。'
```

生成位置：`src/features/cameraStage/application/cameraStageReflection.ts` 的 `animatableProperties()`（约 99–114 行），属性路径来自 `src/features/cameraStage/domain/animatableProps.ts` 的 `listAnimatablePropertyPaths()`。

### store 侧

- `updatePoseJoint(id, jointId, euler, autoKeyPaths?)`：改单个关节的欧拉偏移（角度制）
- `applyPosePreset(id, preset)`：整体替换当前姿态

两者都在 `src/features/cameraStage/store/cameraStageStore.ts`。**注意 `updatePoseJoint` 已经有 `autoKeyPaths` 参数**——界面上人拖手柄时就是靠它自动打点的。这是方案 C 可以直接复用的现成机制。

### 核心陷阱（重要记录 002）

直接放开成可写会出现两条互相覆盖的路径：

助手写 `animatable.pose.leftArm.x = 30` → 该轨道上有关键帧 → 播放头一动，采样器（`src/features/cameraStage/store/playbackSampling.ts` / `playbackAppliers.ts`）立刻把值覆盖回插值结果。

用户看到的是「助手说改好了，值自己跳回去了」——**比「改不了」更糟**。

### 方案 C（倾向决定）

- 轨道**无**关键帧 → 写静态值
- 轨道**有**关键帧 → 等价于在当前播放时间点写/建一个关键帧

与界面上人拖手柄时的自动打点语义完全一致，用户心智模型统一。

## 实施方案

1. 把 63 条 `animatable.*` 的 `readOnlyReason` 去掉（或按方案 C 改写成说明语义的描述文字，而不是拒绝理由）。
2. 在三维 object / camera 的 Fields 文件（1.3 产出）里为 `animatable.*` 补写入实现，实现方案 C 的分支：
   - 查该对象该属性路径在 `animation.tracks` 里有没有关键帧
   - 无 → 走静态值写入（`updateTransform` / `updatePoseJoint` 不带 autoKey）
   - 有 → 走 `autoKeyPaths` 在当前播放时间点打点
3. `applyPosePreset` 是整体替换，涉及多个关节一次写入。判断它能否表达成「一批 `animatable.pose.*` 属性的批量写入」——能则绑属性，不能则考虑语义能力（并书面说明理由）。
4. **属性描述要写清语义**：模型看到的描述里必须说明「该轨道已有关键帧时，写入等价于在当前时间点打点」，否则模型不知道自己的写入会产生关键帧。

## 执行记录

### 2026-08-08

**决策**：任务文档明确"若用户未表态，按方案 C 执行并在执行记录里注明"，按此执行方案 C；用户后续确认了这一方向。方案 C 的最终结论、简易模式判断、`applyPosePreset` 处理方式均已写入 `重要记录.md` 记录 002。

**读代码确认的事实**（执行步骤 1-3）：
1. `listAnimatablePropertyPaths()`（`animatableProps.ts`）：63 条路径，object 兼容 55 条（除 fov）、camera 兼容 8 条（transform.position/rotation + color + fov）。叶子描述子的 `valueType` 只有 `scalar`/`color`，从不是 `vec3`——每条动画属性的值类型天然是 number 或 string。
2. `store.updatePoseJoint`/`updateTransform`（`cameraStageStore.ts`）：专业模式下已经完整实现方案 C——先无条件更新对象静态值，再对 `explicitAutoKeyPaths`（或全部涉及分量）调用 `autoKeyPaths()`，后者内部 `if (!getTrack(...)) continue` 跳过没有轨道的分量。这段逻辑早就存在（人拖手柄用的就是它），2.4 不重写，只是新增一条路径去调用它。
3. `playbackSampling.ts` 的 `applyAnimationAtTime`/`sampleAnimationFrame`：只对**有轨道**的属性重新采样覆盖对象值，没有轨道的属性完全不碰。这解释了方案 C 为什么正确：无轨道时静态写入天然不会被播放头覆盖；有轨道时新关键帧就是采样源，写入即生效。

**发现并解决的架构陷阱**（比"要不要自动打点"更根本）：三维 object/camera 现有 16 条建模属性全部经 `CameraStageObjectDraft.update` 累加，最终提交到 `cameraStageApplicationService.updateObject()` → `store.updateObjectAcrossShots()`——**建模语义**，一律同步全部镜头卡、从不自动打点（修"白色球体播放变色"bug 定的规则）。若 `animatable.*`/`pose_preset` 复用同一条路径，会全部落进建模语义、`autoKeyPaths` 永远不被调用——等于变相实现了已被否决的方案 B。解法：给 `CameraStageObjectDraft` 加两个独立累加字段（`animatable: Record<string, StageKeyframeValue>` / `posePresetId?: string`），三种语义分流到三个不同落地方法（`updateObject` / `updateAnimatableProperties` / `applyObjectPosePreset`），`CameraStageMutationExecutor.applyObject()` 在提交前用 `[hasRegular, hasAnimatable, hasPosePreset].filter(Boolean).length > 1` 拒绝混用同一批。

**简易模式结论**：不放开。简易模式没有独立的关键帧轨道（`animation` 由镜头卡编译而来），"轨道有没有关键帧"这个判断条件本身不成立。`updateAnimatableProperties()`/`applyObjectPosePreset()` 在非专业模式下直接抛 `ANIMATABLE_WRITE_REQUIRES_PRO_MODE`，错误信息指向 2.2 的 `capture_object_refs` 或 2.3 的 `bake_camera_stage_to_pro`。`GAP_BASELINE` 按两项 gap 全部烧掉计算（降 2）——专业模式下的写入是完整能力，不是半成品。

**`applyPosePreset` 处理**：没有走专用能力。预设是离散命名值（`POSE_PRESETS`：`stand`/`talk`/`walk`/`sit`/`crouch` 共 5 个），做成 `camera_stage.object.pose_preset` 枚举属性即可表达——不需要 `ApplicationCapabilityDefinition`。写入查表后委托给已有的 `store.applyPosePreset()`（未重写）。读取没有持久化的"当前预设"概念，始终为空，属性描述里写明了效果验证方式。
