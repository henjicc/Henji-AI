## 当前情况

### `clearTrack`

store 侧在 `src/features/cameraStage/store/animationActions.ts` 或 `cameraStageStore.ts`（执行时确认）。

助手侧现状：`camera_stage.keyframe` 已经声明了 `collectionWrite: { creatable: true, removable: true }`，但 `remove_items` 只支持**逐条指定引用**。清空一条轨道意味着删掉该 `objectId + propertyPath` 下的全部关键帧，助手需要先列举再逐条删——条数多时会撞上 `maxItemsPerChange: 128` 的上限，而且啰嗦。

这一项**不需要新能力**，需要的是一条能按轨道整体删除的路径。可选形态：
- 让 `remove_items` 的 target 支持轨道级引用（如 `objectId:propertyPath` 不带时间）
- 或在 `camera_stage.keyframe` 之外加一个 `camera_stage.track` 实体，其 `collectionWrite.removable` 表达「删掉整条轨道」

执行时评估两者，选一个并说明理由。

### 轨迹（`setShotSpatialPath` / `setShotPathAnchor`）

`camera_stage.trajectory` 实体**整体标着** `writeExclusion`：

```
'轨迹由 apply_camera_stage_camera_move 的轨迹采样算法产生，属算法型操作的产物。'
```

位置：`src/features/cameraStage/application/cameraStageReflection.ts` 的 `createCameraStageReflectionRegistrations`。

四条属性全部只读：`shot_ref`、`object_ref`、`source`、`knot_count`。

**这个理由只对「轨迹怎么产生」成立，对「产生之后能不能编辑」不成立。** 界面上用户可以拖动控制点调整轨迹，助手不行。

### 轨迹的数据结构

`src/features/cameraStage/domain/shotTypes.ts`：

```
StageSpatialPath { knots: StageSpatialPathKnot[] }   // knots 仅保存过渡内部的空间关键点
StageTransitionDetail { spatialPath?: StageSpatialPath }
```

轨迹挂在 `shot.transition.perObject[objectId].spatialPath` 下。控制点是**数组**——这正是它需要子实体的原因：`knot_count` 是个统计值，改不了；要能编辑就得让每个 knot 成为可寻址的实体。

### 建议形态

新增 `camera_stage.trajectory_knot` 子实体：
- 父实体：`camera_stage.trajectory`
- 属性：`position`（VECTOR3，可写）、`index`（只读或可写用于重排）
- `collectionWrite: { creatable: true, removable: true }`
- `trajectory` 实体的 `writeExclusion` 收窄：改为说明「轨迹整体由采样算法产生；产生后的控制点通过 `camera_stage.trajectory_knot` 编辑」

这样 `setShotSpatialPath`（整条写）= 批量 create knots，`setShotPathAnchor`（拖端点）= 改某个 knot 的 position。

## 执行记录

### 2026-08-08

**`clearTrack` 形态选择**：读 `keyframeSlice.ts` 确认 `clearTrack(objectId, path)` 删的是**单条轨道**（`removeTrack` → `replaceTrackKeyframes(...,[])`），不是某对象全部轨道。选了任务文档的第一种形态——扩展 `remove_items` 的 target 支持轨道级引用，不新增 `camera_stage.track` 实体。理由：`camera_stage.keyframe` 的稳定引用本就是 `工程:对象:属性路径:时间`，去掉时间段（`工程:对象:属性路径`，3 段）天然、无歧义地表达"整条轨道"，不需要为同一份数据（关键帧）造第二个实体。集合执行器按引用段数分流：3 段→ `cameraStageKeyframeService.clearTracks()`（新增，委托 `store.clearTrack`，未重写），4 段→原有的 `removeKeyframes()`；同一批混用两种粒度直接拒绝（`MIXED_REMOVE_TARGETS_NOT_SUPPORTED`），因为原子性语义不清（该整批算轨道清空还是单点删除）。

**轨迹形态选择（推翻了任务文档"新增 trajectory_knot 子实体"的建议）**：读 `StageMotionPathOverlay.tsx`（轨迹编辑的唯一 UI）发现，拖任意一个控制点、拖切线手柄（in/out handle）、拖路径自身的起止切线（`startOutTangent`/`endInTangent`），**全部**收敛到同一个 store 动作 `setShotSpatialPath`——每次交互都是"读当前完整路径 → 改一处 → 整条写回"，`store` 层根本没有"改一个控制点"这个原语。既然实现层面没有增量 API，`trajectory_knot` 子实体 + 集合 create/remove 的设计会需要我自己在**服务层**发明拆分/合并语义，比直接对齐真实交互模型更复杂、更容易跑偏。改用更贴近事实的设计：`knots` 作为一条 `kind: 'json'` 数组属性整体读写（写入即替换全部控制点，元素 `id` 省略时自动生成），与 `start_out_tangent`/`end_in_tangent`（路径自身的边缘切线）一起累加进同一个 draft，一次性调用 `setShotSpatialPath`。`kind: 'json'` 类型与写入语义参考了 `assetFields.ts` 的 `asset.tags`（同样是"整条数组替换"的既有先例，未发明新模式）。

另外发现 `setShotPathAnchor`（任务文档称"拖动轨迹端点控制点"）实际语义与 knots 无关：拖起止端点改的是**相邻镜头卡里该对象的位置快照**（`shot.objectStates[objectId].transform.position`），不是 `spatialPath.knots`——轨迹的起止点"由相邻镜头卡快照提供，不重复存储"（`shotTypes.ts` 原有注释）。因此 `start_position`/`end_position` 做成两条独立属性，写入走独立的 `setShotPathAnchor`，与 `knots`/切线属性（走 `setShotSpatialPath`）是两条不冲突的独立路径，可以在同一批里都出现（不像三维 object 那样需要互斥检测——这里没有语义混淆的风险，两个 store 动作各管各的字段）。

**`trajectory` 实体从整体 `writeExclusion` 变为正常可写实体**：新增 `CameraStageMutationExecutor` 处理 `camera_stage.trajectory`（此前 `MutationEntityType` 显式排除了它），复用与其他实体一致的三段式流程（读快照建 draft → `applyWriterTable` → 提交业务方法）。稳定引用沿用反射层已有的 `工程:镜头:对象` 格式（`allRefs()` 里 `childRef` 拼的 `${shot.id}:${objectId}`），未新增引用格式。

**与 `apply_camera_stage_camera_move` 的共存关系**：两条路径落地到同一个字段（`shot.transition.perObject[objectId].spatialPath`）但互不知道对方存在——算法采样产生初始轨迹，手工编辑修改已产生的轨迹，后写的值就是最终值。这与界面上"先套预设、再手动微调控制点"完全一致的既有行为（`StageMotionPathOverlay.tsx` 的 `updatePath` 就是在预设生成的路径基础上继续编辑），不是新引入的交互，不需要额外协调机制。
