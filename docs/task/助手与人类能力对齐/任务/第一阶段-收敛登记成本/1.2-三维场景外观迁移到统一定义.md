## 任务目标

把三维场景的 28 条属性（外观 25 + 时间轴 3）从「4 处分散登记」迁到「1 处统一定义」，作为统一字段定义机制的**首个试点**，用真实数据验证收益与坑。

选这一组做试点的原因：它正是当初漏掉 24 项的那一组，条目多、形态齐（颜色/数值/布尔/枚举/向量三维），且彼此独立、迁移风险低。

完成后判断标准：三维场景的四处登记压成一处，且**门禁断言结果与迁移前完全一致**（纯重构，不改变任何覆盖判定）。

## 实施方案

新建 `src/features/cameraStage/application/cameraStageSceneFields.ts`，用 1.1 的机制把 28 条写成一张表。每条形如：

```ts
sceneField('sky_color', '天空颜色', COLOR, {
  read: (settings) => settings.sky.color,
  write: (store, value) => store.setSceneSkyColor(stringValue(value)),
  storeAction: 'setSceneSkyColor',
})
```

然后把四个消费方改成从这张表派生：

- `cameraStageReflection.ts` 的 `propertiesByEntity[scene]`：`[...固定的只读几条, ...fieldDescriptors(SCENE_FIELDS)]`
- `sceneAppearanceProperties()`：改为 `fieldReadValues(SCENE_FIELDS, settings)`（保留导出名，其他地方在用）
- `CAMERA_STAGE_SCENE_WRITERS`：改为 `fieldWriterTable(SCENE_FIELDS)`
- 账本：改为展开 `fieldLedgerEntries(SCENE_FIELDS)`

**账本展开的类型陷阱**：账本用 `Record<ActionName, …>` 做编译期完整性检查，而展开一个计算出来的 record 会丢掉字面量 key 类型。需要在 1.1 的 `fieldLedgerEntries` 上用泛型保住 key 字面量类型，或在账本侧显式断言并补一条运行时校验「展开的 key 集合等于预期的 28 个动作名」。**这一点在执行时必须实际验证，不能想当然。**
