# 实施方案

## 一、必读的既有机制（新 AI 从这里开始）

助手操作应用**只有一条正路**：反射层通用动词。理解下面四件事就能执行本计划的绝大多数任务。

### 1. 通用动词永远是 4 个工具

`describe_application_entities` / `list_application_entities` / `read_application_entity` / `change_application_entities`（定义在 `src/core/assistant/capabilities/applicationReflectionApplicationCapabilities.ts`）。

**再注册 500 条属性，工具数还是 4。** 只有 `defineApplicationCapability()` 那一支会撑大工具目录（现约 92 项）。

因此 `AGENTS.md` 的规则是：新增专用能力必须书面回答「为什么它不能表达成属性写入或集合增删」。答不上来就去注册属性。

### 2. 执行链路

```
模型 tool_call
  → electron/main/services/agent-runtime/tools/builtin/frontend-capabilities.ts（适配成工具）
  → IPC → src/features/assistant/applicationCapabilities/registry.ts
  → applicationReflectionAdapter.ts（changes → PlannedStep）
  → src/core/application-control/execution/engine.ts（plan / preflight / commit）
  → feature 执行器 → 正式领域服务 → store
```

唯一注册入口：`src/features/assistant/applicationCapabilities/applicationControlRegistry.ts`。

### 3. 三种执行器

| 类型 | 管什么 | 接口 |
|---|---|---|
| `ApplicationMutationExecutor` | 改已有实体的属性 | 必须声明 `writableProperties` / `propertyOperations`，且由写入表派生 |
| `ApplicationCollectionExecutor` | 在父实体下增删成员 | 实体上要声明 `collectionWrite` |
| `ApplicationSemanticOperationExecutor` | 算法型操作（轨迹采样、碰撞检测） | 配套专用能力定义 |

契约在 `src/core/application-control/execution/types.ts`。

### 4. 三道已建好的门禁

| 门禁 | 文件 | 盯什么 |
|---|---|---|
| 实体级 | `collectionCoverage.test.ts` | 每个实体要么有写入执行器，要么有 `writeExclusion.reason` |
| 属性级 | `propertyCoverage.test.ts` | 声明可写 ↔ 执行器 `writableProperties` 双向一致；operation 声明一致 |
| 界面级 | `storeActionCoverage.test.ts` | store 的每个函数键都要在账本里归类；`GAP_BASELINE` 棘轮 |

三者都串在 `npm run check:assistant-capabilities` 上，已接入 `build` / `electron:build` / CI。

**账本的五档绑定**（`src/core/application-control/storeActionLedger.ts`）：

- `property` / `collection` / `capability`：已覆盖
- `excluded`：有意不开放（分五类：`view_state` / `transient_selection` / `derived` / `internal` / `user_only`），必须写明由谁维护
- `gap`：人能做、助手还不能做，且不合理。**这是燃尽目标**

## 二、当前问题

### 问题 1：一个属性要在 4 处登记（根因）

以「天空颜色」为例，实测要碰 3 个文件、4 个位置：

| # | 位置 | 内容 |
|---|---|---|
| 1 | `cameraStageReflection.ts` 的 `propertiesByEntity` | 属性描述（模型看的说明书） |
| 2 | `cameraStageReflection.ts` 的 `sceneAppearanceProperties()` | 怎么把值读出来 |
| 3 | `cameraStageWriterTables.ts` 的 `CAMERA_STAGE_SCENE_WRITERS` | 怎么把值写进去 |
| 4 | `cameraStageStoreLedger.ts` 的 `entries` | 这件事在界面上是哪个动作 |

**缺任何一处都是静默失效。** 三维场景外观 24 项当初漏掉的正是第 1、2 处。

三道门禁能在事后抓到不一致，但它们治的是症状——**因为一件事要说四遍，所以造三个机器人去核对这四遍说得一不一致**。

### 问题 2：账本只覆盖 3 / 18 个 store

| 已建账（3） | 未建账（15） |
|---|---|
| `cameraStageStore`（81 动作） | `projectStore`（20）、`settingsStore`（31）、`generationHistoryFilterStore`（16） |
| `canvasStore`（32 动作） | `navigationStore`（4）、`uiStore`（4）、`themeStore`（2） |
| `assetLibraryStore`（9 动作） | `cameraStageSessionStore` / `ToolStore` / `ViewportStore` |
| | `imageEditorUiStore` / `imageEditorHandoffStore` |
| | `assistantUiStore`、`alertDialogStore` |
| | `canvasGenerationProgressStore`、`generationTaskProgressStore` |

### 问题 3：门禁清点有 `src/stores/` 盲区

`scripts/check-assistant-capabilities.cjs` 的领域清点只遍历 `src/features/*`。而 `canvasStore`、`projectStore`、`settingsStore`、`themeStore`、`navigationStore`、`uiStore` 全在 `src/stores/`——**完全不在扫描范围内**。canvas 之所以过关，是因为它所属的 `src/features/canvas/` 目录里有 Reflection 和账本，与 store 本身在哪无关。

### 问题 4：剩余 16 项 gap

**三维 11 项**：`removeShot`、`removeShots`、`reorderShot`、`captureIntoSelectedShot`、`clearTrack`、`setShotSpatialPath`、`setShotPathAnchor`、`setEditorMode`、`bakeToProMode`、`updatePoseJoint`、`applyPosePreset`

**画布 5 项**：`clearCanvas`、`ungroupNode`、`redo`、`updateStoryboardFrame`、`reorderStoryboardFrame`

### 问题 5：两个领域全域失明

- **generation**：输入态不在 store 里，是 `src/components/MediaGenerator/state/useUIState.ts` 的 18 个 `useState`。助手只能一次性提交，不能像人一样逐步搭建。
- **imageMark**：无 Reflection、无能力、无执行器。文档态全在 `useMarkController` / `useMarkHistory` 局部态里。

## 三、总体解决思路

### 核心动作：统一字段定义

把 4 处登记压成 1 处。目标形态（最终签名以任务 1.1 的设计为准）：

```ts
sceneField('sky_color', '天空颜色', COLOR, {
  read: (settings) => settings.sky.color,
  write: (store, value) => store.setSceneSkyColor(value),
  storeAction: 'setSceneSkyColor',
})
```

从这一条派生出：属性描述、读取映射、写入表项、账本条目。

**收益**：那 24 项当初漏不掉，因为没有能单独漏掉的东西。以后新增界面设置的助手同步成本从「4 处」降到「1 处」。

**边界（重要）**：不做代码生成、不做运行时反射魔法。就是一个返回四元组的普通函数，四个消费方各取所需。保持可读、可跳转、可断点。

### 收敛不动的部分

数据分级（C0–C3）、暴露面、五档风险、revision 乐观并发——对单机应用偏重，但在跑、没添麻烦、拆除风险大于收益。**本任务不碰。**

## 四、阶段划分与依赖

```
第一阶段（收敛登记成本）
  ├─必须先于─▶ 第二阶段（三维缺口）
  ├─必须先于─▶ 第三阶段（画布缺口）
  ├─必须先于─▶ 5.4（注册生成草稿）
  └─必须先于─▶ 6.2（注册标注文档）

第四阶段（账本覆盖）      ← 与二、三阶段无依赖，可并行
第五阶段 5.1→5.2→5.3     ← 与一、二、三阶段无依赖，可并行
第六阶段 6.1             ← 与其他阶段无依赖，可并行
```

**为什么第一阶段必须在前**：先补缺口再收敛，等于用旧的高成本方式再写 16 遍，且迁移时要改两遍。

**为什么 5.2 必须在 5.3 之前**：参数联动（`getFilteredOptions`）目前在 React 层。不先提纯，助手走 store 写入会**绕过联动**，用户看到非法参数组合而界面不提示。

## 五、兼容与回退

- **对外契约不变**：本任务不改 `change_application_entities` 的输入形状，不改属性 id 命名。已有助手会话与技能不受影响。
- **第一阶段是纯重构**：迁移前后 `propertyCoverage` / `storeActionCoverage` 门禁的断言结果必须完全一致。任一门禁变化即说明迁移有偏差。
- **第五阶段分四步、每步可独立回滚**：5.1/5.2 纯提取（快照可证），5.3 纯搬家（对外 API 一字不改），5.4 只加不改。
- **回退原则**：每个任务一次独立 Git 提交。出问题 `git revert` 单个提交即可，不需要连带回滚。

## 六、全局开发约束

来自 `AGENTS.md` 与 `docs/rules/`，本任务全程适用：

- 优先通用动词；**禁止**为「设置某个值」「增删一条记录」手写专用能力。
- 新增专用能力必须书面回答「为什么不能表达成属性写入」。
- 补 `collectionWrite` 的同一次提交必须删掉功能重复的专用能力。
- 文件优先 ≤400 行，>500 行禁止继续膨胀。
- 禁止新增裸 `any`；禁止硬编码颜色；禁止同功能多份实现。
- 属性写入执行器**禁止**手写 if-else 属性链（已有静态门禁拦截）。
- 每道新门禁必须实跑断牙验证。
- 涉及鼠标操作的验证写清步骤交给用户，不自行上手。
- 每次改完必须明确告知 `✔️无需重启` 或 `⚠️ 需要重启`。

## 八、最终验收条件

1. `storeActionCoverage.test.ts` 的 `GAP_BASELINE` **降到 0**。
2. `check-assistant-capabilities.cjs` 的 `ASSISTANT_BLIND_FEATURES` 白名单**清空**。
3. 领域清点覆盖 `src/features/*` **与** `src/stores/*`，18 个 store 全部有账本或登记原因。
4. 新增一个界面设置时，助手同步接上**只需改一处**（用一次真实新增验证）。
5. `npm run check:assistant-capabilities` 与 `npm test` 全绿。
6. 实机验收（交给用户操作）：助手能删镜头卡、切专业模式、播放预览、清空画布、逐步搭建生成参数并提交。
