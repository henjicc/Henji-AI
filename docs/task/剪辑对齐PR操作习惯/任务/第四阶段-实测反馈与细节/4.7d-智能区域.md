## 做了什么

### 推理底座（`electron/main/services/local-inference/`，入口 `electron/main/local-inference-utility.ts`）

- 依赖 `onnxruntime-node@1.30.0`。Windows 包自带 `cpu`、`dml`（DirectML）、`webgpu` 三种执行提供者，没有 CUDA（CUDA 只在 Linux 包里）。
- 打包：`asarUnpack` 解包 `onnxruntime-node`（原生绑定要和同目录的 `onnxruntime.dll`、`DirectML.dll` 一起在真实目录加载）；Windows 用 `win.files` 去掉 darwin、linux、win32/arm64 原生库（约省 160MB）；`afterPack` 的随包核对新增两项：三个 win32/x64 文件必须在 `app.asar.unpacked`，且不得混入其他平台。
- 后台进程：主进程按需 `utilityProcess.fork` 一个“痕迹AI本地推理”进程，空闲 60 秒退出（释放显存与模型内存）；进程意外退出时进行中的分析以失败结束，下次自动重启进程。一次只跑一个分析（显卡与解码都是独占负载），其余排队。
- 执行提供者按顺序回退：Windows DirectML → CPU，macOS CoreML → CPU，Linux CPU（开启时 CUDA → CPU）。创建会话失败、或第一次运行失败（驱动不支持某个算子常在首帧才暴露）都换下一个，并记 `local_inference.provider.fallback`。
- 会话复用：同一模型、同一输入尺寸、同一执行顺序共用一个会话（DirectML 创建约 0.5–1.4 秒，固定尺寸后最快，见实测），最多保留 3 个。
- 取消：主进程发 cancel，当前帧结束后停止，并结束 FFmpeg 子进程。
- **Float16 问题**：onnxruntime-common 1.30 在有全局 `Float16Array`（Node 24 / Electron 42 都有）时把 float16 张量存成 `Float16Array`，原生绑定按 N-API 类型数组读取，读到 0 字节（实测报 `not enough space: expected N, got 0`，CPU 与 DirectML 都一样，RVM fp16 无法运行）。推理进程加载 onnxruntime 前移除全局 `Float16Array`，回到 `Uint16Array` 存位模式；这个进程只做推理，不影响别处。半精度换算用查表（输入 256 项、输出 65536 项）。
- 结构化日志域 `main.local_inference`（会话创建、回退、进程启动 / 空闲退出 / 意外退出）与 `main.smart_regions`（`smart_regions.analyze.start/completed/failed/cancelled`，完成时带模型、执行提供者、帧数、帧率、总耗时、等待解码与推理耗时、摘要）。

### 分析一次、缓存结果（`electron/main/services/local-inference/analysis.ts`、`electron/main/services/smart-regions/`）

- 取帧：与缩略帧、导出同一份 FFmpeg（Windows 为随包 BtbN 9.0），在后台进程里作为子进程运行，`-ss` 输入侧精确定位（相对容器起点）、`-t` 限定范围、`fps` 滤镜放到固定间隔、直接缩放到模型输入尺寸输出 RGB24 原始帧，只把小帧读进内存。
- 人脸：YuNet（640×640 固定输入，画面按比例放到左上角补零），解码与 OpenCV FaceDetectorYN 一致（三个步长网格、`sqrt(cls×obj)`、NMS 0.3），阈值 0.6；逐帧跟随用 SORT 思路（中心与宽高各一个匀速卡尔曼滤波 + IoU 贪心匹配，无额外权重）：连续命中 2 帧或单帧置信度 ≥ 0.85 才确认，确认后回补试探帧；检测丢失时按轨迹继续覆盖 0.5 秒（打码宁可多盖不漏盖）。分析帧率上限 30，播放时按轨迹在相邻两帧之间插值。
- 人物：Robust Video Matting（MobileNetV3 fp16），长边 512（16 对齐）、`downsample_ratio` 0.5，4 个时间递归状态逐帧接续（输出数组直接作为下一帧输入，不复制）；先用一帧零输入试跑，RVM 拿不到或跑不了时退到 MediaPipe Selfie（256×256，按显示比例重采样）。帧率上限 60（跟住边缘）。
- 文字：PP-OCRv4 移动端检测（长边 736、32 对齐，BGR、(x/255−0.5)/0.5），DBNet 后处理（阈值 0.3 → 连通域 → 框内平均概率 ≥ 0.6 → 按“面积×1.6/周长”外扩），轴对齐框；相邻帧并集去闪烁。帧率上限 10。
- 缓存：程序目录 `SmartRegions/`（内容寻址，上限 4GB，按最久未用清理）。一段素材 + 一种分析 = 一个 `.hsrg` 文件：16 字节前导 + JSON 头（种类、模型、起止、帧率、帧数、显示尺寸、框序列或蒙版尺寸、摘要）+ 帧索引 + 每帧 deflate 压缩的蒙版。键 = 素材内容身份 + 种类 + 格式版本 + 范围（按整秒取整）+ 帧率；同一素材同一种类另有一份小索引，新请求被已有段落覆盖就直接用（片段修短不重新分析）。
- 模型：第一次用到时经 `ensureLocalModel` 自动下载并校验（4.11）；下载期间与分析期间登记作品目录忙碌探针。
- IPC：`smartRegions:ensure`（已有缓存直接返回，否则开始或加入进行中的分析，不等待）、`smartRegions:cancel`、进度事件 `smartRegions:progress`；素材路径必须在已授权目录内。失败原因 `model` / `decode` / `inference` / `disk` 在渲染层换成用户语言。

### 接到效果上

- 存储：效果的 `mask` 槽位开放为 `{ regionId: 'face' | 'person' | 'background' | 'text', feather?, expand?, invert? }`。羽化 0–100 ≈ 边缘过渡占画面高度 0–10%，扩展 -100–100 ≈ 向外 / 向内各 0–10%，缺省按区域默认（人脸 20 / 30，人物与背景 10 / 0，文字 10 / 15）。`background` 就是人物取反。只用于视频、图片片段上的内置画面效果（代码滤镜、音频效果、文字 / 图形 / 调整图层上的效果被拒绝并说明）。`regionId` 仍是字段名，以后跟踪器的区域走同一个字段。
- 渲染（预览与导出同一路径）：渲染 Worker 拿到已分析段落（`henji-media://` 地址），按片段在这一帧的素材时间取结果——人物蒙版按 16 帧一组 Range 读取并用 `DecompressionStream` 解压，人脸 / 文字框画成椭圆 / 矩形蒙版（长边 512），再按羽化、扩展、反转处理（滑动最大最小值 + 两遍盒式模糊，都在蒙版分辨率上做，O(n)）；生成的蒙版与解压帧各留一小份缓存。合成时把蒙版上传成纹理，**用合成器自己按片段的位置、缩放、旋转画到序列尺寸**（与片段画面逐像素对齐，回放分辨率下自动同比缩小），最后在一个新着色器里 `mix(原画面, 效果后画面, 蒙版 × 效果强度)`。全场景只多占两张共用画面。
- 未就绪：区域还在分析时预览先不画这个效果（完成后自动重画当前帧）；导出前等待这一序列需要的全部区域完成，失败时以用户语言报错停止。
- 协调（`application/videoEditSmartRegions.ts`）：订阅剪辑领域变化，打开着的剪辑里凡是挂了作用区域的效果（含暂时关闭的），按片段用到的素材范围请求分析；不再需要且仍在分析的取消；失败不自动重试。由剪辑领域在应用启动时登记，不依赖剪辑页面是否打开。

### 界面

- 效果控件：内置画面效果展开后多一行“作用区域”（整个画面 / 人脸 / 人物 / 背景 / 文字）；选了区域再出现羽化、扩展（数值拖动一步撤销、可重置）、反转（开关）。分析中显示“正在分析画面 45%，完成后效果自动出现”；失败用 `UiError` 显示原因与“重试”，模型下载失败另有“去下载模型”直接打开设置 › 文件与下载 › 本地模型。文字、图形、调整图层等不能分析画面的片段不显示这一组。不展示模型名、执行提供者、缓存等内部状态。
- 效果面板“智能”文件夹：人脸打码、人脸模糊、背景虚化、背景压暗、文字打码（擦除文字的第一版：先遮挡，不修补背景）、文字模糊。拖到片段上或选中后双击即加上（内置效果 + 作用区域，一步撤销），只加到视频、图片片段，拖动高亮同一规则。

### 助手（能力增量，走通用实体读写）

- `video_edit.effect` 新增可写属性 `mask`（说明列出四种区域、羽化 / 扩展 / 反转的量纲与默认、只用于视频图片片段、写入后自动开始分析、导出自动等待）与只读属性 `region_status`（`''` / `ready` / `analyzing:45%` / `failed:<给用户的说明>`），只读原因写明“写 mask 后自动开始分析”。

- 没有专用工具、没有新 store（协调状态是普通订阅，不进 Zustand 账本）。

## 实测（RTX 4090，驱动 610.47，Windows 10，2026-10-06）

### 选型依据：单次推理每帧耗时（onnxruntime-node 1.30，随机输入，每个尺寸新建会话后跑 60 次取平均）

| 模型 | 输入 | DirectML | CPU |
|---|---|---|---|
| YuNet 人脸 | 640×640 | 1.5 ms | 5.8 ms |
| RVM 人物 | 384×216，ds 1 | 8.7 ms | 28.9 ms |
| RVM 人物 | 512×288，ds 1 | 10.5 ms | 54.6 ms |
| RVM 人物 | **512×288，ds 0.5（采用）** | **9.6 ms** | **21.2 ms** |
| RVM 人物 | 640×360，ds 1 | 14.8 ms | 84.2 ms |
| RVM 人物 | 1280×720，ds 0.25 | 14.3 ms | 44.7 ms |
| Selfie 人像 | 256×256 | 2.4 ms | 6.8 ms |
| PP-OCR 文字 | 736×416 | 6.8 ms | 90.5 ms |

- **同一个 DirectML 会话切换输入尺寸很慢**（第一个尺寸 10.8 ms，之后换尺寸变成 45–65 ms），所以会话按“模型 + 固定尺寸”复用，每个尺寸单独建会话；这条数据决定了会话复用的键。
- RVM 选 512×288、ds 0.5：DirectML 与 CPU 都在前三，CPU 也能接近实时（47 帧/秒），作为低配后备的 Selfie 只在 RVM 不可用时启用。

### 整段分析（1080p 30fps 10 秒合成样片，含 FFmpeg 解码、预处理、推理、后处理；`localInference.native.test.ts` 实测项）

| 分析 | 模型 | 执行 | 帧数 | 每帧推理 | 每帧等待解码 | 合计 |
|---|---|---|---|---|---|---|
| 人脸 | YuNet | DirectML | 300 | 2.7 ms | 1.4 ms | 2.04 s |
| 人脸 | YuNet | CPU | 300 | 6.1 ms | 1.5 ms | 2.30 s |
| 人物 | RVM | DirectML | 300 | 12.4 ms | 1.0 ms | 4.40 s |
| 人物 | RVM | CPU | 300 | 18.3 ms | 1.0 ms | 6.00 s |
| 文字 | PP-OCR | DirectML | 100 | 18.9 ms | 2.6 ms | 2.37 s |
| 文字 | PP-OCR | CPU | 100 | 39.9 ms | 2.7 ms | 4.41 s |

- 三种分析都比播放快（10 秒素材 2–6 秒分析完）；人脸摘要为 1 张人脸全程跟随，文字每帧检出字幕条，人物平均面积 16.5%。
- 真实 Electron 42 utility process 里加载 onnxruntime-node 并用 DirectML 跑 RVM：60 帧，每帧推理 8.4 ms（会话创建 541 ms）。

## 选型与决策

- **推理用 onnxruntime-node 原生**（重要记录 003）：不用 onnxruntime-web，避免与剪辑合成争用同一个 WebGPU 设备、不支持算子回落 CPU 的来回拷贝。WebGPU 执行提供者 Windows 包里也有，但实测（4.10 EfficientTAM）比 DirectML 慢约 2.6 倍，不列入顺序。
- **跟踪不用额外权重**：人脸跟随用 SORT（Bewley 2016）的卡尔曼 + IoU 思路，离线分析再加“回补试探帧”和“按轨迹覆盖丢失帧”，覆盖打码的主要失败形态（侧脸、遮挡、运动模糊）。DeepSORT / ByteTrack 需要外观模型或在线逐帧阈值调参，对打码收益小。
- **取帧用 FFmpeg 命令行**：与缩略帧、导出共用随包 FFmpeg；原生解码服务的显卡帧走渲染 Worker 的共享纹理通道，送不到后台进程，且分析是一次性批处理，不该占用预览解码会话。
- **蒙版在 CPU 上按参数生成、GPU 只做放大与混合**：蒙版分辨率只有长边 512，滑动最大最小值与盒式模糊都是 O(n)，几毫秒内完成并可缓存；放到 GPU 要多几道工序与中间纹理，且难以单测。几何对齐交给合成器本身（与片段画面同一套顶点变换），不复制一份反变换数学。
- **文字只做检测**：擦除文字第一版做打码 / 模糊（实施方案原话），真正“修补背景”需要视频修复模型，后续再评估。

## 设计自查

1. **助手只凭名称和说明，能不能用对？** 能。`mask` 的说明列出四种区域各自的用途与搭配（人脸 + 马赛克 = 打码、背景 + 模糊 = 虚化）、参数量纲与默认值、适用片段、写入后的后台分析与导出等待；`region_status` 给出可读进度与用户语言的失败原因；写错片段类型时拒绝信息说明原因并告诉改用 `mask: null`。精确测试按助手真实路径（`change_application_entities` 创建、`change` 改区域与清空、读 `region_status`、文字片段被拒）跑通。
2. **能不能让 AI 先做掉、人只确认或微调？** 能。一句“给路人脸打码”就是一个效果 + 一个区域，分析在后台自动进行、模型自动下载；用户在效果面板“智能”文件夹里也是拖一下就完成，再在效果控件里拖羽化、扩展微调或换区域。
3. **产物能不能直接流进其他工作区或其他步骤？** 区域是效果的一部分，随剪辑保存、复制粘贴效果、导出同一路径渲染；分析结果按素材内容缓存，同一素材在别的剪辑、别的片段里直接复用。推理底座（后台进程、执行提供者回退、会话复用、取帧）与结果格式会被 4.10 跟踪器直接使用，助手的“观察画面”能取帧核对打码结果。

## 后续（未做，原因）

- **天空区域**：实施方案提过“天空”，第一批模型里没有天空分割，等有合适小模型再加区域种类。
- **擦除文字（修补背景）**：需要视频修复模型，体积与速度都要另行评估；现在用打码 / 模糊遮挡。
- **区域的手动修正**：漏检或误检时还不能在监视器上补画 / 擦除，归 4.10（手绘遮罩、跟踪纠错）。
- **调整图层上的区域**：调整图层处理的是下方合成画面，不对应单一素材，暂不支持。
- **macOS CoreML**：执行顺序已写，未在 Mac 真机验证（与其他 macOS 验收一并做）。
- **超长素材的人物分析**：人物蒙版每分钟约 10–20MB 缓存，1 小时素材整段分析会占用数百 MB 并耗时十几分钟；目前按片段实际用到的范围分析，可接受，后续可考虑分析时降帧率。
