# 4.28 代理剪辑

状态：实现与定向验证完成，待总管理者审查提交、用户实测。2026-10-07；本任务不执行 Git 写操作，不修改 SDK，不启动或重启 Electron。

## 入口与行为

- 素材面板选中视频右键“创建代理…”选择 720p / 540p；后台转码，列表“代理”列显示无 / 生成中（百分比）/ 已有。右键可取消，多选串行创建；取消当前项停止本批剩余项。失败可查看正式错误提示并重新创建，不回滚已导入原片。
- 素材面板导入菜单可设置“导入高于 1080p 素材时自动创建代理”，为宽超过 1920 或高超过 1080 的视频创建默认 720p 代理。开关按剪辑文档保存为本机视图偏好，不改作品内容。
- 节目与源监视器按钮条新增“切换代理”，共用一项开关，默认关闭；已有自定义按钮布局可通过按钮编辑器添加。缺少代理的素材继续读原片。切换保持播放头时刻；节目播放中的原片声音重新接续，源监视器切换暂停在原时刻。
- 只替换回放画面，音轨与波形始终读取原片；关闭代理、导出、选帧/封面、智能区域、跟踪分析等没有显式回放授权的会话仍用原片。节目选帧先切回原片重画，取完恢复代理。

## 选型与时间契约

复用成熟 FFmpeg/libx264 和现有随包定位器、内容身份、ContentDiskCache、PAL/IPC、统一日志及 VideoEditFrameRouter，没有新增编码库或云端调用。对比 H.264 常规长 GOP、H.264 全帧内、ProRes/DNxHR、MJPEG：全帧内 H.264/yuv420p/MP4 保留现有原生与浏览器 WebCodecs 的兼容性，减少长 GOP 拖动时的帧依赖；ProRes/DNxHR/MJPEG 的文件体积与跨后端兼容性较差。选用 libx264 ultrafast、CRF 23、GOP 1、无 B 帧、两个编码线程，优先后台创建速度与随机访问。全帧内比普通 H.264 更占缓存，实际 4K 长片性能尚未验收，不宣称已达到性能目标。FFmpeg/libx264 的 GPL 分发义务复用既有随包许可流程，H.264 专利义务沿现有分发审查。

4.9 的结论是原生/WebCodecs 解码仍按码流尺寸进行，回放分辨率只降低解码后缓存/合成开销。本任务提前生成较小码流，从同一个 FrameRouter 前的图片源选择入口供两个后端使用，不改原生服务协议，不另造 WebCodecs 路径；720p/540p 为编码画面的目标高度，保持比例、偶数尺寸、不放大，不强制改原媒体几何、时长或帧率字段。

使用 `-copyts`、`-fps_mode passthrough`、`-enc_time_base demux`、禁用负时间戳自动平移，保留每帧 PTS 与非零起点；不设置 `-r`、不使用 `setpts`。ffprobe 读取真正视频流（排除封面图），生成后核对帧数与排序后的每帧 PTS，误差大于 2 微秒就拒绝发布。片段源时间、速度、倒放与序列帧率映射沿原契约，不用代理名义帧率重新换算。

依据：[FFmpeg 主文档](https://ffmpeg.org/ffmpeg.html)、[FFmpeg libx264 参数](https://ffmpeg.org/ffmpeg-codecs.html)、现有 4.9、4.16、4.20 实现。真实 FFmpeg 9 随包路径与 ffmpeg-ffprobe-static 6.1 路径各覆盖 30fps、30000/1001、丢帧形成的不规则 VFR，均保留非零起点并缩到 960×540。

## 缓存、权限与生命周期

- 缓存位于程序数据目录 `cache/video-proxies`，不在作品目录；沿既有 realpath/dev/inode/size/mtime/ctime 内容身份与预设、编码契约版本构造 SHA-256 键（没有另加全文件字节哈希）。MP4 预算 20GiB，元数据预算 16MiB，复用既有 LRU。命中核对内容身份、键、预设、实际字节大小；缺失/截断缓存淘汰。解码打开前再次验证身份及缓存可用性。
- 最大两项并行，同键重复创建拒绝；UI 多选及导入批次串行。进度只发原窗口，取消必须属于原窗口；窗口销毁、主框架导航、应用退出取消主进程任务，剪辑关闭与换源拒绝迟到挂接。原片创建前后身份不一致时不发布缓存。
- 只接受已授权本地媒体路径，再核对 realpath，拒绝软链接逃逸。仅核验通过的代理缓存目录加入已有媒体读取授权。失败/取消清理临时文件；所有错误进入已有日志，不新增日志文件或诊断通道。
- 派生缓存不进入作品撤销栈；切换与自动创建偏好沿既有视图事务读写/回滚，不增加内容历史。缓存可丢弃并重建，原片与作品路径保持原值。

## 助手覆盖分级

属于“能力增量 + 视图属性增量”。新算法能力 `generate_video_edit_proxy(documentRef, mediaRef, preset)` 为免费本地、可取消操作，只接受正式视频素材引用，回读缓存与状态核验效果；沿既有权限、操作账本与执行器登记，无专用设置工具。超时遵守目录上限 600000ms。

`video_edit.document.proxy_preference` 通用读写 `{ enabled, autoCreate }`，`video_edit.media.proxy_state` 通用只读 `{ status, progress, error }`，首次读取可恢复已有缓存。正式公共 Harness 覆盖创建、通用状态读取/切换、非法值、只读权限拒绝和事务回滚；Pi/MCP 客户端没有真实运行，不把 Harness 证据称为实机已通。

## 边界与待验收

单素材最多一百万帧，以限制主进程时间戳核对的内存；超限明确报错，不偷偷降帧。助手操作遵守统一的 10 分钟执行超时，超时取消，可从 UI 继续创建更耗时素材。透明视频拒绝生成，继续使用原片，避免丢失 alpha。代理为 8bit 4:2:0 有损图像，HDR/10bit/高色度素材的代理不能作为精确调色依据，调色检查请关闭代理；原片导出不受影响。旋转/非方形像素/多视频流、真实 4K/高码率长片、硬解设备、打包版和实机音画切换未验收；现有流选择仍是首个非封面视频流。

缓存尺寸校验不是逐字节完整性校验；同长度位损坏或已打开媒体被 LRU 淘汰的运行中恢复没有专门实测，必要时关闭代理使用原片。任务不做崩溃续转、不复制代理到作品、不自动批量预处理历史素材。首次调研与测试均未修改 SDK、文本剪辑或多机位实现。

主进程、preload 已改；总管理者集成后须更新运行产物并重启主进程，再做真实节目/源监视器、导入自动创建、取消、导出原片与 4K 性能验收。本轮按用户限制未构建、未启动/重启 Electron、未运行付费网络调用。

## 设计自查

1. **助手只凭名称和说明能否用对？** 能。创建能力说明引用来源、720p/540p、免费/取消/帧数及超时边界以及回读状态；切换走通用偏好，明示回放才使用代理，导出与分析用原片。
2. **能否 AI 先做、人只确认？** 能。助手可读素材尺寸/代理状态、创建代理并切换；导入自动创建省去逐项处理，人选择预设或切回原片检查，取消与失败状态可读。
3. **产物能否直接流进其他工作区？** 正式原片仍是共享素材，节目选帧/封面及导出输出沿原片流转既有画布/资产/图片编辑路径；代理是可丢弃的回放缓存，主动不注册为交付素材，不需要搬文件或改跨工作区引用。
