# 应用能力通用化与双路径收口实施方案

## 一、当前项目与相关功能现状

### 1. 内部应用接口已具备的基础

- `src/core/application-control/` 冻结了 `application-control/v1` 调用方中立契约：稳定引用、实体/属性反射、观察、计划、事务、撤销、验证。
- 事务引擎 `src/core/application-control/execution/engine.ts` 支持三种计划步骤：
  - `mutation`：改已有实体的属性，执行器接口 `ApplicationMutationExecutor`
  - `operation`：算法型语义操作，执行器接口 `ApplicationSemanticOperationExecutor`
  - `collection`：在父实体下增删子实体，执行器接口 `ApplicationCollectionExecutor`（2026-08-04 新增）
- 实体描述 `ApplicationEntityTypeDescriptor` 新增 `collectionWrite` 字段，声明该类型可否增删、必填属性、单次上限。
- 四个通用能力已注册并常驻活动工具集：`describe_application_entities`、`list_application_entities`、`read_application_entity`、`change_application_entities`。
- 单轮活动工具预算 32 个 / 96KB，唯一来源 `src/core/assistant/toolBudget.ts`。

### 2. 各领域覆盖现状

反射注册入口：`src/features/assistant/applicationCapabilities/applicationControlRegistry.ts`

| 领域 | 实体类型 | 属性写入 | 集合写入 | 说明 |
|---|---|---|---|---|
| settings | `settings.registry` | ✅ `SettingsMutationExecutor` | 不适用 | 单实体，无集合语义 |
| camera_stage | project / scene / object / camera / shot / trajectory / keyframe | ✅ 6 类型 | ✅ keyframe | 本次任务的样板，已完成 |
| canvas | `canvas.project` / `canvas.node` / `canvas.edge` | ⚠️ 仅 node | ❌ | 节点与连线的增删全靠 11 个专用能力 |
| storyboard | `storyboard.project` / `storyboard.card` | ❌ | ❌ | 卡片增删无通用路径 |
| image_edit | `image_edit.session` / `document` / `layer` | ❌ | ❌ | 图层增删无通用路径 |
| assets | `asset` / `asset.library` | ❌ | ❌ | 待确认可写范围 |
| toolbox | `toolbox.tool` | ❌ | ❌ | 工具由注册表定义，预计只读 |
| generation | `generation.model` / `task` / `result` | ❌ | ❌ | 模型目录只读；任务创建属算法型操作 |
| assistant_runtime | `assistant.run` / `assistant.artifact` | ❌ | ❌ | 运行时自有状态，预计只读 |

专用能力总数约 81 个（不含内置），其中 `canvasMutationApplicationCapabilities.ts` 单文件 11 个，是通用化收益最大的一处。

### 3. 已确认的双路径缺陷（本计划创建前已修复，作为判定样本）

| 缺陷 | 两条路径 | 暴露方式 |
|---|---|---|
| 活动工具数 | 运行时激活 8 / 上下文构建 8 / 事件契约 12 / 保存点契约 12 | 上限改成 16 后每次运行都被 schema 挡下 |
| token 估算 | 压缩链路按字符类别加权 / 分层预算 `length/4` / 技能索引 `预算×4` | 中文任务的活动工具被莫名砍掉 |
| 关键帧写入 | 领域层有完整轨道 API / 反射层只暴露读改 | 助手做不了任何对象动画 |
| 摄像机朝向 | 拖动时间轴写 store 后重算 / 空格播放不写 store 不重算 | 播放时镜头始终朝前 |

四例的共同结构：**语义单一，实现分叉，其中一条无人维护**。

## 二、当前存在的问题

1. **通用动词覆盖率低。** 9 个领域中只有 3 个能被通用动词写入，其余领域的能力对助手等同于不存在。
2. **专用能力增长无边界。** 每新增一个「加一条记录」都要写一个能力，遗漏无法被发现。
3. **双路径缺陷无门禁。** 四例都是在用户实测中暴露的，平均每例消耗一轮完整的「跑—查—改」循环。
4. **缺少覆盖矩阵。** 没有任何文件回答「哪些领域状态应该可写、哪些故意只读」，排除决策没有留痕。

## 三、最终目标

- 全部应该可写的领域实体都能被通用动词读改增删，助手不需要专用能力即可完成常规操作。
- 每一个只读实体都有显式的排除原因记录，不存在「没人想起来」的缺口。
- 项目内不存在同一语义的多份实现；新引入分叉时构建失败。
- 规则文档与两侧 skill 与实际约束一致。

## 四、总体解决思路

分四步推进，前两步补覆盖，第三步清历史债，第四步固化：

1. **先建矩阵再动手。** 任务 1.1 产出覆盖矩阵，后续任务按矩阵逐领域实施，避免边做边猜。
2. **按领域纵向切分。** 每个领域一个任务，独立实施、独立验证、独立提交，失败只回退单个领域。
3. **双路径按类别横切。** 采样/渲染类与能力/服务类分开处理，判定口径先统一（任务 3.1）。
4. **门禁最后统一建立。** 覆盖率与一致性门禁在实现完成后一次性接入构建，避免中途反复调整门禁本身。

## 五、技术方案

### 1. 集合写入的标准实施模式（以 camera_stage.keyframe 为参照）

每个领域按同一套四步接入：

1. **正式服务**：在领域的 `application/` 下提供批量增删服务，包含纯输入校验、失败回滚、结构化日志。校验必须在任何写入之前完成。
2. **实体声明**：在该领域的 `*Reflection.ts` 中为目标实体加 `collectionWrite`，声明 `creatable` / `removable` / `requiredPropertyIds` / `maxItemsPerChange`。
3. **集合执行器**：实现 `ApplicationCollectionExecutor`，把 `collection` 步骤翻译成对正式服务的调用，返回 `producedRefs`、`resultingRevisions`、`evidence`、`undoToken`。
4. **注册**：在 `applicationControlRegistry.ts` 中 `registerCollectionExecutor`。

参照实现：
- 服务 `src/features/cameraStage/application/cameraStageKeyframeService.ts`
- 执行器 `src/features/cameraStage/application/cameraStageKeyframeCollectionExecutor.ts`
- 声明 `src/features/cameraStage/application/cameraStageReflection.ts` 中 keyframe 分支

### 2. 安全边界

- **属性路径白名单。** 可写属性必须显式枚举，禁止放开任意路径——那等于开放任意 store patch。参照 `cameraStageKeyframeService.ts` 的 `WRITABLE_PROPERTY_PATHS`。
- **数量上限。** `maxItemsPerChange` 防止单次事务写爆。
- **校验先于写入。** 所有能靠输入判断的错误都在写入前抛出，错误信息必须列出合法取值，让模型可自我修正。
- **失败必回滚。** 领域执行器自己负责单步内部的部分写入回滚，引擎只负责跨步补偿。

### 3. 双路径的判定与收口口径

判定为双路径的条件（任务 3.1 细化）：

- 同一业务语义存在两个及以上实现入口，且
- 两者可被不同触发条件分别激活，且
- 两者不共享同一份计算或数据来源

收口方式按优先级：

1. **合并到唯一来源**：一方委托另一方（如 token 估算收口到 `tokenEstimate.ts`）。
2. **提取共享内核**：两条路径都调用同一个纯函数（如播放与导出共用 `applyAnimationToPlaybackAppliers`）。
3. **无法合并时加一致性断言**：用行为测试要求两条路径对同一输入给出同一结果。

### 4. 门禁设计

- **覆盖门禁**：声明 `collectionWrite` 的实体必须注册集合执行器（已存在，`collectionCoverage.test.ts`）；扩展为「矩阵中标记为可写的实体必须有对应执行器，标记为只读的必须有排除原因」。
- **一致性门禁**：对每一类已收口的双路径建立行为断言，要求两条路径结果一致。
- 全部门禁接入 `npm run check:assistant-capabilities` 或全量测试，随 `electron:build` 执行。

## 六、任务范围与非范围

### 范围

- `src/core/application-control/**`：仅在契约确需扩展时改动
- `src/features/*/application/**`：新增服务与集合执行器
- `src/features/assistant/applicationCapabilities/**`：注册与适配
- `electron/main/services/agent-runtime/**`：双路径收口涉及的运行时
- `docs/rules/**`、`AGENTS.md`、`.claude/skills/**`、`.codex/skills/**`：规则同步

### 非范围

- 删除或下线现有专用能力
- 界面组件的视觉与交互改造
- 新增业务功能
- 模型侧提示词调优

## 七、新旧实现兼容方式

- 通用动词与专用能力**并存**。同一操作两条都能走通，专用能力保持原有输入输出契约不变。
- 集合写入新增的是能力，不改变任何既有能力的行为，因此无数据迁移需求。
- 反射实体描述新增 `collectionWrite` 为可选字段，不声明即等同于「只能改不能建」，对既有领域零影响。

## 八、风险控制与回退

| 风险 | 控制方式 |
|---|---|
| 通用写入绕过业务校验 | 集合执行器必须调用正式服务，禁止直接操作 store；由代码评审与 `check:assistant-capabilities` 的 store patch 禁令拦截 |
| 单次写入过大拖垮界面 | `maxItemsPerChange` 上限 + 领域服务内的批量校验 |
| 活动工具位被撑爆 | 通用动词固定 4 个常驻位，新增领域不增加工具数；预算门禁 `budget-consistency.test.ts` |
| 双路径收口引入回归 | 每一类收口都先建行为断言再改实现，断言必须做断牙验证 |
| 单领域改动失败 | 按领域独立提交，回退只影响该领域 |

## 九、全局开发约束

- 遵循 `AGENTS.md` 与 `docs/rules/` 全部既有规则。
- 每个任务独立 Git 提交，提交信息用中文说明改动目的。
- 收尾前按 `docs/rules/testing.md` 跑匹配的检查，如实报告结果。
- 每次改完代码必须明确告知是否需要重启 `npm run electron:dev`。
- 新增门禁必须做断牙验证并在任务记录中写明验证输出。
- `.claude/skills/` 与 `.codex/skills/` 两侧内容必须保持一致。

## 十、最终验收条件

- [ ] 覆盖矩阵中标记为可写的实体，全部具备对应的属性写入或集合写入执行器。
- [ ] 覆盖矩阵中标记为只读的实体，全部有显式排除原因。
- [ ] 双路径清单中的每一项都已收口或有一致性断言，并注明处理方式。
- [ ] 覆盖门禁与一致性门禁全部接入构建，且均通过断牙验证。
- [ ] `npm run test`、双端 tsc、两侧 ESLint、`npm run electron:build` 全绿。
- [ ] `AGENTS.md`、相关 `docs/rules/` 与两侧 skill 已同步。
- [ ] 用户实机验证：三维、画布、图片编辑各完成一个多步任务，助手不出现「没有 XX 能力」类停摆。
