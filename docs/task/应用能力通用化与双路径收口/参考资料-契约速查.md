# 参考资料 · 契约速查

本文件把执行任务时需要反复查阅的契约、现状与约定集中在一处。**执行任务前先读本文件，不要再去逐个文件翻找。**

---

## 一、三个写入动词的契约

### 1. 属性写入（mutation）

计划步骤形状（`src/core/application-control/transactions.ts`）：

```ts
{
  kind: 'mutation',
  target: { kind: string, id: string },   // 实体稳定引用
  entityType: string,
  expectedRevisions: Record<string, number>,
  mutations: Array<{ propertyId: string, operation: 'set'|'clear'|'append'|'remove', value?: JsonValue }>
}
```

执行器接口（`src/core/application-control/execution/types.ts`）：

```ts
interface ApplicationMutationExecutor {
  readonly entityType: string
  apply(step, context): Promise<ApplicationCompletedStepResult>
  applyAtomic?(steps, context): Promise<ApplicationCompletedStepResult[]>
  compensate?(step, result, context): Promise<ApplicationEvidence[]>
  undo?(undoToken, context): Promise<ApplicationCompletedStepResult>
}
```

### 2. 集合写入（collection）

计划步骤形状：

```ts
{
  kind: 'collection',
  parent: { kind: string, id: string },   // 父实体稳定引用
  entityType: string,                     // 要增删的子实体类型
  expectedRevisions: Record<string, number>,
  operation:
    | { kind: 'create', items: Array<{ properties: Record<propertyId, JsonValue> }> }
    | { kind: 'remove', targets: Array<{ kind: string, id: string }> }
}
```

执行器接口：

```ts
interface ApplicationCollectionExecutor {
  readonly entityType: string
  apply(step, context): Promise<ApplicationCompletedStepResult>
  compensate?(step, result, context): Promise<ApplicationEvidence[]>
  undo?(undoToken, context): Promise<ApplicationCompletedStepResult>
}
```

实体描述里的声明（`src/core/application-control/reflection.ts`）：

```ts
collectionWrite: {
  creatable: boolean
  removable: boolean
  requiredPropertyIds: string[]      // 最多 32 个
  maxItemsPerChange: number          // 默认 64，最大 256
}
```

**未声明 `collectionWrite` 的实体无法被创建**，引擎在预检阶段抛 `COLLECTION_WRITE_NOT_DECLARED`。

### 3. 语义操作（operation）

用于带算法的操作（轨迹采样、碰撞检测）。本计划不新增此类，只在双路径排查时涉及。

### 引擎的预检顺序（`execution/engine.ts`）

1. `assertCompensable`：多步且非 `non_reversible` 时，每步执行器必须实现 `compensate`
2. `assertCollectionAllowed`：类型声明了可增删、必填属性齐全、数量不超上限
3. 属性可写性：`getPropertyAvailability` 返回 `writable: false` 即拒绝
4. 权限与 `normalizeInput`

**结论：能靠输入判断的错误都在预检拒绝，执行器内部只需处理执行期失败。**

## 二、执行器返回值形状

```ts
{
  status: 'completed',
  resultingRevisions: { <scope>: number },
  producedRefs: Array<{ kind, id, revision? , label? }>,
  evidence: Array<{
    kind: 'operation_result' | 'entity_state' | 'property_value',
    target?: { kind, id, revision },
    fact: string,
    data?: JsonValue,
    capturedAt: string,   // new Date().toISOString()
  }>,
  undoToken?: string,
}
```

`evidence` 不能为空：引擎在提交阶段有 `SUCCESS_EVIDENCE_REQUIRED` 断言。

## 五、实施模板

### 集合写入服务的标准结构

参照 `cameraStageKeyframeService.ts`，必须包含：

1. **属性路径/类型白名单**（模块级 `Set`），错误信息列出全部合法值
2. **`ensureProjectLoaded`** 等前置状态准备
3. **`assertXxxValid`**：纯输入校验，**在任何写入之前**调用
4. **`captureUndo`** 抓快照
5. `try { 写入; await 持久化; return } catch { await rollback(); throw }`
6. **`rollback` 自身失败单独记日志，不覆盖原始错误**
7. 结构化日志三点：`start` / `completed` / `failed`

### 错误信息的写法要求

必须让模型能自我修正。反例与正例：

- ❌ `throw new Error('NOT_FOUND')`
- ✅ `` throw new Error(`KEYFRAME_OBJECT_NOT_FOUND：第 ${index} 项的 objectId «${id}» 不在本场景中。objectId 必须取自观察结果里 objects[].id 的原值。当前可用：${available.join('、')}。`) ``

### 测试约定

- 需要真实模型注册表时：`// @vitest-environment jsdom` + `await loadRealModelsIntoRegistry()`（`src/tests/loadRealModels.ts`）
- 领域 store 测试的 mock 写法参照 `src/features/cameraStage/application/cameraStagePlacementFailure.test.ts` 顶部的 `vi.hoisted` + `vi.mock`
- 覆盖门禁参照 `src/features/assistant/applicationCapabilities/collectionCoverage.test.ts`

### 断牙验证的做法

**注意：本机 `python3` 是 Windows 商店空壳，静默不执行。改文件用 `sed -i` 或编辑工具，不要用 python。**

```bash
cp 目标文件 /tmp/备份.ts
sed -i 's/要撤掉的那一行//' 目标文件
npx vitest run 对应测试文件      # 必须变红，记录报错输出
cp /tmp/备份.ts 目标文件
```

## 六、常用命令

```bash
npx vitest run <路径>                    # 跑单个测试文件
npm run test                             # 全量单测
npm run lint                             # 渲染层 ESLint
npx eslint electron --ext ts             # 主进程 ESLint
npx tsc --noEmit -p tsconfig.json        # 渲染层类型检查
npx tsc --noEmit -p tsconfig.node.json   # 主进程类型检查
npx tsc --noEmit -p tsconfig.electron.json   # electron:build 用的那份，含测试文件
npm run check:assistant-capabilities     # 能力覆盖与旧路径禁令
npm run electron:build                   # 五道门禁 + 双端 tsc + 构建
```

`electron:build` 使用的类型配置是 `tsconfig.electron.json`，它**包含测试文件**，而 `tsconfig.node.json` 不包含。只跑后者会漏掉测试文件的类型错误。

## 七、必须遵守的既有规则

| 场景 | 规则文件 |
|---|---|
| 新增模块、跨层调用、目录结构 | `docs/rules/architecture.md` |
| 改动 `src/features/canvas/**`、画布性能 | `docs/rules/canvas.md` |
| 新增能力、Surface、设置项 | `docs/rules/assistant-capability.md` + skill `henji-application-capability` |
| 收尾前的检查选择 | `docs/rules/testing.md` |
| 日志 | `docs/rules/logging.md` |

硬性约束（`AGENTS.md`）：

- 禁止在能力层直接 store patch，写入必须委托领域服务
- 禁止为「设置某个值」「增删一条记录」手写专用能力
- 新文件优先 ≤400 行，>500 行禁止继续膨胀
- 禁止新增裸 `any`
- 每次改完代码必须明确告知 `✔️无需重启` 或 `⚠️ 需要重启`
