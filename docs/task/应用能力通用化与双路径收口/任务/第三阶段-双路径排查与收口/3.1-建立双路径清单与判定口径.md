# 3.1 建立双路径清单与判定口径

## 任务状态

- 状态：已完成
- 所属阶段：第三阶段 · 双路径排查与收口
- 前置任务：无
- 关联任务：3.2、3.3、4.1
- 是否可以并行：可与第一阶段全部任务并行

## 任务目标

产出一份全项目双路径清单，逐条记录「同一语义、两处实现」的位置、触发条件、当前是否已分叉、建议的收口方式。清单是任务 3.2 与 3.3 的唯一依据，也是任务 4.1 建立一致性门禁的输入。

## 当前情况

本项目已确认并修复四例，它们是判定口径的样本：

| 样本 | 两条路径 | 分叉后果 | 已用的收口方式 |
|---|---|---|---|
| 活动工具数 | 运行时激活 / 上下文构建 / 事件契约 / 保存点契约，四处各写一份 | 改上限后每次运行都被 schema 挡下 | 收口到 `src/core/assistant/toolBudget.ts` 具名常量 |
| token 估算 | 压缩链路加权 / 分层预算 `length/4` / 技能索引 `预算×4` | 中文任务的活动工具被莫名砍掉 | 收口到 `src/core/assistant/tokenEstimate.ts` |
| 关键帧写入 | 领域层完整轨道 API / 反射层只暴露读改 | 助手做不了任何对象动画 | 补齐缺失的一侧（集合写入动词） |
| 摄像机朝向 | 拖动写 store 后重算 / 播放不写 store 不重算 | 播放时镜头始终朝前 | 在共享采样层补齐，复用已有 applier 通道 |

共同结构：**语义单一，实现分叉，其中一条无人维护**。四例全部由用户实测暴露，说明缺少系统性排查手段。

已知的高风险区域（待本任务确认）：
- `src/features/cameraStage/`：编辑态与播放态、预览与离屏导出
- `electron/main/services/agent-runtime/context/`：预算、估算、裁剪
- `src/features/assistant/applicationCapabilities/`：专用能力与通用动词对同一状态的两条写入路径
- `src/features/canvas/`：界面交互写入与能力写入
- `src/core/application-control/`：计划器与引擎各自的校验

## 实施方案

分四类系统排查，每类给出明确的检索线索，避免漫无目的地翻代码：

1. **预算与阈值类**：同一个数字在多处出现。检索线索是数值字面量与常量名不一致的地方。
2. **采样与渲染类**：同一份状态被「响应式路径」与「命令式路径」分别消费。检索线索是 `useFrame`、`registerPlaybackApplier`、`requestAnimationFrame`、`setState` 的组合出现。
3. **能力与服务类**：同一业务操作既有专用能力实现又有服务层实现，或两个适配器各自翻译。检索线索是同名动词出现在 `capabilities/` 与 `application/` 两侧。
4. **校验与契约类**：同一条约束在 schema 与运行时各写一份。检索线索是 `.max(`、`slice(`、`throw new Error('` 与 schema 定义的对应关系。

对每一条候选，按判定条件确认是否成立：

- 同一业务语义存在两个及以上实现入口
- 两者可被不同触发条件分别激活
- 两者不共享同一份计算或数据来源

三条全部成立才计入清单。只是「调用了同一个函数的两个地方」不算。

## 执行步骤

1. 在计划目录下新建 `双路径清单.md`，建立表格骨架：位置 A、位置 B、共同语义、触发条件差异、是否已分叉、风险等级、建议收口方式、归属任务。
2. **预算阈值类排查**：检索 `electron/main/services/agent-runtime/` 与 `src/core/assistant/` 下的数值上限，逐个确认是否已收口到具名常量，未收口的计入清单。
3. **采样渲染类排查**：检索 `src/features/cameraStage/scene/` 与 `store/` 下同时存在响应式与命令式写入的状态，重点确认导出链路是否与预览共用采样函数。
4. **能力服务类排查**：对第一、第二阶段涉及的每个领域，比对 `src/core/assistant/capabilities/<领域>*.ts` 中的能力动词与 `src/features/<领域>/application/` 中的服务函数，找出同一操作的两条实现。
5. **校验契约类排查**：检索各 `*ApplicationCapabilities.ts` 中的 schema 上限与对应服务/执行器中的截断、循环上限，确认是否同源。
6. 对每条候选按判定条件确认，剔除不成立项，保留项标注风险等级（高：已知会导致用户可见故障；中：结果不一致但不致停摆；低：仅维护成本）。
7. 为每条保留项指定收口方式与归属任务（3.2 或 3.3），并在 `00-任务总览.md` 的任务清单中确认是否需要新增任务。
8. 将四例样本一并写入清单并标注「已收口」，作为门禁设计的参照。
