# 3.3 收口能力与服务类双路径

## 任务状态

- 状态：已完成
- 所属阶段：第三阶段 · 双路径排查与收口
- 前置任务：3.1
- 关联任务：4.1
- 是否可以并行：可与 3.2 并行

## 任务目标

把双路径清单中归类为「能力与服务」「校验与契约」的条目全部收口，确保同一业务操作只有一份真实实现，同一条约束只有一个定义处。

## 当前情况

- 本次任务新增的通用动词与既有专用能力**会对同一状态形成两条写入路径**，这是设计上的有意共存，但要求两条路径**最终落到同一个领域服务**。若某个专用能力绕过服务直接改 store，就构成真正的分叉。
- 已知的结构性风险点：
  - 专用能力适配器：`src/features/assistant/applicationCapabilities/` 下 `registerCanvasCapabilityHandlers.ts`、`registerAssetCapabilityHandlers.ts`、`registerGenerationCapabilityHandlers.ts`、`registerToolboxCapabilityHandlers.ts`、`cameraStageCapabilityAdapter.ts`、`applicationReflectionAdapter.ts`
  - 计划器与引擎各自的校验：`src/core/application-control/execution/planner.ts` 与 `engine.ts`。本次已把集合写入的可行性判定统一放在引擎，计划器只做并发基线复核，需确认其余判定没有两份。
  - schema 上限与运行时截断：各 `*ApplicationCapabilities.ts` 的 `.max(` 与对应服务中的 `slice(`
- `check:assistant-capabilities` 已能拦截「能力层直接 Store Patch」，但拦不住「两个服务函数做同一件事」。

## 实施方案

按三种收口方式分别处理：

1. **委托收口**：专用能力改为调用与通用动词相同的领域服务，删除其内部的重复实现。这是首选方式，不改变专用能力的对外契约。
2. **常量收口**：同一条约束抽成具名常量，schema 与运行时共同引用。参照 `src/core/assistant/toolBudget.ts` 的写法。
3. **断言兜底**：确实无法合并的，写一致性断言要求两条路径对同一输入给出同一结果。

处理顺序按清单中的风险等级，高风险优先。

不改变任何专用能力的输入输出契约——本任务只统一内部实现，对外行为必须完全不变。

## 执行步骤

1. 打开 `双路径清单.md`，筛出归类为「能力与服务」「校验与契约」且归属本任务的条目，按风险等级排序。
2. 对每条「能力与服务」条目：
   - 确认两条路径最终调用的函数
   - 若专用能力有独立实现，改为委托到领域服务
   - 保留专用能力的输入输出契约不变，用既有测试确认对外行为未变
3. 对每条「校验与契约」条目：
   - 确认 schema 上限与运行时截断的实际数值
   - 抽成具名常量，两侧引用同一份
   - 在 `budget-consistency.test.ts` 或对应契约测试中补一条行为断言：按上限造满载数据，要求通过契约
4. 复核 `planner.ts` 与 `engine.ts` 的职责边界：同一类判定只应存在于一处，重复的移除并在注释中写明判定归属。
5. 逐条做断牙验证：撤掉收口改动，确认对应断言变红。
6. 运行 `npm run check:assistant-capabilities`，确认没有新增的 store patch 或旧路径。
7. 按 `docs/rules/testing.md` 跑相关检查。
