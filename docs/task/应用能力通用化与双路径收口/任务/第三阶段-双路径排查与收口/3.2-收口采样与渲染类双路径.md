# 3.2 收口采样与渲染类双路径

## 任务状态

- 状态：待开始
- 所属阶段：第三阶段 · 双路径排查与收口
- 前置任务：3.1
- 关联任务：4.1
- 是否可以并行：可与 3.3 并行

## 任务目标

把双路径清单中归类为「采样与渲染」的条目全部收口，使同一份场景状态在编辑态、播放态、导出态三条链路上得到一致结果，并为每条收口建立行为断言。

## 当前情况

- 3D 镜头参考存在两套状态消费方式，这是设计使然而非缺陷：
  - **编辑/拖动态**：写 zustand store，组件响应式重渲染（`cameraStageStore.ts` 第 649 行 `applySampledObjectsSilently`）
  - **播放态**：按性能约束不写 store，逐帧命令式直改 three 对象（`StagePlaybackDriver.tsx` + `playbackAppliers.ts`）
- 风险不在于「有两套」，而在于**某个状态只在其中一套里被处理**。已修复的摄像机朝向缺陷正是如此：朝向由 `lookAt` 解算，只有 store 路径会重算。
- 已收口部分：`applyAnimationToPlaybackAppliers` 现在会按采样位置重算摄像机朝向，播放与离屏导出共用同一条采样路径（见 `playbackAppliers.ts` 顶部注释）。
- 待确认（由任务 3.1 清单给出）：除朝向之外，是否还有其他「只在 store 路径处理」的状态，例如摄像机效果器、可见性、颜色、角色姿态、雾效等。

## 实施方案

对清单中每一条采样渲染类条目：

1. **先建断言再改实现**。为该状态写一条行为断言：给定同一份场景与时间点，两条路径必须得到一致结果。断言先失败，再动实现。
2. **优先提取共享内核**。让两条路径调用同一个纯函数计算结果，差异只保留在「结果怎么写出去」（写 store 还是直改 three 对象）。
3. 无法提取共享内核的，保留断言作为长期护栏，并在清单中注明原因。

不要为了统一而取消命令式播放路径——它是明确的性能约束（见 `playbackAppliers.ts` 文件头注释与 3.1 方案），本任务不改变这一架构决定。

## 执行步骤

1. 打开 `双路径清单.md`，筛出归类为「采样与渲染」且归属本任务的条目。
2. 对每条条目，确认两条路径的实际入口函数与触发条件，记录在清单中。
3. 为每条条目新增行为断言测试：构造同一场景与时间点，分别经两条路径求值，断言结果一致。参照 `src/features/cameraStage/store/playbackCameraLookAt.test.ts` 的写法。
4. 运行断言，记录哪些条目当前就不一致（真实缺陷）、哪些一致（仅结构风险）。
5. 对不一致的条目实施收口：提取共享纯函数，两条路径改为调用它。
6. 对一致但结构分叉的条目，保留断言作为护栏，不强行重构。
7. 逐条做断牙验证：撤掉收口改动，确认对应断言变红。
8. 确认离屏导出链路与播放链路仍共用同一采样入口，未因本次改动分叉。
9. 按 `docs/rules/testing.md` 与 `docs/rules/canvas.md` 跑相关检查，重点确认播放帧率未退化。
