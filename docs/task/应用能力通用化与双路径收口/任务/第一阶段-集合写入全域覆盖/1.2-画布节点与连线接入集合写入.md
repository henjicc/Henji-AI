## 任务目标

让助手能够通过通用动词 `change_application_entities` 在画布上新增和删除节点与连线，不再必须依赖专用能力。完成后，画布的「加一个节点」「连两个节点」「删几个节点」三类操作都存在通用路径。

## 当前情况

### 实体与属性（实测）

`src/features/canvas/application/canvasReflection.ts`，三个实体：

| 实体 | 属性 id（去前缀） | 可写性 |
|---|---|---|
| `canvas.project` | `name` / `node_count` / `edge_count` | `name` 可写，两个计数只读 |
| `canvas.node` | `project_ref` / `node_type` / `display_name` / `position` | `display_name`、`position` 可写；`project_ref`、`node_type` 只读 |
| `canvas.edge` | `project_ref` / `source_ref` / `target_ref` / `source_handle` / `target_handle` | **全部只读** |

`canvas.edge` 全部只读是逐条声明的结果，理由充分（端点由正式连接操作维护、端口来自节点目录与连接校验）。**因此连线只需要"创建/删除"，不需要"修改"——本任务的集合写入正是它唯一的通用写入路径。**

节点引用格式：`${projectId}:${nodeId}`（见 `canvasReflection.ts` 第 115 行 `childRef`）。

### 约束

画布性能敏感，改动需遵守 `docs/rules/canvas.md`。集合写入是低频操作，但批量创建时要避免每条触发一次全量重渲染——优先一次性提交后再持久化。

## 实施方案

按实施方案第五节的四步标准模式接入，复用既有的画布服务，不新增业务逻辑：

1. 在 `src/features/canvas/application/` 下新增集合写入服务，提供节点批量新增/删除、连线批量新增/删除，内部调用既有的 `canvasMutationService` / `canvasApplicationService`。
2. 在 `canvasReflection.ts` 为 `canvas.node` 与 `canvas.edge` 声明 `collectionWrite`，父实体为 `canvas.project`。
3. 新增集合执行器，把 `collection` 步骤翻译为对上述服务的调用。
4. 在 `applicationControlRegistry.ts` 注册。

按实测属性推导的 `collectionWrite` 声明（执行时按实际情况微调）：

```ts
// canvas.node，父实体 canvas.project
collectionWrite: {
  creatable: true,
  removable: true,
  requiredPropertyIds: ['canvas.node.node_type'],
  maxItemsPerChange: 64,
}

// canvas.edge，父实体 canvas.project
collectionWrite: {
  creatable: true,
  removable: true,
  requiredPropertyIds: ['canvas.edge.source_ref', 'canvas.edge.target_ref'],
  maxItemsPerChange: 64,
}
```

注意 `node_type` 与 `source_ref` / `target_ref` 都是**只读属性**——只读指的是「创建后不可修改」，不妨碍它们作为创建时的必填项。这一点在 `camera_stage.keyframe` 上同理（`object_ref` 与 `property_path` 都是只读且必填）。

节点类型必须走白名单（记录 002），白名单来源是画布节点注册表 `src/features/canvas/**/nodeRegistry.ts`，执行时确认准确路径。

参照实现：`src/features/cameraStage/application/cameraStageKeyframeService.ts` 与 `cameraStageKeyframeCollectionExecutor.ts`；标准结构见 `参考资料-契约速查.md` 第五节。
