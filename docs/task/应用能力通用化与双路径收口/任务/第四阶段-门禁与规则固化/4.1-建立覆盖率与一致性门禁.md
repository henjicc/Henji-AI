# 4.1 建立覆盖率与一致性门禁

## 任务状态

- 状态：已完成
- 所属阶段：第四阶段 · 门禁与规则固化
- 前置任务：2.3、3.2、3.3
- 关联任务：4.2
- 是否可以并行：否

## 任务目标

把前三阶段的结论变成构建期门禁：新增领域忘了接通用动词、新引入双路径分叉，都要在 `npm run electron:build` 阶段失败，而不是等用户实测发现。

## 当前情况

现有门禁及其覆盖范围：

| 门禁 | 位置 | 覆盖 | 不覆盖 |
|---|---|---|---|
| 旧路径禁令 | `scripts/check-assistant-capabilities.cjs` | 旧 command/query、eval、能力层 store patch | 覆盖率、一致性 |
| 集合覆盖 | `src/features/assistant/applicationCapabilities/collectionCoverage.test.ts` | 声明 `collectionWrite` 却没注册执行器 | 反过来：该可写却没声明 |
| 预算一致性 | `electron/main/services/agent-runtime/context/budget-consistency.test.ts` | 满载数据能否通过契约、通用动词是否常驻 | 新增领域的覆盖率 |
| 反射注册表可建 | `applicationControlRegistry.test.ts` | 全领域注册项能否建起来 | 是否覆盖完整 |

缺口是明确的：**没有任何门禁能回答「这个实体该可写却没人实现」**。任务 2.3 引入的 `writeExclusion` 正是为了补上这个缺口——有了它，「无执行器且无排除原因」就是一个可判定的错误状态。

## 实施方案

新增两类门禁，接入既有的 `check:assistant-capabilities` 链路：

1. **覆盖率门禁**：遍历反射注册表全部实体，要求每个实体满足二选一——有写入执行器（属性或集合），或有 `writeExclusion.reason`。两者皆无即失败，失败信息列出实体 id 与所属领域。
2. **一致性门禁**：把任务 3.2、3.3 建立的行为断言归拢，确保它们随构建执行而不是散落在各模块测试里被遗忘。归拢方式是在断言文件顶部注明所属清单条目编号，并在双路径清单中反向链接测试文件路径。

门禁必须**先失败再通过**：接入后临时移除一个实体的执行器与排除原因，确认门禁报错且信息可定位，随后恢复。

## 执行步骤

1. 确认任务 2.3 已完成，`writeExclusion` 字段可用且全部只读实体已填写。
2. 扩展 `src/features/assistant/applicationCapabilities/collectionCoverage.test.ts`，或新建同目录下的覆盖率测试：
   - 构建完整反射注册表（需先装真实模型，参照 `src/tests/loadRealModels.ts`）
   - 取出全部实体，逐个判定是否有 mutation 执行器、collection 执行器或 `writeExclusion`
   - 三者皆无则失败，错误信息列出实体 id、所属领域、以及应当补哪一项
3. 断牙验证覆盖率门禁：临时移除某个实体的排除原因，确认变红且信息可定位。
4. 归拢一致性断言：检查任务 3.2、3.3 产出的断言测试是否都在 `npm run test` 范围内；在每个断言文件顶部注明对应的双路径清单条目。
5. 在 `双路径清单.md` 中为每条已处理条目回填对应的测试文件路径，形成双向链接。
6. 确认 `npm run electron:build` 会执行上述全部门禁；若 `check:assistant-capabilities` 未包含，将其加入该脚本的调用链。
7. 完整跑一次 `npm run electron:build`，确认五道门禁全绿。
