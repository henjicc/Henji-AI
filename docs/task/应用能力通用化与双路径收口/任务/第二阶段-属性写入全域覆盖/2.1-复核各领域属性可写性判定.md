# 2.1 复核各领域属性可写性判定

## 任务状态

- 状态：待开始
- 所属阶段：第二阶段 · 属性写入全域覆盖
- 前置任务：1.1
- 关联任务：2.2、2.3、4.1
- 是否可以并行：可与 1.2、1.3、1.4 并行

## 任务目标

把「一刀切写死的只读」与「逐条判断后确实该只读」区分开，得出每个属性的真实可写性判定。本任务只做判定与声明结构的修正，不实现执行器（执行器由 2.2 完成）。

## 当前情况

实测结果（详见 `参考资料-契约速查.md` 第三节）：

| 实体 | 可写属性 | 只读属性 | 只读理由的写法 |
|---|---|---|---|
| `canvas.project` | `name` | `node_count`、`edge_count` | 逐条声明 ✅ |
| `canvas.node` | `display_name`、`position` | `project_ref`、`node_type` | 逐条声明 ✅ |
| `canvas.edge` | **无** | 全部 5 个 | 逐条声明 ✅ |
| `storyboard.*` | **无** | 全部 5 个 | ⚠️ **helper 硬编码，一刀切** |
| `image_edit.*` | **无** | 全部 9 个 | ⚠️ **helper 硬编码，一刀切** |
| `asset` | `tags` | 其余 5 个 | 逐条声明 ✅ |
| `asset.library` | **无** | `name` | 逐条声明 ✅ |

两处一刀切的具体位置：

- `src/features/canvas/application/storyboardReflection.ts` 第 28 行的 `property()` helper，`readOnlyReason` 写死为「当前分镜对象通过画布分镜编辑器与正式画布事务维护。」，函数签名**不接受** `readOnlyReason` 参数。
- `src/features/imageEdit/application/imageEditReflection.ts` 第 29 行的 `property()` helper，写死为「编辑内容通过正式预览与提交操作维护。」，同样不接受参数。

对照写法正确的领域（`assetReflection.ts` 第 34 行）：helper 的第 5 个参数是可选的 `readOnlyReason`，不传即为可写，`requiredPermissions.write` 也随之变化。

**这意味着分镜与图片编辑两个领域内，没有任何属性有可能被声明为可写——不是逐条判断的结果，而是 helper 的结构决定的。** 这正是本计划要消除的模式：判定被结构固化，没人做过真正的决策。

需要重新判断的候选（不预设结论，执行时逐条确认）：

- `image_edit.layer.enabled`：图层启停在界面上就是一个开关，助手大概率也应该能开关
- `image_edit.layer.params`：图层参数在界面上可调
- `storyboard.card.node_type`：卡片类型是否可改，取决于记录 004 的从属关系判定
- `asset.display_name`：素材显示名在界面上能否重命名

**注意：`canvas.edge` 全部属性只读是逐条声明的结果，且理由充分（端点由正式连接操作维护、端口来自节点目录与连接校验），本任务不改动它。连线是"创建/删除"而不是"修改"，由任务 1.2 的集合写入覆盖。**

## 实施方案

三步走，先修结构再做判定：

1. **修正两处 helper 的结构**：让 `storyboardReflection.ts` 与 `imageEditReflection.ts` 的 `property()` 接受可选 `readOnlyReason` 参数，写法对齐 `assetReflection.ts`。修正后默认行为保持不变（全部传入原有理由），确保这一步零行为变化。
2. **逐条判定**：对两个领域的每个属性，按「界面上用户能不能改」「领域服务有没有对应更新入口」两条判断是否应当可写。
3. **只改声明不改实现**：判定为可写的属性去掉 `readOnlyReason`，但**此时还没有 mutation 执行器**，写入会命中 `MUTATION_EXECUTOR_NOT_FOUND`。因此本任务完成后必须紧接 2.2，两者之间不要发版。

判定原则：

- 界面上用户能直接改的，原则上助手也应该能改
- 领域服务没有对应更新入口的，保持只读并说明「由 XX 链路维护」，本任务不新增业务写入逻辑
- 由系统计算或外部导入产生的（计数、尺寸、检查状态、媒体路径），一律只读

## 执行步骤

1. 打开 `参考资料-契约速查.md` 第三节，确认属性可写性现状表仍与代码一致（若不一致，先更新该表）。
2. 修改 `storyboardReflection.ts` 第 28 行的 `property()`：增加可选第 5 参数 `readOnlyReason?: string`，`requiredPermissions.write` 按有无理由取 `[]` 或 `['storyboard:write']`，`readOnlyReason` 改为条件展开。所有现有调用点显式传入原有理由字符串，保证行为不变。
3. 运行 `npm run test` 确认第 2 步零行为变化。
4. 对 `imageEditReflection.ts` 第 29 行的 `property()` 做同样的结构修正，写权限用 `['image_edit:write']`。
5. 运行 `npm run test` 确认第 4 步零行为变化。
6. 逐条判定分镜 5 个属性与图片编辑 9 个属性：
   - 打开对应的界面组件，确认该属性在界面上能否被用户直接修改
   - 在领域 `application/` 目录下查找对应的更新函数
   - 两者都成立才判为可写
7. 判定为可写的属性去掉 `readOnlyReason` 参数；判定为只读的把一刀切的通用理由改为**针对该属性**的具体理由（说明由哪个链路维护）。
8. 同步更新 `覆盖矩阵.md` 与 `参考资料-契约速查.md` 第三节的表格。
9. 在 `重要记录.md` 记录判定结论与依据。
10. 运行 `npm run test`、`npm run lint`、`npx tsc --noEmit -p tsconfig.electron.json`。

## 风险与注意事项

- 本任务完成后，判定为可写的属性**尚无执行器**，写入会失败。必须与 2.2 连续执行，中间不发版。
- 修改 helper 时若漏传某个调用点的 `readOnlyReason`，该属性会静默变为可写。第 3、5 步的零变化验证就是为了拦住这种情况，不可跳过。
