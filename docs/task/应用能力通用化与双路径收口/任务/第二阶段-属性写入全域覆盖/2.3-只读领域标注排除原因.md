# 2.3 只读领域标注排除原因

## 任务状态

- 状态：待验证
- 所属阶段：第二阶段 · 属性写入全域覆盖
- 前置任务：1.1
- 关联任务：4.1
- 是否可以并行：可与 2.1、2.2 并行

## 任务目标

为覆盖矩阵中判定为只读的实体在代码中留下显式、可被门禁读取的排除原因，使「有意只读」与「忘了实现」在机器层面可区分。这是任务 4.1 覆盖门禁能够成立的前提。

## 当前情况

- 目前只有属性级别有 `readOnlyReason`（见各 `*Reflection.ts` 中 `property(...)` 的选项），**实体级别没有任何排除标记**。
- 因此无法区分：`toolbox.tool` 没有写入执行器是因为工具由静态注册表定义（有意），还是因为没人实现（遗漏）。
- 预计判定为只读的实体（最终以任务 1.1 矩阵为准）：
  - `toolbox.tool`：工具由 `src/features/toolbox/` 的注册表定义，不是用户数据
  - `generation.model`：模型目录来自 `src/models/**` 的静态定义
  - `generation.task` / `generation.result`：任务由生成链路创建，创建属算法型操作，已有专用能力 `create_visible_generation_task`
  - `assistant.run` / `assistant.artifact`：运行时自有状态，由 Agent 运行时维护
  - `settings.registry`：单实体，无集合语义，属性写入已具备
- 上述判定均标记为「待矩阵确认」，本任务不自行拍板。

## 实施方案

在实体描述层增加显式的只读排除声明，而不是靠「没有执行器」来隐式表达：

1. 评估两种记录方式，二选一并在 `重要记录.md` 说明选择原因：
   - **方式甲**：在 `ApplicationEntityTypeDescriptor` 增加可选字段 `writeExclusion: { reason: string }`，由各领域 reflection 声明。优点是与实体描述同源、门禁可直接读取；代价是动契约。
   - **方式乙**：在覆盖矩阵文档中维护清单，门禁从文档解析。优点是不动契约；代价是文档与代码可能漂移。
2. 建议采用方式甲：本计划的核心结论就是「声明与实现必须同源」，把排除原因放在文档里等于再造一处会漂移的副本。
3. 为矩阵中每个只读实体填写排除原因，原因必须说明「这个状态由谁维护」，不使用「暂不需要」这类无法验证的表述。

## 执行步骤

1. 打开 `覆盖矩阵.md`，取出全部标记为「只读」的实体清单。
2. 在 `重要记录.md` 记录方式甲/乙的选择及原因。
3. 若选方式甲：在 `src/core/application-control/reflection.ts` 的 `applicationEntityTypeDescriptorSchema` 增加可选字段 `writeExclusion`，字段含 `reason`（1~500 字符）。
4. 为每个只读实体在其 `*Reflection.ts` 中填写 `writeExclusion.reason`，说明该状态由哪个模块维护、为什么不开放给助手写入。
5. 检查是否存在「既没有写入执行器、也没有 writeExclusion」的实体；若有，说明矩阵有遗漏，回到任务 1.1 补充。
6. 运行 `npm run check:assistant-capabilities` 与全量测试，确认契约扩展未破坏既有注册。
7. 按 `docs/rules/testing.md` 跑相关检查。
