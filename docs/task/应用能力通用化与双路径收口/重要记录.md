# 重要记录

## 记录 001：通用动词与专用能力长期共存，不做能力下线

- 日期：2026-08-04
- 状态：已确定
- 背景：反射层的三个通用动词（读属性、改属性、增删集合成员）已经可用之后，画布等领域存在大量功能重叠的专用能力，例如 `canvasMutationApplicationCapabilities.ts` 里的 11 个。一次性下线可以减少能力数量，但会同时改变所有既有调用方的契约。
- 最终决定：本任务只补通用路径，不删除、不下线任何专用能力。专用能力的输入输出契约保持完全不变，内部实现可以下沉到与通用动词相同的领域服务。
- 选择原因：能力下线是对外契约变更，风险与本任务的目标无关；而且专用能力承载了算法型语义（碰撞检测、轨迹采样），本来就不该被属性写入取代。把两件事分开做，回退粒度更小。
- 影响任务：1.2、1.3、1.4、3.3

## 记录 002：集合写入的属性路径必须走白名单

- 日期：2026-08-04
- 状态：已确定
- 背景：3D 关键帧集合写入实现时面临选择——是允许任意属性路径，还是枚举可写路径。允许任意路径实现简单，且对模型更灵活。
- 最终决定：必须白名单。参照 `src/features/cameraStage/application/cameraStageKeyframeService.ts` 的 `WRITABLE_PROPERTY_PATHS`，只放开 position / rotation / scale 九个轴。
- 选择原因：放开任意路径等价于开放任意 store patch，`AGENTS.md` 与 `check:assistant-capabilities` 明确禁止。白名单同时让错误信息能列出合法取值，模型可以自我修正。
- 影响任务：1.2、1.3、1.4

## 记录 006：新增门禁必须做断牙验证

- 日期：2026-08-04
- 状态：已确定
- 背景：本次开发过程中出现过「门禁写了但其实测不到东西」的情况——用来临时撤销修复的脚本工具在本机是空壳，静默什么都没做，导致门禁看起来是绿的，实际从未被验证过。
- 最终决定：每一条新增门禁都必须做断牙验证：临时撤掉对应修复，确认门禁变红，记录实际报错输出，然后恢复。验证输出写入任务执行记录。
- 选择原因：没有做过断牙验证的门禁不能证明它能拦住问题，等同于没有门禁，而且会造成虚假的安全感。
- 影响任务：全部涉及新增测试的任务

## 记录 007：分镜与图片编辑的只读判定是 helper 硬编码，不是逐条决策

- 日期：2026-08-04
- 状态：已确定
- 背景：建立计划时假设各领域「有些属性可写、有些只读」，据此设计了第二阶段的两个任务。实测后发现事实不同：
  - `storyboardReflection.ts` 第 28 行与 `imageEditReflection.ts` 第 29 行的 `property()` helper 把 `readOnlyReason` 写死在函数体里，**函数签名根本不接受这个参数**。
  - 因此这两个领域内没有任何属性有可能被声明为可写，与属性本身的语义无关。
  - 对照 `assetReflection.ts` 第 34 行：helper 的第 5 参数是可选的 `readOnlyReason`，不传即可写，`requiredPermissions.write` 随之变化。这是正确写法。
- 最终决定：第二阶段重新划分。原 2.1、2.2 作废，改为：
  - 新 2.1「复核各领域属性可写性判定」：先修正两处 helper 的结构（零行为变化），再逐条判定。
  - 新 2.2「为确认可写的属性补齐执行器」：按 2.1 结论补执行器。
  - 同时发现 `asset.tags` 是**已声明可写但没有 mutation 执行器**的悬空声明——`describe_application_entities` 会告诉模型它可写，实际写入必然失败。这是既有缺陷，由新 2.2 闭合。
- 选择原因：「判定被结构固化、没人做过真正决策」正是本计划要消除的模式。如果按原计划直接补执行器，等于在一个从未被判断过的只读集合上做实现，方向就错了。
- 影响任务：2.1、2.2、2.3、4.1

## 记录 008：canvas.edge 只需要创建删除，不需要属性修改

- 日期：2026-08-04
- 状态：已确定
- 背景：`canvas.edge` 的 5 个属性全部只读，且理由是逐条声明的：`project_ref` 所属项目不可变更、`source_ref` / `target_ref` 端点通过正式连接操作维护、`source_handle` / `target_handle` 端口来自节点目录与连接校验。
- 最终决定：不为 `canvas.edge` 补 mutation 执行器。连线的通用写入路径只有集合写入（创建/删除），由任务 1.2 覆盖。
- 选择原因：改一条连线的端点在语义上等于「删掉重连」，强行支持属性修改会绕过连接校验。只读判定本身是对的，不需要复核。
- 影响任务：1.2、2.1、2.2

## 记录 009：只读属性可以作为创建时的必填项

- 日期：2026-08-04
- 状态：已确定
- 背景：设计 `collectionWrite.requiredPropertyIds` 时出现疑问——`canvas.node.node_type` 声明为只读，能否作为创建必填项。
- 最终决定：可以。「只读」的含义是**创建后不可修改**，不影响它在创建时必须提供。`camera_stage.keyframe` 已经这么做：`object_ref` 与 `property_path` 都是只读且必填。
- 选择原因：这两个概念在契约上是分开的——属性可写性由 `getPropertyAvailability` 判定，创建必填项由 `collectionWrite.requiredPropertyIds` 判定，引擎的预检分别处理，互不干扰。
- 影响任务：1.2、1.3、1.4
