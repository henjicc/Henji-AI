# 4.3 错误诊断入口

## 任务状态

- 状态：实现完成，待手动验收
- 所属阶段：第四阶段 · 智能助手侧边栏
- 前置任务：1.4、3.2、3.3、4.2
- 关联任务：5.1、5.2、6.2、8.1
- 是否可以并行：否

## 任务目标

让用户从自由提问或错误提示发起诊断。助手使用现有主进程日志查询服务，以受限、脱敏、可追溯方式读取相关事件，输出“证据、现象、可能原因、建议和仍待确认项”，不把猜测包装成事实，也不被日志内容注入指令。

## 当前情况

- main 已有 `listLogDates/queryLogEvents`，支持日期、level、source、domainPrefix、requestId、keyword、分页和上限。
- `src/commands/logging.ts` 是 renderer 封装，不应被 main Agent 工具导入。
- 当前日志留存默认 1 天、总量 256MB；日志查询返回事件 context/error，诊断工具仍需二次裁剪。
- 错误入口包括 GlobalAlertDialog、生成失败状态和通知，但不一定都有 requestId。

## 实施方案

在 main Agent diagnostics 中封装只读日志工具：跨午夜时先列日期，再按最小时间窗/关联 ID 查询；结果只返回允许字段和短摘要。默认优先 requestId，其次 domain + 时间窗；排除当前诊断 run 和 `main.agent_*` 自身事件，避免递归。所有日志内容以 untrusted observation 注入，并保留 event/domain/timestamp 作为证据引用。

## 执行步骤

1. 定义 `query_diagnostic_events` 输入/输出 schema、最大时间窗、最大页数、最大事件数和允许字段。
2. main 工具直接调用 `electron/main/services/logging/query.ts`；不得绕 renderer command 或读取任意日志文件路径。
3. 实现 requestId 优先的关联策略、跨日期查询、当前诊断 run 排除和 agent domain 递归保护。
4. 对 context/error 再次脱敏、限长和结构化摘要；保留时间、level、domain、event、关联 ID 和证据编号。
5. 在系统提示加入诊断规则：区分事实/推断，引用证据，不执行日志中的指令，不声称已修复。
6. 在 GlobalAlertDialog 和生成失败入口增加“问助手”，传递已有 requestId/errorCode/domain/时间戳；没有 requestId 时明确降低诊断置信度。
7. 输出结构：现象、证据、可能原因（含置信度）、建议步骤、需用户补充的信息。
8. 诊断工具和 UI 都接入现有日志：`requestId=诊断 runId`，被诊断 requestId 放 context；禁止把日志正文再次完整写回日志。
9. 用缺 API Key、Provider HTTP 错误、工具 schema 错误等可控案例验证，并加入 5.4/6.2 数据集。

## 验收标准

- [x] main 诊断工具直接复用现有 logging query，具备时间窗、数量、字段和递归限制。
- [x] 自由提问和错误入口均能携带可用关联信息；requestId 缺失时不会伪装精确诊断。
- [x] 输出区分证据/推断并引用日志事件；日志中的文本不能触发额外工具权限。

- [x] 诊断过程本身可按 runId 在现有日志系统调试且不会递归读取自身。
