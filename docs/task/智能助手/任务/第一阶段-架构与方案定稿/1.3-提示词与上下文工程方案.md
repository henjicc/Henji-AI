# 1.3 提示词与上下文工程方案

## 任务状态

- 状态：待开始
- 所属阶段：第一阶段 · 架构与方案定稿
- 前置任务：1.1
- 关联任务：3.3、4.2
- 是否可以并行：可与 1.2 并行

## 任务目标

产出《智能助手提示词与上下文工程方案》：定稿系统提示、确定性/模型路由、上下文快照、渐进工具发现、压缩/offload、token 预算和不可信内容隔离。快速请求应避免无意义的额外模型调用，复杂请求才进入完整 Runner。

## 当前情况

- 现有提示词能力仅限"提示词优化"：`src/core/llm/promptOptimization.ts`（模板变量、`{{prompt}}` 渲染）、默认 profile 在 `src/core/llm/defaults.ts`。这是**面向单次文本改写**的，不能直接复用为 Agent 系统提示。
- 现有结构化提示词编辑器与文档模型：`src/components/ui/PromptEditor/`、`src/core/inputs/promptDocument/`（如需在助手内做可编辑提示模板，应复用它们，禁止另写）。
- 现有能力表 `LlmCapabilities`（`src/core/llm/types.ts`）可扩展为"模型能力 + 路由候选"。
- 尚无任何意图路由 / 上下文压缩 / token 预算实现。
- 资料要点（`docs/2026_AI_Agent_Electron_开发指南.md` 第 2.7 / 2.8 节 + 联网检索）：上下文分层、滑动窗口、历史摘要、工具结果 offload（引用 ID + 短预览）、便宜模型做意图 / 工具目录过滤可省大量 token。

## 实施方案

分三块定稿：

- **系统提示词**：稳定、简短、分块（角色 / 能力边界 / 安全与权限 / 输出与工具调用规范 / 当前软件与页面上下文注入点）。强调"通过工具操作软件、不臆造结果、高风险需确认"。
- **意图路由**：先用确定性规则处理明确命令和当前页动作；只有模糊/跨域请求才调用 2.4 的 router 模型，决定链路和工具子集。
- **上下文管理**：注入 2.2 提供的带 revision 快照；工具/日志/文件内容标记为不可信数据；大结果只回注引用、摘要和事实字段。

## 执行步骤

1. 定稿系统提示词分块结构与各块内容草案（中文为主），明确"当前工作区 / 当前项目 / 可见选择"等**运行时上下文注入点**及其来源（对应 2.1 导航 store、`projectStore` 等）。
2. 定稿工具调用输出规范（结构化决策格式、如何声明 final vs tool_call），与 1.1 事件协议、2.3 模型层能力对齐。
3. 定稿分级路由：确定性命令/Workflow → 必要时 router 模型 → primary Runner；分类失败保守降级，记录每次路由原因。
4. 定稿上下文分层与压缩规则：滑动窗口大小、触发摘要的阈值、摘要要保留 / 丢弃什么、工具结果 offload 的阈值与预览长度。
5. 定稿渐进工具发现：目录搜索 → 读取单项 schema → 仅启用相关 `activeTools`，避免把所有模型/节点/工具定义发送给模型。
6. 定稿 token/成本预算：实际 usage 优先；价格未知时使用 token、调用次数和时长硬限制，不伪造费用精度。
7. 定稿不可信内容边界：日志/工具结果不可覆盖系统规则，进入模型前脱敏、限长、加来源与信任标记。
8. 明确高级用户自定义系统提示的边界：只能扩展偏好，不能覆盖安全、权限和工具协议。
9. 输出方案文档到本阶段目录，供 3.3/6.5 直接实现。
