# 2.4 智能助手模型配置与能力验证

## 任务目标

为智能助手建立独立、可配置、可验证的模型 Profile，覆盖 primary/router/summarizer/fallback，并记录真实 token usage、延迟和可证实费用。防止用户选择不支持工具的模型后进入不可解释失败。

## 当前情况

- `LlmConfigState` 只有提示词优化 profile；模型能力已有 text/image/video/audio/streaming/toolCall/jsonOutput，但内置默认 toolCall/jsonOutput 为 false。
- 设置页可编辑部分模型能力，但没有 Agent 角色、fallback、上下文长度、parallel tools、usage/cost 和 capability smoke。
- 现有 LLM Trace 主要记录输入/输出字符数，不能执行精确 token 预算。

## 实施方案

在现有 LLM 配置体系上新增 `AgentModelProfile`，不复制 Provider/API Key 管理。Profile 保存模型角色和运行策略，不保存密钥。静态能力来自配置，动态 smoke 记录实际验证结果、时间和错误；运行前两者共同判断。价格未知时显示“未知”并只执行 token/调用/时长预算，不伪造费用。

## 执行步骤

1. 定义 AgentModelProfile：primary/router/summarizer/fallback、模型参数、超时、重试、上下文/输出预算。
2. 扩展能力模型：toolCall、parallelTools、structuredOutputMode、reasoning、sampling、contextWindow、maxOutputTokens、usage。
3. 在设置页复用现有 Ui* 增加智能助手模型选择和能力状态；不新建平行 Provider/密钥配置。
4. 实现 capability smoke：最小文本、tool-call、Output.object、stream、usage、cancel；结果带 verifiedAt/provider/model/version。
5. 启动 run 前校验 primary 能力；不满足时自动选择已验证 fallback 或给出明确设置入口，不能静默降级成无工具聊天。
6. router/summarizer 缺失时允许复用 primary；确定性路由命中时不调用 router。
7. 采集 input/output/reasoning/cache token、调用次数和延迟；价格有可靠来源时估算费用，否则标记 unknown。
8. 接入现有日志：Profile 选择、能力验证、fallback 和 usage 使用 `requestId=runId` 或独立验证 requestId，带 modelId/providerId；不记录 API Key/测试 prompt 原文。
9. 写配置迁移、能力判断、fallback、usage 和设置 UI 测试。
