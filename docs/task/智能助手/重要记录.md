# 重要记录 —— 智能助手（全局 Agent）

> 只记录会影响多个任务或长期方向的决定。普通实现细节写入对应任务执行记录。

## 记录 001：Agent 运行时进程落点

- 日期：2026-07-23
- 状态：已确定
- 背景：当前仓库尚未使用 Electron `utilityProcess`；一开始引入进程生命周期、MessagePort 和崩溃恢复会拖慢首个闭环，但长期运行的 Agent 不应永久占用主进程。
- 最终决定：MVP 先落 `electron/main/services/agent-runtime/`，只通过可序列化契约通信；完成检查点、评测和长稳基线后，由 6.4 迁移到 `utilityProcess`。主进程最终只负责窗口、权限、凭据和运行时进程管理。
- 选择原因：先降低 MVP 复杂度，同时通过稳定边界避免未来重写。
- 影响任务：1.1、3.1、3.2、3.3、6.1、6.4

## 记录 002：模型适配层使用 Vercel AI SDK

- 日期：2026-07-23
- 状态：已确定
- 背景：现有手写 SSE 只解析文本与 reasoning，不解析工具调用；不同 Provider 的工具调用和结构化输出差异不适合继续手写。
- 最终决定：引入 `ai`、`@ai-sdk/openai-compatible`、`zod`，专用 Provider 包按真实需求增加。使用 `streamText`/`generateText`、`tool()` 和 AI SDK 6 的 `Output.object()` 等接口；不再以已弃用的 `generateObject` 作为目标 API。保留并扩展自有 `LlmCapabilities`。
- 选择原因：把 Provider 协议差异交给成熟 SDK，同时不把业务、权限和 Harness 绑定到 SDK 内部类型。
- 影响任务：2.3、2.4、3.1、3.3

## 记录 003：Runner 是唯一循环所有者

- 日期：2026-07-23
- 状态：已确定
- 背景：原计划同时出现自研 while Runner 与 AI SDK `ToolLoopAgent/stopWhen` 自动多步循环，可能形成两套预算、审批、消息和停止状态机。
- 最终决定：自研薄 Harness Runner 是唯一循环、预算、审批、检查点和状态机所有者。AI SDK 负责单步模型调用、流式事件、工具调用解析和结构化输出；Runner 显式追加模型响应与工具结果后决定下一轮。首版不使用 `ToolLoopAgent` 自动循环，不引入 Mastra，不引入 Python Sidecar。
- 选择原因：前端工具需要跨进程等待结果，审批需要可暂停/恢复，检查点与现有日志/SQLite 必须由本项目统一控制。
- 影响任务：1.1、2.3、3.1、3.2、3.3、6.1

## 记录 004：首批闭环范围

- 日期：2026-07-23
- 状态：已确定
- 背景：必须先以真实、可验证用例证明 Harness，而不是直接铺开所有工具。
- 最终决定：第一批闭环为“生成工作区产生用户可见记录 + 读取日志诊断”；第二批闭环为“当前画布项目放置、连接并定位节点”。全部内置能力在第七阶段接入。
- 选择原因：覆盖前端动作、后端服务、长任务、日志读取和 UI 结果呈现，同时控制首版规模。
- 影响任务：1.2、5.1、5.3、7.1～7.4

## 记录 005：统一使用 Zod 做边界校验

- 日期：2026-07-23
- 状态：已确定
- 背景：工具入参、结构化模型输出和 IPC 都属于不可信边界。
- 最终决定：引入 `zod`，共享的可序列化 DTO 在 main/renderer 两侧都验证；Zod schema 不通过 IPC 传输，只传普通对象。工具输出也必须有 `outputSchema` 或等价校验。
- 选择原因：避免只校验模型输入、不校验工具结果和跨进程消息。
- 影响任务：1.1、1.4、2.2、2.3、3.2

## 记录 006：宿主命令面与上下文快照

- 日期：2026-07-23
- 状态：已确定
- 背景：生成任务记录存在于 React Hook 局部状态；导航、画布项目和选择状态存在于 renderer store，主进程 Agent 无法直接读取或调用。
- 最终决定：建设与 Agent 无关的 `HostCommand/HostQuery/HostContextSnapshot` 契约。生成、导航、画布等 UI 业务通过稳定宿主命令执行；运行开始和关键动作前使用带 `revision` 的上下文快照，工具提交时校验项目/工作区等前置条件，防止用户切页后操作错对象。
- 选择原因：让 UI、Agent 和未来其它入口复用同一命令面，避免跨层 import 和直接操纵组件内部状态。
- 影响任务：1.1、1.2、2.2、3.1、3.3、5.1、5.3、7.1～7.4

## 记录 007：Agent 日志必须复用现有日志系统

- 日期：2026-07-23
- 状态：已确定
- 背景：Agent 包含模型、工具、审批、上下文压缩、前端动作和长任务，若没有一致关联 ID 将很难复现问题；项目规则禁止平行日志体系。
- 最终决定：main 使用 `createMainLogger`，renderer 使用 `createLogger`；未来 utility process 不直接另写文件，而是把校验、脱敏后的结构化日志 DTO 交给 main 现有日志 sink。禁止 Agent 专用日志文件、查看器和查询服务。统一使用 `requestId = runId`、`taskId = toolCallId`，模型事件继续携带 `modelId/providerId`，`threadId/toolName/usage/step` 放入脱敏 `context`。至少记录 run/model/tool/approval/context/checkpoint/UI-action 的 `start/completed/failed`，高频 token/进度使用 debug/trace。日志自动进入现有 JSONL、日志窗口和 `npm run logs:query`。
- 选择原因：保证一次运行可以按 `requestId` 串联前后端事件，且遵守日志单一数据源约束。
- 影响任务：1.1、1.4、2.2～2.4、3.1～3.3、4.2、4.3、5.1～5.4、6.1、6.2、6.4、8.1、8.2

## 记录 008：评测与生产可用边界

- 日期：2026-07-23
- 状态：已确定
- 背景：用户要求优先保证效果；仅跑通一个演示用例不足以证明工具选择、参数、安全和不同模型表现稳定。
- 最终决定：5.4 建立 MVP 最小发布门槛；6.2 建立可持续评测机制；第七阶段接完能力后由 8.1/8.2 做最终全量回归和生产化验收。未通过 8.2 前，只能称为开发版智能助手，不能称为全能生产版本。
- 选择原因：把效果、安全、token、延迟和回归变成可度量结果，而不是凭主观体验判断。
- 影响任务：5.4、6.2、7.1～7.4、8.1、8.2
