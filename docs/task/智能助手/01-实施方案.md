# 01 · 实施方案 —— 智能助手（全局 Agent）

> 本文件记录相对稳定的整体方案。任务状态和跳转看 `00-任务总览.md`，跨任务决策看 `重要记录.md`。

## 一、当前项目与相关能力现状

Henji-AI 是 Electron + React + TypeScript 桌面应用，业务基线为配置驱动、PAL 收口和前后端职责分离。

### 1. 应用外壳与工作区

- 工作区：`generation | nodes | tools | assets`，类型在 `src/core/types/workspace.ts`。
- `src/App.tsx` 当前用局部 `activeTab` 管理工作区，Agent 尚无稳定切页入口。
- 工具箱 `activeToolId` 仍是 `ToolboxWorkspace.tsx` 局部状态；3D 子视图有 `cameraStageSessionStore`。
- 素材库已有 workspace/floating 两种形态，可作为助手容器布局参考。

### 2. 生成工作区

- 模型执行入口为 `src/core/services/GenerationService.ts`，真实 Provider 执行落在 `electron/main/services/ai-runtime/`。
- 用户可见任务由 `GenerationWorkspace` 内 `useTaskState` 的局部数组和 `useTaskGeneration.handleGenerate()` 创建；`handleGenerate` 会做上传落盘、参数规整、任务排队、历史状态和用户提示。
- 因此 Agent 不能只调用 `GenerationService.generate()`；必须先抽取可被 UI 与 Agent 共用的“创建用户可见生成任务”命令。

### 3. 画布与工具箱

- 画布状态在 `src/stores/canvasStore.ts`，已有 `addNode/addEdge/undo/redo`；项目状态在 `src/stores/projectStore.ts`。
- 节点定义在 `src/features/canvas/domain/nodeRegistry.ts`，具备配置驱动基础。
- 工具箱包含图片编辑与 3D 镜头参考；分镜、素材库、项目和媒体命令已有部分 `src/commands/*` 接口，但没有统一宿主能力目录。

### 4. LLM 现状

- `electron/main/services/llm/streaming.ts` 是手写 OpenAI-compatible SSE，仅解析文本/reasoning，不解析 `tool_calls`。
- `src/core/llm/types.ts` 已有 `LlmCapabilities`、`LlmToolSchema`、`LlmPolicy`、`LlmMemoryScope` 雏形；内置模型的 `toolCall/jsonOutput` 默认关闭。
- 当前 LLM 配置主要服务提示词优化，没有智能助手主模型、路由模型、摘要模型、fallback、usage/cost 配置。
- 项目尚未安装 `ai`、`@ai-sdk/*`、`zod`。

### 5. 可复用基础设施

| 能力 | 当前入口 | Agent 复用原则 |
|---|---|---|
| 安全 IPC | `src/commands` → `src/platform` → preload → main IPC | 新增最小、明确、双侧校验的 Agent API |
| 日志 | `createLogger` / `createMainLogger`、JSONL、日志窗口、`logs:query` | 直接复用，禁止平行体系 |
| 日志查询 | `electron/main/services/logging/query.ts` | 后端诊断工具直接调用主进程服务 |
| 凭据 | safeStorage keystore | Agent 只引用 provider，不读取/暴露明文密钥 |
| 数据库 | `electron/main/services/db.ts` + better-sqlite3 | Agent 独立表；先补版本/迁移约定 |
| 取消 | LLM/AI Runtime 的任务注册与 AbortController | 扩展为 run/model/tool 统一取消链 |
| 画布撤销 | `canvasStore.undo/redo` | Agent 写操作返回撤销信息，优先接现有历史 |

## 二、需要解决的核心问题

1. UI 能力散落在组件 Hook/store，缺少稳定宿主命令与查询面。
2. main Agent 不能直接读取 renderer store，需要可序列化、带版本的上下文快照。
3. LLM 层缺工具调用、结构化输出和 Agent 模型配置。
4. 必须只有一个循环/状态机所有者，避免 SDK 自动循环与自研 Runner 打架。
5. 缺工具网关、审批、幂等、重试、预算、前置条件、撤销和不可信数据隔离。
6. 缺从 run 到模型/工具/UI 动作的日志关联规则。
7. 目前计划覆盖的是 MVP 工具，尚未系统接入全部内置能力。
8. 缺可度量的效果、安全、token、延迟和不同模型回归门槛。

## 三、最终目标

智能助手能够基于当前工作区、项目、选中对象和用户授权理解目标，通过稳定工具操控软件，在真实界面产生可见、可跳转、可撤销或可恢复的结果。用户能看到计划、工具、审批、耗时、token/费用和失败原因，能随时取消、接管或询问日志诊断。

第八阶段验收后，能力范围应覆盖：导航、生成、画布、工具箱、3D 镜头、分镜、图片编辑、素材库、诊断以及跨工作区组合流程。

## 四、稳定架构决定

### 4.1 唯一 Runner

自研薄 Harness Runner 是唯一循环、状态、预算、审批、消息、检查点和停止条件所有者。Vercel AI SDK 只负责：

- Provider/模型协议适配；
- 单步 `streamText/generateText`；
- `tool()` 输入协议与 tool-call 解析；
- `Output.object()` 等结构化输出；
- usage、流式和 Provider 原生参数。

Runner 每轮显式执行：预算/取消检查 → 构建上下文 → 单步模型调用 → 解析 final/tool-call → 工具网关 → 观察回注 → 检查点 → 判停。首版不使用 `ToolLoopAgent` 自动多步循环，也不建立第二套 AI SDK 审批状态机。

### 4.2 宿主命令、查询与上下文快照

新增与 Agent 解耦的三类契约：

- `HostCommand`：执行有语义的应用动作，如切换工作区、创建可见生成任务、在指定项目加节点。
- `HostQuery`：查询模型目录、节点目录、项目和任务状态，不产生副作用。
- `HostContextSnapshot`：当前工作区、当前项目、当前工具、选中对象、界面就绪状态、可用命令和 `revision`。

工具执行时携带显式目标 ID 和可选 `expectedRevision`；上下文已变化时返回可恢复冲突，不凭“当前”猜测目标。renderer 只执行必须由 UI/store 完成的命令，main 工具直接调用 main service。

### 4.3 两侧工具、一个权威网关

- frontend 工具：导航、可见生成任务、画布/项目、工具箱/3D/分镜等 renderer 状态动作。
- backend 工具：LLM、AI Runtime 后端能力、日志查询、文件处理、SQLite 等。
- 工具定义的权限、风险、描述和可见性由主运行时注册表权威管理；renderer 只维护 handler 映射，并再次验证共享 DTO。

推荐工具契约至少包括：`name/version/title/description/inputSchema/outputSchema/side/risk/permissions/readOnly/destructive/openWorld/idempotent/timeoutMs/retryPolicy/supportsPreview/supportsUndo/concurrencyKey/requiredContext`。

### 4.4 事件与前端工具往返

`AgentEvent` 至少包含：

- run：started/paused/resumed/completed/failed/cancelled；
- model：started/delta/completed/failed；
- plan/context：updated/compacted/artifact-offloaded；
- tool：requested/started/progress/completed/failed；
- approval：required/resolved/expired；
- checkpoint：saved/restored。

所有事件带 `schemaVersion/eventId/sequence/occurredAt/runId`；工具事件带 `toolCallId`。前端工具使用 request → acknowledged → completed/failed 往返，支持超时、取消、renderer 重载、重复回传去重和未知调用拒绝。

### 4.5 Agent 模型角色

新增 `AgentModelProfile`：

- primary：复杂推理和工具调用；
- router：仅在确定性路由无法判断时使用；
- summarizer：上下文摘要，可与 primary 共用；
- fallback：primary 不可用或不支持能力时降级。

启动前验证模型 `toolCall/structuredOutput/streaming/reasoning/sampling/parallelTools/contextWindow` 等能力。工具调用能力不得只依赖模型名称猜测；支持配置、探测和实际 smoke 结果。

### 4.6 上下文与 token 策略

- 先做确定性路由：明确命令、当前页面和少量关键词能判定时不额外调用路由模型。
- 模糊或跨域请求才调用 router；分类失败保守进入完整 Runner。
- 使用工具目录搜索和 `activeTools` 渐进暴露，不把全部模型、节点和工具 schema 一次塞入上下文。
- 工具大结果 offload，只回注引用、摘要和校验事实。
- 记录实际 input/output/reasoning/cache token；价格已知时估算费用，未知时至少执行 token/调用次数/时长预算。

### 4.7 安全与不可信数据

- 用户输入、模型输出、日志、文件、工具结果和 MCP 内容均为不可信。
- schema、权限、路径/域名、审批、最大输出、超时和结果校验由代码执行。
- 写操作优先 `prepare/preview → approve → commit`；审批绑定工具、参数摘要、目标、revision、有效期和作用域。
- 高风险授权不得“永久放行”；其它记住授权也必须可查看、撤销、过期。
- Agent IPC 必须验证 sender，preload 每个能力暴露独立方法，不暴露通用 send/invoke。
- 工具输出进入下一轮前做脱敏、长度限制和“不可信内容”标记，防止间接提示词注入。

## 五、日志与调试方案

Agent 日志完全接入项目现有日志系统：

- main 运行态使用 `createMainLogger('main.agent_runtime')`、`createMainLogger('main.agent_tool')` 等既有入口；迁移后 utility process 通过受限日志 DTO 把事件交给 main 现有 sink，不直接写平行文件；
- renderer 使用 `createLogger('features.assistant.*')`；
- `requestId = runId`，`taskId = toolCallId`；模型调用继续带 `modelId/providerId`；`threadId/toolName/step/usage` 放脱敏 context；
- 关键链路至少记录 `start/completed/failed`，取消、重试、审批、压缩、检查点和前端动作均有事件；token/进度等高频内容使用 debug/trace；
- 禁止记录 API Key、Authorization、完整用户提示、完整消息历史和未裁剪工具结果；详细捕获也不取消脱敏；
- 诊断工具直接调用 `electron/main/services/logging/query.ts`，按日期/时间窗、level、domain、requestId、limit 查询；默认排除当前诊断 run，避免递归读取自身日志；
- 不新建 Agent 日志文件、查看器、IPC、数据库 Trace 平行通道。SQLite 只保存可恢复运行状态、检查点、授权和评测索引；调试日志仍以现有 JSONL 为事实源；
- 在 6.2/8.2 评估 Agent 日志量对当前 1 天/256MB 留存策略的影响，如需调整只扩展现有日志设置。

推荐 event 命名：

```text
agent_runtime.run.started|completed|failed|cancelled
agent_runtime.model_call.started|completed|failed
agent_runtime.context.compacted|artifact_offloaded
agent_tool.execute.started|completed|failed
agent_approval.requested|resolved|expired
agent_checkpoint.saved|restored
assistant_ui.frontend_tool.started|completed|failed
```

## 六、目标目录与职责

```text
src/features/assistant/
├─ sidebar/                 # 侧边栏与执行可视化
├─ frontendTools/           # renderer handler 与单点订阅
├─ hostContext/             # 上下文快照提供者
└─ store/                   # 纯 UI/会话展示状态

src/core/assistant/         # 中立 DTO、schema、事件和宿主契约，不依赖 UI/main
src/commands/assistant.ts   # renderer 命令桥
src/platform/contracts/assistant.ts

electron/main/services/agent-runtime/
├─ runner/                  # 唯一循环、状态、预算
├─ models/                  # AI SDK adapter 与 capability
├─ tools/                   # 注册表、网关、审批
├─ context/                 # 路由、压缩、offload
├─ persistence/             # run/checkpoint/permission
└─ diagnostics/             # 对现有日志查询服务的受限封装
```

目录以 1.1 最终设计为准；新文件优先不超过 400 行。

## 七、阶段关系

1. 第一阶段先冻结稳定契约和威胁模型。
2. 第二阶段建设宿主命令面、LLM adapter 和 Agent 模型配置；2.1 与 2.3 可并行。
3. 第三阶段实现唯一 Runner、网关和上下文；3.2/3.3 在 3.1 后并行。
4. 第四阶段接 UI、审批和诊断；4.1 可提前并行。
5. 第五阶段依次验证生成/诊断、护栏、画布和最小评测，5.4 是 MVP 门槛。
6. 第六阶段建设持久化、持续回归、utility process 和记忆隐私；6.3 MCP 可跳过且不阻塞其它任务。
7. 第七阶段把稳定模式扩展到所有内置能力。
8. 第八阶段以最终能力集做全量效果、安全、性能、token 和长稳验收。

## 八、兼容与迁移原则

- 现有提示词优化保持可用；新 adapter 先旁路验证，再决定是否统一旧路径。
- 原有 UI 仍调用同一宿主命令，Agent 是新增调用方，不保留两套业务编排。
- 生成任务抽取必须保持上传处理、队列、历史、重试、通知和可见记录行为一致。
- 新 Agent SQLite 表独立于现有业务表；执行 6.1 前先确认并补齐 schema 版本/迁移机制。
- `AgentEvent`、工具契约和 checkpoint 带版本；不兼容变更必须提供迁移或明确拒绝恢复。
- 每个代码任务独立提交；依赖引入、宿主改造、运行时和 UI 分开，便于回退。

## 九、全局验证要求

- 静态：`npm run lint`、`npx tsc -p tsconfig.electron.json --noEmit`、主进程 ESLint、颜色检查。
- 契约：main/renderer schema 双侧解析、事件顺序、重复/超时/取消、IPC sender。
- 模型：每个 Agent 候选至少验证文本、tool-call、结构化输出、usage 和取消。
- 工具：成功、非法参数、缺前置、越权、审批拒绝、重复调用、撤销/补偿。
- 日志：按 `requestId=runId` 能完整串联前后端，敏感字段不落盘，失败可定位。
- UI/鼠标：停靠、拖拽、画布、3D 等写明操作步骤交用户真实 Electron 手动验收。
- 评测：提示词、模型、工具描述/schema、权限、路由或记忆变化后执行相关回归。

### 持续回归触发点

以下任一项变化都必须执行 `npm run test:assistant-eval`，并按影响范围补充黄金、历史失败或对抗用例：系统/路由提示、Agent 模型与 Profile、Provider adapter、工具描述与参数 schema、路由策略、权限和批准规则、记忆策略、IPC/事件/utility process 协议、确定性工作流。涉及真实 Provider 行为时，在自动回归通过后再按最终测试清单记录真实成功率、延迟、token 和可证实费用。

## 十、最终验收条件

1. 侧边栏支持左右停靠、悬浮、拖动、恢复和全局唤起。
2. 生成、诊断和画布闭环稳定通过；第七阶段列出的所有内置能力均有受控工具入口。
3. Agent 只通过宿主命令/服务操作软件，跨工作区流程能检查上下文 revision，并支持撤销或明确补偿。
4. 所有工具经统一网关；审批、预算、取消、超时、幂等、重试和不可信数据隔离有效。
5. 每次 run 可在现有日志系统按 requestId 完整追踪，日志脱敏且诊断工具不会递归读取自身。
6. 模型 Profile、能力验证、fallback、token/费用统计可用，不支持工具的模型不会被错误启用。
7. 会话、检查点、授权和记忆可恢复、可查看、可删除并有版本/作用域。
8. 最终评测、安全、性能、token、日志容量和长稳验收全部通过，不破坏既有功能。
