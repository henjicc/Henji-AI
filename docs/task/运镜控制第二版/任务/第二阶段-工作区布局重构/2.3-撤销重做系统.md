## 任务目标

编辑器获得可靠的撤销/重做能力：对象增删改、变换（含 gizmo 拖拽）、姿态调整、颜色/显隐、场景设置等数据操作全部可撤销重做；选中态、视角模式、面板布局等界面态不进历史；gizmo 拖拽、滑杆连续调整等高频操作合并为单条历史记录。为第三阶段的关键帧编辑操作预留接入方式。

## 当前情况

- `src/features/cameraStage/store/cameraStageStore.ts` 是 zustand v5 单 store，无任何历史机制。
- 需要区分两类状态：**数据态**（`objects` 及未来的场景设置、动画轨道——进历史）与**界面态**（`selectedId`/`gizmoMode`/`viewMode`/`activeCameraId`——不进历史）。
- 高频写入点：gizmo 拖拽（`StageScene.handleGizmoChange` 拖动过程每帧回写 store）、`NumberInput` 的 `commitOnChange`/滚轮、姿态滑杆——若每次 set 都记一条历史，一次拖拽会产生上百条记录，必须节流/合批。
- 项目内没有其他撤销重做实现可复用（画布 `@xyflow/react` 场景另有自己的历史逻辑，不通用）。
- 候选方案：`zundo`（zustand 官方生态 temporal 中间件，支持 `partialize` 排除界面态、`handleSet` 节流合批）；若与 zustand v5 版本兼容性实测有问题，则自研轻量补丁栈（快照或反向补丁）。

## 实施方案

优先用 `zundo` 给 `cameraStageStore` 挂 temporal 中间件：`partialize` 只跟踪数据态切片；连续操作合批采用「操作会话」语义——gizmo 拖拽 start/end、滑杆按下/松开之间暂停记录，结束时记一条（zundo 的 pause/resume 或 handleSet 节流实现，执行时实测选择）；历史栈长度设上限（如 100 步）。对外暴露 `undo`/`redo`/`canUndo`/`canRedo` 给工具栏按钮与快捷键。工程加载（1.1 的 `loadScene`）后清空历史。若 zundo 兼容性验证失败，自研方案保持同一对外接口，内部用不可变快照栈实现（objects 数组本身是不可变更新，快照成本可接受）。

- 遗留问题（交用户在 Electron 窗口验证鼠标合批手感）：① 一次 gizmo 拖拽 = 一条记录；② 一次姿态/数值滑杆连续拖动 = 一条记录；③ Ctrl+Z/Ctrl+Shift+Z 与按钮禁用态表现。
- 用户验证步骤：① 进编辑器加几个对象，拖 gizmo 移动一个对象后 Ctrl+Z，应一步回到拖拽前；② 选中角色，拖某关节滑杆连续调整后 Ctrl+Z，应一步回到拖前；③ 连点撤销/重做按钮，禁用态随栈变化；④ 打开另一个工程，确认 Ctrl+Z 不会退回上一个工程的数据。
- 与原计划偏差：批处理采用「会话式 handleSet（会话内只记首帧前态）」而非 zundo 原生 pause/resume——因 pause/resume 会丢失拖拽起点前态（导致撤销越过起点），会话式能精确实现「一次交互=一条记录」；数值/滑杆合批走 PropertyPanel 的 focus/blur 捕获而非改共享 `NumberInput` primitive（不污染通用组件）。
- 对后续任务影响：3.1 关键帧增删改动作天然进历史栈；3.2/3.3 的关键帧拖拽/曲线编辑可复用 `beginHistorySession`/`endHistorySession` 合批。
