# 1.1 分离应用执行入口与助手依赖

## 任务状态

- 状态：待验证
- 所属阶段：第一阶段：独立入口与本地连接
- 前置任务：无
- 关联任务：1.2、2.1
- 是否可以并行：否；涉及公共契约和根宿主，先形成单一可用入口。

## 任务目标

建立不需要助手运行、聊天历史、模型调用或脚本租约的应用能力执行入口。旧助手源码和历史保留，可隐藏入口；正常应用仍能构建和运行。

## 当前情况

- `src/core/application-control/` 已有实体引用、反射、事务和验证。
- `src/core/assistant/applicationCapabilities.ts` 与 `builtinApplicationCapabilityRegistry.ts` 保存语义定义，但混有助手类型依赖。
- `src/features/assistant/applicationCapabilities/applicationControlRegistry.ts` 和 `registry.ts` 负责领域注册；`applicationReflectionAdapter.ts` 当前固定 assistant 暴露类型，并组装全部已声明属性权限。
- `electron/main/services/agent-runtime/tools/types.ts` 要求 runId、threadId 等助手上下文；`gateway.ts` 从运行编号取宿主。
- `src/App.tsx` 根层挂载宿主桥，另外还有侧栏、快捷键和诊断入口；隐藏侧栏不能关闭 MCP 将复用的宿主。
- 规则及双份能力技能要求应用操作走 Henji Script；`package.json` 的构建链含助手检查。用户已明确改变本任务优先级，需准确调整适用范围。

## 实施方案

沿既有注册和执行链抽离最小共享职责，不整体搬迁目录。定义应用调用上下文，由可信宿主填充调用来源、允许范围、并发基线及取消信号。执行端重新检查权限与动态可用性；不要直接把现有反射处理器接到网络上。先用内存调用适配和正式领域回读证明脱离助手可执行，外部端口在 1.2 实现。

阅读[实施方案](../../01-实施方案.md)后执行；若实际代码与本文件不同，先更新路径和方案再开发，不重做无关全仓调查。

## 执行步骤

1. 对照注册表列出外部能力边界，记录八个业务写域及只读域的实际入口；明确排除助手运行、内部工具和密钥，结果写入本任务执行记录。
2. 梳理发现、参数校验、授权、调度、执行、回执之间的依赖；在既有核心和主进程服务目录内抽离共享入口，保持领域执行器唯一。
3. 把原反射适配器的固定权限改为来源可信且逐层可验证的调用上下文；定义外部输入不能覆盖的字段，不伪造助手 runId、用户消息或审批事实。
4. 根宿主桥与助手侧栏解耦；默认隐藏侧栏入口、快捷键及诊断唤起，保留源码和历史。保留界面业务根服务，不要求修复旧助手运行能力。
5. 调整相关规则及两份能力技能：MCP 可直接调用应用能力；助手专属协议不约束 MCP。把构建检查里的领域安全不变量与助手行为要求区分开，不全局跳过检查。
6. 使用正式反射、执行器和非付费夹具证明读取及一项内存事务可调用，且没有模型请求或助手记录；验证权限拒绝及正常应用构建边界。2.1 再正式开放持久写入。
