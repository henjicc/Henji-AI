## 根因、修法与结论

### 1. 免费整理吸附后重新接续

已匹配真实案例：文档 `30eacc11-4cad-4c4d-93f0-715bbdf48ffb` 的序列 `e2b6bbd5-fefd-4af7-9ea3-465aec1ee164`。`37069f02-2a21-4d8c-95c5-e4726a6e5c74` 有完整显式样式，`94fea73d-1761-414d-96a4-ece54f54bb3a` 未设置样式；现有整理按样式分组，所以是两次独立词对齐。前条从 235–386 吸附为 235–374，后一组从 386 开始；组内接续看不到跨组的 12 帧间隔。

修法：所有组生成并吸附完成后，在最终序列帧时钟再执行接续；正间隔小于 joinGapMs 时延长前条结束到后条开始。不修改未选字幕，选中的前条允许接到未选的后一条；接续产生的修改进入 updatedIds，与其余整理一起走一次正式编辑和撤销。处理使用排序、集合和线性扫描，无数量限制。

同源排查：`segmentTimedSubtitles` 已在分段后接续；`buildSpeechSubtitles` 已在源时间映射到序列帧并排序后再接续（包含倒放）；`buildAutoSubtitles` 的中文路径先分段接续，再以同一帧边界量化两端。没有发现它们漏掉同类步骤。本项一条测试同时核对免费整理、原文生成、识别生成：间隔只为 0 或至少 500ms，并保留阈值等于 500ms 的间隔。

复测：按原案例保留不同样式，先把前条恢复成 start=235、duration=151，后条 start=386、duration=70；仅选这两条调用默认 `segment_video_edit_subtitles`。结果仍为两条，前条结束应为 386，间隔为 0。一次撤销回到整理前状态。

### 2. 手动拆分是否保留、顿号如何复测

**没有“手动拆分锁定”的字段或规则。** 整理重新按原句、气口、时长及两行容量排版；相同片段、相同样式且间隔低于阈值的邻条可进入同一组。不同样式、不同绑定片段、非相邻选择或超过接续阈值不会合并。最短时长只是合并原因之一，两条都满足最短时长也不保证保持拆分。

原案例不合并的直接原因是样式不同，不是两条都超过最短时长。这个保护合理：显式样式与未设置样式在渲染中走不同文字呈现，不能整理时丢失后一条的视觉选择。因此不改这项分组规则。

另发现无逐词时间的估算路径把字幕排版换行原样交给分段器，分段器将换行视作原句边界，会不合理地保留两行容得下的意群拆分；改为和逐词路径一致，先用已有 joinCaptionText 拼回连续原句。参考原文仍保留标点，段尾被移除的顿号通过已存 sourceText 恢复，人工改字仍受原有匹配保护。测试使用两段均超过最短时长的同样式字幕，第一段原句末尾带顿号/换行，验证合并、顿号恢复及移除引用。

可直接复测原案例：

1. 经字幕实体读取前条完整 `style`，将后一条 `style` 设为同值；两条 clipId 保持为 `50537739-bf5b-4105-88d4-d1ba4ec0ea44`。
2. 保留前条 source_text 为“它不只是会聊天，还能帮你写代码、”，后条为“画图、做视频……”。不要只把可见文字中的顿号删掉后连 source_text 也一并删掉。
3. 选中这两条，默认调用 `segment_video_edit_subtitles`；该列举意群可容纳两行，预期合成一条，正文为“它不只是会聊天\n还能帮你写代码、画图、做视频……”，段中“代码、画图”的顿号恢复。
4. 若另测短尾兜底，在同样式、同绑定片段的前提下将后一条压至 24 帧（60fps 默认最短为 50 帧），再整理。**只缩短时长而不统一样式不能触发跨样式合并。** 两行容量/最长时长或真实气口不允许时仍不保证合并；上面步骤 1–3 是本案例的确定复测条件。

### 3. 466 帧的真实来源

读取的真实文件为 `E:/文档/痕迹AI/项目/都叫AI，却不是一个AI/验收_2.4.0.henji-video`，序列及文档同第 1 项。绑定的唯一旁白片段 `50537739-bf5b-4105-88d4-d1ba4ec0ea44` 实际 start=0、duration=466，不是 456；源素材 `335462a5-baa4-4fc6-8177-8f6f29965da5` 登记 durationSeconds=7.776000000000001，入点=0、未变速/倒放。三条字幕的结束分别为 235、374、456；没有标记和转场。

`makeVideoEditItemClip` 对媒体时长使用 `floor(durationSeconds * fps + 1e-6)`，60fps 得到 466；`videoEditDuration` 对片段、字幕和标记末尾取最大，故为 466。该序列已归档 taskId=`78c49d0e-5226-4141-ac58-9b840aab8cfe` 的区间也是 0–466，rangeSource=content。**十帧来自旁白文件在末词字幕结束后的剩余媒体时长，既非字幕、标记或效果尾部，也非导出添加余量。** 未分析最后十帧声音是否静音，媒体仍属于内容；不自动按字幕尾或最后一个词截断声音。

不改区间算法和 rangeSource。新增一条正式构造/导出/查询测试：7.776 秒声音在 60fps 放置成 466 帧，三段字幕最后到 456、无标记/转场，导出 0–466；用户显式修剪片段 duration 到 456 后，新导出为 0–456，历史导出仍保留原区间。

复测：读取上述 clipRef 的 duration，预期 466；默认导出预期 466。若希望成片止于 456，应显式修剪旁白片段到 456 或给导出指定 0–456。查询旧任务仍应显示其提交时的 466，不应随新编辑改写历史。

### 4. source_text 首尾空白

真实第一条 source_text 确有末尾换行。分段器把末尾空白并入排版前原句，原句恢复也会从参考文本带回这些空白。

修法：分段生成 sourceText 和参考原文恢复结果都 trim；剪辑领域的正式编辑、内容保存及读取入口统一去 sourceText 首尾空白，保证通用实体写入与已存在数据读取同样生效。仅清理该参考文本，不清理原文内部空白，不改变原始传入对象，不在读取时写回文件。字段、可选性、schema、落盘格式、版本与外部工具契约均未变化，无迁移、dev-break、契约版本/指纹修改。

一条测试覆盖生成、追加、内容保存、已有含空白内容读取、内部换行保留、原输入未修改和保存重开。

复测：读取第一条字幕的 source_text，应不再以换行结束；已有文件只读打开不改写原件，下一次明确保存才保存清理后的值。
