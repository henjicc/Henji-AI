## 根因、覆盖分级与实现

这是既有应用能力的公开并发契约修正，按应用能力变更完整核对声明、执行、读回与恢复；无新增业务入口、实体、属性或 MCP 工具。

镜头参考原先把 toolbox 当成同一个修订范围：能力 requiredScopes/control.impacts、字段及实体 revisionScopes、动态 availability、事务 expectedRevisions、执行器 resultingRevisions、反射 revisions、宿主 scopeRevisions 和写后通知都绑定了它。仅替换外部返回键会使严格写入与事务计划判断失配。

现统一使用 camera_stage，覆盖文档、场景、对象、摄像机、状态关键帧、轨迹和播放实体，以及放置、复制、删除、属性修改、运镜、候选应用与补偿/撤销回执。宿主初始化独立计数并通知新键；toolbox 自身的目录/状态声明与反射继续保留 toolbox，工具选择仍只推进 navigation。

hostScopeRevisionsSchema 原本通过 catchall 接受领域修订键，与 image_edit/audio_edit/video_edit 等现有域一致；无需把新键改成强制宿主字段或变更落盘格式。

持久读取基线仍按原 ReadBaseline JSON 保存。执行协调器遇到引用属于 camera_stage.* 且 revisions 含 toolbox 的基线时返回 BASELINE_EXPIRED，并明确要求 read_application_entity 重读原目标、使用新 baselineId。即使数值相同也不映射、不迁移、不放行；其他领域的 toolbox 基线不被该规则否定。原先宿主代次过期和目标绑定保护继续生效。运行中的严格 expected-revision 旧键由正式入口以可恢复 CONFLICT 拒绝。

t189 核对路径（运行时/dispatcher → read_application_entity → 领域 provider → reviewPresentation）没有硬编码修订键，新 provider 会直接返回 camera_stage。核对面板只消费可感知的名称/内容，不显示 revision。测试证明旧操作账本里的 toolbox 期望值不会阻止新范围读回，仍要求用户核对，不凭当前状态自动改判成功，也不重写历史操作结果。

外部契约从本工作区的 2.5.3 升为 **2.6.0**；describe_application_contract 工具说明和返回工作流均说明范围变更及旧基线恢复。规范化工具目录 SHA-256：

## 按实体判断冲突的评估（本任务不实现）

**可行，但不属于小改动。** 当前 readRevision() 无文档/实体参数，由 getHostScopeRevisions().camera_stage 提供领域级计数：实际上比“整份文档”还粗，不同文档也可能相互使严格基线过期。本次只改归属键，不改变计数粒度或现有业务并发语义。

执行协调器对未知/未保存操作已有按目标引用的 write/append 保护及文档包含子实体判断；它与乐观并发修订是两种保护，不能仅放宽前者就声称实现实体级冲突。

若后续实施，需要一起设计：

- 文档实例及对象的单调修订来源，覆盖界面操作、后台实例、撤销/重做、重新加载与删除后同名引用重建；宿主汇总计数和目标写入基线分开。
- 描述符/provider 的作用域解析、availability、expectedRevisions 合并、计划与每步提交校验，以及所有执行/补偿回执；不能只在 MCP 按 ref 比较。
- 动画修改会自动创建或更新包含完整场景状态的关键帧；运镜还读取摄像机、目标物体、轨迹、时间轴等依赖。应记录实际读集合与写集合，保留场景/集合结构修订，避免修改不同对象却覆盖共享关键帧或使用过期包围盒。
- 事务锁、未知结果保护、操作核对、持久基线过期策略，以及删除/复制/集合重排和批量事务的组合回归。外部作用域键再次变化需升级契约；可先做按文档独立计数，再做受控实体级细分。

验收至少应证明“同文档互不依赖的对象可并行、同对象竞争拒绝、跨对象读依赖拒绝、关键帧级联不丢失、删除与撤销不越过保护、不同文档不互相误冲突”。现有领域级计数不足以安全支持这些结论。

## 给外部 Agent 的复测步骤

由总管理者集成并更新运行产物后进行；本任务没有启停实例。

1. 建立新连接并 tools/list；调用 describe_application_contract，确认 externalContractVersion=2.6.0、说明包含 camera_stage 更名。旧客户端目录缓存须重新拉取。
2. 对测试镜头文档及任一对象调用 read_application_entity，带 includeRevisions:true；确认 revisions 仅含 camera_stage，新 baselineId 可用于严格写入。scopeRevisions 可同时含 toolbox，但它是工具箱的独立键，不是镜头修订。
3. 在测试文档调用 place_camera_stage_object（免费几何体，新的 operationId，includeRevisions:true），确认 resultingRevisions 使用 camera_stage、核对 verified，并读回返回对象的真实位置和名称。
4. 先读对象取得 baselineId，再通过另一操作修改同场景；用旧 baselineId 严格写入应收到 CONFLICT、recoverable:true，提示重读。重新读取并以新操作标识提交应成功；核对未重复创建对象。
5. 使用升级前留下的镜头 toolbox baselineId，应收到 BASELINE_EXPIRED 并提示重读；重启使宿主代次变更也会按原规则返回过期。新读取后继续可写，不要求迁移或清空数据库。
6. 对具备删除授权的测试对象，读取新基线后删除，确认后续同文档写入继续可用。切换工具箱页面不应使 camera_stage 基线增加；实际镜头编辑应增加 camera_stage。
7. 若有旧 unknown 镜头操作，按原 operationId 进入 review_application_operation：读取当前目标后仍由应用内面板核对，界面不展示 revision，不自动重放旧操作。不要为构造场景调用真实付费生成。
