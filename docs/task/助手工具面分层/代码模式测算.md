# 助手工具面分层：代码模式测算

2026-11-14，零成本测算：只读已有基线的日志链路，不跑助手、不花钱。问题是给内置助手加“运行脚本”工具（模型写一段标准 JS，只经 `app.call(name, input)` 调应用能力，中间结果留在执行环境，只把 log / return 交回模型）之后，请求轮数与累计输入 token 能降多少，以及它在“整份快照读取”（[分类.md](分类.md) 第 2 批）之上还剩多少增量。

## 一、数据与口径

- 运行：[基线.md](基线.md) 首轮 `results/基线-11-14.json` 的 V1–V3、C1–C2、A1–A2 各 2 次；修图两条用 `results/4u5-修图.json` 的重跑（首轮 I1、I2 四次都因应用缺口失败，路径不代表工具面成本，只在第六节作参照）。共 9 条任务、18 次运行，同一模型（DeepSeek V4.1 Flash）。
- 逐调用数据：每次运行用 `node scripts/query-logs.cjs --chain <runId> --json` 取回，按“每轮请求的输入（含缓存命中）/ 输出，以及这一轮发出的调用、调用参数、调用结果”整理。
- 本文的调用数**含 `load_application_tools`**（基线表的“工具调用”不含它），所以比基线表多 2–4 次。
- **实测**：现状的请求轮数与累计输入 token，每条调用的标注。**估计**：快照与脚本两种情形的轮数与 token，全部由下文第三节的规则推出，没有真实运行过。

## 三、推算方法

### 3.1 现状怎么还原成可改写的账

对每轮请求 i，`Δi = 第 i+1 轮输入 − 第 i 轮输入`，就是第 i 轮往对话里新加的内容（模型输出 + 本轮调用结果 + 加载工具带来的定义增长）。抽查过：小结果的轮次 Δ ≈ 输出 + 结果长度，输出（含推理）确实留在后续上下文里。Δ 扣掉本轮输出后按本轮各调用的结果长度分给各调用。用“第 1 轮输入 + 前面各轮 Δ 之和”重算 18 次运行，与实测累计输入完全一致。

### 3.2 只做整份快照（估计）

按分类.md 第 2 批的设想：读文档状态一次拿到分层快照，属性名与当前值都在里面。

- 调用序列里**连续的**读状态调用（`list` / `read` / `get_canvas_document` / `get_canvas_node`）合成一次快照，占一轮；其中因属性名猜错而失败的读调用消失。
- 快照结果按被合并的读结果之和计，下限 600、上限 3000 token（小文档的整份快照比一次点名读大，比一串读小）。
- **保守**：查结构（`describe_application_entities`）全部保留。**乐观**：针对单个实体类型的 `describe` 也被快照顶掉（快照里已有属性名与可写性），领域目录级的 `describe`、契约、技能、工具目录仍保留。
- 写入失败（引用格式、文字片段建法猜错）照样保留。

### 3.3 快照 + 脚本（估计，下限）

在 3.2 的调用序列上分段：**连续的机械调用合进一段脚本，一段脚本只占一轮请求**；遇到“学 / 错 / 看”这类结果必须交回模型的调用，这一段在它之后结束，下一段另起一轮。最后加一轮作答。

- 脚本段往对话里新加的内容 = 被合并各轮的输出（当作脚本代码）+ 交回模型的结果（学、错的全文；机械部分只交回 log / return，按至多 400 token 计）。
- 运行脚本工具本身的说明按每轮多 1000 token 输入计。
- “下限”的意思是假设模型写的脚本一次就对。**失败一次**列假设每段含写入的脚本都先失败一次、多一轮修正，作为脚本情形的现实上沿。

## 五、读法

1. **之前估的“脚本在快照之上约 40%”落在区间里，偏保守一侧。** 理想下限是 53%~58%，每段带写入的脚本都失败一次时是 37%~43%。真实值大概在两者之间。
2. **只做快照省得少（9%~20%），原因有两个，在序列里都看得到。** 一是读调用大多夹在两次写之间（写完要读回新建出来的引用才能写下一步），不连续，合不成一次快照。二是读结果本身不大：剪辑每次运行里“学”的结果约 3.6 万 token，机械调用的结果合计只有约 0.8 万。累计输入贵，是因为前面学来的三四万 token 被后面每一轮重带一遍，而轮数主要被“写→读→写”的串行依赖撑着。快照压的是读的体积和查结构的次数，压不掉轮数；脚本把写和读回放进同一段程序，直接压轮数。乐观口径（快照顶掉单实体的结构查询）在剪辑 V2 上能省 37%，说明快照能否省掉 `describe` 是它自身收益的关键。
3. **最受益：剪辑（V1–V3）、画布 C2、修图 I2，以及所有“读回再写”的串行小步任务。** 剪辑三条绝对量最大，累计输入 363 万 → 约 108–155 万；C2 与 I2 的形态相同。音频按比例同样省一半以上，但绝对量只有几十万。
4. **不受益或受益小：判断步骤占比高的任务。** C1 只省约三成五（26.6 → 17.4 万）：它的读本来就是一轮里并行发出（`读读读读`），可合并的轮次少；剩下的前几轮是查节点类型和节点结构，属于“学”，脚本合不掉。I1 本来就只有 10 次上下的调用，省的绝对量很小。处理意外错误同样合不掉：V1 两次各有 5–8 次失败，每次失败都把一段脚本截断，V1 是剪辑里省得最少的一条。
5. **这 9 条偏向脚本有利。** 任务文字给定了全部数值，无窗口实例不取帧，没有一次“看画面”或“创作取舍”。真实创作里每看一次画面、每做一次取舍都要交回模型，增量会低于本表；本表适合作为“机械型操作”的上限参考。

## 六、口径之外的说明

- 首轮 I1、I2 四次失败运行（应用缺口导致）同样标注过：判断步骤占一半左右（I1#2 有 24 次“学”、2 次“看”），脚本合并后仍要 16–30 轮，说明能力缺口带来的试探与绕路脚本救不了，要先修能力本身（已在 4u5 修掉）。
- 累计输入含缓存命中。费用主要由未命中输入决定（未命中单价约为命中的 50 倍），轮数减少同样减少“加载后重算”的机会，但本表不换算成费用。
- 批次 01（加载工具不再改工具列表）之后的运行没有纳入：它改变的是每轮未命中比例，不改变调用序列形态，结论方向不受影响。
- 所有估计都按单个模型、每条两次运行；运行间波动在 20%~30%，按工作区看方向，不按单条精确值读。
- 测算脚本与中间数据只放在临时目录，没有进仓库；需要复算时按第三节规则对同一批 runId 重做即可。
