# 助手工具面分层：基线

2026-11-14 首次测量。每合并一批工具后重跑同一组任务，对比成功率、步数、token 与耗时。分类表见 [分类.md](分类.md)。

## 一、怎么跑

```bash
# 全部九条任务各跑两次（已有同名结果时接着跑，不重跑已完成的轮次）
node docs/task/助手工具面分层/baseline.cjs --label <批次名>

# 只跑点名的任务
node docs/task/助手工具面分层/baseline.cjs --label <批次名> --only V1,C2 --runs 1

# 只统计对外工具面的体积，不跑助手
node docs/task/助手工具面分层/baseline.cjs --static
```

- 底下用的是 `npm run assistant:cli`（无窗口实例，内置助手），跑在**真实配置与真实数据目录**上。无窗口实例不参与单实例锁，可以和带窗口的应用同时运行。
- 只在项目“工具面基线 11-14”里新建文档；任务文字里写明不调付费能力、不往素材库加东西、不切换界面。
- 需要最新的 `out/` 产物。别的任务也在改源码时启动器会报“产物比源码旧”；确认产物是刚打的之后可以加 `HENJI_SKIP_BUILD_FRESHNESS=1`。
- 测试素材（6 秒视频、一张图片、10 秒声音）由脚本用 ffmpeg 生成到系统临时目录的 `henji-tool-surface-baseline/`。
- **每次运行有上限**：累计输入 token 超过 150 万或工具调用超过 45 次就中止这次运行，记为“失败（超限）”。可用 `--max-input-tokens`、`--max-tool-calls` 调整。模型调用按 token 计费，这条不要去掉。首轮（11-14）用的是 100 万与 30 次：剪辑三条本来就要 28–36 次，30 太紧，11-14 修图重跑起放宽；首轮只有 I2 第二次是被 100 万上限中止的，其余结果不受影响。
- **带窗口的正式实例正在用 `out/` 时不重新打包**：另建一份产物 `node --max-old-space-size=8192 node_modules/electron-vite/bin/electron-vite.js build --outDir .tmp/assistant-baseline-build`（SDK 改过先 `node scripts/build-sdk-if-needed.cjs`），再用 `HENJI_BASELINE_BUILD_DIR=.tmp/assistant-baseline-build` 运行本脚本。
- 结果写到 `results/<批次名>.json`：每次运行的调用序列、用量、费用，以及工具面体积。
- 无窗口实例关了显卡，任务里不含取帧、导出这类要合成画面的步骤。
- 是否通过：助手必须在回复最后一行给出从应用读回的 `RESULT: {…}`，脚本核对数值。这是“助手自己读回”的口径，不是脚本另行检查文件。

## 四、从首轮看出的事

1. **步数是主要成本，不是工具个数。** 剪辑三条都是三四步就能说清的小任务，却要 28–36 次调用、110–130 万累计输入。调用序列里反复出现的是 `describe_application_entities`、`list_application_entities`、`read_application_entity`：先查有哪些属性，再一种实体一种实体地列，再逐个读。画布有现成的整份读取（`get_canvas_document`），同等复杂度只要 27–57 万；音频实体少，只要 18–27 万。这直接支持分类表里“先补整份快照读取”排在前面。
2. **每加载一次工具，缓存就失效一次。** 加载后那一轮的未命中输入会从几百跳到几万甚至十几万（I1 第二次里出现过 11 万、16 万、18 万）。对应待办 4u1。
3. **查结构很贵。** 一次 `describe_application_entities` 带 `detail="full"`、一次 `describe_application_contract` 带 `includeSchemas`，单轮输入就涨 1.5–4.6 万 token。I1 第二次到后面每轮都带着约 19 万 token 的上下文跑，43 轮累计 583 万、¥2.45。对应待办 4u2。
4. **剪辑每条都有 2–6 次失败调用**，多数是属性名、引用格式或单位猜错后自纠。快照里直接给出属性名与当前值，这类试错会少。
5. **两套撤销让助手拿不准。** C2 两次都是先调 `undo_canvas_change` 又调 `undo_application_changes` 才把删除撤回来，对应分类表里“撤销重做统一”。

### 修图两条为什么全失败

两条卡在同一处，是应用能力缺口，不是工具太多：

- `create_document` 的参数枚举里有 `image_document`，但调用被拒绝：“这种文档请在它自己的编辑器里新建”。后面还拼了一句无关的“文件损坏时从备份恢复”。声明说能建、实际不能建，拒绝也没有指出该走哪条路。
- 没有“不开界面、不进素材库，按本机路径把图片放进图片文档”的路径。唯一走得通的是先 `import_local_media` 进素材库，再 `open_image_editor_with_source` 打开编辑器。
- I1 第一次：助手守住了约束，查了 24 次后如实说做不到（89 万 token）。
- I1 第二次：助手自行放宽约束，把测试图片加进了素材库、打开了图片编辑器、建出文档并改好了图层名和不透明度；随后 `read_application_media` 以图片方式返回结果，当前模型不接受工具结果里带图片，接口报 400，整次运行失败。**工具结果带图片时没有退路，一次调用就让整个任务报废**（待办 4t 里“不支持视觉时的退路”）。
- I2 两次同样先被 `create_document` 挡住，一次死在同一个 400，一次超过 100 万上限被中止。

这三处（图片文档建不出来、没有按路径导入、图片结果让运行崩掉）建议单独记进待办，和工具面分层分开修；修好之前 I1、I2 的基线数字不代表“工具面”的成本。

### 这轮留下的痕迹

- 项目“工具面基线 11-14”里新增了约 20 份测试文档（剪辑、画布、口播、图片文档）。
- I1 第二次违反任务约束，往素材库加了一条 `still.png`（来自系统临时目录的测试图片），并新建了一份图片文档后移进测试项目。没有碰其他项目和已有作品。
- 没有任何付费能力调用（每次运行的 `paidCalls` 都是 0）。

## 四点五、修图缺口修完后的重跑（2026-11-14，结果 `results/4u5-修图.json`）

三处缺口修掉后（`create_document` 可后台建图片文档并带本机图片作底图、回执带内容实体引用；DeepSeek 挂联网工具时工具结果里的图片挪到随后的 user 消息），只重跑修图两条，各 2 次，同模型同任务文字。

读法：

- **加载后不再整段未命中，这点成立。** 逐请求看，加载工具之后那一次请求的未命中输入从几万降到几千（例：V1 第二次加载后 2811 未命中、15872 命中）。未命中输入除 C1 外都下降（约降一半到三分之二），费用除 C1 外都下降（V1 只是略降）；与修图 4u5 重跑相比，I2 也从 ¥0.25 降到 ¥0.12。
- **V1 变差，需要盯住。** 两次都在做完前撞上 150 万上限；把上限放宽到 250 万另跑两次（`results/批次01-V1放宽上限.json`）都能做对：36、37 次调用，227 万、135 万累计输入，¥0.46、¥0.25。调用次数与首轮相同（36），累计输入四次里三次高于首轮的 131 万。失败调用全是属性名、引用格式、文字片段建法猜错后自纠（首轮同一类），没有一次出在分派调用上；但累计输入偏高是否与“定义进了对话内容”有关，四次运行下不了结论。它本来就贴着上限，根子是步数，等整份读回。
- **C1 也偏高**（两次 27、25 次调用，首轮 22）：多出来的是绕去读项目记忆、重复查节点结构，同样不是分派出错；费用 ¥0.16、¥0.12 高于首轮 ¥0.09。样本少，记为未改善。
- 一次运行的波动在 20–30%，这张表每条只有 1–2 次，除 V1、C1 外的差别按“方向一致”读，不按精确倍数读。
- 本轮基线共约 ¥2.3（全量 ¥1.21、V1 与 C1 加跑 ¥0.39、V1 放宽上限 ¥0.72）。

## 五、之后怎么比

每批合并后用新的批次名重跑，对比 `results/` 里两份文件的 `summary`：

- 通过数不能降。
- 工具调用、模型请求、累计输入 token、耗时不能升；合并“整份快照”那一批之后，剪辑三条应当明显下降。
- `surface` 里的工具数与输入结构字符数随合并下降。

模型输出有随机性，单条两次的波动在 20–30% 左右（V3 两次是 31 与 24 次调用）。差别在这个范围内的不算变化；要下结论时把 `--runs` 提到 3 或 4。
