## 记录 001：关键帧动画引擎选型

- 日期：2026-07-02
- 状态：已确定（选型已定，但本次任务不实施，留给后续关键帧动画任务）
- 背景：调研参考产品 LibLib TV「3D导演台」时发现其最大短板是只能导出静态图片，没有关键帧/时间线/速度曲线能力。用户明确希望后续做出这块差异化能力（能给属性做关键帧、能导出动态视频）。调研比较了"引入 Theatre.js core"和"完全自研关键帧/曲线系统"两条路。
- 最终决定：使用 Theatre.js 的 `@theatre/core`（纯动画引擎：关键帧数据结构、插值、贝塞尔缓动曲线数学），不使用它自带的 Studio 编辑器 UI；时间线/关键帧的可视化界面自己用项目现有 `Ui*` 组件搭建，保持视觉一致。
- 选择原因：Theatre.js 是成熟开源方案（Apache-2.0，持续维护），专为 three.js/WebGL 场景的电影级关键帧动画设计，能省去自研插值和曲线数学的工作量和踩坑成本；只取其核心引擎、自研 UI 层，避免引入不匹配项目设计语言的现成界面。
- 影响任务：不影响本次「运镜控制」一期任务（1.1-3.2），影响未来的关键帧动画任务立项时的技术选型起点。

## 记录 002：免费动作库来源选型

- 日期：2026-07-02（2026-07-03 经 1.2 实测与调研修订）
- 状态：已修订（Quaternius 升级为角色骨架/通用姿势主要来源，Mixamo 降为长尾姿势补充来源）
- 背景：需要人形角色的骨骼绑定和动作/姿势数据来源，调研了 Mixamo（Adobe 免费服务，标准人形骨架+数千免费动作，仅出 FBX/Collada，需转 glTF）和 CC0 低多边形库（Poly Pizza 原生 glTF、Quaternius、Kenney.nl，模型现成但动作稀少）两条路。
- 最初决定（2026-07-02）：人形骨骼与基础姿势/动作以 Mixamo 为主要来源；道具、几何体等非角色资源以 CC0 低多边形库为主要来源。
- **修订后决定（2026-07-03）**：改为 Quaternius Universal Animation Library 作为角色骨架和通用姿势的**主要来源**（1.2 已实测验证：原生 glTF 免转换、单包 43 个姿势/动作片段、CC0 协议）；Mixamo 降级为**长尾补充来源**，只在 Quaternius 覆盖不到具体动作（如踢球、看手机等）时才下载使用，届时需要走 FBX→glTF 转换流程。两者骨骼结构可互相重定向，不冲突。
- 修订原因：① Quaternius 原生 glTF，省掉 1.2 原计划里整套 FBX 转换管线验证工作；② Quaternius 是 CC0，比 Mixamo"可商用但不能单独重新分发原始文件"的条款更干净、理解成本更低；③ 调研同时澄清 Mixamo 实际条款其实足够宽松（转换后打包进应用分发不构成"单独重新分发原始文件"），原担忧偏保守，但已有更优选项时无需再依赖它做主力。
- 影响任务：1.2（已实测，执行记录已更新）、2.2（角色姿态系统，预设姿势库设计时需对照 Quaternius 现有 43 个片段清单确定缺口，缺口部分才需要引入 Mixamo）。自定义上传模型自动复用动作库需要额外的骨骼映射与重定向能力（可参考 VRM Humanoid 规范，`pixiv/three-vrm` 生态已有 Mixamo→VRM 重定向工具），本次任务不做，留独立任务。

## 记录 006：三维资源加载路径不能走 public/ 静态资源

- 日期：2026-07-03
- 状态：已确定
- 背景：1.2 验证 Quaternius 角色资源加载时，最初把 GLB 放进 `public/camera-stage-verify/` 并用绝对路径 `/camera-stage-verify/xxx.glb` 引用（Vite 默认约定：`public/` 内容原样拷贝到产物根目录，绝对路径引用）。开发态（`npm run electron:dev`，vite dev server）加载正常，但走完整 `electron:build` 后在打包产物里实测报 `ERR_FILE_NOT_FOUND`。
- 根因：打包态 Electron 用 `win.loadFile` 以 `file://` 协议加载 `out/renderer/index.html`（`electron/main/window.ts:48`），此时以 `/` 开头的绝对路径会被解析为磁盘根目录（如 `file:///xxx`），而不是应用目录，这与部署到 http 服务器时"绝对路径指向站点根"的常见假设不同。
- 最终决定：2.x/3.x 正式的三维模型/动作/道具资源不采用 `public/` 静态资源 + 路径引用的方式，统一走项目现有的 `henji-media://` 协议 + 主进程媒体根目录白名单机制（`electron/main/protocol.ts`）读取，与图片/视频资源的加载方式保持一致。
- 选择原因：`henji-media://` 协议在开发态和打包态行为一致，不受 `file://` 绝对路径这个坑影响；同时符合项目"不新建一套独立资源加载方式"的既有架构约定。1.1/1.2 验证代码里用相对路径是验证期权宜写法，不代表正式方案，2.1 正式开发时需重写为协议加载方式。
- 影响任务：2.1（场景数据模型与对象编辑，涉及首次正式设计资源加载方式）、2.2（角色姿态系统，涉及角色模型/动作资源加载）、3.1（子项目持久化，工程文件里对资源的路径引用方式需要和这个结论一致）。
