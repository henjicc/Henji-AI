## 目标

设置里查看与更换作品目录（默认“文档/痕迹AI”）：主进程整体移动文件夹，失败或取消时原目录保持完整、设置不变；不改写任何数据库记录与文档（位置都是相对写法）。删除渲染层逐文件复制的旧迁移。

## 实现

### 主进程（`electron/main/services/work-root/`）

| 文件 | 职责 |
|---|---|
| `moveWorkRoot.ts` | 纯文件系统移动：目标检查（不存在或空文件夹；不能在旧目录里面或包含旧目录）；同盘整体 `rename`（原子，文件被占用时系统拒绝 → `in_use`）；跨盘或 `EXDEV` 时复制（清点 → 空间检查 → 逐个 `COPYFILE_EXCL` 复制 → 补拷 → 逐个核对大小 → `commit` → 删除旧目录）。`commit` 之前任何失败或取消都回滚：改名模式改回原处，复制模式删除新副本（目标原本是空文件夹则清空保留），并删掉为此新建的父文件夹 |
| `service.ts` | `createWorkRootService(deps)`：解析目标、单实例运行（并发报 `busy`）、生成结果仍在取回或保存时拒绝、`commit` 里切换设置、完成后建分类文件夹并刷新作品索引、`dispose` 取消并等待回滚 |
| `runtime.ts` | 正式依赖：`appPaths` 布局、`dataRoot.writeCustomDataRoot`、`getDocumentService().refreshIndex()`、`ai-runtime.hasActiveGenerationWork()`；`openWorkRoot`（`shell.openPath`）、`relaunchAfterWorkRootChange`、`disposeWorkRootChange`（登记到 `bindApplicationShutdown`，退出时移动未完成则取消并等回滚） |

- 目标解析：恢复默认 = 默认位置；自选文件夹名字是“痕迹AI / Henji AI”或是空文件夹（含不存在）就直接用，否则在其中新建“痕迹AI”（按作品目录确定时的语言）。
- 设置：`custom_data_directory` 经 `settings/raw.ts` 原样写入（新增 `deleteRawSetting`，恢复默认即删除该行）；`user_data_root`（默认位置）不变。
- 不改写记录：数据库仓库按 `henji://user/…`、`henji://project/<ID>/…` 存取，切换后按新作品目录解码；作品索引里的项目路径由刷新扫描按项目说明里的稳定 ID 重新认领（旧位置不在后不会误判副本）。外部位置（作品目录之外的项目、另存位置）不在移动范围内，不动。
- 媒体授权：`henji-media` 协议每次按 `getUserRootDir()` 授权，切换设置后立即覆盖新位置，无需另行刷新。
- `ai-runtime/runtime.ts` 新增 `hasActiveGenerationWork()`（提交中的生成 + 正在轮询的任务）。
- 日志：`main.work_root` 域 `work_root.move.start/completed/failed/cancelled/cancel_requested`、`work_root.setting.switched`、`work_root.index.refresh_failed`、`work_root.cleanup.incomplete`、`work_root.open.completed/failed`、`work_root.relaunch.requested`、`work_root.shutdown.cancel`。

### 接口

IPC `electron/main/ipc/work-root.ts`（`workRoot:getInfo / inspectTarget / change / cancel / open / relaunch`，进度事件 `workRoot:progress`）→ preload `work-root-api.ts`（`henjiNative.workRoot`）→ PAL `src/platform/contracts/workRoot.ts`（`WorkRootPlatform`、通道表、错误码）→ adapter `workRoot.ts` → `src/commands/workRoot.ts`。失败原因写在错误消息前缀（`busy:`、`in_use:`、`cancelled:` …），渲染层用 `readWorkRootMoveErrorCode` 取出。`ipc/window.ts` 新增 `approveAllWindowsClose()` 供重启使用。

### 渲染层

- 设置 › 文件与下载 › 作品目录（`DataPathSection`）：只读路径（观察遮罩）、“在文件夹中打开”、“更换位置…”、自定义时“恢复默认位置”；常驻说明讲清只移动作品、程序数据不动、完成后重新启动。
- `useDataPath`：选文件夹 → 主进程检查目标（不可用直接提示原因）→ 确认框（显示实际目标路径，观察遮罩）→ 在应用关闭屏障 `closeApplication` 里执行：先像关闭应用一样保存全部打开的文档会话（2.4 登记表的关闭守卫）与各工具实例并冻结新的写入，再移动，成功后在冻结期间重启。屏障拒绝（有操作在进行）、主进程失败、取消都解除冻结并提示“作品目录保持不变”。
- 弹窗统一为 `DataPathDialogs`（设置页与首次引导共用）；进度弹窗在可回滚阶段（清点、复制、核对）提供“取消”。`SettingsDialog` 增加 `detailPath`（路径单独一行、观察遮罩），`SettingsProgressDialog` 增加可选取消。
- 首次引导的“数据目录”一步改叫“作品目录”，复用同一套弹窗。
- 删除：`src/utils/dataPath.ts` 的逐文件复制迁移（`migrateData`、合并 / 覆盖、迁移标记、`validateDirectory`、`hasExistingData`、`setCustomDataRoot`、`resetToDefaultDataRoot` 等）及其测试 `dataPath.migration.test.ts`；localStorage 旧设置搬运（记录 008 不兼容老数据）；无人使用的 `getDefaultDataRoot`、`getHistoryFilePath`、`getPresetsFilePath`；生成工作区对 `dataPathChanged` 事件的监听（更换后整个应用重启）。合并 / 覆盖等旧文案删除。

### 助手

按 skill `henji-application-capability` 分级：作品目录是已有的受保护设置 `storage.data_path`（只读，`writable: false`），本次只改说明与读取值，不新增能力。读取返回 `usesDefaultLocation`（是否默认位置，来自渲染层最近一次目录快照），不返回本地路径。不开放更换：要整体移动全部作品、先保存并冻结所有打开的内容、完成后重启应用，且新位置必须由用户在系统选择器里选定；说明里给出 `open_application_surface` 到 `files-storage` 的替代路径。

### 选型

- 移动自写（约 300 行）：`fs-extra.move` 跨盘时“复制后删除”但不做逐文件核对、不支持取消与中途回滚，也不区分“目标原本是空文件夹”；`move-file` 只处理单个文件。需要的都是 Node 自带能力（`rename`、`copyFile` 的 `COPYFILE_EXCL`、`statfs`）。
- 同盘整体改名而不是逐项改名合并：目标必须为空，一次 `rename` 原子完成，失败时不存在半截状态。
- 更换走应用关闭屏障而不是另写“保存全部”：屏障已经覆盖文档会话、各工具实例、空草稿处理与写入冻结，更换后本来就要重启。

## 遗留

- 未运行真实 Electron：设置页界面、系统文件夹选择框、真实同盘改名 / 跨盘复制、`shell.openPath`、更换后自动重启（窗口批准关闭 → `app.relaunch`）、重启后作品索引与生成记录按新位置显示，需在下一次 `electron:bundle` 后的真实窗口确认（建议：设置 › 文件与下载 › 作品目录 → 更换到另一盘的空文件夹 → 重启后打开生成记录与项目页）。
- 尚未接入文档底座的旧工具存储（画布 `storyboard_projects`、镜头参考、口播的工程表，渲染层直接写的 `.henji-video`）内容里仍是绝对路径，更换作品目录后这些旧工程引用的作品目录内文件会失效；按记录 008 不兼容旧工程，3.x 各工具接入后消失。
- 首次引导中更换会重启应用，重启后引导从头显示（引导未标记完成）。
- 后台写入作品目录的其他长任务（视频导出、图片导出等）未单独检查；它们若由工具实例发起会被关闭屏障的“有操作在进行”拦下，主进程独立长任务没有统一的忙碌查询。
- 媒体协议过去为作品目录内子文件夹持久化过的授权不会清理（在默认范围内的不会持久化，影响很小）。
