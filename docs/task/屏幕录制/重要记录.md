## 记录 001：录制产物是“录制会话文档”，不是单个视频文件

- 日期：2026-10-14
- 状态：已确定
- 背景：传统录屏只输出 mp4，后续推近、光标、打码只能在烤死的画面上做。
- 最终决定：新增文档类型“录制会话”，内容包括多轨原片引用（屏幕、摄像头、麦克风、系统声音）、事件日志、标记、理解结果（文字稿、步骤、候选打码）和派生成片的引用。成片是剪辑工程里的序列，引用会话的原片轨，不复制文件。格式按 `persistence.md` 登记基线。
- 选择原因：保留原始信号，AI 才能事后重新推近、重绘光标、改画幅、重录某一步；也让助手能读回“每一步发生了什么”。
- 影响任务：1.5、2.1–2.4、3.1、3.2、4.1–4.3

## 记录 002：Windows 主路径用 FFmpeg gfxcapture 录无光标原片，getDisplayMedia 兜底

- 日期：2026-10-14
- 状态：已确定（1.2 先做实测，数据不支持时改用兜底路径为主，并在本记录补充）
- 背景：调研比较了 getDisplayMedia + WebCodecs、FFmpeg gfxcapture/ddagrab/gdigrab、libobs、ScreenCaptureKit。随包 FFmpeg（BtbN n9.0.2 GPL shared）已带 gfxcapture 和 nvenc/qsv/amf。
- 最终决定：
  - Windows 10 1903 及以上：主进程子进程 `gfxcapture`（`capture_cursor=0`）加硬件编码，分片写盘；
  - 其他环境：`getDisplayMedia`（主进程 `setDisplayMediaRequestHandler` 选源）加 WebCodecs + mediabunny（复用剪辑导出编码器）；
  - 两条路径实现同一个采集后端接口，上层不感知差异；
  - 兜底路径的光标烤在画面里，光标重绘相关功能在会话里标记为不可用，并在界面上如实说明。
- 选择原因：gfxcapture 画面不出显卡、可单录窗口、可关光标，是光标重绘与零拷贝的前提；成熟方案直接用，不自研采集。
- 影响任务：1.2、2.1

### 1.2 实测补充（2026-10-14）

- Windows / Ryzen 9 5900X / RTX 4090，双 4K 显示器、150% DPI；单隔离 Electron 中同时持续播放剪辑预览，两条正式后端各录 1080p60、4K60 约两分钟。
- 实际解码计数：WGC 1080p 为 121.283 秒 / 7277 帧（60.00fps），4K 为 121.550 秒 / 7291 帧（59.98fps）；Chromium 1080p 为 120.383 秒 / 6240 帧（51.83fps），4K 为 120.750 秒 / 5469 帧（45.29fps）。兼容路径在本机负载下未持续达到 60fps。
- **保留原决定：Windows 默认 WGC，Chromium 兼容兜底。** WGC 原片抽样未见光标，Chromium 样本可见光标。两条路径的暂停续录、损坏尾片恢复、正式剪辑定位/播放均通过。
- 资源指标、统计口径、完整命令与限制见 [1.2 执行记录](任务/第一阶段-采集底座/1.2-屏幕采集与编码后端.md#双后端实测口径)。显存为整卡值，不据此宣称独占开销或零拷贝；60 分钟多轨、macOS 和设备变更仍需后续联合验收。

## 记录 003：所有轨道与事件对齐到同一个单调时钟

- 日期：2026-10-14
- 状态：已确定
- 最终决定：屏幕帧、摄像头帧、麦克风、系统声音、光标与点击事件、能力调用全部换算到 `src/core/audioEdit/recordingClock.ts` 的 `monoUs`，每 5 秒重新校准一次漂移（沿用 2.7 的做法，修正量限制在一个量子内，时间不倒退）。验收标准：60 分钟录制音画与事件漂移不超过 1 帧/分钟。
- 影响任务：1.2–1.4

## 记录 005：隐私默认值

- 日期：2026-10-14
- 状态：已确定
- 最终决定：
  - 按键默认只记“有按键”和组合键类别（例如“复制”“撤销”），不记字符内容；
  - 录制控制条、倒计时、录屏工具自身的浮窗用 `setContentProtection(true)` 排除在画面外；
  - 录前可以选择排除窗口；
  - 暂停期间不采集、不补造事件；
  - 敏感信息打码只出候选，由人确认后才生效（AI 先做、人确认）；
  - 全局输入钩子只在录制中启用，停止后立即卸载。
- 选择原因：全局钩子容易被当成键盘记录器，默认最小采集。
- 影响任务：1.1、1.4、3.1

## 记录 009：OCR 借鉴用户的 FlashOCR，模型与策略并入现有推理进程

- 日期：2026-10-14
- 状态：已确定
- 背景：用户提供了自己的项目 `D:/VibeCode/REA-TEST/FlashOCR`（纯 Rust + ONNX Runtime，PP-OCRv6，针对整屏截图优化）。实测 4K 稠密页（96 行）常驻模式约 240–270ms。3.1 已合并的管线未用真实模型测过，并有三个性能缺陷：识别会话按行宽反复重建、逐行串行无批处理、只有整帧逐字节相同才跳帧。
- 最终决定：采用“借模型与策略、并入现有 onnxruntime-node 本地推理进程”的方案，不把 FlashOCR 作为第二个推理子进程分发（避免同功能两套 ORT 推理与 DB 后处理，也免去 macOS 新打包链）。具体包括：
  - 模型换 PP-OCRv6 tiny（检测 + 识别）；可选 small 识别做精确档；
  - 检测最长边 960、短边下限 448；识别裁片取原分辨率；
  - 识别按宽度排序、按像素预算装批，固定一个动态形状会话，识别走 CPU；
  - 分块差异跳帧，屏蔽光标区域；未变化的框按裁片哈希复用结果。
  FlashOCR 只作为开发机上的速度和精度对照工具。
- 影响任务：3.1（返工 3.1b）、剪辑智能区域“擦字幕 / 文字打码”（共用检测模型与后处理，需要回归）
