# 1.3 多轨声音摄像头与时钟对齐

## 任务状态

- 状态：待验证
- 所属阶段：第一阶段-采集底座
- 前置任务：1.1
- 关联任务：1.5、2.3、2.4

## 任务目标

同时录麦克风、系统声音和摄像头，各自成轨，并与屏幕帧、事件日志对齐到同一时钟，长时间录制也不漂移。

## 当前情况

- 麦克风：`src/features/creativeIntent/recording/microphone.ts`（getUserMedia + AudioWorklet）和 `src/core/audioEdit/recordingClock.ts`（把声卡时钟对齐到 `monoUs`，2.7 已加上每 5 秒校准一次）。
- 系统声音：Chromium 回环。Windows 走 WASAPI loopback；macOS 14.2+ 需要 `NSAudioCaptureUsageDescription`，缺了它会得到一条哑音轨，而且不报错。
- 摄像头：全仓还没有采集。

## 实施方案

1. 麦克风轨复用现有采集和时钟，不另写一套。系统声音轨和麦克风分开写盘，方便事后单独调整和对白闪避。
2. 系统声音哑轨检测：开始录制后如果一直是静音，而当前平台已知有这个风险，就提示用户检查权限。
3. 摄像头轨：可选设备、分辨率、帧率，单独编码成一条视频轨；录制控制条里显示小预览（不进录制画面）。
4. 对齐：每条轨的起始时刻和周期校准点写入会话。导入剪辑时按 `monoUs` 精确对齐，并记录各轨的延迟补偿。
5. 设备在录制中断开或恢复时，会话里记下这段空档，不补造数据。

## 验收标准

- 单测覆盖对齐换算、漂移校准、设备断开空档。
- 自动化：巡检场景录 1 分钟（虚拟设备或系统默认设备），导入后各轨起点对齐误差不超过 1 帧。
- 总管理者本机验收：录 60 分钟，音画和光标漂移不超过每分钟 1 帧。
- 相关测试与门禁通过（按 `docs/rules/testing.md` 裁剪）；新增能力过能力门禁；界面改动过界面门禁；涉及 skill 或规则文档时同步更新。
- 执行记录写明改动文件、证据、计划差异和三句自查：助手能否只凭名称和说明用对？能否 AI 先做、人只确认？产物能否直接流进其他工作区？

## 执行记录

### 实现结论

- 独立底座位于 `src/features/screenRecording/tracks/`；不修改并行 1.2 的 capture 目录，不创建第二套会话控制状态机。`RecordingTracksSession` 提供 start/pause/resume/stop/cancel、轨道快照与正式读取入口，供 1.5 的唯一会话协调器调用。
- 麦克风复用原 `captureMicrophone` 与 AudioWorklet；增加可选设备、外部流、动态时钟原点和双声道。系统声音经已安装的唯一权限服务选源，回环与麦克风分别输出。Chromium 屏幕兜底可传入克隆音轨，避免第二次选源；独立回环会立即停止不需要的视频轨。
- 摄像头支持设备、分辨率、帧率；MediaStreamTrackProcessor 采帧，现有剪辑编码配置 + WebCodecs/Mediabunny 编码独立 MP4；硬件编码不支持时探测软件编码。控制条显示保持比例、最大 160×90、最多 2Hz 的 JPEG 预览，沿已有请求/状态通道发送，复用 1.1 的受保护窗口；不传跨窗口 MediaStream、不混入屏幕编码。
- 每轨按约 5 秒独立分段：音频 PCM16 WAV、摄像头 fragmented MP4；StreamTarget 经现有 PAL 按位置写盘，禁止整段内存缓存。每音轨排队最多 4MiB，摄像头最多两个原生缓冲帧并等待编码背压，超限终止并报告失败。
- 共享时钟桥位于 `src/core/captureLog/clockSync.ts`，通过已有 `screenRecording:request` 获取主进程单调微秒；所有轨道使用事件日志相同 `originUs`。沿用每 5 秒校准，单量子修正、单调时间、不确定度；相机使用设备帧时间与最佳投递相关点，而非逐帧投递时刻。`tracks.json` 保留真实起止、音频采样锚点、校准端点、设备延迟补偿、源时钟偏移、空档和告警。
- 暂停释放媒体设备，恢复重开；mute/ended 与 PCM 缺样本封段并记真实空档；摄像头缺帧保留 MP4 的真实 PTS 和缺口元数据，不重启编码器、不补帧。devicechange 只重试断开的轨道，其他轨继续；取消屏障覆盖迟到权限、启动、帧、尾包、异步写盘，停止后的迟到预览/校准失败不污染旧会话。已知系统声哑轨风险的平台连续静音 5 秒只告警一次，有声音后移除实时提醒、保留历史事实。
- `screen-recording-tracks` 已登记资源持久化契约与正式构造器生成的黄金样本、基线。新增 IPC 是原通道内的两个 action，轨道状态只允许权威 owner 写入；设备/校准等内部字段不显示在界面。

### 架构与选型

- 规模：60 分钟、两条 48kHz 声音、默认 1280×720@30 摄像头（配置上限 3840×2160@60）；约每轨 720 个分段，内存随背压上限而不是录制时长增长。4K/60 和物理设备耗时、内存、磁盘预算需总管理者实测。
- 选型：复用已安装的 Chromium/Web Audio、Mediabunny（现有 MPL-2.0 许可登记）与剪辑编码器；MediaRecorder/RecordRTC 缺少已有 AudioWorklet 的采样帧与校准锚点，libobs 引入另一套原生采集和权限链，均不采用。未新增依赖、未复制第三方源码。官方资料：<https://mediabunny.dev/guide/media-sources>、<https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrackProcessor>。
- 唯一真相：轨道服务持有采集和元数据，主进程控制服务持有录制会话控制，页面只订阅；公开会话实体、导航、设置属性与导入落位由 1.5 接入，不为内部采集驱动创建专用 MCP 工具。
- 落盘：每段 finalize 与回调是分段保存屏障，stop 等设备尾包、队列与封段后，通过既有原子文本写入保存 tracks.json；保存失败不报完成。取消保留已写片段供上层会话恢复/回收，不擅删还可能被引用的媒体。
- 验证：L2（跨进程契约、异步采集、取消、文件写入）；精确测试验证时钟/状态/失败，单次隔离 Electron 巡检验证真实 Worklet、编码与解码、受保护预览。物理采集延迟估计不等同真实测量，不把模拟漂移当物理音画验证。

### 计划差异与交接

1. 1.4 已把采集日志时钟抽出，本任务用该共享模块承载轨道关联，录音设备相关点仍复用原 recordingClock；不另建录制事件时钟。
2. 原方案“一条轨”实现为逻辑轨道 + 5 秒可独立播放的文件分段，以封存缺口、限制 WAV 体积与长录制内存；导入方按每段 monoSpanUs 定位，不把分段简单首尾拼接。
3. `recordingTrackPlacement` 已提供帧定位；真实“导入工程后误差不超过一帧”的完整链路依赖 1.2 屏幕轨与 1.5 会话文档/导入。本任务巡检只验证正式编码回读与定位换算，不冒充工程导入验收。
4. 摄像头帧时钟没有浏览器提供的物理曝光与主时钟精确相关 API；用最佳投递相关点并保留至少一帧的不确定度。物理音画误差、设备管线延迟不能由此宣称已精确测量，需总管理者长录制实测。
5. 1.5 衔接：由主进程创建唯一 originUs，传给屏幕后端、RecordingEventSession 和本服务；先在一个会话 grant 中授权全部选定媒体类型与屏幕来源（grant 替换该会话的类型集合，不能分别授权覆盖），在同一控制后端的 start/pause/resume/stop/cancel 屏障组合它们。`onFailure` 委托正式 captureFailed 清理会话；`onSegment` 接入会话资源保存，以服务快照为唯一元数据；把设备和配置字段注册为通用实体属性。monoSpanUs 已含音频延迟补偿，导入不可重复减去补偿；摄像头 MP4 内部缺帧也须按 gaps 保留空档，不能只看文件之间的空档。底座现有显式排除归 1.5，未增加助手欠账清单、未改变已通能力。
6. 总管理者验收：真实麦克风+系统回环+摄像头录制，暂停/恢复、拔插设备、静音/哑轨提示；Windows 两条屏幕路径验证控制条及摄像头预览均不进屏幕原片；macOS 14.2+ 真机核对已存在的 NSAudioCaptureUsageDescription 与权限；60 分钟使用拍手/闪帧/点击信号逐分钟核对音画与光标漂移 ≤1 帧/分钟，1080p60/4K60 并行剪辑预览实测。不得把本任务虚拟系统轨当真实 WASAPI/CoreAudio 验收。
7. 验证迭代差异：一次被产物新鲜度拦截，未启动应用；一次启动夹具过早读窗口而失败，未采集媒体。首个完整短录制虽然解码/布局断言通过，回读发现摄像头 159 分段、153 缺口，已新增红→绿保护并修复缺帧重启反馈；因此在最终验证阶段追加同一短场景复验（最终 12 分段、4 缺口）。这是由实际缺陷触发的定向复验，不做性能矩阵或长录制，不并行启动实例；首个统计保留在 `.ui-tour/recording-tracks/evidence-before-camera-fix.json`，不借它宣称修复后的结果。

### 三句自查

- 助手能否只凭名称和说明用对：本任务不开放第二套内部驱动工具；1.5 注册唯一录制会话实体与参数/控制，届时人与助手调用同一协调器。此处不宣称已完成公开能力。
