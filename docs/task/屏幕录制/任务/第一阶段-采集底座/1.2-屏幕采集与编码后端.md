# 1.2 屏幕采集与编码后端

## 任务状态

- 状态：待验证
- 所属阶段：第一阶段-采集底座
- 前置任务：1.1
- 关联任务：1.3、1.5、2.1

## 任务目标

在同一个采集后端接口下实现两条屏幕采集路径，录出无光标（Windows 主路径）、能长时间稳定运行、崩溃后可恢复的屏幕原片。

## 当前情况

- 随包 FFmpeg 自带 `gfxcapture`（基于 WGC，可按显示器、窗口句柄、进程采集；`capture_cursor=0` 关闭光标；最高 60fps），以及 nvenc/qsv/amf 硬件编码。
- `electron/main/services/video/hwaccel.ts` 已有硬件编码探测，`ffmpeg-loader.ts` 是 FFmpeg 的定位入口。
- 剪辑导出已有 WebCodecs `VideoEncoder` + mediabunny 封装（`src/features/videoEdit/engine/videoEditExportEncoder.ts`）。

## 实施方案

1. **先实测，再定型**：用 gfxcapture + 硬件编码分别录 1080p60 和 4K60，各 2 分钟，同时打开剪辑预览，记录 CPU、GPU、显存占用和丢帧，再与 getDisplayMedia + WebCodecs 对比。结果写进执行记录，并补充到重要记录 002。
2. 定义采集后端接口（准备、开始、暂停、恢复、停止、状态、错误），实现两个后端：
   - `gfxcapture` 后端：主进程子进程，分片输出（例如每 10 秒一个分片，或可恢复的分段 mp4）。硬件编码失败时回退到软件编码并记日志。帧时间戳换算到 `monoUs`。
   - `getDisplayMedia` 后端：渲染进程采集，复用导出编码器，分片写盘。
3. 源选择：显示器、窗口、区域（区域由整屏裁剪实现）；帧率和分辨率档位；多显示器与 DPI 换算。
4. 崩溃与异常：应用崩溃或子进程被杀后，已写的分片能恢复为可用素材；磁盘空间不足时提前预警并安全停止。
5. 子进程生命周期按 B1 的经验，以 `close` 事件判定结束。所有失败可读、可重试，按 `logging.md` 打日志。

## 验收标准

- 两个后端都有单元测试，用假子进程和假流覆盖开始、暂停、停止、崩溃恢复、编码回退。
- 实测数据写入执行记录；Windows 主路径录出的原片不带光标。
- 在构建产物中用巡检场景录 30 秒，素材能被剪辑正常导入、拖动和播放。
- 相关测试与门禁通过（按 `docs/rules/testing.md` 裁剪）；新增能力过能力门禁；界面改动过界面门禁；涉及 skill 或规则文档时同步更新。

- 帧数由 `ffprobe -count_frames` 实际解码计数；“相对 60fps 缺口”按文件时长 × 60 推算，包含源帧供给、背压及时间戳等因素，不冒充驱动丢帧计数。分辨率是实际输出文件尺寸，未单独采样 Chromium 源轨道内部尺寸。
- 资源均值略去头两个样本：Electron CPU 是 `app.getAppMetrics()` 各进程的原始百分比之和；FFmpeg CPU 由进程累计 CPU 秒 / 墙钟秒计算，100% 表示一个逻辑核。两种口径分列，不直接相加。内存为 working set；GPU/编码器/显存是 `nvidia-smi` 整卡数据，含剪辑与其他桌面负载，不代表录制独占开销。
