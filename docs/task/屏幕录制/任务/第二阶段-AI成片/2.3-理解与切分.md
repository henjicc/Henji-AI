# 2.3 理解与切分

## 任务状态

- 状态：待验证
- 所属阶段：第二阶段-AI成片
- 前置任务：1.3、1.4
- 关联任务：2.4、3.2、4.1

## 任务目标

把一次录制理解成一组“步骤”：文字稿、步骤边界和标题、等待段、停顿和语气词、操作失误与回退、章节。

## 当前情况

- 已有转写与字幕：`autoSubtitles`、`speechSubtitles`、`textTranscript`、`asrCatalog.ts`。
- 已有删停顿和语气词：`silence.ts`、`analysis.ts`、`videoEditPauseMap.ts`。
- 已有场景检测：`sceneDetection.ts`。

## 实施方案

1. 文字稿：复用现有转写链路。转写模型按用户设置选择，涉及付费时遵守付费策略。
2. 步骤切分：优先用确定性信号，优先级依次是能力调用、窗口切换、点击簇、画面大幅变化；再用文字稿语义做合并或拆分。每一步生成简短的标题和说明（调用大模型时遵守付费策略，可以关掉）。
3. 等待段：画面几乎不变、没有输入、没有旁白（比如加载进度条）的片段，标记为“可加速”。停顿和语气词沿用现有分析。
4. 失误与回退：撤销操作、错误弹窗、短时间内来回点击，标记为“可能要剪掉”的候选。
5. 结果写入录制会话，可以读回，也可以人工修改；读回和修改都开放为应用能力。

## 验收标准

- 单测覆盖各类信号的切分规则和合并逻辑。
- 用一段带旁白的样例录制（仓库测试夹具）跑一遍，产出的步骤和等待段与人工标注基本一致，结果写入执行记录。
- 相关测试与门禁通过（按 `docs/rules/testing.md` 裁剪）；新增能力过能力门禁；界面改动过界面门禁；涉及 skill 或规则文档时同步更新。
- 执行记录写明改动文件、证据、计划差异和三句自查：助手能否只凭名称和说明用对？能否 AI 先做、人只确认？产物能否直接流进其他工作区？

## 执行记录

### 实施边界与选型

- 本任务仅在 `codex/rec-2.3` 实现理解层，不修改会话页、工具箱和总览；总管理者负责合并推送。没有新增第三方依赖、Node 脚本测试或 UI barrel 导出。
- 典型输入为带旁白的多段屏幕原片；按 60 分钟、120Hz 共 432000 条光标事件和 18000 个词验证规模。逐个媒体调用既有 FFmpeg 子进程，解码限 2 线程；事件分页读取后立即丢弃不参与步骤切分的光标样本。纯信号聚合不做像素计算，文字稿使用游标扫描，避免每步重扫全稿。
- 复用现有 `sceneDetection`、FFmpeg `scdet/freezedetect`、`audioEdit.detectSilence`、`transcribeAudioEdit` 和语气词置信度实现。对照 [FFmpeg 官方滤镜说明](https://www.ffmpeg.org/ffmpeg-filters.html#freezedetect)，采用已有随包 FFmpeg 的静止检测，不另引入 OpenCV/PySceneDetect、解码器或自研逐像素差分。既有 FFmpeg 许可范围不变。
- 业务真相是录制文档的 `understanding`；生成与手工校正通过同一通用属性事务写入，保存使用磁盘 revision 乐观校验。取消、页损坏、文件变化、并发修改均拒绝迟到提交；保存失败原文件不变。单独口播文档保留已识别结果，撤销理解不删除已付费识别产物。

### 逐项结论与接线契约

1. **文字稿**：默认复用同源口播文档的已有词/句时间戳，不发起识别。`transcribe=true` 才经 `transcribeAudioEdit` 和统一付费策略处理，模型由现有转写链选择；额外要求 `audio_edit:write`。找不到同源口播时创建正式口播草稿，失败/取消后仍可用其稳定引用恢复。多段声音按 `media.monoUs + sample / sampleRate` 映射，保留粒度和受保护词，不把句级识别伪装成词级精剪。
2. **步骤**：用户标记作为显式锚点；其余按能力调用、窗口切换、点击簇、画面变化、旁白依次取证。近邻信号合并，连续一句内的弱点击/画面边界合并，强能力/窗口信号保留。标题与说明取实际旁白或确定性操作描述，不伪造应用意图。
3. **等待与停顿**：等待必须同时满足 FFmpeg 实测静止、本地声音能量静音、无输入与已封闭的事件采集区间。旁白、点击、按键、滚动和调用周边避让；设备缺口与暂停不补造证据。没有声音轨且录前未启用声音时可按无旁白处理，启用了但缺失声音轨则不生成等待。ASR 词间空白不是静音证据。
4. **失误**：撤销/取消、能力返回失败和两秒内 A→B→A 往返点击只生成 `pending` 候选，不自动删除原片。独立语气词沿既有置信度规则，只有非保护的词级结果才生成候选。章节由步骤、窗口/用户标记与长段落组织。
5. **读改与撤销**：正式能力 `understand_screen_recording({sessionRef, transcribe:false, detectVisuals:true})`；返回 `screen_recording.understanding` 引用、数量、保存核实、`undoRef` 及实际新增/修改的口播引用。引用 id 等于会话文档 id；通用 `read_application_entity` 读取 `screen_recording.understanding.result`，读基线后 `change_application_entities` 整组校正标题、说明、时间、章节和候选状态；`undo_application_changes` 撤销。数据分类与既有口播正文一致为 C1，仍要求领域读写权限，采集会话的旧摘要不夹带正文。登记结果场景，Pi/MCP 同源投影。
6. **格式与 2.4**：录制文档内容版本升至 2，正式生成 `document.screen_recording/v2.json` 并登记开发期 dev-break，不做旧占位格式迁移。`transcript/steps/candidates` 的 `startUs/endUs` 均为与媒体和事件一致的、相对采集原点的单调微秒，绝不是去暂停后的 `recordingUs`，也不是序列帧。2.4 按 1.5 的实际素材放置原点换算为帧，保留缺片/暂停空档；`chapters.stepIds` 引用稳定步骤，候选 accepted/rejected 只是人的决定，剪切与变速由 2.4 正式剪辑事务实施。2.1 光标与 2.2 推近契约未改。

### 计划差异与验收边界

- 本轮不接额外的大模型语义请求。标题/说明采用实际文字稿与事件描述，语义合并采用句界与连续讲解；助手可通过通用属性校正。这样没有第二条模型或付费链，也不把启发式结果冒充大模型审片。
- 现有事件没有错误弹窗语义。本轮识别失败能力、撤销和往返点击，不声称能辨认任意第三方软件的错误弹窗；OCR/视觉补充属于后续任务。
- 文字稿、结果都落录制文档；界面列表留 2.4，不碰并行 1.5b。没有新增 UI，因此不触发界面 skill、样张或规则 E 登记。真实 FFmpeg 加正式公共入口精确测试可证明本轮结论，不依赖窗口布局，未运行 Electron bundle/tour。
- 单次公共能力沿既有 10 分钟超时上限；特别长或慢机器解码可能被取消，结果不半写，已完成的画面缓存/口播结果可以复用。真实 60 分钟磁盘分页、解码耗时和内存仍交总管理者验收。
- 同源排查覆盖事件分页与标记分页、场景检测原调用方/缓存/EOF、录制格式媒体引用、音频分段映射/设备空档、词级保护、公共属性事务及调用者撤销。没有扩展为全项目审计。

### 总管理者待验

1. 合并后用新的短录制会话（格式 v2），包含旁白、窗口切换、点击、等待、撤销、暂停/恢复；调用理解能力并读回，对照实际操作检查步骤、等待候选与时间。默认关闭转写可以先复用人工或既有转写；真实付费测试另由用户授权后进行。
2. 2.4 将步骤与候选接到会话/成片入口，再核对原片、文字稿、光标和推近使用同一源时钟，人工改结果能在序列生成前生效。
3. 真实麦克风/系统声音丢失、多轨重叠、长录制磁盘读取、1080p/4K 解码及 macOS 行为；本轮离线样本不代替这些设备结论。

### 三句自查

- 助手能否只凭名称和说明用对：能力声明明确停止后分析、转写费用和输出引用；字段说明明确微秒、整组校正与读基线，正式公共调用已验，真实 Pi/MCP 自主规划未验。
- 能否 AI 先做、人只确认：算法先出步骤、章节和待审剪辑候选，人改标题/时间或确认/拒绝，理解修改共用事务撤销，不剪原片。
- 产物能否直接流进其他工作区：结果是正式会话内容，引用原媒体与口播，2.4 可直接换算到既有剪辑序列；本任务不创建第二份媒体或私有成片格式。
