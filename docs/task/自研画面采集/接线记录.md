# 自研画面采集 · 主进程接线记录

2026-11-13。原生画面采集进程（`native/screen-capture`，协议 2）接进主进程，作为录屏的一种画面采集方式。默认关闭，开发开关 `HENJI_NATIVE_SCREEN_CAPTURE=1` 打开；不支持时照现有录法录，不向用户报错。原生侧归 Fable，本文只记主进程一侧、两边的约定和要原生配合的事。

## 做了什么

| 部分 | 位置 | 内容 |
|---|---|---|
| 原生进程客户端（共用） | `electron/main/services/native-process/` | 录音进程客户端里的进程管理抽成共用基类：按需启动、握手核对协议号（原生回 `PROTOCOL_MISMATCH` 或协议号不同都按“版本不配套”处理，不算失联）、请求超时与主进程卡顿宽限、时钟校准（三次往返取误差最小）、失联收拢、退役（关输入让它自己收尾，宽限过了才强杀）、空闲 30 秒关闭、应用退出。分帧读取与时钟对应也在这里。录音客户端改为继承它，行为不变（原有测试全过） |
| 画面采集客户端 | `capture/native-client.ts` | 协议 2 的应答与事件解析；事件按会话号交给订阅者；不认识的事件只记日志（以后加事件不断开正在录的进程）；可执行文件路径与随包位置；应用退出时先停录制（文件收尾）再关进程 |
| 采集后端 | `capture/native.ts` | `prepare`/`start`/`pause`/`resume`/`stop` 映射到协议指令；“取消”在已经开始后按 `stop` 收尾（录制宿主的取消只是不导入，不能让原生删文件），只在还没开始时发 `cancel` |
| 后端选择与回退 | `capture/service.ts` | 开关打开且满足条件（Windows、整块显示器、无区域、不录光标、编码器为自动或 NVIDIA、录制尺寸等于显示器物理尺寸）才试原生；`prepare` 抛任何错（不支持、进程起不来、版本不配套）都记日志 `recording.capture.native.fallback` 后改用 FFmpeg gfxcapture |
| 时刻表 | `capture/native-timing.ts` | 读 `.frames`（舍去被杀后半条的尾巴）；分段、上屏偏移、暂停区间、合并分组都从这里推 |
| 会话收尾 | `session-document.ts` | 画面只有一个文件且旁边有时刻表时，暂停区间按时刻表定，不再按“分片第一帧”猜 |
| 导入剪辑 | `combine.ts`、`recordingVideoImport.ts` | 连续文件按时刻表分段成一组（各片同一个文件），画面直接用原件、不重拼；声音照这组拼。界面在“有暂停”时也去问主进程 |
| 剪辑代理 | `capture/native.ts`、`services/video/proxy-runtime.ts` | `prepare` 带 `proxy`（高度取剪辑 auto 档），停止后核对代理与原片时长一致（差不到 1.5 帧），用剪辑代理服务同一套缓存与校验登记（搬进缓存、按原片身份登记）；之后剪辑查 auto 档直接命中，不再转码。代理短了或登记失败只记日志 |
| 活动时间线 | `recordingReflection.ts` | 会话读回的 `details.activity`：`{path, exists}`，没有改会话文档格式 |
| 构建与打包 | `scripts/lib/electronBundlePlan.cjs`、`package.json`、`electron-builder.yml`、`scripts/electron-builder-after-pack.cjs`、`scripts/lib/thirdPartyLicenses.cjs`、`.github/workflows/build.yml` | 轻量构建与 `electron:build` 都构建它；Windows 随包到 `resources/video-decoder/`，与解码服务共用同一份 FFmpeg DLL（DLL 名单两边一致，已核对）；装包前核对它在随包清单里；许可清单收它的 Rust 依赖；CI 在解码服务那个作业里跑它的 `cargo test` 与 release 构建。macOS 不随包 |

## 与现有流程的差异与处理

| 差异 | 处理 |
|---|---|
| 一次录制一个画面文件，暂停不产生新文件，文件里没有暂停的画面 | 会话清单仍是一个分片（文件名 `screen-000000.mp4`，原生的 `name` 就用它），会话文档里一个画面原件；时长是文件时间轴长度（`frames / fps`）。持久格式没改：分辨“连续文件”的依据是它旁边的时刻表 |
| 暂停对齐 | 原来靠“恢复后分片的第一帧”估暂停结束；现在三处用同一组数：事件时钟恢复点 = 按下暂停的时刻 + 跳过的格数 × 格时长（`resumed.atUs − paused.atUs`）；会话暂停区间与合并各段都按时刻表的格号推。真实进程上实测事件时钟扣掉的 1 016 667 微秒与时刻表推出的暂停长度相差 1 微秒 |
| 第一帧时刻 | 开始时事件时钟零点按网格起点（`started.originUs` 换算到主进程时钟）往前留 1 秒；停止后把分片起点改到“第 0 帧画面真正上屏的时刻” = 网格起点 + 新画面上屏时刻相对格时刻的中位偏移（同一时钟里的差，与校准无关） |
| 时钟 | 原生时刻是 QPC 微秒，经客户端校准（`correlateNativeClock`）换算到主进程 `hrtime`；会话恢复与合并只用格号差，不需要校准值 |
| 显示器坐标 | 原生按物理像素找显示器：用 Electron 显示器中心经 `dipToScreenPoint` 换算（副屏在 DIP 1280 起、缩放 150% 时中心是物理 (2880, 540)，有测试） |
| 显示器断开（协议 2 起原生会等它回来、同一文件续录） | 收到 `sourceLost`（或 `paused` 带 `sourceLost`）就按“来源没了”正常停止收尾，与主干 82bc3490f 的做法一致。原因：续录那段空档在事件时钟与声音里并没有暂停，若当暂停算会错开 |
| 分辨率变了（`sourceChanged`） | 只记日志 `recording.capture.native.source_changed`；不另开一段 |
| 显卡设备丢失、编码或写盘失败（`interrupted`） | 收尾封口已录部分（按结果里的帧数），按采集失败结束：会话记为“已中断”、可以导入。没有做“重新 prepare 开新段续录” |
| 进程崩溃 | 后端按采集失败结束，分片不封口，会话收尾时按文件里真实写到的画面补齐（分片 MP4 被杀后可读）；下次录制重新启动进程 |
| 编码统计 | 丢帧 = `droppedFrames + captureDropped`，重复帧 = `repeatedFrames`，编码器名如 `h264_nvenc`；进长录事实与收尾汇总日志 |

## 日志里看什么

- 每次录制用的哪条路：`recording.capture.prepare.completed` 与 `recording.capture.summary` 的 `capturer`（`native` / `ffmpeg` / `chromium`）
- 不走原生的原因：`recording.capture.native.skipped`（条件不满足）、`recording.capture.native.fallback`（原生 `prepare` 失败，带 `code`）
- 原生进程：`screen_capture.process.start` / `.completed` / `.version_mismatch` / `.failed`
- 开始：`recording.capture.start`（`capturer: native`、`encoder`、`firstFrameLagUs`）；收尾：`recording.capture.native.finished`；代理：`recording.capture.native.proxy_adopted` / `proxy_short` / `proxy_failed`
- 暂停：`recording.pauses.timing`（按时刻表定下的暂停数）

## 真实窗口验证步骤（这次没做）

1. 构建：`npm run electron:bundle`（会构建原生画面采集进程），或单独 `node scripts/build-screen-capture.cjs`
2. 启动：`HENJI_NATIVE_SCREEN_CAPTURE=1 npm run electron:dev -- --dev-skip-onboarding`（用 Bash 后台启动）
3. 选副屏整屏录制，录制尺寸选与显示器原尺寸一致（4K 屏选 3840×2160），倒计时后录 20 秒，中间暂停 5 秒再继续，停止
4. 日志：`recording.capture.prepare.completed` 的 `capturer` 应为 `native`；有 `recording.pauses.timing`、`recording.capture.native.proxy_adopted`
5. 会话目录（`uploads/screen-recordings/<会话号>/`）里有 `screen-000000.mp4 / .frames / .activity.jsonl / .capture.json`，没有 `screen-000001.mp4`；代理已搬进代理缓存
6. 助手读 `screen_recording.session` 的 `details`：`media` 一个画面、`pauses` 一段、`activity.exists` 为 true、`capture.video.encoder` 为 `h264_nvenc`
7. 进剪辑：一个画面片段，时长 = 录制时长 − 暂停；拖过暂停前后看光标与画面是否对齐（点按处的点击圈落在按钮上）；播放时用的是代理
8. 回退：录一个区域或开“录光标”，日志应有 `recording.capture.native.skipped`；把可执行文件改名后再录，应有 `recording.capture.native.fallback` 且照常录完

## 没做的

- 预览（`startPreview` 共享纹理接到“录屏边录边剪”的录制样子）：主进程与界面都没接。接法：主进程在 `prepare` 之后发 `startPreview`（`clientPid` 用渲染进程的 `webContents.getOSProcessId()`），把应答里的 `slots` 句柄与 `preview` 事件经现有的 `texture-bridge` 通道交给界面导入，界面在指针停在结尾时与录制中显示；开关失败只停预览
- 设备丢失后重新 `prepare` 开新段续录：现在按中断保存。做的话要先让连续文件与多个分片混合时的合并、暂停推算能处理（现在只认“一个画面文件带时刻表”）
- 显示器断开后续录、分辨率变化另开一段：见上表，第一版都按停止或只记日志
- 其他按会话时钟读画面的地方（快速导出、成片、隐私遮挡、重演等）还按“画面文件 = 会话时间减起点”换算；带暂停的原生录制在这些地方会错开。导入剪辑（合并路径）是对的。要改的话把“文件位置”统一成一个按时刻表或暂停换算的入口
- 活动时间线的落盘格式登记（`.frames`、`.capture.json`、`.activity.jsonl` 按 persistence.md 登记与黄金样本）
- 固定延迟标定（真实事件链路下点按到上屏的延迟）

## 需要原生配合或确认的

1. 时刻表里暂停空档与来源丢失空档长得一样。现在主进程靠“来源丢失就停止”避免混淆；以后要支持断开后续录，主进程需要分辨两种空档（读活动时间线的 `pause` / `sourceLost` 也行，或者时刻表标志位里给“继续后的第一帧”再区分原因），请定一个约定
2. `stop` 的结果里没有代理的帧数：主进程现在用 ffprobe 比两份文件的时长来判断代理是否中途停了。若结果里能带上代理的实际帧数（或 `proxyComplete`），就不用多跑两次探测
3. `paused` 事件在 `pause` 应答之后才发、且“同一格里”不发：主进程在 `resume` 后最多等 1.5 秒的 `resumed`，等不到就当没暂停。若 `resume` 的应答能直接带上 `{cell, atUs}`（或明确没暂停），这个等待可以去掉
