## 实测数字

机器：Windows 10 19045，RTX 4090（驱动 610.47），副屏 3840×2160 @ 60 Hz，`h264_nvenc`，恒定质量。命令见 README。

| 项目 | 结果 |
|---|---|
| 5 分钟 4K60（副屏放 ffplay 测试图） | 18001 帧；**丢弃 0**、采集队列丢 0；新帧 17958、重复 43。43 次重复全部对应“来源相邻两帧隔了两个刷新周期”（ffplay 不按垂直同步出帧，偶尔错过一次刷新；系统没有新画面可给） |

## 实测中确认的事实（设计依据）

1. **`SystemRelativeTime` 是这一帧上屏的时刻，不是合成完成的时刻。** 帧到达进程时，它带的时刻平均还在 10–19 毫秒之后。时刻表里记的就是它。
2. **Windows 10 19045 上黄色边框只画在屏幕上，不进采集画面**（截图核对）。准备时出现、结束时消失。
3. **系统只在重新合成时给帧**：屏幕完全静止时不出帧（网格补重复帧）；但只要有窗口不停重画（哪怕内容没变）就一直有新帧。所以“画面在不在变”不能只看有没有新帧——活动时间线里另记了每秒编码后的字节数（没变的帧只有几百字节）。
4. Windows 10 上没有“最小更新间隔”，拿到的是合成器的全部帧；60 Hz 屏录 60 帧正好一对一。

## 自己定的取舍（方向文档没覆盖的）

| 取舍 | 定法与理由 |
|---|---|
| 采集层自己写，不依赖 `windows-capture` | 帧池大小、回调线程、帧的归还时机、设备移除正是要自己掌握的地方；自己写约 170 行 |
| 色彩转换用自己的着色器，不用系统视频处理器 | 视频处理器的输出受显卡驱动“视频”设置影响；着色器的矩阵与范围写死，有数值测试 |
| 网格选帧留一张缓冲（先出旧的） | 来源与网格同频、相位贴着判定线时不来回丢帧与重复；代价是这一状态下画面在文件时间轴上晚一格（时刻表照实记录） |
| 起点 | 开始那一刻手里有画面：起点 = 开始时刻；否则 = 第一帧的系统时刻 |
| 编码跟不上时 | 落后超过半秒才丢格；丢的格子占帧序号（时间轴不缩短、音画不漂），时刻表里标出 |
| 状态只在会话线程 | 指令都交给会话线程判断并应答（独立审查指出两个线程各存一份状态时，中断收尾期间的停止会丢应答） |
| 编码时不持设备锁 | 与 FFmpeg 命令行里采集滤镜和 NVENC 各在各线程的用法相同；实测 5 分钟无异常 |
| 进程优先级“高于标准”、显卡线程优先级提高 | 本进程几乎不占处理器，但每帧有时限 |
| 自测脚本放在 `native/screen-capture/selftest/` | 它同时是主进程用法的可运行示例；不是 `scripts/` 下的仓库脚本 |

## 已知问题与没做的

- **只支持 NVIDIA、整块显示器、Windows。** 其他情况 `prepare` 报错，主进程要回到现有录法。
- **没测过的意外情况**：显示器换分辨率（代码里按原输出尺寸等比缩放、留黑边，没实测）、拔显示器（发 `SOURCE_LOST` 并收尾，没实测）、显卡设备重置、锁屏、休眠、远程桌面、高刷新率显示器（网格逻辑有单元测试，没实机）、混合显卡笔记本、HDR 显示器。
- **编码是同步的**：每帧等编码器出包（4090 上 7.7 毫秒）。弱一些的 NVIDIA 显卡在 4K60 下余量不大，跟不上时会按上面的规则丢格。可以改成让编码器攒一两帧再取包（管线化），但暂停时要能排空，需单独验证。
- **内存约 500 MB**：其中大部分是显卡驱动与编码会话在进程内的占用，稳定不增长；没有再细分。
- **固定延迟没有标定**：闪烁色块实测“画完到上屏时刻”最小 27 毫秒（GDI 窗口）。鼠标点击等事件与画面对齐时要减多少，要用真实的事件采集链路再量一次。
- **落盘格式还没登记**：`.frames`、`.capture.json`、`.activity.jsonl` 接进应用时要按 `docs/rules/persistence.md` 登记并补黄金样本。
- **没做**：1080P 代理、把实时画面共享给界面、点击与输入集中时段、光标形状变化、窗口与区域采集、AMD / Intel 编码、正常停止时转成普通 MP4（现在始终是分片 MP4）、断电保护（没有逐分片 fsync）。
- 活动时间线里的窗口标题是明文，只在本机；接线时注意它会随工程走。

## 第二阶段（2026-11-13）

测量时的外部负载：主仓库同时在副屏做真实窗口验证（整机处理器平均 20–26%、峰值 52–60%，显卡峰值 40%）。下面的数字都是在这种负载下量的，屏幕内容大多静止（主文件码率很低），所以编码耗时可比、码率不可比。

### 一、设备移除与来源变化

对照（调研文档第 2、5.5 节）：OBS 采集失败后每 3 秒重新取显示器句柄再试；WebRTC 把错误分成临时与永久；Cap 把关闭分成设备被移除、目标消失、偶发三类，并注明设备被移除后系统的采集组件会在别的线程上直接终止进程，所以不能再把那个设备交回给采集接口；采显示器时 Cap 保持原输出尺寸、后面缩放。

我们的做法：

| 情况 | 行为 | 验证 |
|---|---|---|
| 显示器断开再接回 | 不结束录制。断开那一刻起的格子不进文件（已录内容立刻落成分片），时刻表里是一段空档；每秒按设备名找一次，找到就新建采集项接着采，续录的第一帧是关键帧，同一个文件 | 注入“来源丢失”（真的停掉系统采集、再按设备名重新建立）：空档 61 格（约一秒），事件顺序 `sourceLost → paused(sourceLost) → sourceRestored → resumed`，文件与时刻表一致。**真的拔线没测**（要动真实显示器） |
| 显示器换分辨率或缩放 | 帧池按新尺寸重建，文件尺寸不变，画面等比缩放、四周留黑；发 `sourceChanged`，要不要另开一段由主进程定 | 留黑边的转换有真实显卡上的数值测试（64×32 的来源进 64×64 的输出）。**真的改分辨率没测**（副屏在被别人用）；帧池重建那几行只经过代码审读 |
| 显卡设备丢失或驱动重置 | 采集回调、会话线程每秒的检查、编码出错三处任一发现设备没了，都收尾并发 `interrupted`（`DEVICE_REMOVED`）；文件结尾照样写好（封装不依赖显卡）；设备没了之后不再重建帧池。不在同一文件续录——编码会话绑在设备上，换了设备就是另一路流，由主进程重新 `prepare` 开新段 | 注入“采集报设备被移除”：`interrupted` 事件、随后的 `stop` 被拒绝为 `SESSION_MISSING`、文件 895 帧等于事件里的已编码帧数、时刻表 1030 条。**真的设备丢失没测**：`dxcap -forcetdr` 会重置整块显卡，机器上别人正在用；D3D11 没有只移除单个设备的办法。所以“设备真没了时编码器与系统采集组件会不会让进程直接崩掉”仍未知，底线是崩了文件也读得到最后一个分片（强杀场景已验证） |

### 二、编码管线化

读代码与实测后的判断：NVENC 一个会话一次只编一帧，4K H.264 约 7.7 毫秒，上限约 130 帧每秒；让编码器攒帧（异步模式）并不能提高这个上限，只是不让调用方等。所以没有用编码器的异步模式，而是把编码从会话线程里拆出来：

- 新增编码线程，独占写文件接口；会话线程（网格）只往有界的编码队列里放，从不等编码。
- 丢帧规则改成一条：**编码队列满了，这一格就丢**（占帧序号、时刻表里标出、计 `droppedFrames`）。短停顿被队列吸收后追上；持续过慢时队列保持满，多出来的格子均匀地丢，而不是攒半秒再一次丢一批。
- 采集回调仍然只做转换与入队。

| 验证 | 结果 |
|---|---|
| 4090 上不比原来差 | 每帧编码 7.2–8.2 毫秒（原来 7.7），队列长度 0–1，采集回调最大 1.9–2.6 毫秒 |
| 注入一次 150 毫秒的编码停顿（复现那次“系统停顿 139 毫秒丢 9 张”） | 丢格 0、采集队列丢 0 |
| 注入每帧多 25 毫秒（一秒只编得了约 30 帧），持续 5 秒 | 丢格 112（约每两格丢一格），**采集队列丢 0**，采集回调不受影响；取消延迟后编码队列回到 0、不再丢格 |
| 过载时的资源 | 两个队列装满时内存到 854 MB、显存到 730 MB（平时 500 / 380），之后不降回去 |

### 三、1080P 代理与预览

**代理**：每张来源帧在显卡上多缩一份 1920×1080，第二个 NVENC 会话编码，写 `<name>.proxy.mp4`。

| 验证 | 结果 |
|---|---|
| 40 秒 4K60 含一次暂停 | 主文件与代理都是 2401 帧、时长相同；代理里继续后的第一帧也是关键帧 |
| 性能影响 | 每帧编码（两路合计）9.7 毫秒，比只录主画面多约 2 毫秒；采集回调最大 2.6 毫秒；内存 +75 MB、显存 +50 MB；丢格 0 |
| NVENC 并发会话 | 本机（驱动 610.47）两个会话同时开没有问题。消费级显卡的并发会话数有上限（随驱动版本不同），所以代理的编码器开不出来时只是不录代理，主文件照常 |

**预览**：采集回调里把画面缩到不超过 1280 宽，画进 3 张带共享句柄的 BGRA 纹理，句柄复制到界面所在的进程——与视频解码服务给界面送帧的做法相同（`shared_texture.rs` 的句柄复制与回收、`texture-bridge.ts` 的 `importSharedTexture`），主进程可以直接沿用，不用新造通道。没有用键控互斥体（3 张轮着写、写完才通知）。

| 验证 | 结果 |
|---|---|
| 另一个进程按句柄打开并读回（`selftest.cjs preview`） | 3 张都能打开，读回 1280×720 的非空画面；两秒半里收到约 70 条 `preview` 事件（15 帧每秒） |
| 对主录制的影响 | 开预览期间丢格 0、采集队列丢 0；采集回调平均 0.6–0.8 毫秒（不开时约 0.5） |
| 没验证的 | **Electron 渲染层真的显示出来**（接线归另一位；我这边只证明了跨进程句柄可用）；屏幕静止，没能看到画面内容随时间变化 |

预览做出来时发现并修掉一个死锁（十次里约五次卡在 `stopPreview`）：在占着“预览”这把锁的时候释放显卡对象，而采集回调此刻也要这把锁。改成先从锁里取出来、放开锁再释放；同样的写法在停采集的两处一并改了。修后连续十次通过。

### 第二阶段之后的已知问题

- 真实的拔显示器、改分辨率、设备丢失都没有实机验证（见上表），需要用户在场时各做一次。
- 过载后帧队列占的显存不降回去；要省可以在队列空了之后收缩帧池（没做）。
- 代理中途出错会停掉代理，此时代理比主文件短；主进程读代理前应核对帧数。
- 预览没有背压：对方不读也照常写（3 张轮转，只是白画）。

## 第二轮独立审查（2026-11-13）的处理

审查从严读了全部源码，结论“接进应用前必须修三条”，都已修并有自测：

| 条目 | 处理 |
|---|---|
| 预览开着时再 `startPreview` 会死锁 | 旧的预览先从锁里换出来、出了锁再放下。自测：连开四次，之后照常读回 |
| 缺错误分级，一次暂时性错误就结束整段录制 | 分三档（对照 WebRTC 的临时 / 永久、Cap 的偶发自动重启、OBS 的定时重试）：单帧取帧或转换失败只丢这一张并计 `captureFailed`；连着失败满一秒当成来源丢失，走现成的重新接上；帧池重建失败但设备还在同样重新接上；只有设备被移除直接收尾。自测：注入 5 张失败不中断，注入 90 张后重新接上、同一文件续录 |
| 时刻表落盘比视频分片晚 | 每条记录写完即落盘，并且先落盘再把帧交给编码（先看编码队列有没有空位，再定这一格丢不丢）；活动时间线每行即落盘。强杀自测的判据收紧为“时刻表条数不少于可读帧数”：660 帧可读、720 条记录 |

顺手修的：`is_ended` 改用结束标志；发布构建设 `panic = "abort"`（任何线程出意外就整个退出，走主进程“采集进程意外退出”的路，不留半死进程；没有用 catch_unwind，因为出了意外的线程手里的状态已不可信）；`inject` 要环境变量 `HENJI_SCREEN_CAPTURE_INJECT=1` 才接受；收尾先主文件后代理；换分辨率的那一帧丢掉；README 里 encodedFrames、被杀后的长度、恒定帧率三处说法改正。

## 自测结果补充

|---|---|

## 独立审查

一轮（全新上下文、只读）。重要问题两条：

1. 会话因故障中断时，在途或随后的停止 / 取消收不到应答——根因是状态在主循环与会话线程各存一份。已改成状态只在会话线程、每条指令由它恰好应答一次，结束时在同一把锁里回绝残留指令。
2. 编码时不持设备锁是否安全（审查标为拿不准）——保持不加锁，依据见上表“编码时不持设备锁”，并写进了代码注释。

小问题里已修：未来的 `atUs`、准备失败留下空文件、落盘帧数按帧序号报、退出等待上限不生效、会话结束后收件箱仍占着显存、丢弃的格子计入活动时间线、磁盘已满的判断里有平台错误码、发送失败时包泄漏、写盘线程中途退出被当成成功。没修、记为已知：分配失败不判空（内存耗尽时进程本来也无法继续）；落盘格式登记留到接线时做。修复后的增量没有再做第二轮独立审查，靠单元测试与上面五个场景验证。
