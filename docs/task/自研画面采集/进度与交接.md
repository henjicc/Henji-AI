## 实测中确认的事实（设计依据）

1. **`SystemRelativeTime` 是这一帧上屏的时刻，不是合成完成的时刻。** 帧到达进程时，它带的时刻平均还在 10–19 毫秒之后。时刻表里记的就是它。
2. **Windows 10 19045 上黄色边框只画在屏幕上，不进采集画面**（截图核对）。准备时出现、结束时消失。
3. **系统只在重新合成时给帧**：屏幕完全静止时不出帧（网格补重复帧）；但只要有窗口不停重画（哪怕内容没变）就一直有新帧。所以“画面在不在变”不能只看有没有新帧——活动时间线里另记了每秒编码后的字节数（没变的帧只有几百字节）。
4. Windows 10 上没有“最小更新间隔”，拿到的是合成器的全部帧；60 Hz 屏录 60 帧正好一对一。

## 自己定的取舍（方向文档没覆盖的）

| 取舍 | 定法与理由 |
|---|---|
| 采集层自己写，不依赖 `windows-capture` | 帧池大小、回调线程、帧的归还时机、设备移除正是要自己掌握的地方；自己写约 170 行 |
| 色彩转换用自己的着色器，不用系统视频处理器 | 视频处理器的输出受显卡驱动“视频”设置影响；着色器的矩阵与范围写死，有数值测试 |
| 网格选帧留一张缓冲（先出旧的） | 来源与网格同频、相位贴着判定线时不来回丢帧与重复；代价是这一状态下画面在文件时间轴上晚一格（时刻表照实记录） |
| 起点 | 开始那一刻手里有画面：起点 = 开始时刻；否则 = 第一帧的系统时刻 |
| 编码跟不上时 | 落后超过半秒才丢格；丢的格子占帧序号（时间轴不缩短、音画不漂），时刻表里标出 |
| 状态只在会话线程 | 指令都交给会话线程判断并应答（独立审查指出两个线程各存一份状态时，中断收尾期间的停止会丢应答） |
| 编码时不持设备锁 | 与 FFmpeg 命令行里采集滤镜和 NVENC 各在各线程的用法相同；实测 5 分钟无异常 |
| 进程优先级“高于标准”、显卡线程优先级提高 | 本进程几乎不占处理器，但每帧有时限 |
| 自测脚本放在 `native/screen-capture/selftest/` | 它同时是主进程用法的可运行示例；不是 `scripts/` 下的仓库脚本 |

## 已知问题与没做的

- **只支持 NVIDIA、整块显示器、Windows。** 其他情况 `prepare` 报错，主进程要回到现有录法。
- **没测过的意外情况**：显示器换分辨率（代码里按原输出尺寸等比缩放、留黑边，没实测）、拔显示器（发 `SOURCE_LOST` 并收尾，没实测）、显卡设备重置、锁屏、休眠、远程桌面、高刷新率显示器（网格逻辑有单元测试，没实机）、混合显卡笔记本、HDR 显示器。
- **编码是同步的**：每帧等编码器出包（4090 上 7.7 毫秒）。弱一些的 NVIDIA 显卡在 4K60 下余量不大，跟不上时会按上面的规则丢格。可以改成让编码器攒一两帧再取包（管线化），但暂停时要能排空，需单独验证。
- **内存约 500 MB**：其中大部分是显卡驱动与编码会话在进程内的占用，稳定不增长；没有再细分。
- ~~固定延迟没有标定~~：已标定并接上（一个刷新周期），见文末“暂停时刻与光标对齐”。
- **落盘格式还没登记**：`.frames`、`.capture.json`、`.activity.jsonl` 接进应用时要按 `docs/rules/persistence.md` 登记并补黄金样本。
- **没做**：1080P 代理、把实时画面共享给界面、点击与输入集中时段、光标形状变化、窗口与区域采集、AMD / Intel 编码、正常停止时转成普通 MP4（现在始终是分片 MP4）、断电保护（没有逐分片 fsync）。
- 活动时间线里的窗口标题是明文，只在本机；接线时注意它会随工程走。

## 第二阶段（2026-11-13）

测量时的外部负载：主仓库同时在副屏做真实窗口验证（整机处理器平均 20–26%、峰值 52–60%，显卡峰值 40%）。下面的数字都是在这种负载下量的，屏幕内容大多静止（主文件码率很低），所以编码耗时可比、码率不可比。

### 一、设备移除与来源变化

对照（调研文档第 2、5.5 节）：OBS 采集失败后每 3 秒重新取显示器句柄再试；WebRTC 把错误分成临时与永久；Cap 把关闭分成设备被移除、目标消失、偶发三类，并注明设备被移除后系统的采集组件会在别的线程上直接终止进程，所以不能再把那个设备交回给采集接口；采显示器时 Cap 保持原输出尺寸、后面缩放。

我们的做法：

| 情况 | 行为 | 验证 |
|---|---|---|
| 显示器断开再接回 | 不结束录制。断开那一刻起的格子不进文件（已录内容立刻落成分片），时刻表里是一段空档；每秒按设备名找一次，找到就新建采集项接着采，续录的第一帧是关键帧，同一个文件 | 注入“来源丢失”（真的停掉系统采集、再按设备名重新建立）：空档 61 格（约一秒），事件顺序 `sourceLost → paused(sourceLost) → sourceRestored → resumed`，文件与时刻表一致。**真的拔线没测**（要动真实显示器） |
| 显示器换分辨率或缩放 | 帧池按新尺寸重建，文件尺寸不变，画面等比缩放、四周留黑；发 `sourceChanged`，要不要另开一段由主进程定 | 留黑边的转换有真实显卡上的数值测试（64×32 的来源进 64×64 的输出）。**真的改分辨率没测**（副屏在被别人用）；帧池重建那几行只经过代码审读 |
| 显卡设备丢失或驱动重置 | 采集回调、会话线程每秒的检查、编码出错三处任一发现设备没了，都收尾并发 `interrupted`（`DEVICE_REMOVED`）；文件结尾照样写好（封装不依赖显卡）；设备没了之后不再重建帧池。不在同一文件续录——编码会话绑在设备上，换了设备就是另一路流，由主进程重新 `prepare` 开新段 | 注入“采集报设备被移除”：`interrupted` 事件、随后的 `stop` 被拒绝为 `SESSION_MISSING`、文件 895 帧等于事件里的已编码帧数、时刻表 1030 条。**真的设备丢失没测**：`dxcap -forcetdr` 会重置整块显卡，机器上别人正在用；D3D11 没有只移除单个设备的办法。所以“设备真没了时编码器与系统采集组件会不会让进程直接崩掉”仍未知，底线是崩了文件也读得到最后一个分片（强杀场景已验证） |

### 二、编码管线化

读代码与实测后的判断：NVENC 一个会话一次只编一帧，4K H.264 约 7.7 毫秒，上限约 130 帧每秒；让编码器攒帧（异步模式）并不能提高这个上限，只是不让调用方等。所以没有用编码器的异步模式，而是把编码从会话线程里拆出来：

- 新增编码线程，独占写文件接口；会话线程（网格）只往有界的编码队列里放，从不等编码。
- 丢帧规则改成一条：**编码队列满了，这一格就丢**（占帧序号、时刻表里标出、计 `droppedFrames`）。短停顿被队列吸收后追上；持续过慢时队列保持满，多出来的格子均匀地丢，而不是攒半秒再一次丢一批。
- 采集回调仍然只做转换与入队。

| 验证 | 结果 |
|---|---|
| 4090 上不比原来差 | 每帧编码 7.2–8.2 毫秒（原来 7.7），队列长度 0–1，采集回调最大 1.9–2.6 毫秒 |
| 注入一次 150 毫秒的编码停顿（复现那次“系统停顿 139 毫秒丢 9 张”） | 丢格 0、采集队列丢 0 |
| 注入每帧多 25 毫秒（一秒只编得了约 30 帧），持续 5 秒 | 丢格 112（约每两格丢一格），**采集队列丢 0**，采集回调不受影响；取消延迟后编码队列回到 0、不再丢格 |
| 过载时的资源 | 两个队列装满时内存到 854 MB、显存到 730 MB（平时 500 / 380），之后不降回去 |

### 三、1080P 代理与预览

**代理**：每张来源帧在显卡上多缩一份 1920×1080，第二个 NVENC 会话编码，写 `<name>.proxy.mp4`。

| 验证 | 结果 |
|---|---|
| 40 秒 4K60 含一次暂停 | 主文件与代理都是 2401 帧、时长相同；代理里继续后的第一帧也是关键帧 |
| 性能影响 | 每帧编码（两路合计）9.7 毫秒，比只录主画面多约 2 毫秒；采集回调最大 2.6 毫秒；内存 +75 MB、显存 +50 MB；丢格 0 |
| NVENC 并发会话 | 本机（驱动 610.47）两个会话同时开没有问题。消费级显卡的并发会话数有上限（随驱动版本不同），所以代理的编码器开不出来时只是不录代理，主文件照常 |

**预览**：采集回调里把画面缩到不超过 1280 宽，画进 3 张带共享句柄的 BGRA 纹理，句柄复制到界面所在的进程——与视频解码服务给界面送帧的做法相同（`shared_texture.rs` 的句柄复制与回收、`texture-bridge.ts` 的 `importSharedTexture`），主进程可以直接沿用，不用新造通道。没有用键控互斥体（3 张轮着写、写完才通知）。

| 验证 | 结果 |
|---|---|
| 另一个进程按句柄打开并读回（`selftest.cjs preview`） | 3 张都能打开，读回 1280×720 的非空画面；两秒半里收到约 70 条 `preview` 事件（15 帧每秒） |
| 对主录制的影响 | 开预览期间丢格 0、采集队列丢 0；采集回调平均 0.6–0.8 毫秒（不开时约 0.5） |
| 没验证的 | **Electron 渲染层真的显示出来**（接线归另一位；我这边只证明了跨进程句柄可用）；屏幕静止，没能看到画面内容随时间变化 |

## 暂停时刻与光标对齐（2026-11-13，走查第七轮之后）

第七轮查出两处：暂停与继续在会话时钟上记的时刻比画面真正停下、续上早 0.37–0.47 秒；光标比画面早约 2 帧（中位 33 ms，旧录法 15.5 ms）。两处都已修，下面是对照、根因、做法与实测。

### 对照成熟做法

| 问题 | 它们怎么做 | 依据 |
|---|---|---|
| 暂停切在哪一刻 | OBS 把暂停起点定在“最后一帧视频时刻之后的下一个帧格”，而且往后取：`closest_v_ts = last_video_ts + ((now − last_video_ts + 2 × 帧间隔) / 帧间隔) × 帧间隔`，即按下之后一到两帧的那个帧时刻。视频帧时刻不早于它的都不进文件，直到等于继续的那个帧时刻；声音按同一对时刻裁（`pause_audio` / `unpause_audio`）。各路用的是同一对数，来源是视频帧的时刻，不是按键的时刻 | `libobs/obs-output.c` 的 `get_closest_v_ts`、`obs_output_pause`；`libobs/obs-encoder.c` 的 `video_pause_check`、`audio_pause_check` |
| 帧的时刻取什么 | OBS 的 WGC 采集不读 `SystemRelativeTime`（它按自己的渲染节拍出帧）；它在采集会话上关掉系统光标（`IsCursorCaptureEnabled(false)`），自己画光标。FFmpeg gfxcapture、Cap、windows-capture 都直接用 `SystemRelativeTime` | `libobs-winrt/winrt-capture.cpp`（全文没有 `SystemRelativeTime`）；调研文档第 2 节 |
| `SystemRelativeTime` 是什么时刻 | 微软文档写的是“合成器渲染这一帧的 QPC 时刻”。实测不是：帧到达进程时这个时刻还在 4–16 毫秒之后，它是这一帧上屏的时刻 | 微软文档 `Direct3D11CaptureFrame.SystemRelativeTime`；本机实测见下 |
| 事件与画面之间的固定延迟 | 没有查到哪个开源项目给出过这个常数（OBS 自己画光标、Cap 没有逐帧对齐事件）。按调研里定的实验自己量 | 未查到：翻过 OBS、Cap、windows-capture 的采集代码与调研文档第 2 节 |

我们的做法与差别：暂停与继续同 OBS，取“按下之后第一个帧格”的时刻，各路都用它；差别是 OBS 往后取到两帧，我们取到一帧以内。帧时刻仍用 `SystemRelativeTime`，但对到事件时减去一个刷新周期（下面的标定）。

### 一、暂停与继续的时刻

根因（两条，都在主进程，不在采集进程）：

1. 按下暂停后，主进程先把暂停写进会话文档（存一次文档约 0.4 秒），之后才向采集进程发 `pause`。采集进程只能从收到那一刻起停（已经出的格子收不回来），所以画面多录了 0.4 秒；而事件时钟与事件里的暂停、继续记的是“按下的时刻”与“按下的时刻 + 跳过的格数”，长度对、位置早 0.4 秒。
2. 按下继续后，事件输入要等声音与界面那几路都续上才重新挂上（麦克风与系统声重新起来要几百毫秒），而画面在几十毫秒内就续上了。所以继续后的头 0.4 秒画面里没有新的光标事件，光标停在暂停前的位置。

做法（修在源头，读取方没有动）：

- 采集后端新增一对入口 `hold` / `unhold`：按下暂停、继续时**最先**调，立刻向采集进程发指令，等它报出生效的那一格（`paused` / `resumed` 事件的 `atUs`），把那一格的时刻返回。事件时钟就停在、续在这两个时刻；会话文档当场记的也是它们；收尾时按时刻表推出的暂停与它们是同一组数。
- 事件输入在按下暂停时就停；按下继续后各路同时开始续，画面一续上输入就接着采，不等声音。
- 要画面内容正好切在按下的那一刻，采集进程该切的帧时刻要晚一个上屏提前量（见第二节），所以 `pause` / `resume` 的时刻可以略晚于现在（采集进程接受最多 100 毫秒）。结果是：画面内容截到“按下之后的第一格”，偏差在 0 到 1 帧之间。
- FFmpeg 录法没有这对入口，走的仍是原来的路（按下的时刻、等各路续上后从画面第一帧接着走），行为不变。

### 二、光标对齐

时刻表里每帧记的是 `SystemRelativeTime`，即这一帧**上屏**的时刻（帧到达进程时它还在未来 4–16 毫秒）。合成器是提前一个刷新周期把光标位置与各窗口内容取好的，所以系统时刻为 S 的帧里，是 S 减一个刷新周期那一刻的光标与内容。鼠标键盘事件记的是发生的时刻，拿上屏时刻去对就会早一帧多。

标定（`node native/screen-capture/selftest/selftest.cjs flash --cursor`，副屏 4K 60 Hz，各 60 次）：让系统把光标合成进画面，程序把鼠标移到色块另一个角并记下移完的时刻，找第一张带上新光标位置的帧。

| 条件 | 鼠标移完 → 那一帧的系统时刻 | 色块画完 → 那一帧的系统时刻 | 帧到达进程 − 系统时刻 |
|---|---|---|---|
| 空闲 | 17.1–33.2 毫秒，散布 0.97 帧 | 22.5–38.9 毫秒 | −16.0 至 −4.0，平均 −8.7 |
| 同时放 60 帧测试图并录代理 | 17.1–33.0 毫秒，散布 0.95 帧 | 22.5–38.4 毫秒 | −15.7 至 −4.1，平均 −9.0 |

鼠标在一个刷新周期里的任意时刻移动，要等到下一次合成才被取到，所以这个差值本来就该有一个周期宽；它从 17.1 毫秒起，就是说“合成器取光标”到“这一帧上屏”正好一个刷新周期（60 Hz 是 16.7 毫秒），有没有负载都一样。同一次实验里，系统合成进去的光标比 GDI 色块早 0 或 1 帧进画面（平均 5–7 毫秒）——GDI 窗口重画后要再过一次合成才进画面，这一段是被录程序自己的延迟，不是我们的。

做法：采集程序的平台层在 `prepare` 应答里报 `presentLeadUs`（Windows 上是被录显示器的一个刷新周期；刷新率取不到时按 60）；主进程把会话时钟上的画面时刻一律记成“内容的时刻”= 上屏时刻 − `presentLeadUs`，换算只在 `capture/native.ts`。时刻表本身不变，仍记上屏时刻。

没有验证的：60 Hz 以外的刷新率（高刷屏、两块刷新率不同的显示器）是否仍是“正好一个周期”；录制中改刷新率不会更新这个值。

### 实测（真实应用，副屏整屏 4K60，翻转窗口法）

测法与第七轮相同：翻转窗口每秒黑白翻转并把鼠标移到窗口另一侧，记下 QPC 时刻；外部助手连接驱动录制、暂停、继续。脚本与结果在 `tickets/46-正式使用链路/证据/原生采集/`（`pause-check.cjs`、`复测-*.json`、`标定-*.json`）。

| 项 | 修之前（第七轮 C） | 修之后（复测 C2、C3，各暂停继续两次） |
|---|---|---|
| 事件里的暂停 − 画面空档起点 | −385 ms | C2：−6.4、−6.4 ms；C3：+0.8、+0.5 ms |
| 事件里的继续 − 画面空档终点 | −385 ms | 同上（两端一起偏） |
| 事件时钟扣掉的暂停长度 − 画面空档长度 | 0.3 ms | 0（四次都是 0） |
| 按下暂停到画面内容截止（暂停前最后一个光标事件到暂停时刻） | 约 390 ms | 9–17 ms（一帧以内） |
| 继续后第一个光标事件 | 画面续上后约 405 ms | 38–46 ms |
| 光标对齐中位（剪辑取光标的时刻 − 光标事件） | 33.1 ms（旧录法 15.5 ms） | C2：12.3 ms（暂停前 12.3、后 11.4）；C3：9.4 ms（前 9.4、后 12.1） |
| 画面标称时刻 − 帧的系统时刻 | 多数为 0，有一段晚一格 | 全程 0（最大 0.4 ms） |

说明：

- C2 里两端一起偏的 6 毫秒，是主进程与采集进程之间时钟校准的估计值在“暂停当时”与“收尾时”差了这么多（两边本是同一个计数器，差值来自往返测量的抖动）。暂停长度按采集进程自己时钟里两格之差算，不受它影响，所以暂停后的对齐不变。要把这几毫秒也去掉，得把会话起点也钉在同一次校准上，没做。
- 光标对齐剩下的约 10 毫秒不是画面的时刻偏：翻转窗口是 GDI 窗口，重画后平均要多等半帧才被合成进画面（标定里系统自己合成的光标也比色块早 5–7 毫秒），另外光标事件本身比真实移动晚 0–15 毫秒（见下一条）。
- 复测中另外发现并修掉一处：录制一开始，“开始前留着的旧画面”和第一张新画面会同时落进第 0 格，网格按“先出旧的、留一张缓冲”处理，结果之后每一格都晚一格，直到第一次暂停才复位（复测 C1 里暂停前画面比系统时刻晚 16.1 毫秒、暂停后为 0）。改为第一格与空档后一样直接取最新的一张，有单元测试。长录里相位慢慢漂到判定线上时仍会有一段晚一格，这是恒定帧率网格固有的，时刻表照实记着。

### 没做的与新发现

- **光标采样实际只有约 65 Hz**：事件采集按 120 Hz 设的定时器，在主进程里受系统 15.6 毫秒计时精度限制，实测相邻光标事件间隔中位 15.1–15.3 毫秒，所以光标事件比真实移动晚 0–15 毫秒。新旧录法都一样，不属于这次的范围；要改得提高主进程计时精度或把光标采样挪进原生进程。
- 继续后的头 40 毫秒左右（等采集进程报出续上的那一格）还没有光标事件。
- 来源丢失期间按暂停、暂停中来源丢失且继续时还没回来：事件时钟扣掉的长度与时刻表里的空档对不上（原来就有，这次没有变差）。
- 修之前用新录法录的会话，画面起点没有减上屏提前量，也带着 0.4 秒的暂停偏差；没有做迁移（只有走查的测试会话）。

## 余项第二轮（2026-11-14）

每组先记一句成熟项目怎么做（依据见 [调研-Rust画面采集进程](../../../tickets/46-正式使用链路/调研-Rust画面采集进程.md) 第 5.5 节的对照表，没有重新调研）。

### 一、拔显示器、锁屏、改分辨率、设备丢失的单测与模拟

成熟项目怎么做：WGC 的 `ContentSize` 变了就 `Recreate` 并丢掉这一帧（windows-capture、Cap、FFmpeg gfxcapture、OBS 都是）；显示器拔掉靠 `Closed` 事件，OBS 每 3 秒重新取显示器句柄再试，Cap 把“目标消失”与“设备被移除”分开；设备被移除后不能再把那个设备交给采集接口（Cap 的注释）。锁屏、休眠期间 WGC 的表现没查到文档，各项目也没有专门处理。我们的处理与它们同构，这一轮只补验证。

| 情况 | 怎么验的 |
|---|---|
| 拔显示器（一直没接回、几次找不到后接回、开始前就断开） | `session.rs` 三条单测：断开期间一帧不写、接回后同一文件续录且第一帧是关键帧、空档标成来源丢失；一直没接回时停止照样收好文件；开始前断开时文件从接回后的第一张画面起 |
| 显卡设备没了 | 一条单测走四种发现方式：等显示器回来时、每秒的检查、编码出错且设备已丢（统一报 `DEVICE_REMOVED`）、设备还在而编码器出错（照实报 `ENCODER_FAILED`）；都核对文件收尾、事件里的帧数与时刻表一致、清单记下原因 |
| 改分辨率 | 单测核对 `sourceChanged` 只报一次、录制不停、没有空档。新增注入 `resize`：把帧池换成一半大小，下一张来源帧走真实的“内容尺寸与帧池对不上 → 丢这一帧 → 按内容尺寸重建帧池”。**在真实显卡上跑过**（`selftest.cjs faults --motion`，副屏 4K）：先报 1920×1080、两帧后报回 3840×2160，之后照常录，文件尺寸不变。真的改系统分辨率仍未实测 |
| 锁屏、画面不变 | 单测：来源不出帧也不报错时网格照常走、重复最后一张，没有空档、不发事件。取帧连着失败的升级规则（零星的不升级、连着满一秒才当成来源丢失、升级后重新计时）抽成纯逻辑并有单测 |

测试暴露并修掉的两处：

1. **屏幕静止时按开始会一直等不到第一帧**：会话线程每轮循环都把“开始前留着的那张画面”取走丢掉（取与判断写在同一个元组里），所以开始的那一刻手里其实没有画面，要等屏幕下一次变化才出第 0 帧；屏幕完全静止时主进程等 10 秒后报“开始后没有收到画面”。改为还没要求开始时那张画面留着不动。此前的真实走查屏幕上一直有东西在变，没碰到。**真实应用里未复测。**
2. **画面起点没算第 0 帧所在的格**：主进程收尾时按“网格起点 + 上屏偏移”定画面起点；第 0 帧不在第 0 格时（还没出第一帧就暂停过、开始时来源正丢着）起点早了那么多格。改为按第 0 帧所在格算（`captureTimingFirstFrameUs`）。上屏偏移不再把每段的第一帧算进去（屏幕静止时它是留下的旧画面）。没封口的分片在恢复时按同一份时刻表补上这段偏移（原来恢复出的起点停在网格起点上）。

顺带：时刻表文件名只留一处定义（主进程与助手读回判断录法用同一个），恢复时另存的 `recovered-N.mp4` 旁边是 `recovered-N.frames`，读回认得出。

独立审查一轮，无重要问题；小问题里修了恢复路径的起点、上屏偏移改为按结构排除、测试里偏紧的断言与 README 的说法。记下没改的：开始前来源就丢了且一直没接回时，会话终点（来源丢失的时刻）早于起点，得到一段时长为 0 的录制（区间计算会钳到起点，不出错）。

### 二、长时间停摆记成空档，编码跟不上时先停代理

成熟项目怎么做：休眠与唤醒没找到成熟项目的专门处理（调研第 5.5 节对照表）；OBS 的视频线程落后时按落后的帧数补重复帧，编码队列（16 帧）满了就计跳过帧并提示编码过载（[调研-对照OBS](../../../tickets/46-正式使用链路/调研-对照OBS.md)），没有“先停次要输出”的做法；Cap 的偶发错误自动重启。我们的差别：短停顿与 OBS 一样占着时间轴（丢格），两秒以上的停摆不补，记成空档——我们有逐帧时刻表与画面条目的 `gaps`，读取方本来就按它换算，不需要靠补帧维持时间轴。

| 事项 | 做法 | 验证 |
|---|---|---|
| 停摆记成空档 | 会话线程隔了两秒以上才又轮到（整机休眠、进程被挂起、磁盘长时间卡住）：从还没出的第一格到此刻的格子不进文件，时刻表里与来源丢失一样标 16（声音与事件的时钟没停，不是暂停），`paused` 事件的 `reason` 是 `stall`、紧接着 `resumed`，活动时间线记 `stall`。两秒以内照旧：队列吸收或按丢格（占帧序号，画面停在上一帧）。准备好到开始之间等多久都不算。主进程不用做什么：空档进画面条目的 `gaps`，不进会话暂停 | 单测（注入 `sessionStall`）：2.6 秒的停摆是一段约 130 格的空档、之后第一帧是关键帧且是新画面；0.8 秒的只丢格、时间轴不断；准备后等 2.3 秒再开始不误判；停摆后紧接停止不把那段补进文件。**真实显卡上跑过**（`selftest.cjs faults --motion --proxy`）：157 格的空档，之后照常录 |
| 画面不变、锁屏 | 不属于停摆：来源不出帧时网格照常走、重复最后一张（每帧几百字节），时间轴与声音一致。锁屏期间系统给不给帧没查到文档、也没实测；给不给都落在“重复最后一张”或“取帧连着失败满一秒 → 重新接上”这两条已有的路上 | 单测见上一节 |
| 代理拖累主录制 | 编码队列连着满了一秒（中间没有超过半秒的缓和）且开着代理：编码线程在写下一帧前停掉代理（已写的部分收好），采集回调不再多画代理画面，发 `proxyStopped`。主进程记日志；停止后代理比原片短，不登记并删掉这份半截的代理（剪辑需要时现转） | 单测：队列刚满不停、满一秒才停、只停一次、主画面接着录；没有代理时不发事件。**真实显卡上跑过**：每帧多等 25 毫秒时停了一次代理，之后主画面照常 |

审查一轮。重要一条已修并补了测试：停摆的计时起点原来取的是准备好的时刻，准备到开始隔两秒以上（等用户点开始，是常态）时每次开录都会在第 0 格误记一段空档——改为从网格建好那一刻起算。记下没改的：会话线程若冻在出格循环内部（逐格落盘时磁盘卡住），醒来仍按丢格补；停摆与来源丢失或用户暂停首尾相连时 `paused` 的原因一律报 `stall`（时刻表标志是对的）；代理若已因出错停掉，之后过载仍会发一条 `proxyStopped`；一次一秒多的编码卡顿会让这次录制之后都没有代理。**真的休眠、锁屏没有实测。**

### 三、采集中断后在同一次录制里自动续录

成熟项目怎么做：OBS 设备丢失后由 `device_loss_release` / `device_loss_rebuild` 重建采集资源；Cap 把“设备被移除”单独分类，不把已移除的设备再交给采集接口，最多重启 3 次；我们自己的 FFmpeg 录法（`gfxcapture.ts` 的 `restart`）编码进程意外退出就在新分片里续录、一分钟最多 5 次、两片之间如实留空。原生采集照最后这一种做：编码会话绑在显卡设备上，设备换了就是另一路流，接不回原文件，所以另开一个画面分片。

| 部分 | 做法 |
|---|---|
| 什么时候续录 | 采集进程报 `interrupted` 且原因是 `DEVICE_REMOVED` / `ENCODER_FAILED` / `CAPTURE_FAILED`，或采集进程退出、没有应答。磁盘满、写文件出错不续录（照旧按采集失败收尾）；显示器断开仍走“等它回来、等不到就结束”那条路 |
| 怎么续 | 先收好中断的分片（时长取事件里的帧数与文件里实际读得回的较小者：中断时还在编码队列里的几帧没写进文件），再向采集进程重新 `prepare` + `start`，文件是会话清单里的下一个分片（`screen-000001.mp4`，各有各的时刻表与代理）。显卡刚重置完设备可能还起不来：隔 0 / 0.5 / 1.5 / 3 秒各试一次。事件时钟与声音没有停，两个分片之间那一两秒没有画面，如实留空，不算暂停。提示用户“画面采集中断过一次，已自动接着录” |
| 中断时正暂停着 | 只收好中断的分片，等按下继续再开新分片；一直没继续就停止时不向采集进程发停止 |
| 续不上 | 四次都准备不起来、新分片没能开始、一分钟内中断超过 5 次：按采集失败结束（会话记为已中断、已录部分可以导入），与原来相同 |
| 续录途中的操作 | 暂停、继续、停止都等续录有了结果再做；续录途中按停止就不再开新分片，按正常停止收尾。暂停或继续的指令在途时中断：暂停改在新分片上生效；继续返回新分片的起点，事件时钟与会话文档的暂停都算到那一刻 |
| 合并（导入剪辑） | `combine.ts`：每个带时刻表的画面文件各成一组（文件里暂停过的按时刻表分段，没暂停过的整段一片），画面都直接用原件，声音按各组各拼一条；两个文件不接在一起。都没暂停过时不合并，照原样逐个导入。带时刻表的文件与没有时刻表的分片混在一起（现在不会出现）时不合并 |
| 暂停推算 | `recordedPauses`：各文件里的暂停按各自的时刻表定；落在两个文件之间的暂停（中断时正暂停着）不在任何一份时刻表里，沿用当场记下的。单个文件、没有时刻表的旧会话与改动前逐值相同 |

持久格式没有改：会话清单里多一个画面分片，FFmpeg 录法本来就有。

验证：`native.test.ts` 六条（设备丢失后续录并在新分片上暂停与停止、暂停期间中断延后到继续、续不上与不可续的原因、继续或暂停途中中断、新分片没能开始、进程退出）；`combine.test.ts` 与 `session-document.test.ts` 各一条多文件的。独立审查三轮：第一轮两条重要（继续在途时中断被当成暂停着、新分片没能开始时留下没人管的采集），判断为状态时序上的疏漏、方案与 `gfxcapture.ts` 的续录一致，直接修；第二轮一条重要（第一轮的修法让继续提前返回，事件时钟没扣暂停），改为等续录完成后返回新分片起点；第三轮无重要问题。

记下没改的：续录途中进程在“已准备好、等第一帧”时退出不重试，直接按采集失败结束；续录的 `prepare` 在途时按停止，会多出一个极短的分片；显示器真的拔掉且同时设备丢失时，四次准备失败后报采集失败而不是“来源已关闭”；暂停着中断、继续时又续不上而此时用户按了停止，会记成失败。**真实的显卡重置（`dxcap -forcetdr`）没有实测**；采集进程被杀后续录见下一节的真实窗口验证。

### 四、真实窗口验证（2026-11-14，正式构建，副屏 4K60）

`npm run electron:bundle` 后重启应用，由外部助手连接开始录制（整屏 3840×2160 60 帧，不录声音），录约 9 秒后从外面强杀采集进程（`taskkill /IM henji-screen-capture.exe /F`），再录约 8 秒后停止。

### 五、预览接到边录边剪界面（没做）

查清了接法，没有动手：

- 边录边剪现在的画面区（`src/features/videoEdit/recording/ProjectRecordingView.tsx`）：指针在结尾时显示来源缩略图、每 2 秒取一张；录制中停在最后一张（当时定的是“不另开一路采集流”）。也就是低频缩略帧这一步已经有了，缺的是录制中的实时画面。
- 渲染层收显卡纹理帧的通道可以直接复用，不用改 preload：`videoFrames.connect()` 得到一个通道标识与端口，preload 里唯一的接收端按帧元数据里的 `route` 把 `VideoFrame` 投到对应端口（`electron/preload/video-frames-api.ts`）。
- 要新写的：① 主进程一个小的预览桥——向采集进程发 `startPreview`（`clientPid` 用主进程自己的进程号：与解码服务的做法一样，句柄复制进主进程，由主进程 `importSharedTexture` 再 `sendSharedTexture` 给界面；接线记录里写的“用渲染进程的进程号”不对），收 `preview` 事件按槽位导入并发给界面，录制结束或界面离开时 `stopPreview`；② 录制请求里加一个“开 / 关预览”的操作（`src/core/screenRecording/capture.ts` 的请求类型与主进程 `handleCaptureRequest`）；③ 界面上一个只在录制中出现的画布，把收到的帧画上去、画完经端口交还。
- 没做的原因：这是一条新的显卡纹理通道（现在 `texture-bridge.ts` 是主进程唯一用 `sharedTexture` 的地方，而且带槽位归还协议，采集预览的三张槽位没有归还协议、是轮着写的），属于 preload / IPC 这一类高风险路径，要独立审查，并且必须在真实窗口里看着画面验（格式不对会让显卡进程崩）。这一轮前三组做完后没有再开这一项。
- 退一步的做法（录制中也每 2 秒取一张缩略图）没有采用：取缩略图要让系统另开一次采集，会打扰正在进行的 4K60 录制，这正是当初定“录制中停在最后一张”的原因。要低频画面，更合适的是让采集进程自己每秒读回一张小图随事件发出来（协议里应答与事件本来就能带二进制），没做。
