## 任务目标

原生后端素材的音频（含 MXF、MOV 内 PCM、浏览器不支持的音频编码）由原生服务解码为 PCM，接入渲染器现有 `mixAudio`，节目播放、电平、音频时钟与导出混音全部正确；源监视器能播放专业格式素材的声音。

## 当前情况

- 混音入口：`src/features/videoEdit/engine/videoEditRenderer.ts` `mixAudio(start, duration)` 返回 `Float32Array[]`（按序列采样率与声道数），内部对每个可闻片段用 mediabunny `AudioSampleSink` 取样并按音量/静音/独奏混合；Worker 消息 `audio`（`engine/videoEditWorker.ts`）以 transfer 返回。
- 调用方：节目播放 `src/features/videoEdit/VideoEditPreview.tsx`（每次约 0.5 秒块、AudioContext 播放并作为播放时钟）；导出 `application/videoEditExport.ts`（每秒一块，AAC 编码）；电平 `engine/videoEditAudioMeter.ts`。
- 源监视器音频：`panels/videoEditSourcePresenter.ts` 用媒体元素 `<audio>`/`<video>` 与 MediaElement 音频图（电平）。
- 波形：主进程 `electron/main/services/audio/ops.ts` 用 FFmpeg CLI 解 PCM，已支持专业格式，本任务不改。
- 自动化验收静音（`--mute-audio`）不影响混音与电平读数（2026-10-02 monitor 场景已验证）。

## 实施方案

原生服务新增音频会话：`openAudio(file, stream)`、`pcm(session, startUs, durationUs, sampleRate, channels)`，在原生侧完成解码与重采样（libswresample，LGPL）到序列采样率，返回平面 float32（**阶段 A 调整**：原生只解码并转为平面 float32，保持流自身采样率与声道，按绝对采样序号读取；转序列采样率与声道映射仍由 `mixAudio` 统一负责，理由见执行记录）；数据量小（48kHz 双声道约 384KB/秒），经主进程与 MessagePort 送达渲染 Worker（不走纹理通道）。渲染器音频取样同样抽象为接口，浏览器实现保留 `AudioSampleSink`。采样边界规则与现有实现一致（绝对采样边界换算、片段源入点微秒）。

## 执行步骤

1. 原生服务实现音频会话与 PCM 区间读取（含任意起点、跨包、末尾补零、声道布局映射）。
2. 渲染器音频取样改为接口，原生实现接入 `mixAudio`；浏览器实现行为不变。
3. 源监视器：原生后端素材的声音改由渲染会话混音播放（与 2.2 的源监视器路径对齐）。
4. 验证：用带 PCM 的 ProRes MOV、MXF（DNxHR + PCM）、AAC MP4 样本，与 `ffmpeg` 直接解出的 PCM 做互相关（时差、相关系数）；`video-edit-monitor` 场景在原生后端下通过（电平、静音、独奏、两种音频格式）。
5. 播放时钟：原生后端标准负载的时钟偏差 ≤1%（与 2.2 一起测）。

**完成内容**

- **步骤 2（渲染层部分）核对**：2.1 已让 `mixAudio` 只经帧源接口取声音（`source.audio.chunks()`，渲染器不再引用 mediabunny 运行时），本任务不需要再改取样路径；补齐的是原生实现需要的接口语义与生命周期。
- **音频取样契约**（写在 `engine/videoEditFrameSource.ts` 的 `VideoEditAudioChunk`/`VideoEditClipAudio` 注释里，两种后端共同遵守）：
  - 时间口径：源文件的绝对时间轴（容器呈现时间，不按流起点归零），与片段源入点 `sourceInUs`（含分数微秒余数）同一口径；流从 0.523s 才开始时，之前是静音。这与 2.1 的“时长按绝对结束时间”一致。
  - 块内第 i 个样本在 `timestamp + i / sampleRate` 播放，`duration = numberOfFrames / sampleRate`。
  - 一次 `chunks(start, end)` 的块按时间升序且互不重叠（重叠会被混两次）；块可以超出范围，缺口即静音。
  - **重采样与声道映射只由 `mixAudio` 负责**：块保持流自身采样率与声道；`mixAudio` 用线性插值转到序列采样率；单声道序列取全部声道平均，否则第 c 声道取源声道 min(c, 声道数-1)。所以第 0、1 平面必须是前左、前右（FFmpeg 原生顺序本来如此）。
  - 混音在块内相邻样本间插值、在块末保持最后一个样本，所以读取方应交付范围前后各一个样本，范围内块边界越少越好。
  - 同一片段的读取不会并发（渲染 Worker 串行处理请求）。
  - **新增可选 `close()`**：每个片段一个读取器，原生读取器持有原生会话，需要释放。渲染器在丢弃片段源（离开混音范围、文档变更、关闭）时调用一次；浏览器读取器没有实现，行为不变。
- **原生取样实现骨架**：新建 `engine/videoEditNativeAudio.ts`。
  - `VideoEditPcmSession`（依赖注入，阶段 B 由端口实现）：`sampleRate`、`channels`、`read(startFrame, frames)` 返回恰好 `frames` 个样本的平面 float32（起点可为负；流开始前、缺口、结束后补零）、`close()`。
  - `videoEditPcmReadRange(start, end, rate)`：绝对采样边界换算 `[floor(start·rate) − 1, ceil(end·rate) + 2)`，即前后各一个保护样本，加上插值需要的下一个样本。
  - `createVideoEditNativeClipAudio(open)`：首次读取时才打开会话（画面片段也会拿到读取器但从不读），打开失败不缓存；每次读取最多 2 秒，混音每次最多 1 秒，所以一次混音只读一次、块内没有边界；校验声道数与长度；`close()` 只释放一次，打开中途关闭也会释放。
- **采样率由谁转换（与原计划的偏差，请主控确认）**：原计划是原生用 libswresample 转到序列采样率。阶段 A 改为原生保持流自身采样率，由 `mixAudio` 统一转换。理由：
  1. 浏览器与原生按同一规则出声，运行中回退或换后端时听感一致；预览与导出本来就共用 `mixAudio`。
  2. 原生在任意起点重采样时，要让输出对齐序列采样网格，每次定位都要算重采样器相位，容易错；按源采样序号读取没有这个问题。
  3. 修改序列采样率不需要重开会话；数据量相差不大。
  - 代价：转换质量仍是线性插值（96k/44.1k 转 48k 有轻微混叠），与当前浏览器路径相同。若要提升，应在 `mixAudio` 中为两种后端统一改，不在原生侧单独做。

**阶段 B 设计（1.3 完成后执行）**

1. **原生服务**（`native/video-decoder/src/audio/`，新增）：
   - 每个声音会话一个线程，独立解封装上下文，不分配纹理。
   - 选流与浏览器一致：首个声音流（不用 `av_find_best_stream` 按声道数挑选，避免两种后端听到不同的流）。
   - 解码后用 libswresample 只做格式转换（任意采样格式 → 平面 float32），采样率与声道数不变。自定义/未指定声道顺序保持原索引顺序。
   - 绝对采样网格：样本 n 在 n/采样率 秒。每段解码（打开或定位后）首帧按 `round(pts·采样率)` 落位（FFmpeg 已按 `skip_samples` 去掉 AAC/Opus 起始填充），之后按样本数连续累加；包时间偏离超过 1ms 时重新落位，缺口补零、重叠裁掉并记一次日志。
   - 读取：保留最近约 0.5 秒已解样本。与上次读取相邻或重叠（相邻混音块有约 3 个样本的保护重叠），或在当前位置之后 2 秒内时继续解码；否则定位到起点前预滚量处（Opus 至少 80ms，其余取解码器延迟与 100ms 的较大者）并 flush。负起点、流开始前与结束后补零。
   - Rust 纯函数测试：落位、重新落位、补零、预滚与续解判定（`audio/timing.rs`）。
2. **协议**（与 1.3 的版本号合并协商）：

   - `read_audio { audioId, ticket, startFrame, frames }` → 头 `{ ticket, frames, channels, seeked, decodeMs }` + 二进制负载（平面 float32 小端，声道 × 帧 × 4 字节）。单次 ≤ 2 秒且 ≤ 16MB。
   - `close_audio { audioId }`。
   - 传输：1.1 的 stdio 是长度前缀 JSON。建议加“JSON 头 + 二进制附件”帧，不用 base64（48kHz 立体声约 384KB/秒/片段，base64 多 1/3 且主进程要解析大字符串）。具体帧格式读完 1.3 最终协议后再定。

**遗留问题**

- 单次读取超过 2 秒才会在块边界保持最后一个样本，混音不会请求这么长的范围。
- 线性插值的转换质量（两种后端相同），见上。

**对后续任务的影响**

- **2.2**：原生帧后端的 `clipAudio()` 直接用 `createVideoEditNativeClipAudio`；片段画面读取器（`VideoEditClipFrames`）如果也持有原生会话，需要同样的 `close()` 生命周期（渲染器释放点已集中在 `release()`，可在同处调用）；源监视器的原生路径需留出声音会话与播放时钟的接口（见设计 7）。

### 2026-10-02 主控决定（阶段 A 提出的问题）

1. 接受采样率转换与声道映射统一放在 `mixAudio`（原生保持流自身采样率与声道），作为对原计划“原生 libswresample 重采样”的偏差记录；线性插值质量与现有浏览器路径一致，重采样质量提升不在本任务范围。
