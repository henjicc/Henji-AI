## 任务目标

1. 渲染器内所有取视频帧的地方统一到一个“帧源”接口，现有 mediabunny + WebCodecs 实现原样迁到接口之后（行为与性能不变），为 2.2 接入原生实现留好位置。
2. 素材导入/探测改为：先问原生服务 `probe`，再决定后端（原生 → 浏览器 → 无法解码提示）；导入入口接受专业容器扩展名。

## 当前情况

- 取帧位置（`src/features/videoEdit/engine/videoEditRenderer.ts`）：`acquireDemux`/`source()`（共享 `Input`，`VideoSampleSink` 顺序与 `getSample`）、`preroll()`、`buildPlayback()`（H.264 走 `videoEditPlaybackDecoder.ts` 的 `scheduledVideoSamples`，其他编码走 `samplesAtTimestamps`）、定位走 `videoEditSeekDecoder.ts`；画面统一进入 `videoEditGpuCompositor.ts` 的 `snapshot()`。
- 读取失败已转换为用户语言：`engine/videoEditSourceErrors.ts`；渲染失败在节目监视器就地提示并在序列变化/移动播放头后重试（`VideoEditPreview.tsx`）。
- 探测：`src/features/videoEdit/application/videoEditMedia.ts` `inspectMedia()` 用 mediabunny `Input`，`canDecode()` 失败即拒绝（“请先转为 H.264 SDR 视频”）；帧率用 `computeFrameRateMetrics` 推断并归到 `VIDEO_EDIT_FRAME_RATES`。
- 导入入口：`videoEditMedia.ts` 第 148 行文件对话框扩展名 `mp4/mov/webm/mkv/mp3/wav/m4a/flac/ogg/png/jpg/jpeg/webp/avif`（无 mxf/avi/mpg/mts 等）；拖入 `application/videoEditDrop.ts`；资产库导入的类型判定在 `electron/main/services/media-import/format.ts`（执行时核对）。
- 素材模型：`src/core/videoEdit/document.ts` `videoEditMediaSchema` 为 `.strict()`，已有 `hasAudio`、`frameRate`、`frameRateMode`、`sourceRevision`、`assetId`、`assetContent` 等字段。

## 实施方案

- 定义渲染器内部接口（暂名 `VideoEditFrameSource`）：`open(media)`、`frameAt(ptsSeconds)`、`schedule(timestamps)`（连续播放）、`metadata`、`dispose`，返回 `VideoSample`（原生实现用 `new VideoSample(videoFrame)` 包装，保证 `snapshot()` 不变）。浏览器实现封装现有代码；选择逻辑集中在一处，按探测结果与运行时健康状态选择。
- 探测服务：渲染层经 `src/platform/` 调用 1.1 的 `probe`，结果映射到 `VideoEditMedia`；需要新增字段时（如位深、色度采样、透明）以可选字段加入 schema（重要记录 006）。原生不可用时退回现有 mediabunny 探测。
- 开发诊断：新增环境变量（如 `HENJI_VIDEO_DECODER=browser|native`，名称执行时确定）强制后端，只用于测试，不出现在正式界面。

**遗留问题**

### 2026-10-02 主控验收修复（第 1 轮）

**问题 1：`video-edit-media-probe` 复跑在旧工程阶段超时**（两个尺寸都失败，等第 0 帧 90s 超时）

- **根因：场景依赖其他场景的缓存，不是旧工程本身打开失败。**
  - `closure` 快照引用了 `video-edit-probe/card.png`，并带固定素材库引用。它的内容身份由“路径、大小、时间、inode”算出。
  - `video-edit-engine-probe` 每次运行都会用 `-y` 重新生成这张图。
  - 所以之后再打开 `closure`，应用会按设计判定“源文件已改变”而拒绝画面，第 0 帧永远出不来。
  - 我之前三次通过，是因为都跑在最后那次 engine-probe 之前；主控复跑时 engine-probe 已重新生成过这张图。尺寸和前一次运行残留都不是原因。
- **修复：**
  - 把两个旧工程引用的全部素材一次性冻结到场景自己的目录 `node_modules/.cache/video-edit-media-probe/legacy/media/<工程>/`（约 101MB，本机证据）。
  - 每次运行打开一份副本，其中素材路径指向冻结文件；工程其余内容不变，打开前后比对这份副本的 SHA256。
  - `monitor`（普通引用）必须出第 0 帧。
  - `closure` 的固定引用经冻结后必然对不上，断言为“工程照常载入、文件不变，且这张图被判为已改变”，验证固定引用的保护仍然生效。
  - 快照或冻结素材缺失时，明确报“缺少旧工程快照”，不再静默跳过。
- 文件：`scripts/lib/uiInspectionSceneVideoEditMediaProbe.cjs`。

**问题 2：H.264 导入日志 `backend: "native"` 有误导**

  - 日志 `video_edit.media.inspect.completed` 现在为 `{ backend, native, nativeDecodes, browserDecodes, forced? }`。
