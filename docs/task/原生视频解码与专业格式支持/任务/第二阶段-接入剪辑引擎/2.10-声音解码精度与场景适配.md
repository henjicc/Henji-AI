## 执行记录

### 第一段：原生 Rust 侧（缺陷 1、2，2026-10-03）

范围：只改 `native/video-decoder/src/**`；工作区有 2.4 在用 release 产物跑 Reality，本段只跑 `node scripts/video-decoder-ffmpeg.cjs test`（debug 构建），未重建 release、未运行 Electron/Reality。

#### 根因

1. **缺陷 1（流开头一帧解错）**：`Input::seek_start()` 以流 `start_time` 调 `avformat_seek_file`。MP4 编辑列表下 AAC 的首包 pts 为 −1024、带 `AV_PKT_DATA_SKIP_SAMPLES`（skip 1024），而 `start_time` 已按 skip 算成 0，所以定位落在 pts 0 的包上、跳过了首包。首包整帧本应由解码器解出后丢弃，它是下一帧 MDCT 重叠的预滚；缺了它第一帧（0–1023）解错（OBS 样本最大误差 0.433）。
2. **缺陷 2（第二条 AAC 流末尾约 1024 样本不一致）**：不是末尾裁剪，也不是 libsoxr 排空。FFmpeg 自带的 AAC 编码器默认启用感知噪声替代（PNS），解码器用内部线性同余随机数生成噪声带，状态从第一个包起逐包推进。缺陷 1 少解一个包，此后所有噪声带的随机序列都错开：全程有 1e-7–1e-5 级差异，信号在末尾含较强噪声带的流（OBS 第二条流）才在最后约 1300 个样本超过 1e-4（本次复现最大 1.63e-3，2.6 混音场景中 ≤0.0075）。证据：同一信号用 `-aac_pns 0` 编码时，旧代码只有 0–1023 错、末尾逐样本一致；启用 PNS 时末尾出现偏差；修正缺陷 1 后两条流从头到尾与 FFmpeg 完整解码**逐位相同**（最大误差 0）。末包的 `discard_padding=512` 一直由 FFmpeg 正确处理。
3. **同源问题 A：重新定位用 `avcodec_flush_buffers`**。flush 只清重叠缓冲，不重置 PNS 等随机数状态，所以“读过别处再回到开头”的输出与完整解码不同（最大 3.1e-3），且同一位置的输出随此前读过多少而变。
4. **同源问题 B：定位后首帧按 1ms 容差合并**。`fill()` 对段内每帧都用“与预期相差 ≤1ms 视为连续”，但段起点 `next_in` 是按目标算出的位置、不是上一帧的延续；跨过起点的那一帧若离起点 ≤1ms（AAC 1024 样本帧约 1/10 的定位命中，Opus 20ms 帧同样），整段输出错位最多 48 个样本（实测 Opus 定位到 150000 时整段晚 40 个样本，最大误差 0.49）。2.3 场景的定位点恰好没命中。

#### 改法

- `decode/demux.rs` `seek_start()`：**声音流**定位到 `min(start_time, 索引最早时间)`，落到含预滚的首包，由解封装器注入的 skip_samples 和解码器自己丢弃预滚样本（复用 FFmpeg 的 `AV_PKT_DATA_SKIP_SAMPLES`/`initial_padding` 机制，不自写补偿）。视频流行为不变（不影响 2.4 等画面路径）。
- `audio/mod.rs` `seek()`：重新打开解码器代替 flush，与 FFmpeg CLI `-ss` 定位后新建解码器一致；实测打开耗时 AAC 0.40ms、Opus 0.19ms、AC-3 0.11ms、MP3 <0.01ms（debug 测试进程，一次定位+读取约 0.4–0.8ms），只在不连续读取时发生。
- `audio/mod.rs` `Segment.fed`：本段送入第一批解码样本之前的帧一律精确落位（跨过起点的帧精确丢掉起点前的样本），之后才按 1ms 容差合并时间戳抖动。
- 新增 Rust 测试 3 项（`audio::tests`）：
  - `aac_with_priming_and_noise_substitution_matches_ffmpeg_from_start_to_end`：默认（PNS）AAC MP4 从 −480 起 0.5 秒块带 3 样本重叠续读到流结束之后，与 FFmpeg 完整解码逐位相同；读过 2.5s 处后回到开头仍逐位相同。
  - `seeks_place_the_first_frame_exactly_at_every_phase`：关 PNS 的 AAC 48 个定位目标（覆盖 1024 帧内各相位）逐位相同；Ogg Opus 流开头（pre-skip 312）逐位相同、4 个定位点误差 <1e-5。
  - `mp3_encoder_delay_and_resampling_stay_on_the_absolute_grid`：44.1k LAME MP3（编码器延迟 1105）→48k soxr 的开头、定位、结尾与网格对齐参考误差 <1e-6。
  - 逐项回退验证：撤掉 `seek_start` 改动，第 1 项在“从 −480 起的块”失败；把重新打开换回 flush，第 1 项在“回到开头”失败；去掉精确落位，第 2 项失败。

#### 选型依据

- 预滚与首尾填充：FFmpeg 已有完整机制（解封装器按编辑列表/`initial_padding`/LAME 头注入 `AV_PKT_DATA_SKIP_SAMPLES`，libavcodec 丢弃并修正 pts），问题只在我们的定位绕过了首包，所以只改定位目标，不另写补偿表。
- 定位后解码器状态：比较了 flush（现状，状态随历史变化）、重开解码器（与 FFmpeg CLI 精确定位相同）、从流开头解码到目标（与完整解码完全一致但长文件不可接受）；选重开，代价 <0.5ms。

#### 比对数值

方法沿用 2.6：随包 FFmpeg 9.0.2 生成样本与参考 PCM（`ffmpeg -map 0:a:N [-af aresample=48000:resampler=soxr:precision=28] -f f32le`），按首个解码帧时间放到绝对时间轴，与原生会话输出逐采样比较。样本、参考与读取结果在 `node_modules/.cache/audio-precision/`（`matrix.json`）。每个样本三组读取：从 −480 起读 1 秒；0.5 秒块（3 样本保护重叠）连续读到结束之后；同一会话依次定位到 72000、12000、0、150000（读到结尾）、30011。

说明：

- **PNS 噪声**：AAC 噪声带本身就是解码器随机生成的，定位到流中间时随机数状态不可能与“从头解到这里”相同（FFmpeg CLI `-ss` 同样如此），误差 ≤1.6e-3、只出现在编码器选为噪声的频带；回到开头已逐位一致。关 PNS 的同一信号定位误差为 0，证明落位与预滚都正确。
- **重采样流开头**：原生在流开始前送零，soxr 线性相位滤波器在绝对 0 之前有前振铃（AAC 44.1k 5.6e-4、PCM 96k 8.1e-4，只在负时间），AAC 44.1k 流内开头 4 个样本差 5.4e-4；FFmpeg 参考从 0 截断。片段源入点 ≥0，听不到负时间部分。
- **参考的网格**：流起点不在输出网格上时（MP3 44.1k 起点 1105/44100s），`aresample` 参考的输出样本 k 落在“起点 + k/48000”，偏离绝对网格 0.28 个样本（未对齐时误差 0.02）；参考改为 `adelay=<起点样本>S:all=1,aresample=…` 后与原生 4.4e-16。原生按绝对网格是对的；2.6 场景的样本起点都是 0，不受影响。

#### 遗留

- **毫秒时间基容器（MKV/WebM）定位后最多偏 0.5ms（24 个样本）**：Matroska 块时间戳只到毫秒，定位后第一帧只能按四舍五入的时间落位（连续读取不受影响，从开头读也逐位一致）。FFmpeg/mpv 同样受此限制。可选改进：对固定帧长的编码（AAC 1024、MP3 1152、AC-3 1536）在时间基粗于一个样本时，把定位后首帧吸附到“流首帧 + k×帧长”的网格（偏差限制在半个时间刻度内）；Opus/Vorbis 帧长可变无法这样做。OBS 默认录制 MKV，是否做请主控决定。
- 测试命令与结果：`node scripts/video-decoder-ffmpeg.cjs test` 57/57 通过（原 54 项 + 新增 3 项），无编译警告。
