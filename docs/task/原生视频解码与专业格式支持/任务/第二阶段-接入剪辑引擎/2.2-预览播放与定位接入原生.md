## 任务目标

节目监视器的播放、逐帧、定位、拖动、反向播放，以及源监视器，对原生后端素材全部走原生帧源，满足 5.1 的 4K60 容差；专业格式（如 ProRes、DNxHR）在源监视器中也能播放和精确定位。

## 当前情况

- 渲染器在 2.1 后只依赖帧源接口；原生帧源的底层能力（单帧、连续计划、纹理通道）由 1.2/1.3 提供。
- 节目播放调度：`src/features/videoEdit/VideoEditPreview.tsx`（播放时钟、`renderer.present`、截帧回执）；渲染器内连续播放计划 `buildPlayback()`、预取 `preroll()`、定位缓存 `VideoEditFrameCache`（节目 8GiB）。
- 源监视器：`panels/videoEditSourcePresenter.ts` 正常播放用 `HTMLVideoElement`，精确帧/反向用 `engine/videoEditSourceFrames.ts`（复用渲染会话，缓存 3GiB）。`<video>` 不能播放专业格式。
- 现有验收场景：`video-edit-performance`（`HENJI_PERF_SOURCE` 可替换素材）、`video-edit-4k60-scrub`（逐帧校验源时间戳）、`video-edit-composite-pressure`（32 轨/500 片段）、`video-edit-popout`、`video-edit-project-source`（源监视器）。
- 2.1 留下的开关：只有原生能解码、浏览器解不了的素材（ProRes、DNxHR、MXF、MPEG-2 等）目前在导入时按具体格式拒绝；本任务接通原生播放时把 `engine/videoEditFrameSource.ts` 的 `VIDEO_EDIT_NATIVE_PLAYBACK_READY` 改为 `true` 放开导入，并把 `video-edit-media-probe` 场景改为断言可导入且元数据来自原生探测。

## 实施方案

- 原生帧源实现：连续正向播放用一个长期会话按计划取帧（与浏览器路径同语义：不 flush、剪辑点从目标关键帧续解、按微秒 PTS 精确对帧、对不上的帧返回 null 交常规路径）；定位/拖动按时间取单帧并利用现有帧缓存；反向播放复用缓存与 GOP 缓存策略（帧内编码格式直接按帧取）。
- 源监视器：对原生后端素材不用 `<video>`，统一走 `VideoEditSourceFrames`（播放也走渲染会话）；浏览器后端素材保持现状，避免回归。
- 多图层：每个文件一个会话，同文件多片段共享会话；并发会话数与显存按 3.1 的预算执行（本任务先设保守上限并记录）。

## 执行步骤

1. 实现原生帧源（连续计划、单帧、释放），在 2.1 的选择器中接入。
2. 节目监视器：播放、逐帧、定位、拖动、反向、剪辑点在原生后端下逐项验证；渲染失败沿用就地提示机制。
3. 源监视器：原生后端素材改走渲染会话播放与定位；音频由 2.3 提供（本任务源监视器先静音或沿用现有音频，执行时确定并记录）。
4. 性能：`video-edit-performance` 分别用原片头、ProRes 422 HQ 4K60、DNxHR HQX 4K60 跑完整 60 秒（`HENJI_PERF_SOURCE`），各至少 2 次；`video-edit-4k60-scrub`、`video-edit-composite-pressure`、`video-edit-popout` 在原生后端下回归。
5. 对照：同一素材浏览器后端与原生后端各跑一次标准负载，记录差异（帧间隔、CPU、GPU 主线程占用）。

**完成内容**

- 端口请求（平台契约 `videoFrameTypes.ts`/`videoFrames.ts`、preload、主进程）：
  - 新增端口消息 `request`/`response`（`openDecoder/frameAt/schedule/cancelSchedule/closeStream`）与 `ended`（流因原生出错或服务退出而结束）。preload 把请求转为原有 IPC，`openDecoder` 一律改写为本通道 route；未知方法回错误。
  - 计划结束事件带上 `delivered`（本计划发出的帧数），区间计划据此判断最后一帧（帧与事件经不同通道，可能晚到）。
  - 新增 `videoFrames:closeRoute`：通道断开时由 preload 调用，主进程关闭该窗口该通道上仍打开的会话（Worker 被终止、崩溃时兜底）。
- Worker 接收端 `videoEditNativeFrames.ts`：`call()` 请求/响应按编号对账；`subscribeEnded`；`dispose()` 改为返回 Promise——拒绝在途请求、交回全部借出帧，等推迟的交回消息发出后才关闭端口（最多等 2 秒），Worker 等它完成才回复关闭，避免终止 Worker 时帧泄漏。
- 借用画面 `engine/videoEditNativePicture.ts`：时间取 `ptsUs`（与 mediabunny `microsecondTimestamp` 同口径）、时长取 `durationUs`（缺失用 1/帧率）、显示旋转按 FFmpeg 显示矩阵角取反为顺时针（与 mediabunny 一致）；`holdUntil(fence)` + `close()` 等全部 GPU 读取完成再交回且只交回一次。`snapshot()` 识别借用画面：直接导入、不关闭，复制命令完成后由画面关闭交回。
- 原生帧后端 `engine/videoEditNativeFrameSource.ts`：
  - 每个文件（路径 + 版本）一个文件源：一个 `playback` 会话承载正向连续计划（新计划取消旧计划，剪辑点续解不 flush，按 index 对齐帧与缺帧事件，计划外与过期的帧立即交回）；一个 `seek` 会话由单帧读取与定位器共用，操作串行，前台请求抢占预取；每个顺序读取器（`frames(start)`，预取下一剪辑点与导出用）独占一个 `playback` 会话，随读取器结束关闭。
  - 帧丢失不卡死：后面的帧已到或计划已结束时给 1 秒宽限，之后按缺帧处理（计划失败只等一次宽限）；原生流异常结束时等待中的读取立即以用户语言失败。
  - 会话保守上限每个渲染器 10 个（主进程每窗口 16 个），超限给出用户语言提示；打开失败转为“重新定位源文件”提示并通知路由层。
  - 声音：`clipAudio()` 返回 undefined（2.3 阶段 B 接入），用原生后端的文件暂时无声。
  - 定位器 `VideoEditNativeSeeker`：见选型表。
- 路由层 `engine/videoEditFrameRouter.ts`：每个文件决定一次后端（`video_edit.decode.backend.selected` 日志）；原生可读本地文件且非强制、非原生主路径时才问浏览器能否完整解码，询问时打开的浏览器解析由第一次打开复用（浏览器后端不重复解析）；浏览器读不了的文件下次重新决定；决定前即释放的打开不再打开底层后端。原生会话打开失败后，若浏览器可能能解，该文件之后的打开改走浏览器（`video_edit.decode.native.fallback`）；已打开的读取器在本帧就地提示，在途恢复属 3.1。强制后端不替换。
- Worker/会话接线：`VideoEditRenderSession` 启动时查询原生状态与诊断变量，建立帧通道并在 `init` 前把端口交给 Worker；`init`/`update` 附带“可取 URL → 本地原路径”映射（媒体 URL 规则：Worker 只见 `henji-media://`，原生服务读真实路径，转换在会话这一层）；Worker 的结构化日志经会话写入应用日志（Worker 内无法直接写日志）；关闭时 Worker 依次释放渲染器、等原生会话关闭、交回全部帧再回复，会话终止 Worker 后断开通道。任何一步失败只记警告（`video_edit.decode.native.channel_failed`），本会话只用浏览器解码。
- 源监视器：`videoEditSourceBackend()`（与 Worker 同一决定规则，按文件缓存）与 `<video>` 加载并行进行，浏览器能解的素材打开速度不变、行为不变；只有原生能解的视频不用媒体元素，画布 `data-video-edit-source-media="video"`、`data-video-edit-source-canvas` 与 `data-presented-time-us` 记录确认画面；`VideoEditSourceFrames.playFrame()` 新增正向播放（整段片段、连续帧、按节拍 deadline）；暂停/定位/反向沿用 `present()`；静音、电平为空。
- 导入开关：`VIDEO_EDIT_NATIVE_PLAYBACK_READY = true`。导入日志的 `backend` 与渲染器同一规则：浏览器能完整解码的文件为 browser（强制原生时为 native），只有原生能解的为 native。
- Reality 场景 `video-edit-media-probe` 改为新断言（未运行）：非强制浏览器时专业样本可导入、素材只有现有字段、元数据与 ffprobe 推出的期望（宽高、平均帧率、恒定/可变、各流绝对结束时间最大值）一致、日志 `backend: native, browserDecodes: false`；随后逐个在源监视器打开：无媒体元素、三处定位落在请求时间所在帧、播放 1.2 秒内画面持续前进不倒退；强制浏览器时仍按格式拒绝且工程不变；H.264 对照样本后端为 browser（强制原生时 native）。

- 只有原生能解的素材在 2.3 阶段 B 前无声（节目、源监视器、导出）；浏览器能完整解码的文件整体留在浏览器，原生成为主路径要等 `VIDEO_EDIT_NATIVE_PRIMARY` 打开。
- 只有原生能解的纯声音素材（AC-3、TrueHD、纯 PCM MXF）已可导入但无声，源监视器仍用 `<audio>`（解不了时报“源文件无法播放”），随 2.3 阶段 B 处理。
- 播放计划一次发送窗口内全部时间点（30 分钟 60fps 约 10.8 万个，约 2MB 消息）；超过原生上限 20 万的部分走常规路径。起播耗时待真实环境测量，必要时改为分段计划。
- 会话上限与显存：每个原生文件在节目监视器常驻一个播放会话与一个定位会话（rgbaf16 4K 约 0.6–1.4 GiB/文件，见 1.3），每渲染器最多 10 个会话为保守值，正式预算与空闲会话回收属 3.1。
- 运行中回退只对之后的打开生效；当前策略下自动模式只有浏览器解不了的文件走原生，原生失败无可回退的后端，按就地提示显示。
- 长 GOP 定位按一秒窗口解码，窗口不与 GOP 对齐，反向拖动时每个窗口要从所在关键帧重解（约 1.5 倍于浏览器整 GOP 的解码量）；`video-edit-4k60-scrub` 的速度断言需在真实环境确认。

**对后续任务的影响**

- 2.3 阶段 B：原生声音接入 `VideoEditNativeFileSource.clipAudio()`（`engine/videoEditNativeFrameSource.ts`），端口请求可沿用本任务的 `call()` 通道；接通后把 `VIDEO_EDIT_NATIVE_PRIMARY` 改为 true（导入日志、Worker 路由、源监视器同时生效），源监视器原生素材的声音与播放时钟接在 `runNative()`。
- 2.4：导出会话同样建立帧通道；导出逐片段 `frames(start)` 走独占的原生区间会话，`frameAt` 走共享定位会话；导出时只有原生能解的素材目前无声。
- 2.7：原生帧进入合成器的唯一位置是 `snapshot()` 中的借用画面分支，rgbaf16 帧的 `format` 为 null，现按 rgba8 复制；改高位深时在此按会话输出格式选择 16 位浮点自有纹理。
- 3.1：会话上限常量 `VIDEO_EDIT_NATIVE_MAX_SESSIONS`、空闲会话回收、在途读取器的回退、`videoFrames:closeRoute` 兜底与流结束通知（`ended` 端口消息）都是本任务留下的接口。

**修复 1：`video-edit-engine-probe` 自动后端下缺失素材提示错误**（主控复现）

- 现象：缺失源文件用例提示“素材「1920-30.mp4」无法读取…”，场景要求“找不到素材…重新定位源文件”。
- 根因：自动模式下浏览器读不了缺失文件，路由层把它当作“浏览器解不了”交给原生；原生打开失败的系统错误是 `无法打开文件：No such file or directory`，用户语言转换 `videoEditSourceReadError()` 只认 Chromium 的 404/ENOENT，于是落到“无法读取”。路由层对读不了的文件本来就会在下次打开时重新决定，重新定位后恢复正常。
- 修复：`engine/videoEditSourceErrors.ts` 把 `no such file` 也认作缺失（两种后端同一提示）；帧源测试补用例。复跑 `video-edit-engine-probe`（自动）通过两次（修复后、最终代码各一次）。

**修复 2：`video-edit-media-probe` 源监视器在 mpeg2.mpg 上超时**

- 根因（同源缺陷，浏览器后端读起点非零的 MPEG-TS 同样存在）：MPEG 节目流画面从 0.533 秒开始（2.1 定的绝对时间轴，起点前是空白）。渲染器对“此时间没有画面”一律抛错，源监视器打开在 0 秒、定位 0.5 秒都落在首帧之前，状态变为错误，场景等到超时；节目监视器里同一素材的片段开头同样会整帧失败。修复后又暴露一处：顺序读取器从首帧之前开始时会把首帧（0.533 秒）提前交出，源监视器播放从 0.1 秒起直接显示 0.533 秒的画面并重复上报。
- 修复：
  - 渲染器：源时间在素材时长内却没有画面时，该层画透明（合成器 `blank()`，共享 1×1 透明纹理），不记源时间、计入 `blankPictures`，不再让整帧失败；超出素材时长仍报错。顺序读取器交出的画面时间晚于请求时间时保留到它自己的时间，之前画透明。
  - 源监视器（`VideoEditSourceFrames`）：渲染回执只有一个透明层时，确认位置取标称帧格（定位、反向按帧后退、正向播放都能前进）；其他缺少时间戳的回执仍拒绝。
  - 测试：渲染器（首帧之前透明、超出时长报错、提前交出的首帧等到自己的时间）、源帧（透明回执按帧格确认，普通缺失仍拒绝）。
- 复跑 `video-edit-media-probe` 自动、`HENJI_VIDEO_DECODER=browser`、`HENJI_VIDEO_DECODER=native` 三次均通过（见下）。场景的倒退断言改为输出出错位置附近的时间（定位用，未放宽）。
