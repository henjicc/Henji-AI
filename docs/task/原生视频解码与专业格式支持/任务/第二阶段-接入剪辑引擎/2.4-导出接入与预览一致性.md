## 任务目标

含原生后端素材（专业格式）的序列能完整导出：每一帧都是精确的源帧（不出现缺帧、重复帧或交回 null 后的错误画面），导出与预览逐帧一致、音画同步；导出期间编辑、取消、入出点范围导出等现有行为保持不变。导出编码格式不在本任务范围（仍为 MP4/AVC + AAC）。

## 当前情况

- 导出：`src/features/videoEdit/application/videoEditExport.ts` 冻结序列快照，`VideoEditRenderSession`（无预览宽度，走全尺寸定位路径）逐帧 `render(frame, true)` + 每秒一块 `mixAudio`，mediabunny `Output`（`CanvasSource` AVC 8Mbps、`AudioBufferSource` AAC 192k）写入；支持入出点半开范围、取消清理、导出期间编辑不污染快照（2026-10-02 提交 `e36a8621`、`d79f9188`）。
- 闭环验收：`scripts/lib/uiInspectionSceneVideoEditProbe.cjs`（场景 `video-edit-engine-probe`）对 1080p/4K × 30/60 四种规格做预览与导出逐帧 PSNR（>24dB）、音频互相关（>0.98）、范围导出与故障注入。
- 原生帧源在 2.2 中对“对不上的帧返回 null 交常规路径”；导出不能接受降级画面，必须拿到精确帧。

## 实施方案

导出使用原生帧源的“按时间取单帧/顺序计划”模式，要求严格精确：拿不到精确帧时重试单帧取帧，仍失败则导出失败并给出用户语言原因（保留已有清理逻辑），绝不写入错误画面。导出与预览共用同一渲染、合成与混音实现，不另建求值。

## 执行步骤

1. 渲染器导出路径（非预览）接入原生帧源，并实现“精确帧或失败”策略。
2. 扩展闭环场景：在现有四种规格之外加入 ProRes 422 HQ 4K、DNxHR HQX 4K（MXF）、ProRes 4444 透明素材的导出比对（逐帧 PSNR、透明区域合成正确、音频互相关）。
3. 导出性能记录：每种格式 2 秒/10 秒成片耗时与原生进程 CPU；与浏览器后端同素材对比（H.264）。
4. 回归：入出点范围导出、取消、导出期间编辑、导出期间关闭被拒等既有故障注入在含原生素材的工程中通过。

**现状核对**

- 导出会话（`VideoEditRenderSession` 无预览宽度）本来就建立帧通道，素材按与预览同一规则走原生（2.3 起原生为主路径）；导出逐帧 `render(frame, true)` 走渲染器的顺序读取器 `frames(start)`（原生为独占的区间计划会话），每秒一块 `mixAudio`。
- 缺口：顺序读取器给不出准确画面时导出会写入替代画面。原生区间计划对解码丢弃的包、损坏帧不发 `frame_missing`，途中丢失的帧过 1 秒宽限后被跳过；渲染器于是拿到晚于请求时间的下一帧并把该层画成透明（“提前到达”分支），读取器提前结束时则一直沿用旧画面（重复帧）。声音一侧读取失败本来就会让混音报错，不会补静音。

**选型**

| 问题 | 方案比较 | 结论 |
|---|---|---|
| 导出取帧方式 | ①每帧单帧读取（请求往返串行，长 GOP 每次可能重新定位，慢）；②复用预览的按文件时间计划（同文件重叠片段、超过 4 个文件时仍要回落到顺序读取器，且改动预览共用的计划构建）；③保留顺序读取器（原生在编码时继续预解），画面不准确时才用单帧读取裁决 | ③，与实施方案“顺序计划 + 拿不到精确帧时重试单帧取帧”一致；正常恒定帧率素材每帧都被读取器画面覆盖，零额外开销 |
| “准确画面”的定义 | 按片段时长覆盖判定（可变帧率、流末尾的保持画面会被误判）；单帧读取的定义 | 与单帧读取（原生 `frame_at`、mediabunny `getSample`）、预览定位和播放计划同一定义：开始时间不晚于源时间的最后一帧；源时间早于流首帧时该层透明（MPEG 节目流）。读取器画面覆盖源时间即准确，否则一律由单帧读取裁决 |
| 读取器提前给出的下一帧 | 丢弃后下一帧重开读取器（每次缺口一次定位）；存进片段源的新字段（要改渲染器所有释放路径） | 包一层可退回一帧的读取器：退回的画面属于读取器，渲染器已有的 `iterator.return()` 释放路径一并交回，渲染器释放路径不改 |
| 失败策略 | 读取器出错直接失败；读取器出错先单帧读取 | 读取器出错或没给出准确画面时由单帧读取决定这一帧（下一帧重开读取器）；单帧读取也失败（或给出晚于请求时间的画面）时该帧失败、导出停止，沿用已有的取消编码与删除半成品逻辑，不写替代画面 |
| 失败提示 | 沿用后端原文；加序列位置 | 渲染层：`素材「X」取不到准确的画面：<后端原因>`（后端原因已是用户语言时去掉重复的素材名，原始解码错误换成可操作说明，原因保留在 cause）；导出层：`导出在 <序列时间码> 处停止。<原因>`，画面与声音同样适用 |

**遗留与风险**

- 单帧读取裁决的代价：恒定帧率素材几乎不触发；可变帧率且容器时长不准的素材（如没有帧时长的 MKV）在保持画面期间每帧一次单帧读取（原生定位会话在同一 GOP 内续解、到文件末尾后直接给最后一帧，代价小；浏览器后备 `getSample` 每次从关键帧解码，较慢）。
- 源文件本身损坏、解码器丢弃的帧：单帧读取同样解不出，按定义呈现开始时间不晚于源时间的最后一帧（与预览播放计划、帧内编码定位一致），不判为取帧失败。
- 端口代理丢帧会触发原生接收端 1 秒的丢帧宽限，故障注入导出因此多用约 3 秒；属测试手段，不影响正常导出。
- 同类实现排查（未改，属预览路径）：预览播放中时间计划给出空帧后回落到顺序读取器时，读取器漏帧仍会画透明层；原生长 GOP 定位窗口按帧时长查缓存，可变帧率且时长不准时保持画面会画透明。两者都只影响预览显示，与导出口径（单帧读取定义）在这些罕见素材上可能不同，交 3.1/3.2 评估。
