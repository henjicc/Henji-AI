## 实施方案

建立格式矩阵（容器 × 编码 × 位深/采样 × 透明 × 音频），每格生成或选取样本；逐格执行功能清单与性能测量；原生与浏览器两后端在 H.264/HEVC/AV1/VP9 上对照。偶发呈现层长间隔单独跟踪，不与解码问题混报。

## 执行步骤

1. 补齐样本：MPEG-2、CineForm、DNxHD 1080p、DNxHR 444、ProRes Proxy/LT/4444 XQ、H.264 4:2:2 10 位、VP9 透明 WebM、MXF（OP1a，含 PCM 音频）；生成脚本放 `scripts/` 或场景内，样本放 `node_modules/.cache/`。
2. 功能矩阵：每格在剪辑中导入、播放、逐帧、拖动、反向、源监视器、混音、导出（逐帧 PSNR、音频互相关），记录结果。
3. 性能：原生后端标准 4K60 负载用原片头、ProRes 422 HQ、DNxHR HQX 各跑 3 次完整 60 秒；ProRes 4444 透明与 Tripo 长片单独记录；每次记录更新率、遗漏、p95/p99/最大间隔、时钟偏差、CPU（原生进程核数）、显存、资源循环增长。
4. 后备路径：用诊断变量强制浏览器后端跑一次标准负载与 engine-probe，确认仍满足既有标准。
5. 全量剪辑 Reality 回归（engine-probe、project-source、code-project、code-controls、4k60-scrub（合成源与原片头）、monitor、composite-pressure、popout、creative-results、agent-loop、asset-references、performance）。
6. 把最终支持格式与已知边界写入执行记录，并按需更新 `docs/rules/` 中受影响的规则（如媒体与验收规则）。

**矩阵首轮发现缺陷 D1：源监视器原生反向浏览在长 GOP 素材上每步重解整秒窗口并显示黑帧**

- 定位（渲染 Worker 消息追踪，诊断开关 `HENJI_FORMAT_MATRIX_TRACE=1`）：原生画面的时间戳与时长分别取整到微秒，相邻两帧之间留下 1µs 空隙（帧 1.166666 + 0.016666 = 1.183332，下一帧从 1.183333 开始）。源监视器反向浏览按“已显示画面时间 − 1µs”后退，恰好落在空隙里：`VideoEditFrameCache.get` 按 [起点, 起点+时长) 查不到 → 长 GOP 定位器每步重解一整秒窗口（约 0.57 秒）；窗口为闭合空隙重定时长的副本又因缓存里已有同一时间戳的条目被 `put()` 丢弃，窗口结束仍查不到 → 该层按“流首帧之前”画透明（黑帧）。追踪：第 80 次请求（1.183332）未命中、解码 573ms、源时间戳为空（透明）；下一请求 1.166666 命中。帧内编码（ProRes 等）走单帧读取，节目监视器按序列帧格的精确时间查询，均不受影响。
- 修法演变：
  - 先拟在缓存侧给 `VideoEditFrameCache.get` 加容差吸收取整空隙，实现后被既有用例否决：缓存只看得到截断后的起点与时长，区分不了“截断留下的 1µs 空隙”与“起点、时长本就是整微秒、首尾精确衔接”——后者在下一帧起点上会被错判为前一帧（既有用例 `frame(1.037, .05)` 查 1.087 应未命中）。缓存侧方案撤回，`src/` 未留改动。
  - 根因在原生服务：`native/video-decoder/src/decode/mod.rs` 帧事件的 `durationUs` 用 `pts_to_us(duration)` 单独截断，起点 `pts_to_us(pts)` 也截断，两者之和比真实结束点（= 下一帧起点）少最多 1µs。改为结束点同样截断后相减：新增 `decode/timing.rs` `duration_to_us(pts, duration, base) = pts_to_us(pts + duration) − pts_to_us(pts)`，帧事件改用它；时长未知时的回退分支不变。时长连续的相邻帧首尾按微秒精确衔接，整微秒时长结果不变；协议不变，时长只会加长 ≤1µs，渲染层与导出无需改动。浏览器后端的时间戳是浮点秒、没有这个截断，不受影响。
  - 验证：`node scripts/video-decoder-ffmpeg.cjs test`（debug）60 项通过；新增 Rust 用例 `frame_durations_join_the_next_frame_start_to_the_microsecond`（60/59.94/29.97/25fps 各 2000 帧首尾相接、D1 实例 1166666µs + 16667 = 1183333、整微秒不变）；断牙：把函数临时改回单独截断时该用例失败，恢复后通过。待 3.3 安装验证结束后 `build:video-decoder`（release）+ bundle，再真实复验。

**3.1 移交 2：软解私有提交残留——根因与修复（缺陷 D2）**

- 复现（协议直连 release 服务的诊断脚本：打开 ProRes/DNxHR 播放会话、按区间连续取帧并逐帧归还、关闭会话、空闲 3 秒后读服务 `stats`；脚本不入库）：每会话解 6000 帧，ProRes 422 HQ 25 个会话私有提交 308.7→416.8MB，线性约 +4.7MB/会话（≈0.8KB/帧）、未见平台；DNxHR HQX 同样线性（307.3→368.0MB/14 会话）；句柄、显存恒定；每会话只解 400 帧时不增长 → 残留按解码帧数累积、与会话开关次数无关；3.1 记录硬解 H.264 无此趋势。
- 根因：软解画面的上传复制（`platform/windows/convert.rs` `copy_planes` 与 NV12 上传两处）每帧用 `std::thread::scope` 新建 4 个线程，4K60 每秒约 240 次建/销线程；Windows 上每个新线程都让进程内已加载的 DLL（显卡驱动等）收到线程挂接，按线程分配而不随线程退出完全释放的内存随帧数累积。硬解路径不走这段复制，故无趋势。
- 选型：依赖树里原无 rayon/crossbeam；比较“引入 rayon 固定线程池（scope 分发，借用安全，工作窃取应对多路并发）”与“自写 4 线程池（约 50 行、需自管 unsafe 指针与完成等待）”，按成熟开源优先采用 rayon 1.12（新增 rayon、rayon-core、crossbeam-deque/epoch/utils、either，均 MIT/Apache-2.0；第三方许可清单由 `gen:licenses`（bundle 时）自动纳入，`resources/licenses/` 为生成物不入库）。
- 修复：`Cargo.toml` Windows 依赖加 `rayon = "1"`；`convert.rs` 新增进程内常驻 4 线程池 `copy_pool()`（`ThreadPoolBuilder`，线程名 upload-copy-N，建池失败退回当前线程顺序复制）与 `run_copies()`（`pool.scope` 分发并等待全部完成），两处每帧建线程改为它；`SendPtr` 加 `get()` 使闭包整体捕获。新增 Rust 单测 `upload_copies_run_on_resident_threads_and_match_a_direct_copy`（9MB 三平面并行复制与直接复制逐字节一致；200 次×4 任务只用到常驻的 ≤4 个线程）；断牙：`run_copies` 临时改回每次 `std::thread::scope` 时该用例失败，恢复后通过。`node scripts/video-decoder-ffmpeg.cjs test` 61 项通过；`build:video-decoder`（release）15 秒。
- 改后同协议对照（release）：ProRes 422 HQ 12 会话×6000 帧，私有提交第 1→11 会话 299.8→298.8MB（改前同区间 308.7→353.8MB），句柄 562–570 恒定；DNxHR HQX 12 会话×6000 帧 298.6→299.1MB（改前 307.3→354.7MB）。性能不退：单路 4K ProRes 422 HQ 软解不限速吞吐（6 会话×2000 帧，取第 1–5 会话）改前上传 4.4–4.7ms/帧、160–167 帧/秒 → 改后 3.7–3.9ms/帧、174–188 帧/秒；渲染提交 0.17→0.15ms。
