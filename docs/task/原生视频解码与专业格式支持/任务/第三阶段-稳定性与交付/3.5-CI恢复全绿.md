1. 用 `gh run view <id> --log-failed` 列全部失败用例；按“首次失败的提交”二分定位引入点。
2. 按根因修（产品缺陷修产品；测试与平台/换行符相关就让测试与平台无关），不删用例、不放宽断言。
3. 本地复现 CI 条件（必要时在 WSL/Linux 路径语义下跑相关测试，或用 path.posix 构造用例）。

同期其他门禁的历史失败（颜色令牌、ESLint 渲染层、原生 SQLite 清单、测试分层完整性）在 `37098094038` 前已被后续提交修好，HEAD 运行中这些步骤均通过。

**根因与修复**：

1. 音频波形两组（13 项）——测试写死 Windows 盘符路径。`D:/source.wav`、`D:/allowed/source.wav` 在 Linux 上 `path.isAbsolute` 为假，被实现正确地当成“非本地素材”拒绝，后续断言全部落空。产品实现没有问题（Linux 的本地素材本来就是 `/` 开头）。修复：两个测试改用 `path.resolve(path.sep, …)` 构造宿主平台的绝对路径，断言内容不变。
2. `assetLibrarySchema`——不是换行符问题。`7dfeccb9` 把代码资产 `code` 加进 `assets.media_type` 约束（旧库由 `upgradeAssetSources` 补齐），这条读源码的断言没有同步，Windows 与 Linux 都失败；断言是单行子串，与 CRLF 无关。修复：断言改为当前约束 `('image', 'video', 'audio', 'code')`。
3. `ffmpeg-loader`——实现缺陷。`unifiedFfmpegDirectory` 只服务 Windows（上下文 `platform: 'win32'`），但拼接与绝对路径判定用的是宿主 `path`；在 Linux 上执行时 `C:/evil/bin` 不算绝对路径，越界保护失效。修复：该函数与 `unifiedMediaBinaryPath` 改用 `path.win32`，测试期望同步改用 `path.win32.join`。Windows 上 `path === path.win32`，运行行为不变。
4. `video-decoder/paths`——开发诊断覆盖读取真实环境变量与文件系统，按宿主判定绝对路径是正确的；测试写死 `D:` 路径导致 Linux 下判为相对路径。修复：测试改用宿主绝对路径。同文件的 `videoDecoderExecutableCandidates` 与第 3 条同源（Windows 专用上下文却用宿主 `path`，目前只因测试同样用宿主 `path` 而碰巧通过），一并改用 `path.win32`，测试期望同步。

**同类排查**：

- 注入 `platform` 上下文的实现：全仓只有 `ffmpeg-loader.ts`、`video-decoder/paths.ts`、`logging/diagnostic-bundle.ts`，后者只记录平台名，不拼路径。
- 写死盘符路径的测试：CI Linux 全量单测中只有上述文件失败；其余带盘符的测试不经过宿主绝对路径判定。
- 读源码比对的测试（换行符）：本机 Windows（`core.autocrlf=true`，存在 CRLF/LF 混合检出）全量单测中没有任何读源码断言失败，没有发现对换行符敏感的断言。
