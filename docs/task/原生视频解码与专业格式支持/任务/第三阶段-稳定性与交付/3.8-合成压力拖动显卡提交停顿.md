# 3.8 合成压力拖动显卡提交停顿（额外任务）

[返回总览](../../00-任务总览.md) · [实施方案](../../01-实施方案.md) · [重要记录](../../重要记录.md)

## 任务状态

- 状态：已完成
- 所属阶段：第三阶段-稳定性与交付
- 前置任务：3.2（首次记录）

- 是否可以并行：需要 Electron，按全局串行调度

## 任务目标

`video-edit-composite-pressure` 拖动在第 124–127 帧附近稳定出现一次 130–185ms 的显卡提交停顿（解码 0ms），拖动帧率 56.8–58.0 次/秒，贴近或低于 58 的门槛。3.2 时 57.99/58.03，界面 3.5 验收时 56.81/57.46/57.75，用 HEAD 版本对照同样 57.72/57.80，说明与界面改动无关。查清停顿根因（着色器/管线首次编译、纹理或缓冲首次分配、合成层数跨过某阈值、Chromium 呈现等），按根因修复，使拖动稳定 ≥58 次/秒且无 >100ms 停顿。

## 执行步骤

1. 用 Chromium tracing / GPU 进程 trace 与渲染器内计时定位第 127 帧附近的停顿来源；对照不同片段数、不同合成层组合确认触发条件。
2. 按根因修（例如预热管线/着色器、预分配资源、避免在拖动中重建绑定组），不改判据。
3. 复跑 composite-pressure（至少 3 次）与 performance、scrub 回归，确认不退。

## 执行记录

### 2026-10-04 定位与修复（子 Agent）

**一、复现（修复前产物，1440×900，副屏）**

- 拖动 58.10 次/秒，第 124→125 帧一次 130ms 长间隔（GPU 112ms、解码 0、缓存命中 2）；第 125、126 两帧的 `gpuMs` 都在 105–112ms，第 127–130 帧被跳过。与 3.2（124→125）、界面 3.5（127–129）同一位置。
- 拖动范围内（第 0–180 帧）真正参与合成的只有 3 个片段：主画面（源 0s 起）、叠加（源 1s 起，同一文件）、新增的动态代码片段，外加主画面上的代码滤镜。500 片段 / 32 轨不在这一段时间内，与停顿无关。

**二、根因（Chromium trace：GPU 进程 + 渲染进程，`HENJI_COMPOSITE_TRACE=1`）**

1. 拖动到第 120 帧时，叠加层的源时间到 3.0s。原生拖动解码器（`VideoEditNativeSeeker`）按方向预取下一个一秒窗口 [4s, 5s)；此前正向播放只缓存到叠加层源时间 3.98s，窗口未缓存，于是**第一次打开原生“定位”解码会话**并开始解这个窗口。素材关键帧在 0 / 1.35 / 3.833s，窗口要从 3.833s 的关键帧解到 4.0s 才交出第一帧。
2. trace 时间线（相对录制开始；修复前产物）：2084.7ms 第一张原生帧到达 Worker（GPU 进程同时 `OnCreateSharedImagePool`），2087.2ms 渲染器把它快照复制进自有纹理（Dawn D3D12 提交序号 2707）。**这一次提交在显卡上 119.0ms 才完成**；紧随其后的合成提交 2708–2712 完成延迟 93–110ms（平时 0.4–3.6ms）；同一时段 viz 的 `DXGISwapChainImageBacking::Present` 一次 60.6ms。除这次被显卡拖住的 Present 外，整个拖动中没有超过 40ms 的 CPU 任务——停顿在显卡时间线上。
3. 机制：原生服务把帧写进共享纹理后，在 CPU 侧提交（释放键控互斥体 + Flush）就立即发出帧消息，并不等显卡执行完。会话的第一帧背后压着“建硬件解码器 + 从关键帧解到目标”的全部工作（约 110ms）。Chromium 导入这张纹理（ANGLE D3D11 拷贝 + D3D12 等待）时，显卡侧要等原生进程这些工作做完；WebGPU 队列按序执行，**合成器整条队列连同之后的每一帧一起等待**。
4. 对照实验（临时代码，已撤回）：预取窗口的第一帧到达后延迟 250ms 再做快照复制——拖动 59.99 次/秒、无 >50ms 间隔、没有任何慢提交。证明停顿取决于“何时消费”，即消费方在显卡上等生产方的积压，而不是解码器创建或显存换页这类全局停顿。
5. 3.2 记录里“32 轨 500 片段在该帧的一次性 GPU 提交停顿”的归因不准确：触发条件是**拖动中第一次打开原生定位会话 / 窗口需从关键帧解多帧**，与片段数、合成层数无关；只要拖动越过已缓存范围、预取需要新开会话或长距离定位，任何工程都会出现。

**三、修复（原生服务；渲染层与判据不变）**

- 交帧契约改为：会话第一帧、以及交出前已解出（含丢弃）≥3 帧的帧（定位后从关键帧解到目标、长距离续解），**在原生进程里等本设备显卡工作完成后再交出**（D3D11 事件查询，超时 2s 照常交出并记一次警告）。客户端只承担它本来就要等的那一帧，不再让 Chromium 的队列替它等。连续播放（每交出一帧多解一帧）、二倍速、逐帧取帧不等，照常流水。
- 有终点的区间取帧（拖动的一秒解码窗口，含预取）每帧交出前等**上一帧**的显卡工作完成：显卡上始终只压一两帧，CPU 与显卡仍然重叠。三种取舍都实测过：
  - 只等第一帧：窗口后续帧一口气连发，与合成争用显卡，首个快照仍要 33.8ms，拖动最大间隔 48ms；
  - 逐帧等全部完成：最大间隔 21–23ms，但窗口变慢，4k60-scrub 合成源首帧 1851ms（修复前 1565、最终版本 1571 / 1635）；
  - 隔一帧等（落后两帧）：最大间隔 30–39ms，原片头首帧 1575，两项都不如只落后一帧，未采用。
- 无终点区间（导出、预滚的顺序读取）不受影响。
- 计数：会话统计新增 `settles` / `settleUsTotal`（等全部完成）与 `paces` / `paceUsTotal`（窗口内等上一帧）。
- 同源排查：所有原生消费方（拖动窗口、单帧取帧、播放计划的起播与非预接续剪辑点、源监视器、导出顺序读取）都经同一个 `deliver`，一处修复全部覆盖。**浏览器后备路径**（WebCodecs 解码器在 Chromium 自己的设备上）同类积压理论上同样存在，未修、未验证；它只在原生不可用时使用。
