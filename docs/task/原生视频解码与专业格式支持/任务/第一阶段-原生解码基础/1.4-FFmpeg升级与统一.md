## 任务目标

按重要记录 014：Windows 上全项目只保留一份 FFmpeg——BtbN `win64-gpl-shared` 9.0.1（9.0 分支最新维护版，固定版本与 SHA256）。原生解码服务链接其 DLL；主进程所有 FFmpeg CLI 用途（缩略图、波形、压缩、帧导出、探测、硬件编码检测）改用同包的 `ffmpeg.exe`/`ffprobe.exe`。功能与性能不回退，安装包 FFmpeg 体积下降。

## 当前情况（2026-10-02 主控核对）

- 原生解码：`scripts/video-decoder-ffmpeg.cjs` 固定 BtbN `n8.1.2` `win64-lgpl-shared`，下载到 `native/video-decoder/ffmpeg/`；`native/video-decoder/Cargo.toml` `ffmpeg-sys-next =8.1.0`；`platform/windows/` 内手写 `hwcontext_d3d11va` 结构布局（有布局测试）。
- CLI：`electron/main/services/video/ffmpeg-loader.ts` 定位 `ffmpeg-ffprobe-static` 6.1.2（GPL 静态，各 121MB）；`electron-builder.yml` `asarUnpack: node_modules/ffmpeg-ffprobe-static/**`；`prepare:media-binaries` 脚本；`hwaccel.ts` 用 `h264_nvenc` 与 `libx264`，`frame-export.ts` 用 `libx264`；`media-import/probe.ts` 用 ffprobe；波形 `services/audio/ops.ts`。
- `ffmpeg-sys-next` 9.0.0 已发布（2026-08-05）；FFmpeg 9.0 全部 7 个库升大版本（ABI 变化）。

## 实施方案

- 获取脚本改为 9.0.1 GPL 共享包（版本、地址、SHA256 唯一定义处不变）；`Cargo.toml` 升 `ffmpeg-sys-next` 9.0.x，按 9.0 头文件核对并修正手写 D3D11VA 结构与其它 API 变化；必需解码器清单与 `hello` 许可上报更新（gplEnabled=true 为预期）。
- 主进程 FFmpeg CLI 统一从同一目录定位（开发：`native/video-decoder/ffmpeg/.../bin`；打包：3.3 统一放置的位置，路径解析在本任务定好）；Windows 移除对 `ffmpeg-ffprobe-static` 的依赖与 `asarUnpack` 条目（非 Windows 维持现状）。
- 按 AGENTS.md 规则“成熟开源优先”记录本次版本选择依据（9.0 新特性中与剪辑相关的：MP4/MKV 多线程解封装等，执行时以官方 Changelog 核实）。

## 执行记录

### 2026-10-03 完成

**版本选择（重要记录 012、014）**

- BtbN 执行时 9.0 分支已有 9.0.2（2026-09-19 发布 tag），按记录 014“或当时最新维护版”选 `n9.0.2-17-g2a571b6068`，取 9 月月末构建 `autobuild-2026-09-30-13-08`（BtbN 长期保留月末发布；日构建会被清理）。地址、大小、SHA256 见记录 014，哈希与 GitHub 资产摘要一致。
- 官方 Changelog 核实：9.0 大版本条目里没有“MP4/MKV 多线程解封装”，任务里的这条说法不成立；9.0 与剪辑相关的是 Animated WebP 解码、SMPTE 2094-50 元数据、AMF 色彩转换 HDR 等。选 9.0.2 的实际理由是维护分支修复：cfhd 越界与缓冲修复、h264 场编码 colocated/ER 修复、vp9 flush 时释放引用、mov 解封装若干加固、`pthread_frame` 副数据同步、libdav1d 失败泄漏，以及 GPL 构建自带 libx264/x265/libaom/libsvtav1/zimg/libwebp/libplacebo。9.0 删除了旧 NVENC 选项，本项目用的 `-preset p4 -tune hq -rc vbr -cq` 不受影响（已实测）。

**完成内容**

- FFmpeg 获取（`scripts/video-decoder-ffmpeg.cjs`）：改为 9.0.2 GPL 共享包；`ensure` 额外校验包内 `ffmpeg.exe`/`ffprobe.exe`，写入开发定位指针 `native/video-decoder/ffmpeg/current.json`，并删除此前解压的旧版本目录（8.1 LGPL 已清除）；`build` 把服务 DLL、`avfilter`/`avdevice` 与两个 CLI 复制到 `target/<profile>`，并清掉旧主版本 DLL（如 `avcodec-62.dll`）。导出 `ffmpegBinDir`、`ensureFfmpeg` 等供脚本复用。
- 原生服务：`ffmpeg-sys-next =9.0.0`；构建零告警，API 无破坏性变化需要改代码。9.0.0 绑定已由 bindgen 从真实 `hwcontext_d3d11va.h` 生成 `AVD3D11VADeviceContext` 等结构（自带编译期布局断言），按“成熟开源优先”删除 1.3 手写的三个结构，改用绑定声明；头文件与 8.1 逐字节相同。布局测试改为两项：绑定偏移（x64）+ 真实校验——在服务设备上让所链接的 9.0 DLL 初始化 D3D11VA 设备，读回其填入的 `device/device_context/video_device/video_context/lock_ctx` 与本进程从同一设备取得的接口指针逐一相等。`hello` 许可上报改为 GPL 预期（测试断言 `gplEnabled=true`、`nonfreeEnabled=false`、许可以 “GPL version 3” 开头、版本 `n9.0.`、libavcodec 63）；必需解码器清单加 `libvpx-vp9`（1.3 透明 VP9 用）。
- 主进程 CLI 定位（`electron/main/services/video/ffmpeg-loader.ts`，唯一入口，调用方不变）：Windows 开发读 `current.json` 指向的包 `bin`，打包为 `resources/video-decoder/`（与服务同目录，共用 DLL）；指针缺失/越界/损坏时报错并写明修复命令，不回退旧静态包；非 Windows 维持 `ffmpeg-ffprobe-static`。不再静态依赖 `electron`（Node 单元测试与 Worker 可直接用）。
- 打包（`electron-builder.yml`）：`ffmpeg-ffprobe-static` 的 `asarUnpack` 移到 `mac:`；`win:` 排除该包文件，并新增 `extraResources`：`native/video-decoder/target/release` 的服务 exe、全部 FFmpeg DLL、`ffmpeg.exe`、`ffprobe.exe` → `resources/video-decoder/`。electron-builder 对 `files`/`extraResources`/`asarUnpack` 是顶层与平台级拼接（已读 app-builder-lib 26.15.3 `getFileMatchers` 核对）。
- `prepare:media-binaries`（`scripts/ensure-media-binary-permissions.cjs`）：Windows 改为确保统一 FFmpeg 就绪（缺失时下载校验），非 Windows 照旧修复可执行权限。
- 脚本侧：新增 `scripts/lib/mediaBinaries.cjs`（与主进程同一约定），16 个 Reality 场景/基准脚本里的 `require('ffmpeg-ffprobe-static')` 改为它；`video-decode` 与 `video-edit-media-probe` 场景里硬编码的 8.1 路径改为同一定位。
- 同源回归修复（升级暴露）：
  - HDR AVIF 导出（`image-editor-v3/export/hdr-avif-encoder.ts`）：FFmpeg 9.0 的 `zscale` 遇到带 alpha 的输入（`gbrap16le`）会在颜色变换中一并处理 alpha，非不透明像素颜色被改写（精确测试最大误差 57380/65535）。颜色支先 `format=gbrp16le` 去掉 alpha 再进 `zscale`（alpha 本来就单独编码），6.1 与 9.0 结果逐码值相同，测试恢复通过。
  - ffprobe 9.0 的 `-show_entries stream=…` 会同时输出 `stream_groups` 里的同一流，CSV 输出重复：`video-decode` 场景取时间基改读 JSON 顶层 `streams`。主进程与其他场景的 ffprobe 用法均为 JSON 顶层 `streams` 或 packet/frame/format 项，逐处核对未受影响。
  - `hwaccel.ts` 探测缓存版本 2 → 3，使已有用户在换 FFmpeg 后重新探测可用硬件编码器。
- `package.json`、`electron.vite.config.ts` 未改：`ffmpeg-ffprobe-static` 仍是 npm 依赖（macOS 需要；npm 无法按平台跳过第三方依赖），Windows 运行时、打包与脚本已不使用它。
