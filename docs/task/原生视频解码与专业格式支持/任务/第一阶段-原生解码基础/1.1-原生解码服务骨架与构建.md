## 任务目标

得到一个可构建、可由主进程启动并长期驻留的原生解码服务：能打开素材文件并返回准确的流信息（容器、编解码器、尺寸、帧率、时长、位深、色度采样、色彩信息、透明、音频轨），主进程有统一的服务客户端（启动、握手、请求/响应、取消、超时、崩溃重启、日志转入现有结构化日志），开发与打包两种路径都能找到二进制与 FFmpeg 库。

## 当前情况

- 原生程序先例：`native/audio-worker/`（Rust，`Cargo.toml` 依赖 `serde`、`serde_json`、`vst3-host`、`hound`），`package.json` 脚本 `build:audio-worker`（`cargo build --release --manifest-path native/audio-worker/Cargo.toml`），被 `electron:build` 调用；`electron-builder.yml` `extraResources` 打包到 `resources/henji-audio-worker.exe`。
- 客户端先例：`electron/main/services/audio-edit/audio-worker-client.ts` 的 `executablePath()`（打包走 `process.resourcesPath/resources`，开发走 `native/.../target/{release,debug}`），每次命令 spawn 一次、stdio 单行 JSON、超时与取消。原生解码服务需要**长期驻留**，不能沿用一次性模型，但可复用路径解析与协议风格。
- FFmpeg 现状：`ffmpeg-ffprobe-static` 6.1.2 GPL 静态 CLI（`electron/main/services/video/ffmpeg-loader.ts`），不能作为库链接。
- 日志：`docs/rules/logging.md` 规定统一结构化日志，禁止另建日志文件或查看器。

## 实施方案

按重要记录 004 的建议新建 `native/video-decoder`（Rust）：二进制启动后通过 stdio 交换长度前缀的 JSON 控制消息（大数据不走控制通道）；本任务只实现 `hello`（版本、FFmpeg 版本与已启用解码器列表、D3D11 设备信息）、`probe`（libavformat 打开文件读取流信息）、`shutdown`。FFmpeg 以记录 003 确认的 LGPL 共享库动态链接，开发时从仓库约定位置（待确认，例如 `native/video-decoder/ffmpeg/`，不入 Git 的需写获取脚本）加载。主进程新增服务模块管理单实例生命周期，暴露 Promise 接口给后续任务。

## 执行步骤

1. 确认记录 003、004（许可、语言、FFmpeg 获取方式），把结论写回 `重要记录.md`。
2. 新建 `native/video-decoder/` crate：stdio 消息循环、`hello`、`probe`、`shutdown`；stderr 输出单行结构化日志（级别、事件名、上下文）。
3. 编写 FFmpeg 获取/定位脚本（`scripts/` 下，开发与 CI 共用），记录版本与校验和；构建脚本 `build:video-decoder` 加入 `package.json`，并接入 `electron:bundle`/`electron:build`（参照 `build:audio-worker`）。
4. 主进程新增 `electron/main/services/video-decoder/`：二进制与库路径解析（开发/打包）、单实例启动与握手、请求 ID 与超时、取消、退出检测与有限次自动重启、stderr 日志转入现有 logger。
5. `probe` 用以下样本逐一验证：原片头 H.264 4K60、Tripo NVENC H.264（yuvj420p）、`node_modules/.cache/native-decode/` 中 HEVC 10 位、AV1、ProRes 422 HQ、DNxHR HQX，以及 Tripo `010_荷花_高细节_独立透明缓转_v2.mov`（ProRes 4444 透明）；生成 MXF（DNxHR）与 MPEG-2 样本补充。样本缺失时用随包 FFmpeg CLI 生成到 `node_modules/.cache/native-decode/`。
6. Rust 单元测试（消息编解码、probe 字段映射）+ 主进程客户端精确测试（启动失败、超时、崩溃重启、并发请求）。

**遗留问题**

- 真实 Electron 进程内的日志 JSONL 回读未做：服务尚无调用方；日志内容已用正式客户端与真实二进制验证，2.1 接入调用方后随正式场景确认。
- 打包路径（`resources/video-decoder/`）只在客户端约定，`electron-builder.yml` 未加资源条目，安装包暂不含服务（3.3）。
- 请求超时只取消该请求、不判定进程卡死；主循环无响应的检测（心跳）留给 3.1。

**对后续任务的影响**

- 1.2：D3D11 设备已在服务内按高性能适配器创建（`gpu.rs`，带视频支持），共享纹理与 NT 句柄可直接在其上实现；握手返回适配器 LUID，可用于与 Electron GPU 进程核对是否同一适配器。
- 1.3：ffmpeg-sys-next 8.1 生成的绑定**不含** `libavutil/hwcontext_d3d11va.h`（`AVD3D11VADeviceContext` 等），D3D11VA 共享设备需在 crate 内手写该结构声明或增加专用 bindgen。本机 D3D11 硬解配置见上（h264/hevc main/main10/vp9/av1/mpeg2），ProRes/DNxHR/CineForm 走软解。
- 2.1：`probe` 已返回素材探测所需字段（含位深、色度采样、透明、色彩、HDR 标记、音频轨），可直接用于后端选择；`getVideoDecoderService().probe()` 为 Promise 接口，支持 `AbortSignal` 与超时。
- 3.3：分发需包含 exe 与 avcodec/avformat/avutil/swscale/swresample 五个 DLL（约 109MB）及 LGPL v3 许可文本（BtbN 包内 `LICENSE.txt`）；专利解码器风险按记录 003 届时处理。
