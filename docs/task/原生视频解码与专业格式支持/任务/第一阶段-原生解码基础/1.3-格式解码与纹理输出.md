## 任务目标

原生服务能把真实素材解码为共享纹理：可硬解的编码（H.264、HEVC、AV1、VP9、MPEG-2）走 D3D11VA 硬解，其余（ProRes、DNxHD/DNxHR、CineForm 等）多线程软解后上传；在显卡上转换为重要记录 007 确定的共享格式。提供两种取帧方式：**按时间取单帧**（定位、拖动、导出）与**连续计划取帧**（播放，每文件一个长期解码会话，播放中不 flush）。画面像素与 FFmpeg 参考帧一致。

## 实施方案

- 硬解：libavcodec + D3D11VA，解码器与共享纹理池使用同一 D3D11 设备；解码输出（纹理数组切片）用 `CopySubresourceRegion` 或格式转换着色器写入池纹理，解码表面立即归还。
- 软解：libavcodec 多线程（帧级/片级）；帧数据经可写 D3D11 纹理上传，再由计算着色器按色彩矩阵/范围/位深转换为目标共享格式；不在 CPU 上做 swscale。
- 色彩：读取 `color_primaries`/`trc`/`matrix`/`range`，转换到渲染器约定的 SDR BT.709 空间（HDR 按重要记录 008 处理），并在 `textureInfo.colorSpace` 中如实标注。
- 透明：ProRes 4444、带透明的 VP9/HEVC 等保留预乘约定与渲染器一致（执行时确认渲染器的 `premultipliedAlpha` 约定）。
- 取帧会话：`open(file) → session`；`frameAt(session, ptsUs)`；`schedule(session, ptsList)` 流式产出；`close`。播放会话不 flush，剪辑点从目标关键帧续解；帧内编码直接解目标帧。

## 执行步骤

1. 实现硬解路径（H.264 8 位、HEVC 10 位、AV1、VP9、MPEG-2），输出 nv12/p010le（或记录 007 的替代格式）到纹理池。
2. 实现软解 + 上传 + 计算着色器转换路径（ProRes 422 HQ、ProRes 4444 透明、DNxHR HQX、CineForm、H.264 4:2:2 10 位），输出 rgbaf16/nv16（以记录 007 为准）。
3. 实现按时间取单帧（含 B 帧、开放 GOP、可变帧率的精确规则）与连续计划取帧（不 flush、剪辑点跳转、在途上限、背压）。
4. 像素一致性：对每种样本抽取首帧、关键帧前后、剪辑点、末帧，在 Worker 读回与 `ffmpeg -vf select` 参考帧比较（PSNR 或最大误差，阈值执行时按格式确定并记录）。
5. 性能：每种格式单路 4K60（ProRes 4444 用 2560²）连续计划播放 60 秒，记录送达帧率、帧间隔、原生进程 CPU 核数、显存；按时间随机取帧的冷/热耗时。
6. Rust 单元测试（PTS 换算、计划续解规则、池回收）与协议精确测试。

## 执行记录

### 设计（实现前，2026-10-02）

只读调研段：读了 1.1/1.2 全部原生、主进程、preload、平台、Worker 代码与浏览器解码参照（`videoEditPlaybackDecoder.ts`、`videoEditSeekDecoder.ts`、2.1 新增的 `videoEditFrameSource.ts`），核对了 BtbN 8.1 头文件与样本时间戳；未改源码、未在仓库内构建。

**调研结论（一手证据）**

- D3D11VA 可用：BtbN 8.1 自带 ffmpeg.exe `-hwaccel d3d11va -hwaccel_output_format d3d11` 解码到显卡帧：原片头 H.264 4K60 259 帧/秒、HEVC Main10 4K60 约 470、AV1 4K60 364、MPEG-2 1080 正常；ProRes/DNxHR/CineForm 无硬解配置，走软解。
- `hwcontext_d3d11va.h`（8.1）`AVD3D11VADeviceContext` 比旧版多两个字段：`device, device_context, video_device, video_context, lock, unlock, lock_ctx, BindFlags, MiscFlags`（x64 共 64 字节）；`lock` 必须**可重入**；释放设备上下文会 Release 传入的 `ID3D11Device`（传入前须 AddRef）。硬件帧 `data[0]` 为 `ID3D11Texture2D*`、`data[1]` 为数组切片号。
- 样本时间戳：H.264/HEVC 有 B 帧（`has_b_frames` 1–2，DTS 负起点）；`h264_aac.mp4` 前段带 `D`（丢弃）标志的负 PTS 包（编辑列表裁切）；`mpeg2.mpg`（MPEG-PS）首帧 PTS 0.533s；HEVC 编码高度 2176、显示 2160；Tripo NVENC 为 `pc` 范围 + `bt470bg` 矩阵、传输/原色未标；ProRes 4444 `yuva444p12le`、传输 `iec61966-2-1`、帧 `alpha_mode=unspecified`。
- mediabunny 时间口径：`microsecondTimestamp = Math.trunc(1e6·(1+ε)·timestamp)`；MP4 `timestamp = (pts − 编辑列表偏移)/timescale`，MPEG-TS 保留原始 PTS（只处理回绕），**都不减起始时间**；按时间取帧 = 呈现时间 ≤ 请求时间的最后一帧（请求换算为时间基刻度时“几乎整数则取整”）。FFmpeg 解封装同样已应用编辑列表，二者对 MP4/MOV/MKV/WebM/TS 一致。
- 渲染器约定：合成管线把视频外部纹理当**非预乘**（`rgb·alpha` 后 `one, one-minus-src-alpha` 混合），与记录 007“alpha 不预乘”一致。`snapshot()` 自有纹理为 `rgba8unorm` 或 `r8+rg8`，且会在 Worker 内 `frame.close()`——这是 2.2 接入时要改的点（记录 002 硬约束），1.3 不动渲染器。
- 2.1 的帧源接口需要三种读法：`schedule(times)`（按请求顺序每个时间恰好一帧或 null）、`clipFrames().frames(start)`（连续帧）、`frameAt(seconds)`，加定位器 `sample(time, direction)`；播放计划由渲染器一次给出窗口内全部时间（含剪辑点）。原生协议按这三种读法设计。
- HLSL 编译：本机 Windows 10 有系统自带 `d3dcompiler_47.dll`（Electron 也随包带一份）与 Windows SDK `fxc.exe`。

**关键技术决定**

1. **会话即流**：沿用 1.2 的流模型（每会话一个共享纹理池、启动闸门、`release_frame` 回收、`stop_stream` 回收句柄与 Flush），新增“解码生产者”替换测试画面生产者。区别：解码流**不丢帧**——无空闲槽位时生产线程阻塞等待释放（同时检查取消），在途上限 = 池大小；不按帧率节拍，按请求驱动。主进程桥、preload、Worker 接收端原样承载，只扩展元数据与请求入口。
2. **输出格式只由像素布局决定**（与硬解/软解无关，硬解失败中途回落软解不换格式）：8 位、4:2:0、YUV、无透明 → `nv12`；其余 → `rgbaf16`（记录 007）。`rgba` 省带宽选项先不启用，实现段多路实测后再定并补记 007。池尺寸按流宽高（`nv12` 取偶数），`visibleRect` 为实际显示尺寸；中途分辨率/布局变化以 `FORMAT_CHANGED` 结束流，由客户端重开。默认池：播放 `nv12` 8 张、`rgbaf16` 6 张；单帧会话 3 张。
3. **四条显卡写入路径**（全部在原生进程、同一 D3D11 设备）：
   - A 硬解 8 位 4:2:0：解码表面数组切片 `CopySubresourceRegion`（box 取显示区域）→ 共享 `nv12` 槽位；复制命令下发后立即 `av_frame_unref` 归还表面（同一立即上下文，GPU 按序执行，无需额外同步）。
   - B 硬解 10 位 4:2:0（HEVC Main10、VP9 Profile 2、AV1 10 位）：切片复制到一张独立 P010 中间纹理（带 SRV，Y 用 `R16_UNORM`、UV 用 `R16G16_UNORM` 视图）→ 计算着色器 → 共享 `rgbaf16`。不在解码器数组上开 SRV（避免驱动对 DECODER|SHADER_RESOURCE 组合的兼容差异，额外一次显存内复制约 25MB，可忽略）。
   - C 软解 8 位 4:2:0 无透明（MPEG-2/H.264 软解回落、libdav1d 8 位等）：CPU 把 U/V 交错成 NV12 写入 STAGING 环（3 张，`MAP_FLAG_DO_NOT_WAIT` 轮转）→ `CopyResource` 到共享 `nv12` 槽位（1.2 已验证的上传方式）。
   - D 软解其余（平面 YUV 4:2:2/4:4:4 8–16 位含透明、`gbrp/gbrap` 系 RGB 平面如 CineForm、10 位 4:2:0 软解）：各平面原样写入一个 DYNAMIC `ByteAddressBuffer`（`WRITE_DISCARD`，按 FFmpeg 行距整块复制）→ 通用计算着色器按格式描述常量（每样本字节数、平面偏移/行距、色度下采样、位深、范围、矩阵、透明）转换 → 共享 `rgbaf16`（UAV 写入；池纹理加 `BIND_UNORDERED_ACCESS`，驱动不允许时改写中间纹理再 `CopyResource`）。
   - 罕见打包格式（如 `uyvy422`、调色板）不进主路径：CPU `swscale` 转 `yuva444p16le`/`yuv444p16le` 后走 D，并记 `decode.cpu_convert_fallback` 警告（见待决定事项 3）。
4. **D3D11VA 接入**：在 crate 内手写 `#[repr(C)]` 的 `AVD3D11VADeviceContext`/`AVD3D11VAFramesContext`/`AVD3D11FrameDescriptor`（新文件 `d3d11va.rs`），用 `offset_of!`/`size_of` 单元测试固定 8.1 布局（升级 FFmpeg 时必查）；不加专用 bindgen。进程内一个共享 `AVHWDeviceContext`（首个硬解会话时惰性创建，`device` 传 AddRef 后的服务设备）；`get_format` 有 `AV_PIX_FMT_D3D11` 且该编解码器/档次在设备上有配置时选硬件，否则选软件格式；`extra_hw_frames` 取小值（表面即用即还）。AV1 硬解用 `av1` 解码器、软解用 `libdav1d`；VP9 带透明（WebM BlockAdditional）用 `libvpx-vp9` 软解，其余 VP9 用 `vp9`（可硬解）。
5. **锁**：把 `GpuDevice.context` 的 `std::sync::Mutex` 换成基于 `ID3D11Multithread::Enter/Leave` 的可重入锁守卫（设备已开启多线程保护），同时作为 FFmpeg 的 `lock/unlock` 回调——FFmpeg 解码调用、1.2 测试流、复制与着色器调度都在同一把锁下，不会交错改动管线状态。大块内存复制不持锁：持锁 `Map` → 释放锁复制 → 再持锁 `Unmap` + `Dispatch`（D3D11 允许映射期间其他线程使用上下文）。键控互斥体仍先于上下文锁获取（沿用 1.2）。
6. **HLSL 运行时编译**：`windows` crate `Win32_Graphics_Direct3D_Fxc` 调系统 `d3dcompiler_47.dll` 的 `D3DCompile`（`cs_5_0`），进程内按入口缓存，HLSL 源码 `include_str!` 入库可审阅；`cargo test` 编译全部入口拦住语法错误。理由：不改构建链（不依赖 SDK `fxc` 路径）、不入库二进制字节码；`d3dcompiler_47` 是 Windows 10 系统组件，无额外分发或许可义务（3.3 无需处理）。首次编译耗时实现段实测，若 >100ms 改为服务启动后后台预编译。
7. **色彩**：矩阵/范围/位深取 `AVFrame`（缺省回落 codecpar），**未标注时按 WebCodecs 路径的默认补齐**（`completeColorSpace`：bt709 原色/传输/矩阵、有限范围），保证同一文件两条后端解释一致。
   - `nv12`：不在原生侧换算，按文件信息填 `textureInfo.colorSpace`（矩阵 bt709/bt470bg/smpte170m/bt2020-ncl…、范围 limited/full），由 Chromium 换算（Tripo NVENC 的 `pc` + `bt470bg` 走这里，需实测验证 Chromium 是否尊重）。
   - `rgbaf16`：着色器按矩阵与范围（含 10/12/16 位码值缩放、透明恒为全范围）解出非线性 R'G'B'A，不做传输与色域换算；`matrix: rgb`、`range: full`，原色/传输标注方式见待决定事项 2。
   - HDR（PQ/HLG）按记录 008：矩阵照实（如 bt2020-ncl），传输改标 bt709 不做色调映射，记 `decode.hdr_as_sdr` 警告。
   - 色度上采样（4:2:x → 4:4:4）在着色器内按 `chroma_location` 线性插值（缺省左侧共址）。
8. **透明**：输出非预乘 alpha（与合成管线一致）；帧 `alpha_mode` 为 premultiplied 时着色器内反预乘，unspecified/straight 原样（ProRes 4444 样本为 unspecified）。HEVC 带透明层 FFmpeg 8.1 能否解出未确认，先记为限制。
9. **时间口径（固定规则）**：
   - 帧时间取 `frame->pts`，缺失用 `best_effort_timestamp`，仍缺失按上一帧 + 时长推算并记 `decode.pts_missing`；`ptsUs = trunc(pts·tb.num·1e6 / tb.den)`（i128 整数运算，向零取整），同时返回 `timestampSeconds = pts·num/den`（f64）与 `durationSeconds`（`frame->duration`，缺失用 1/帧率）。
   - **不减起始时间**（与 mediabunny 对 MP4/MOV/MKV/WebM/TS 完全一致）；带丢弃标志的帧（编辑列表前导）由 libavcodec 丢弃，不交付；损坏帧（`AV_FRAME_FLAG_CORRUPT`）不交付。
   - 请求时间 t（秒）→ 刻度 `x = t·den/num`，`|x/round(x) − 1| < 10ε` 取整（mediabunny `roundIfAlmostInteger`）；所选帧 = 呈现时间刻度 ≤ x 的最后一帧；没有则为缺帧（null）。
   - 帧号 `frameIndex` 改为会话内交付序号（诊断用），身份以 `ptsUs` 为准。
10. **取帧语义**：
    - `frame_at`：会话记住解码位置。目标位于当前连续段内且不早于已解出的最后一帧、未越过下一个关键帧时直接向前续解；否则按目标刻度 `av_seek_frame(BACKWARD)` + `avcodec_flush_buffers`（单帧会话允许 flush；FFmpeg+D3D11VA 的 flush 不重建硬件解码器，与 Chromium 的 80ms 问题无关）。向前解到出现呈现时间 > 目标的帧或文件结束，返回最后一个 ≤ 目标的候选。定位后首帧已晚于目标（开放 GOP 前导帧不可解、解封装定位不准）时，以该关键帧之前再定位，最多回退 3 次。帧内编码（ProRes/DNx/CineForm，全关键帧）直接定位到目标帧。
    - `schedule`（播放）：语义与 `scheduledVideoSamples` 相同——按请求顺序每项恰好一帧或缺帧；**整个计划不 flush**。相邻请求向前且目标关键帧不早于已送入的最后一个包时续解；剪辑点（跳到别处）把解封装定位到目标关键帧继续送包，不 flush，开一个新“段”；输出帧按段的待出 PTS 集合认领，旧段延迟输出与开放 GOP 前导帧被丢弃；被新请求取代的帧不交付。计划结束才 drain。
    - `schedule` 区间模式：交付 `[from, to)` 内每一帧（对应 `clipFrames().frames(start)` 与定位器整 GOP 预解）。
    - 同一会话同时只有一个操作：新 `schedule` 取消旧计划（旧计划收到 `schedule_done: cancelled`）；计划进行中收到 `frame_at` 返回 `BUSY`。播放与定位用不同会话（对应浏览器路径的播放泵与定位解码器分离）。
    - 线程：播放会话用帧级多线程（软解线程数按核数取上限，ProRes 4444 约需 6 核），单帧会话用片级多线程（避免帧线程的输出延迟）；硬解由 FFmpeg 单线程驱动。每会话一个生产线程负责解封装、解码、上传与调度。

**协议（控制通道，协议版本升到 3）**

| 命令/事件 | 内容 |
|---|---|
| `open_decoder`（请求） | `{ streamId, path, streamIndex?, purpose: 'playback' \| 'seek', poolSize?, hardware?: 'auto' \| 'off' }` → `{ streamId, format, codedSize, visibleRect, colorSpace, fps, keyedMutex, slots[], decoder: { codec, decoderName, hardware, pixelFormat, bitDepth, chromaSubsampling, hasAlpha, path: 'copy_nv12' \| 'shader_p010' \| 'upload_nv12' \| 'shader_planar' \| 'cpu_fallback' }, timeBase, startSeconds, endSeconds, frameRate, intraOnly, rotationDegrees, setupMs }`。路径规则同 probe（绝对路径、`file:` + 协议白名单）。 |
| `frame_at`（请求） | `{ streamId, time, ticket }` → 命中时先发 `frame` 事件再响应 `{ ticket, found: true, ptsUs, timestampSeconds, durationSeconds, seeked, decodeMs }`；未命中 `{ ticket, found: false }`。 |
| `schedule`（请求） | `{ streamId, scheduleId, times: number[] }` 或 `{ streamId, scheduleId, range: { from, to? } }` → 立即确认 `{ scheduleId, count }`，之后发事件。`times` 长度上限 20 万（单条消息 16MB 内）。 |
| `cancel_schedule`（请求） | `{ streamId, scheduleId }` → `{ cancelled }`。 |

**风险**

- Chromium 对 `nv12` 的非 bt709 矩阵/全范围标注是否照办未验证；不照办时该类素材改走 D 路径输出 `rgbaf16`（代价显存与转换）。
- 传输特性标注影响 Chromium 的换算，`nv12` 与 `rgbaf16` 两类输出可能出现系统性色差；以第 0 步实验定标注规则。
- 软解专业格式每帧上传 33–52MB：单线程复制可能成为瓶颈，计划按平面并行复制；ProRes 4444 2560² 约 6 核软解 + 约 3GB/s 上传，单路可能达不到 59 帧/秒，如实记录边界（验收已允许）。
- `rgbaf16` 对 12 位素材在接近白处精度略低于 12 位（f16 尾数 10 位）；`snapshot()` 当前落成 8 位自有纹理，高位深在合成阶段的保留属 2.2/3.2。
- 隔行素材（MPEG-2 1080i、隔行 DNxHD）不做去隔行，与浏览器路径一致；HEVC 透明层支持未确认。
- 解码线程与多会话叠加可能超订 CPU；3.1 再定全局线程/会话预算。

**待决定事项（需主控或用户确认）**

1. **非零起点容器的时间原点**（影响正在进行的 2.1）：本设计为与浏览器后端一致，原生帧时间不减起始时间。MPEG-PS 样本首帧在 0.533s，若 2.1 的素材时长继续取 `container.durationSeconds`（FFmpeg 的“终点 − 起点”），这类素材开头会空 0.533s、结尾少 0.533s。建议 2.1 对原生探测把时长取为“起点 + 时长”（与 mediabunny `computeDuration` 返回终点时间同义），起点前的空白与浏览器路径读 MPEG-TS 时的行为一致；若希望这类素材从 0 开始，需另加可选字段（如素材起点）由片段默认入点使用（记录 006 允许以可选字段加入），属 2.1/2.2 决定。
2. **`rgbaf16` 的传输特性标注**：记录 007 写的是“按 sRGB 编码写入、传输标 srgb”（来自测试画面），而本设计倾向 `nv12` 与 `rgbaf16` 都照实标注文件的原色与传输，使两类输出经过 Chromium 的同一换算、与浏览器路径一致。以第 0 步实验为准：若 Chromium 对 bt709 与 srgb 传输的处理不同，按实验结果统一并更新记录 007（属技术细节修正，实验结论写回记录即可，除非与用户既定的 SDR 决定冲突）。
3. **CPU 格式转换回落**：任务要求“不在 CPU 上做 swscale”；本设计只对罕见打包像素格式保留 CPU 转换回落并记警告日志，主路径格式（ProRes/DNx/CineForm/H.264/HEVC/AV1/VP9/MPEG-2）全部显卡转换。如不接受，这类罕见格式直接报“不支持的像素格式”。

**主控决定（2026-10-02，2.1 提交 `d8315ac4` 后）**

1. 时间原点：素材时长已在 2.1 按 mediabunny `computeDuration()` 口径（各音视频流“起点 + 时长”的最大值）落地；不新增素材起点字段；原生 `ptsUs` 不减起始时间，与 mediabunny 一致。
2. `rgbaf16` 传输特性：按本设计在第 0 步实验对比，结论写回重要记录 007。
3. CPU 转换回落：接受，仅限罕见打包像素格式并记警告日志；第 1、2 步所列主流格式一律走显卡路径，性能验收不得依赖回落。
4. 测试样本：允许用随包 FFmpeg CLI（含 GPL 编码器，只生成测试数据、不进产物）生成到 `node_modules/.cache/native-decode/`。

**关键实现与设计偏差**

- 时间口径与取帧规则按设计实现（`timing.rs`、`plan.rs`）；实测补充两条：
  - 无索引容器（MPEG-PS）定位不精确，同一落点重复时加大回退量；只有落在文件第一个关键帧时才接受“关键帧晚于目标”（即目标早于首帧）。
  - 单帧会话里帧内编码用片级多线程（无输出延迟），候选帧是否最终只看下一个包的时间，不再多解一帧（ProRes/DNxHR 冷取帧约减半）；播放会话仍用帧级多线程。
- `rgbaf16` 写入：着色器写会话私有的 UAV 纹理，再在键控互斥体内整体复制到共享槽位（共享池不加 UAV 绑定）。
- 硬解 10 位 4:2:0：解码表面切片复制到 P010 中间纹理再转换（不在解码器数组上开 SRV）；8 位 4:2:0 硬解直接切片复制到 `nv12` 槽位。
- 软解上传：持锁 `Map` → 释放锁按平面分 4 线程复制 → 持锁 `Unmap`/调度/复制到槽位；4K 4:2:2 10 位约 2.3ms、ProRes 4444 2560² 约 4.1ms。（验收修复第 1 轮把 DYNAMIC 上传缓冲改为 STAGING 环，见下）
- 调色板格式按 RGB 走 CPU 回落（转 `gbrap16le`），避免引入矩阵换算。
- 播放计划的剪辑点不 flush；解码器读到文件末尾排空后，再回到前面必须 flush（FFmpeg 的 EOF 状态只能这样复位），单独计为 `eofFlushes`，与播放中的 `flushes` 分开。

**选型比较（重要记录 012：成熟开源优先、效果与性能第一）**

- 格式转换与上传

  | 方案 | 能否覆盖本任务格式 | 效果与性能依据 | 结论 |
  |---|---|---|---|
  | 自研 HLSL 计算着色器（当前） | 全部：硬解 NV12/P010 与软解任意平面/半平面/打包 8–16 位 YUV、RGB、透明（通用格式描述驱动） | 18 个样本对 FFmpeg 参考 PSNR 49–61dB；原生 `nv12` 与浏览器后端逐点相同；显卡侧每帧 0.1–0.3ms；与 D3D11VA、共享纹理池同一设备，无额外跨设备复制 | 保留 |
  | libplacebo | 能做 YUV→RGB 与色彩管理/色调映射 | D3D11 后端要运行时把 GLSL 经 shaderc/SPIRV-Cross 转成 HLSL，新增大体量依赖；它的长项（色调映射、色彩管理、高质量缩放）都超出本计划（HDR 由记录 008 排除；显示色彩由 Chromium 按标注处理）；本任务所需的矩阵换算自研已与参考一致，性能不是瓶颈 | 不引入（主控亦明确本计划不引入）；HDR 另立计划时作首选候选 |
  | FFmpeg `hwupload` / D3D11 滤镜（`scale_d3d11` 等） | 只能上传、处理 D3D11 有对应纹理格式的像素格式（NV12/P010 等），ProRes/DNxHR 的 `yuv422p10`、`yuva444p12` 平面格式没有对应 DXGI 格式，需先在 CPU 用 swscale 转换（多耗 CPU、丢 4:4:4/透明）；还需链接本服务刻意未链接的 libavfilter | 上传本身就是“STAGING + 显卡复制”，本轮已采用同一做法替换自研的 DYNAMIC 上传 | 采用其上传做法；不采用滤镜链 |
  | D3D11 视频处理器（`ID3D11VideoProcessor`） | 输入限 NV12/P010/YUY2/Y210/Y410/AYUV 等打包或半平面格式，不支持平面 4:2:2/4:4:4 与透明；矩阵、范围、色度位置由驱动实现决定 | 只能覆盖硬解路径，而该路径自研着色器每帧约 0.1ms，没有可省的开销 | 不采用 |

- 取帧规则

  | 方案 | 适配本项目的程度 | 结论 |
  |---|---|---|
  | 自研规则（`decode/plan.rs`、`timing.rs`）+ FFmpeg 解封装与解码 | 底层定位、解码都用成熟的 libavformat/libavcodec；自研部分只有“取哪一帧”和“旧段帧认领”，必须与浏览器后端 mediabunny 的帧身份完全一致（工程时间口径不能随后端变），协议级 36/36、Reality 计划 0 错位 0 flush | 保留 |
  | GStreamer / GES | 成熟的非线编框架，但会带来整套管线运行时与它自己的 D3D11 设备和内存管理，要与本服务的共享纹理池互通；时间语义是 segment/running time，与 mediabunny 的包时间戳规则不同，需要再做一层映射；剪辑点“不 flush 续解”与 GStreamer 的 flushing seek 模型冲突；时间线已由剪辑渲染器负责，用不上 GES 的编排能力 | 不采用 |
  | libmpv 等播放器内核 | 面向播放（hr-seek），没有把解码帧交给外部共享纹理池的接口，时间线语义同样不一致 | 不采用 |

- 未达标项与成熟实现的关系：CineForm 4K60 的瓶颈在 FFmpeg 自带 cfhd 解码器本身（同版本 CLI 不做转换也只有约 60 帧/秒），换转换或上传实现无助于此。改用 STAGING 环后原生吞吐的复测留给 3.2。
