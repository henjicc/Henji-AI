## 一、当前项目现状（2026-10-02，基线提交 `301b91a1`）

技术栈：Electron 42.5.0、React 18、TypeScript、WebGPU；mediabunny 1.61.0；`ffmpeg-ffprobe-static` 6.1.2（GPL 静态 CLI）。本机：Windows 10、AMD Ryzen 9 5900X（12 核 24 线程）、RTX 4090。渲染进程 `sandbox: true`、`contextIsolation: true`，preload 通过 `contextBridge` 暴露 `henjiNative`。

## 二、当前问题

1. 格式受 Chromium 限制：ProRes、DNxHD/DNxHR、CineForm、MPEG-2、高规格 H.264（4:2:2/4:4:4/10 位）、MXF 封装等无法导入或播放；透明通道仅 WebM VP8/VP9 可靠。
2. 解码器生命周期不可控：flush 触发 Chromium 在 GPU 主线程同步重建 D3D11 解码器（约 80ms）、解码缓冲池大小由 Chromium 推算；已用解码泵与级别提升绕过，但仍依赖 Chromium 内部行为。
3. 源监视器依赖 `<video>`，专业格式无法播放。

## 三、方案依据（2026-10-02 实测，原型在临时目录，不入库）

| 测试 | 结果 |
|---|---|
| FFmpeg 纯解码（到内存） | H.264 4K60 软解 497fps / NVDEC 250fps；HEVC 10 位 4K60 硬解 123fps；AV1 4K60 硬解 149fps；ProRes 422 HQ 4K60 软解 336fps；DNxHR HQX 10 位 4K60 软解 305fps；ProRes 4444 透明 2560² 软解 148fps。按 60fps 实时折算 CPU：4K 专业格式约 2.5–2.7 核，ProRes 4444 2560² 约 6 核 |
| CPU 拷贝通道（utility 进程 → MessagePort → 页面） | 约 700MB/s 上限：8 位 4:2:0 4K 58.8 帧/秒，10 位 4:2:0 28.5，10 位 4:2:2 22.1，12 位 4:4:4+A 13.9；页面 `writeTexture` 每 12MB 约 9ms。**专业格式 4K60 不可行** |
| 显卡纹理共享（Electron `sharedTexture`，NT 句柄） | 约 4K（3843×2102 bgra，离屏渲染产生）稳定 60 帧/秒，帧间隔 p99 18.8–20.3ms、最大 20.3–32ms；主进程每帧交接 0.6ms，CPU 约 0.05 核 |
| 沙盒 preload | `sandbox: true` + `contextIsolation: true` 的 preload 中 `sharedTexture.setSharedTextureReceiver` 可用 |

`sharedTexture` 可导入格式：`bgra`、`rgba`、`rgbaf16`、`nv12`、`nv16`、`p010le`；Windows 用 NT 句柄（`nv12` 带 keyed mutex）；API 标注为实验性；`importSharedTexture`/`sendSharedTexture` 仅主进程，`sendSharedTexture` 有 1000ms 超时，接收端必须在 preload 注册。

## 四、最终目标

1. 剪辑导入、预览（播放/定位/拖动/反向）、源监视器、混音、导出对下列格式全部可用，并以原生解码为主路径：容器 MP4、MOV、MKV、WebM、MXF（AVI 待确认）；视频 H.264（8/10 位，4:2:0/4:2:2）、HEVC（8/10 位）、AV1、VP9、ProRes（Proxy/LT/422/HQ/4444/4444 XQ，含透明）、DNxHD/DNxHR（含 HQX/444）、CineForm、MPEG-2；音频 AAC、PCM（16/24 位、32 位浮点）、MP3、FLAC、Opus/Vorbis（AC-3 等待确认）。
2. 4K60 专业格式在标准负载下满足 5.1 容差（≥59.0 次实际画面更新/秒、遗漏 ≤1%、最大间隔 ≤100ms、时钟偏差 ≤1%、资源循环增长 ≤15%）。
3. 原生服务不可用或失败时，浏览器能解的格式自动回退到现有路径；不能解的格式给出用户语言提示，不显示错帧。
4. 安装包自带原生解码服务与合规的 FFmpeg 库，干净机器可运行。

## 五、总体方案

```
素材文件 ──► 原生解码服务（独立进程，Rust/FFmpeg，待确认见记录004）
              ├─ 解封装 + 解码：能硬解（D3D11VA）→ 显卡纹理；软解（ProRes/DNxHR…）→ 上传 D3D11 纹理
              ├─ 显卡上转换为可共享格式：8位4:2:0→nv12，8位4:2:2→nv16，10位4:2:0→p010le，其余高位深/4:4:4/透明→rgbaf16
              └─ 共享纹理池（NT 句柄）+ 每帧元数据（时间戳、尺寸、色彩）
                      │ 句柄复制到主进程（DuplicateHandle）+ 控制消息（命名管道/stdio）
主进程 ──► sharedTexture.importSharedTexture → sendSharedTexture(主窗口 frame)
                      │
preload（沙盒）──► setSharedTextureReceiver → getVideoFrame → 经 MessagePort 转交剪辑渲染 Worker
                      │
渲染 Worker ──► VideoSample(VideoFrame) → compositor.snapshot()（现有唯一汇合点）→ 合成/缓存/导出不变
音频 PCM ──► 原生服务 → 主进程 → MessagePort → 渲染 Worker mixAudio（数据量小，走 CPU）
后备 ──► 原生不可用/失败时，同一 FrameSource 接口切回 mediabunny + WebCodecs（现有代码）
```

关键设计：

- **唯一汇合点不变**：新路径交付的仍是 `VideoSample`/`VideoFrame`，`snapshot()` 之后的合成、帧缓存、代码素材、导出全部复用，禁止另建平行渲染器。
- **帧源抽象**：渲染器内顺序播放、预取、定位、连续播放泵统一为“帧源”接口（2.1），原生实现与浏览器实现并存，按素材选择。
- **服务进程模型**：长期驻留（不同于 audio-worker 的一次性 spawn），每个解码流有独立会话；纹理池按流分配并由 `allReferencesReleased` 回收；按帧请求/连续计划两种取帧方式（对应现有定位与连续播放）。
- **精确帧**：以容器 PTS（微秒）为唯一标识，与现有 `clipSourceSeconds`/`microsecondTimestamp` 口径一致；帧内编码格式（ProRes/DNxHR）定位直接解目标帧。
- **工程兼容**：工程文件不记录解码后端（运行时按探测结果选择），旧工程无需迁移（重要记录 006）。

## 六、任务范围与非任务范围

范围（2026-10-02 用户追加 2.5、2.6）：片段链接编辑完善（任意类型链接、联动拆分、取消链接、Alt 单独操作与失步显示）；多声音流素材按 Premiere 方式展开到多条音频轨，片段声道类型（单声道/立体声）与声道映射。

原有范围：原生解码服务（构建、启动、协议、日志）、纹理共享通道、格式解码与纹理输出、素材探测与后端选择、剪辑预览/定位/拖动/反向/源监视器、混音、导出读取侧、故障回退与资源治理、专业格式与性能验收、安装包与许可。

非任务范围：新的导出编码格式（如导出 ProRes/DNxHR，待确认是否另立计划）；RAW 摄影机格式；HDR（PQ/HLG）显示与色调映射（10 位素材按 SDR 处理，待确认）；代理/优化媒体工作流；画布、生成结果等其他工作区的视频播放；macOS 实现（待确认，`sharedTexture` 在 macOS 用 IOSurface，可后续独立规划）；缩略图与波形（已走 FFmpeg CLI，不改）。

## 七、阶段划分与关系

1. **第一阶段 原生解码基础**：1.1 服务骨架 → 1.2 纹理通道（用合成帧验证） → 1.3 真实解码输出纹理。完成后有一个可独立测试的“文件→显卡纹理→剪辑 Worker”链路。
2. **第二阶段 接入剪辑引擎**：2.1 帧源抽象与探测（只依赖 1.1，可与 1.2/1.3 并行）；2.2 预览接入与 2.3 音频接入可并行；2.4 导出最后接入。
3. **第三阶段 稳定性与交付**：3.1 回退与资源治理 → 3.2 全面验收；3.3 打包与许可可在 1.3 后提前启动、与第二阶段并行，3.1 后收尾。

## 八、新旧实现兼容与回退原则

- 现有浏览器路径代码（`videoEditRenderer.ts` 的 mediabunny 分支、`videoEditPlaybackDecoder.ts`、`videoEditSeekDecoder.ts`）移到帧源接口后**保留**作为后备，不删除；任何任务都不得让后备路径失效。
- 后端选择顺序：原生可用且探测成功 → 原生；否则若浏览器可解 → 浏览器；否则提示无法解码（用户语言，指明格式）。
- 运行中原生失败（进程退出、设备丢失、超时）：当前会话内对浏览器可解素材切回浏览器路径并记日志；不可解素材在节目监视器就地提示，不显示错帧（沿用 2026-10-02 渲染失败就地提示机制）。
- 每个任务可独立回退：新增代码通过后端选择接入，回退只需让选择器不选原生。
- 不提供面向用户的后端切换开关（不在正式界面暴露实现状态）；开发诊断可用环境变量强制后端（命名在 2.1 确定）。

## 九、全局开发约束

- 遵守 `AGENTS.md`：IPC 走 `src/platform/*`/`src/commands/*` 与 preload；主进程不 import `components/`；禁止新增独立日志文件/查看器（原生服务日志转入现有结构化日志）；禁止裸 `any`；正式界面不展示内部状态（解码后端、句柄、缓存命中等只进日志/诊断）。
- 原文件原路径读取，不复制、不默认转码；媒体读取权限沿用 `media.allowRoot` 与 `henji-media` 规则（`docs/rules/media-url.md`）。
- 原生服务不得阻塞主进程；CPU 重活在原生进程内多线程完成。
- 性能每个任务同步验证，不留到最后；trace 证据用 `HENJI_PERF_TRACE*`。
- 改 `electron/main/**`、`electron/preload/**` 先读 `docs/rules/electron-desktop.md`；改渲染引擎先读 `docs/rules/architecture.md`、`docs/rules/media-url.md`；收尾按 `docs/rules/testing.md` 裁剪验证。
- 自动化验收静音、放副屏；`electron:bundle` 后再跑 Reality；不对用户开发实例静音。

## 十、风险控制

| 风险 | 控制方式 |
|---|---|
| `sharedTexture` 为实验性 API，Electron 升级可能变化 | 封装在主进程单一模块；1.2 写协议级测试；升级 Electron 时作为必测项；失败自动回退浏览器路径 |
| VideoFrame 从 preload（隔离世界）转交渲染 Worker 不可行 | 1.2 首步验证；备选：preload 内用 OffscreenCanvas/WebGPU 先拷贝再转交（需评估开销） |
| `rgbaf16`/`p010le`/`nv16` 帧在 WebGPU `importExternalTexture` 中不受支持或色彩错误 | 1.2 逐格式像素校验；不支持的格式在原生侧统一转 `rgbaf16` 或 `rgba` |
| 多图层多流并发（如 9 路 4K）超出单通道交接能力或显存 | 1.2 做多流基准；3.1 设流数与显存总预算、超限明确提示 |
| FFmpeg 链接许可 | 1.1 开始前确认（重要记录 003）；分发前 3.3 复核 |
| 专业格式软解占用 CPU 高（ProRes 4444 约 6 核/路） | 3.2 记录每格式每路 CPU；超限给出明确边界，不降预览分辨率冒充达标 |
| 原生服务崩溃影响剪辑 | 独立进程隔离；3.1 自动重启与回退 |

## 十一、最终验收条件

- 四中所列格式（以 3.2 实际矩阵为准）在剪辑中可导入、预览、定位、源监视、混音、导出；预览与导出逐帧 PSNR 达到现有闭环场景标准（>24dB，实际以 3.2 记录为准）。
- 标准 4K60 负载（原片头 + 至少 ProRes 422 HQ、DNxHR HQX 两种专业格式）满足 5.1 容差；ProRes 4444 透明素材有明确实测边界。
- 原生不可用、进程崩溃、单文件失败三类故障均验证回退或就地提示。
- 现有剪辑 Reality 回归（engine-probe、scrub、monitor、composite-pressure、code-project、popout、performance 等）全部通过。
- 干净 Windows 机器安装包可运行；许可文件随包分发。

## 十二、执行规则

开始前：读 `00-任务总览.md`、本文件、当前任务文件及前置任务执行记录；核对计划与当前代码是否一致；把任务状态改为“进行中”。

执行中：只做当前任务范围；计划与实际不符先更新任务文件；新依赖/风险/关联任务及时记录；不重新编号；整体方案变化同步本文件；重要决定变化同步 `重要记录.md`。

完成后：按任务验收标准验证；填写执行记录（实际改动、验证结果、遗留问题、偏差、对后续影响、提交）；通过后“已完成”，未充分验证为“待验证”；同步总览；检查后续任务；独立 Git 提交（`<type>(范围): 中文描述`）。

阻塞时：状态改“已阻塞”，记录原因、解除条件、受影响任务与替代方案。
