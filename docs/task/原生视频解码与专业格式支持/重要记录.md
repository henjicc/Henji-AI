## 记录 001：原生解码为主路径，浏览器解码为后备

- 日期：2026-10-02
- 状态：已确定
- 背景：剪辑工作区只能解码 Chromium 支持的格式，且解码器行为受 Chromium 内部限制；用户计划把剪辑发展为专业工具，需要支持 ProRes、DNxHR 等专业格式。
- 最终决定：用户确认“全面转向原生，浏览器路径做备份”。原生解码服务负责所有格式；mediabunny + WebCodecs 现有实现保留在同一帧源接口下作为后备，不删除。
- 选择原因：原生（FFmpeg）格式覆盖最全，解码器生命周期、缓冲、定位完全自控；浏览器路径已调优且同为零拷贝硬解，作为后备可抵御实验性 API 变化与个别机器的显卡互通失败。
- 影响任务：全部。

## 记录 002：画面传输只走显卡纹理零拷贝

- 日期：2026-10-02
- 状态：已确定
- 背景：原型实测 utility 进程经 MessagePort 向页面传送原始帧上限约 700MB/s，10 位 4:2:2 4K 仅 22 帧/秒、12 位 4:4:4+A 2560² 仅 14 帧/秒，页面 `writeTexture` 每 12MB 约 9ms；而 `sharedTexture` 零拷贝传送约 4K 纹理稳定 60 帧/秒、主进程每帧 0.6ms。
- 最终决定：原生解码的画面在原生进程内放到 D3D11 共享纹理，经 NT 句柄 → 主进程 `importSharedTexture` → `sendSharedTexture` → 沙盒 preload 接收 → 渲染 Worker，全程不经 CPU 拷贝像素。仅音频 PCM 走 CPU 消息通道。
- 选择原因：只有零拷贝能满足专业格式 4K60 全分辨率；CPU 通道即使改为进程内 libav 也无法绕过进程间与 `writeTexture` 的带宽限制。
- 1.2 实测补充（2026-10-02，Electron 42.5、RTX 4090）：
  - 转交方式成立：沙盒 preload 收到帧后 `getVideoFrame()`，经自建 `MessageChannel`（端口用 window message 交给页面，页面再 transfer 给 Worker）把 VideoFrame transfer 到渲染 Worker，Worker 内 `importExternalTexture` 正常，不需要风险表里“preload 先拷贝再转交”的备选。
  - **硬约束：共享纹理 VideoFrame 只能在渲染进程主线程关闭。** 在 Worker 里 `close()` 会让整个渲染进程以 STATUS_BREAKPOINT 崩溃（Electron 释放回调的线程检查）。因此 Worker 用完把帧原样交回同一端口，由 preload 关闭；交回推迟到 GPU 已提交工作完成之后。Worker 被终止时未交回的帧会泄漏到页面卸载。
  - 句柄所有权：原生服务为每个池槽位创建一次 NT 句柄并 `DuplicateHandle` 到主进程，`stop_stream` 时用 `DUPLICATE_CLOSE_SOURCE` 远程关闭；Electron 每次导入自行再复制一份。原生进程崩溃来不及关闭的句柄由主进程记下，交给下一个服务进程关闭。
  - 已知限制：页面重载（同一 frame 不销毁）时页面里在途的帧不再有释放回执，Electron 不会自动回收，这些导入要到窗口销毁才释放（每路至多一个纹理池，实测每次重载遗留 1–3 个）；强行 `subtle.release()` 会使主进程崩溃，不可用。窗口销毁时全部回收（已实测）。
- 影响任务：1.2、1.3、2.2、2.4、3.1。

## 记录 003：FFmpeg 链接与分发许可方式

- 日期：2026-10-02
- 状态：已被记录 014 取代（统一为 FFmpeg 9.0.1 GPL 共享库）
- 背景：项目当前随包分发 `ffmpeg-ffprobe-static` 6.1.2，为 `--enable-gpl` 静态 CLI，以独立子进程调用。原生解码服务需要把 FFmpeg 库（libavformat/libavcodec/libavutil/libswscale）链接进项目自有二进制，许可义务与“调用独立 CLI”不同。
- 最终决定：采纳建议。使用 **LGPL、不含 `--enable-gpl`/`--enable-nonfree` 的共享库（DLL）构建**并动态链接，随包附带许可文本与源码获取方式；ProRes/DNxHR/CineForm/MPEG-2/H.264/HEVC/AV1(dav1d) 等解码器在 LGPL 构建中可用。
  - FFmpeg 来源：GitHub `BtbN/FFmpeg-Builds` 的 `win64-lgpl-shared` 预编译包，固定版本，不使用 latest/master 浮动构建。1.1 选定（2026-10-02）：
    - 版本：FFmpeg 8.1 发布分支 `n8.1.2-50-g1a748fe2cd`（库自报 `n8.1.2-50-g1a748fe2cd-20260831`，libavcodec 62.28.102、libavformat 62.12.102），许可自报 “LGPL version 3 or later”（BtbN LGPL 构建带 `--enable-version3`，无 `--enable-gpl`/`--enable-nonfree`）。BtbN 当时已不再构建 n7.1，只有 n8.1/n9.0；选 8.1 是因为其 Rust 绑定 `ffmpeg-sys-next 8.1.0` 已发布半年以上，9.0 绑定刚发布一个月。
    - 下载地址：`https://github.com/BtbN/FFmpeg-Builds/releases/download/autobuild-2026-08-31-13-27/ffmpeg-n8.1.2-50-g1a748fe2cd-win64-lgpl-shared-8.1.zip`（月末构建，BtbN 长期保留月末发布）。
    - 文件：70,835,150 字节，SHA256 `e9712ffbdb03ef71bbab660c75b835bfe698ef6fad0247c76d8d394a39a3db63`。
    - 获取与校验：`scripts/video-decoder-ffmpeg.cjs`（版本、地址、哈希唯一定义处），解压到 `native/video-decoder/ffmpeg/`（不入 Git）；运行时只随服务分发 avcodec/avformat/avutil/swscale/swresample 五个 DLL。
    - 注意：许可为 LGPL **v3**（不是 v2.1），3.3 分发复核时一并确认。
  - 专利授权（HEVC、AAC 等）：本次不处理，开发阶段照常启用解码器；3.3 打包分发时列出涉及专利的解码器并记录风险，由用户届时决定。
  - 是否继续保留现有 GPL CLI 包（`ffmpeg-ffprobe-static`）另行评估，不在本次决定。
- 选择原因：动态链接 LGPL 库对闭源分发义务最小、可替换升级。
- 影响任务：1.1、1.3、3.3。

## 记录 004：原生服务实现语言与形态

- 日期：2026-10-02

## 记录 007：高位深与透明素材的共享格式

- 日期：2026-10-02
- 状态：已确定（1.2 实测）
- 背景：`sharedTexture` 只接受 bgra/rgba/rgbaf16/nv12/nv16/p010le；专业素材常见 10/12 位 4:2:2、4:4:4 与透明通道。
- 实测（1.2，Electron 42.5、Windows 10、RTX 4090，原生服务合成测试画面 → 渲染 Worker WebGPU `importExternalTexture` + 计算着色器读回；3840×2160 与 2560×2560 均测）：
  | 格式 | 结果 |
  |---|---|
  | `nv12` | 可用。BT.709 有限范围色条最大误差 0.0049（约 1.25/255），帧号正确，灰阶 220 级（8 位有限范围应有 219 级），alpha 恒为 1 |
  | `rgba` / `bgra` | 可用。最大误差 0.001，灰阶 256 级，半透明块 alpha 0.502、颜色未预乘 |
  | `rgbaf16` | 可用且精确。误差 0，灰阶 2945 级（4K 行）/2305 级（2560 行），alpha 0.5 原样保留；VideoFrame.format 为 null（WebCodecs 无对应枚举）但不影响导入 |
  | `p010le` | **不可用**。渲染进程 VideoFrame.format 为 null，GPU 进程卡顿约 0.8 秒，随后渲染进程崩溃（STATUS_BREAKPOINT），有无键控互斥体相同 |
  | `nv16` | **不可用**。对应的 `DXGI_FORMAT_P208` 在本机驱动上不能创建为 2D 纹理（CheckFormatSupport 全为否，CreateTexture2D 返回 E_INVALIDARG） |
  - 键控互斥体：四种可用格式带 `SHARED_KEYEDMUTEX` 与不带（改用事件查询等写入完成）都能正确导入；带键控互斥体时原生每帧写入约 0.2–0.27ms，事件查询约 0.6–0.95ms，默认使用键控互斥体。
- 最终决定：
  - 8 位 4:2:0（无透明）→ `nv12`（硬解输出可直接复制）。
  - 其余一切（8 位 4:2:2、10/12 位 4:2:0/4:2:2/4:4:4、任何带透明素材，如 HEVC Main10、ProRes、DNxHR HQX、ProRes 4444）→ 按原定规则在原生侧显卡转换为 `rgbaf16`：数值按 sRGB 编码写入、色彩空间传输特性标 `srgb`，alpha 不预乘（传输特性标注已由 1.3 修订为照实标注，见下方补记）。
  - `rgba`/`bgra` 已实测可用（含透明），可作为 8 位非 4:2:0 素材的省带宽选项（4K 每帧 33MB，`rgbaf16` 为 66MB）；是否采用由 1.3 按实测负载决定并在此补记。
  - 不使用 `p010le`、`nv16`；主进程纹理桥默认拒绝这两种格式（诊断复测用 `HENJI_VIDEO_FRAMES_UNSUPPORTED_FORMATS=1` 放行）。Electron 升级后可复测。
- 1.3 补记（2026-10-02，真实素材，场景 `video-decode-native` 的标注实验；Electron 42.5、RTX 4090）：
  - **传输特性标注不影响像素**：同一帧以 `nv12`/`rgbaf16` 输出、`transfer` 标 `bt709` 或 `srgb`，Worker `importExternalTexture` 读回逐点完全相同（H.264、Tripo NVENC、HEVC Main10、ProRes 4444 四个样本）。Chromium 对这些 SDR 传输特性不做换算。
  - 因此修订上文“传输特性标 `srgb`”：**所有输出都照实标注文件的原色与传输特性**（未标注按 WebCodecs 默认补齐为 bt709；PQ/HLG 按记录 008 标 bt709）；`rgbaf16` 的矩阵标 `rgb`、范围 `full`，写入的仍是非线性 R'G'B'，alpha 不预乘。
  - `nv12` 与浏览器后端逐点一致：原片头 H.264 与 Tripo NVENC（`pc` 范围 + `bt470bg` 矩阵）的原生 `nv12` 帧与浏览器后端（mediabunny + WebCodecs）同一帧读回最大误差 0——Chromium 照办 `nv12` 的矩阵与范围标注，同一文件两条后端颜色相同。
  - 原生着色器（`rgbaf16`）与 Chromium（`nv12`）对同一 8 位 4:2:0 帧：PSNR 50–60dB，最大误差 0.03–0.04（色度采样位置不同：原生按文件 `chroma_location`，缺省左侧共址；Chromium 按纹理中心采样）；HEVC Main10 原生对浏览器后端 PSNR 49dB、最大 0.037。
  - `rgba` 省带宽选项不采用：单路 4K60 各专业格式在 `rgbaf16` 下已达 60 帧/秒；多路预算留 3.1。
  - `rgbaf16` 的写入方式：计算着色器写入会话私有的 UAV 纹理，再在键控互斥体内整体复制到共享槽位（共享池纹理不加 UAV 绑定，4K 复制约 0.1ms）。
- 选择原因：只保留实测像素正确且不会崩溃的格式；高位深与透明不丢精度。代价：`rgbaf16` 4K 每帧约 66MB 显存，9 路 4K60 `rgbaf16` 已到边界（见 1.2 执行记录）。
- 影响任务：1.2、1.3、2.2、3.1、3.2。

## 记录 010：多音轨素材按轨道展开与链接编辑（纳入本计划 2.5、2.6）

- 日期：2026-10-02
- 状态：已确定（2026-10-02 用户追加要求纳入本计划：“像专业剪辑软件一样铺到不同轨道上，分单声道和双声道”；链接需支持视频-音频、音频-音频、视频-视频及多条之间，联动剃刀，可取消链接，Alt 单独选中操作；具体做法参照 Premiere Pro）
- 背景：MXF（摄影机/广播常见 2–8 条单声道）、OBS 多轨录制的 MP4/MKV 等素材含多条声音流；目前浏览器后端与 2.3 原生声音会话都只取第一条声音流，其余听不到。用户明确：不能只保留一条，必须处理。
- 主流做法调研：Premiere Pro 默认按文件声道配置（Use File）把每条单声道作为独立音频片段，放到时间线时铺到 A1…An 并与画面链接，可在素材箱用“修改 > 音频声道”改映射（如两条单声道合成立体声）；DaVinci Resolve 用片段属性 > 音频按“格式 + 嵌入声道”映射，每条映射轨在时间线各占一条音频轨；Avid Media Composer 链接时把源声道映射为单声道或立体声对，A1–A8 各自上轨，可在源监视器关掉不需要的轨；Final Cut Pro 在单个片段内以“音频组件”呈现，可设为双单声道/多单声道并展开编辑。共同点：默认不丢弃任何一条，每条声音流（或声道对）是可单独调音量、静音、独奏的独立轨，并保持与画面的链接；声道映射可事后调整。
- 方向：沿用现有链接片段模型（`linkId` + `sourceComponent: 'audio'`），为音频片段增加“源声音流/声道映射”可选字段，素材记录声音流清单；插入时每条声音流生成一个链接音频片段铺到相邻音频轨；后续提供声道映射调整（单声道 ↔ 立体声对）。具体字段、交互与助手能力在后续计划中设计。
- 影响任务：2.3 仍只取第一条声音流但按声音流序号打开会话；2.5 完善链接编辑；2.6 实现多声音流铺轨、声道类型与映射；2.4、3.2 验收时覆盖多轨导出。


## 记录 011：原生显卡代码收拢为平台层；libplacebo 留作 HDR 候选

- 日期：2026-10-02
- 状态：已确定（用户采纳主控建议，并授权此类技术取舍由主控自行决定）
- 背景：用户询问能否用现成工具替代 1.3 的自研部分，以及将来接入 macOS 是否要重写。调研：libplacebo（LGPL，D3D11/Vulkan/OpenGL，含 HDR 色调映射）可替代格式转换着色器；Windows D3D11 视频处理器只覆盖部分硬解格式；GStreamer（含 GES）可整体替代但属换框架；取帧规则（精确定位、连续计划、剪辑点续解）无现成可直接套用的实现。macOS 上 VideoToolbox 可硬解 ProRes/H.264/HEVC 到 IOSurface，Electron `sharedTexture` 在 macOS 用 IOSurface。
- 最终决定：

## 记录 013：为 Log 素材与后续调色准备高位深合成管线；调色色彩管理选 OpenColorIO

- 日期：2026-10-02
- 状态：已确定（用户提出后续要做调色：相机 Log 素材如索尼 S-Log 需套 LUT 还原；主控按记录 012 与用户授权自行决定技术路线）
- 背景：主控核对发现剪辑合成器的唯一汇合点 `videoEditGpuCompositor.ts` `snapshot()` 把所有画面存为 8 位自有纹理（`r8unorm`/`rg8unorm`/`rgba8unorm`），合成目标也是 8 位。原生路径虽按 `rgbaf16` 交付 10/12 位画面，进入合成器即被截断为 8 位；Log 素材拉伸反差时会出现色带，调色无法建立在这条管线上。
- 选型比较：
  - libplacebo（LGPL）：支持 .cube 3D LUT（含四面体插值）、S-Log/V-Log 等传输与色域、HDR 色调映射；但它是自带渲染流程的播放渲染库，只能放在原生解码侧做“入源转换”，无法进入 Chromium 内的 WebGPU 合成器，不能逐片段、带关键帧调色，浏览器后备路径与图片/代码素材也用不上。
  - OpenColorIO 2.x（BSD，影视行业标准）：内置 99 个转换，含 Sony S-Log3/S-Gamut3(.Cine)、ARRI LogC、ACES 等相机 Log 转换；可生成 GLSL/HLSL/MSL 着色器或烘焙 LUT。可在主进程/原生侧把转换烘焙为 3D LUT（+1D 整形曲线）交给 WebGPU 合成器采样，两种解码后端与导出一致。
  - 自研：.cube 解析与 3D LUT 采样（三线性/四面体）在 WGSL 中实现量小，作为 OCIO 烘焙结果与用户 LUT 的统一应用点。
- 最终决定：
  - 本计划新增任务 2.7：合成器对 10 位及以上素材使用 16 位浮点自有纹理与 16 位浮点合成目标（8 位素材保持现有紧凑格式以控制显存与带宽），预览、帧缓存、导出全链路不截断精度；以 4K60 标准负载验证性能，帧缓存预算按新格式重算。
  - 调色（Log 还原、LUT、色彩管理）另立计划：色彩管理用 OpenColorIO 内置相机转换，LUT 应用在 WebGPU 合成器内统一实现；libplacebo 不用于调色，仍保留为 HDR 显示色调映射候选（记录 011）。
- 影响任务：2.2（交付 `rgbaf16` 原生帧时不得在 2.7 前另做 8 位假设以外的改动）、2.7（新增）、2.4（导出精度一致性，依赖 2.7）、3.2。

## 记录 015：H.264/HEVC 在剪辑点 flush（修订 1.3 的「剪辑点不 flush」）

- 日期：2026-10-03
- 状态：已确定（3.1 实测根因，主控确认）
- 背景：1.3 为降低剪辑点延迟，在剪辑点不 flush 解码器。3.1 查明 10 位长 GOP 拖动只有约 52 次/秒的根因：H.264/HEVC 不 flush 时图序号（POC）计算错误，之后整段只输出关键帧；这也是预览时间计划给出空帧/错帧的来源之一。
- 最终决定：H.264、HEVC 在剪辑点先 flush 再送新区间；其他编码（ProRes、DNxHR 等帧内编码）保持不 flush——全部 flush 会让 ProRes 4444 每个剪辑点迟到 1 帧。实测 10 位长 GOP 快速正向拖动 58.5–59.1 次/秒（门槛 57）。
- 影响任务：1.3（设计修订）、3.1、3.2（性能验收沿用此行为）。
