## 记录 001：原生解码为主路径，浏览器解码为后备

- 日期：2026-10-02
- 状态：已确定
- 背景：剪辑工作区只能解码 Chromium 支持的格式，且解码器行为受 Chromium 内部限制；用户计划把剪辑发展为专业工具，需要支持 ProRes、DNxHR 等专业格式。
- 最终决定：用户确认“全面转向原生，浏览器路径做备份”。原生解码服务负责所有格式；mediabunny + WebCodecs 现有实现保留在同一帧源接口下作为后备，不删除。
- 选择原因：原生（FFmpeg）格式覆盖最全，解码器生命周期、缓冲、定位完全自控；浏览器路径已调优且同为零拷贝硬解，作为后备可抵御实验性 API 变化与个别机器的显卡互通失败。
- 影响任务：全部。

## 记录 002：画面传输只走显卡纹理零拷贝

- 日期：2026-10-02
- 状态：已确定
- 背景：原型实测 utility 进程经 MessagePort 向页面传送原始帧上限约 700MB/s，10 位 4:2:2 4K 仅 22 帧/秒、12 位 4:4:4+A 2560² 仅 14 帧/秒，页面 `writeTexture` 每 12MB 约 9ms；而 `sharedTexture` 零拷贝传送约 4K 纹理稳定 60 帧/秒、主进程每帧 0.6ms。
- 最终决定：原生解码的画面在原生进程内放到 D3D11 共享纹理，经 NT 句柄 → 主进程 `importSharedTexture` → `sendSharedTexture` → 沙盒 preload 接收 → 渲染 Worker，全程不经 CPU 拷贝像素。仅音频 PCM 走 CPU 消息通道。
- 选择原因：只有零拷贝能满足专业格式 4K60 全分辨率；CPU 通道即使改为进程内 libav 也无法绕过进程间与 `writeTexture` 的带宽限制。
- 影响任务：1.2、1.3、2.2、2.4、3.1。

## 记录 003：FFmpeg 链接与分发许可方式

- 日期：2026-10-02
- 状态：已确定（2026-10-02 用户确认）
- 背景：项目当前随包分发 `ffmpeg-ffprobe-static` 6.1.2，为 `--enable-gpl` 静态 CLI，以独立子进程调用。原生解码服务需要把 FFmpeg 库（libavformat/libavcodec/libavutil/libswscale）链接进项目自有二进制，许可义务与“调用独立 CLI”不同。
- 最终决定：采纳建议。使用 **LGPL、不含 `--enable-gpl`/`--enable-nonfree` 的共享库（DLL）构建**并动态链接，随包附带许可文本与源码获取方式；ProRes/DNxHR/CineForm/MPEG-2/H.264/HEVC/AV1(dav1d) 等解码器在 LGPL 构建中可用。
  - FFmpeg 来源：GitHub `BtbN/FFmpeg-Builds` 的 `win64-lgpl-shared` 预编译包，固定到一个正式版本（如 n7.1 系列），1.1 选定后在本条记录具体版本、下载地址与文件哈希；不使用 latest/master 浮动构建。
  - 专利授权（HEVC、AAC 等）：本次不处理，开发阶段照常启用解码器；3.3 打包分发时列出涉及专利的解码器并记录风险，由用户届时决定。
  - 是否继续保留现有 GPL CLI 包（`ffmpeg-ffprobe-static`）另行评估，不在本次决定。
- 选择原因：动态链接 LGPL 库对闭源分发义务最小、可替换升级。
- 影响任务：1.1、1.3、3.3。

## 记录 004：原生服务实现语言与形态

- 日期：2026-10-02
- 状态：已确定（2026-10-02 用户确认）
- 背景：仓库已有 Rust 原生程序 `native/audio-worker`（cargo 构建、`extraResources` 打包、stdio JSON 协议），工具链已就绪。原生服务需要 D3D11 设备与共享纹理、FFmpeg 绑定、计算着色器格式转换。
- 最终决定：采纳建议。新建独立 Rust crate `native/video-decoder`（长期驻留进程，不与一次性 audio-worker 合并），D3D11 用 `windows` crate，FFmpeg 用成熟绑定（如 `ffmpeg-sys-next`/`rsmpeg`，1.1 选定并记录版本）；主进程以子进程方式启动，控制面走 stdio 或命名管道，纹理句柄用 `DuplicateHandle` 复制到 Electron 主进程。备选：C++ 原生程序，或 Node 原生模块（不推荐，崩溃会拖垮主进程）。
- 选择原因：沿用现有 Rust 工具链与打包方式；独立进程隔离崩溃；不受渲染沙盒限制。
- 影响任务：1.1、1.2、1.3、3.3。

## 记录 005：平台范围先做 Windows

- 日期：2026-10-02
- 状态：已确定（2026-10-02 用户确认）
- 背景：用户机器为 Windows；`electron-builder.yml` 同时配置了 macOS DMG。`sharedTexture` 在 macOS 使用 IOSurface，原生解码需改用 VideoToolbox/Metal 互通。
- 最终决定：本次只做 Windows，只实现并验收 Windows；macOS 继续使用浏览器后备路径，原生实现另立计划。
- 选择原因：控制范围；Windows 互通链路已实测可行。
- 影响任务：1.1、1.2、1.3、3.3。

## 记录 006：工程文件不记录解码后端

- 日期：2026-10-02
- 状态：已确定
- 背景：同一工程可能在有/无原生服务的环境打开；后端是运行时能力，不是创作内容。
- 最终决定：`.henji-video` 工程与 `VideoEditMedia` 不新增“解码后端”字段，打开时按探测结果选择；素材元数据（尺寸、帧率、时长、是否有音频、透明）沿用现有字段，必要的新字段（如位深、色彩信息）只在 2.1 评估后以可选字段加入，旧工程无需迁移。
- 选择原因：保持工程可移植与旧工程兼容，避免把实现状态写进用户数据。
- 影响任务：2.1、2.2。

## 记录 007：高位深与透明素材的共享格式

- 日期：2026-10-02
- 状态：待确认（1.2 实测后确定）
- 背景：`sharedTexture` 只接受 bgra/rgba/rgbaf16/nv12/nv16/p010le；专业素材常见 10/12 位 4:2:2、4:4:4 与透明通道。
- 最终决定：待确认。建议映射：8 位 4:2:0→`nv12`，8 位 4:2:2→`nv16`，10 位 4:2:0→`p010le`，10/12 位 4:2:2、4:4:4 及任何带透明素材→原生侧显卡转换为 `rgbaf16`（保留精度与透明）。以 1.2 中各格式在 WebGPU `importExternalTexture` 的像素校验结果为准，不支持的统一走 `rgbaf16`。
- 选择原因：不丢精度、不丢透明，且避免 CPU 转换。
- 影响任务：1.2、1.3、2.2。
