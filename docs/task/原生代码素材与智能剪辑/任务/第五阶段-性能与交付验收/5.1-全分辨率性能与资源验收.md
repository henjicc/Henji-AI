## 实施方案

性能从 1.1 开始逐任务验证，本任务汇总并压力复测。先按现有样本建立可重复基线，再增加一个代码生成片段、一个受控效果、音轨及多文件。绝不以 720P 代理或 rAF 计数替代真实视频帧与正确画面。

## 执行步骤

1. 记录机器、驱动、Electron/Chromium、编码/色彩、素材帧率、分辨率和层数；保留原样本与新增负载的结果分别对比。
2. 测冷启动/首次解码、缓存命中随机定位、连续正反拖动、松手定位、参数到正确画面、持续播放及片段边界；记录 P50/P95/P99 和最大帧间隔。
3. 测主/渲染/GPU 进程内存、可获得的显存、各会话缓存及反复切页/浮窗/工程关闭释放；区分进程数据和整机 GPU 数据。
4. 对大量资产、长时间线、多文件、多显示面和代码复杂度逐项加压，建立跨会话总预算、预取优先级和取消规则，按剖析证据修改。
5. 参考 AEPR 编译缓存、纹理复用、拷贝路径和透明处理经验，结合 Henji 现有解码池/迟到隔离优化；只有实测证明必要才研究原生模块。
6. 固定验收负载和数值容差后重测，记录不达标场景及最小后续动作；不通过降低画质或把压力样本移出报告达成通过。

### 2026-10-02 15:30：最大帧间隔根因与方案A落地（用户选择A）

- 根因（Chromium trace实证）：mediabunny `samplesAtTimestamps` 每跨一个关键帧组就 `flush`；Chromium随后重新初始化硬件解码器，首个 `D3D11VideoDecoder::DoDecode` 在GPU主线程（也执行WebGPU）同步重建解码器约83ms，画面停顿。Chromium实验性D3D12解码后端实测同样停顿（100–110ms），换演示库无效（都用同一Chromium解码器），直接删flush会破坏mediabunny的时间标签修正。
- 方案A：新增 `src/features/videoEdit/engine/videoEditPlaybackDecoder.ts`，H.264连续正向播放由每文件一个长期解码器驱动：跨关键帧组持续送包、剪辑点直接从目标关键帧起跑，播放中从不flush；用mediabunny截断后的微秒时间（`microsecondTimestamp`）按Chromium保留的块时间精确对帧，B帧提前输出的画面暂存待领取，任何不能精确对上的帧返回null交回原定位路径（不会给出错帧）。Chromium解码缓冲池=参考帧缓冲+5，4K在5.x级别只有10–11个，长期解码器会在剪辑点耗尽而阻塞GPU主线程；因此把配置与码流内SPS的 `level_idc` 提到允许16帧参考缓冲的最低级别（4K→6.0，1080p→5.1，码流对更高级别同样合规，只改一个字节），缓冲池升至21–22，并限制在途画面≤10、等待交付≤6；消费者等待时始终放行送包，保证不死锁。其他编码仍走mediabunny原路径。

  - 用户Tripo素材（NVENC 4K60 High@5.2，B帧2）标准负载：005夜景108Mbps最大47ms、001全范围yuvj420p 113Mbps最大70ms、014长片2秒GOP最大33.5ms、012低码率三次分别148/34/72ms。
