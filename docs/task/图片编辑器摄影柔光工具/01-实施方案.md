# 图片编辑器摄影柔光工具实施方案

## 当前项目与相关功能现状

### 技术基线

- 桌面框架为 Electron 42.5，Renderer 使用 React 18、TypeScript 和 Vite。
- 项目已安装 Sharp 0.35.2，Electron 主进程已有图片读取、缩放、裁剪、合成和文件保存服务。
- `henji-media://` 已注册为安全、可流式读取且支持 Fetch/CORS 的自定义协议，可供 Renderer 和工作线程读取本地图片。
- 当前只面向 Windows x64 完成首轮性能验收；其他平台行为待后续项目范围确认。

### 图片编辑核心

- `src/core/imageEdit/` 已有 V2 有序操作文档、旧标注文档迁移、操作注册、严格解析和执行端口。
- `image.diffusion`、完整参数结构、默认值、参数校验、非空判断和有序插入已经提交。
- 当前执行端口已支持预览/导出目的、质量、`revision`、取消和能力声明，但仍含旧路线的 `native-gpu`、`native-cpu` 命名。
- `src/core/imageEdit/shaders/diffusion.wgsl` 只是单 Pass 技术基线，尚未实现线性光、六层金字塔、能量重分配和原尺寸分块。
- `src/core/imageEdit/webgpu.ts` 只有 Renderer 能力探针，尚无 Worker 生命周期和设备丢失恢复。

### 编辑器与会话

- `src/features/imageEdit/` 已有共享 `ImageEditor`、顶部标注工具栏、右侧工具轨道、可折叠/缩放参数面板和工具注册表。
- 工具注册表当前只有“几何”；参数面板没有通用图片编辑文档控制器。
- `useImageEditorSession.ts` 已维护整份 `ImageEditDocument` 的撤销/重做栈，但目前只把标注控制器暴露给 UI，尚不能让任意 Inspector 以一次事务修改柔光操作。
- 工具箱、图片查看器、画布编辑工具和智能助手均调用统一的 `exportImageEditDocument()`，具备一次接入、多宿主复用的基础。

### 当前渲染与导出

- `browserImageEditExecution.ts` 只支持朝向、标注和裁剪；发现启用的柔光操作会明确报错，不会静默丢失效果。
- `exportMarkedImage.ts` 使用 DOM Canvas 按原尺寸执行“朝向 → 标注 → 裁剪”，最终返回 Data URL。
- `orientedImage.ts` 和 `drawMarks.ts` 依赖 `document.createElement`、`HTMLCanvasElement`、`CanvasRenderingContext2D`，不能直接在 Worker 中复用。
- Electron Main 已有 `persistImageBinary()`、`saveImageSourceToPath()` 等最小文件保存通道，不需要新增全尺寸像素 IPC。

### 已知基线问题

- 全量 `npx tsc --noEmit` 当前会在未修改的 `src/core/modelCatalog/generationModelDescriptions.test.ts` 报一处既有类型错误。它不属于柔光功能，但如果阻塞最终构建，需要单独确认处理范围。
- 现有着色器注释仍写有 Rust 共用描述，执行后端类型仍含原生后端名称，统一在 2.1 修正。

## 当前存在的问题

1. 没有 WebGPU Worker、纹理池、渲染图和预览 revision 管理。
2. 当前单 Pass 着色器不满足摄影柔光的线性光、多尺度长尾和能量重分配要求。
3. 原尺寸导出仍是 DOM Canvas/Data URL，容易产生大图内存峰值，也无法复用柔光 GPU 结果。
4. 标注光栅化依赖 DOM Canvas，不能在 Worker 中完成正确的操作顺序。
5. 参数面板无法读取和事务式更新任意图片编辑操作。
6. Sharp 虽可高效处理图片，但缺少硬取消，且不适合作为与 WGSL 完全一致的主效果引擎。
7. 通用预设、数据授权边界、Golden 图和性能基准尚未落地。

## 最终目标

建立一个可复用的摄影柔光操作模块，支持黑柔、白柔、辉光三种独立模式和现有完整参数。Renderer 工作线程使用同一份参数配方和 WGSL 完成实时预览与原尺寸导出，主进程只保存编码结果；WebGPU 不可用时由 Sharp 提供降低性能但可用的兼容路径。

完成后，所有现有图片编辑宿主均可保存、恢复、撤销、重做和导出柔光文档；未来独立画布节点只需复用 `image.diffusion`、参数解析和执行端口，不复制算法或 UI 业务逻辑。

## 总体架构

```text
React 参数面板
  → 图片编辑会话与执行端口
  → Web Worker
      → WebGPU 预览：ImageBitmap
      → WebGPU 导出：OffscreenCanvas → 编码 Blob
  → PAL / preload / IPC
      → Electron Main 保存编码字节

WebGPU 不可用或连续恢复失败
  → Electron Main Sharp 小尺寸预览 / 兼容导出
```

### 职责边界

- React 组件只负责参数展示、交互和即时状态，不直接编排 GPU Pass。
- `src/core/imageEdit/` 负责操作 schema、共享参数配方、执行请求/结果和 Worker 消息契约。
- 独立 Worker 模块负责 WebGPU 设备、纹理、Shader、预览和导出任务。
- `src/features/imageEdit/` 负责会话事务、工具注册、Inspector 和预览呈现。
- Electron Main 负责文件系统、编码结果落盘、Sharp 降级和结构化日志。
- IPC 只传路径、文档、任务状态和编码字节，不传全尺寸 Raw Pixel Buffer。

## 核心算法

### 工作空间和源图

- 首版把浏览器解码后的图片视为八位 sRGB 输入，在 WGSL 中解除传递函数，进入 Linear sRGB 代理空间。
- 散射、模糊、能量扣除和混合均在线性空间执行，输出前重新编码到 sRGB。
- 首版不承诺恢复真实场景辐射值，不支持 RAW、HDR 或超过 1.0 的专业场景线性输入。

### 柔光模型

```text
输入线性光
  → 高光响应源
  → 微扩散源
  → 六层归一化高斯混合
  → 从直接光扣除被散射能量
  → 按尺度回填散射光
  → 黑位、雾幕、色彩和细节修正
```

- 高光响应使用 EV 阈值、Soft Knee 和幂曲线，不使用硬阈值。
- 六层半径和权重由统一的 `compileDiffusionRecipe()` 根据图片尺寸、模式、质量和参数生成。
- 每层核权重归一化；最终使用“直接光扣除 + 散射回填”，避免简单 Add/Screen 凭空增加光能。
- 黑柔、白柔、辉光分别使用不同的高光源、微扩散、长尾、黑位保持和散射去饱和响应。
- 归一化半径基于图片空间，屏幕缩放、DPI 和 Inspector 宽度不影响效果。

### 预览路径

- 默认最大 2MP；RTX 4090 实测预热平均 10.13ms、P95 13.2ms，达到最低性能门槛。
- 中间纹理优先使用 `rgba16float`，亮度和掩码使用更小格式。
- 小半径使用可分离 Gaussian 和双线性采样合并；远距离散射在低分辨率金字塔完成。
- 纹理池按尺寸/格式复用，参数依赖决定从哪个 Pass 重新计算。
- UI 只接受最新 `revision`；过期 `ImageBitmap` 必须关闭。

### 原尺寸导出

- 不保留六组全尺寸 FP16 纹理。
- 先建立最长边 2048 的全局散射金字塔，再按 1536 像素 Tile、64 像素 Halo 计算近距扩散和最终合成。
- Tile 与全局散射尺寸允许根据 `maxTextureDimension2D` 和后续设备内存预算自适应降低；首版输出默认 PNG，JPEG/WebP 为显式选择。
- 最终写入 OffscreenCanvas，只编码一次 PNG/JPEG/WebP Blob，再交给 Main 保存。
- 标注和裁剪必须在柔光之后执行，不能通过二次有损编码衔接。

### Sharp 降级

- WebGPU 不可用时，预览采用防抖的小尺寸 Sharp 渲染，不执行 Renderer 全图 CPU 循环。
- 导出使用相同配方的兼容实现，允许在已登记的视觉容差内与 WebGPU 不同，不宣称逐像素一致。
- Sharp 正在执行的 libvips 管线没有可靠硬取消；只能做排队取消、超时、过期结果丢弃和任务结束清理。
- 如果降级无法满足某个专家参数，应明确返回能力信息，不能静默忽略操作。

## 稳定接口与兼容要求

### 图片编辑文档

- `ImageEditDocument.version` 保持 `2`。
- 操作 ID 保持 `image.diffusion`。
- `DiffusionOperationParams.schemaVersion` 首版保持 `1`。
- 旧 V1 标注文档、旧 `markDoc`、未知操作和既有 V2 文档继续可读。
- 旧 `markDoc` 只承载标注兼容影子，不承载柔光参数。
- 操作顺序固定为“朝向 → 柔光/辉光 → 标注 → 裁剪”。

### 执行请求

请求至少包含：

- 图片源；
- 完整图片编辑文档；
- `requestId`、`revision`；
- `preview` 或 `export`；
- `realtime` 或 `high`；
- 预览像素/尺寸上限；
- 导出格式与质量。

结果至少包含：

- 实际执行后端；
- `revision`；
- 尺寸和耗时；
- 预览可显示对象或导出编码结果；
- 降级原因和能力信息。

### Worker 消息

- 消息必须使用可判别联合类型，不使用裸 `any`。
- 支持能力探测、预览、导出、取消、设备丢失、进度和结构化错误。
- Worker 可以在 Pass/Tile 边界取消；连续设备恢复失败后转入 Sharp 降级。

## 任务范围

- 黑柔、白柔、辉光和完整现有参数。
- WebGPU Worker 实时预览与原尺寸导出。
- JPEG、PNG、WebP 输入和八位 sRGB 输出。
- Sharp 兼容降级。
- 编辑器参数面板、历史事务、标注/裁剪合成、文件保存。
- 工具箱、查看器、画布编辑工具、智能助手接入。
- 通用预设、合成测试图、Golden 图、性能与人工验收。
- 未来独立画布节点所需的操作 ID、schema 和执行端口契约。

## 非任务范围

- 任何 Sidecar、子进程、UtilityProcess 或新增原生扩展。
- RAW、EXR、HDR、十六位 PNG/TIFF、ACES、OpenColorIO。
- 复杂实测非对称 PSF、FFT 卷积、品牌/镜头/档位精确复刻。
- AI 高光恢复、端到端风格模型。
- 胶片红色光晕、鬼影、星芒、横向拉丝、颗粒、景深和镜头畸变。
- 正式独立画布节点界面。

## 阶段划分与关系

1. 第一阶段先用真实 Electron 验证 Worker、WebGPU、OffscreenCanvas、编码、内存和 Sharp 降级，不通过门槛不展开完整 UI。
2. 第二阶段根据实测结果冻结公共配方和执行契约，再实现主引擎、导出、取消和降级。
3. 第三阶段可在 2.1 完成后并行开发参数面板，待导出执行器稳定后接入标注合成、保存和多宿主。
4. 第四阶段的预设标定可在 2.2 后与后续接入并行，最终统一执行所有自动和人工验收。

## 风险控制

### WebGPU 可用性

- 真实 Electron 运行时探测 `navigator.gpu`、Adapter、Device、限制和必要格式。
- 监听 `device.lost`，重建设备、Pipeline、Bind Group 和纹理池。
- 连续恢复失败后切换 Sharp，并向 UI 暴露降级状态。

### 显存与系统内存

- 预览限制像素总量，不按原图尺寸渲染。
- 远距散射只保留低分辨率金字塔。
- 原尺寸近距计算分块，避免全尺寸多层 FP16。
- 每次任务结束主动关闭 ImageBitmap、销毁不复用纹理并撤销临时 URL。

### 视觉一致性

- 预览和导出共用参数配方及 WGSL Pass，不分别维护两套效果公式。
- Sharp 只按径向曲线、能量、黑位和感知指标做容差一致，不追求位级一致。
- 使用程序化点光源、阶梯、色块、边缘和真实照片建立 Golden。

### 数据和预设

- 可参考 ProMist-5K 的线性空间和六层 Gaussian 方法。
- 数据集和派生资产只有在授权明确后才能进入仓库。
- 首版预设只称“通用黑柔/白柔/辉光”，不使用真实品牌或声称精确档位复刻。

### 回退原则

- 操作文档保持向后兼容，执行器更换不改文档版本。
- 新执行器失败时保留原图和文档，不覆盖用户文件。
- 柔光执行器不得静默跳过未知或不支持的启用操作。
- 每个任务使用独立提交；出现回归时优先回退当前任务提交。

## 全局开发约束

- 遵守 PAL 边界，业务组件不得直接调用 Electron IPC。
- 新增长耗时、导入导出和可见失败链路必须使用现有结构化日志，覆盖开始、完成、失败。
- 不在 JavaScript 中遍历全尺寸像素。
- 不新增通用 UI Primitive；参数面板复用现有 `Ui*` 控件。
- 参数拖动只生成一次历史事务，不按每个刻度写撤销记录。
- 新文件优先不超过 400 行，禁止新增裸 `any`，导出函数写显式返回类型。
- 正式测试集中在 4.2；前置任务只执行技术门槛和任务完成所必需的最小检查。

## 最终验收条件

- 三种模式具有可稳定辨认的光学差异，且不是同一效果的不同强度。
- 散射在线性代理空间执行，高光无硬阈值断层，图像边缘无黑边。
- 2MP 预览在确认的参考硬件上达到至少 30 FPS，预热后参数到画面 P95 不超过 50ms。
- 24MP 导出不建立六组全尺寸 FP16 纹理；时间和峰值内存达到 1.2 确认的门槛。
- JPEG、PNG、WebP 输入和输出可重新打开，默认 PNG 导出与有损质量策略得到确认。
- 撤销/重做按一次参数事务工作，过期 revision 不覆盖新画面。
- WebGPU 设备丢失、无 GPU、Sharp 降级和取消边界均有明确行为。
- 朝向、柔光、标注、裁剪顺序正确，既有多宿主行为不回归。
- Electron 构建、核心自动测试、Golden、性能记录和用户人工交互验收完成。
