# 2.2 实现多尺度图形处理引擎

## 任务状态

- 状态：待开始
- 所属阶段：第二阶段——核心引擎实现
- 前置任务：2.1
- 关联任务：2.3、3.1、4.1、4.2
- 是否可以并行：可以与 3.1 的参数面板骨架并行

## 任务目标

实现可被预览和导出共同调用的 WebGPU Worker 多尺度柔光引擎，完成线性光、高光/微扩散源、六层 Gaussian 混合、能量重分配、色调与细节修正，并建立可复用的设备、Pipeline、纹理池和依赖缓存。

## 当前情况

- 当前 WGSL 只在一个 Fragment Pass 中进行少量邻域采样和加法，不是最终摄影柔光算法。
- 已有完整用户参数，但尚未转换为六层核和后端统一常量。
- 1.1、1.2 应已提供 Worker、设备能力和分块/编码实测结论。
- 当前没有渲染图、Pipeline 异步编译、纹理池或参数依赖缓存。

## 实施方案

将算法拆成少量可融合的 Pass，统一使用 2.1 的执行配方。预览和导出只改变输入尺寸、Tile 和质量，不改变效果公式。近距层使用可分离 Gaussian；中远距层在降采样金字塔用短核完成。关键中间数据使用 FP16，最终合成使用足够精度避免明显 Banding。

## 执行步骤

1. 实现 sRGB 解码、线性亮度、EV 阈值、Soft Knee、高光源和微扩散源生成。
2. 建立六层降采样金字塔和每层横向/纵向可分离 Gaussian，使用双线性采样合并相邻 tap。
3. 按配方上采样并混合各尺度，确保每层核与总散射权重归一化。
4. 实现直接光扣除、散射回填、雾幕、黑位保持、散射去饱和、色彩扩散和细节保留。
5. 分别实现黑柔、白柔、辉光的源图响应，禁止只通过强度区分。
6. 建立设备管理、异步 Pipeline 编译、Bind Group 缓存、纹理池和任务资源释放。
7. 根据参数依赖决定重建源图、重建金字塔或只执行最终混合，避免每次滑块全部重算。
8. 加入边界处理、透明像素处理和 sRGB 输出编码。
9. 为点光源、阶梯、色块和边缘程序图登记 Golden/数值测试项，统一在 4.2 执行。

## 涉及内容

### 新增文件

- `src/core/imageEdit/webgpu/deviceManager.ts`：设备、丢失恢复和 Pipeline 生命周期。
- `src/core/imageEdit/webgpu/texturePool.ts`：纹理复用和内存预算。
- `src/core/imageEdit/webgpu/diffusionRenderer.ts`：Pass 编排和缓存失效。
- `src/core/imageEdit/webgpu/renderGraph.ts`：如编排复杂度确有需要时新增，避免无必要抽象。
- `src/core/imageEdit/shaders/` 下按职责拆分的 WGSL 文件：颜色、源图、模糊、合成。

### 修改文件

- `src/core/imageEdit/shaders/diffusion.wgsl`：从技术基线迁移或拆分为正式 Pass。
- `src/core/imageEdit/shaders.ts`：集中导出 Shader 源和版本。
- `src/core/imageEdit/worker/imageEditWorker.ts`：接入正式预览执行。
- `src/core/imageEdit/diffusionRecipe.ts`：仅在实现发现契约缺陷时先更新任务记录再修正。

### 可能废弃

- 当前单 Pass `fragment_main` 技术基线，正式多 Pass 完成后替换。

## 验收标准

- [ ] 散射与混合在线性 sRGB 代理空间执行，输出前正确回编码。
- [ ] 六层 Gaussian 半径、权重和能量来源均来自共享配方。
- [ ] 黑柔、白柔、辉光在相同强度下具有可辨认的源图和黑位差异。
- [ ] 预览与导出可调用同一渲染器，不维护第二套公式。
- [ ] 参数依赖缓存、纹理池和 Pipeline 复用已落地，过期任务资源得到释放。
- [ ] 图像边缘和透明区域没有黑边、接缝或明显污染。
- [ ] 没有全尺寸 JavaScript 像素循环、Raw Pixel IPC 或 Sidecar。
- [ ] 应在 4.2 执行的数值、Golden 和性能测试项已登记。
