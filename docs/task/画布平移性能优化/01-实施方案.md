# 画布平移性能优化 · 实施方案

本文件记录相对稳定的整体方案与全局约束。任务进度不写在这里，见 `00-任务总览.md`。

## 一、现状

### 画布渲染链路

- 画布主实现：`src/features/canvas/Canvas.tsx`，基于 `@xyflow/react`（ReactFlow v12）
- 节点类型注册：`src/features/canvas/nodes/index.ts` 的 `nodeTypes` 映射，**共 21 个类型，是唯一注册点**
- 节点面板实现分散在 11 个文件（都含 `rounded-[var(--node-radius)]`）：
  `nodes/shared/GenerationNodeShell.tsx`、`nodes/value/ValueSourceShell.tsx`、`nodes/ImageNode.tsx`、`nodes/UploadNode.tsx`、`nodes/VideoNode.tsx`、`nodes/AudioNode.tsx`、`nodes/StoryboardNode.tsx`、`nodes/StoryboardGenNode.tsx`、`nodes/CameraStageNode.tsx`、`nodes/TextAnnotationNode.tsx`、`nodes/cameraStage/CameraStagePreviewPanel.tsx`
- 画布专属样式：`src/features/canvas/storyboard.css`（**懒加载**，全局变量不能放这里）
- 手势状态：`Canvas.tsx` 的 `handleMoveStart` / `handleMoveEnd` 用 `classList` 在画布包装层直接切 `.canvas-viewport-moving`，不走 React state
- 已有的性能措施：
  - 视口状态只在 `onMoveEnd` 写 store（避免每帧触发全画布选择器）
  - 低倍率内容 LOD：`nodes/shared/useCanvasContentLod.ts`，阈值由设置项 `settingsStore.canvasLodLevel` 控制（off / detail 0.25 / balanced 0.4 / performance 0.6）
  - 媒体微缩略图：`useMicroThumbnail.ts` / `application/microThumbnail.ts`
  - 高密度毛玻璃降级：`hooks/useCanvasGlassPerformance.ts`
  - 连线流动动画在手势期间暂停（`storyboard.css`）
  - `onlyRenderVisibleElements` 已被移除，且不应重新开启（挂载抖动是缩放长任务主源）

### 节点 DOM 结构（以 `GenerationNodeShell` 为例）

`NODE_HEADER_FLOATING_POSITION_CLASS` 定义在 `src/features/canvas/ui/NodeHeader.tsx:51`。

### 实测现状（真实 TEST 项目，31 节点 / 14 种类型 / 26 张真实图片；窗口 2560×1400，DPR 1.5，显示器 60Hz）

| 操作 | 帧率 |
|---|---|
| 原地小幅来回拖 | 60fps（瓦片全在缓存里，测不出问题） |
| 持续朝一个方向拖过新内容 | **30~46fps**，帧间隔 p95 40~60ms |

复制成 124 节点（真实节点 ×4）后现状约 34~51fps。

> **2026-07-29 更新（任务 1.1 交付后，以下为可复现的正式基准）**
> 上面这组数字来自调研期的临时脚本，扫掠速度与路径都不固定，只能作定性参考。
> `npm run electron:pan-bench` 落地后的正式基准（同机、窗口 2560×1439、DPR 1.5、缩放 0.5441、屏幕内 22 个节点）：
>
> | 场景 | 视口内 DOM 元素 | 现状 `off` | 渲染上限 `hidenodes` |
> |---|---|---|---|
> | `TEST` ×1（31 节点） | 2523 | 54.9~57.8 fps | 60.6~60.9 fps |
> | `TEST` ×4（124 节点） | 10077 | **26.9 fps**（p95 53.7ms） | 56.3 fps（p95 29.8ms） |
>
> ×1 与 ×4 的**屏幕内可见节点数相同**（副本是横向单排铺开），所以成本主要随视口内节点总量增长，而不是随屏幕像素量增长——详见 `重要记录.md` 记录 007。
> **判定收益以 ×4 为准**：×1 两次独立运行中位数就能差 2.9fps。

### 瓶颈定位

把节点内容整体隐藏（`.react-flow__node{visibility:hidden}`）→ 立刻回到 58~60fps。
单独去掉阴影、圆角、连线、图片、文字色都几乎没有变化。
**结论：开销全部来自可见节点内容的逐帧重绘，不是 JS、不是图片解码、不是毛玻璃、不是连线动画。**

## 二、已排除的方案（不要重试）

| 方案 | 结果 | 原因 |
|---|---|---|
| `will-change: transform`（视口层） | 31 节点 34.6→38.4，124 节点 34.2→**20.8（更差）**；且拖动中 0.63%~1.9% 像素变化、单点最大差 225/255（肉眼可见发虚） | 合成层光栅倍率被钉死。已用"位移吸附到整设备像素"实验证明与分数像素无关：吸附后仍差 1.68%/226 |
| `will-change: transform`（节点层） | 同样模糊（1.8%/225） | 同上 |
| `translate: 0 0 0`（想借 3D 变换提升合成层） | **空操作**，浏览器把计算值折叠成 `0px` | — |
| `translate: 0 0 0.001px`（节点层，手势期） | 31 节点 33→42，但拖动中连线与节点的叠放顺序改变（连线画到了节点上面），非零外观差异 | 3D 变换创建了新的层叠上下文 |
| `content-visibility: auto`（节点内容层，ComfyUI 的做法） | 31 节点无效果；124 节点 **8.4fps，p95 1197ms（灾难）** | 我们的节点是深层嵌套（约 77 元素/节点），进出屏幕时反复重建渲染子树的代价远超收益 |
| `contain: layout style`（节点根，ComfyUI 的做法） | 无可测量效果 | — |
| `contain: paint`（直接加在 `.react-flow__node`） | 帧率收益最大，但**裁掉浮动标题、端口、resize 手柄** | 节点的绘制内容超出自身盒子 |

## 三、选定方案

**用内层透明扩展框 + 外层节点根形成两级 `contain: paint` 边界，并用 `overflow-clip-margin` 保留出框装饰。**

原理：内层 `CanvasNodePaintFrame` 用透明 padding 和等量负 margin 包住浮动标题、端口、resize 手柄等装饰；外层 `.react-flow__node` 再建立一次绘制隔离，让 Chromium 在视口层录制绘制指令时能跳过整棵离屏节点子树。外层只用不进入盒模型的 `overflow-clip-margin` 扩展裁剪边界，因此 React Flow 的测量尺寸不变。

任务 2.2 正式 A/B（同一次 Electron 启动内交替采样，各 5 次）：

| 场景 | 关闭隔离 `paintdisabled` | 两级隔离 `off` | 隐藏节点上限 `hidenodes` |
|---|---:|---:|---:|
| `TEST` ×1（31 节点） | 53.9fps，p95 26.5ms | **59.1fps，p95 24.6ms** | 61.3fps |
| `TEST` ×4（124 节点） | 23.1fps，p95 63.4ms | **43.8fps，p95 35.2ms** | 53.2fps |

×4 fps 提升 89.6%；>50ms 严重长帧中位数 7 → 0。21/21 节点类型严格 fixture 的像素变化为 0（单通道最大差 1），节点盒、minimap 与连线路径几何一致。结果距离建议的 45fps 线尚差 1.2fps，记录为“显著改善但未达到建议线”；进一步逼近上限需要另行治理单节点 DOM / 绘制复杂度。

### 落地要解决的两个问题

1. **不能用 padding / margin 撑大 `.react-flow__node`**：实测节点盒会从 320×286 变成 368×342，污染 xyflow 的 ResizeObserver。
   → 解决：内层壳承担透明扩展，节点根只用 `overflow-clip-margin` 扩展绘制裁剪边界，不改变盒模型。
2. **模型选择器超框结论是假阳性**：原始探测把滚动容器已经裁掉的后代也算入溢出。任务 2.1 改为计算祖先裁剪交集后，三种选择器的实际可绘制向下溢出均为 0。
   → 解决：不改选择器布局，全部类型统一启用隔离；图片节点与分镜生成节点按真实装饰范围增大下边界。

### 实施点

绘制隔离壳套在 `src/features/canvas/nodes/index.ts` 的 `nodeTypes` 映射上（用一个包装高阶组件统一处理 21 个类型），**不逐个改节点组件**。溢出量作为壳的参数与 CSS 变量，允许按节点类型覆盖。

## 四、阶段划分与关系

```text
第一阶段（可信基准）──┬──> 第二阶段（绘制隔离）──> 第三阶段（收尾沉淀）
  1.1 性能基准脚本    │      2.1 修超框（前置 1.2）
  1.2 外观回归脚本 ───┘      2.2 隔离壳落地（前置 1.1/1.2/2.1）
```

- 第一阶段的两个任务**可以并行**，且都不改动业务代码。
- 第一阶段是硬前置：没有可信基准，第二阶段无法判断收益真假（本次调研已经因此两次得出错误结论）。
- 2.1 需要 1.2 的外观校验能力来确认"修布局"没有改变现有观感。

## 五、全局开发约束

沿用 `CLAUDE.md` 的既有约定，本任务额外强调：

1. **外观逐像素不变是硬约束。** 每次改动后用 1.2 的脚本比对截图，差异需为 0.000%（允许最大单点差 ≤ 2，属于截图舍入）。
2. **不得改变 `.react-flow__node` 的测量尺寸。** 2.2 的验收必须包含改动前后节点 `getBoundingClientRect()` 对比。
3. **样式落点**：画布专属样式写 `src/features/canvas/storyboard.css`；不得在此文件放全局主题变量（该文件是懒加载的）。视觉数值需遵守 `CLAUDE.md` 的登记制。
4. **手势态一律用 `classList` 直接写 DOM**，不引入 React state（避免手势起点多一次渲染）。这一点与参考项目 ComfyUI_frontend 的 `TransformPane.vue` 做法一致。
5. **禁止重新开启 `onlyRenderVisibleElements`**。
6. 测量脚本放 `scripts/`，遵循现有 `scripts/lib/electronLaunch.cjs` 的启动方式；产物目录加入 `.gitignore`。
7. 测量脚本**不得污染用户真实数据**：临时项目用固定前缀命名并在结束时删除；若需改动真实项目的视口，必须在结束时还原（本次调研已发生过一次误改）。

## 六、风险与回退

| 风险 | 应对 |
|---|---|
| `contain: paint` 裁掉某些节点类型的浮层/溢出内容 | 壳按节点类型可配置溢出量；发现问题的类型可单独关闭隔离 |
| xyflow 测量被污染导致 minimap / 框选 / 连线锚点偏移 | 2.2 验收强制对比节点盒尺寸与连线锚点截图 |
| 收益在不同机器/不同缩放倍率下不一致 | 1.1 的基准脚本记录环境信息（窗口尺寸、DPR、刷新率、节点数、可见节点数、缩放倍率） |
| 改动后仍达不到目标帧率 | 方案本身是 CSS 层面的、可一行开关；回退成本极低。若不达标则评估是否立项"减少单节点 DOM 量" |

回退原则：隔离壳提供统一开关（常量或设置项，**待确认是否需要暴露给用户**），关闭后行为与现状完全一致。

## 七、最终验收条件

1. 真实 TEST ×4 连续扫掠平移相对关闭隔离有显著提升；最终为 23.1 → 43.8fps（+89.6%），>50ms 严重长帧中位数 7 → 0。建议的 45fps 线未完全达到，差 1.2fps，后续如需继续提升应另立 DOM / 绘制复杂度治理任务。
2. 改动前后截图逐像素差异为 0.000%。
3. `.react-flow__node` 的测量尺寸不变；minimap、框选、连线锚点、节点拖拽、resize 手柄行为正常。
4. 全部 21 个节点类型逐一确认无裁剪。
5. `npm run lint`、`npx tsc -p tsconfig.electron.json --noEmit`、`npm run check:colors`、`npm run check:surface:strict` 通过。
6. 性能结论已沉淀进项目约定文档，旧压测脚本的局限已被标注或修正。
