## 记录 001：`will-change: transform` 在本项目不可用

- 日期：2026-07-29
- 状态：已确定
- 背景：历史上用 `will-change: transform` 把画布视口提升为合成层来救平移帧率（`a311593`），但拖动过程中文字发虚，于是在 `9c07487` / `51e894f` 中移除。移除后平移顿挫回归。本次需要判断"能否用某种方式保住提升、去掉模糊"。
- 最终决定：**放弃一切基于 `will-change: transform` 的合成层提升**，视口层与节点层都不用。
- 选择原因：
  - 收益本身很小甚至为负：31 节点 34.6→38.4fps，124 节点 34.2→**20.8fps（更差）**。
  - 模糊无法消除。曾假设成因是"合成层落在分数设备像素上被双线性重采样"，做了决定性实验：把视口位移**强制吸附到整设备像素**后与未提升状态对比，仍然差 1.68% 像素 / 单点最大差 226。说明成因是 `will-change` 把合成层的**光栅倍率钉死**——画布常用工作倍率约 0.54，图层按 `0.54 × DPR` 光栅再放大回屏幕，文字必糊。只要画布缩放不等于 1，这个问题就无解。
  - 参考项目 ComfyUI_frontend 用的正是这个手法（`TransformPane.vue`），它靠"停手 256ms 后重新光栅"来掩盖，交互过程中同样是糊的——这正是用户明确拒绝的效果。
- 影响任务：2.2（不得采用）、3.1（写入项目约定防止重蹈）

## 记录 002：`content-visibility: auto` 在本项目是负优化

- 日期：2026-07-29
- 状态：已确定
- 背景：参考项目 ComfyUI_frontend 在节点内容层（`NodeContent.vue`）使用 `content-visibility: auto`，看起来是可直接借鉴的做法。
- 最终决定：**不采用**。
- 选择原因：实测在我们的节点内容层加 `content-visibility: auto`（配 `contain-intrinsic-size: auto none`）后，31 节点无效果，124 节点掉到 **8.4fps、帧间隔 p95 1197ms**。原因是我们的节点是深层嵌套结构（约 77 个 DOM 元素/节点），节点进出屏幕时反复销毁重建渲染子树的代价远超省下的绘制；ComfyUI 的节点结构更扁平、更统一，才吃得到这个收益。同时验证 `contain: layout style`（其节点根做法）对我们没有可测量效果。
- 影响任务：2.2（不得采用）、3.1（写入项目约定）

## 记录 003：选定「扩展绘制框 + `contain: paint`」作为落地方案

- 日期：2026-07-29
- 状态：已确定
- 背景：瓶颈定位为"可见节点内容的逐帧重绘"（把节点内容整体隐藏立刻回到 58~60fps，而单独去掉阴影/圆角/连线/图片/文字色都几乎无变化）。需要一个既有大幅收益、又满足"外观逐像素不变"硬约束的方案。
- 最终决定：统一在 `src/features/canvas/nodes/index.ts` 的 `nodeTypes`（21 个类型的唯一注册点）套透明扩展绘制框，并在 React Flow 节点根用 `overflow-clip-margin` 为 `contain: paint` 保留装饰绘制范围；不逐个改节点面板组件。最终落地采用“内层隔离壳 + 外层节点根隔离”两级边界，详见记录 009。
- 选择原因：实测 124 节点 34~51 → **59.5fps**（渲染上限 59.7），31 节点也有明确提升，且截图**逐像素差异 0.000%、单点最大差 1**。是所有候选中唯一同时满足"大幅收益 + 外观不变"的。
- 已知约束：不能用 padding / margin 直接撑大 `.react-flow__node`——实测会污染 xyflow 的 ResizeObserver 测量，影响 minimap / fitView / 框选。最终通过不改变盒模型的 `overflow-clip-margin` 解决外层装饰裁剪问题。
- 影响任务：2.1（前置条件）、2.2（主实施）、3.1（沉淀）

## 记录 004：画布性能测量方法约定

- 日期：2026-07-29
- 状态：已确定
- 背景：本次调研过程中，因为测量方法有缺陷，**两次得出并推翻了错误结论**：
  1. 按"配置 A → B → C"顺序测，结果第一个配置永远最慢；交替 A/B/A/B 复测后差异消失——那不是配置差异，是冷启动预热。
  2. 扫掠驱动的"松手再抓"没有先发一次 `buttons: 0` 的移动，d3-zoom 把跳变当成继续拖动，视口偏移**指数爆炸到 `1e237`**，画布飞到无穷远，之后几轮"稳定 60fps"实际是在空画布上测的。
- 最终决定：画布性能测量必须同时满足以下四条，否则结论不予采信：
  1. **负载用真实项目节点**（真实图片/视频/各类节点类型），不用占位图 fixture。
  2. **驱动用连续单向扫掠**（不断露出未光栅过的新内容），不用原地小幅来回拖——后者瓦片全命中缓存，稳定 60fps，测不出任何问题。
  3. **同一次启动内交替采样**各配置并取中位数，不按配置顺序逐个测。
  4. **每轮自检**：视口坐标有限、净位移足够、屏幕内可见节点数 ≥ 5，不满足则该轮作废。
- 影响任务：1.1（据此实现基准脚本）、1.2、2.2（据此判定收益）、3.1（标注旧压测脚本局限）

## 记录 007：成本主要随「视口内节点总量」增长，而不是随屏幕像素量增长

- 日期：2026-07-29
- 状态：已确定（来自任务 1.1 的实测）
- 背景：之前只测到「把节点内容整体隐藏就回到 58~60fps」，但没有把「屏幕上的可见像素量」与「视口内的节点总量」这两个变量分开，因此无法判断绘制成本到底跟谁走。
- 实测：任务 1.1 的 fixture 把真实项目**横向单排**复制，屏幕内可见节点数在 ×1 与 ×4 下**完全相同（都是 22 个）**，只有视口内节点总量从 31 变成 124（DOM 元素 2523 → 10077）。结果 `off` 从 54.9fps 掉到 **26.9fps**，而 `hidenodes` 只从 60.9 掉到 56.3。
- 结论：主要成本不在「屏幕上要画多少像素」，而在「整层要生成多大的绘制记录」。光栅只处理可见瓦片，但绘制记录（paint recording）是整层一次性生成的。
- 影响：
  - 这正是 `contain: paint` 起作用的机制——让合成器可以跳过被裁剪掉的子树，因此记录 003 选定的方案方向得到了独立佐证。
  - 也意味着**节点数多但都在屏幕外**的项目同样会卡，2.2 的收益应该在高节点数场景更明显。
  - 测量时 `BENCH_MULT=4` 是判定收益的主场景（单次运行内 4 轮波动仅 1.8fps）；`BENCH_MULT=1` 只作真实项目原样参照，两次独立运行波动达 2.9fps，**3fps 以内的差异在 ×1 下不足以下结论**。
- 影响任务：2.2（收益判定口径）、3.1（沉淀）

## 记录 008：溢出探测必须区分「原始 DOM 几何」与「实际可绘制区域」

- 日期：2026-07-29
- 状态：已确定（来自任务 1.2 的实测）
- 背景：调研期的探测直接遍历节点全部后代并比较 `getBoundingClientRect()`，因此把滚动列表内已被祖先 `overflow` 裁掉的后代、不可见测量节点也算成了绘制溢出，得到模型选择器向下超框 843~1346px 的结论。
- 实测：改为沿祖先链计算 `display` / `visibility` / `opacity` 与 `overflow-x/y` 的可见裁剪交集后，当前真实 `TEST` 中 `imageModelSelectorNode` / `videoModelSelectorNode` 的原始后代几何向下溢出分别为 1378.666 / 1767.334px，但**实际可绘制向下溢出均为 0**；截图也确认列表被节点内滚动容器正常裁剪。
- 决定：后续绘制隔离的扩展框只依据“实际可绘制溢出”，原始几何只作为诊断信息。模型选择器不需要为了假阳性改布局，也不需要跳过 `contain: paint`。
- 附带更正：`src/features/canvas/nodes/index.ts` 实际注册 21 种节点，计划中的“20 种”计数错误；自动报告以 21 种为准。
- 影响任务：2.1（结论 B 的前提被推翻，不改布局）、2.2（选择器可启用隔离壳）、3.1（修正规约数字）

## 记录 009：最终采用两级绘制隔离，几何与像素回归通过

- 日期：2026-07-29
- 状态：已确定（来自任务 2.2 的正式实测）
- 背景：只在节点内容外套透明扩展框虽然不改变 React Flow 测量几何，但正式 ×4 基准仅从 18.1 提升到约 20.6fps，隔离边界仍不足；只在节点根隔离也只能达到约 38~42fps。
- 最终实现：
  - `CanvasNodePaintFrame` 为全部 21 种节点提供统一的内层透明扩展绘制框，默认预留上/右/下/左 36/24/28/24px；图片节点与分镜生成节点按已测装饰范围加大下边界。
  - `.react-flow__node` 同时启用 `contain: paint`，用 `overflow-clip-margin` 扩展裁剪范围，不写入 padding / margin，因此不改变节点盒模型或 xyflow 测量值。
  - 基准与视觉脚本的 `paintdisabled` 会同时关闭内外两级隔离，保证 A/B 对照完整。
- 回归结果：21/21 节点类型严格 fixture 通过；重复截图、隔离开关、拖动画布状态的像素差均为 0 个变化像素（单通道最大差仅 1，属于截图光栅噪声）；节点盒、minimap、边路径几何完全一致。`will-change` 负对照稳定产生约 1.39% 像素变化，证明校验器能识别真实退化。
- 性能结果：
  - ×1：53.9 → 59.1fps，p95 26.5 → 24.6ms。
  - ×4：23.1 → 43.8fps，p95 63.4 → 35.2ms，>50ms 严重长帧中位数 7 → 0；隐藏节点的渲染上限为 53.2fps。
- 结论：两级隔离是当前在“不改外观、不改节点几何、不启用模糊合成层”约束下收益最稳定的方案；剩余差距主要需要更大范围的节点 DOM / 绘制复杂度治理。
- 影响任务：2.2（实施与验收）、3.1（沉淀为工程约定）
