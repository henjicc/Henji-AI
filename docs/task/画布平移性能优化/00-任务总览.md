# 画布平移性能优化 · 任务总览

## 任务目标

画布在**持续朝一个方向拖动、不断露出新内容**时跑不满 60fps（真实 TEST 项目实测 30~46fps，掉帧明显）。历史上曾用 `will-change: transform` 提升视口合成层来缓解，但它会让拖动过程中的文字发虚，于是在 commit `9c07487` / `51e894f` 中被移除——**移除是对的，但没有任何东西补上**，所以现在是"字清楚但顿挫"。

本次要达到的结果：在**外观逐像素不变**的前提下，把真实项目的连续平移帧率提到接近渲染上限（实测上限约 59~60fps），并留下一套可信、可重复的性能与外观回归测量手段，避免以后再用错误的测法得出错误结论。

**属于本次任务**：

- 画布平移（拖动画布）的渲染性能
- 节点层的绘制隔离（`contain: paint` + 扩展绘制框）
- 阻塞该方案落地的节点布局问题（模型选择器节点内容超框）
- 可信的性能基准脚本与外观/功能回归校验脚本
- 结论沉淀（避免后人重走 `will-change` 死路）

**不属于本次任务**：

- 缩放（zoom）性能、节点拖拽性能、框选性能
- 减少单个节点的 DOM 元素数量（当前每节点约 77 个元素）——这是更大的结构工程，若第二阶段后仍不达标再单独立项
- 画布 LOD 等级体系的调整（`useCanvasContentLod` / `canvasLodLevel` 已存在且工作正常）
- 连线渲染、毛玻璃密度降级（`useCanvasGlassPerformance` 已存在）
- 智能助手、生成链路等非画布渲染的部分

## 重要说明

1. **`will-change: transform` 在本项目是死路，不要再试。** 原因不是"分数像素重采样"，而是它把合成层的光栅倍率钉死：画布视口的 `scale` 通常不等于 1（常用工作倍率约 0.54），图层按 `0.54 × DPR` 光栅再放大回屏幕，文字必糊。已用"把位移强制吸附到整设备像素后再对比"的实验排除了分数像素这个解释。详见 `重要记录.md` 记录 001。
2. **性能测量必须用"连续扫掠 + 同启动内交替采样"**，否则结论不可信。原地小幅来回拖是 60fps，测不出任何问题；按配置顺序测会产生"第一个配置永远最慢"的预热假象。详见 `重要记录.md` 记录 004。
3. **外观必须逐像素不变**，这是用户明确的硬约束。任何方案落地前后都要用 1.2 的脚本比对截图。
4. **性能基准怎么跑**：`npm run electron:pan-bench`（默认 `BENCH_MULT=1`）跑真实项目原样；`BENCH_MULT=4 npm run electron:pan-bench` 是**判定收益的主场景**。×1 两次独立运行的中位数就能差 2.9fps，3fps 以内的差异在 ×1 下不构成结论。详见 `重要记录.md` 记录 007。
5. **待确认（3 项）**：
   - 验收帧率口径——**待确认**。原建议（TEST ×1 fps ≥ 55）已被 1.1 的实测证明区分度不够（现状本来就有 54.9~57.8）。修订建议：以 `BENCH_MULT=4` 为准，现状 26.9fps、渲染上限 56.3fps，达标线取 fps 中位 ≥ 45 且 >25ms 的帧数下降 ≥ 60%
   - 是否允许改动 `ModelSelectorNodes` 的布局以消除内容超框——**待确认**
   - 若第二阶段后仍达不到目标，是否立项"减少单节点 DOM 量"——**待确认**
