## 任务目标

把本次调研得到的、容易被后人重复踩坑的结论写进项目约定，并处理旧压测脚本"测不出真实问题"的局限，使下一次有人改画布渲染时不会重走 `will-change` 这条死路、也不会再被原地小幅拖动的假 60fps 误导。

## 当前情况

### 结论已经被踩过两次

`will-change: transform` 在本项目的历史轨迹：

- `a311593` 引入（只给平移，不给缩放）
- `9c07487` / `51e894f` 因"文字发虚"移除
- 本次调研再次验证：收益小甚至为负，且模糊不可消除

`CLAUDE.md` 目前记录了大量画布与 UI 约定，但**没有关于画布渲染性能手段的条目**；`src/features/canvas/storyboard.css` 中原先的 `will-change` 注释已随代码一起删除，结论没有留存位置。

### 旧压测脚本的局限

`scripts/electron-phase4-canvas-stress.cjs`（`npm run electron:canvas-stress`）：

- fixture 用 2×2 像素占位图（`scripts/lib/canvasStressFixtures.cjs`）
- `scripts/lib/canvasPerf.cjs` 的 `drivePan` 在中心 ±30px 来回晃，且每步 `waitForTimeout(40)`

两者叠加导致它在真实存在顿挫的画布上也报 60fps。它作为**冒烟**（能否加载、有无控制台报错、内存是否异常）仍然有价值，但不能作为性能结论来源。

### 现有 skill 与文档

- `henji-ui-surface`（含"性能分层规则"参考）
- `canvas-node-builder`
- `CLAUDE.md` 的「核心架构原则 / 画布模块拆分约定 / 关键约束」

## 实施方案

只做文档与脚本注释层面的最小改动，不动业务代码。结论要写在"下次会被读到的地方"：`CLAUDE.md`（每次会话都加载）、`storyboard.css`（改画布样式时必然看到）、旧压测脚本头部（打算用它测性能时必然看到）。

## 执行步骤

1. 在 `CLAUDE.md` 的画布相关章节新增一条约定，至少写明：
   - 画布平移的性能瓶颈是可见节点内容的逐帧重绘，衡量手段是 `npm run electron:pan-bench`
   - **禁止**用 `will-change: transform` 提升画布视口或节点合成层：会钉死光栅倍率，画布常用倍率约 0.54，文字必糊；已用"位移吸附到整设备像素"实验排除分数像素这一解释
   - **禁止**在节点上使用 `content-visibility: auto`：我们的节点是深层嵌套，124 节点时掉到 8.4fps
   - `translate: 0 0 0` 是空操作（计算值被折叠成 `0px`），不要用它来"提升合成层"
   - 当前采用的是节点绘制隔离壳（`contain: paint` + 扩展绘制框），改动画布节点 DOM 结构时要同步确认溢出量
2. 在 `src/features/canvas/storyboard.css` 的 `.canvas-node-paint-frame` 规则注释中补全上述取舍的实测数字（2.2 已写一部分，本任务补充对照表）。
3. 在 `scripts/electron-phase4-canvas-stress.cjs` 头部加注释，写明该脚本的 fixture 与驱动方式**不能用于性能结论**，性能请用 `npm run electron:pan-bench`；同时在 `scripts/lib/canvasPerf.cjs` 的 `drivePan` 上加注说明"原地来回晃，瓦片命中缓存"。
4. 在 `CLAUDE.md` 的「重构后回归检查」小节补入 `npm run electron:pan-bench` 与 `npm run check:canvas-visual` 的使用时机（画布渲染相关改动时执行）。
5. 评估 `henji-ui-surface` skill 的性能分层参考是否需要同步补充画布这一条（若需要则更新；不需要则在执行记录中说明原因）。
6. 更新本计划目录：把 2.2 的最终实测数字回填到 `01-实施方案.md` 的方案对照表，`00-任务总览.md` 标记整体完成。
7. 为本任务创建一次独立 Git 提交。
