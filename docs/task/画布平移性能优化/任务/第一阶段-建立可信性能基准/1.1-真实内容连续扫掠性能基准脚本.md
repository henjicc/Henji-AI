## 任务目标

产出一个可重复运行的画布平移性能基准脚本，能**稳定复现**真实项目上的平移顿挫，并能在同一次运行内公平对比多个候选配置。运行结果需包含足够的环境信息，使不同机器上的数字可以互相解释。

## 当前情况

### 已有的压测脚本测不出这个问题

`scripts/electron-phase4-canvas-stress.cjs` + `scripts/lib/canvasPerf.cjs`（`npm run electron:canvas-stress`）存在两个致命局限：

1. **fixture 不真实**：`scripts/lib/canvasStressFixtures.cjs` 用 2×2 像素占位图和结构最简单的生成节点，光栅负担与真实节点差一个量级。
2. **驱动方式不真实**：`canvasPerf.cjs` 的 `drivePan` 在画布中心 ±30px 来回晃，瓦片全部命中缓存 → 稳定 60fps，**问题完全被掩盖**。

### 本次调研已验证的正确测法（必须继承）

- **负载**：用真实项目（`TEST`，31 节点 / 14 种类型 / 26 张真实图片）的 `nodes_json` 按网格复制 N 份生成临时项目，媒体路径原样保留，因此仍是真实图片/视频。
- **驱动**：**连续朝一个方向扫掠**，走到屏幕边缘就"松手再抓"继续同向前进，让画面里一直有从未光栅过的新内容。
- **⚠️「松手再抓」必须先发一次 `buttons: 0` 的 `mouseMoved`**，否则 d3-zoom 会把跳变当作继续拖动，视口偏移**指数爆炸**（实测到 `1e237`），画布飞到无穷远，之后测的全是空画布上的 60fps。
- **输入**：走 CDP `Input.dispatchMouseEvent`（含命中测试），不要在页面内 `window.dispatchEvent` 合成事件（会跳过命中测试）；也不要 `await` 每一次派发（Playwright 往返会把输入频率限制在约 30Hz，掩盖真实差异）。
- **采样**：在页面内用 rAF 记录帧间隔，同时记录 `.react-flow__viewport` 的 transform，用于自检。
- **对比方法**：**同一次启动内交替采样**多个配置（A/B/C/A/B/C…），取每配置中位数。按配置顺序逐个测会产生"第一个配置永远最慢"的预热假象（本次调研已两次因此得出错误结论）。
- **自检**：每轮结束校验视口净位移足够大、坐标有限、屏幕内可见节点数 ≥ 5，不满足则该轮标记为无效并排除。

### 环境基线（本机）

- 窗口 2560×1400，`devicePixelRatio` 1.5，显示器 3840×2160 @ 60Hz
- 真实项目 `TEST`：31 节点、9 条连线、2379 个视口内 DOM 元素、原始视口 `{x: 725.995, y: -314.71, zoom: 0.544069}`
- ×4 复制后：124 节点、101 张图片、9501 个 DOM 元素、约 26 个节点在屏幕内

## 执行步骤

1. 新建 `scripts/lib/canvasPanBench.cjs`，导出：
   - `createRealContentFixture(page, { sourceProject, multiplier, tempName })`：读取源项目 `nodes_json` / `edges_json` / `history_json`，按网格复制 `multiplier` 份（节点 id 加 `__c{n}` 后缀，边同步改写），写入名为 `tempName` 的临时项目，视口固定为源项目原始视口。返回节点数与节点类型数。
   - `removeFixtures(page, prefix)`：按名称前缀删除临时项目。
   - `findEmptyPanePoint(page)`：用 `document.elementFromPoint` 找到落在 `.react-flow__pane` 上的抓取点（落在节点上会变成拖节点，视口根本不动）。
   - `sweep(page, session, { grab, durationMs, direction, step, measure })`：连续扫掠驱动 + 帧采样 + 自检，返回 `{ valid, fps, p95, p99, max, dropped, netMove, visibleNow }`。
2. 在 `sweep` 中实现「松手再抓」序列：`mouseReleased` → `mouseMoved(buttons: 0)` → 等待一帧 → `mousePressed`。
3. 新建 `scripts/electron-canvas-pan-bench.cjs`：
   - 读取环境变量：`BENCH_PROJECT`（默认 `TEST`）、`BENCH_MULT`（默认 1）、`BENCH_SWEEP_MS`、`BENCH_REPS`、`BENCH_SET`（逗号分隔的配置名）。
   - 内置配置表至少包含 `off`（现状）与 `hidenodes`（`.react-flow__node{visibility:hidden}`，作为渲染上限参照）；配置以注入 `<style>` 的方式生效。
   - 流程：启动 → 生成 fixture → 打开项目 → 采集环境信息 → 预热若干轮 → 交替采样 → 输出 JSON → 清理临时项目。
   - 每轮测量后追加一次反向扫掠（不计入测量），让下一轮起点一致。
4. 输出中必须包含：窗口尺寸、DPR、节点数、屏幕内可见节点数、图片数、视口内 DOM 元素数、当前缩放倍率、每轮原始数据与各配置中位数、无效轮次数量。
5. 在 `package.json` 增加脚本 `"electron:pan-bench": "node scripts/electron-canvas-pan-bench.cjs"`。
6. 把基准产物目录（如 `.pan-bench/`）加入 `.gitignore`。
7. 用 `off` 与 `hidenodes` 两个配置在 `BENCH_MULT=1` 和 `BENCH_MULT=4` 下各跑一次，确认能复现出「现状明显低于上限」的差距；把实测数字写入本文件的执行记录。

#### 与原计划的五处偏离（都是实测倒逼的，后续任务按这里为准）

1. **不能沿用源项目保存的视口。** 计划写的是「视口固定为源项目原始视口」，但那是用户上次停留的位置，会随用户操作漂移。实测 `TEST` 当前视口 `{x: 2956, y: 648.29}` 落在项目左侧的空白区，**屏幕内只有 4 个节点**，跑出来是假的 60fps（第一次运行 6 轮全部被自检判为无效，自检起了作用）。改为 `planSweepViewport()`：扫描节点最密集的横向条带，把起点放在该条带内容的左端。改后屏幕内节点数 4 → **22**。
2. **副本改为横向单排铺开**，不用计划里说的网格。网格铺法会让扫掠很快走进两块之间的空白，后半段又变成空画布测量。
3. **扫掠长度按内容长度封顶。** `planSweepViewport` 额外返回 `availableSweepScreenDistance`，入口脚本用它把 `BENCH_SWEEP_MS` 压到不会走出内容范围（`TEST` ×1 实际只有 735ms 可用，×4 是完整 1200ms）。输出里同时给出 `requestedSweepMs` 与 `effectiveSweepMs`。
4. **反向扫掠改成精确视口复位。** 计划里的「反向扫掠让下一轮起点一致」实测做不到一致：起点在 3 轮内从 2800 漂到 2584。改为 `resetViewport()`，按 `目标视口 − 当前视口` 的差值直接拖回（平移与鼠标位移 1:1），并且**复位阶段逐个 `await` 派发**（复位不参与测量，精度比速度重要）。改后 4 轮起点完全相同，`resetFailures` 为空。
5. **有效性判据里的可见节点数改为取首尾较小值。** 只看结束时刻会误杀：扫掠是从密集区走向稀疏区，结束时天然偏少。

#### 实测数据（本机：2560×1439 窗口、DPR 1.5、缩放 0.5441）

| 场景 | 节点数 | 视口内 DOM 元素 | 屏幕内节点 | `off` fps 中位 | `hidenodes` fps 中位 | 差距 |
|---|---|---|---|---|---|---|
| `TEST` ×1（735ms 扫掠） | 31 | 2523 | 22 | **54.9** / 57.8（两次运行） | 60.9 / 60.6 | 3~6 fps |
| `TEST` ×4（1200ms 扫掠） | 124 | 10077 | 22 | **26.9**（26.1~27.9） | 56.3（50.6~57.2） | **29.4 fps** |

- `off` 在 ×4 下 p95 帧间隔 53.7ms、p99 57.6ms、>25ms 的帧 32 个；`hidenodes` 对应 29.75 / 37.5 / 10 个。
- 全部轮次 `valid`，`resetFailures` 为空。
- **run-to-run 波动**：×1 `off` 两次独立运行中位数 54.9 与 57.8，差 2.9 fps（约 5%）；`hidenodes` 差 0.3 fps。×4 单次运行内 4 轮的 min~max 只有 1.8 fps。→ **×4 是判定收益的主场景，×1 只作为"真实项目原样"的参照，×1 的 3 fps 以内差异不足以下结论。**

#### 一个新发现（会影响第二阶段的预期）

×1 与 ×4 的**屏幕内可见节点数完全相同（都是 22）**，因为副本是横向单排铺开、密度没变；但 fps 从 54.9 掉到 26.9。也就是说**成本主要随视口内节点总量增长，而不是只随屏幕上的像素量增长**。

这与「绘制记录（paint recording）是整层一次性生成、光栅只做可见瓦片」的机制一致，也正好是 `contain: paint` 能起作用的地方——它让合成器可以跳过被裁剪掉的子树。之前的调研只测到"隐藏节点内容就回到 60fps"，没有把"可见像素量"和"节点总量"这两个变量分开，这次分开了。
