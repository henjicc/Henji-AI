# 5.1 界面门禁接入日常验证

## 任务状态

## 任务目标

界面问题在本地 `verify:changed` 就能被拦下，而不是等到 CI；原生控件禁令、外观覆盖、豁免标记都有可执行的门禁；只改 skill 文档的提交也会触发同步检查。

## 当前情况

- `scripts/lib/changedVerificationPlan.cjs:176-210` 对 `src/` 改动只排 tsc、eslint、依赖图等，不跑 `check:surface/colors/icons/ui-residue`；这四项只在 `build`、`electron:build` 与 CI。
- `npm run check:surface` 默认非 strict，退出码恒为 0，而 `docs/rules/testing.md` 让开发者跑的正是它；`ui-residue-scan.cjs` 禁止 `--strict` 与 `--files` 同用。
- 原生 `<button>/<input>/<select>/<textarea>` 禁令没有 ESLint 规则（`.eslintrc.json` 只拦颜色等）；当前正式代码 0 处，全靠自觉；另有 6 处 `div role="button"`。
- 规则 E 把内边距和 gap 视为布局放行，按钮类约 60 处内边距覆盖、29 处 `!important`；规则 E 不覆盖字段类组件；两套“外观覆盖”检查口径不同；新组件纳入规则 E 靠人工加名单。
- `check:surface` 规则 C 已失效、4 处死豁免标记无过期检测；`ui-residue` allowlist 无上限。
- `.github/workflows/build.yml` 的 `paths-ignore` 忽略 `**/*.md`，只改 skill 的推送会跳过 CI，`check:skill-sync` 形同虚设。

## 实施方案

`changedVerificationPlan.cjs` 在改动含 `.tsx/.css` 时加入四项界面门禁（局部模式）；`check:surface` 默认 strict、另设 report 模式；`ui-residue-scan.cjs` 增加局部严格模式；ESLint 增加原生控件与 `role="button"` 规则；规则 E 合并为一套口径、覆盖字段组件与非 Ui 前缀共享组件、按钮类内边距与 `!important` 纳入检查、组件名单从 `src/components/ui` 导出自动生成；豁免标记要求带接手任务并检查过期；allowlist 设上限只降不升；CI 对 `.claude/skills/**`、`.codex/skills/**` 不再忽略。

### 问题 1：日常 verify:changed 不跑任何 UI 门禁，check:surface 默认又是只告警，问题要到 CI 才暴露

- 审计编号：`ui-comp-2`
- 位置：`scripts/lib/changedVerificationPlan.cjs:203`；严重度：高
- 证据：changedVerificationPlan.cjs:186-210 对 src/ 改动只排 tsc、eslint、dependency-graph、main-imports、ipc-contract、persistence:baseline，没有 check:surface/colors/icons/ui-residue；这四项只接在 package.json:53 build、:76 electron:build 与 build.yml:63-73。check-surface-tokens.cjs 末尾 `process.exit(strict ? 1 : 0)`，而 testing.md:214 让开发者跑的是非 strict 的 `npm run check:surface`。ui-residue-scan.cjs parseArgs 明确禁止 --strict 与 --files 同用，所以局部也无法严格跑。
- 改法：changedVerificationPlan.cjs 增加：改动含 .tsx/.css 时自动加 gate('界面表面', 'check:surface:strict')、check:colors、check:icons:strict；ui-residue-scan.cjs 增加 `--strict-local --files`（跳过过期登记判定、其余按严格口径）并接入同一计划；testing.md:214 改为 strict 命令；package.json 把 check:surface 默认改 strict，保留 check:surface:report 做告警模式。

### 问题 2：UI 门禁不在日常验证链：verify:changed 不跑 surface/colors/icons/residue，testing.md 推荐的非 strict 命令退出码恒为 0，build 不跑 ESLint

- 审计编号：`ui-gate-3`
- 位置：`scripts/lib/changedVerificationPlan.cjs:176`；严重度：高
- 证据：changedVerificationPlan.cjs:140-214 只为改动文件安排精确测试、ESLint、tsc、依赖图、IPC 和持久化门禁，没有任何 check:surface/colors/icons/ui-residue 步骤。docs/rules/testing.md:213-216 让界面改动跑 `npm run check:surface` 和 `npm run check:icons`，这两个是非 strict 版本：check-surface-tokens.cjs 末尾 `process.exit(strict ? 1 : 0)`，check-icon-tokens.cjs 头注释写明“告警式，退出码恒为 0”。package.json:53（build）和 :76（electron:build）都不含 lint，ESLint 独有的规则（z-10、duration-200、backdrop-blur-*、text-[13px]、shadow-[..]）只有 CI 和 verify:changed 会执行。结果是违规要到 CI 才暴露。
- 改法：1）在 changedVerificationPlan.cjs 中，只要改动含 src/**/*.tsx|.css|tailwind.config.js|styleTokens.ts，就追加 gate('界面令牌', 'check:colors')、check:surface:strict、check:icons:strict、check:ui-residue；四个都是秒级全仓扫描，成本可以接受。2）把 testing.md:213-216 改为 strict 命令。3）在 package.json 的 build 和 electron:build 里串上 `npm run lint`，或把 ESLint 的 no-restricted-syntax 规则下沉为 ui-residue 的同名类别，使 build 与 CI 口径一致。

### 问题 3：原生 <button>/<input>/<select>/<textarea> 禁令没有任何自动门禁，只靠纪律

- 审计编号：`ui-comp-1`
- 位置：`.eslintrc.json:35`；严重度：高；涉及数量：0
- 证据：docs/rules/frontend-ui.md:10 规定原生控件只允许在 primitives.tsx；但 .eslintrc.json:35-118 的 no-restricted-syntax 只有颜色/字号/阴影/z/时长/backdrop 的 Literal 选择器，没有 JSXOpeningElement 规则；check-surface-tokens.cjs:37 整个 ui 目录豁免且规则 A-E 都不查原生标签；uiResidueRules.cjs:276 只查 /^Ui[A-Z]/ 的 className。当前 grep 结果：src 非 ui 目录 26 处命中全部在 .test.tsx，正式代码 0——合规完全靠自觉。另有 6 处 div role="button"（cameraStage StaticClipBlock.tsx:147、TransitionClipBlock.tsx:88/109/123、videoEdit/VideoEditCaptionTrack.tsx:85、canvas NodeGenerationError.tsx:30）同样无人拦。
- 改法：.eslintrc.json 新增 no-restricted-syntax 选择器 `JSXOpeningElement[name.name=/^(button|input|select|textarea)$/]`，并在 overrides 里只对 src/components/ui/primitives.tsx 与 *.test.tsx 关闭；同时加 `JSXAttribute[name.name='role'][value.value='button']` 告警级规则，要求写 ui-surface-allow 理由。

### 问题 4：规则 E 把内边距和 gap 视为布局放行：按钮类组件约 60 处内边距覆盖、29 处 !important，同一按钮视觉尺寸被调用点改写

- 审计编号：`ui-gate-1`
- 位置：`scripts/lib/buttonAppearanceOverrides.cjs:8`；严重度：高
- 证据：buttonAppearanceOverrides.cjs:8-10 明确规定“className 只放布局（…外边距、内边距…）”。AST 统计非 ui 目录约 1073 个按钮类元素：UiOptionButton 的 px/py/p 覆盖 39 处，UiButton 的 p/px 覆盖 14 处，UiChipButton 的 px 覆盖 4 处，UiNavButton 的 pr 覆盖 3 处，带 !important 的覆盖 29 处。例如 VideoEditTrackHeader.tsx:69 写了 `!justify-start !gap-1.5 !px-1`，VideoEditProjectPanel.tsx:284 写了 `!p-1.5`、:297 写了 `!px-1.5`。另外 UiButton 内部已有 gap-1.5（primitiveInternals.ts:272-273），但仍有 19 处图标再写 `size={14} className="mr-1.5"`（如 CameraStageEditor.tsx:383、:438），使图文间距变成 12px，而其他按钮是 6px；还有 23 处 UiButton 的 gap 覆盖。ui-residue 的 APPEARANCE_CLASS_PATTERN 也不含 p/gap。
- 改法：1）在 buttonAppearanceOverrides.cjs 的 classifyToken 中，对 UiButton/UiIconButton/UiChipButton/UiNavButton/UiFieldTrigger，把 p*/gap-*、以及任何带 `!` 前缀的类判为“尺寸覆盖”违规；UiOptionButton 的 tile/cover 等内容卡变体仍允许 min-h/h-full。2）需要贴边对齐的场景给 UiButton 加有限枚举 `inset="flush"`（负外边距对齐列），代替 -ml-2；需要左对齐的给 `align="start"`，代替 !justify-start。3）在 uiResidueRules.cjs 新增 iconSpacingInButton：Ui*Button 子节点里的 lucide 图标带 m[lr]-* 即违规。

### 问题 5：两套“调用点覆盖外观”门禁口径不一致，非 Ui 前缀组件与动态 className 两边都不查

- 审计编号：`ui-comp-10`
- 位置：`scripts/lib/buttonAppearanceOverrides.cjs:29`；严重度：中
- 证据：规则 E（buttonAppearanceOverrides.cjs:29-50）用 AST 展开常量/三元/import，但受检名单是手写的 17 个名字，不含 UiInput/UiSelect/UiSwitch/UiCheckbox/UiPanel/UiRangeInput/NumberInput/ProgressBar/Tooltip/FileUploader；residue 的 appearanceOverride（uiResidueRules.cjs:276）覆盖全部 /^Ui[A-Z]/ 但只匹配字面量 className（CLASS_LITERAL_PATTERN :41），`className={cond ? 'bg-x' : ''}` 与 `${}` 插值都被跳过，且 NumberInput/Dropdown/PanelTrigger 的 className 不在内。当前 grep 两类未覆盖写法均为 0 命中，但没有机制保证。
- 改法：以规则 E 为唯一实现：CHECKED_ATTRIBUTES 改为从 src/components/ui/index.ts 导出自动生成（所有接受 className/buttonClassName 的组件），residue 的 appearanceOverride 降为报告视图不再二次判定；为 UiInput/UiSelect/UiSwitch/UiCheckbox/UiPanel/NumberInput/ProgressBar/Tooltip 定义各自允许的布局类白名单（如 UiPanel 允许 p-*/gap-*）。

### 问题 6：规则 E 不覆盖字段类组件，调用点能用 ! 覆盖 UiColorInput/UiCheckbox 的尺寸

- 审计编号：`ui-token-11`
- 位置：`scripts/lib/buttonAppearanceOverrides.cjs:28`；严重度：中
- 证据：CHECKED_ATTRIBUTES（:28-49）只覆盖 18 个组件，UiInput、UiSelect、NumberInput、UiColorInput、UiCheckbox、UiSwitch、UiRangeInput 都不在内。但 styleTokens.ts 的 UI_FIELD_SIZE_CLASS 注释写着这些组件“调用点不再写高度与字号”。实例都能过门禁：ThemeSection.tsx:218 <UiColorInput className="!h-8 !w-8">（组件本身是 h-9 w-9，primitives.tsx:579）；ExportPanel.tsx:126 <UiCheckbox className="h-4 w-4">（组件本身是 h-6 w-6，primitives.tsx:598，这样点击区域缩到 16px）。
- 改法：把 UiInput、UiSelect、NumberInput、UiColorInput、UiCheckbox、UiSwitch、UiRangeInput、UiSeedInput、UiDatePicker 加进 CHECKED_ATTRIBUTES，宽度和弹性仍然放行。UiColorInput 和 UiCheckbox 若确有尺寸需求，增加 size 枚举（sm/md）后修正这两处调用点。

### 问题 7：新组件要纳入规则 E 只靠人工加名单，没有检查

- 审计编号：`ui-docs-14`
- 位置：`scripts/lib/buttonAppearanceOverrides.cjs:29`；严重度：低；涉及数量：19
- 证据：frontend-ui.md:13 和 SKILL.md:621 要求新组件“纳入 check:surface 规则 E”。实际受检名单是 buttonAppearanceOverrides.cjs:29-50 手写的 CHECKED_ATTRIBUTES，共 19 个组件；@/components/ui 导出约 47 个 Ui 组件，UiInput、UiSwitch、UiCheckbox、UiRangeInput、NumberInput、UiAngleDial 等不在名单里，也没有测试比对导出与名单。目前用简单正则只扫到 4 处外观类覆盖，均为布局，没有违规；但这条要求本身没有强制力。
- 改法：仿照 uiGalleryCoverage.test.ts 新增 surfaceRuleCoverage.test.ts：从 components/ui/index.ts 收集导出组件，要求每个组件要么在 CHECKED_ATTRIBUTES 中，要么在 RULE_E_EXEMPT 中写明理由（例如纯容器、只接受 layout className）。

### 问题 8：check:surface 规则 C 已失效，豁免标记无过期检测（4 处死标记）；规则 A/B 不扫 .ts 类串

- 审计编号：`ui-gate-6`
- 位置：`scripts/check-surface-tokens.cjs:196`；严重度：中
- 证据：check-surface-tokens.cjs:196 的 OVERLAY_SCRIM_PATTERN 为 /bg-black\/|bg-black\s+bg-opacity-/，而 check-color-tokens.cjs:75 的 mono 规则禁止所有 bg-black，因此通过颜色门禁的代码永远触发不了规则 C。现在手写弹窗会用 bg-scrim 或 bg-media（tailwind.config.js:205-211）。ImageViewerModal.tsx:239、VideoViewerModal.tsx:415、AudioViewerModal.tsx:98、PanoramaViewerModal.tsx:191 上的 ui-surface-allow 已经抑制不到任何东西：这些查看器用的是 bg-media，本来就不会命中；ui-residue 只校验理由字数 ≥8，不校验标记是否仍有对应命中。规则 A/B 只扫 .tsx 的 className=（:38、:72），所以 src/features/canvas/ui/nodeControlStyles.ts:29 的 `rounded-lg border border-line bg-window` 和 src/components/dockviewDocking.ts:138 的 `rounded-control border border-accent/60 bg-panel/50` 都逃过了门禁。
- 改法：1）把规则 C 改为结构判定：非 components/ui 文件里出现 `fixed` + inset-0（或 UI_CONTENT_OVERLAY_INSET_CLASS）+ role="dialog"/aria-modal，且未使用 UiModal/AlertDialog，即命中；遮罩色改匹配 bg-scrim*、bg-media、ui-glass-scrim。2）在 check-surface-tokens.cjs 增加“过期豁免”检测：标记所在行与下一行在去掉标记后不再产生 A–E 命中时报错，与 ui-residue 的过期登记同口径。3）规则 A/B 扩到 .ts 文件里 *Class/*_CLASS 常量的字符串字面量，复用 buttonAppearanceOverrides 已有的常量展开逻辑。

### 问题 9：只改 skill .md 的推送会跳过整个 CI，check:skill-sync 门禁形同虚设

- 审计编号：`ui-gate-13`
- 位置：`.github/workflows/build.yml:10`；严重度：中
- 证据：build.yml:10-12 的 push 触发器设置了 `paths-ignore: ['docs/**', '**/*.md']`。.claude/skills 与 .codex/skills 共 53 个文件，其中 50 个是 .md、3 个是 .yaml。AGENTS.md 规定默认在 main 上直接推送，所以只改一侧 SKILL.md 或 references/*.md 的提交不会触发 check:skill-sync。仓库没有 .husky 或 git hooks（`ls .husky`、`git config core.hooksPath` 均为空），本地也没有兜底。
- 改法：在 build.yml 新增一个不设 paths-ignore 的轻量 workflow（例如 .github/workflows/skill-sync.yml，`on: push: paths: ['.claude/skills/**', '.codex/skills/**']`），只跑 `npm ci --ignore-scripts && npm run check:skill-sync`；或把 '!.claude/skills/**'、'!.codex/skills/**' 的取反规则加进现有 paths-ignore（GitHub Actions 支持 ! 前缀重新纳入）。
