# 4.4 动效底座统一

## 任务状态

- 状态：待开始
- 所属阶段：第四阶段-设计系统中心与界面底座
- 前置任务：4.1
- 关联任务：无
- 是否可以并行：可以与 4.2、4.3 并行（主要改 `motion.ts`、`index.css` 动画段、进出场组件）

## 任务目标

所有过渡与动画都落在 120/180/240/500 四档与统一缓动上；进出场统一用一个 hook；CSS 动画时长与 JS 卸载计时由测试保证一致；有明确的“减少动效”策略。

## 当前情况

- `src/components/ui/motion.ts` 定义四档时长与 `uiTransition()`，`useDialogTransition.ts` 是唯一公共进出场 hook，但 11 个文件各自手写进出场状态机。
- 不写 `duration-*` 时 Tailwind 默认 150ms，不在档位内且门禁不拦，核心 primitives 也有（`tailwind.config.js:109`）。
- `.ui-btn`（所有按钮的过渡）用 `ease` 与 80ms（`src/index.css:500`）。
- `animate-scale-in` 与 `@keyframes pulse` 在 `tailwind.config.js` 与 `index.css` 各定义一份；浮层展开实际 180ms，配置写 120ms，`UI_POPOVER_TRANSITION_MS=120` 是只在测试里用的死常量。
- 只有 3 处尊重 `prefers-reduced-motion`；`references/motion.md` 的“已登记布局过渡”表过时。

## 实施方案

Tailwind 默认 `transitionDuration` 设为 180ms 并限定可用档；`.ui-btn` 改用档位与全局缓动；动画关键帧只保留一处定义；把 11 处手写进出场迁移到 `useDialogTransition`（必要时扩展参数）；`motion.test.ts` 增加对 `index.css` 中动画时长与 JS 常量的一致性检查；在 `index.css` 统一加 `prefers-reduced-motion` 规则并写进 `references/motion.md`。

### 问题 1：transition-* 不写 duration 时落到 Tailwind 默认 150ms，档位外且门禁不拦，核心 primitives 带头违规

- 审计编号：`ui-motion-0`
- 位置：`tailwind.config.js:109`；严重度：高；涉及数量：28
- 证据：tailwind.config.js:103-113 用 extend 覆盖了 transitionTimingFunction.DEFAULT，但 transitionDuration 只加了 120/180/240，没有 DEFAULT。实测编译产物：.transition-colors{transition-duration:150ms}。在 transition-* 前后 3 行内找不到 duration-*、transitionDuration 或 UI_DURATION_CLASS 的有 28 处，分布在 18 个文件。其中包括 primitives.tsx:106 UiNavButton、:197 UiChipButton、:394 和 :423 UiOptionButton，styleTokens.ts:280 UI_OPTION_ITEM_CLASS，nodeControlStyles.ts:29，promptEditorStyles.ts:13。ESLint 规则（.eslintrc.json:114-119）只拦写出来的非档位 duration-N，“没写 duration”拦不住。check:surface 和 check:ui-residue 都通过。
- 改法：在 tailwind.config.js 的 transitionDuration 里补上 DEFAULT: '120ms'，和缓动 DEFAULT 的处理方式一致，一行就能把 28 处收回档位。在 src/components/ui/designTokens.test.ts 里加断言 tailwindConfig 包含 DEFAULT: '120ms'。在 motion.md 和 frontend-ui.md:85 补一句“不写 duration 即 fast 120”。

### 问题 2：.ui-btn（所有 UiButton/UiIconButton 的过渡）用 `ease` 和 80ms，偏离统一缓动与档位

- 审计编号：`ui-motion-1`
- 位置：`src/index.css:500`；严重度：高
- 证据：index.css:500-506 的 .ui-btn 写的是 transition: background-color 120ms ease, color 120ms ease, box-shadow 120ms ease, transform 80ms ease。这里的 `ease` 等于 cubic-bezier(.25,.1,.25,1)，不是 motion.ts:45 的 UI_EASE；80ms 也不在 120/180/240/500 四档里。primitives.tsx:81 和 :135 说明全部按钮都走这个类。ESLint 时长规则只检查 TS 字面量，CSS 文件不在任何门禁范围内。
- 改法：在 index.css 的 :root 里定义 --ui-duration-fast/base/slow/viewer 和 --ui-ease，由 motion.ts 的值镜像生成，再由 designTokens.test.ts 断言一致。.ui-btn 改成 var(--ui-duration-fast) var(--ui-ease)；按压反馈的 transform 也用 fast，或者在 motion.ts 登记一个具名的按压档并写明理由。

### 问题 3：animate-scale-in 和 @keyframes pulse 在 tailwind.config 与 index.css 里各定义一份，结果取决于产物里的先后顺序

- 审计编号：`ui-motion-2`
- 位置：`src/index.css:829`；严重度：高
- 证据：tailwind.config.js:310 定义 'scale-in' 为 120ms，注释写“展开 120”；index.css:843 的 .animate-scale-in 是 180ms，而且写在 @layer 之外，排在 utilities 后面，所以实际生效的是 180。编译产物里 .animate-scale-in 出现了两次（第 3138 行和第 6217 行）。@keyframes pulse 在产物里有三份：3102 行是 Tailwind 的 50%→.5；6202 行是 index.css:829 的 0.2↔0.1；7199 行在 @media(prefers-reduced-motion:no-preference) 里，由 AssetLibrarySurface.tsx:348 的 motion-safe:animate-pulse 引入。系统开启减少动效时，最后这条不生效，于是 AssistantTraceList.tsx:148、VideoEditImportProgress.tsx:18、VideoEditInPlacePlaceholders.tsx:59 等 5 处 .animate-pulse 会在 10%–20% 不透明度之间闪，几乎看不见，而且无视减少动效设置。另外 scaleIn 和 scale-in 两个同义 keyframe 并存（tailwind.config.js:291/295 与 index.css:785）。
- 改法：动画只留一个来源，放在 tailwind.config.js 的 keyframes/animation 里，时长取档位，删掉 index.css:784-861 的重复 keyframes 和 .animate-* 类。自定义 keyframe 一律加 ui- 前缀，避免和 Tailwind 内置名字冲突。新增测试 src/components/ui/motionCss.test.ts：用 tailwindcss 编译一次，断言产物里没有同名 @keyframes、每个 .animate-* 只定义一次。

### 问题 4：浮层展开动画实际是 180ms，tailwind 配置写的 120ms 被 index.css 里未分层的同名类静默覆盖

- 审计编号：`ui-token-4`
- 位置：`src/index.css:843`；严重度：中
- 证据：tailwind.config.js:310 定义 'scale-in': 'scale-in 120ms ease-out'，:308 注释写“展开 120（fast）”。index.css:843 又在任何 @layer 之外定义了 .animate-scale-in { animation: scaleIn 180ms ease-out forwards }。用 tailwindcss CLI 编译后，第 3138 行是 120ms 版，第 6217 行是 180ms 版，后者生效。Dropdown.tsx:474/501 和 PanelTrigger.tsx:495 用的就是这个类。.animate-scale-out 和 .animate-pulse 也重复定义了两次。keyframes 里 scaleIn 和 scale-in 两套并存，animate-scaleIn 引用数为 0。说法本身也冲突：motion.ts 说浮层和下拉是 180，tailwind 注释说展开 120。index.css:287 自己就写过“裸 CSS 排在 utilities 之后会盖掉”的警告，却在这里重蹈覆辙。
- 改法：删除 index.css:785-861 的 keyframes 和 .animate-* 定义，keyframes 和 animation 只在 tailwind.config.js 保留一份，先统一决定展开用 120 还是 180，再同步 motion.ts 和 motion.md。在 designTokens.test.ts 加两条断言：index.css 里不得出现 .animate- 选择器；tailwind animation 里的毫秒值必须属于 UI_DURATION。ui-residue 的 CSS 扫描增加 animation/transition 字面毫秒值检查，不在 120/180/240/500 内的判违规或登记。

### 问题 5：UI_POPOVER_TRANSITION_MS=120 是只有测试在用的死常量，和浮层实际用的 180ms 矛盾

- 审计编号：`ui-motion-7`
- 位置：`src/components/ui/motion.ts:94`；严重度：中
- 证据：motion.ts:93-94 注释写“浮层（下拉、右键菜单、节点菜单）的进出场时长”，值是 fast=120。rg 结果显示它只在 motion.test.ts:8/24 出现。Dropdown.tsx:126 和 PanelTrigger.tsx:282 的卸载计时用的是 UI_DURATION.base（180），实际生效的 .animate-scale-in/out 也是 180（见 keyframes 冲突那条）。测试在断言一个没人用、而且与事实不符的值。
- 改法：把 UI_POPOVER_TRANSITION_MS 改成 UI_DURATION.base，并让 Dropdown、PanelTrigger、ContextMenu 改为引用这个常量；或者直接删除它和对应的断言。tailwind.config.js:309-314 的 animation 注释也一起改。

### 问题 6：进出场状态机有 1 个公共 hook，却有 11 个文件各自手写，帧数、时长常量和卸载兜底都不一致

- 审计编号：`ui-motion-3`
- 位置：`src/components/ui/useDialogTransition.ts:16`；严重度：高；涉及数量：11
- 证据：useDialogTransition 的调用方只有 UiModal、TestModePanel、AssistantSidebar、AssetLibraryFloatingPanel 这 4 个。手写的有：AudioViewerModal.tsx:41-59（双 rAF，时长写死 500）、VideoViewerModal.tsx:95-141（写死 500）、ImageViewerModal.tsx:180-183、PanoramaViewerModal.tsx:88-100（单 rAF）、AlertDialog.tsx:84/102（单 rAF）、Settings/index.tsx:95、Tooltip.tsx:114-117、Dropdown.tsx:126、PanelTrigger.tsx:282、NotificationContext.tsx:52-58、useToast.ts:37-43、TaskInputPreview.tsx:123/139。其中 NotificationContext.tsx:54 在挂载 UiToast 的同一次提交里就 setNotificationVisible(true)，全局通知没有进场过渡；生成页的 useToast.ts:37 用 setTimeout(0) 延后一拍，会有进场过渡，两处表现不一致。这些手写实现大多只靠计时器卸载，没有 hook 注释里提到的 onTransitionEnd 兜底（后台窗口计时器会被节流）。
- 改法：把 useDialogTransition 泛化成 src/components/ui/usePresence.ts，支持 durationMs（默认取档位）、appear、onTransitionEnd/onAnimationEnd 两种结束信号，useDialogTransition 作为它的别名保留；另加 useTimedToast(displayMs, exitMs)，供 NotificationContext 和 useToast 共用。逐个迁移上面 11 个文件。再加 ESLint 规则：src/** 里禁止 `setTimeout(` 和 setVisible/setShouldRender/setIsVisible(false) 同出现在一个 effect 中（可以用 check-surface-tokens 新增规则 F 实现，带豁免登记）。

### 问题 7：CSS 里的动画时长与 JS 卸载计时只靠人工对齐，motion.test 只校验 motion.ts 内部一致

- 审计编号：`ui-motion-8`
- 位置：`src/components/ui/motion.test.ts:12`；严重度：中
- 证据：motion.test.ts 只比较 UI_DURATION 和 UI_DURATION_CLASS。index.css:852/856 的 animate-fade-in/out 写死 240ms，靠 Tooltip.tsx:117 的 UI_DURATION.slow 人工对齐；index.css:882 的 promptOptimizePreviewOut 写死 240ms ease-in（未登记的缓动），靠 usePromptOptimizationPreviewPlayback.ts:5 的 PREVIEW_CLOSE_MS 人工对齐；index.css:860 是 2s，storyboard.css:79 是 1.5s。用 rg 查 .eslintrc 和 scripts，没有任何规则读 .css 里的 transition 或 animation。
- 改法：所有 CSS 动画和过渡改用 var(--ui-duration-*) / var(--ui-ease)。在 designTokens.test.ts 增加一项扫描：src/**/*.css 中的 transition/animation 声明，时长只允许 var(--ui-duration-*)、已登记的循环档（新增 UI_LOOP_MS，用于 pulse 和执行脉冲）或 0；缓动只允许 var(--ui-ease)、linear 和已登记的具名缓动。

### 问题 8：没有减少动效（reduced-motion）政策：只有 3 处尊重系统设置，规则文档里一字未提

- 审计编号：`ui-motion-9`
- 位置：`.claude/skills/henji-ui-surface/references/motion.md:1`；严重度：中
- 证据：全仓 prefers-reduced-motion 只出现在 storyboard.css:82/211、edgeFlowCanvas.ts:24、useMultiAngleTransition.ts:27；motion-safe/motion-reduce 有 9 处。animate-spin 14 处、animate-pulse 5 处、各类查看器 500ms 淡入都不受这个设置约束。在 motion.md、performance.md、frontend-ui.md 里搜 reduced-motion，命中 0 处。
- 改法：在 index.css 加全局 @media (prefers-reduced-motion: reduce)：把 *、::before、::after 的 transition-duration 和 animation-duration 压到 0.01ms，只放行表达“进行中”语义的 animate-spin（加白名单类 .ui-motion-essential）。motion.md 新增“减少动效”一节说明这个规则。usePresence 读取 matchMedia，减少动效时立即卸载，不必等过渡结束。

### 问题 9：动效没有统一的 prefers-reduced-motion 策略，各处实现不一致

- 审计编号：`ui-token-12`
- 位置：`src/index.css:843`；严重度：低
- 证据：index.css 全文没有 prefers-reduced-motion，motion.md 和 frontend-ui.md 也没有相关规则。animate-spin 共 14 处，只有 8 处加了 motion-safe:；animate-pulse 共 4 处，只有 1 处加了。animate-scale-in/fade-in 和 prompt-optimize 系列动画（index.css:878-907，含 500ms 的 stream rise）无条件播放。只有 storyboard.css:82/211、useMultiAngleTransition.ts:27、edgeFlowCanvas.ts:24 各自做了处理。
- 改法：在 index.css 增加全局规则：@media (prefers-reduced-motion: reduce) 下把非必要动画和过渡的时长压到约 0ms，必要动画用 [data-motion-essential] 退出；motion.md 补一节“减少动效”。ESLint 增加规则：animate-spin/animate-pulse 必须带 motion-safe: 前缀，或者统一由全局规则接管后删掉这些前缀，保持一种写法。

### 问题 10：motion.md 的“已登记布局过渡”表过时，布局属性过渡也没有门禁

- 审计编号：`ui-motion-6`
- 位置：`.claude/skills/henji-ui-surface/references/motion.md:72`；严重度：中
- 证据：表里登记了 `LlmSettingsSection` 的 grid-template-rows，但仓库里没有这个文件，实际位置是 src/components/ui/layout.tsx:397 的 UiDisclosurePanel。表里登记了 `AssetLibrarySurface` 的 width 过渡，但该文件里只有 transition-colors/opacity（:333、:334、:367），没有 width 过渡。真正的 width 过渡在 StackedMediaUploader.tsx:308 和 TaskInputPreview.tsx:219。任何规则都不会拦新写的 transition-[height] 或 transition-[top]。
- 改法：按实际位置更新表格（.claude 和 .codex 两份同步，然后跑 check:skill-sync）。在 .eslintrc.json 加 no-restricted-syntax：对 /transition-\[[^\]]*(width|height|padding|margin|top|left|max-height|grid-template)/ 报错，已登记的 5 个文件用 overrides 豁免，这样表格就由门禁自动维护。

### 问题 11：提示词优化逐字动画：每个字的 span 都永久挂着 will-change，而且 transform 对 inline 元素无效

- 审计编号：`ui-motion-11`
- 位置：`src/index.css:905`；严重度：低
- 证据：index.css:905-909 的 .prompt-optimize-preview__glyph 设置了 display:inline、animation 180ms、will-change: opacity, transform。PromptOptimizationPreviewText.tsx:20 每个字生成一个 span，数量随流式输出增长。keyframe promptOptimizeGlyphIn 里的 translateY(0.18em) 作用在非替换 inline 盒上，不会生效；will-change 在动画结束后也不会撤销，每个字都会形成独立的层或叠放上下文。
- 改法：删掉 will-change；位移要么去掉，要么把字改成 inline-block（同时注意换行）。在 performance.md 写一条：will-change 只能在交互期间临时挂上（参考 useImageEditorViewportNavigationGestureV3.ts:77/120 的做法），禁止写在会批量生成的元素的静态类上。
