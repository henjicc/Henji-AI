## 任务目标

智能区域分析与跟踪在撤销重做、停止、取消、素材被覆盖等情况下都能给出终态，导出前的等待不会永久挂起。

## 当前情况

- 渲染层等待在 `src/features/videoEdit/application/videoEditSmartRegions.ts`、`videoEditTracking.ts`（跟踪已有 `exportRequests` 租约，智能区域没有）。
- 主进程服务在 `electron/main/services/smart-regions/service.ts`、`electron/main/services/tracking/service.ts`；测试 `service.test.ts` 只覆盖“取消后旧任务结束再 ensure”。
- 这两条“导出永久挂起”都是高严重度，用户只能手动取消导出。

## 实施方案

渲染层：智能区域复用跟踪的等待租约模式；等待逻辑遇到 idle 状态按已有 attempts 规则重跑一次。租约释放前返回快照所需蒙版，导出与嵌套跟踪继续消费该快照。主进程：`ensure` 遇到已取消任务时等旧任务结束后重新请求；取消标志在作业提交前最后检查，成功分支同样遵守取消标志；跟踪探测缓存键加入每次重新读取的文件身份。

### 缺陷 1：导出前等待智能区域分析无租约：任一领域变更触发 reconcile 删除条目并取消分析后，导出永久挂在 running

- 排查编号：`veapp-0`
- 位置：`src/features/videoEdit/application/videoEditSmartRegions.ts:170`；相关：`src/features/videoEdit/application/videoEditExport.ts`、`src/features/videoEdit/application/videoEditTracking.ts`
- 严重度：高；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：前提：某片段挂了带智能区域的效果（人脸打码或背景虚化）并且已经启用，导出开始时这段区域分析还没有完成（条目状态为 analyzing，或者由 wait 内的 ensure() 新建）。
  1. exportVideoEdit 对 structuredClone 出来的快照调用 waitVideoEditSmartRegions。
  2. 分析完成之前，用户在同一剪辑里做了某个操作，让当前文档不再需要这个请求。例如：撤销或删除该效果、删除片段、修改区域类型、修剪片段使取整后的源范围变了、改速度。导出期间编辑并没有被禁止。
  3. 这个操作经 publishVideoEditDomain 触发 reconcile()。neededRequests() 只看打开着的实例的当前文档，于是对该 key 执行 entries.delete，并发出 smartRegions.cancel，整个过程不调用 publish()。
  4. 之后：onProgress 的守卫 `entries.has(key)` 把主进程推来的 ready/failed 都丢掉；check() 得到的状态是 undefined，既不 reject 也不 resolve。
  5. 结果：导出任务一直停在 running、进度 0（busy=true，阻塞这个剪辑后续的导出），只能由用户手动取消。
  同源路径：prepareSequenceTracking 里对嵌套序列 composition 的等待。即使用户没有修改文档，只要 ensure() 临时新建的请求不在 neededRequests() 的结果里（判断条件不同，例如范围计算不一致），任何一次领域变更都会把它删掉并挂起。
- 修法：仿照 videoEditTracking.ts 的 exportRequests 租约，在 videoEditSmartRegions.ts 里实现：
  1. 增加模块级的 `const waitLeases = new Map<object, Map<string, SmartRegionRequest>>()`。
  2. waitVideoEditSmartRegions 在调用 ensure() 之前登记 `const lease = {}; waitLeases.set(lease, requests)`，并且无论 resolve、reject 还是 abort，都在 finally 里执行 `waitLeases.delete(lease)`。删除之后再调用一次 reconcile()，让不再被需要、仍在分析的请求被正常取消。
  3. neededRequests() 把所有租约里的请求合并进 needed。这样 reconcile 不会删除或取消导出正在等待的请求，onProgress 推来的状态也能继续记录。
  4. 兜底：check() 遇到 status 为 undefined 时，按失败处理并 reject（例如提示「所需区域分析已被取消，请重新导出」）；reconcile() 在删除了条目时调用 publish()，让正在等待的 check 能收到通知。即使以后还有别的删除路径，也不会无限等待。
  验证方法：在 videoEditSmartRegions.test.tsx 里加一个用例，步骤为「等待 → undoVideoEdit 撤掉效果 → 用 progress 推 ready」，断言 wait 能 resolve，并且这期间不会对该请求调用 cancel。另外补一个用例覆盖 prepareSequenceTracking 的嵌套 composition 路径。
- 测试缺口：src/features/videoEdit/application/videoEditSmartRegions.test.tsx 里的「导出前等待区域分析：完成后继续；失败时给出用户语言的原因」和「嵌套导出等待子序列智能区域」两个用例，在等待期间都没有修改当前文档、没有触发 reconcile，所以没覆盖到条目被删、进度被守卫丢弃的情况。tracking 一侧有租约，smart regions 一侧没有对应的测试。

### 缺陷 2：导出前等待跟踪：用户在准备阶段点“停止”把状态记为 idle 后，waitVideoEditTracking 既不重跑也不结束

- 排查编号：`veapp-4`
- 位置：`src/features/videoEdit/application/videoEditTracking.ts:254`；相关：`src/features/videoEdit/application/videoEditExport.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：前提：导出（videoEditExport.ts:96 → waitVideoEditTracking）正在等某个跟踪定义，该定义还处在渲染层准备阶段，即 preparing 里有 controller。实际可稳定命中的是嵌套序列源：prepareSequenceTracking 要先等子序列的跟踪和智能区域完成，这段时间可能很长。这时用户在跟踪面板点“停止”（准备期状态是 tracking，按钮可用），stopVideoEditTracking 先 abort，再 record({state:'idle'})。之后 tracking.run 不会发出，主进程也没有 job 可停、不会 emit 进度，check() 却把 idle 当成“与我无关”跳过，导出永久挂起，直到用户手动取消。
  补充一点：如果是普通文件源，而且 stop 恰好落在 run 的 IPC 往返期间，主进程那边的 run 往往会照常建 job 并推送进度，等待最终能收敛（不过这时“停止”实际没生效，属于另一个小问题）。所以必挂的路径是嵌套源，或者主进程确实没有建 job 的情况。现有测试“导出等待使用的跟踪；停止后仅续跟一次…”只覆盖了 ready+stopped 分支。
- 修法：改 waitVideoEditTracking 的 check()（videoEditTracking.ts:254 附近）：如果某条请求的状态是 idle（或者没有状态），并且结果没有覆盖 request.range，就按现有 attempts 规则处理。attempts<1 时 attempts+1，置 pending=true，调用 runVideoEditTracking(request.definition, request.range, {direction:'both'})；已经重跑过一次仍是 idle 时，finish() 并 reject(new Error('跟踪已被停止，导出无法继续，请重新开始跟踪后再导出'))。也可以把重跑条件从 `status?.state !== 'ready'` 放宽为 `status?.state !== 'ready' && status?.state !== 'idle'`，复用同一套 attempts 逻辑，再在 attempts 用尽时对 idle 显式 reject。另外建议在 videoEditTracking.test.tsx 补一个用例：run 挂起期间调用 stopVideoEditTracking，断言等待会重跑或报错。
- 测试缺口：src/features/videoEdit/application/videoEditTracking.test.tsx 中的“导出等待使用的跟踪；停止后仅续跟一次仍不满则按已有部分导出，失败与取消均结束等待”只测了停止后进度事件变成 ready+stopped 的分支，没有测准备阶段被停止、状态回到 idle 的分支。

### 缺陷 3：智能区域分析在取消后马上重新请求，会拿到已取消任务的“分析中”状态，之后不再推送任何事件，界面一直显示分析中，导出无限等待

- 排查编号：`localinfer-0`
- 位置：`electron/main/services/smart-regions/service.ts:105`；相关：`src/features/videoEdit/application/videoEditSmartRegions.ts`、`src/features/videoEdit/application/videoEditReframe.ts`
- 严重度：高；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：片段上的“人脸/人物/文字”作用区域还在分析中（包括首次使用时还在下载模型）时，用户撤销再重做，或者助手先删除再加回同一效果：
  1. 撤销触发 reconcile，删除渲染层条目，并调用主进程 cancel，把 job.cancelled 设为 true。
  2. 旧任务结束之前又发生了重做。渲染层 ensure 调用主进程 SmartRegionService.ensure；第 104-105 行 `if (running) return running.status` 直接复用这个已取消任务，返回 analyzing。
  3. 旧任务最终失败（被 cancelAnalysis 终止，或在 ensureModel 之后的 cancelled 检查里抛出）。第 142 行在 cancelled 加 failed 时只写日志、不广播；进度回调也被 !job.cancelled 屏蔽。jobs 中的键被删除，主进程不再有任务。
  4. 渲染层条目永远停在 analyzing。UI 没有重试入口，因为重试只在 failed 时出现；助手读到的一直是 analyzing:0%。
  5. waitVideoEditSmartRegions 永不结束，导出和跟踪等待一直挂起，直到用户手动取消。
  时间窗口：在模型下载阶段可能长达数分钟，因为 ensureModel 不可中途取消；在分析阶段是 cancel IPC 到后台进程终止之间的这段时间，用快捷键撤销/重做或助手连续操作就能命中。
  现有测试 service.test.ts 第 82-102 行只覆盖了“旧任务彻底结束之后再 ensure”的情况，没有覆盖“取消后、结束前再 ensure”。
- 修法：只改 electron/main/services/smart-regions/service.ts，不需要改渲染层。推荐做法：ensure 遇到 running 且 running.cancelled 时不复用这个任务。
  方案 A（简单）：把 running.cancelled 改回 false，让旧任务继续跑并正常 publish 结果。需要注意，如果 cancelAnalysis 已经把后台进程杀掉，旧任务会以 failed 结束并被广播，渲染层会显示失败、需要重试，体验差一些，但不会挂起。
  方案 B（更好）：ensure 遇到已取消任务时，等待 running.done（catch 吞掉错误），然后重新走 cached 和 start 的流程，把新任务的状态返回或广播出去。也可以在 start 的 then 里判断：如果 job.cancelled 且期间有新的请求方，记一个 `rerequested` 标记，jobs.delete 之后立即 this.start(key, request, identity)。
  另外，wait() 走的也是同一路径，要一并检查：它拿到的 job.done 可能是已取消任务的 failed。
  附带发现：run() 只在 ensureModel 之后检查 cancelled。如果 probe、prepareTemporary 期间被取消，cancelAnalysis(job.id) 会早于 analyze 注册，任务仍会跑完。建议在调用 analyze 之前再检查一次 job.cancelled。
  回归测试要补在 service.test.ts：ensure → cancel → ensure → 旧任务以 cancelled 拒绝，之后应出现新的 analyze 调用，或者广播一个终态；还要覆盖 ensureModel 挂起时取消再 ensure 的情况。
- 测试缺口：electron/main/services/smart-regions/service.test.ts 的用例“失败原因…取消不广播失败，之后可重新开始”（第 82-102 行）是先让被取消任务 reject 并 flush，然后才再次 ensure。它从没测过“cancel 之后、旧任务结束之前再 ensure”的时序，也没有覆盖 ensureModel 挂起期间的取消。渲染层也没有“撤销/重做同一智能区域效果后，waitVideoEditSmartRegions 能结束”的测试。

### 缺陷 4：智能区域请求的起点按整秒向下取整，可能早于容器起点；这时 FFmpeg 从容器起点解码，结果头仍写取整后的 startUs，遮罩整体错位

- 排查编号：`localinfer-2`
- 位置：`electron/main/services/smart-regions/service.ts:173`；相关：`electron/main/services/local-inference/frameReader.ts`、`electron/main/services/local-inference/analysis.ts`、`src/platform/contracts/smartRegions.ts`、`src/core/videoEdit/smartRegions.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：素材的容器 start_time 不是整秒时，只要请求起点取整后早于容器起点就会出问题。例如 MTS/M2TS 的 start_time=1.4s，片段从素材开头用，源入点约 1.4s；或者请求从 0s 开始而素材 start_time&gt;0。具体过程：normalizeSmartRegionRange 把 1.4s 向下取整到 1.0s，service 算出 seekSeconds=0，FFmpeg 不加 -ss，从容器起点 1.4s 开始解码出第 0 帧，但结果头记的 startUs 是 1.0s。之后人脸、人物、文字遮罩全都比画面提前 (containerStart - floor(start)) 秒，可能接近 1 秒，导致打码或抠像对不上运动物体。MP4 的 start_time 一般是 0.02–0.07s，误差只有 1–2 帧；MTS/TS 这类素材误差明显。错位的结果会按内容身份存进缓存索引，之后被覆盖范围的请求都会复用这份错位数据。
- 修法：在 SmartRegionService.run 里（electron/main/services/smart-regions/service.ts 第 170–175 行附近）按实际解码起点来算：analysisStartUs = max(request.startUs, containerStartUs)，seekSeconds = (analysisStartUs - containerStartUs)/1e6，durationSeconds = (request.endUs - analysisStartUs)/1e6，并把 analysisJob.startUs 设为 analysisStartUs，这样 analysis.ts 写进结果头的第 0 帧时间就和实际一致。索引条目和返回的 SegmentRef 继续用请求范围 request.startUs/endUs 判断覆盖：容器起点之前本来没有画面，smartRegionFrameAt 会把起点之前的时间夹到第 0 帧。如果 request.endUs &lt;= containerStartUs，应按 decode 失败处理或返回空段。
  另外在 service.test.ts 补一个用例：probe.startSeconds=1.4，请求 startUs=1.4e6，断言 job.startUs === containerStartUs + seekSeconds*1e6。现有用例的 startSeconds 是 0.5，请求取整后是 2.0s，始终大于容器起点，所以覆盖不到这个分支。还可以顺带检查 tracking/service.ts 用 containerStartUs 的地方是否有同样的不对称（我没有深入核对）。
- 测试缺口：electron/main/services/smart-regions/service.test.ts 的“按整秒范围分析一次”用例只测了 probe.startSeconds=0.5、请求取整后 2.0s 大于容器起点的情况。请求起点取整后早于容器起点（seekSeconds 被夹到 0）这条分支，以及结果头 startUs 和实际第 0 帧对应时间是否一致，都没有测试覆盖。

### 缺陷 5：跟踪服务按“路径+方式+提示”永久缓存素材身份和探测结果，素材文件被覆盖后仍复用旧内容的跟踪结果

- 排查编号：`localinfer-3`
- 位置：`electron/main/services/tracking/service.ts:71`；相关：`electron/main/services/media/content-identity.ts`、`src/platform/contracts/tracking.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：在同一主进程生命周期里，用户对本地文件 D:/clip.mp4 跑过任意 status/run/candidates（会建立 prepared 缓存），之后在外部用同名文件覆盖它（size/mtime/ctime 或 inode 变化）。再次调用 status() 时，仍用旧 identity 算出的结果键 locate 到旧 .htrk，直接返回 ready，于是旧视频的跟踪遮罩会套到新视频上。run() 会把旧结果当 found/existingPath 续跟，新旧内容混在同一份结果里。ensureCovered（导出前）也走这条路径。旧 probe 的 fps、尺寸和 startSeconds 同样被沿用，会让帧号换算和候选（candidates）的 containerStartUs 出错。只有 prepare 失败或缓存条目超过 64 条被挤出时才会恢复。source 为对象（帧提供方，带 signature）的分支不受影响，因为它的键本身包含 signature。
- 修法：在 electron/main/services/tracking/service.ts 的 prepare() 里，对字符串 source 每次都先 await this.deps.identity(source)（只做 realpath+stat，开销很小）。然后改用 identity（或 trackingDefinitionKey+identity）作为缓存键缓存 probe 和 fps，让结果键随文件版本变化。也可以保留现在的 definitionKey 缓存，但在 Prepared 里同时存 identity，命中时重新算 identity，不一致就丢弃重算。失败时仍删除对应条目。补一个测试：两次 status 之间改变 identity 后，locate 的 key 应该不同，probe 也应该重新调用。
- 测试缺口：electron/main/services/tracking/service.test.ts 和 src/features/videoEdit/application/videoEditNestedTracking.test.ts 都把 identity 写死为常量，没有测试同一路径的素材内容变化后结果键是否跟着失效。

- 位置：`electron/main/services/tracking/service.ts:201`；相关：`electron/main/services/local-inference/host.ts`、`electron/main/services/smart-regions/service.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：TrackingService.execute（electron/main/services/tracking/service.ts:200-212）只在 `await this.models()` 之后检查一次 `job.stopped`，之后还有三处 await 才调用 `deps.track`：`results.prepareTemporary`、对 trackingJob 字面量求值时的 `await this.deps.ffmpegPath()`，以及 track 内部的 send。用户在这段时间点“停止”时，stop() 把 job.stopped 设为 true，并调用 inference.cancel(job.id)。但 LocalInferenceHost.cancel（local-inference/host.ts:121）在 pending 里还找不到这个 id，于是什么也不做。随后 track 正常提交并跑完整个范围，返回 stopped:false。execute 正常 resolve，走的是 then 的成功分支，所以不会读 job.stopped，最终发布普通 `{state:'ready'}`，没有 stopped 标记。用户看到“停止”没有生效，跟踪一直跑到范围结束。
  SmartRegionService.run（smart-regions/service.ts:156-175）同理：模型循环内最后一次检查 `job.cancelled` 之后，还有 deps.probe（ffprobe 子进程）、segments.prepareTemporary、ffmpegPath 三处 await。这期间调用 cancel() 也会丢失，analyze 照常跑完，然后发布 ready 并写入缓存与索引。start() 只在 failed 时屏蔽广播，cancelled 加 ready 不会屏蔽。
  dispose() 发生在同一窗口时，同样只能靠 send 里的 `this.disposed` 拦截，这一路宿主会拒绝；但服务层的 job 仍会占住 jobs，直到 send 被拒绝。
  影响：后台白跑一次完整的本地推理，跟踪的“停止”需要再点一次。不会损坏数据，严重度低。
- 修法：最小修复：在服务层把取消检查推到提交前的最后一刻，并让成功分支也遵守取消标志。
  1) tracking/service.ts execute：先 `const ffmpegPath = await this.deps.ffmpegPath()`，再组装 trackingJob。在调用 `this.deps.track(...)` 前紧挨着再检查一次 `if (this.disposed || job.stopped) throw new TrackingFailure('inference', '跟踪已停止。')`。失败分支已经把 job.stopped 映射为“回到已有结果/idle”，不需要另改。prepareTemporary 产生的临时目录如需清理，可以顺手处理。
  2) smart-regions/service.ts run：同样先 await ffmpegPath，在 `this.deps.analyze(...)` 前紧挨着检查 `if (this.disposed || job.cancelled) throw new SmartRegionFailure('inference', '分析已取消。')`。这条错误会走现有的“已取消不广播失败”分支。
  备选（更彻底）：让 LocalInferenceHost 记住 send 之前就被 cancel 的 id（例如一个短期 Set），send 命中时立即以 LocalInferenceFailure('cancelled') 拒绝。这样 candidates 等其他入口也一并受保护。但它要求服务层先拿到 id 再调用 cancel，并要防止 Set 泄漏，所以优先采用服务层的检查。
  补测试：在 tracking/service.test.ts 和 smart-regions/service.test.ts 各加一个用例。做法是让 prepareTemporary 或 probe 卡在 gate 上，期间调用 stop/cancel，断言 track/analyze 没有被调用，且最终状态为 idle/stopped，或者不广播 ready。
- 测试缺口：electron/main/services/tracking/service.test.ts 完全没有停止相关用例。electron/main/services/smart-regions/service.test.ts 第 96 行附近的取消用例只覆盖 analyze 已经提交之后的取消（cancelAnalysis 命中已入队的作业），没有覆盖模型就绪之后、analyze 提交之前的窗口。
