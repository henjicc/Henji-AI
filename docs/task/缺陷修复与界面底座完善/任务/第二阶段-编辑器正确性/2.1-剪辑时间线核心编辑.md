### 缺陷 1：覆盖（overwrite）切出的左右两段不裁剪关键帧与效果曲线，整次覆盖被 schema 拒绝或动画错位

- 排查编号：`vecore-0`
- 位置：`src/core/videoEdit/timelineEdits.ts:389`；相关：`src/core/videoEdit/keyframes.ts`、`src/core/videoEdit/document.ts`、`src/core/videoEdit/dropPlacement.ts`
- 严重度：高；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：序列中片段 a（start=10，duration=60）带任意关键帧（clip.curves，如 opacity {0→0, 59→1}）或内置效果曲线（effects[].builtin.curves）。以 overwrite 模式把一段 10 帧素材放在第 40 帧（覆盖按钮、节目监视器“覆盖/放在顶层/添加到末尾”、拖放 'end'/'top' 模式、替换所选片段、标题模板放置都走 dropPlacement → mode 'overwrite'）。placeClips 的 overwrite 分支把 a 切成左段（10–40，duration 30）与右段（50–70，duration 20），但两段仍原样携带 time=0/59 的关键帧：左段 time 59 ≥ 30，右段 time 0/59 未按 (end - clip.start)=40 前移且 59 ≥ 20。随后 videoEditDocumentSchema.parse（document.ts:195/197 assertVideoEditKeyframeTimes）抛“time 越界”，宿主 applyVideoEditDocument 失败，整次覆盖丢失；若关键帧恰好都 < 新时长则不报错但右段动画整体早 40 帧播放。insert 模式不受影响（走 splitVideoEditClip，已正确裁剪）。
- 修法：在 src/core/videoEdit/timelineEdits.ts placeClips 的 overwrite 分支（:389-390）与 document.ts splitVideoEditClip 对齐：
  - 左段：`const leftPart = { ...sliceVideoEditClipKeyframes(clip, 0, edit.frame - clip.start), duration: edit.frame - clip.start }; delete leftPart.fadeOutFrames`（淡出不再属于左段，因为左段结尾现在是覆盖切口）。
  - 右段：先 `const sliced = sliceVideoEditClipKeyframes(clip, end - clip.start, clip.start + clip.duration - end)`，再基于 sliced（而非原 clip）structuredClone、重新分配 effects id、设置 start=end、duration、`...splitVideoEditClipSource(clip, end - clip.start, sequence.frameRate)`；若左段存在则 `delete right.fadeInFrames`（淡入只留左段）。注意 sliceVideoEditClipKeyframes 已覆盖 effects[].builtin.curves，现有 effects 重新生成 id 的 map 应作用在 sliced.effects 上。
  - 需从 './keyframes' 导入 sliceVideoEditClipKeyframes（timelineEdits.ts 目前未导入）。
  - 补测试到 src/core/videoEdit/timelineEdits.test.ts：被覆盖片段带 curves.opacity 与一个带 builtin.curves 的效果，overwrite 后断言左段关键帧 time < 左段时长、右段关键帧 time 已减去 (end - clip.start) 且 < 右段时长、淡入/淡出归属，以及 videoEditDocumentSchema.parse 不抛错。
  验证：`npx vitest run src/core/videoEdit/timelineEdits.test.ts src/core/videoEdit/keyframes.test.ts src/core/videoEdit/dropPlacement.test.ts`。
- 测试缺口：src/core/videoEdit/timelineEdits.test.ts 中的 overwrite 用例（“插入和覆盖只选择实际放置片段…”:30、“完整音画覆盖后左右各自关联…”:43、:183 的 overwrite 用例）都对被切开的片段做了 duration/start/链接断言并通过 schema parse，但被覆盖的片段均不带 curves 或效果曲线，因此关键帧裁剪缺失从未被触发；与 keyframes.test.ts / reframe.test.ts 只直接测 sliceVideoEditClipKeyframes 本身，不覆盖 overwrite 路径。

### 缺陷 2：非波纹改速度 / 比率拉伸时，同轨相邻且同被选中的片段互相不作为边界，结果在同一轨道重叠

- 排查编号：`vecore-1`
- 位置：`src/core/videoEdit/clipSpeedEdits.ts:64`；相关：`src/core/videoEdit/timelineEdits.ts`、`src/features/videoEdit/panels/VideoEditSpeedDialog.tsx`、`src/features/videoEdit/application/videoEditTimeline.ts`
- 严重度：高；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：同一轨道上相邻（或仅隔小空隙）的两个视频/音频片段 a、b 同时选中，关闭“波纹编辑”：(1) Ctrl+R 把速度设为 <100% 或把持续时间设得更长；(2) 比率拉伸工具向右拖 a 或 b 的出点；(3) 比率拉伸工具向左拖入点。非波纹模式下每个片段计算可用空间时把其他被选中片段排除在外，于是 a 延伸进了 b 的位置（或 b 向左伸进 a），结果在同一轨道产生重叠片段，并通过 schema 与时间线编辑校验直接写入文档和撤销栈。单选时行为正确（现有 clipSpeedEdits.test.ts 只覆盖单选）。
- 修法：在 src/core/videoEdit/clipSpeedEdits.ts：
  1. applyVideoEditSpeedChange 非波纹分支（:64）：计算 room 时只排除片段自身，不排除其他被编辑片段，即 `nextStart(sequence, clip, new Set([clip.id]), limit)`（或改 nextStart 签名为仅排除自身）。同轨多个被选中片段各自只能用到自己与后一片段之间的空白，这与单选时“变长只用到后面片段之前的空白”的既定语义一致。
  2. applyVideoEditRateStretch（:99-100）：同样把 excluded 改为仅自身，这样共享的 delta 上限自然收紧为 min(各片段到相邻片段的空隙)；对于紧邻的 a、b，out 端 delta 收紧到 0（符合“碰到相邻片段时收紧”的注释）。
  3. 防御性兜底：在两个函数 `finish(...)` 之前，对非波纹结果调用 timelineTrims.ts 的 assertNoTrackOverlap（需导出）或在 applyVideoEditTimelineEditResult 对 speed/stretch 结果做同轨重叠校验并给出用户可读错误，防止未来回归。
  4. 在 clipSpeedEdits.test.ts 增加多选同轨相邻片段的三条用例（speed 非波纹、stretch out、stretch in），断言无重叠且各片段的收紧结果。波纹分支不受影响（它按 delta 推后后续片段），无需改动。
- 测试缺口：src/core/videoEdit/clipSpeedEdits.test.ts 的「50% 不波纹：变长只用到后面片段之前的空白」与「比率拉伸工具（R）」两组用例只用单个 clipId（'b'）调用，没有任何多选同轨片段的用例，因此无法暴露 excluded=ids 导致的互不作边界问题。

### 缺陷 3：嵌套时只平移标注的 frame，不平移 endFrame 与 range 目标，含时间段标注的选区无法嵌套

- 排查编号：`vecore-2`
- 位置：`src/core/videoEdit/nestedSequences.ts:55`；相关：`src/core/videoEdit/annotations.ts`、`src/core/videoEdit/document.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：父序列片段 a（start=30, duration=60）上挂一条带 clipId='a' 的标注。情形 A：range 标注 {frame:40,endFrame:60,target:{kind:'range',startFrame:40,endFrame:60,clipIds:['a']}}（可由助手 change_application_entities 创建）；对 a 执行嵌套（VideoEditNestDialog 或 nest_video_edit_clips 能力）→ 子序列标注 frame=10 但 endFrame=60、target.startFrame=40，nestVideoEditClips 内部 videoEditDocumentSchema.parse 抛出 zod 自定义错误“时间段标注的定位帧、结束帧必须与目标范围一致（含两端）。”，嵌套整体失败，用户/助手收到原始 ZodError。情形 B：点/区域/元素标注带 endFrame（例如 frame:40,endFrame:70，拆分片段后的 element 标注或 askAssistantAtVideoEditFrame 复用的标注）→ 嵌套不报错，但子序列中标注为 [10,70] 而非 [10,40]，时长被从 31 帧拉长到 61 帧，且 endFrame 可能超出子序列实际长度。
- 修法：在 src/core/videoEdit/nestedSequences.ts:55 改为 `annotations: parent.annotations.filter(anchored).map(value => mapVideoEditAnnotationTime(value, frame => frame - start))`（从 './annotations' 导入 mapVideoEditAnnotationTime；该函数已同步处理 frame、endFrame 与 range target 的 startFrame/endFrame）。可选补强：对 range 目标的 clipIds 过滤为 ids 内的片段（`clipIds: target.clipIds?.filter(id => ids.has(id))`，空数组时删除该字段），避免子序列标注引用留在父序列的片段。验证：在 src/core/videoEdit/nestedSequences.test.ts 增加两条断言——range 标注嵌套后 {frame:10,endFrame:30,target:{startFrame:10,endFrame:30}}；带 endFrame 的点标注嵌套后 [frame,endFrame]=[10,40]；跑 `npx vitest run src/core/videoEdit/nestedSequences.test.ts`。
- 测试缺口：src/core/videoEdit/nestedSequences.test.ts 第一个用例「嵌套保持源时钟与锚点，仅在父序列替换选区」断言了 markers?.[0].frame 和 captions?.[0].start 的平移，但没有在 parent.annotations 里放任何标注，因此未覆盖 annotations 的 endFrame 与 range target 平移。

### 缺陷 4：文本摘选同样只映射标注 frame，endFrame/range 目标不变，插入摘选时被 schema 拒绝或标注拉长

- 排查编号：`vecore-3`
- 位置：`src/core/videoEdit/textEdits.ts:36`；相关：`src/core/videoEdit/annotations.ts`、`src/core/videoEdit/nestedSequences.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：textEdits.ts:36 的 extractVideoEditTextRanges 只用 mapFrame 映射 annotation.frame，endFrame 和 range 目标的 startFrame/endFrame 都保持原序列时间。
  (a) extract 动作：若摘选范围内有 range 目标标注，生成的新序列 frame≠target.startFrame，加入文档时被 schema 拒绝，整个「文本摘选为新序列」操作失败。若是 point/region 等目标的时间段标注，endFrame 原样保留，不会报错，但会超出摘选序列（例：clip 0–60，标注 10–120）。
  (b) insert 动作：不会像原发现说的那样被 schema 拒绝。原因是 placeClips（timelineEdits.ts:406）里的 mapVideoEditAnnotationTime 会把 target 重新对齐到 frame/endFrame。但 endFrame 是按原时间偏移平移的，标注会被拉长：本例插入在 200 时结果为 210–320，应为 210–250，超出插入内容。
  (c) 多段选区时，若 frame/endFrame 落在被删的间隙里，同样没有裁剪或丢弃。现在 frame 由 mapFrame 夹到相邻选区边界，而 endFrame 完全没处理。
- 修法：在 textEdits.ts:36 把 annotations 改为先按选区裁剪，再整体映射：
  1. 对每个标注取区间 [frame, endFrame ?? frame]，与 selected 求交。没有交集的丢弃（与 markers/captions 的处理一致）。
  2. 有交集的，把 frame/endFrame 夹到交集内的首个、末个有效帧，再用 mapVideoEditAnnotationTime(value, mapFrame) 映射，让 range 目标的 startFrame/endFrame 同步更新。endFrame 是闭区间，夹到 range.to-1 再映射，避免落到下一段的起点。
  3. range 目标的 clipIds 若引用了已删片段，按存活片段过滤。
  补测试：在 textEditing.test.ts 的摘选用例中加入 point 时间段标注和 range 目标标注，断言 excerpt 能通过 videoEditDocumentSchema，标注为 [10,50]；insert 后标注长度保持 40 帧。
- 测试缺口：src/core/videoEdit/textEditing.test.ts 中「extracts disjoint ranges into a new compact sequence and inserts at the playhead」的夹具没有 annotations。它的 schema 断言因此测不到时间段标注或 range 目标标注的映射。

### 缺陷 5：滚动编辑（roll）多选同轨相邻片段时没有重叠校验，左段延长会盖住右段

- 排查编号：`vecore-4`
- 位置：`src/core/videoEdit/timelineTrims.ts:130`；相关：`src/core/videoEdit/timelineEdits.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：用户可以通过界面触发这条路径，不需要人为构造多选。步骤：同一轨道上把相邻的 a、b 编组（Ctrl+G 写入同一个 groupId），右侧还有 c。用滚动工具（N）抓住 a 的出点向右拖 20 帧，或者让助手对 a 调用 trim_video_edit_clip(mode:'roll', edge:'out', frames:20)。expandVideoEditSelection 按编组把 b 也展开进 clipIds。roll() 里 a 的配对右侧片段和 gap 计算都把同样被选中的 b 排除了，于是 a 的上界变成 c.start - end(a)；b 又与 c 单独组成一个编辑点。结果 a 和 b 都变成 80 帧长，a=10..90 与 b=70..150 重叠 20 帧，最后写入文档并进撤销栈，期间没有任何报错。roll 的 in 端情况对称：b 的左侧片段排除了 a，gap.previous 取到 a 之前的结束点。另外，同轨多个片段在同一次 roll 里都被改，本身就违背"移动一个编辑点、总长不变"的语义。现有测试 timelineTrims.test.ts 的滚动编辑用例只覆盖单个片段（a / b / a-sound），没有同轨多片段或编组的场景。
- 修法：在 src/core/videoEdit/timelineTrims.ts 的 roll() 里改：
  (1) 查找配对时，同一轨道上紧邻的被选中片段不应排除。out 端用 adjacent(clip,'after', 空集)，in 端用 adjacent(clip,'before', 空集)；gap() 也改用只排除自身的集合。这样 a|b 这类同一编辑点算作一个配对，用 pairs 的 key 去重。b 作为右段后，不应再与 c 组成另一个编辑点。可选的规则是：某片段若已作为本次编辑点的右段（out 端）或左段（in 端），就跳过它自己的配对；或者同一轨道只保留选区中最靠前（out 端）/最靠后（in 端）的那一个编辑点。
  (2) 与 ripple/slide 保持一致，在 roll 返回前对结果调用 assertNoTrackOverlap(clips, '滚动编辑会让片段重叠，请调整范围。')，作为兜底。
  (3) 在 timelineTrims.test.ts 补用例：同轨编组的 a、b 做 roll out +20，结果应无重叠，且序列总长不变。
  slide 也用了同一种 adjacent/gap 排除逻辑，但它已有 assertNoTrackOverlap，最多误报错误，不会产生错误数据；修复时可以顺带核对同轨编组片段做内滑时是否被过度拒绝。
- 测试缺口：src/core/videoEdit/timelineTrims.test.ts 的「滚动编辑」用例只测单个片段（'a'、'b'、'a-sound'，后者在另一条轨道上），没有同一轨道多个被选中片段（编组或多选）做 roll 的用例，也没有对 roll 结果做重叠断言。

### 缺陷 6：改序列帧率时字幕/转场可能缩到 0 帧或不足 2 帧，只有片段有前置校验，用户看到原始 zod 报错

- 排查编号：`vecore-5`
- 位置：`src/core/videoEdit/document.ts:389`；相关：`src/core/videoEdit/transitions.ts`、`src/core/videoEdit/timedContent.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：在 60fps 序列中，下面两种情况会让 changeVideoEditSequenceSettings 抛出原始 ZodError，整次序列设置修改失败；无论从界面的序列设置还是助手属性写入（video_edit.sequence）改帧率都会遇到：
  - 一条字幕在新帧率下换算后为 0 帧。例如 start=0、duration=1，改成 24fps 后 round(0.4)-0=0。能否触发取决于起点，start=1 时换算结果为 1，不会触发。
  - 一个转场换算后少于 2 帧。2 帧或 3 帧的转场改成 24fps 后 convert 结果都是 1，必定触发。
  用户看到的是 "Too small: expected number to be >=1/2" 这样的 zod JSON，而不是片段那种“请先调整…”的可读提示。降帧率的比例越大（例如 120→24），能触发的字幕和转场长度范围越大。
- 修法：在 src/core/videoEdit/document.ts 的 changeVideoEditSequenceSettings 中补下限，二选一，与片段处理方式一致即可：
  (a) 下限钳制：字幕 duration 取 Math.max(1, convert(start+duration)-convert(start))；转场 const frames = Math.max(2, convert(transition.durationFrames))，然后同时传给 resizeVideoEditTransition(transition, frames, convert) 和 framesBeforeCut 的 Math.min 上限。fadeInFrames/fadeOutFrames 已经这样处理。钳制时要注意：字幕延长后不能越过所属片段或序列的边界（可沿用 reconcileVideoEditTimedContent 的约束）；转场 frames=2 时还要能放进相邻片段的余量。
  (b) 像片段一样提前校验，抛出中文可读错误，例如“新帧率会使部分字幕/转场过短，请先调整后再修改帧率”。
  建议选 (a) 或在 (a) 基础上兜底 (b)，并在 transitions.test.ts 或 keyframes.test.ts 补用例：60→24fps，1 帧字幕（start=0）和 2 帧转场不应抛出 ZodError。
- 测试缺口：src/core/videoEdit/transitions.test.ts:58 的帧率转换用例只用了 30 帧转场（60→30fps），src/core/videoEdit/keyframes.test.ts:115 只测片段关键帧换算。没有用例覆盖字幕或短转场在降帧率后跌破 schema 下限的情况。

### 缺陷 7：粘贴时随片段复制的时间段标注按剪贴板最早片段起点换算，早于该起点的部分会变成负帧且负数取整偏差 1 帧

- 排查编号：`vecore-6`
- 位置：`src/core/videoEdit/timelineEdits.ts:361`；相关：`src/core/videoEdit/time.ts`、`src/core/videoEdit/annotations.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：前提：一条范围标注跨多个片段（clipIds 含 a、b），且标注起点早于被复制片段中最早的起点。
  - 只复制 b(70–130) 时，copyVideoEditClips 会把整条标注 {20..100} 带进剪贴板。
  - placeClips 按 from=70 换算：标注起点偏移是 -50；rescaleVideoEditFrame 对负数向零截断，结果是 -49。
  - 两帧率相同时：粘贴到 200 帧，标注变成 151..230（应为 150，或应裁到 200..230）；粘贴到 0 帧，标注 frame/startFrame 为 -49，文档 schema（frame>=0）不通过，粘贴会被拒或产生非法数据。
  - 偏移为负、且需要四舍五入时（相同帧率下的 .5 情形，或不同帧率），都会多出 1 帧偏差。markers 和 captions 只取片段内的数据，偏移不为负，不受影响。
- 修法：1. placeClips（timelineEdits.ts:404-405）：映射前，把剪贴板中的范围标注裁到被复制片段的时间并集内，至少裁到 [from, max(clip.start+duration)]，即只保留与这些片段相交的部分；完全不相交的丢弃。裁剪后偏移不会为负，结果也符合"只复制了 b"的语义。
  2. time.ts rescaleVideoEditFrame：改成 floor 语义的四舍五入，让负数结果正确。做法是 n*2n+d 为负时先按 floor 处理，例如 q = (n*2n+d)/(2d)，再在余数为负时减 1n。改完后需要回归 document.ts:388（序列改帧率）、videoEditService.ts:387、videoEditDrop.ts:80 这三处调用；它们的输入一般非负，行为应当不变。
  3. 在 annotations.test.ts 或 timelineEdits.test.ts 补一条用例：跨两个片段的标注只复制后一个片段，粘贴到 0 帧和 200 帧，断言起点不为负、文档 schema 通过、时间不差 1 帧。
- 测试缺口：src/core/videoEdit/annotations.test.ts 中「复制范围标注随粘贴重映射目标片段和轨道…」只测了复制单个片段、且标注落在片段内的情况，没有测范围标注跨多个片段、只复制其中后一段（标注起点早于剪贴板最早片段起点）的情况。
