### 缺陷 1：选区转蒙版把矢量蒙版当普通栅格蒙版合并，矢量覆盖被忽略并在整块瓦片上被覆盖

- 排查编号：`imageedit-0`
- 位置：`src/features/imageEdit/v3/editor/selectionMaskCommitV3.ts:158`；相关：`src/features/imageEdit/v3/editor/selectionMaskLayerV3.ts`、`src/core/imageEdit/v3/selection/rasterize.ts`、`src/features/imageEdit/v3/editor/maskBrushTilesV3.ts`、`src/core/imageEdit/v3/commandReducer.ts`、`src/features/imageEdit/v3/execution/viewportCompositePixelsV3.ts`、`src/features/imageEdit/v3/export/maskRegion.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：图层蒙版是矢量蒙版（kind=sparse-mask、defaultValue=0、tiles 为空、带 vectorPaths；来自 tools/vector/service.ts attachImageEditVectorMaskV3，或扩图 core/imageEdit/v3/aiWorkflows/outpaint.ts）时，选区转蒙版会被当作可编辑的 default0 稀疏蒙版，四种组合模式都开放。(1) add：选区外接框涉及的每个 512 瓦片都以全 0 作为旧值，新瓦片只含选区覆盖；渲染和导出都用瓦片整块替换矢量栅格，这些瓦片里原有的矢量覆盖被抹掉（已复现：全覆盖矢量蒙版加选一个小矩形后，(40,40) 从 1 变为 0）。(2) replace/intersect 不清除 vectorPaths，选区没触及的瓦片继续显示原矢量覆盖（已复现 vectorPaths 保留）。(3) subtract 的 plan 只遍历已有栅格瓦片，对纯矢量蒙版完全不生效。
- 修法：推荐做法：在 selectionMaskCommitV3.ts 的 editableMask 判定和 selectionMaskLayerV3.ts 的 imageEditorSelectionAllowedCombineModesV3 中，把带 vectorPaths 的蒙版也视为不可增量编辑（追加 `&& !mask.vectorPaths`），这样它只允许 replace，走 commitReplacement。commitReplacement 用 createImageEditSparseMaskReferenceV3 新建蒙版，本身不含 vectorPaths，replace 就能整体替换掉矢量覆盖。
  如果要保留 add/subtract/intersect 对矢量蒙版的支持，需要同时做到：plan 的坐标集合包含 vectorPaths 外接框覆盖的所有瓦片；rasterize 对没有已有瓦片的位置，也通过 createImageEditorMaskBrushTileLoaderV3 读出矢量覆盖作为旧值，而不是用全 0；提交时把矢量覆盖完整栅格化进稀疏瓦片，并清除 vectorPaths（用 layer.set-mask，不能只用 mask.apply-tile-delta）。
  建议在 selectionMaskCommitV3.test.ts 和 selectionMaskLayerV3.test.ts 补充矢量蒙版的用例。
- 测试缺口：src/features/imageEdit/v3/editor/selectionMaskCommitV3.test.ts 和 selectionMaskLayerV3.test.ts 只覆盖无蒙版、纯栅格 default0 和 default1 稀疏蒙版，没有一个用例针对带 vectorPaths 的蒙版的组合模式与提交结果。

### 缺陷 2：每次自动保存都重读、重哈希、重写并 fsync 全部历史页，页数还随保存次数线性增长

- 排查编号：`imageedit-1`
- 位置：`electron/main/services/image-editor-v3/history-pages/store.ts:44`；相关：`electron/main/services/image-editor-v3/document-repository.ts`、`electron/main/services/image-editor-v3/resource-store.ts`、`electron/main/ipc/image-editor-v3.ts`、`src/core/imageEdit/v3/historyPaging/checkpoint.ts`、`src/features/imageEdit/v3/application/imageEditCommandBus.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：只要编辑节奏让每次操作都单独触发一次自动保存（间隔超过 500ms 去抖）就会出现。每次保存回执后，imageEditDocumentInstances.ts:116 调用 confirmPersistedHistory，把全部历史换成 cold 快照（prefixLength = checkpoint.total，undo 和 redo 为空）。下一次保存时，document-repository.persist 调用 historyPages.prepare，sourcePages 对 cold.checkpoint.pages 逐页执行 readValidatedPage（租约、verify 全量哈希、readFile、JSON 解码），再执行 stringify 和 putBufferLeased（暂存写入、fsync、link 遇 EEXIST、verifyExistingObject 再算哈希）。热尾部只有 1 条命令，由 splitImageEditHistoryPagesV3 单独成页，不与上一个未满的冷页合并。结果是第 N 次保存要处理 N 页、做 N-1 次全量哈希校验和 N 次带 fsync 的写入；实测 40 次保存后单次 prepare 从 21ms 增长到 301ms，并且线性继续增长。checkpoint 中的 pages 也线性增长，打开文档（open/restore/validate）同样要逐页读取。长会话（上千次操作）中保存期间一直持有文档锁，耗时越来越长，可能触发 30s 锁陈旧判定或保存超时。
- 修法：在 ImageEditHistoryPageStoreV3.prepare / sourcePages 中：
  (1) 对 cold.checkpoint 中完全落在 prefixLength 以内（descriptor.start + descriptor.count <= prefixLength）的页，直接复用原描述（resourceId、byteSize、count，start 按顺序重算），不再执行 readValidatedPage 和 putBufferLeased，只对该页 resourceId 取一次租约。资源引用（retained）直接取自 cold.checkpoint.resources 中这些页的引用；如果无法按页区分，就合并整份 checkpoint.resources，并在只有截断时才读取被截断的那一页。命令 ID 与 revision 顺序可改用 cold.commandIds 校验，不必读页。
  (2) 只对被 prefixLength 截断的最后一页，以及末尾未满 IMAGE_EDIT_HISTORY_PAGE_ENTRIES_V3 的冷页，读出条目后与热尾部（tail undo/redo）合并，再交给 splitImageEditHistoryPagesV3 重新切页，使页数保持在约 total/64。
  (3) 资源 acquireLease 和 describe 只对新增引用执行。
  补充回归测试（加到 history-pages/store.test.ts）：循环「execute 1 条 → prepare → 用 toReference 形状构造 cold → history.restore」N 次，断言最后一次 prepare 的 putBufferLeased 次数 ≤ 2、verify 次数 ≤ 1，页数 ≤ ceil(N/64)+1，并且 restore(checkpoint) 能完整撤销全部 N 条命令。
- 测试缺口：electron/main/services/image-editor-v3/history-pages/store.test.ts 中「新操作只重写末页，移动游标不重写既有不可变页」只对同一份未冷化快照连续 prepare 两次，没有覆盖「prepare → confirmPersistedHistory 转冷 → 再 prepare」的多轮循环，也没有断言页数受限或冷页不被重读和重写。

### 缺陷 3：去重写入的画笔/蒙版瓦片既不刷新 mtime 也不加租约，GC 的“60 秒年龄保护”失效，可能删掉尚未保存的引用

- 排查编号：`imageedit-2`
- 位置：`electron/main/services/image-editor-v3/resource-store.ts:263`；相关：`electron/main/services/image-editor-v3/brush-tile-store.ts`、`electron/main/ipc/image-editor-v3.ts`、`electron/main/ipc/image-editor-v3-brush-tiles.ts`、`src/features/imageEdit/v3/editor/selectionMaskCommitV3.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：前提：某个画笔或蒙版瓦片对象（常见的是全 1 蒙版块或纯色块）早先已经落盘，后来在保存的文档中失去引用，比如蒙版被删除或历史被裁剪。主进程只在渲染层主动请求时才做 GC，所以这个对象 mtime 是旧的，一直留在盘上。
  过程：用户再次做选区转蒙版或画笔，persistTile 去重命中，putBuffer 返回 created=false，既不刷新 mtime 也不加租约。引用暂时只在渲染层内存中，要等批量写瓦片结束、500ms 去抖后自动保存才落盘。如果在这之前有 GC 发生，对象就会被删。可能的 GC 来源：其他画布多图层文档的回收或回滚（retainedResourceRefs=[]），其他文档或本文档其他服务失败后的 collectOrphans（只带调用方单文档的引用）。
  后果：本文档后续 saveDocument 在 acquireLease 处报 Resource not found，自动保存持续失败；readTile、界面和导出也读不到该瓦片。新建（created=true）的瓦片至少有 60 秒年龄保护，去重命中的瓦片这层保护等于 0，两者行为不一致。
- 修法：最小修复：在 resource-store.ts 的 putReadable 中，当 verifyExistingObject 通过、准备 return false 时，在同一个 executor.run(id) 内执行 `await fsp.utimes(destination, now, now)` 刷新 mtime，让去重命中和新建获得相同的 GC 年龄保护。为避免与 GC 的 stat 判断交错，更稳妥的做法是在 'resource-leases' 键下执行，或在 GC 删除前重新 stat。
  更彻底的修复：persistTile 改用 putBufferLeased，与 history-pages/store.ts:64 和 layout-rebind.ts 的模式一致，把租约挂在请求或 sender 上，直到 saveDocument 确认引用落盘、或会话/窗口释放时再释放。GC 的 live 集也应并入所有已打开实例尚未保存的引用。仅刷新 mtime 仍然受 60 秒窗口限制：未保存超过 60 秒的新瓦片同样有风险，例如保存一直失败或长时间批处理。
  回归测试：在 brush-tile-store.test.ts 或 resource-store.test.ts 增加用例：持久化一次，把 mtime 改旧，再持久化同内容，然后用默认 minimumAgeMs 执行 garbageCollect(new Set())，断言对象未被删除。
- 测试缺口：resource-store.test.ts 的"按 SHA-256 去重"用例只断言 created=false 和 id 相同，没有检查去重后 mtime 是否刷新、能否抵御 GC。brush-tile-store.test.ts 中 GC 相关用例都用 minimumAgeMs: 0，只验证中止后不遗留租约，没有覆盖"去重写入后、保存前遇到默认年龄 GC"的场景。

### 缺陷 4：另存为对话框返回的路径被静默改扩展名，可能未经确认覆盖另一个已存在的文件

- 排查编号：`imageedit-3`
- 位置：`electron/main/ipc/image-editor-v3-raster-export.ts:77`；相关：`electron/main/services/image-editor-v3/tile-output-sink.ts`、`electron/main/services/fs/atomic-file.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：图片编辑 V3 导出栅格图：选 JPEG（或 TIFF/WebP/PNG/AVIF 中任一种），对话框返回的路径扩展名和该格式不符。Windows 上，用户在 JPEG 筛选器下输入 `photo.png`，png 是系统已注册的扩展名，IFileDialog 会保留它，覆盖确认只针对 photo.png（文件不存在就不提示）。也可能是用户输入了没有扩展名、但对话框没有自动补全的名字。主进程的 normalizeSelectedPath 会把目标静默改成 `photo.jpg`。如果同目录已经有 photo.jpg，导出完成时 replaceFileAtomically 直接 rename 覆盖它，用户从来没有确认过这次覆盖，原文件丢失。macOS 的 NSSavePanel 会强制或询问扩展名，基本不可达；Linux 不在 electron-builder 发布目标内。所以实际风险主要在 Windows 上输入其他已注册扩展名的情况，严重度低。
- 修法：只在 electron/main/ipc/image-editor-v3-raster-export.ts 的 normalizeSelectedPath 及其调用处修改。路径没有被改写时（扩展名已经匹配），保持现状。确实要改写时（扩展名缺失或不匹配），可以在调用 manager.start 之前用 fsp.access/lstat 检查改写后的路径：如果已存在，就重新弹出带改写后 defaultPath 的保存对话框，让系统再做一次覆盖确认（或用 dialog.showMessageBox 明确询问是否覆盖）；用户拒绝就返回 { status: 'cancelled' }，不能直接写出。另一种做法是扩展名不匹配时不改写，直接报错或重新弹框。不要做成写出时用 wx 独占创建：rename 发布本身无法独占，也会破坏用户已经在对话框里确认过的正常覆盖。补一个单测，形式和本次复现一致：mock dialog 返回 photo.png，format=jpeg，photo.jpg 已存在，断言没有在未确认的情况下用 photo.jpg 调用 manager.start；再补一个反例：扩展名已匹配且用户确认覆盖时照常导出。
- 测试缺口：electron/main/ipc/ 下没有 image-editor-v3-raster-export 的测试文件。image-editor-v3-export-payloads.test.ts 只测载荷解析，electron/preload/image-editor-v3-api.test.ts 只测 preload 通道，都没有覆盖 normalizeSelectedPath 改写路径，也没有覆盖改写后目标已存在的情况。

### 缺陷 5：受管预览物化在文档锁外读取再以同 revision 保存，会用旧历史覆盖并发的同版本历史保存

- 排查编号：`imageedit-4`
- 位置：`electron/main/services/image-editor-v3/managed-raster-materializer.ts:131`；相关：`electron/main/services/image-editor-v3/document-repository.ts`、`src/features/imageEdit/v3/application/imageEditCommandBus.ts`、`src/features/imageEdit/v3/application/imageEditPersistenceQueue.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：编辑器打开时，画布投影确认（imageEditPersistenceOwner.confirmProjection）调用 completeManagedRasterExport，主进程 ManagedRasterMaterializer.complete 在文档锁外执行 documents.loadPaged，读到历史 H1。在它执行 documents.save 之前，渲染层完成一次同 revision、只改历史的保存，例如 setSelection 时丢弃了文档重做分支，或历史被清空，写入 H2。物化随后以 expectedRevision=nextRevision=R、history=H1 保存。revision 校验能通过，document 也相同，所以 H2 被 H1 覆盖。渲染层持久化队列的 persistedHistory 已记为 H2，不会补写。如果之后没有新的编辑就关闭，重开时已丢弃的重做分支或已清空的历史会重新出现。触发需要两次写入在很短的窗口内交错，概率低，但没有任何互斥能阻止它。
- 修法：在 ImageEditDocumentRepository 中新增原子操作，例如 publishPreview(documentId, { expectedRevision, sourceFingerprint, previewRef })。它在 executor.run 和 withDocumentLock 内部用 loadCheckpoint 读取当前 envelope，校验 revision 和 createImageEditSourceFingerprint 是否与物化快照一致，然后只替换 previewRef 并用 mergePersistedImageEditResourceRefsV3 重算 resourceRefs。磁盘上已有的 history 和 historyCheckpoint 原样保留，不经 loadPaged 物化历史，也不重写历史，最后 persist。managed-raster-materializer.ts:131-145 改为调用这个方法，删除锁外的 loadPaged、指纹比较和 save 组合。另外补一个回归测试：在物化的读取和写入之间插入同 revision 历史保存，断言历史保持为后写入的版本。
- 测试缺口：electron/main/services/image-editor-v3/managed-raster-materializer.test.ts 只覆盖 publication 映射、重启和旧 session，没有测物化读取与写入之间发生并发保存的情况。document-repository.test.ts 测了同 revision 的历史保存，但没有测"读后同 revision 回写会覆盖历史"这一点。

### 缺陷 6：导出暂存文件名在目标基名上再加约 42 个字符并交给 libvips，长路径或长文件名下导出失败

- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：场景一：任意平台。用户导出时保存对话框里的文件名合法，但字节数在约 214 到 255 之间，例如 72 个以上中文字符加 .png（Linux ext4/macOS 按 255 字节计；Windows 按 255 个 UTF-16 单元计，需要约 214 个以上字符）。FileTileOutputSinkBase.begin 生成的暂存名 `.<basename>.<uuid>.tmp` 超过 NAME_MAX，导出在 complete 阶段报 "File name too long"，用户选的合法目标无法导出。
  - 转码格式（PNG/JPEG/WebP/TIFF/AVIF）在 sharp.toFile 处失败。
  - BigTIFF 走 Node 的 fs.open，同样会因 ENAMETOOLONG 失败。
  场景二：Windows，目标完整路径约 218 到 259 字符（不超过 MAX_PATH，合法）。暂存路径会超过 260，libvips 原生 API 不支持长路径，toFile 和 verifyStagedFile 里的 sharp(stagedPath) 会失败。transcoding-output-sink.ts:187-197 的注释已经实测记录过同类症状 "Input file is missing"。
  另外注意：在场景二里，中间文件 `<dir>/.<uuid>.source.btf` 本身也比目录长 49 个字符。当目录长度超过约 211 时，即使暂存名改短，中间文件仍会越过 260。这部分只能缓解，修复者需要知道。
  影响面：仅限名字或路径极长的少数情况，失败会明确抛错，并由基类 fail() 回滚，不会损坏数据，所以严重度为 low。

  4. 可选：Windows 长目录场景下，可以把 UUID 缩短（例如 12 位十六进制），进一步减小暂存文件和中间文件超出目录的长度。也可以在超过 MAX_PATH 时提前给出用户可读的错误，避免 libvips 报出难懂的 "Input file is missing"。
