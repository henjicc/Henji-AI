# 2.6 镜头参考撤销与后台渲染

## 任务状态

- 状态：待开始
- 所属阶段：第二阶段-编辑器正确性
- 前置任务：无
- 关联任务：3.3（能力层撤销回执）；`docs/rules/product-goal.md` 4.6 要求镜头参考与其他工作区共用同一撤销栈
- 是否可以并行：可以

## 任务目标

镜头参考的助手写入与用户操作共用同一撤销栈且不打乱用户视图；助手写入的关键帧停留时长生效；后台渲染等资源加载完再抓帧；模型加载失败可恢复。

## 当前情况

- 助手撤销在 `src/features/cameraStage/application/cameraStageUndo.ts`：独立的快照 `Map` 只增不减，回滚经 `loadSnapshot` 落地会重置视图与播放头。
- 用户历史在 `src/features/cameraStage/store/cameraStageStore.ts`（约 175 行起），状态关键帧在 `store/stateKeyframeSlice.ts`。
- 后台渲染窗口 `src/features/cameraStage/render/CameraStageRenderWorker.tsx` 场景提交后 32ms 即抓帧。
- `docs/rules/assistant-status.md` 第一节写明镜头参考 AI 撤销与用户历史“未核实”，本任务会改变该结论，完成后需按其第零节更新台账。

## 实施方案

把助手写入改为走 store 的普通提交并记入同一历史（撤销回执只记录历史位置），删除独立快照表；`hold` 写入路径保留值；渲染窗口等待 GLB 与贴图的加载完成信号（复用 drei 的加载状态或自建计数）后再抓帧。

### 缺陷 1：助手撤销快照 Map 只增不减，每次成功的助手写入都泄漏一份整场景克隆

- 排查编号：`camerastage-0`
- 位置：`src/features/cameraStage/application/cameraStageUndo.ts:12`；相关：`src/core/application-control/execution/engine.ts`、`src/features/cameraStage/application/cameraStageApplicationService.ts`、`src/features/cameraStage/application/cameraStageControlExecutors.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：助手在同一渲染进程会话中对镜头参考反复执行任意成功写入能力（placeObject/updateObject/applyPlayback/applyScene/updateStateKeyframe/createStateKeyframes/机位示范等 12 个捕获点中任一）。每次写入在动手前 `captureCameraStageUndo` 深克隆整场景进模块级 Map；成功路径下引擎只把 undoToken 存进 `undoRecords`（也无上限），两者都只在用户真的触发撤销或写入失败回滚时才 delete。一个 40 对象 + 40 关键帧的中等场景每份快照约 36 KB，3000 次写入即泄漏约 107 MB；场景越大（含更多对象/关键帧/动画轨道）单份越大。切换/关闭/删除文档也不会清理（`restoreCameraStageUndo` 需要跨实例可用，因此 dispose 时不清是设计使然，但也意味着永远不清）。
- 修法：1) 给 `undoSnapshots` 加有上限的 LRU（例如沿用引擎 `maxIdempotencyResults` 的量级 128/256），超限淘汰最旧 token；淘汰后 `restoreCameraStageUndo` 抛现有 `NOT_FOUND`，引擎已能把它映射为撤销失败。2) 引擎 `undoRecords`（engine.ts:84/449）同样加上限，并在淘汰 undoRecord 时逐步调用各 executor 的释放钩子（可在 `ApplicationMutationExecutor/CollectionExecutor/OperationExecutor` 上加可选 `forget?(undoToken)`，镜头参考实现为 `forgetCameraStageUndo`），让两个 Map 的生命周期一致；或至少在同一事务 undoRef 被新事务淘汰时释放对应快照。3) 可选降本：store 走不可变更新，快照可直接持有 `objects/animation/sceneSettings/stateKeyframes` 的引用而非 `structuredClone`（restore 时 `loadSnapshot` 再克隆一次即可），把每份快照从约 36 KB 降到几个指针，但仍需上限以防引用链持有旧数组。注意不要按 projectId 在实例 dispose 时批量清理——`cameraStageProjectRuntime.test.ts` 的“切换回来保留可用撤销”依赖跨实例恢复。修复后为 cameraStageUndo 补一条“超限淘汰最旧快照、最旧 token restore 抛 NOT_FOUND”的单元测试。
- 测试缺口：src/features/cameraStage/application/cameraStageProjectRuntime.test.ts 只验证 capture→restore 的单次往返（“切换回来保留可用撤销”），没有任何测试覆盖成功提交后快照的生命周期或 Map 上限；src/core/application-control/execution/engine*.test.ts 对 undoRecords 同样只测撤销路径，没有验证 undoRecords/快照在多次事务后是否有界。

### 缺陷 2：助手回滚/撤销通过 loadSnapshot 落地，会重置用户视图与播放头并混入用户撤销栈

- 排查编号：`camerastage-4`
- 位置：`src/features/cameraStage/application/cameraStageUndo.ts:42`；相关：`src/features/cameraStage/store/cameraStageStore.ts`、`src/features/cameraStage/application/cameraStageApplicationService.ts`、`src/features/cameraStage/application/cameraStageProjectRuntime.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：用户正在编辑镜头参考文档 A（它就是界面附着的 store），当前在摄像机视角、播放头在 2s。助手对 A 执行写入，随后事务补偿或助手撤销（compensate/undo/rollbackFailedPlacement 等所有路径都走 restoreCameraStageUndo）→ loadSnapshot：(1) 视口被强制切回 director，选中项清空，播放头和播放运行时归 0；(2) 回滚这次 set 被 zundo 记为新历史条目（实测 pastStates 从 0 变成 2：助手的写入一条，回滚一条）。用户随后按 Ctrl+Z，第一步就回到回滚前的失败中间态，被回滚的助手对象重新出现，自动保存还会把它落盘。这样“事务已回滚”和“场景被改动”同时成立，人和 AI 的撤销栈也分叉了。如果 A 只在后台、没有附着，就不受影响（已有测试覆盖这一点）。
- 修法：在 cameraStageStore 中新增专用动作，例如 restoreSceneContent(snapshot)。它只替换 objects、animation（由 stateKeyframes 重新编译）、sceneSettings、stateKeyframes、activeCameraId，并按当前 playback.currentTime 重新采样对象。viewMode、gizmoMode 和 playback 保持不变；selectedId 和 selectedStateKeyframeId(s) 仍然存在就保留，否则置空。不调用 resetCameraStagePlaybackRuntime。restoreCameraStageUndo 改调这个动作。历史有两种处理：一是回滚 set 期间执行 temporal.pause()/resume()，并把“助手写入那一段”的 pastStates 截回 capture 时的长度，可在 captureCameraStageUndo 时记录 pastStates.length 并在恢复时裁剪；二是让助手一次事务在 beginHistorySession/endHistorySession 内执行，回滚时丢弃该会话，不提交。不论哪种，回滚后用户 Ctrl+Z 都不能回到被回滚的中间态。回归测试补在 cameraStageProjectRuntime.test.ts：针对附着文档断言 viewMode、播放头保持不变，且回滚后 temporal.undo 不会让已回滚的对象重新出现。
- 测试缺口：src/features/cameraStage/application/cameraStageProjectRuntime.test.ts 的「并发取得 B 只读取一次，后台读改、保存和补偿不改变界面上的 A」只验证非附着文档 B 的补偿，没有覆盖对当前附着文档补偿或撤销时的视图、播放头保持和 temporal 历史。

### 缺陷 3：助手可写的状态关键帧『停留时长』(hold) 在 store 内被无条件归零，写入静默无效

- 排查编号：`camerastage-1`
- 位置：`src/features/cameraStage/store/stateKeyframeSlice.ts:377`；相关：`src/features/cameraStage/application/cameraStageTimelineFields.ts`、`src/features/cameraStage/application/cameraStageApplicationService.ts`、`src/features/cameraStage/application/cameraStageStateKeyframeService.ts`、`src/features/cameraStage/domain/stateKeyframeCompiler.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：助手写属性 camera_stage.state_keyframe.hold=2，或在批量创建状态关键帧的条目里带 hold，请求会走到 cameraStageApplicationService.updateStateKeyframe / cameraStageStateKeyframeService，再到 store.updateStateKeyframeTiming。这个动作先写入 hold，末尾的 syncTransitionDurations 再把所有关键帧的 hold 一律置 0。结果是请求成功、已落盘、返回 undoToken，但读回 hold=0，动画节奏也没变。助手看到的是“写成功了但值不对”，可能反复重试或误判场景状态。这条路径在当前代码上 100% 可复现。现有的 stateKeyframeSlice.test.ts 没有测试写 hold 后读回；transition_duration 账本里绑定的 storeAction 也和实际调用的动作不一致。
- 修法：按当前设计，状态关键帧用绝对时间（time），hold 是遗留字段。建议把它从可写的助手接口中删掉，不要恢复 hold 的语义。具体改动：
  1. 从 cameraStageTimelineFields.ts 的 STATE_KEYFRAME_FIELDS 中删除 hold 字段。如果仍想让助手读到它，改成只读，但更建议直接删除。
  2. 从 CameraStageStateKeyframeUpdate（cameraStageApplicationService.ts:44）、cameraStageStateKeyframeService.ts:26 的创建输入，以及 cameraStageStateKeyframeCollectionExecutor.ts:88 的 hold 解析中删除 hold。按“开发期不兼容旧数据”规则，同时删除 updateStateKeyframeTiming 的 patch.hold 分支，以及 :571 注释里关于 hold 的说法。
  3. 把 transition_duration 字段（cameraStageTimelineFields.ts:85）的 storeActions 从 updateStateKeyframeTransition 改为实际执行的 updateStateKeyframeTiming，让台账归因与实际调用一致。
  4. 在 stateKeyframeSlice.test.ts 或 application 层测试中补一条测试：写 transition_duration 后读回结果与相邻关键帧时间一致；并确认 hold 已不在属性目录中。
  如果坚持保留 hold，就得让 syncTransitionDurations 不再清零 hold，同时让 compiler 正式支持非零 hold。这和 cameraMotionCandidates 的绝对时间前提冲突，不建议这样做。
- 测试缺口：src/features/cameraStage/store/stateKeyframeSlice.test.ts 只测了 moveStateKeyframeTime 怎样重算过渡时长，没有测试 updateStateKeyframeTiming 写入 hold 后能否读回。application 层和属性写入回环的测试（如 src/tests/applicationHarness.writeLoop.test.ts）也没有覆盖 camera_stage.state_keyframe.hold 写入后读回。

### 缺陷 4：后台渲染工作窗口在场景提交后 32ms 即抓帧，不等待角色 GLB / 全景贴图异步加载

- 排查编号：`camerastage-2`
- 位置：`src/features/cameraStage/render/CameraStageRenderWorker.tsx:127`；相关：`src/features/cameraStage/scene/StageScene.tsx`、`src/features/cameraStage/scene/StageObjectMesh.tsx`、`src/features/cameraStage/scene/useCharacterModelUrl.ts`、`src/features/cameraStage/scene/CharacterModel.tsx`
- 严重度：中；核实方式：调用链追踪确认（未写复现测试）
- 现象：有两种触发路径。(a) 主进程刚创建隐藏渲染窗口（首次使用，或窗口被销毁、超时后重建）后的第一个画布 3D 输出任务：useCharacterModelUrl/useCameraModelUrl 的 IPC 还没返回，或 useGLTF 还在下载解析 GLB，角色和摄像机都是胶囊或方块占位体。(b) 场景设置了 sky.environmentImageUrl 的任意任务：StageScene 按 requestId 重挂载，StageEnvironment 每次都重新异步加载全景图，32ms 内通常拿不到 onLoad，背景是 sky.color 纯色，环境反射也没有。worker 只等 captureRef 出现再加 32ms 就抓帧。结果是图片输出整张带占位体或没有全景背景，视频输出的开头若干帧（直到资源加载完）同样如此，中途画面还会突变，而任务照常以 completed 落进画布节点。主窗口导出不受影响，因为视口早已加载好这些资源。
- 修法：在 worker 抓帧前加资源就绪门控，并设超时（超时后按失败处理，或记日志后降级继续，二选一，但必须明确）：
  1) 预解析与预加载。在 CameraStageRenderWorker 挂载场景前（或 notifyReady 前），用 await 拿到 getBundledResourceUrl('camera-stage/UAL1_Standard.glb' / 'camera-stage/Video Camera.glb')，写入 useCharacterModelUrl.ts 的模块缓存（建议导出一个 `resolveCameraStageBundledResourceUrls()` 复用 pendingResolves），再调用 useGLTF.preload(url) 并等待加载完成（例如 await 一次 useLoader 缓存的 promise，或改用 GLTFLoader.loadAsync 后放进 drei 缓存）。
  2) 环境贴图。让 StageEnvironment 在 onLoad 或 onError 时上报就绪：新增一个场景资源就绪注册表（如 scene/stageAssetReadiness.ts，提供 begin(id)/end(id)/waitIdle(timeout)），或者由 worker 用 TextureLoader.loadAsync 预载同一 URL。CharacterMesh/CameraHelperMesh 也应在模型挂载完成（或进入 ErrorBoundary 失败态）时 end 掉自己登记的项。
  3) worker 中把 waitForSceneCommit 改为：await waitForCaptureBridge → await waitStageAssetsIdle(timeout) → 用 flushSync 或一次 rAF 确保 Suspense 解析后的子树和姿态 effect 已提交，然后再 capture 或 export。
  4) 补测试：mock 掉资源就绪注册表，断言注册表 idle 之前 worker 不会调用 exportCameraStageImage/exportCameraStageVideo。
- 测试缺口：CameraStageRenderWorker 没有任何单元测试。electron/main/services/camera-stage-render.test.ts 只覆盖主进程的窗口和任务调度，不涉及渲染侧在抓帧前的资源就绪判断。

### 缺陷 5：隐藏渲染窗口里的 StageCaptureBridge 会反向写入文档封面

- 排查编号：`camerastage-5`
- 位置：`src/features/cameraStage/scene/StageCaptureBridge.tsx:118`；相关：`src/features/cameraStage/render/CameraStageRenderWorker.tsx`、`src/features/cameraStage/projects/cameraStageProjectCover.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：用户在画布上让 3D 镜头参考节点后台渲染视频。隐藏的 worker 窗口用 request.cameraStageDocumentId 建投影 store，再挂载 StageScene（primary+captureRef）。StageCaptureBridge 不区分自己挂在哪个宿主，照样订阅 store 并安排 1.2s 后刷新封面。
  渲染帧阶段每帧 seek 都会改 objects，定时器一直被重置，所以这期间不会写。帧循环结束后进入 finishVideoFrameExport（FFmpeg 编码），只要编码超过 1.2s（较长视频几乎一定超过），定时器就会触发：隐藏窗口把渲染画面 toDataURL 下来（摄像机视图、动画末帧、来自任务提交时的快照），通过 saveDocumentCover 覆盖该文档的列表封面。
  结果是：用户编辑器里最后保存的封面被替换成渲染任务的末帧，如果主窗口同时开着该文档，还会和它的封面写入互相竞争。另外两种情况也会写：静态帧任务超过 1.2s；任务中 worker 窗口被 destroy 或 close，触发 pagehide 时立即写。
  这和 worker 自己的设计约定矛盾。CameraStageRenderWorker.tsx:97 写明“渲染宿主……不向镜头参考反向保存”，StageCaptureBridge 第 125 行的注释也说它“只服务导出”。目前没有任何测试覆盖 StageCaptureBridge 的封面刷新行为。
- 修法：让封面刷新由宿主显式开启，后台渲染 worker 不开。
  做法一（推荐）：把第 96-123 行的封面刷新逻辑（订阅、首次 schedule、visibilitychange、pagehide）从 StageCaptureBridge 拆成独立的 hook 或组件，比如 useCameraStageCoverRefresh(captureRef)，只在镜头参考编辑器宿主里挂载。这里的编辑器宿主指 StageViewportWorkspace/CameraStageEditor 一侧，并且主视口要持有 captureRef。StageCaptureBridge 只保留注册 captureFrame 和 disposeOffscreen。
  做法二：给 StageScene 和 StageCaptureBridge 加 coverRefresh?: boolean，默认 false；只有编辑器主视口传 true，CameraStageRenderWorker 和画布内嵌视口不传。
  两种做法都需要一条回归测试：用投影 store 挂载桥，模拟 seek 后静默超过 1.2s，再派发 pagehide，断言 saveDocumentCover 未被调用；同时验证编辑器宿主下封面刷新仍然生效。另外要检查其他以 primary+captureRef 挂载 StageScene 的位置（StageViewportPane.tsx:129），确认只有真正的编辑器会话才开启封面刷新。
- 测试缺口：目前没有任何测试覆盖 StageCaptureBridge 的封面刷新行为。CameraStageRenderWorker 也没有测试断言渲染宿主不会对文档执行写操作（例如 saveDocumentCover）。

### 缺陷 6：内置模型 URL 解析失败后永久卡死，所有角色/摄像机只渲染占位体且产生未处理拒绝

- 排查编号：`camerastage-6`
- 位置：`src/features/cameraStage/scene/useCharacterModelUrl.ts:29`；相关：`src/features/cameraStage/scene/StageObjectMesh.tsx`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：机制是确定的。只要 getBundledResourceUrl 第一次 reject，后果就是：(1) pendingResolves 永远保存这个 rejected promise，cachedUrls 不会写入；(2) 在整个渲染进程生命周期内，之后每个 CharacterMesh / CameraHelperMesh 挂载都复用它，永远不会重试，角色和摄像机模型一直显示占位体；(3) 每次挂载产生一条 unhandledrejection。
  触发概率不高：主进程 handler 是同步的，资源路径是常量，资源缺失时返回 null 而不是抛错。会 reject 的情况只有这几种：IPC handler 还没注册或主进程出错（nativeInvoke 收到 ok:false 后抛错）、statSync 碰到竞态或权限异常、payload 校验失败、getPlatform() 抛错。因此严重度维持 low。现有测试里没有任何用例覆盖 useCharacterModelUrl / useCameraModelUrl。
- 修法：在 useBundledCameraStageResourceUrl 里给 pendingResolve 加失败分支，例如改成 `pendingResolve.then(onValue, (error) => { pendingResolves.delete(resourcePath); 用项目统一日志入口记录 warn（参照 docs/rules/logging.md，不要新开日志通道）; if (mounted) setUrl(null) })`。
  不要把失败结果写进 cachedUrls，这样下次挂载可以重试，占位体回退的行为保持不变。
  另外，pendingResolves.delete 只能删除当前这个 promise：先判断 `pendingResolves.get(resourcePath) === pendingResolve` 再删，避免并发挂载时误删后来发起的重试。
  建议补一个 jsdom renderHook 单测，覆盖这三点：首次 reject 后再挂载会重新调用并拿到 URL；不产生 unhandledRejection；成功后结果命中缓存。
- 测试缺口：仓库里没有任何测试引用 useCharacterModelUrl 或 useCameraModelUrl。applicationHarness.cameraStageRender.test.ts 等场景测试没有覆盖内置资源 URL 解析失败的分支。

### 缺陷 7：open/close_application_surface 对工作区 Surface 的回执与真实导航状态不一致

- 排查编号：`camerastage-7`
- 位置：`src/features/navigation/application/surfaceNavigationService.ts:53`；相关：`src/features/navigation/application/surfaceCapabilityService.ts`、`src/features/toolbox/application/registerToolboxCapabilityHandlers.ts`、`src/stores/navigationStore.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：1) 在工具箱的子工具里（tools / cameraStage）调用 open_application_surface('workspace.tools')：isApplicationSurfaceActive 对没有 toolId 的 Surface 只比较 activeWorkspace，于是直接返回 already_active，verified=true。界面仍停在镜头参考，助手却以为已经回到工具首页。
  2) close_application_surface 的目标是 workspace.generation / canvas / video_edit / tools 这类工作区时，不执行任何动作，但回执 status:'closed'。
  3) 最常见的真实路径：在镜头参考（或任一工具子页）里、助手浮层未打开（例如外部 MCP 调用）时，以无参形式调用 close_application_surface。自动选中的目标是 workspace.tools（目录中它排在 tool.* 之前），结果不执行动作却回执 closed，工具子页没有关闭。另外，助手浮层打开时无参 close 会先命中 overlay.assistant，把助手自己关掉，修复时应一并考虑。
- 修法：surfaceNavigationService.ts 需要改三处：
  (a) isApplicationSurfaceActive：对 surface.id==='workspace.tools'（或者 kind==='workspace' 且 workspace==='tools'），额外要求 navigation.activeToolId === null。openApplicationSurface 的通用分支里，workspace 为 tools 且没有 toolId 时，调用 selectToolboxTool(null)。
  (b) closeApplicationSurface 无参推断目标时，优先选最具体的活动 Surface：先 tool.* / settings.* / overlay.assets，最后才是工作区，并排除 overlay.assistant 或把它放到最低优先级。可以改成按 kind 排序，或者先过滤 kind!=='workspace'。
  (c) 目标是不可关闭的工作区时（generation / nodes / videoEdit，以及没有子工具的 tools），返回 'no_op' 或抛出 ApplicationPreflightFailure（例如 UNSUPPORTED），不再回执 closed。workspace.tools 在有子工具时可以按 selectToolboxTool(null) 处理。同步扩展 SurfaceNavigationResult.status 的类型和 revisionOutputSchema。
  补测试：在 surfaceCapabilityService.test.ts 中补上上面 A/B/C 三个场景。
- 测试缺口：surfaceCapabilityService.test.ts 只测了从 generation 打开 tool.camera_stage，没测"已在子工具时打开 workspace.tools"。close_application_surface（无参和带工作区 ID 两种情况）完全没有单元测试。
