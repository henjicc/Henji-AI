## 任务目标

Groq 等供应商返回的带时间转写能被接受，失败也不会把口播永久锁死；口播助手撤销正确且不泄漏内存；本地模型删除与下载不互相破坏；音频 Worker 的结果不被进程退出事件抢走；录制讲解的时间对齐可靠。

## 当前情况

- 转写校验在 `src/core/audioEdit/timestampedTranscript.ts`，比 SDK 的公共 DTO 更严；防重复付费门禁在 `electron/main/services/audio-edit/asr.ts:76`。

- 录制讲解 `src/features/creativeIntent/recording/microphone.ts`。

## 实施方案

转写校验按 SDK 契约放宽（把越界词夹到句子范围或改挂靠），校验失败时把计费状态记为“已完成但解析失败”以允许不重复付费地重新解析；撤销记录改为有上限或随实例释放；模型删除与 ensure 串行化；Worker 改听 `close` 事件。

### 缺陷 1：带时间转写的校验比 SDK 的公共 DTO 更严：Groq 的词按“最近句”挂靠，常有词越出所属句；一旦整单失败，这份口播会被永久锁死，不能再转写

- 排查编号：`localinfer-1`
- 位置：`src/core/audioEdit/timestampedTranscript.ts:61`；相关：`electron/main/services/audio-edit/asr.ts`、`electron/main/services/audio-edit/timestamped-asr.ts`、`packages/ai-sdk/src/capabilities/speech-recognition/groq/parse.ts`
- 严重度：高；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：这是两个问题叠在一起。
  (A) 校验过严：normalizeTimestampedTranscript 有两处会让整单失败。
  - 词的时间超出所属句：SDK 的 groq attachTopLevelWords 按中点把词挂到最近的句子，设计上就允许跨句边界的词超出该句的起止。
  - 任一端点 > durationMs：Whisper 的时间以 20ms 量化，末句或末词的结束时间可能比宿主的 WAV 实长多几毫秒。
  (B) 已付费结果丢失并被永久锁死：normalize 在供应商完成之后才执行，失败时任务记为 failed，不写 billing，也不写原始 output。对 Groq 这类同步、不发 started/processing 事件的模型，provider_task_id 为空。下次转写会在 asr.ts:76 抛"上次转写的提交结果无法确认"，preflight 也在 asr.ts:42 拒绝，这份口播从此无法再转写。讲解录音路径 explanation-audio.ts:115 同理。
  (B) 不限于 Groq：凡是供应商完成后的本地失败都会触发，包括 normalize、audioEditTranscriptBlocks 为空（asr.ts:122）、写回前的 verifyAudioEditSource（asr.ts:144），而且只要 provider_task_id 为空就会锁死。
- 修法：1) 修改 src/core/audioEdit/timestampedTranscript.ts，改为容忍合法的 DTO：
  - 词超出所属句时，不再抛错，保留词自身的精确时间（下游 audioEditTranscriptBlocks 只用词时间，不需要嵌套）；也可以把该句降级为句段粒度。
  - 端点超过 durationMs 但在一个量化容差内（例如 ≤ 20–40ms）时，夹到 durationMs；超出明显更多才拒绝。
  - 同步修改 timestampedTranscript.test.ts 里"拒绝超出所属句的词"这个用例的预期。这个用例目前把错误契约固化了。
  2) 修改 electron/main/services/audio-edit/asr.ts，把 billing='completed' 提前到 execute 拿到 SDK 原始 output 之后，normalize 之前（需要 timestampedAsrService.execute 把原始 SpeechRecognitionOutput 或规范化错误分开返回）。后续本地失败时，catch 中把 {billing:'completed', rawOutput} 写进任务的 result_json。重试时，如果检测到 rawOutput 且 sourceDigest 一致，就复用它重新规范化，不再走 asr.ts:76 的"无法确认"分支。preflightAudioEditTranscription（asr.ts:31-42）也要识别这种状态。
  3) explanation-audio.ts:115 的锁死条件按同一原则处理。
  4) 补测试：用 parseGroqTranscription 解析跨句词和量化超长的夹具，确认 normalize 通过；asr.test.ts 增加"execute 完成后本地失败 → 重试复用已付费结果，不报锁死"。
- 测试缺口：src/core/audioEdit/timestampedTranscript.test.ts 只用手写的合成 DTO，并且明确断言"拒绝超出所属句的词"和"拒绝 1001>1000 的端点"，等于把过严的契约固化了，没有用 SDK 的 parseGroqTranscription 真实输出（attachTopLevelWords 的跨句挂靠）做夹具。electron/main/services/audio-edit/asr.test.ts 没有覆盖"execute 完成后本地失败，再重试"的路径，也没有覆盖 provider_task_id 为空的同步模型（Groq）。explanation-audio.test.ts 同样缺少这条路径。

### 缺陷 2：口播助手改写的撤销记录全局 Map 只增不减，每条保存两份完整口播文档

- 排查编号：`localinfer-6`
- 位置：`src/features/audioEdit/application/audioEditMutationExecutor.ts:18`；相关：`src/features/audioEdit/application/audioEditProjectInstances.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：In one renderer session, the assistant makes many property writes to an audio-edit (口播) project through the application control engine (audio_edit.project / transcriptBlock / suggestion / processorChain), for example correcting words one by one or applying suggestions one by one. Each apply adds a {previous, after} record to the module-level undoRecords in audioEditMutationExecutor.ts:18. A record is removed only when its undo succeeds. Undos rejected because of later edits, records left after the document is closed or released (releaseAudioEditProject / leaveAudioEditProject dispose), and the ordinary case where nobody undoes are all kept until the process exits.
  Correction to the original report: it says each record holds two full copies. In fact `previous` is the live document from the previous commit (the same object as the prior record's `after`, or a shallow copy that shares fields with it). The new copy per record is mostly the deep copy that structuredClone makes for `after`. Memory therefore grows linearly at about one full document per write (transcript + suggestions + cuts), not two. The instance's own undo stack is capped at 50, so this Map is the only unbounded retainer.
  The impact is a slow memory leak and nothing else; no behavior is wrong. Severity stays low.
- 修法：Follow canvasApplicationService.ts. In audioEditMutationExecutor.ts:
  1. Add a constant such as MAX_UNDO_RECORDS = 50, matching the instance's past limit. After undoRecords.set, while undoRecords.size exceeds it, delete undoRecords.keys().next().value.
  2. Key the records by project, or add a function such as clearAudioEditUndoRecords(projectId), and call it when releaseAudioEditProject / leaveAudioEditProject / abandonAudioEditDocument dispose the instance. That way a closed document no longer keeps its snapshots. Also export a test reset like the asset executors' clear().
  3. Optional: store `after` as a content fingerprint, such as JSON.stringify of the document with revision and updatedAt zeroed, or a hash of it, instead of a full structuredClone copy. undo already compares only content(after), so this saves another copy per record.
  After the change, add a unit test that applies more than the cap without undoing, then checks that the oldest token's undo returns AUDIO_EDIT_UNDO_NOT_FOUND and that an undo inside the cap still works.
- 测试缺口：No test covers AudioEditMutationExecutor. The existing tests next to it (audioEditProjectInstances.test.ts, audioEditQuickProcess.test.ts, audioEditReflectionResult.test.ts) cover the instance and the reflection result only. Nothing tests the executor's undo-record lifecycle: cap, release after a rejected undo, or cleanup when the document closes. Canvas has the cap in code, but this executor was not checked against it.

### 缺陷 3：助手对口播属性写入的撤销走普通编辑的锁校验，同一步里“删除再锁定”的改动无法撤销或补偿

- 排查编号：`localinfer-7`
- 位置：`src/features/audioEdit/application/audioEditMutationExecutor.ts:67`；相关：`src/core/audioEdit/edits.ts`、`src/features/audioEdit/application/audioEditProjectInstances.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：助手在一次 modify_properties 中，对同一个 audio_edit.transcript_block 先后提交 included=false（或 text、caption_break_after）和 locked=true，也就是“删掉并锁定”。apply 成功。之后助手撤销这一步，或者同一事务中后续步骤失败、触发 compensate，都会走 AudioEditMutationExecutor.undo。它调用 editAudioEditProject(id, () => previous)，后者执行 assertAudioEditLocks(当前文档, previous)：当前文档里该块已锁定，而 previous 中它的 included 不同，于是抛出“锁定内容不能修改，请先解锁。”。结果是撤销失败、事务补偿失败、undo 记录残留，修改保留在半完成状态。这与 resetAudioEditProject 和 undoAudioEditProject 的约定不一致：两者注释写明撤销应把锁一并恢复。
- 修法：在 audioEditProjectInstances.ts 中新增一个仅供撤销/补偿使用的提交入口，例如 restoreAudioEditProjectSnapshot(id, snapshot, expectedContent)。保留 assertApplicationWritesAllowed、busy 检查、IMMUTABLE_SOURCE 校验（source 取当前值）、id/name/editBaseline 规范化，以及 audioEditProjectSchema.parse，只去掉 assertAudioEditLocks，然后走 commitEdit，这样撤销栈和 batchDepth 的语义不变。AudioEditMutationExecutor.undo（第 67 行）改为调用这个入口。普通 editAudioEditProject 继续做锁校验。回归测试：在同一步里提交 [included=false, locked=true]，执行 apply 再 undo，词块应恢复为 {included:true, locked:false}；同时确认普通编辑仍然无法修改已锁定的块。
- 测试缺口：audioEditProjectInstances.test.ts 只覆盖了两件事：普通 edit 被锁拒绝，以及 undoAudioEditProject 能恢复。AudioEditMutationExecutor 的 apply/undo/compensate 没有任何直接测试，“同一步内先改再上锁”后撤销的组合也没有覆盖。

### 缺陷 4：删除本地模型时，等旧下载结束和执行 rm 之间可能插入一次新的 ensure，导致新下载的文件被删掉，或者下载以磁盘错误失败

- 排查编号：`localinfer-8`
- 位置：`electron/main/services/local-models/service.ts:358`；相关：`electron/main/services/download/verifiedDownload.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：用户在设置页或通过助手删除某个本地模型（IPC local-models:remove）。remove() 先取消旧下载并等它结束，然后执行 fs.promises.rm 递归删除模型目录。这个删除是异步的，大模型目录还要多花时间。在等旧下载结束之后、rm 完成之前，如果智能区域、跟踪任务或渲染层通过 IPC 调用 ensure(id)，ensure 看到 active 为空、磁盘状态不是 ready，就会在同一目录 mkdir 并开始写 .part。rm 随后删掉新的 .part 或整个目录，新下载在 rename 时以 ENOENT 失败，错误码为 'disk'，failures 被记成 disk，调用方的任务（如智能区域检测）也跟着失败。另外，remove 结束时会 emit 一个磁盘状态（not_downloaded），这时新下载仍在 active，UI 状态会短暂错乱。复现前提是删除和 ensure 在时间上重叠，所以严重度低。
- 修法：在 LocalModelService 里增加 `private readonly removing = new Map<LocalModelId, Promise<void>>()`。remove() 开头如果已有进行中的删除，直接复用；否则把从 abort/await 到 rm、清理 verified/failures、emit 这一整段包成一个 promise 放进 removing，在 finally 里删除这一项。ensure() 开头（检查 active 之前）先 `const pending = this.removing.get(id); if (pending) await pending.catch(() => undefined)`，等删除完成后再判断 active 和 diskStatus。diskStatus 的 await 之后已经二次检查了 active，这里还要再检查一次 removing，或者改成循环判断。这样删除中发起的 ensure 会等到删除完成后再在干净的目录里开始下载。info() 在删除期间可以照常返回磁盘状态。cancel() 不需要改。另外建议在 service.test.ts 中补充“删除进行中调用 ensure 应在删除后成功下载”的用例，用 vi.spyOn(fs.promises,'rm') 加门控来模拟删除耗时。
- 测试缺口：electron/main/services/local-models/service.test.ts 里的“取消下载报 cancelled；删除后状态回到未下载”只覆盖串行流程：先 ensure 完成，再 remove。“同一模型并发 ensure 只下载一次”只覆盖两个 ensure 之间的并发。没有测试覆盖 remove 和 ensure 并发，也没有测试 remove 期间发起的 ensure。

### 缺陷 5：音频 Worker 调用：子进程 exit 事件可能先于 stdout 最后一行到达，正常结果被当作“未返回处理结果”拒绝

- 排查编号：`mediamain-1`
- 位置：`electron/main/services/audio-edit/audio-worker-client.ts:68`；相关：`electron/main/services/audio-edit/processors.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：真实调用的流程：invokeAudioWorker 用 child.stdin.end() 写入一行请求，Rust worker 跑完这一行后 stdin 到 EOF，于是循环退出。它在退出前已经 flush 了这一行 JSON 响应，然后以退出码 0 退出。Node 主进程可能先收到 child 的 'exit'，后收到 stdout 的数据。exit 处理函数看到 code===0，就 reject('音频 Worker 未返回处理结果。')，正确的结果被丢掉。实测在 1000 次顺序调用里命中约 0.6%，概率会随机器负载变化。
  影响：
  (1) discoverAudioEditProcessors 里的 scan 失败后，会降级为在 JS 里遍历目录，问题不大。但 inspect 失败时，这个插件会被标成 available:false，reason 显示为“音频 Worker 未返回处理结果。”。如果列表有缓存，用户导出时 processAudioEditVstChain 会抛出“口播使用的声音插件不可用”。
  (2) process 命令最长可以跑 30 分钟。跑完后，即使已经正确写出 vst-*.wav，只要命中这个竞态，catch 分支就会删掉临时文件，整个处理或导出都会失败。
  目前只有 win32 平台会真正走到这条路径。
- 修法：在 electron/main/services/audio-edit/audio-worker-client.ts 里，把判定“没有返回结果 / 异常退出”的监听从 child.once('exit') 改为 child.once('close', (code, signal) => ...)。'close' 要等 stdio 全部关闭后才触发，那时 stdout 里缓冲的行已经全部交给 readline 分发过，如果有响应，'line' 一定已经 settle 了。'close' 回调里的逻辑不变：code 非 0 时 reject，并带上 stderr；否则 reject “未返回处理结果”。
  另一种做法：把 stdout 累积起来，在 'end' 或 'close' 时再解析第一行。
  建议同时补一个单元测试：用 mock spawn 返回一个假 child，先 emit('exit', 0)，再推入 stdout 行，最后 emit('close')，断言结果 resolve。这样可以确定性地覆盖这个竞态。
  还要排查一下其他 spawn 后读 stdout 再用 exit 判定的同类实现。
- 测试缺口：audio-worker-client.ts 没有任何单元测试。export.test.ts 用 vi.mock('./processors') 绕开了 worker 调用，所以“worker 正常响应后立即退出”这个时序完全没有被覆盖。

### 缺陷 6：录制讲解的音频与墙钟只在开麦时对齐一次，用的还是输出时间戳：长时间录制会随设备时钟漂移，并带有未计入不确定度的输出延迟偏差

- 排查编号：`localinfer-5`
- 位置：`src/features/creativeIntent/recording/microphone.ts:18`；相关：`src/core/audioEdit/recordingClock.ts`、`src/core/creativeIntent/recordingAlignment.ts`、`src/features/videoEdit/application/videoEditExplanation.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：用户在视频编辑器或图片编辑器 v3 里开始录制讲解，中途不暂停（暂停后 resume 会重新打开麦克风并重新校准）。captureMicrophone 在第 15-18 行只调用一次 getOutputTimestamp，得到常量 offsetUs/uncertaintyUs，此后每块的时刻都是 monoStartUs = offsetUs + firstFrame/sampleRate。
  (a) 偏差：(contextTime, performanceTime) 这对值描述的是输出帧在扬声器上播出的时刻；同一渲染量子里的输入帧要早 outputLatency（再加 inputLatency）才被采集。代码没有扣除 outputLatency，也没有把它计入不确定度。使用蓝牙耳机等高输出延迟设备时（150-300ms），所有词的时间戳都偏晚这么多。而 uncertaintyUs 只有约 23ms（baseLatency + 128/sr + track.latency），低于 50ms 门槛，词仍被标为 precise，"这里"这类指代因此绑定到偏后的画面或指针。
  (b) 漂移：声卡时钟与 performance.now 之间的 ppm 级偏差随录制时长线性累积（60ppm 时 30 分钟约 108ms），uncertaintyUs 却不增长，后段词同样可能被误标为 precise。
- 修法：只改 src/features/creativeIntent/recording/microphone.ts 和 src/core/audioEdit/recordingClock.ts。
  1) correlateRecordingClock 增加 outputLatency 入参（取 context.outputLatency，缺省按未知处理）。在 offset 中扣除 outputLatency 与 inputLatency，把输出呈现时刻换算成输入采集时刻；或者至少把 outputLatency 计入 uncertaintyUs，未知时取保守值，让高延迟设备落入 coarse。
  2) captureMicrophone 里每 5-10 s 重新调用 getOutputTimestamp，可以在 port.onmessage 中按时间节流，也可以用 setInterval 并在 stop 时清理。用最新相关点（或对多点做线性拟合得到斜率）计算 monoStartUs，并为 uncertaintyUs 加上与距上次校准时长成正比的漂移项（例如 100ppm × Δt）。重新校准不能让相邻块的 monoStartUs 倒退或跳变超过不确定度，否则 videoEditExplanation 的连续性检查和对齐结果会出错。
