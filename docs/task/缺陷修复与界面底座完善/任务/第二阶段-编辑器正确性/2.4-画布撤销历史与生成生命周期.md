# 2.4 画布撤销历史与生成生命周期

## 任务状态

- 状态：待开始
- 所属阶段：第二阶段-编辑器正确性
- 前置任务：无
- 关联任务：3.3（助手撤销回执）
- 是否可以并行：可以

## 任务目标

画布撤销栈只记录真实编辑；历史满 50 步后助手的修改与撤销仍判断正确；删除节点会取消其上的生成；切换画布不会清空别处的生成进度。

## 当前情况

- 画布 store 拆在 `src/stores/canvasStore*.ts`；历史上限 `MAX_HISTORY_STEPS=50`，满了以后 `pushSnapshot` 会 `shift`，所以“用 `past.length` 判断有没有变化”的写法全部失效。
- 应用服务在 `src/features/canvas/application/`（`canvasMutationService.ts`、`canvasApplicationService.ts`、`canvasBatchService.ts`、`canvasProjectInstances.ts`）。
- `src/stores/projectStore.ts` 的画布打开流程可被新的打开请求抢占。
- 现有测试 `canvasStore.nodeResize.test.ts`、`canvasStore.mediaAutoResize.test.ts` 只发带 `resizing` 的尺寸变更。

## 实施方案

纯测量事件不进历史；所有“是否变化/是否过期”判断改为比较历史或节点数组的引用、或使用单调递增的历史序号，不再比较长度；删除节点时调用已有的生成取消入口；`setCanvasData` 的全局副作用收窄到当前画布。

## 缺陷明细

以下条目来自 2026-10-13 排查，位置与行号以当时 `main` 为准；开始前先用行号附近的代码片段重新定位。

### 缺陷 1：ReactFlow 的 ResizeObserver 测量事件被当作用户编辑推入撤销历史并清空 redo，新增节点后第一次撤销无效、重做栈被清空

- 排查编号：`canvas-0`
- 位置：`src/stores/canvasStoreConnectionActions.ts:144`；相关：`src/features/canvas/Canvas.tsx`、`src/stores/canvasStoreHelpers.ts`
- 严重度：高；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：任何经 ReactFlow 渲染的节点首次（或恢复到无 measured 的快照后）被 ResizeObserver 测量时，xyflow 发出 {type:'dimensions', dimensions}（不带 resizing），store.onNodesChange 把它当用户编辑：推入一份测量前快照且清空 future。后果：1) 新增节点后第一次 Ctrl+Z 只回到"节点已存在但未测量"的状态，看起来无效，需按两次才撤掉新增；2) 撤销后 ReactFlow 对恢复的节点重新测量，立刻又推快照并清空 redo，重做不可用；3) 打开项目/setCanvasData 后首批测量、内容高度变化导致的自动尺寸测量同样会产生空撤销步并清空 redo。
- 修法：在 src/stores/canvasStoreConnectionActions.ts onNodesChange 中把纯测量变更（change.type === 'dimensions' && !('resizing' in change)，以及 setAttributes 的父节点扩展可另议）排除在 hasMeaningfulChange 之外：仍 applyNodeChanges 更新 nodes/measured，但不推快照、不清 future、不重置 dragHistorySnapshot。同时检查 Canvas.tsx handleNodesChange 后续逻辑与 bindCanvasSession 的持久化脏标记是否也把纯测量当编辑（可忽略仅 measured 变化）。补一条单测：addNode 后发纯 dimensions 变更，past 长度不变；undo 一次即移除节点；再发测量事件 future 保持 1。
- 测试缺口：src/stores/canvasStore.nodeResize.test.ts 与 canvasStore.mediaAutoResize.test.ts 只用带 resizing:true/false 的 dimensions 变更测撤销，从未模拟 ReactFlow 不带 resizing 的纯测量事件对 history 的影响。

### 缺陷 2：updateCanvasNode 用 history.past.length 判断“是否有变化”，历史满 50 步后永远相等：数据已改并落盘却抛 INVALID_INPUT，批事务内直接整批回滚

- 排查编号：`canvas-1`
- 位置：`src/features/canvas/application/canvasMutationService.ts:359`；相关：`src/stores/canvasStoreHelpers.ts`、`src/features/canvas/application/canvasBatchService.ts`
- 严重度：高；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：前提：画布撤销历史 history.past 已达到上限 MAX_HISTORY_STEPS=50。这有两种来源：本次会话里做了 50 步以上可撤销编辑；或者重新打开一个历史很长的工程，加载时 normalize 做了 slice(-50)，栈一开始就是满的。
  此时用 updateCanvasNode（助手的 update_canvas_node 或通用属性写入）提交一个确实不同的 data 值：
  - 单独调用时：节点数据已改、已落盘，但函数抛出 INVALID_INPUT「节点数据未发生可保存的变化（提交的值与当前值相同）」，也不登记 undoRef。助手会以为没写进去，于是重试或乱改参数。
  - 在 runCanvasTransaction / applyCanvasOperationsAtomically 批事务里：这个错误不是 ZodError，于是整批已成功的操作都被 setCanvasData 回滚，最后抛 CanvasTransactionRolledBackError。只要历史满了，凡是包含 update_canvas_node 的批量操作都会失败。
  单元测试已稳定复现上面两种情况。
- 修法：修改 src/features/canvas/application/canvasMutationService.ts 的 updateCanvasNode：
  1. 写入前取 `const before = store.getState()`，保存 `before.nodes` 的引用。
  2. 写入后改为 `if (store.getState().nodes === before.nodes) { throw ... }`。理由：updateNodeData 在没有变化时返回 {}，nodes 引用不变；有变化时 map 会产生新数组。
  3. 另一种做法是让 store 的 updateNodeData 返回 changed 布尔值，由 applyCanvasNodePatches 透传。
  不要再用 history.past.length 判断，也不要改用 history 引用判断：skipHistory/historyGroup 路径不会更新 history，同样会误判。
  还要排查同源写法：全仓搜 `history.past.length` 的比较，确认其他「是否有变化 / 是否产生撤销步骤」的判断（例如 rememberCanvasUndo 以及其他 mutation 服务）有没有依赖同一个长度。
  再补一条回归测试：用 updateNodeData 把历史填到 MAX_HISTORY_STEPS 以上，然后断言 updateCanvasNode 成功并返回 undoRef；同时在 runCanvasTransaction 内断言不会回滚。
- 测试缺口：canvasMutationService.test.ts 的「updateCanvasNode 的拒绝信息」只测了 data 键被过滤成空补丁的情况，每个用例都从空历史（past: []）开始。没有任何测试覆盖历史栈已达 MAX_HISTORY_STEPS 时提交真实变化的情况，单独调用和 runCanvasTransaction 两条路径都没覆盖。

### 缺陷 3：undo_canvas_change 的 historyDepth 过期校验在历史满 50 步后失效，会撤销掉别人后来的操作

- 排查编号：`canvas-2`
- 位置：`src/features/canvas/application/canvasApplicationService.ts:387`；相关：`src/stores/canvasStoreHelpers.ts`
- 严重度：高；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：前提：画布 history.past 已达到 50 步上限（例如用户在一个长会话里编辑了 50 次以上）。之后助手执行任意一个会调用 rememberCanvasUndo 的写操作（add_node、update_node、delete_nodes、connect_nodes、group 等），拿到 undoRef，此时记录的 historyDepth=50。随后用户在界面又编辑了 N 次（N≥1），每次 pushSnapshot 都会把最旧的一步 shift 出去，past.length 一直是 50。助手再调用 undo_canvas_change(undoRef) 时，长度校验通过，canvas.undo() 撤销的是用户最新的那一步。结果：用户的编辑被静默回退，助手的操作仍保留，助手还收到 status:'undone' 的成功回执，并据此继续推理。
  还有一种同源情形：历史已满时，助手操作后用户先撤销一步再做新编辑，长度同样可能对上，同样会误撤。历史未满时，长度校验能正常拦截。
- 修法：撤销引用的身份不要再用长度表示。rememberCanvasUndo 改为记录操作完成那一刻的状态引用 `{ nodes, edges, history }`（或者只记 history 对象引用；store 的每次正向编辑都会生成新的 history 对象）。undoCanvasChange 的 apply 回调里改成：`if (canvas.history !== record.history || canvas.nodes !== record.nodes || canvas.edges !== record.edges) throw STALE_CONTEXT`。这和 canvasPersistenceService.runPersistedCanvasUndo 里 pendingUndos 的引用比较是同一种做法。
  需要注意两点：
  1. 只改选区、视口这类不进历史的动作，如果也会替换 nodes 引用，就会让引用比较过严。到时可以只比较 history 引用，或者给每个快照加一个单调递增的 id，记录并比较 past 末尾快照的 id。
  2. canvasBatchService 里批量撤销（canvas-batch-undo:）如果也是用长度或深度校验，要一起检查并改掉。
  回归测试：在 canvasApplicationService.test.ts 中加一个用例，先把历史填满 50 步，再执行“助手 add_node → 用户 updateNodeData → undoCanvasChange”，断言抛出 STALE_CONTEXT，并且用户的编辑仍然保留。
- 测试缺口：canvasApplicationService.test.ts 和 canvasMutationService.test.ts 里所有调用 undoCanvasChange 的用例，历史都远低于 50 步，没有任何用例覆盖“历史已满后，再有一次中间编辑，然后撤销旧引用”。也没有用例测试过 STALE_CONTEXT 在 MAX_HISTORY_STEPS 边界上的行为。

### 缺陷 4：文本编辑的 activeHistoryGroup 不会被结构性动作重置，中途插入的新增/连线/删除会和后续继续输入合并成同一撤销步

- 排查编号：`canvas-3`
- 位置：`src/stores/canvasStoreNodeUpdateActions.ts:95`；相关：`src/stores/canvasStoreNodeCreationActions.ts`、`src/stores/canvasStoreConnectionActions.ts`、`src/stores/canvasStoreStructureActions.ts`、`src/features/canvas/hooks/useCanvasTextHistory.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：用户在节点 A 的提示词或文本里保持聚焦并连续输入，此时 activeHistoryGroup=canvas-text:A:field，第一次输入已推入快照 S0。输入期间发生一次异步结构变更，例如生成完成后 generationOutputApplicationService 调用 addNode/addEdge，或者 generationNodeExecutor、multiAngleNodeExecutor、panorama 快照、canvasApplicationService 的单步 addNode/onConnect、canvasMutationService 的 deleteNodes。这次变更推入快照 S1，但没有清空 activeHistoryGroup。用户接着输入时，updateNodeData 认为仍在同一分组，不再推快照。按一次撤销会回到 S1，也就是结构变更之前的状态：新增的输出节点或连线被撤掉，变更之后输入的文字也一起消失，只能靠 redo 找回。经 canvasBatchService 的助手批量写入会在结束时清空分组，不受影响；其他直接调用 store 的路径都受影响。
- 修法：所有推入新快照、但不属于当前文本分组的 store 动作，都要把 activeHistoryGroup 置为 null。涉及：canvasStoreNodeCreationActions 的 addNode/addEdge/addDerived*/addStoryboardSplitNode 等 set 处，canvasStoreConnectionActions 的 onConnect/onNodesChange/onEdgesChange 中推快照的分支，canvasStoreStructureActions 的 deleteNodes/groupNodes/ungroupNode/deleteEdge 等，canvasStoreNodeUpdateActions 的 updateNodePosition/updateStoryboardFrame/reorderStoryboardFrame，以及 canvasMutationService.ts:253 手工 setState 写 history 的位置。也可以在 withApplicationWriteBarrier 或 set 包装层统一处理：本次 set 让 history.past 变化，且 patch 没有显式给出 activeHistoryGroup 时，把它补成 null，这样只需改一处。updateNodeData 自己的 patch 已显式写入 activeHistoryGroup，不受影响。需要在 canvasStore.textHistory.test.ts 补用例：分组输入 → addNode → 继续输入 → undo，断言新增节点仍在、文字回到插入前的内容。
- 测试缺口：src/stores/canvasStore.textHistory.test.ts 只覆盖三种情况：同一分组连续输入合并为一步、endHistoryGroup 后开新步、结构化提示词与兼容字符串合并。没有覆盖分组期间插入其他推快照动作（addNode/onConnect/deleteNodes）后继续输入的情况。

### 缺陷 5：setCanvasData 带全局副作用：后台打开另一份画布、批事务回滚、批量撤销都会清空当前画布所有生成进度与文本流预览，并把在途生成占位改写成失败态

- 排查编号：`canvas-4`
- 位置：`src/stores/canvasStoreConnectionActions.ts:384`；相关：`src/features/canvas/application/canvasProjectInstances.ts`、`src/features/canvas/application/canvasBatchService.ts`、`src/features/canvas/application/canvasBatchUndo.ts`、`src/stores/canvasStoreNormalization.ts`、`src/features/canvas/domain/nodeMigrationCore.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：(1) 画布 A 有节点正在生成（进度条可见），或文本节点正在流式输出。这时只要有任何一份此前没加载的画布 B 通过 getCanvasProjectInstance 首次加载（助手 get_canvas_document、readCanvasProjectSnapshot、批量操作等都会触发），B 的 store.setCanvasData 就会清空全局进度和流式预览，A 的进度条和流式文本当场消失。进度要等下一次进度回调（约 200ms 以上）才恢复；流式预览的 runIds 也被清空，要等下一个 token 才恢复。B 已加载时不会触发。clearCanvas（canvasStoreStructureActions.ts:404-405）有同样的全局清空。
  (2) 画布 A 里有一个结果占位节点：isGenerating:true，但还没登记 serverTaskId（同步模型，或任务 ID 尚未返回）。此时针对 A 的批事务在写入之后失败，或者用户/助手执行 undoCanvasBatch，都会经 setCanvasData(beforeNodes) 进入 normalizeNodes 和 resetTransientNodeRuntimeState，占位节点被改成 isGenerating:false，并带上 generationError「生成在项目切换或应用关闭前未返回，请重新生成」。回滚路径还会立刻 persist 落盘。在真实结果提交覆盖之前，用户看到的是失败态，可能因此重复生成、重复计费；回滚还会顺带清掉全局进度。
- 修法：1) setCanvasData 里不要调用 clearAllProgress/clearAllPreviews。应改为只清本 store 中不再存在的节点：比较替换前后的 nodeId 集合，对已移除的 id 调 clearProgress(ids)/clearPreviews(ids)。或者把清理交给界面 attach/detach。clearCanvas 也同样改成只清本 store 原有节点的 id。
  2) 把「加载外部数据并做规范化」和「恢复内存快照」拆成两个 action。bindCanvasSession 和打开项目继续用带 normalizeNodes 的 setCanvasData。runCanvasTransaction 回滚（canvasBatchService.ts:214）和 undoCanvasBatch（canvasBatchUndo.ts:33）改用新的 restoreCanvasSnapshot，直接 set 回 beforeNodes/beforeEdges/beforeHistory 的原始引用，重置 selection/dialog/drag/historyGroup/imageViewer，但不调用 resetTransientNodeRuntimeState，也不清全局瞬态 store。
  3) 补两类测试：后台加载画布 B 不影响 A 的 progress/previews；批事务写入后抛错回滚时，在途占位节点的 isGenerating 保持不变。
- 测试缺口：canvasBatchService 的回滚测试和 canvasBatchUndo 的测试都没有覆盖「回滚前已有 isGenerating:true 且没有 serverTaskId 的节点」这种情况。canvasProjectInstances 和 canvasTextStreamStore 的测试也都没有验证「加载另一个实例不影响全局进度和流式预览」。现有测试反而常在 beforeEach 里主动调用 clearAllProgress/clearAllPreviews，等于把这类全局副作用掩盖了。

### 缺陷 6：删除正在生成的结果/来源节点不会取消生成：请求继续计费跑完，结果因节点不存在被丢弃

- 排查编号：`canvas-5`
- 位置：`src/features/canvas/application/canvasMutationService.ts:413`；相关：`src/stores/canvasStoreStructureActions.ts`、`src/features/canvas/application/generationOutputApplicationService.ts`、`src/features/canvas/application/canvasGenerationTaskService.ts`、`src/features/canvas/application/generationNodeExecutor.ts`
- 严重度：中；核实方式：调用链追踪确认（未写复现测试）
- 现象：1. 在画布里运行一个标准生成节点，比如视频模型。generationNodeExecutor 会建一个占位结果节点（isGenerating:true, generationTaskId, generationSourceNodeId），任务提交后还会写入 serverTaskId。
  2. 生成还在进行时，用户用工具栏删除按钮或 Delete 键删掉占位节点或来源节点，助手的 delete_nodes 也一样，都走 deleteCanvasNodes。
  3. 删除只取消 3D 舞台的 renderTask。普通生成的 AbortController（canvasGenerationTaskControls[generationTaskId].controller）不会被 abort，也不会调 GenerationService.cancelTask(serverTaskId)，所以供应商任务继续轮询、继续计费。
  4. 结果返回后，媒体先落盘，然后 commit 因节点不存在抛出 CONFLICT，刚写的文件被释放，任务记录标成 error。用户付了费却拿不到结果。
  5. 有一个反向细节要注意：如果用户在生成完成前撤销了这次删除，占位节点会恢复，目前结果仍能正常落图。所以修复不能简单地在删除时立即取消，否则会破坏"删了再撤销"这条路径。
- 修法：在 deleteCanvasNodes 里，confirmCanvasPersistence 成功之后（和 cameraStage 取消一样放进 runAfterCanvasPersistence），收集被删节点里 isGenerating 为真的占位节点的 data.generationTaskId 和 serverTaskId；再对被删的来源节点，找出 generationSourceNodeId 指向它、且仍在生成的占位节点，一并收集。
  对收集到的任务：
  - 有 generationTaskId 时，调 canvasGenerationTaskControls.get(id)?.controller.abort()，或复用 cancelCanvasGenerationTask(id)。它会 abort 控制器并调 GenerationService.cancelTask。
  - 只有 serverTaskId 的，属于重启后的续查任务，要通过 canvasResumePollingService 对应的 abort 或 GenerationService.cancelTask(serverTaskId) 取消。
  clearCanvasProject 也要做同样处理。
  如果产品上要保留"删了再撤销还能拿到结果"，有两个办法：
  - 取消前加一个短暂的宽限，或者等撤销栈确认删除已经落定后再取消；
  - 或者改成在 commit 时发现占位节点缺失但来源节点还在，就重建结果节点，而不是丢弃。
  至少要保证：占位节点和来源节点都确定不存在、且这次删除已经持久化时，立即 abort，避免继续计费、落盘后又被丢弃。
  回归测试建议：mock GenerationService 让 continuePolling 挂起，删除占位节点后断言 controller.signal.aborted 为真、cancelTask 被调用。
- 测试缺口：canvasMutationService.test.ts 里 deleteCanvasNodes 的测试只覆盖 cameraStage 的 renderTask 取消，没有覆盖删除正在生成的普通结果节点或其来源节点时取消 canvasGenerationTaskControls 控制器和供应商任务；也没有任何测试覆盖 commit 时节点缺失导致 CONFLICT 的路径。

### 缺陷 7：runCanvasTransaction 合并历史时按长度裁剪：批内没有产生新快照的事务会丢掉最旧的一步真实撤销并插入一个空操作快照

- 排查编号：`canvas-6`
- 位置：`src/features/canvas/application/canvasBatchService.ts:251`；相关：`src/features/canvas/application/canvasMutationService.ts`、`src/stores/canvasStoreNodeUpdateActions.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：画布已有 N（1..50）步撤销历史时，通过 runCanvasTransaction 提交一个整批都不往 store.history 追加记录的事务，就会触发：
  - 内核路径：applyCanvasOperationsAtomically / commitCanvasBatch，批里只有 select_node。
  - 其他调用方：执行体没写 history 的 runCanvasTransaction，例如批里只有一个与现值相同的 update_node，或者只改 position（updateNodePosition 不记 history）。
  结果：最旧的一步真实撤销被永久丢掉，栈顶多出一条和当前画布一样的空快照。用户第一次按撤销看不到任何变化，最早那步也再也撤不回。
  批内确实新增了历史（K>0）时行为正确，包括已到 50 步上限的情况。
- 修法：在 canvasBatchService.ts 第 251 行附近按“批内是否新增了历史”分支处理：
  - 如果 after.history.past.length 没有超过 beforeHistory.past.length，并且 after.history.past 的末尾仍是 beforeHistory.past 的末尾（引用相同），说明本批没有记录历史。此时：
    - after.nodes/edges 与 beforeNodes/beforeEdges 引用都相同，就把 history 保持为 beforeHistory，future 也一起保留；
    - 只是位置等内容有变化，就追加一条事务前快照，再按 MAX_HISTORY_STEPS（50）裁剪：`[...beforeHistory.past, snap].slice(-MAX_HISTORY_STEPS)`。
  - 有新增时维持现有逻辑。更直接的写法是统一用 `[...beforeHistory.past, snap].slice(-MAX_HISTORY_STEPS)` 合并，只在“完全无变化”时跳过追加，不再拿 after.past.length 当裁剪长度。
  - 同时在 canvasBatchService.test.ts 补一条用例：预置 3 条 past，提交只含 select_node 的批，断言 past[0] 引用不变、长度为 3。
- 测试缺口：canvasBatchService.test.ts 里涉及历史的两条用例：一条是「把多个操作作为一组提交」，初始 past 为空；另一条是「事务成功只压缩运行时历史」，批内 add_node 会新增历史，而且 past 已到 50 步上限。没有用例覆盖“已有非空历史、但批内不新增历史”（例如只有 select_node）的情况。

### 缺陷 8：leaveCanvasProject 忙碌分支与租约释放存在时序窗口：任务在 await leave 期间结束时实例既不关闭也不释放

- 排查编号：`canvas-8`
- 位置：`src/features/canvas/application/canvasProjectInstances.ts:388`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：前提：画布上有后台任务持有租约（例如生成或渲染，leases>0）。用户离开画布（返回列表或切换画布），leaveCanvasProject 先算出 busy=true，然后 await canvasDocumentRegistry().leave(id,{keepOpen:true})。这一步耗时可长可短：有内容的草稿要等用户在“保存/不保存/取消”对话框和起名对话框里操作，几秒都有可能；已保存的文档也要等 session.flush 写盘。
  如果任务恰好在这段时间内结束，租约释放回调会调用 closeIdleInstance。但这时 closeWhenIdle 里还没有这个 id，函数直接返回。leave 返回后，代码仍按旧的 busy=true 走保活分支：解除界面附着，执行 closeWhenIdle.add(id)。此后不会再有释放回调来关闭它。
  结果是：文档会话、canvas store、会话订阅、sessionState 和 instances 里的条目一直留着，直到用户重新打开这份画布（attachCanvasProject 会清掉 closeWhenIdle）、对它执行 releaseCanvasProjectInstance（例如移到回收站），或应用退出。只读画布页面上的数据不受影响，任务结果也已经写回，所以是低危的资源泄漏。在“不保存”草稿的路径上，trashDraft 之后会话可能已经结束（isEnded），这时会走 dispose 分支，不受影响。主要受影响的是已保存文档和“保存”草稿这两条路径。
- 修法：位置：src/features/canvas/application/canvasProjectInstances.ts 的 leaveCanvasProject。
  在 `closeWhenIdle.add(id)` 和 `await instance.sessionState.flush()` 之后，补一次检查：`if (!instance.leases) void closeIdleInstance(instance)`。也可以在 add 之前判断：`instance.leases===0` 时直接走 else 分支，flush 之后 dispose，并调用 `session.close()`。注意此时会话是以 keepOpen 方式保留的，所以必须显式 close，不能只 dispose。
  不建议把 closeWhenIdle.add 提前到 await leave 之前。那样做，closeIdleInstance 可能在 leave 还没结束时就关闭会话，和 registry.leave 里的 flush、草稿保存并发执行。另外如果用户选了“取消”，还得把 id 移出 closeWhenIdle。
  closeIdleInstance 只在实例未附着到画布页（canvasStoreAttachment 不是这个 store）时才关闭，而前面已经调用过 detachCanvasProject，所以补调是安全的。
  建议在 canvasProjectRuntime.test.ts 增加一个用例：用 spy 卡住 registry.leave，在卡住期间结束任务，然后断言会话最终结束、实例被移除。
- 测试缺口：src/features/canvas/application/canvasProjectRuntime.test.ts 的「离开不等后台租约：草稿决定照常处理、界面立即离开，任务写完后会话才关闭」只测了“leave 完成后任务才结束”的顺序。“任务在 await registry.leave 期间结束”的竞态没有测试覆盖。

### 缺陷 9：打开画布途中被新的打开/返回请求抢占时，已载入的目标实例既不展示也不释放，且向调用方返回 true

- 排查编号：`react-1`
- 位置：`src/stores/projectStore.ts:177`；相关：`src/features/canvas/application/canvasProjectInstances.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：当前显示有未保存内容的草稿 A。调用 openCanvasDocument(B)（画布列表点击、助手“打开画布”、文档打开器均经此）：B 已 getCanvasProjectInstance 载入并登记进 instances；随后 leaveCurrentFor(B) → leaveCanvasProject(A) 弹出离开对话框。对话框停留期间，closeProject()（返回按钮）或 openCanvasDocument(C) 使 openRequestSeq 前进；它们对 A 的离开会复用 leaving 中同一个 Promise。用户选择“不保存”后，B 的 openCanvasDocument 走到 L177 `if (seq !== openRequestSeq) return true`：不 show(B)、不 releaseCanvasProjectInstance(B)，B 实例（session 未结束、leases=0、不在 closeWhenIdle）永久留在 instances Map 中，同时向调用方返回 true。对比 L167-170 的同类“载入后被抢占”分支是会释放的。后果：(a) 后台会话泄漏（自动保存订阅、会话状态持有）；(b) 调用方误判：canvasApplicationService.openCanvasProject 随后因 currentProject.id !== projectId 抛出误导性的 PROJECT_NOT_FOUND“画布无法打开”，registerDocumentOpener 会 openApplicationSurface('workspace.canvas') 却没有目标画布；(c) closeProject 抢占的情形下 isOpeningProject 还会卡在 true（currentProjectId 已为 null），画布页停留在“打开中”状态。
- 修法：src/stores/projectStore.ts L177 改为与 L167-170 同样处理：
  ```ts
  if (seq !== openRequestSeq) {
    // 离开当前画布期间又有新的打开或返回：这次打开作废，刚载入的没人用就放掉
    if (get().currentProjectId !== target.id) void releaseCanvasProjectInstance(target.id).catch(() => undefined)
    return false
  }
  ```
  （当 currentProjectId === target.id 时说明别的请求已显示了同一份 B，可返回 true，但该情况 L149 早已短路，实际走到这里 currentProjectId 几乎不会是 B；按 L167 的写法保持一致即可。）
  另外修复同根因暴露的 isOpeningProject 卡死：closeProject() 在 leaveCurrent(false) 返回非 'cancelled' 后应无条件 `set({ isOpeningProject: false })`（或在 leaveCurrent 中把 isOpeningProject 复位移到 `currentProjectId === id` 判断之外），因为 A 被释放时 onCanvasProjectInstanceChanged 监听器已先把 currentProjectId 置空，导致现有复位分支被跳过。
  建议在 src/features/canvas/application/canvasProjectRuntime.test.ts 增加用例：把 prompter.chooseLeaveAction 换成挂起 Promise，分别在对话框期间调用 closeProject() 与 openCanvasDocument(C)，断言 B 的打开返回 false、findCanvasProjectInstance(B) 为 undefined、isOpeningProject 为 false。
- 测试缺口：src/features/canvas/application/canvasProjectRuntime.test.ts 的「草稿离开：…取消留在原处…」与「并发打开与后台执行共享一次加载」只覆盖了同步回答的离开对话框和打开/后台执行并发，没有覆盖“离开对话框停留期间再发起打开/返回请求”的抢占路径；ScriptedPrompter 默认立即回答，无法让对话框挂起。
