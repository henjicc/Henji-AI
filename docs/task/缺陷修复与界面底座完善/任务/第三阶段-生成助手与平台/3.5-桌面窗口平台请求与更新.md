## 任务目标

独立日志窗口可以关闭、应用可以正常退出；日志窗口与主窗口有同等的导航守卫；渲染层网络请求能取消且有超时；自动更新尊重“忽略此版本”、下载失败后可重试、日期文案随界面语言。

## 当前情况

- 日志窗口 `electron/main/windows/log-window.ts`；主窗口的导航守卫可作参照。
- 渲染层请求适配 `src/platform/adapters/electron/system.ts`（`HttpPlatform.fetch` 丢弃 `AbortSignal`）。
- 更新：主进程 `electron/main/services/updater.ts`，渲染层 `src/workspaces/GenerationWorkspace/hooks/useUpdateCheck.ts`、`src/services/updateChecker.ts`。
- `ipc-0` 为高严重度：主窗口关闭后应用无法退出。

## 实施方案

日志窗口关闭时由主进程直接放行或在主窗口关闭时一并销毁；复制主窗口的 `will-navigate` 与 `setWindowOpenHandler`；请求适配透传 signal 并在主进程加默认超时；更新事件先过忽略版本判断，下载失败保留 hasUpdate。

### 缺陷 1：独立日志窗口永远关不掉：关闭被主进程否决后无人确认，主窗口关闭后应用无法退出

- 排查编号：`ipc-0`
- 位置：`electron/main/windows/log-window.ts:49`；相关：`electron/main/ipc/window.ts`、`src/features/logs/LogsShell.tsx`、`src/main.tsx`、`electron/main/window.ts`
- 严重度：高；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：打开独立日志窗口（logging:openWindow → openLogWindow）后：(1) 点击日志窗口标题栏关闭 → LogsShell handleClose → window:close IPC → win.close() → bindWindowStateEvents 的 'close' 处理器发现窗口未在 approvedCloseWindows 中，preventDefault 并发送 window:closeRequested；日志渲染层（只挂载 LogsShell）没有订阅 onCloseRequested，也不调 confirmClose，窗口关不掉。(2) 主窗口经保存屏障正常关闭后，'closed' 回调中的 closeLogWindow() 同样被否决，Windows/Linux 上 window-all-closed 永不触发，进程常驻且日志窗口关不掉。(3) Cmd+Q / app.quit() 关闭所有窗口时也被日志窗口否决，退出被取消。只要日志窗口打开过一次就必现。
- 修法：推荐在主进程修复：日志窗口没有需要保存的内容，不应走保存屏障，也不应登记为 mediaRecycleLifecycle 会话。可以给 bindWindowStateEvents 加参数（如 `{ saveGuard: false }`），跳过时不绑定 'close' 否决、不调用 mediaRecycleLifecycle.opened/closed，只保留 maximize/unmaximize/resize/全屏事件广播；或者拆出 bindWindowStateBroadcast(win)，给 log-window.ts:49 使用。closeLogWindow() 保持 close()。另一种做法是在 LogsShell 里订阅 getPlatform().window.onCloseRequested，收到后立即 confirmClose()，但这样日志窗口仍会作为“未保存会话”参与媒体回收判定，所以不推荐。两种方案只选一种。补一条主进程测试：mock BrowserWindow 后调用 openLogWindow，再调 closeLogWindow，断言没有 preventDefault，并且窗口已销毁。
- 测试缺口：electron/main/ipc/window.test.ts 只覆盖 parseZoomFactor，没有测 bindWindowStateEvents 的关闭屏障，也没有测 log-window 的打开和关闭；Reality 的 logsWindow 步骤（uiReviewSteps.cjs）只打开日志窗口，不关闭，也不验证应用能否退出。

### 缺陷 2：日志窗口缺少主窗口同款的 will-navigate 与 setWindowOpenHandler 守卫，同一份 preload 桥在导航到外部来源后仍然可用

- 排查编号：`ipc-5`
- 位置：`electron/main/windows/log-window.ts:35`；相关：`electron/main/window.ts`、`electron/main/security/main-renderer-url.ts`、`electron/main/services/camera-stage-render.ts`、`electron/main/ipc/system.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：日志窗口（openLogWindow）和三维隐藏渲染窗口（camera-stage-render ensureWorkerWindow）与主窗口共用完整的 henjiNative preload，但都没有导航和开窗守卫。日志窗口的渲染层不处理 drop/dragover，用户把浏览器中的链接拖入日志窗口时，Chromium 默认会做顶层导航，跳到远端 http(s) 页面。preload 无条件 exposeInMainWorld，远端页面因此可以调用 henjiNative 中没有 senderGuard 的通道，包括 fs:readFile、fs:writeFile、fs:remove、fs:copyFile、shell:openExternal 等，实现任意文件读写删。日志页里的 window.open 同样没有拒绝处理器。触发需要用户主动拖入恶意链接，日志内容本身不产生外链，所以严重度维持 low。隐藏渲染窗口不可见、不可交互，只是缺少纵深防御。
- 修法：把 window.ts:68-77 的守卫提取成公共函数，例如在 electron/main/security/ 下新增 installRendererNavigationGuards(webContents, label)，内容包括：setWindowOpenHandler 一律返回 { action: 'deny' }；will-navigate 中 isTrustedMainRendererUrl(url) 为假时 preventDefault 并记 warn 日志；will-attach-webview 时 preventDefault。主窗口的 openHandler 要保留 videoEditPopouts.handleWindowOpen 的放行，所以公共函数需要接受一个可选的 openHandler 回调。然后在 log-window.ts 创建 win 之后，以及 camera-stage-render.ts 的 ensureWorkerWindow 创建 win 之后统一调用。isTrustedMainRendererUrl 会忽略 search 和 hash，?view=logs 和 ?view=camera-stage-render 都能通过。另外补一个单元测试：mock BrowserWindow 后断言两个窗口都注册了 will-navigate 和 setWindowOpenHandler，并且对 https://evil.example 会 preventDefault。可选的纵深防御是在 app 'web-contents-created' 上统一挂这套守卫。
- 测试缺口：electron/main/security/main-renderer-url.test.ts 只测 URL 判定函数，没有测试检查 log-window.ts 或 camera-stage-render.ts 创建窗口后是否挂了 will-navigate 和 setWindowOpenHandler。主窗口这类守卫的注册同样没有窗口级测试。

### 缺陷 3：渲染层 HttpPlatform.fetch 静默丢弃 AbortSignal，主进程 nativeFetch 无超时：魔搭可用性校验 10 秒超时失效，请求可无限挂起

- 排查编号：`ipc-1`
- 位置：`src/platform/adapters/electron/system.ts:127`；相关：`electron/main/services/system.ts`、`electron/main/ipc/system.ts`、`src/platform/contracts/system.ts`、`src/services/modelscopeCustomModels/availability.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：用户添加魔搭自定义模型时会调用 checkModelscopeModelAvailability，它本应在 10 秒后 abort 并返回 { state:'unknown' }。但 Electron 适配器 createHttp().fetch 没有转发 init.signal，自己也不监听 signal；主进程 nativeFetch 调用 Node fetch 时既没有 signal 也没有超时。遇到网络半开、代理黑洞或响应体一直发不完时，abort 对渲染层和主进程都不起作用。结果是 availability 的 Promise 只有等 undici 的默认超时（headersTimeout/bodyTimeout 约 300 秒）才会结束，在此之前界面一直停在“校验中”。按代码注释的本意，这本应在 10 秒内降级为 unknown 并放行。受影响的调用方目前只有 availability.ts，但契约 HttpPlatform.fetch 接受完整 RequestInit，以后任何传 signal 的调用方都会以为自己能取消，实际取消不了。
- 修法：建议改三处，加一个测试：
  1. 契约：NativeFetchRequestDto 和 HenjiNativeFetchRequest 加一个可选的 timeoutMs（正整数，parseNativeFetchRequest 校验上限）。
  2. 主进程 electron/main/services/system.ts 的 nativeFetch：timeoutMs 存在时用 AbortSignal.timeout(timeoutMs) 作为 fetch 的 signal，让读取 body 的 arrayBuffer 也受这个时限约束。
  3. 渲染适配器 src/platform/adapters/electron/system.ts 的 createHttp().fetch：
     - init.signal 已经 aborted 时直接 reject，抛 DOMException('Aborted','AbortError')；
     - 否则用 Promise.race 等 invoke 结果和 signal 的 abort 事件，abort 时立即 reject，监听器要在 finally 里移除；
     - 如需真正中断主进程请求，再加 requestId 和 http:abort 通道。
     availability.ts 改为传 timeoutMs: REQUEST_TIMEOUT_MS，同时保留 signal。
     最低限度的做法：把 HttpPlatform.fetch 的 init 类型收窄为 Pick<RequestInit,'method'|'headers'|'body'> 外加 timeoutMs，让传 signal 在编译期报错。
  4. 测试：在适配器层补一个测试，mock 一个永不返回的 henjiNative.http.fetch，断言 abort 后的 Promise 会 reject；同时断言主进程 nativeFetch 会把 timeout signal 传给全局 fetch。
- 测试缺口：src/services/modelscopeCustomModels/availability.test.ts 在模块边界直接 mock 了 nativeFetch，只验证返回结果的映射，从不检查 signal 是否真被下层尊重。src/platform/adapters/electron/system.ts 的 createHttp 没有任何测试检查 init.signal 和 abort 行为。主进程 nativeFetch 也没有测试检查超时。

### 缺陷 4：忽略版本在 Electron 自动更新路径下失效：更新事件直接弹出更新对话框

- 排查编号：`settings-0`
- 位置：`src/workspaces/GenerationWorkspace/hooks/useUpdateCheck.ts:43`；相关：`electron/main/services/updater.ts`、`src/utils/updateConfig.ts`、`src/components/UpdateDialog.tsx`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：在打包好的 Electron 环境里，用户在 UpdateDialog 点「跳过此版本」后（addIgnoredVersion 写入 localStorage 的 update_config.ignoredVersions），下次启动时 useUpdateCheck 的 run() 调用 checkForUpdates()。主进程 autoUpdater 在 checkForUpdates 的 promise 返回前就发出 update-available 事件，渲染层 onEvent 收到后进入 applyUpdaterResult，因为 hasUpdate=true 直接打开更新弹窗。之后 run() 的 isVersionIgnored 判断只是 return，弹窗不会关闭。结果是被跳过的版本每次启动都会再弹出来，「跳过此版本」在 Electron 路径下实际无效。设置页的「检查更新」（useUpdateConfig.checkNow）也走同一个事件，同样会弹窗。非 Electron 路径（GitHub API）只靠 run() 的返回值决定是否弹窗，不受影响。
- 修法：在 useUpdateCheck.ts 的 applyUpdaterResult 中，先算出 version = result.latestVersion || result.releaseInfo?.version，然后按状态区分处理。status 为 'available' 且 isVersionIgnored(version) 为真时，不调用 setShowUpdateDialog(true)。可以照常 setReleaseInfo，也可以直接 return，但不要打开弹窗。'downloading'/'downloaded' 是用户主动点下载之后才会出现的状态，继续允许打开弹窗。run() 里原有的 isVersionIgnored 判断保留。如果产品希望设置页手动「检查更新」时无视忽略列表，需要给事件路径增加区分来源的标志（例如 manual check 期间暂时放行），这一点要由产品决定，默认按忽略处理即可。建议补一个 renderHook 测试：先忽略版本，再推送 available 事件，断言 showUpdateDialog 为 false；同时覆盖 downloading 状态下仍然弹窗。目前没有 useUpdateCheck 的测试文件。
- 测试缺口：useUpdateCheck 没有任何测试（src/workspaces/GenerationWorkspace/hooks/ 下没有 useUpdateCheck.test.*）。electron/main/services/updater.test.ts 只覆盖主进程 checkForElectronUpdates 的元数据缺失和网络错误，没有覆盖渲染层事件路径与忽略版本的交互。

### 缺陷 5：下载失败后主进程把 hasUpdate 重置为 false，更新对话框的「重试」必然报「No update is available to download」

- 排查编号：`settings-1`
- 位置：`electron/main/services/updater.ts:217`；相关：`src/components/UpdateDialog.tsx`、`src/workspaces/GenerationWorkspace/hooks/useUpdateCheck.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：前提：已检查到新版本（status=available，hasUpdate=true）。用户点「立即更新」，autoUpdater.downloadUpdate 因网络中断等非取消错误失败，electron-updater 先 emit('error')。updater.ts 的 error 监听用 makeBaseStatus('error') 覆盖 currentStatus，hasUpdate 变为 false，latestVersion 和 releaseInfo 被清空。对话框仍按 electron-updater 来源显示「重试」。用户点重试后，downloadElectronUpdate 在 295-296 行检查 hasUpdate 不通过，抛出 "No update is available to download"。只要用户不重新检查更新，重试就永远失败，错误文案也误导用户。另外，检查阶段失败同样会清空状态，不过那时本来就没有可下载的更新，所以影响不大。
- 修法：修改 electron/main/services/updater.ts 中 autoUpdater.on('error') 的处理：如果出错时 currentStatus.hasUpdate 为 true（或 status 为 downloading/available），就保留更新信息，改为 setStatus('error', { ...currentStatus, status: 'error', progress: undefined, errorMessage: error.message })，让 hasUpdate、latestVersion、releaseInfo 留在状态里；检查阶段（之前没有更新）出错时保持现有的 makeBaseStatus('error') 行为。downloadElectronUpdate 的 hasUpdate 前置判断不需要改。在 electron/main/services/updater.test.ts 中补一个用例：先检查到更新，第一次下载先 emit error 再拒绝，第二次重试下载应成功，并断言 error 事件的 result 仍带 hasUpdate=true 和 latestVersion。
- 测试缺口：electron/main/services/updater.test.ts 只测了 checkForElectronUpdates 阶段的元数据缺失和网络错误，downloadElectronUpdate 的失败与重试路径完全没有测试。

### 缺陷 6：更新对话框的发布日期文案硬编码中文，英文界面显示「今天/天前/周前」

- 排查编号：`settings-7`
- 位置：`src/services/updateChecker.ts:189`；相关：`src/components/UpdateDialog.tsx`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：界面语言为 en-US，并检测到新版本（真实 updater/GitHub release，或开发预览 fixture updatePreviewFixture.ts）。UpdateDialog 标题栏版本行的末尾会显示「今天」「昨天」「3 天前」「2 周前」「2 个月前」这类中文；发布超过一年时则显示 zh-CN 格式的日期，例如「2025/3/1」。对话框里其余文案都是英文，只有这一处是中文。
- 修法：让 formatReleaseDate 接收 locale 参数（或由调用方传入 i18n.language），用 `new Intl.RelativeTimeFormat(locale, { numeric: 'auto' })` 输出 day/week/month 级别的相对时间。超过一年时改用 `date.toLocaleDateString(locale)`。也可以改为 i18n key（例如 ui:updateDialog.published.today/yesterday/daysAgo_one/_other 等，带复数），并在 zh-CN 和 en-US 的 ui.json 中补齐。UpdateDialog.tsx:155 改为 `formatReleaseDate(releaseInfo.publishedAt, i18n.language)`，或在组件内用 t() 格式化。同时补一个单元测试，覆盖 en-US 与 zh-CN 两种语言下的输出；UpdateDialog.test.tsx 中把它 mock 成固定中文的写法也一并调整。
- 测试缺口：UpdateDialog.test.tsx:13 把 formatReleaseDate 整体 mock 成返回 '2 天前'，updateChecker 也没有针对 formatReleaseDate 的单元测试，所以多语言输出完全没有测试覆盖。
