# 3.1 生成链路与付费授权

## 任务状态

- 状态：待开始
- 所属阶段：第三阶段-生成助手与平台
- 前置任务：无
- 关联任务：1.4（预检压缩/裁剪）、3.2（SDK 上传取消）

## 任务目标

助手与外部智能体只能把授权目录内的文件作为生成媒体；同一音色重训不会命中旧结果；界面付费确认与主进程账本的过期规则一致且账本可清理；重新编辑任务的参数回填不与模型切换竞争。

## 当前情况

- 媒体引用解析 `src/features/generation/application/generationMediaReferences.ts`；待取结果缓存 `electron/main/services/ai-runtime/pending-results.ts`；付费授权 `electron/main/services/application-runtime/paidApprovalPolicy.ts`。
- 重新编辑回填 `src/components/MediaGenerator/hooks/useReeditContent.ts`。
- `generation-0` 属于安全边界问题（任意本地路径被读取并上传），优先处理。

## 实施方案

媒体路径复用主进程已有的媒体根授权（`media/rootGrants.ts`、`allowMediaRoot`）做校验；待取结果的缓存键加入提交身份；付费确认在界面侧也展示剩余时间或在过期后重新请求；账本加入定期核对与清理。

### 缺陷 1：助手/外部 MCP 传入的任意本地路径被当作生成媒体读取并上传到供应商，未做授权目录校验

- 排查编号：`generation-0`
- 位置：`src/features/generation/application/generationMediaReferences.ts:19`；相关：`electron/main/services/ai-runtime/sdk-runtime.ts`、`electron/main/services/ai-runtime/native-file-upload.ts`、`packages/ai-sdk/src/upload/preprocess-core.ts`、`packages/ai-sdk/src/upload/provider-preprocessors/ppio.ts`、`src/features/generation/application/registerGenerationCapabilityHandlers.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：外部 MCP 客户端（默认 allowWrites 和 allowPaid 均为 true）或被提示注入的内置助手调用 prepare_generation_task 或 create_visible_generation_task，有两种传法：
  - params={uploadedFilePaths:['/Users/x/Pictures/private.jpg']}，不带 images/uploadedImages，此时会完全跳过引用解析；
  - params={uploadedImages:['~/Documents/secret.png']} 或 'file:///etc/hosts'。
  这些字符串会原样进入 options.uploadedFilePaths。主进程 SDK 预处理阶段，electronMediaReader.read 直接 readFile 任意路径，再以 base64 或公网上传的形式发给第三方供应商，图生图结果还可能被助手读回。read_application_media 和 scopedUploadFile 都强制已授权媒体目录，唯独生成链路没有。效果是：只拿到受限媒体读取权限的调用方，可以通过生成任务把授权目录以外的本地文件外发。注意 UI 自身流程的路径来自文件选择或素材库导入，已经执行过 allowMediaRoot，修复不应破坏这条路径。
- 修法：分两层修复。
  1. 渲染层应用边界，修改 generationMediaReferences.ts。该函数只被能力处理器（助手/MCP）调用：
     - 对 uploadedImages/images 等数组中的字符串值，只接受 data: 和 https?:// 远程 URL，拒绝裸文件系统路径、~/、file://、盘符路径和 henji-media 协议，报 INVALID_INPUT 并提示改用 {kind,id}。
     - 对调用方显式传入的 uploadedFilePaths/uploadedVideoFilePaths/uploadedAudioFilePaths 同样校验，或者直接忽略、只用引用解析出的 paths，不再用 `options[field.paths] ?? paths`。
     - 草稿兜底（params 省略时）来自可信 UI 状态，不受影响。
  2. 主进程统一授权，作为根本防线。在 electronMediaReader.read 读取本地路径前，复用 native-file-upload.ts 中 scopedUploadFile 的同一判定：isPathWithinAllowedMediaRoots(local) 加 isRealPathWithinAllowedMediaRoots，失败时抛 AiRuntimeError('media_scope_denied')。最好抽成一个共用的 assertAllowedLocalMedia。同时确认 nativeMediaChunks 的分块读取走同一校验。
  补充测试：
  - generationMediaReferences.test.ts 增加用例，覆盖裸路径和显式 uploadedFilePaths 被拒绝、https 远程结果仍然放行（历史回退用例依赖这一点）；
  - sdk-runtime.test.ts 增加用例，验证授权目录外的路径被拒绝。
- 测试缺口：src/features/generation/application/generationMediaReferences.test.ts 只测了 {kind,id} 引用的解析和拒绝，没有覆盖字符串路径和显式 uploadedFilePaths 的授权拒绝。electron/main/services/ai-runtime/sdk-runtime.test.ts 没有测试 electronMediaReader.read 对授权目录以外路径的拒绝。

### 缺陷 2：pending_task_results 仅按供应商 taskId 缓存，重训同一火山音色时直接命中旧的完成结果而不再查询供应商

- 排查编号：`generation-1`
- 位置：`electron/main/services/ai-runtime/pending-results.ts:37`；相关：`electron/main/services/ai-runtime/runtime.ts`、`src/workspaces/GenerationWorkspace/hooks/continuePollingTask.ts`、`packages/ai-sdk/src/providers/volcengine-voice-clone.ts`、`src/services/voiceLibrary/captureClonedVoice.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：用户在生成工作区用火山 seed-icl-2.0 的「使用已有音色」重训一个预付费槽位 S_xxx（状态为已训练、未激活、有剩余次数），名称沿用上次的名称。第一次训练完成后，pending_task_results 已留下以 taskId 'volc-voice:{speaker:S_xxx,name,postpaid:false}' 为主键的 completed 回执（含旧试听 URL 和本地文件），且该回执永不删除。第二次训练时 voice_clone 返回 status=1，于是 generate 返回 pending，taskId 与上次完全相同。continuePollingTask 先调 aiReadSavedResult(taskId)，命中旧回执，于是不再调用 get_voice，任务立刻标记成功并展示旧试听音频，captureClonedVoice 也用旧 metadata 把音色记为 ready。本次训练的真实结果（仍在训练中、失败 status=3、或新的试听）始终没有核对。假如走主进程 runtime.continuePolling（例如画布 runGeneration、VoiceSelectorPanel），runtime.ts:234 的 consumePendingResult 同样会优先返回旧回执，不发起真实轮询。影响范围限于 taskId 由「身份」而非「本次提交」决定的供应商，目前已确认的是火山音色克隆；其他供应商的 taskId 每次提交都不同，不会触发。
- 修法：首选在 SDK 根治：让 volcengine-voice-clone.ts 的 taskId 带上本次提交的标识。具体做法是在 CloneIdentity 中加入 submission 字段（例如 volcengineRequestId(input.requestId) 或提交时间戳），由 executeVoiceClone 写入；decodeTask/pollVoiceClone 读取时忽略该字段，只用 speaker/postpaid 查询。这样每次训练的 taskId 唯一，宿主缓存语义（taskId 对应一次供应商任务）恢复成立。此项属于 SDK 改动，需按规则先接入痕迹AI并交用户测试，不得自行发版。
  可选的宿主侧防御：主进程 generate 收到 pending 且带 taskId 时，先删除 pending_task_results 中同 taskId 的旧行（新增 deletePendingResult，同时清 unconfirmedResults）。这样旧回执不会冒充新任务，又不影响同一任务中断后的恢复。不要只改渲染层 continuePollingTask，因为主进程 continuePolling 有同样的优先缓存逻辑。
  建议补两条测试：runtime.test.ts 覆盖「同 taskId 的新 pending 提交之后，续查必须调用 SDK」；SDK 测试覆盖「对同一 speaker/name 两次 executeVoiceClone 得到不同 taskId，且 pollVoiceClone 仍能解析」。
- 测试缺口：electron/main/services/ai-runtime/runtime.test.ts 只验证同一 taskId 续查后能恢复回执（「成功链路……使用规范化 taskId 保存 pending 结果」），src/workspaces/GenerationWorkspace/hooks/continuePollingTask.test.ts 只验证命中缓存时跳过轮询。两者都没有覆盖「同一供应商 taskId 被新的一次提交复用」的情况；packages/ai-sdk 的音色克隆测试也没有断言两次提交的 taskId 互不相同。

### 缺陷 3：界面付费确认弹窗无超时，但主进程账本 5 分钟后判确认过期，用户点“允许本次”反而让生成失败

- 排查编号：`generation-2`
- 位置：`electron/main/services/application-runtime/paidApprovalPolicy.ts:67`；相关：`src/core/services/generationSubmissionConfirmation.ts`、`src/core/application-control/userConfirmation.ts`、`src/stores/alertDialogStore.ts`、`src/core/services/GenerationService.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：付费审批模式为 ask，或本次超出单次/每日额度时，用户在生成页（以及识别、翻译、标题、讲解等走 withPaidOperation 的界面付费操作）点生成，弹出付费确认。主进程账本在 prepare 时写入 confirmation.expiresAt=now+5min；界面弹窗（showAlertConfirmation，在 application 确认作用域之外）没有任何定时器，会一直开着。用户 5 分钟后点"允许本次"，paid.confirm 发出 approve，主进程在 paidApprovalPolicy.ts:67 抛出"付费确认已结束，请重新发起。"。渲染层 catch 里先 reject 账本（没有计费），再把原错误上抛。生成路径在 GenerationService 中被包成 GenerationFailedError，任务卡片显示为失败；withPaidOperation 路径则作为普通错误上抛。不会多收费，但用户确认后看到的是一个误导性的失败，而不是"已过期/已取消，请重新发起"。
- 修法：让界面路径与账本使用同一个期限，只在一处修改，覆盖所有调用方：
  1. 推荐在 src/stores/alertDialogStore.ts 的 requestAlertConfirmation 里，当请求带 paidConfirmation 且不在 application 作用域内时，给 showAlertConfirmation 套一个超时用的 AbortController（AbortSignal.any([signal, AbortSignal.timeout(USER_CONFIRMATION_TIMEOUT_MS)]) 或 setTimeout，要清理），超时后弹窗关闭并返回 false。这样 confirmGenerationSubmission 会抛 GenerationSubmissionCancelledError（GenerationService 按取消收口），withPaidOperation 会抛 PaidOperationCancelledError，两条路径都按取消处理，不再标记为失败。更严格的做法是由 prepare 把 expiresAt 回传给渲染层，弹窗按这个时间关闭，避免 IPC 往返带来的边界竞态。
  2. 兜底：在 confirmGenerationSubmission 和 withPaidOperation 中，把 approve 返回的"付费确认已结束"映射为取消类错误（GenerationSubmissionCancelledError / PaidOperationCancelledError），而不是普通失败。
  补测试：paidApprovalPolicy.test.ts 加"过期后 approve 抛错"的用例；alertDialogStore 加"界面付费确认在 USER_CONFIRMATION_TIMEOUT_MS 后自动关闭并返回 false"的用例。
- 测试缺口：electron/main/services/application-runtime/paidApprovalPolicy.test.ts 只用"approve 后不能重放"来断言"已结束"，没有覆盖 expiresAt 到期后 approve 的情况；alertDialogStore 和 generationSubmissionConfirmation 都没有测试覆盖界面路径付费弹窗与 USER_CONFIRMATION_TIMEOUT_MS 的一致性。

### 缺陷 4：界面付费账本记录失败/退出后永久停留在 unknown，从不被核对或清理，持续膨胀并参与每次写操作与注册时的全量扫描

- 排查编号：`generation-3`
- 位置：`electron/main/services/application-runtime/paidApprovalPolicy.ts:80`；相关：`src/core/services/GenerationService.ts`、`electron/main/services/application-runtime/operationStore.ts`、`electron/main/services/application-runtime/persistedOperationRecovery.ts`、`electron/main/services/application-runtime/operationCoordinator.ts`、`electron/main/ipc/application-control.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：用户在界面发起任一付费操作：生成、讲解、转写、翻译、标题、模型验证或助手对话，都走 withPaidOperation / GenerationService。paid.start() 之后，只要出现以下任一情况，记录就会停在 unknown：
  - 供应商报错，包括明确未计费的 4xx 或余额不足；
  - 用户取消；
  - 进程在执行中途退出（recoverInterrupted 会把 executing 改成 unknown）。
  这些记录满足四个条件：callerId=rendererEpoch，没有 requestId/rendererEpoch，没有 targetRefs，input={paid}。重启后没有任何恢复器能认领它们：
  - 历史表按助手的 invocation ID 去查，对界面任务查不到；
  - 转写恢复要求有 requestId；
  - recoverPreflight 只处理免核对能力，create_visible_generation_task 和 transcribe_audio_edit 是写能力，ui_* 不在注册表里，都不会被转换。
  operationAccess 解析失败后 targets 为空，ApplicationOperationReviewBanner 永远不会显示这些条目，用户也就无法 resolve。结果是这些记录永久留在 unresolved() 和 pendingReviews() 中，并带来四个后果：
  1. 每次助手写操作 prepare 都要全量遍历这些记录，并逐条调用 recoverPreflight / operationAccess；
  2. 每次宿主注册时，每条记录都要跑一次 reviewOperation→reconcileVerification；
  3. 每次 publishReviews 都把「这次修改生效了吗？…执行到一半时应用重新加载」这样的幽灵条目发给渲染层，而文案与实际情况不符：这是用户自己的生成失败，不是应用重新加载；
  4. 预留金额当天继续计入 generationSpendSince。对已明确未计费的拒绝来说，这会多占每日额度；其中保守计入未知账单是设计意图（见 withPaidOperation 的注释）。
  数量会随失败或取消次数无限增长，不过单条开销很小，所以严重度低。
- 修法：按优先级：
  1. 界面付费记录（record.origin?.actor==='user' 且 capabilityId ∈ UI_PAID_CAPABILITIES，或 input 只有 paid）不应进入助手的核对体系。
     - 在 operationCoordinator.pendingReviews() 和 prepare 的重叠遍历里跳过这类记录。
     - 在 application-control.ts 注册时的 reviewOperation 循环里也跳过。
     - 更好的做法：在 store.unresolved() 或 recoverPreflight 中识别界面记录，保留 paidReservations 用于计费，但把核对状态收敛为已终结，例如新增 state='failed_unverified'，或者改为 not_executed 并保留预留。
  2. failed 时按错误事实区分。渲染层 withPaidOperation / GenerationService 已经拿得到供应商前置拒绝（未提交任务、4xx 参数错误、余额不足）这类结构化事实，这时应传 action='reject' 或新增 'not_charged'，置为 not_executed，释放当日额度。只有确实可能已计费的失败才保留 unknown。
  3. 应用退出时处于 executing 的界面记录，在 recoverInterrupted 或协调器启动时直接收敛为终态（保留预留），不要留在 unresolved。
  4. 补测试：在 paidApprovalPolicy.test.ts 或原生 operationStore.test.ts 中断言，界面记录在 failed 或重启后不出现在 pendingReviews()/unresolved() 里。
- 测试缺口：electron/main/services/application-runtime/paidApprovalPolicy.test.ts 只断言了 failed 之后状态为 unknown。src/services/paidApproval.test.ts 只断言了 prepare/start/complete/failed 的调用顺序。两者都没有验证这些界面记录在重启后能被 unresolved()/pendingReviews() 收敛或排除；operationStore.test.ts（Electron 原生运行器）也没有覆盖界面来源的记录。

### 缺陷 5：重新编辑任务时用 100ms 定时器回填参数，闭包捕获的是切换前模型的 setParams（旧 schema/旧别名归一化），并与模型切换后的参数重置存在时序竞争

- 排查编号：`react-2`
- 位置：`src/components/MediaGenerator/hooks/useReeditContent.ts:171`；相关：`src/hooks/useModelParams.ts`、`src/workspaces/GenerationWorkspace/hooks/useTaskReplay.ts`、`src/components/MediaGenerator/state/useModelState.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：In the generation page, the user clicks "re-edit" on a task generated by a different model than the one currently selected (useTaskReplay.handleReedit, useTaskReplay.ts L99-111). handleReedit in useReeditContent.ts runs setSelectedModel(model) at L68, then L110-115 calls window.setTimeout(() => modelState.setParams(sanitizedOptions), 100). The modelState here is the object from the render before the switch, so its setParams is bound to the old model's model/schema. Two consequences:
  1. normalizeModelAliasParams uses the old model's aliasParamMappings. When the target model has legacy parameter mappings, those parameters are not mapped. In the repro, the current model stays at its default '1:1' while the value sits under the legacy key.
