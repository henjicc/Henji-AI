### 缺陷 1：密钥保存失败（safeStorage 不可用、密钥文件损坏/版本不符）被静默吞掉，界面仍显示已输入

- 排查编号：`settings-2`
- 位置：`src/components/Settings/hooks/useApiKeys.ts:123`；相关：`electron/main/services/keystore.ts`、`src/components/Settings/sections/ProviderCenterSection.tsx`、`src/components/Settings/hooks/useLlmSettings.ts`、`src/components/Settings/components/ApiKeyInput.tsx`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：在 Linux 没有钥匙串（safeStorage.isEncryptionAvailable() 为 false），或 provider-keys.enc.json 损坏、版本不等于 KEYSTORE_VERSION 时，用户在供应商中心输入生成供应商密钥。450ms 防抖后 aiSetProviderApiKey 被拒绝，useApiKeys 的 catch 只写日志：输入框继续显示刚输入的明文，providerKeyStatus 保持 false，界面上看不到任何提示。之后生成时只会报"未配置密钥"，用户不知道真正原因是设备不支持加密或密钥文件损坏。LLM 供应商密钥走 useLlmSettings.updateKey（commitProviderSettings），catch 同样只写日志。删除密钥（aiRemoveProviderApiKey）走同一个 catch，也有同样问题。
- 修法：1. useApiKeys：增加 errors: Partial<Record<ApiKeyProvider, string>> 状态。catch 里按 error.message 归类成用户可读的 i18n 文案（例如"此设备不支持系统加密，无法保存密钥"、"密钥文件无法读取，请在设置中重置"），写入 errors[provider]。重新输入或保存成功时清除该条。在 UseApiKeysResult 里导出 errors。
  2. useLlmSettings.updateKey 同样增加按 providerId 区分的 keyErrors。
  3. ProviderCenterSection 的三处 ApiKeyInput（多服务列表、单一生成凭据、LLM 凭据）传入 error={...}，复用 ApiKeyInput 已有的 role=alert 渲染。
  4. 可选：失败时把输入框回退到上次已保存的值，或者保留输入但明确标成"未保存"。
  5. 补测试：mock aiSetProviderApiKey 抛错，断言 hook 暴露错误、界面出现 alert；remove 失败的情况同样补一条。
  主进程 keystore 不需要改，它的抛错语义是正确的。
- 测试缺口：src/components/Settings/sections/ProviderCenterSection.test.tsx 把 useApiKeys mock 成了 updateKey: vi.fn()，useApiKeys 和 useLlmSettings 也都没有单独测保存失败（aiSetProviderApiKey 或 commitProviderSettings 被拒绝）的测试，所以失败被吞掉这件事从没被覆盖。

### 缺陷 2：密钥写入防抖在组件卸载时被取消，刚输入的密钥丢失

- 排查编号：`settings-4`
- 位置：`src/components/Settings/hooks/useApiKeys.ts:95`；相关：`src/components/Settings/sections/ProviderCenterSection.tsx`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：用户在「供应商与模型」设置页输入或粘贴生成供应商密钥后，450ms 内让 ProviderCenterSection 卸载，这次写入就会丢失。会导致卸载的操作有：关闭设置弹窗，或切换到别的设置标签页（ProvidersTab 卸载）。原发现中说「切换到别的供应商页」也会触发，这一点不成立：供应商的选择是 ProviderCenterSection 内部的 selectedId 状态，切换供应商时 useApiKeys 不会卸载，各供应商的定时器按 provider 分开存放，互不取消。卸载时，cleanup 会对所有待执行的定时器调用 clearTimeout，aiSetProviderApiKey 或 aiRemoveProviderApiKey 永远不会被调用，store 里的 providerKeyStatus 也不会更新。输入框里看起来已经填好，但下次打开是空的（如果是清空操作，旧密钥会保留下来），生成时会提示未配置密钥。
- 修法：在 useApiKeys 里给每个 provider 记录待写入的值（例如 pendingRef: Record<provider, string>），并把写入逻辑抽成 persistKey(provider, value)。setTimeout 回调执行时调用 persistKey，并删除 pending 条目。卸载 cleanup 时不再只做 clearTimeout，而是对每个仍有 pending 值的 provider 先 clearTimeout，再立即 void persistKey(provider, value)，也就是 flush。这样写入在卸载后照常完成。persistKey 只调用命令和 store/事件，不调用 setKeys，所以卸载后执行是安全的。同时补一个 useApiKeys 的 jsdom 单测：updateKey 之后立即 unmount，断言 aiSetProviderApiKey 被调用；再测一次空值的情况，断言调用的是 aiRemoveProviderApiKey。
- 测试缺口：useApiKeys 本身没有单测；ProviderCenterSection.test.tsx 用 vi.mock 把 useApiKeys 整个替换掉了，所以防抖写入和卸载清理都没有被测到。

### 缺陷 3：「跟随系统」语言下 en-GB/en-AU/en 等非 en-US 英文系统全部回落为中文

- 排查编号：`settings-3`
- 位置：`src/i18n/config.ts:107`；相关：`src/utils/language.ts`、`src/hooks/useI18n.ts`、`src/core/types/I18nText.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：操作系统界面语言是 en-US 以外的英文（en-GB、en-AU、en-IN、en-CA，或只有 'en'），并且用户没有手动选过语言（localStorage 中没有 henji-language）。这时有两种情况：一是首次启动，LanguageDetector 从 navigator 检测到 'en-GB'；二是在设置的语言分区选择「跟随系统」，utils/language.ts:23-24 直接执行 i18n.changeLanguage(navigator.language)。i18next 的解析链是 ['en-GB','en','zh-CN']，前两项都没有资源，界面文案就全部回落为中文。此时 i18n.language 仍然是 'en-GB'：getI18nText(text, i18n.language) 等直接按语言码查找的代码（ParamGroupTrigger、ResolutionPanel 等）同样找不到英文；PriceEstimate 使用的 resolvedLanguage 会是 'zh-CN'。结果就是英文用户在「跟随系统」下看到的是全中文界面。zh-TW、zh-HK 等系统依赖 fallbackLng 碰巧回落到中文，不在本缺陷范围内。
- 修法：最小修复：在 src/i18n/config.ts 的 init 中加上 `supportedLngs: ['zh-CN','en-US']`，并把 fallbackLng 改为 `{ en: ['en-US'], zh: ['zh-CN'], default: ['zh-CN'] }`。加了 supportedLngs 之后，'en-GB' 这类不在列表里的语言码会被 i18next 拒绝，直接走 fallback。这样做能让文案正确，但 i18n.language 可能仍是原始标签或不稳定，所以更推荐下面的做法：
  1. 新增一个归一函数 normalizeLanguage(raw) → 'zh-CN' | 'en-US'（以 'en' 开头的映射为 'en-US'，以 'zh' 开头的映射为 'zh-CN'，其余用默认值）。
  2. 在 detection 中配置 `convertDetectedLanguage: normalizeLanguage`（i18next-browser-languagedetector 支持该选项）。
  3. 在 utils/language.ts 的 'auto' 分支改为 i18n.changeLanguage(normalizeLanguage(navigator.language))。
  这样 i18n.language 永远只会是两个受支持值之一，getI18nText(..., i18n.language) 等直接按语言码查找的消费方也一并修好。补一个单元测试：用 jsdom 把 navigator.language 设为 'en-GB'，调用 changeLanguage('auto') 后断言 t() 返回英文、i18n.language === 'en-US'。目前 Dropdown/GlobalAlertDialog 等测试只调用 changeLanguage('zh-CN'/'en-US')，从未覆盖 'auto' 或非精确匹配的语言标签。
- 测试缺口：src/utils/language.ts 没有任何测试；所有组件测试都只用精确的 'zh-CN'/'en-US' 调用 i18n.changeLanguage，没有覆盖「跟随系统」(auto) 路径，也没有覆盖 en-GB 这类非精确匹配的系统语言标签。

### 缺陷 4：引导进度读取失败后所有写入都抛错，跳过/完成/重新运行引导按钮看起来失灵

- 排查编号：`settings-5`
- 位置：`src/features/onboarding/application/onboardingManager.ts:335`；相关：`src/core/persistence/stateStorage.ts`、`src/features/onboarding/components/OnboardingModal.tsx`、`src/components/Settings/sections/OnboardingSection.tsx`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：触发条件：localStorage 中 henji-onboarding-state 是损坏的 JSON，或 version≠2（例如 1.x 留下的 v1 数据；formatMigrations 中没有 'onboarding' 迁移）。
  1. OnboardingManager 构造时，guardedPlainStorage.getItem 记下 failure 并返回 null。loadState 回退为 not_started、isOpen=true（未传 suppressInitialOpen 时）。
  2. OnboardingModal 挂载后，effect 调用 onboardingManager.open() → update → commit → persist → guardedPlainStorage.setItem 因 failure 抛出 PersistenceError。这个异常冒泡到 main.tsx 的根级 UiErrorBoundary，整个应用显示"界面出现异常"。原数据从未被改写，所以每次启动都会重现。
  3. 即使上面这一步没崩，skip()/complete()/restart()/next()、设置页的"重新运行引导"、provider-key-configured 事件回调里的 markProviderConfigured 也都会在 publish 之前抛错。界面状态不变，按钮看起来没有反应，事件订阅回调也会抛错。
- 修法：在 onboardingManager.ts 里让写入失败不影响内存态和 UI。改法是把 persist() 包进 try/catch，失败时用 persistenceLogger.warn 记录（例如 event 'onboarding.persist.failed'），commit() 照常调用 publish()。这样引导在本次会话里可以正常使用，原数据保持不变，符合"原数据保留"的设计。
  另一种改法：确认读失败后，把损坏值备份到 `${key}:corrupt:<ts>`，再允许覆盖写入。但这会改变 guardedPlainStorage 的通用语义，需要同时检查其他调用方。
  需要补的测试，放在 onboardingManager.test.ts：
  - 分别用损坏 JSON 和 v1 数据构造 manager，调用 open/skip/restart/next，断言不抛错、快照按预期更新、原存储值不变。
  - 可选：在 OnboardingModal.test.tsx 中验证读失败的存储不会触发错误边界。
  同源排查：搜索 guardedPlainStorage 的其他调用方，确认它们的写入路径是否同样没有捕获异常。

### 缺陷 7：图片查看器打开期间全局拦截 Tab 键，键盘无法在查看器的按钮/对比滑块之间移动焦点

- 现象：信息面板默认开启。打开任意图片查看器（非编辑模式，role=dialog aria-modal）后，window 级监听会拦下所有 Tab 和 Shift+Tab：每次都 preventDefault，只切换信息面板的折叠状态，焦点始终不动。键盘用户因此无法把焦点移到关闭、上一张、下一张、对比模式分段、重置视图、对比分界线（role=slider，自身支持方向键、Home、End）等控件。分界线的键盘支持也就没有办法用到。需要说明的是，Tab 切换折叠是有意设计的功能，设置提示文案 imageViewerInfoHint 和 storyboard 的 toggleInfo“（Tab）”都写明了它。所以这里的问题是这个有意设计的快捷键覆盖了标准的焦点导航，造成可访问性断裂，不是逻辑写错。严重度为低：鼠标用户不受影响，Escape 和方向键仍然可用。

### 缺陷 8：引导高亮用 MutationObserver 监听整个 document.body 的子树变化，每次任意 DOM 变更都强制布局并以新对象 setState 重渲染

- 排查编号：`react-4`
- 位置：`src/features/onboarding/components/OnboardingHints.tsx:106`；相关：`src/components/MediaGenerator/hooks/usePromptOptimizationPreviewPlayback.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：触发条件：首次引导的教练阶段正在显示（status=in_progress、firstTaskPrepared=true、firstTaskCompleted=false，且三个教练步骤中还有没看过的）。在这期间，页面上任何地方只要发生 childList 变更（提示词优化的预览逐字形追加 span、任务卡增删节点、通知或 toast 出现等），useHighlightGeometry 的 update 都会同步执行一次 querySelector，再调一次 getBoundingClientRect（强制同步布局），然后用新对象 setGeometry，让 OnboardingHints 整棵子树重渲染一次，即使目标位置完全没变。流式预览期间大约每帧都会多出一次强制布局和一次 React 提交。单测已证明：50 次无关的 DOM 追加带来了 50 次多余提交。不会形成死循环：重渲染只改 style 属性，不会再触发 childList 回调。功能结果是正确的，只是有多余开销，所以严重度为低。
- 修法：修改位置：src/features/onboarding/components/OnboardingHints.tsx 中的 useHighlightGeometry。
  (1) setGeometry 改用函数式更新，逐字段比较 top/left/width/height/popoverTop/popoverLeft/popoverWidth/arrowLeft/popoverAbove；全部相同就返回 previous，避免无效的重渲染。
  (2) 用 requestAnimationFrame 合并回调：MutationObserver、resize、scroll 和 ResizeObserver 的回调只负责排一个 rAF（已经排过就不再重复），真正的测量在同一帧里只做一次；清理时调用 cancelAnimationFrame。
  (3) 可选：MutationObserver 只在需要重新确认目标是否还存在时才有意义。可以在找到目标后只检查 observedTarget.isConnected，或者在 rAF 里做 querySelector，这样能减少每次变更的开销。
  修复后应补一条测试：往 body 追加无关节点时，OnboardingHints 不产生新的提交（可以参考本次复现里的 Profiler 计数做法）；同时保留现有用例「依次聚焦模型、提示词和生成按钮」。
- 测试缺口：src/features/onboarding/components/OnboardingHints.test.tsx 只测了按步骤推进（模型 → 提示词 → 生成 → 结束），没有测无关 DOM 变更时是否会多余地重渲染、重复测量。

### 缺陷 9：loadImage 在图片解码失败时不释放 createObjectURL 产生的 Blob URL

- 排查编号：`react-6`
- 位置：`src/components/params/upload/ImageUpload.tsx:133`
- 严重度：低；核实方式：调用链追踪确认（未写复现测试）
- 现象：param.format === 'base64'（目前没有任何 catalog 模型使用）或 UI 巡检只读模式（HENJI_UI_INSPECTION_READ_ONLY=1）下，用户上传一个 MIME 为 image/png 等白名单类型、但内容损坏或浏览器无法解码的图片。img.onerror 直接 reject，URL.createObjectURL(file) 生成的 blob URL 不会被 revoke，Blob 一直驻留到页面卸载。同时 handleUpload 中的 await loadImage 抛错，整个上传批次中断，onChange 不会被调用，用户也收不到错误提示。正式用户路径当前不可达。
- 修法：在 loadImage 中把 URL 存进局部变量：`const url = URL.createObjectURL(file)`，onload 和 onerror 都先 `URL.revokeObjectURL(url)`，然后分别 resolve / reject（reject 时建议包装成 Error）。可选：在 handleUpload 的 base64 分支用 try/catch 捕获解码失败，showNotification 提示后 continue，避免整批中断。
- 测试缺口：ImageUpload 没有专门测试。base64 分支与 loadImage 的解码失败路径都没有覆盖（DerivedMediaParamControl.test.tsx 等只间接引用了组件）。
