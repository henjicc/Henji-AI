# 3.4 内置助手与外部MCP

## 任务目标

长会话里最新的工具结果不被预算裁空；附件不在每轮重复整份注入；改权限后外部客户端能看到新工具；资源订阅不在每次上下文变化时全量广播；剪辑上下文不会撑爆消息上限；记忆写入策略不误报且并发安全。

### 缺陷 1：上下文预算把可用窗口平均分给所有历史工具结果，长会话中最新写入结果的 ok/executionState 被裁成空壳，回读工具也被同样压缩

- 排查编号：`assistant-0`
- 位置：`electron/main/services/embedded-agent/contextBudget.ts:81`；相关：`electron/main/services/embedded-agent/contextReader.ts`、`electron/main/services/embedded-agent/piEngine.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：长会话（例如 128K 窗口，约 120 次工具调用）里，budgetContext 把剩余预算平均分给全部历史 toolResult 文本段，最新写入结果的份额和最旧结果一样。随着会话变长，最新结果先只剩 facts 加几十字的 excerpt。再往后进入一个窄区间：在“整体超预算直接抛错”之前，perPart 已经小于 wrap('') 信封本身，projectText 就返回不含 facts 的空壳（ok/executionState/operationId 全部丢失，还附带“尚不能据此判定完成”）。模型因此无法确认最新写入是否成功。它改调 read_assistant_context 时，返回的分页同样是 toolResult：contextReader 没有经过 archiveToolResult，reference 退回为 tool:toolCallId:0，下一轮又按同样很小的 perPart 被 projectText 截断。分页信封的字段顺序是 data 在 nextOffset 之前，所以 nextOffset 先被截掉，也就无法续读，可能导致反复读取或误报未完成。实测在 128K 窗口、120 轮、每轮用户约 220 个汉字时，最新结果变成空壳；约 240 个汉字时整体抛出上下文超限错误。
  补充两点：第一，空壳区间较窄，再往后就会硬失败，它不会误报成功，而是让模型无法确认结果。第二，“最新结果的 excerpt 被平分压到极短”在更早阶段就普遍存在。
- 修法：1) projectText 永远保留 facts：wrap('') 超预算时，降级为 {facts, hasMore, reference, read} 的最小形态；facts 中较大的字段（data/message/recovery）先改为 omitted，ok/executionState/operationId/verificationState/persistenceState/error 不得丢弃。只有这些仍放不下时才抛出预算错误，不要返回不含事实的空壳。
  2) budgetContext 改为从最新往前分配：当前轮（最后一条 user 消息之后）的 toolResult 优先拿满份额（上限 4000）；旧结果先降为只保留 facts 加引用，剩余预算再按新到旧依次分配。
  3) read_assistant_context 的结果在当前轮内不再参与二次压缩，或者至少保证分页信封的 nextOffset/hasMore/reference 不被截断（例如把元数据字段放在 data 之前，或投影时单独保留）。
  4) 在 contextBudget.test.ts 补用例：多轮历史 + 最新写入结果，断言最新结果的 facts 和 excerpt 份额不低于旧结果，并覆盖 wrap('') 超预算分支。
- 测试缺口：electron/main/services/embedded-agent/contextBudget.test.ts 只用单条 toolResult 测了 budgetContext 的大窗口和小窗口投影，以及整体超预算抛错。没有覆盖多条历史结果平分预算时新结果被压缩的情况，也没有覆盖 projectText 在 wrap('') 超出 perPart 时丢掉 facts 的空壳分支，更没有覆盖 read_assistant_context 分页结果被二次投影的情况。

### 缺陷 2：用户历史附件在每次模型请求时重新读盘并以 base64 整体注入，且不计入上下文预算

- 排查编号：`assistant-1`
- 位置：`electron/main/services/embedded-agent/piAttachments.ts:57`；相关：`electron/main/services/embedded-agent/piEngine.ts`、`electron/main/services/embedded-agent/contextBudget.ts`、`electron/main/services/embedded-agent/attachments.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：在同一个 Pi 会话里，用户在某一轮附加了大体积媒体。单个视频最多 100MB，单条消息合计最多 128MB，跨轮次的累计量没有上限。PiAttachments.attach 只在消息文本末尾追加标记，实际媒体由 onPayload 里的 apply 在每次请求时注入。这会造成三个问题：
  (a) 之后每一轮、每轮内每次工具循环的模型请求，都会把全部历史附件重新读盘并 base64 后放进请求体。附件在历史里不断累积，请求体也随之增大。
  (b) budgetContext 在注入之前执行，附件只按标记文本计 token，所以“超出上下文预算”的友好提示永远不会因为附件触发。超限时由供应商直接返回 413 或上下文溢出错误。由于附件一直留在历史中，这个会话的后续请求都会持续失败。“持续失败”这一点取决于供应商的限制，未用真实供应商验证。
  (c) 即使请求成功，工具密集的回合也会反复读盘、编码并上传同样的数据。(a) 和 (b) 已由单元测试证实。
- 修法：1) 预算：budgetContext/messageTokens 要能识别附件标记。可以把 PiAttachments 的 entries 或一个 marker 到估算值的映射传进 budgetContext，按模态计入估算：图片取固定值，例如 4096；视频和音频按 durationSeconds 或字节数换算。同时检查请求体总字节，超出时抛出现有的友好错误。
  2) 注入策略：apply 只对最近一条带附件的 user 消息（当前回合）注入真实媒体。较早的视频和音频附件降级为现有的文字引用，例如“用户附件：名称（mediaRef）”，模型需要时再通过工具按 mediaRef 读取。图片可以设一个上限或保留最近 N 张。
  3) 缓存：在 PiAttachments 内按 hash 和 mimeType 缓存已编码的 data URL，至少在同一回合（同一个 requestId）内复用，回合结束后释放，避免重复读盘和 base64。
  4) 补测试：在 contextBudget.test.ts 增加“带附件标记的历史消息计入预算”的用例；在 piAttachments 或 piEngine 测试中断言多次 apply 不会重复读盘，且历史视频不会被重复注入。
- 测试缺口：没有现有测试直接测 PiAttachments.apply：messagePresentation.test.ts 只传了 {} as PiAttachments。contextBudget.test.ts 没有覆盖带附件标记的消息，piEngine.test.ts 也没有断言多次 onPayload 时的附件注入次数和请求体大小。

### 缺陷 3：修改外部连接权限后不发送 tools/list_changed，已连接客户端看不到新授权的工具

- 排查编号：`assistant-2`
- 位置：`electron/main/services/mcp/server.ts:65`；相关：`electron/main/ipc/mcp.ts`、`electron/main/services/mcp/connections.ts`、`electron/main/services/application-runtime/toolCatalog.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：1. 外部智能体用只读连接接入，并通过 subscriptions/listen 订阅 toolsListChanged。此时 tools/list 只返回 49 个读工具。
  2. 用户在设置 → 外部智能体连接中修改这条已有连接的权限，开启修改、删除、付费。前端走 mcp:update，后端只调用 connections.update，令牌不变。
  3. 服务端此后按新权限返回 170 个工具，但不发送 notifications/tools/list_changed。客户端按契约等通知后才重新 tools/list，所以一直用缓存的只读目录，看不到新开放的写工具，直到手动重连。
  4. 反方向也一样：收回权限后客户端仍以为写工具可用，调用时才收到 PERMISSION_DENIED。
  5. 契约 listChangedPolicy 写的是“授权范围调整须新建连接”，和现在“原地修改、下一次请求即生效”的产品行为互相矛盾，外部智能体无法从契约推断出需要重新发现目录。
  现有测试的缺口：server.test.ts 的 list_changed 用例只覆盖宿主目录变化（f.change / f.reconnect 加 mock host.tools），connections.test.ts 只验证 update 后 access() 生效，没有用例覆盖“改权限后的目录通知”。
- 修法：1. LocalMcpServer 增加 accessChanged(callerId)。
     - 内部比较该连接按新旧权限算出的目录签名（buildApplicationToolCatalog 加 connections.access(callerId)）。也可以直接无条件通知，因为改权限是低频操作。
     - 只向该 callerId 的 listen 流发布 { kind: 'tools_list_changed' }。
     - 实现方式：在 ApplicationResourceSubscriptions 中新增 publishTo(callerId, event)，只遍历 owner.callerId === callerId 的 listener。不要用 handler.notify.toolsChanged()，它会广播给所有连接。
     - 同时给该 caller 发一次 resources_list_changed，因为资源读取授权也依赖 access。
  2. ipc/mcp.ts 的 mcp:update 在 connections.update 之后调用 server.accessChanged(id)。
  3. 同步修改 toolCatalog.ts:285 的 listChangedPolicy 文案：把“授权范围调整须新建连接”改为“用户修改连接权限后会向该连接发送 notifications/tools/list_changed，客户端重新 tools/list”。
  4. 在 server.test.ts 增加用例：只读连接订阅后执行 connections.update 加 server.accessChanged，断言本连接收到通知、另一连接没有收到，并且重新 tools/list 后能看到写工具。fixture 需要传入 operations，否则写工具会因“操作账本不可用”被隐藏。
- 测试缺口：server.test.ts 中两个 list_changed 用例（“同一订阅的 schema 变化通知……”和“同一现代订阅真实收到工具变更通知……”）只覆盖宿主目录变化，没有覆盖通过 connections.update 修改连接权限的情况。connections.test.ts 只断言 update 后 access() 返回新权限，没有检查协议层通知。

### 缺陷 4：每次宿主上下文变化都向所有 MCP 订阅流广播资源列表变更，并对每个已订阅 URI 做授权回读和 resource_updated

- 排查编号：`assistant-3`
- 位置：`electron/main/services/mcp/resourceSubscriptions.ts:56`；相关：`electron/main/services/mcp/server.ts`、`src/features/application-control/useApplicationHost.ts`、`src/features/application-control/hostContext/hostContext.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：外部 MCP 客户端调用 subscriptions/listen 订阅了 N 个实体资源 URI（单流最多 128 个，处理器最多 16 个订阅）。随后用户在画布上拖动节点、切换选中、切换工作区，或修改任意设置。只要宿主上下文的 revision 推进，渲染端就会经 IPC 调用 publishContext，主进程据此发出 host.onChange('context')。server.ts 对 context 和 catalog 不作区分，每次都调用 handler.notify.resourcesChanged()。ApplicationResourceSubscriptions.publish 收到 resources_list_changed 后，对每个监听者的每个 URI 都经渲染宿主执行一次 read_application_entity 授权回读，成功后发送 resource_updated。实测 10 次纯上下文变化加 5 个 URI，产生了 50 次渲染端读取和 50 条 resource_updated，而资源数据完全没变。
  拖动时 nodes 每帧都会变化，主进程与渲染端之间会持续产生大量往返，最多达 16×128 个 URI 的读取。listener.pending 只能挡住同一 URI 正在进行中的重复请求，所以读取频率上限约为每个 URI 每次往返一次，并没有真正节流。客户端还会按这些通知不断重读资源。还有一个次要问题：pending 期间到达的变化会被直接丢弃，而不是合并到下一轮，所以真正发生的末次变化有可能漏报。
- 修法：1) server.ts 的 onChange 中，resourcesChanged() 只在 kind==='catalog' 时调用（或在实体目录或 domains 签名真正变化时调用），不再对 'context' 无条件调用。也可以把对已订阅 URI 的检查拆成独立路径，见第 2 条。
  2) resourceSubscriptions.ts:56 不应把 resources_list_changed 等同于“所有订阅资源都已更新”。建议为每个 listener 的每个 URI 记录上次读取结果中的 revisions 或内容哈希，回读后只在发生变化时发送 resource_updated。触发回读应改由 domain 或 scope revision 变化驱动，例如只在对应 scopeRevisions 推进时检查相关 URI，而不是由导航或选中变化驱动。
  3) 对回读做尾沿合并或节流，例如每个 listener 每 250–500ms 最多一轮。pending 期间到达的新变化要标记为 dirty，在本轮结束后补一轮，而不是直接丢弃。
  4) 补测试：publishContext 产生的纯上下文变化不应引起渲染端 read_application_entity 调用，也不应发送 resource_updated；资源 revision 变化时才发送一次；高频变化应合并。同时检查 server.test.ts 中依赖 f.change() 必然产生 resource_updated 的两条用例，改为让 fake 渲染端返回不同的 revisions 来驱动。
- 测试缺口：electron/main/services/mcp/server.test.ts 的「标准订阅只发送选中的资源更新，关闭与撤销释放流」和「订阅建立和每次资源通知按各自调用者核验」都用 f.change() 驱动 resource_updated，默认接受“任何变化都发送全部订阅 URI 的 updated”。没有测试覆盖纯 context 变化不应触发回读，没有测试检查资源未变化时不应发通知，也没有对高频变化的节流或合并做测试。

### 缺陷 5：内置助手 prompt 的 context 上限为 16000 字符，但剪辑上下文里的标注正文没有长度上限，超出后整条消息被 IPC 校验拒绝

- 排查编号：`assistant-4`

- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）

### 缺陷 6：一轮回复有 30 分钟绝对上限，到时直接杀掉 Pi 子进程，多段视频生成等待的合法长任务会被中断

- 排查编号：`assistant-5`
- 位置：`electron/main/services/embedded-agent/service.ts:91`；相关：`electron/main/pi-agent-utility.ts`、`src/core/application-control/domains/generation/generationApplicationCapabilities.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：用户在一条消息里让助手完成需要较长时间的任务，例如多镜头视频或短剧，每个任务调用 wait_generation_task（单次最多 10 分钟，返回 still_running 时按系统提示继续等待），或者模型和工具连续推进的总时长超过 30 分钟。主进程 EmbeddedAgentService.send 为 'prompt' 设置的是从发出时刻算起的 30 分钟绝对定时器，期间子进程发来的 tool、snapshot、log 活动都不会重置它。到时会依次发生：pending reject（'助手运行超时'），this.child.kill() 强杀 Pi utility 进程，exit 处理器 abort 所有正在执行的工具（包括 wait_generation_task），清空 client，界面显示“助手运行已中断”。drain 把这条消息记为失败。已提交的生成任务仍在后台运行，但助手丢失了本轮收尾（结果落位、汇报），Pi 会话也没有经过 session.abort 优雅收尾。
- 修法：在 electron/main/services/embedded-agent/service.ts 中：
  1) 把 prompt 的超时改为无活动超时。child.on('message') 每收到 snapshot、tool、toolResult 回执、log 事件，就对当前 prompt 的 pending 条目执行 clearTimeout 后重新 setTimeout，可以把 pending 条目的 timer 改为可重置，或单独记录 activePromptId。工具执行期间（toolControllers 非空）不应计入空闲，或者空闲阈值至少要大于最长工具 timeoutMs（10 分钟）。如需绝对上限，应明显大于多任务等待场景（例如数小时），或干脆不设。
  2) 超时处理先走优雅路径：调用 this.cancel()，即发送 {action:'cancel'} 让 piEngine 执行 session.abort()。只有 cancel 本身超过 60 秒仍无响应才 kill 子进程。
  3) 在 service.test.ts 中补充 fake-timer 用例：持续有 tool、snapshot 活动、总时长超过 30 分钟时不 kill；完全无活动超过阈值时走 cancel，cancel 无响应再 kill。
- 测试缺口：electron/main/services/embedded-agent/service.test.ts 只用 finish() 手动回复 prompt，没有任何 fake-timer 用例覆盖 prompt 超时或 kill 行为；servicePi.test.ts 同样没有覆盖。

### 缺陷 7：共享记忆写入策略误报：含有 token、error、info、debug 等普通词的偏好会导致整份记忆保存被拒

- 排查编号：`assistant-6`

- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）

  3. 在 memory-policy.test.ts 补充允许用例（含 error/debug/info/token 的普通中文偏好），并保留现有拒绝用例，防止回归。
- 测试缺口：electron/main/services/assistant/memory-policy.test.ts 只有一条不含敏感英文词的允许用例（'生成图片时我更偏好 KIE 供应商。'），没有覆盖中文偏好里夹 error、info、debug、token 等普通单词的情况。memory-store.test.ts 的 updateSharedMemory 用例只用了'偏好水墨质感。'这类内容。

### 缺陷 8：界面对 Responses 协议的模型开放音频附件，主进程在用户确认付费后才拒绝

- 排查编号：`assistant-7`
- 位置：`electron/main/services/embedded-agent/models.ts:22`；相关：`electron/main/services/embedded-agent/attachments.ts`、`electron/main/services/embedded-agent/piAttachments.ts`、`src/features/assistant/conversation/AssistantComposer.tsx`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：出问题的配置：一个模型勾选了“音频”能力，同时 apiProtocol 为 openai-responses。apiProtocol 可以写在模型上，也可以从 provider 继承。resolveEmbeddedModel 取协议用的是 {...provider, ...model}，所以两种写法都会让模型走 Responses 协议。
  界面一侧：listEmbeddedModels 只看 capabilities，返回的 inputModalities 包含 'audio'。助手输入框因此允许添加音频，也允许 @ 引用画布上的音频节点。

- 修法：1. 新增一个共用函数 embeddedInputModalities(capabilities, api)，放在 electron/main/services/embedded-agent 下，或放进 contracts 附近的新模块。它返回 ['image','video','audio'] 中 capabilities 为真的项；当 api==='openai-responses' 时去掉 'audio'。

- 测试缺口：models.test.ts 只测了主模型选择和 image 能力，没有覆盖 apiProtocol='openai-responses'（模型级或 provider 级）与 audio 能力的组合。attachments.test.ts 的 model fixture 固定为 api='openai-completions'，没有测 Responses 拒绝音频的分支。也没有一条测试让 listEmbeddedModels 暴露的模态与 prepareEmbeddedAttachments 接受的模态保持一致。

### 缺陷 9：智能体写共享记忆时的修订号核对形同虚设，“读取→合并→写入”会覆盖期间他人的修改

- 排查编号：`assistant-8`
- 位置：`src/features/assistant/application/sharedMemoryReflection.ts:47`；相关：`electron/main/services/assistant/memory-store.ts`、`electron/main/services/embedded-agent/service.ts`、`electron/main/services/application-runtime/operationCoordinator.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：缺陷可以复现，但原发现对位置的描述需要修正。第 47 行执行器自己的 CAS 并非完全无效：调用方提供 baselineIds 时，engine 会按读取时的修订号核对，旧修订号会被拒绝。用例 (1) 已验证这一点。
  真正的问题是策略层的组合：
  1. assistant.shared_memory.content 是一段整体替换的自由文本，写入方式是“读取 → 由 LLM 合并 → 整段写回”。
  2. 内置 Pi 的系统提示（service.ts 第 47、49 行）和外部 MCP 的说明（toolCatalog.ts 第 251 行）都引导智能体省略 baselineIds。
  3. 省略后，changeEntities 的自动模式以提交时刻的当前修订号作为期望值。
  结果是，从 Pi 读取到提交这几秒到几十秒里，外部 MCP 智能体写入的偏好，或用户在记忆面板保存的内容，都会被 Pi 基于旧版本合并出的文本静默覆盖，不报错，也没有冲突提示。
  另有一个次要窗口：即使带了 baselineIds，engine 核对完修订号之后，执行器会在第 47 行重新 read() 并使用最新的 before.revision。如果在这两步之间有写入，仍然会被覆盖。
- 修法：建议分三处改：
  1. 强制严格基线。对 assistant.shared_memory 的 set_properties，在 operationCoordinator.prepare 或 changeEntities 的 callerGrant 分支中，像 remove_items 一样要求 baselineIds，缺少时返回 BASELINE_REQUIRED，提示“先 read_application_entity 读取 singleton，再带返回的 baselineId 提交”。最好通过实体或属性声明来实现，例如 requiresReadBaseline，不要在通用代码里写实体名分支。
  2. 同步修改说明文字。service.ts 第 49 行和 toolCatalog.ts 第 251 行，改成“读取后携带 baselineIds 合并更新；遇到 CONFLICT 时重新读取、重新合并”。
  3. 执行器使用计划中的期望修订号。SharedMemoryExecutor.apply 应改用 step.expectedRevisions.assistant_memory 作为 updateSharedMemory 的 expectedRevision，没有时才回退到 before.revision。这样可以关闭 engine 核对和执行器之间的窗口。
  需要补的回归测试：在 sharedMemoryReflection.test.ts 中增加两条用例。一条在 expectedRevisions 为 undefined 时先修改修订号，断言被拒或要求基线；另一条传入过期基线，断言被拒。
- 测试缺口：src/features/assistant/application/sharedMemoryReflection.test.ts 中的 context() 固定传入当前修订号作为 expectedRevisions，只验证了正常保存、清空和关闭记忆后不写入。它没有覆盖两种情况：一是不传基线（自动模式）时发生并发写，二是读取后修订号已经变化再提交。

### 缺陷 10：助手追踪分页游标用 started_at 严格小于，同毫秒步骤会被跳过且跨页运行被拆分

- 排查编号：`camerastage-8`
- 位置：`electron/main/services/logging/agent-trace-store.ts:382`；相关：`src/features/logs/components/AssistantTracePanel.tsx`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：日志窗口「助手追踪」点“加载更多”时，AssistantTracePanel 把 queryResult.nextBeforeTimestamp 作为 beforeTimestamp 传给主进程 AgentTraceStore.query。nextBeforeTimestamp 取本页最后一行的 started_at（agent-trace-store.ts:382-386），下一页 SQL 用的是严格小于 `t.started_at < ?`（:309）。如果分页边界上有多条步骤的 started_at 在同一毫秒，排在本页之外的那几条在第二页会被过滤掉，以后任何一页都不会出现。对应运行的 steps、requestCount、completedCount/failedCount、usage、totalElapsedMs 都会永久偏小。另外，ORDER BY 只按 started_at DESC，没有 tiebreaker，同毫秒行的先后顺序本身也不确定。原发现里“跨页运行被拆分”这一半不成立：前端 mergeTraceQueryResults（AssistantTracePanel.tsx:279-299）会按 runId 合并跨页的 run，按 traceId 去重 steps，再重算汇总，所以拆分不会显示出来。真实缺陷只有同毫秒步骤被跳过。触发要求两个步骤的开始时间在同一毫秒，而且恰好落在 limit 边界上，概率低，所以严重度为 low。
- 修法：在 agent-trace-store.ts 的 query 中改用复合游标 (started_at, trace_id)：ORDER BY t.started_at DESC, t.trace_id DESC；游标条件改为 `(t.started_at < ? OR (t.started_at = ? AND t.trace_id < ?))`。agentTraceQuerySchema / AgentTraceQueryResult（src/core/assistant/trace.ts）新增 beforeTraceId / nextBeforeTraceId 字段（或者把两者编码成一个不透明 cursor），AssistantTracePanel 加载更多时一并传回。前端按 traceId 去重合并的逻辑可以保留。补一个分页测试：插入同毫秒的多行，以小 limit 逐页遍历，断言能拿到全部 traceId。测试可以用 node:sqlite 或在 Electron 测试环境里运行，否则现有 describeWithElectronSqlite 会跳过。
- 测试缺口：electron/main/services/logging/agent-trace-store.test.ts 没有任何 beforeTimestamp 或 hasMore 翻页用例，而且整组用 describeWithElectronSqlite，在普通 vitest(Node) 下直接跳过。src/features/logs 下也没有测试覆盖 mergeTraceQueryResults 与游标配合的情况。
