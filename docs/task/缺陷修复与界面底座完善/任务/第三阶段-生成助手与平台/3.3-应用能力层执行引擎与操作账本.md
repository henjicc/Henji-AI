## 任务目标

## 缺陷明细

以下条目来自 2026-10-13 排查，位置与行号以当时 `main` 为准；开始前先用行号附近的代码片段重新定位。

### 缺陷 1：计划器用计划前快照逐步求值：同一事务内对同一属性的两次 append 执行正确却被判 VERIFICATION_FAILED，并把目标永久锁成 partial

- 排查编号：`appcontrol-0`
- 位置：`src/core/application-control/execution/planner.ts:335`；相关：`electron/main/services/application-runtime/operationCoordinator.ts`、`electron/main/services/application-runtime/operationVerificationRecovery.ts`
- 严重度：高；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：change_application_entities 的同一个事务里有两个或更多 mutate_properties change，作用于同一实体的同一个列表属性（ref_list）。例如两个 change 先后 append 不同引用，或者先 remove 再 append。原因：同一 change 内重复 propertyId 会被 DUPLICATE_PROPERTY_MUTATION 拒绝，调用方只能这样拆开写。
  执行器按顺序把每一步都正确写入了。但 ApplicationPlanBuilder.prepareMutation 对每一步都用计划前的快照算期望值；finalVerificationConditions 只保留最后一条，最终期望值 = 原列表 + 最后一次操作，漏掉了前面各步的效果。提交结果因此是 failed/VERIFICATION_FAILED（recoverable）。
  主进程账本随后把这次操作记为 partial。之后对同一目标的写入都会被 RECOVERY_REQUIRED 拒绝，包括独立的 append。append/remove 类记录既不能自动核验（operationVerificationRecovery 只接受 set_properties），也不会进入人工 review（review 只处理 unknown）。
  同源问题：后一步的 set 在 lowerReplaceListMutation 里也是和计划前快照做 diff（:351），所以「set 后再 set」或「append 后再 set」这类组合，生成的 append/remove 差异本身就可能是错的，比如重复追加，或漏掉移除前一步追加的项。这已经不只是验证误报，而是执行错误。
- 修法：在 ApplicationPlanBuilder.build 里维护一份计划内的工作副本：Map<`${target.kind}\0${target.id}\0${propertyId}`, JsonValue>，并传给 prepareMutation。
  prepareMutation 读 currentValue 时，同一目标属性在工作副本里有值就用副本的值，没有才用 snapshot。用这个值做 applyMutation 和 normalizePropertyValue，算出 resultingValue 后写回工作副本。lowerReplaceListMutation 也要用这个 currentValue，这样后一步 set 产生的差异才是相对前一步结果的。key 用 normalizedTarget（snapshot.ref）。
  注意：collection remove 之后，副本里对应目标的项应失效，或保留现有的 omitGeneratedConditionsSupersededByRemoval 行为；revision 断言仍然用真实快照。
  另一种做法是在 planner 层把同一事务内同一目标同一属性的多步写入合并成一步，同时放开 DUPLICATE_PROPERTY_MUTATION 对 append/remove 的限制。
  补充测试：在 engine.test.ts 里，同一事务两步分别 append link-3、link-4，期望 status=completed 且 verificationConditions.expected=[link-1..link-4]；再加 remove 后 append、set 后 set 两个用例。
  此外建议给 operationVerificationRecovery 加一个兜底，或者让 partial 记录可以进入人工 review，避免验证误报把目标永久锁死。
- 测试缺口：engine.test.ts 的「把 ref_list 的整体 set 在计划阶段编译为最小 append/remove 差异」只测了单步骤。finalVerificationConditions 的设计只考虑了 set 型的覆盖写入（seek 0→1→2）。没有测试覆盖同一事务内多步骤对同一属性做 append、remove，或 list set 的累积写入。

### 缺陷 2：同一事务先 append 再对 ref_list 整体 set，set 被按陈旧列表降级为 append，产生重复引用（数据损坏）

- 排查编号：`appcontrol-1`
- 位置：`src/core/application-control/execution/planner.ts:358`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：ApplicationPlanBuilder.prepareMutation 对每个 mutation 步骤都重新读取实体的真实快照，没有叠加同一计划里更早步骤对同一目标、同一属性的写入。所以当写入器不支持 set 的 ref_list 遇到整体 set 时，lowerReplaceListMutation 是拿陈旧列表算 append/remove 差异的。
  fixture 里（append 不去重）的结果：步骤 1 append link-3，步骤 2 set 为 [link-1,link-2,link-3]，最终列表是 [link-1,link-2,link-3,link-3]，事务状态 failed。
  生产唯一命中的是 asset.library_refs，底层是 INSERT OR IGNORE，加上 unordered_set 比较，所以不会产生重复，只是多发一次无害的 append。但下面这个场景在生产上会真实出错：步骤 1 append lib-3，步骤 2 set 为 [lib-1]，本意是移除 lib-3。陈旧快照是 [lib-1,lib-2]，差异只编译出 remove lib-2。最终集合是 {lib-1,lib-3}，不是用户要的 {lib-1}，事务被判 VERIFICATION_FAILED，同时 lib-3 的写入已经落库。反过来也一样：先 remove 某项，再 set 一个包含该项的列表，该项不会被加回。
  同源问题：步骤 2 中 append/remove 的 expected 值（applyMutation(currentValue, ...)）也是用陈旧快照算的，属于上一条发现的同一个根因。
  现有测试缺口：engine.test.ts 里「把 ref_list 的整体 set 在计划阶段编译为最小 append/remove 差异」只测了单步 set，没有覆盖同一事务中对同一属性先 append/remove 再 set 的组合。
- 修法：在 ApplicationPlanBuilder.build 中，为每个 target+propertyId 维护一份计划内工作副本（Map key 为 kind\0id\0propertyId）。prepareMutation 计算 currentValue 时先查这个工作副本，命中就用它，没有命中才用 snapshot.properties，算完后把 resultingValue 写回工作副本。这样 :358 的 lowerReplaceListMutation 和 applyMutation 生成的 expected 都基于叠加了前面步骤结果的列表，上一条同源发现也一并修掉。
  如果中间夹着 collection 删除步骤或语义操作步骤，就清除受影响 target 的工作副本，或者对这种组合直接拒绝。
  备选方案更保守：计划阶段检测到同一事务里对同一 target+property 既有 append/remove 又有 set 时，直接抛 PROPERTY_OPERATION_CONFLICT。
  回归测试补在 engine.test.ts：一个是 append 后 set（不应产生重复），另一个是 append 后 set 排除该项，最终集合应等于 set 值，状态应为 completed。
- 测试缺口：src/core/application-control/execution/engine.test.ts 里的「把 ref_list 的整体 set 在计划阶段编译为最小 append/remove 差异」只测了单步 set，没有覆盖同一事务内对同一属性先 append/remove、后 set 的多步组合。

### 缺陷 3：VERIFICATION_FAILED 导致的 partial 记录没有任何人工或自动解除路径（非 set_properties 变更），目标被永久写锁

- 排查编号：`appcontrol-2`
- 位置：`electron/main/services/application-runtime/operationCoordinator.ts:122`；相关：`electron/main/services/application-runtime/operationVerificationRecovery.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：change_application_entities 中只要有一项 change 不是 set_properties（mutate_properties、create_items、remove_items 或混合事务），事务执行完毕且产生了 effects，提交后的结构化验证却没通过（领域归一化差异、计划器条件错误，或验证器抛错时 engine.ts:233 兜底成 verified=false），engine 就返回 VERIFICATION_FAILED，coordinator.complete() 把账本记成 state=partial。之后会出现以下情况：
  - prepare() 对任何访问同一目标、或包含/被包含于该目标的写入，一律抛 RECOVERY_REQUIRED。append 与 append 也会冲突，因为 :248 排除了 partial。
  - operationVerificationRecovery 不为非 set_properties 生成条件，所以 get_application_operation 和 dispatcher 的自动重验都是空操作。
  - review() 和 pendingReviews() 只处理 unknown 或 review 确认，应用界面没有待核对项；resolveReview 也进不去。
  - retry_application_operation_save 因为没有 persistence.recovery，抛 RECOVERY_UNAVAILABLE。
  - 账本没有过期或清理机制，所以这个目标对所有外部连接和内置助手永久不可写，用户在应用里也看不到任何提示，只能手工改数据库。
  已用单元测试复现：mutate_properties 的 partial 记录既拿不到验证证明，也不出现在 pendingReviews。
- 修法：选最小、最安全的方案：把「state=partial 且 transaction.code=VERIFICATION_FAILED 且没有 persistence」的记录纳入人工核对流程，需要改三处：
  1. operationCoordinator.review() 在 :122 的放行条件加上这类 partial，并在 :132 的 current.state 白名单里加入 'partial'。
  2. pendingReviews() 在 :141 的过滤条件加上同样的判断。
  3. resolveReview 仍然只接受 awaiting_user_confirmation/review，因为 review() 已经会把记录转成这个状态。注意 operationVerificationRecovery 在 awaiting_user_confirmation 状态下只认 recoveryVerification，转成 review 后 set_properties 会失去自动重验，所以要在转状态前先跑 reconcileVerification，或者保留原 partial 事实，例如在 confirmation 里记录 fromState。
  reviewPresentation 的文案要区分「已执行但验证未通过」和「是否执行未知」。用户选 completed 就解除；选 not_executed 时不能伪造成未执行，应该记成 rolled_back 或 completed 加用户声明，或者只允许「已核对，解除保护」这一个选项。
  可选增强：在 operationVerificationRecovery 里为 mutate_properties 的 append/remove 生成集合包含或不包含条件（若 applicationVerificationConditionSchema 支持），为 create_items 使用 transaction.resultRefs 生成 entity_exists 条件。
  补测试：在 operationStore.test.ts 增加 mutate_properties/create_items 在 VERIFICATION_FAILED 后进入 pendingReviews、经 resolveReview 解除写锁的用例。同时把 operationVerificationRecovery.test.ts 里 algorithm 用例的意图改为「必须由人工核对兜底」。
- 测试缺口：现有 partial 解除的测试只用 set_properties 输入，分别是 operationStore.test.ts:278-325 的「新连接仅在全部目标重新核实后…」「完整执行后的核实失败只重新读取…」，以及 operationVerificationRecovery.test.ts。后者还断言 create_items 返回 undefined，等于把「无证明」当作正确行为。没有任何测试检查非 set_properties 的 VERIFICATION_FAILED partial 能否通过 pendingReviews、review 或 resolveReview 解除，也没有测试覆盖这种记录对后续写入的永久阻断。

### 缺陷 4：change_application_entities 幂等键由 requestId+revisions 派生，同一 operationId 在 not_executed 后合法重试时撞键，引擎返回不可恢复的 INVALID_PLAN

- 排查编号：`appcontrol-3`
- 位置：`src/features/application-control/capabilities/applicationReflectionAdapter.ts:487`；相关：`src/core/application-control/execution/planStore.ts`、`src/core/application-control/execution/engine.ts`、`src/features/application-control/localApplicationHost.ts`、`electron/main/services/application-runtime/operationCoordinator.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：调用方（外部 MCP 或内置宿主）用 operationId=X 调用 change_application_entities。领域执行器在第一步就抛了临时错误，比如宿主未就绪或领域内部异常。引擎回滚为零步失败，返回 EXECUTION_FAILED、recoverable:true、partial 全空，并在 engine.ts:297 把幂等键 `change:<applicationInvocationId(caller,X)>:0:<revisions>` 和这次的 planRef 一起存下。协调器把这次记为 not_executed，允许同 ID 重试。
  调用方按契约用同一个 operationId 和同一份输入（相同 baselineIds）重试。目标没被改动，revision 不变，所以适配器算出的幂等键和上次逐字相同；但重试会新建计划，planRef 不同。planStore.getIdempotent 因此抛 IDEMPOTENCY_KEY_REUSED，引擎返回 `INVALID_PLAN 幂等键已用于其他计划。 recoverable:false`，执行器根本没有被调用：
  - 真正的失败原因被盖掉，并且被误标成不可恢复。
  - 这次的 partial 仍为空，协调器又记为 not_executed，同一 operationId 的后续重试会一直撞键。只有目标 revision 被其他修改推进，或幂等缓存被 maxIdempotencyResults 淘汰，才会解除。
  单元测试已稳定复现。
- 修法：首选：在适配器 applicationReflectionAdapter.ts:487 的 execute 里，把本次 plan.planRef 加进 idempotencyKey，例如 `change:${invocation}:${attempt}:${plan.planRef}`。这样每次新计划都用新键。同一次提交的防重放本来就由 planRef 只能 commit 一次（stored.committed）来保证；跨重试的业务幂等由协调器账本保证，它会对 completed、partial 这类状态直接返回 prior。
  备选：在 engine.commitLocked 的 catch 分支（engine.ts:297）里，结果为零步失败（`!executionStarted`，或 partial.completedStepIndexes 为空且没有 persistence）时不调用 saveIdempotent；或者让 planStore.getIdempotent 在旧结果是零步失败时允许被新 planRef 覆盖。
  不管选哪种，都要补两条回归测试：
  - 适配器层：同一 requestId 先零步失败、再重试，第二次应真正执行成功。
  - 引擎层：零步失败后，用同一幂等键提交新计划，不应返回 INVALID_PLAN。
  同源点（建议一起核对）：
  - undoEntities 的键是 `undo:${requestId}`，同样由 operationId 派生，也可能存在同类撞键。
  - 没有 requestId 时会落到常量 'renderer'，不同调用只要 revisions 相同就会共享同一个键。
- 测试缺口：applicationReflectionAdapter.test.ts 把 engine.plan 和 engine.commit 整个 mock 掉了，没有覆盖真实的幂等存储。engine.test.ts 的「提交具备幂等…」只测同一个 planRef 重放，没有测「零步失败后用同一幂等键提交新计划」。operationCoordinator 的测试也没有验证 not_executed 之后用同一 operationId 重试时，渲染层确实会重新执行。

### 缺陷 5：宿主桥 pending 槽位（上限 8）被等待用户确认的写操作长期占用，可让所有调用方（含内置助手的只读请求）得到“应用正忙”

- 排查编号：`appcontrol-4`
- 位置：`electron/main/services/application-runtime/applicationHostBridge.ts:180`；相关：`src/core/application-control/userConfirmation.ts`、`electron/main/services/application-runtime/applicationToolDispatcher.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：ApplicationHostBridge 的 pending 表同时承担两种职责：(a) 仍有调用方在等的在途请求；(b) 等待者已释放、但为 revoke/disconnect/迟到回执而保留关联的已派发写操作（committed）。并发上限 `pending.size >= 8`（:180）把 (b) 也算进去且不分调用方。当任意连接（外部 MCP 或内置助手）提交 8 个目标互不重叠、需要用户确认的写操作（付费生成审批 ask、或渲染端 withApplicationConfirmation 的普通确认）时，每个操作收到 awaiting_user_confirmation 进度后工具调用立即返回，但 pending 条目留存直到最终回执（最长 5 分钟确认超时，确认后执行期间也继续留存）。此期间所有调用方——包括内置助手的 read_application_entity / get_current_application_context 等只读请求、以及用于核对的 reconcileVerification、付费生成的 preparation 读取——都会立即得到“应用正忙，请稍后重试。”，且该错误不是 ApplicationHostNotReadyError，读路径不会重试。单个外部连接即可阻断其他连接和内置助手的全部应用读写。
- 修法：在 applicationHostBridge.ts 中把并发配额只施加于“仍有等待者”的在途请求：给 Pending 增加 `waiting: boolean`（set 时为 true），在 complete 进度分支 cleanup 后、releaseCaller 对 committed 条目、dispatch 内 cancel 对 options.operation 条目这三处置为 false（条目仍保留以供 revoke/cancelPending/迟到回执入账）；:180 改为 `[...this.pending.values()].filter(p => p.waiting).length >= 8`。若需防止单一连接无限堆积 committed 保留条目，另加按 callerId 的保留上限（且仅对新写入生效，只读请求不受他人 committed 条目影响），拒绝时返回明确未执行的可恢复错误。补测试：8 个 committed 条目进入 awaiting_user_confirmation 后，另一调用方的只读请求仍被派发；revoke/disconnect 仍能清理这些保留条目。

### 缺陷 6：每次读取都向 application_observations 插入基线行，无任何清理，数据库无界增长

- 排查编号：`appcontrol-5`
- 位置：`electron/main/services/application-runtime/operationStore.ts:142`；相关：`electron/main/services/application-runtime/operationCoordinator.ts`、`electron/main/services/application-runtime/applicationToolDispatcher.ts`
- 严重度：低；核实方式：调用链追踪确认（未写复现测试）
- 现象：外部 MCP 连接或内置助手每做一次成功的只读调用（read_application_entity、list_application_entities、get_*_task 等，返回 refs/ref/taskRef 加 revisions），operationStore.baseline 都会往 application_observations 插一行新 UUID 记录（含 refs 与 revisions JSON）。对同一目标重复读取也会每次新增一行。表里没有任何删除路径。渲染层重载或应用重启后 rendererEpoch 会换新，旧代次的基线在 prepare 时一律报 BASELINE_EXPIRED，成为永久死数据。长期使用下 SQLite 文件、VACUUM INTO 迁移备份和 media-recycle 的引用扫描（这张表在 MEDIA_REFERENCE_TABLES 里）都会线性变大。不影响正确性，只是资源泄漏。
- 修法：1) 启动时清理：在 ApplicationOperationStore.recoverInterrupted() 末尾（或新加一个 pruneObservations()，由 coordinator 构造时调用）执行 `DELETE FROM application_observations`。重启后旧 rendererEpoch 必然失效，全部清掉是安全的。
  2) 会话内限量：baseline() 插入后按 caller_id 或全表保留最近 N 行（例如 `DELETE FROM application_observations WHERE created_at < ?` 加 TTL，或按 rowid 只留最新 N 行）。也可以在宿主注册新 rendererEpoch 时，删除 record_json 中 rendererEpoch 不等于新值的行。若用后一种，建议给表加 renderer_epoch 列，需要改 schema 并按 persistence.md 走迁移账本；开发期不要求兼容旧数据。
  3) 注意 media-recycle 的 schema.ts:78-82 在 MEDIA_REFERENCE_TABLES 每张表上都建了 DELETE/UPDATE 触发器。批量删除会进入回收 outbox，要确认这些触发器对大批量删除的开销可以接受，必要时分批删。
  4) 补一条原生测试（放在 operationStore.test.ts，走 Electron 原生运行器）：插入多条基线，重启恢复或超过上限后，断言旧行已删除，而当前 epoch 的有效基线仍能被 readBaseline 读到。
- 测试缺口：operationStore.test.ts 和 operationCoordinatorBaseline.test.ts 只验证 baseline 能写入和读回、过期 epoch 会被拒绝，没有任何用例断言旧基线会被回收、表行数有上限，或重启后会清理。

### 缺陷 7：执行引擎 undoRecords 与 creativeIntent undo 闭包表无界增长（只在撤销时删除）

- 排查编号：`appcontrol-6`
- 位置：`src/core/application-control/execution/engine.ts:449`；相关：`src/features/application-control/creativeIntentMutationExecutors.ts`、`src/features/application-control/capabilities/applicationReflectionAdapter.ts`、`src/core/application-control/execution/planStore.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：getApplicationControlExecutionEngine() 返回的执行引擎是进程级单例。每提交一个所有步骤都支持撤销的计划，engine.undoRecords 就新增一条 {steps, results}，results 里带着领域 undoToken。同时还有两处同步增长：applicationReflectionAdapter 的模块级 publicUndos 新增 {callerId, revisions}；对创意原稿（creative intent）的修改，creativeIntentMutationExecutors 的模块级 undos/undoPrivateHeads 新增一个闭包，闭包持有 host.checkpoint() 的恢复函数，连带保留修改前的文档快照。这些表只在对应 undoRef 被撤销（或原稿解释正文被擦除）时才删除，而助手绝大多数提交都不会被撤销，所以长时间会话里几张表都会线性增长。
  单元复现：同一 engine 连续提交 400 个可撤销计划后，undoRecords.size 为 400。planStore 对 plan 和幂等结果分别有 128/256 的上限，undoRecords 没有。
  这不是功能错误，影响是长会话下的内存增长，其中创意原稿快照闭包占用最大。
- 修法：1. 给 ApplicationControlExecutionEngine 加一个依赖项，例如 `maxUndoRecords`，默认值与 maxIdempotencyResults 一致（256）。在 createUndoRef 里 set 之后按插入顺序淘汰最旧的记录，复用 ApplicationExecutionPlanStore.trim 的做法；也可以把 undoRecords 并入 planStore 统一裁剪。
  2. 淘汰时需要通知领域释放 undoToken 背后的资源。建议在 ApplicationMutationExecutor、Collection、Operation 的 executor 接口上加一个可选的 `releaseUndo?(token)`，淘汰记录时对 results 中每个 undoToken 调用它。CreativeIntentMutationExecutor 的实现是删除 undos 和 undoPrivateHeads 里对应的 token。
  3. applicationReflectionAdapter 的 publicUndos 改为同样有上限的 LRU，或在引擎淘汰 undoRef 时回调清理。publicUndos 里查不到记录本来就按“撤销记录已失效”处理，所以淘汰后的行为与现有失效语义一致。
  4. 补一个单元测试：连续提交超过上限的次数后，undoRecords.size 不超过上限；最旧的 undoRef 撤销时返回失效错误，最新的仍可撤销。
- 测试缺口：engine.test.ts 的「提交具备幂等、结构化验证和可逆撤销」和 engineUndoRemovedTarget.test.ts 都只测了单次提交加撤销。没有测试验证撤销记录（undoRecords、publicUndos、creative intent 的 undos）在大量未撤销提交下有上限或会淘汰。
