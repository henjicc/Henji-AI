### 缺陷 1：SDK normalizeLocalSource 把 POSIX file:/// URL 还原成相对路径，与宿主 decodeFileUrlPath 契约不一致

- 排查编号：`sdk-1`
- 位置：`packages/ai-sdk/src/upload/media-fields.ts:122`；相关：`electron/main/services/ai-runtime/sdk-runtime.ts`、`electron/main/services/ai-runtime/native-file-upload.ts`、`electron/main/services/image/source.ts`、`packages/ai-sdk/tests/media-fields.test.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：在 macOS/Linux 上，媒体引用为 `file:///Users/demo/a.png` 或 `file://localhost/Users/demo/a.png` 时，SDK 的 normalizeLocalSource 返回相对路径 `Users/demo/a.png`。经过宿主时有两种结果：electronMediaReader.read 读取相对 cwd 的路径，报 ENOENT；native 直传路径 scopedUploadFile 判为不在授权范围内，报 media_scope_denied。Windows 的 `file:///C:/...` 不受影响。现有测试 packages/ai-sdk/tests/media-fields.test.ts:124-126 只覆盖了 Windows 形态。asset://localhost、tauri://localhost 以及 http(s)://asset.localhost 这几个前缀有同样的切法：路径没有 URL 编码时同样会丢掉开头的 '/'（`%2F` 编码形态没问题）。
- 修法：修复位置在 packages/ai-sdk/src/upload/media-fields.ts。file 系前缀单独处理：把 'file://localhost/' 改成 'file://localhost'，删掉 'file:///'，只保留 'file://'，也就是只剥掉 scheme 和 host，路径开头的 '/' 留着。解码之后再交给 stripWindowsDrivePrefix，由它只去掉 `/C:` 这种盘符前多出来的斜杠。也可以改用 `new URL(source).pathname` 解码，再按盘符去掉开头的斜杠。asset/tauri/asset.localhost 这几个前缀也按同样原则处理：剥掉 host 后，如果解码结果不是绝对路径也不是盘符路径，就补回 '/'。在 tests/media-fields.test.ts 里补上 POSIX 用例：`file:///Users/demo/a.png` 和 `file://localhost/Users/demo/a.png` 都应得到 `/Users/demo/a.png`，同时保留 Windows 用例。改动涉及公共 SDK，按规则需要先接入痕迹AI并交给用户测试，不能自行发版。宿主 electron/main/services/image/source.ts 与 SDK 各有一份 normalizeLocalSource/decodeFileUrlPath，后续可以考虑收敛成一份，但不在这次最小修复的必要范围内。
- 测试缺口：packages/ai-sdk/tests/media-fields.test.ts 的 normalizeLocalSource 用例只断言了 `file:///C:/demo/a.png` 和 `henji-media://local/C:/demo/a.png`，没有 POSIX 绝对路径的 file:/// 或 file://localhost/ 用例。

### 缺陷 2：readJsonResponse 对非 JSON 错误响应（网关 5xx HTML/文本）丢掉 HTTP 状态，错误归类与重试判断失真

- 排查编号：`sdk-2`
- 位置：`packages/ai-sdk/src/providers/helpers.ts:18`；相关：`packages/ai-sdk/src/runtime/retry.ts`、`packages/ai-sdk/src/runtime/error-classify.ts`、`packages/ai-sdk/src/providers/providerAccessErrors.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：任一媒体供应商（Fal/KIE/PPIO/ModelScope/APIMart/Grsai/Bailian/Volcengine/SiliconFlow）的提交或结果请求遇到 CDN/网关返回 5xx 或 429，且 body 是 HTML/纯文本时，readJsonResponse 会先调 response.json() 并在这一步失败，抛出 AiRuntimeError('invalid_json', "Unexpected token '<'...")。结果有三点：
  - 用户和日志都看不到 HTTP 状态码，无法区分“网关故障”和“2xx 但返回体损坏”；
  - KIE/APIMart 返回 402/403、SiliconFlow 返回 402/403 且 body 不是 JSON 时，assertProviderAccess 被跳过，余额不足/无权限得不到可行动的提示（控制台链接、retryable:false）；
  - SiliconFlow TTS 的 !ok 分支同理。
  原发现中“503 被判为不可重试”和“normalizeProviderError 归为 unknown”这两条不成立，或不是本函数特有的问题：提交路径本来就不自动重试 HTTP 错误，轮询路径会对 invalid_json 重试，normalizeProviderError 只服务 LLM 链路。
- 修法：在 helpers.ts 的 readJsonResponse 里先读 `const text = await response.text()`，然后尝试 JSON.parse：
  - 解析失败且 !response.ok 时：先调 assertProviderAccess(provider, {}, response.status)，让按状态码识别的 402/403 生效；再抛 AiRuntimeError('provider_http_error', `${provider} HTTP ${status}: ${text 截断约 500 字}`, { status })。
  - 解析失败且 2xx 时：抛 invalid_json，details 带上 status。
  - 解析成功时保持现有流程，并顺带把 `{ status: response.status }` 放进 provider_http_error 的 details，方便下游分类读取。
  请在 packages/ai-sdk/tests/providers/providerAccessErrors.test.ts（或 helpers 测试）补两个用例：HTML 503 → provider_http_error 且信息包含 503；KIE 纯文本 402 → provider_insufficient_balance。改的是 SDK 源码，按规则需要接入痕迹AI并交给用户测试，不能自行发版。
- 测试缺口：packages/ai-sdk/tests/providers/providerAccessErrors.test.ts 只用 JSON body 测试 readJsonResponse，没有覆盖非 2xx 且 body 为 HTML/纯文本的情况；同类的 cloud-file-asr.test.ts 已经覆盖了纯文本错误体，但 readJsonResponse 这条路径没有对应测试。

### 缺陷 3：KIE / APIMart 上传不接收取消信号，用户取消生成后大文件仍继续上传

- 排查编号：`sdk-3`
- 位置：`packages/ai-sdk/src/upload/kie-upload.ts:20`；相关：`packages/ai-sdk/src/upload/apimart-upload.ts`、`packages/ai-sdk/src/upload/provider-preprocessors/kie.ts`、`packages/ai-sdk/src/upload/provider-preprocessors/ppio.ts`、`packages/ai-sdk/src/upload/provider-preprocessors/apimart.ts`、`packages/ai-sdk/src/upload/fal-transport.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：本地视频或图片要经 KIE 托管上传时会触发：可能是 KIE 模型（provider-preprocessors/kie.ts），也可能是 resolvePpioMediaRewriteMode 判定需要公网 URL 的 PPIO 字段（ppio.ts → uploadPublicUrl → uploadToKie）；APIMart 则是本地图片上传。用户在上传过程中取消生成后，generation/core.ts 的 controller.abort() 到不了 transport.fetch，multipart 请求会一直传完；如果遇到可安全重放的预连接失败，fetchProvider 还会按 1s/3s/8s 继续重试，因为 waitForRetry 也拿不到 signal。直到 preprocess 返回、adapter.execute 发现 signal 已中止，生成才失败。结果是带宽和第三方存储被白白占用，取消在界面上的反馈也被推迟。另外还有一个问题：即使给 uploadToKie 加上 signal，kie.ts 的 `catch {}` 会吞掉 AbortError 并退回 data URI；ppio.ts 的 catch 也会把中止改包成 public_media_url_required。两处 catch 都必须先识别中止。原发现里提到的 ModelScope 在 upload/provider-preprocessors 下没有专用策略，没有找到它走 KIE 上传的证据，不应算进影响范围。
- 修法：1) 给 uploadToKie(apiKey, prepared, transport, signal?: AbortSignal) 和 uploadToApiMart(..., signal?) 加 signal 参数，并写进 fetchProvider 的 init（`{ method, headers, body, signal }`）；可以参照 fal-transport.ts 的 createDeadlineSignal，同时补上上传超时。2) 三个策略 kie.ts、ppio.ts（uploadPublicUrl）、apimart.ts 都从 rewrite 入参解构 signal 并往下传。3) kie.ts 的 catch 和 ppio.ts 的 catch 里，先判断 `signal?.aborted` 或 AbortError，命中时直接 rethrow，或统一抛 AiRuntimeError('cancelled')，不能退回 data URI，也不能改包成 public_media_url_required。apimart.ts 记失败日志时同样要区分取消和失败。4) 在 packages/ai-sdk 的 upload 测试里补回归用例：mock 一个只在 init.signal 中止时才 reject 的 transport，断言三个策略在 abort 后都会尽快以取消状态 reject，且 fetch 收到的就是同一个 signal。
- 测试缺口：packages/ai-sdk 的 upload 与 provider-preprocessors 测试只覆盖 Fal 上传的 signal/deadline，KIE（kie.ts、ppio.ts）和 APIMart 上传都没有取消或中止相关用例。

### 缺陷 4：KIE 预处理静默吞掉托管上传失败并退回 data URI，根因不进日志，用户只看到后续无关的供应商报错

- 排查编号：`sdk-4`
- 位置：`packages/ai-sdk/src/upload/provider-preprocessors/kie.ts:11`；相关：`packages/ai-sdk/src/upload/preprocess.ts`、`packages/ai-sdk/src/upload/kie-upload.ts`、`packages/ai-sdk/docs/model-adaptation/供应商/KIE.md`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：KIE（ModelScope 通过 preprocess.ts 的 `modelscope: kie` 共用同一策略）请求里带本地或 data: 媒体，已配置 KIE Key，但 kieai.redpandaai.co/api/file-stream-upload 失败，比如网络错误、HTTP 4xx/5xx、配额不足，或响应里没有 fileUrl/downloadUrl。这时 kie.ts 的空 catch 把 AiRuntimeError('upload_failed', ...) 吞掉，不留任何日志，然后把整个文件编码成 data URI 写进 input.image_urls/video 等字段，再提交给 createTask。日志里只剩 preprocess-core 的 unresolved_local_media 警告，它把原因说成“字段名可能未命中 hint”，属于误导。用户最终看到的是 createTask 对参数或请求体大小的拒绝（KIE.md 里媒体字段要求公网 URL），真实的上传失败原因（HTTP 状态、响应体）追溯不到。另外，未配置 KIE Key 时也会静默退回 data URI，不会给出 missing_api_key 提示。“KIE 端点拒绝 data URI”这一点依据的是官方文档，没有联网实测。
- 修法：修改 packages/ai-sdk/src/upload/provider-preprocessors/kie.ts，与 fal.ts/apimart.ts 对齐：上传前记 runtime.logger.info（event ai_runtime.upload.kie_started，带 requestId、providerId、context{route,mimeType,bytes}），成功记 kie_completed，失败记 runtime.logger.error（event ai_runtime.upload.kie_failed，带 error）后 rethrow，不再退回 data URI。没有 KIE Key 时抛 AiRuntimeError('missing_api_key', 'KIE 本地文件必须先上传，请先在设置中配置 KIE API Key。')。ModelScope 复用的是 KIE 策略，providerId 应改用 rewrite 入参里的 providerId，或者给 ModelScope 单独核实它是否接受 data URI 再决定是否拆分策略。注意不要依赖 MediaKind 默认分支吞错。补测试：在 packages/ai-sdk/tests/upload.test.ts 加 KIE 上传失败时 reject upload_failed 并记 kie_failed 日志、KIE 无 Key 时 reject missing_api_key 两个用例。这属于 SDK 改动，按规则先接入痕迹AI、交用户测试，用户明确要求后再发版。
- 测试缺口：packages/ai-sdk/tests/upload.test.ts 只覆盖 APIMart 预处理（成功、缺 Key、视频要求公网 URL），没有覆盖 KIE 和 ModelScope 预处理的上传失败分支和缺 Key 分支。packages/ai-sdk/tests/upload-providers.test.ts 只测了 uploadToKie 的成功路径。

### 缺陷 5：火山音色克隆 request() 对非 JSON 响应直接 response.json()，HTML 5xx 变成裸 SyntaxError 逃出 SDK 错误协议

- 排查编号：`sdk-5`
- 位置：`packages/ai-sdk/src/providers/volcengine-voice-clone.ts:39`；相关：`packages/ai-sdk/src/providers/helpers.ts`、`packages/ai-sdk/src/providers/volcengine-speech.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：volcengine-voice-clone.ts 中的 request() 在第 39 行先调用 `await response.json()`，之后才判断 response.ok。触发条件是 openspeech.bytedance.com 的网关或 WAF 返回非 JSON 正文（HTML 或纯文本的 502/503/504、429 页面等），涉及三个调用点：
  - `/api/v3/tts/voice_clone`：新建或重训音色的提交
  - executeVoiceClone 里对已有音色的 `/api/v3/tts/get_voice` 预检
  - pollVoiceClone 的 get_voice 轮询
  前两个调用点的后果：抛出原生 SyntaxError，不是 AiRuntimeError，没有 code，HTTP 状态也丢了。`!response.ok` 分支根本走不到，宿主只能看到 'Unexpected token <'，无法按错误码分类，也无法判断能否重试。对 voice_clone 提交而言，5xx 意味着提交结果不确定，但当前代码既不返回可续查的 pending 身份，也不给结构化错误。
  第三个调用点（轮询）会被 pollUntilResult 当作查询失败重试 20 次，最后变成 provider_task_unreachable，消息里同样没有 HTTP 状态。严重度低：只在网关异常时出现，不会导致误训或重复扣费。
- 修法：只改 packages/ai-sdk/src/providers/volcengine-voice-clone.ts 的 request()：
  1. 先用 `await response.text()` 读出正文，再 try JSON.parse。解析失败时：如果 `!response.ok`，抛 `AiRuntimeError('provider_http_error', \`Volcengine Speech HTTP ${response.status}\`, { status: response.status })`，消息里不要拼接 HTML 正文，最多截一小段做诊断；如果 ok 但解析失败，抛 `AiRuntimeError('invalid_response' 或 'invalid_json', …)`。
  2. 解析成功后保持现有逻辑：非对象抛 invalid_response；`!ok` 或 code≠0 抛 provider_task_failed 并带上 status。
  3. 也可以参照 helpers.readJsonResponse，在 response.json() 上加 .catch，转成 invalid_json 并带上 status。注意 readJsonResponse 本身会先 assertProviderAccess，这里不一定适用。
  可选：如果希望 voice_clone 提交遇到 502/503/504 时也走 executeVoiceClone 现有的“提交不确定，保留可查询身份”分支，要在 catch 里额外识别这类 HTTP 状态。这属于语义扩展，需要单独确认。
  在 packages/ai-sdk/tests/volcengine-voice-clone.test.ts 补用例：用 `new Response('<html>502</html>', {status:502})` 测 execute 新建和已有音色预检两条路径，断言结果是 AiRuntimeError、code 符合预期、消息里有 502。
- 测试缺口：packages/ai-sdk/tests/volcengine-voice-clone.test.ts 的 'rejects malformed or failed responses' 只喂 JSON 正文（status 200），而且只断言 rejects.toThrow()，没有检查错误类型或 code。所以就算加了非 JSON 或 5xx 的输入，这个用例也会照样通过。目前没有任何用例覆盖 HTML 5xx。

### 缺陷 6：KIE 续查把 401/404 等非 200 业务码当作“查询抖动”重试 20 次，鉴权失效要等约一分钟才报错

- 排查编号：`sdk-6`
- 位置：`packages/ai-sdk/src/providers/kie.ts:77`；相关：`packages/ai-sdk/src/protocols/polling.ts`、`packages/ai-sdk/src/providers/providerAccessErrors.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：KIE 任务提交成功并进入续查（recordInfo）阶段后，如果 Key 被吊销或更换、taskId 不存在或已被清理，KIE 会返回 body.code 为 401/403/404 等非 200 的业务码（HTTP 状态是 200 还是 401 都一样）。kie.pollTask 把这类响应统一当作 POLL_QUERY_FAILED，HTTP 非 2xx 则走 provider_http_error，两者都被 pollUntilResult 当作“查询抖动”处理，以默认 3s 间隔连续重试 20 次（约 60 秒）后才抛 provider_task_unreachable。HTTP 200 业务码这条路径上，错误信息固定是 "provider reported a non-success status"，KIE 返回的 code/msg 全部丢失。鉴权类错误不会被识别为 authentication，用户要等一分钟才看到一条无法据此行动的报错。只有 402 能被 assertProviderAccess 立即识别。
- 修法：只改 packages/ai-sdk/src/providers/kie.ts 的 pollTask（另外也检查 sendCreateTask 是否需要同样处理）：
  (a) 对 code 401/403（以及 HTTP 401/403）直接抛不可重试的 AiRuntimeError，带 { retryable:false, category:'authentication', providerCode, providerMessage }，让 shouldRetry 经 details.retryable 立即终止。也可以在 providerAccessErrors.assertProviderAccess 的 KIE 分支里按 KIE 官方错误契约补上 401/403 的识别，避免猜测。
  (b) 其余非 200 业务码不要再返回裸 POLL_QUERY_FAILED，改为抛 AiRuntimeError('provider_http_error', `KIE recordInfo code=${code}: ${msg}`)（默认在 poll-query 模式下可重试）。这样 pollUntilResult 会把它记进 lastFailure，最终的 provider_task_unreachable 信息里就带有供应商原因。404/“任务不存在”是否该立即终止，需先核对 KIE 官方文档再定。
  需补测试：packages/ai-sdk/tests 下新增 KIE 续查用例，覆盖 401 立即失败，以及 404/其他码的最终错误包含 msg。
- 测试缺口：packages/ai-sdk/tests/polling.test.ts 只测了通用的 pollUntilResult（连续失败上限、计数重置），没有任何测试驱动 kie.continuePolling 并让 recordInfo 返回非 200 业务码。provider-fetch.test.ts 只覆盖 recordInfo 的取消和网络重试。KIE 续查的业务码分类（401/403/404 和错误信息透传）没有测试覆盖。
