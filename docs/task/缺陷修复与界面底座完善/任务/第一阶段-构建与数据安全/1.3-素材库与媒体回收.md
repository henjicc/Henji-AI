# 1.3 素材库与媒体回收

## 任务状态

- 状态：待开始
- 所属阶段：第一阶段-构建与数据安全
- 前置任务：无
- 关联任务：1.2（项目回收站与移除）
- 是否可以并行：可以

## 任务目标

项目被移入回收站或移出列表后，素材库仍能正常分页浏览、残留素材可见可删；媒体回收不会因一条残留记录整体失败；删除素材的助手能力与批量删除如实报告成功。

## 当前情况

- 素材库主进程实现在 `electron/main/services/asset-library/index.ts`；位置编解码在 `electron/main/services/db-locations.ts` 与 `src/core/storage/locationCodec.ts`，项目被删后 `henji://project/<id>/…` 无法解码时原样返回。
- 媒体回收在 `electron/main/services/media-recycle/`（providers、runtime、lifecycle），启动时在窗口创建前同步扫描。
- 渲染层素材服务在 `src/features/assets/application/assetApplicationService.ts`。
- 可复用：`index.scale.test.ts` 的内存 SQLite 夹具（注意它 mock 了 `allowMediaRoot`，需要新增不 mock 的用例）、`media-recycle/persistence.native.test.ts`。

## 实施方案

读取侧防御优先：解码失败的素材行标记为缺失而不是让整页失败；回收扫描把无法解码的引用视为“保留”而不是抛错；再在项目移除的三条路径上同步处理素材表（具体策略见重要记录 006，待确认）。

### 缺陷 1：项目移入回收站/移出列表后，残留的 henji://project/… 素材行让整页素材库查询抛错

- 排查编号：`assets-0`
- 位置：`electron/main/services/asset-library/index.ts:355`；相关：`electron/main/services/db-locations.ts`、`src/core/storage/locationCodec.ts`、`electron/main/services/documents/projects.ts`、`electron/main/services/documents/index-store.ts`、`electron/main/protocol.ts`
- 严重度：高；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：用户把某个项目文件夹里的文件收录为素材，项目可以在作品目录内，也可以是外部项目。createAsset 用 deepestRoot 优先匹配项目根，所以 file_path 存成 henji://project/<id>/…。之后只要项目行从作品索引里被删掉，素材库就会出问题。会删项目行的路径有三条：ProjectService.trash（projects.ts:182）、forgetExternal 移除外部项目（projects.ts:259）、索引扫描发现项目已不在作品目录或外部位置范围内（index-scanner.ts:217）。databaseLocations 每次 use 都重新调用 listLocationProjects，所以该项目 ID 从此解码不了，decodePath 原样返回 'henji://project/<id>/…'。queryAssets 的第 355 行对这个值调用 allowMediaRoot(path.dirname(file_path))，assertValidMediaPath 抛出 MediaProtocolError('Media path must be absolute')。凡是包含这一行的分页（按集合、类型、标签、关键词过滤也一样）都整页失败，同页的正常素材也看不到，用户在界面上也删不掉这条残留行。getAsset、inspectAsset 遇到这一行同样拿到非绝对路径，后续读文件或检查会失败。单纯项目文件夹缺失（scanner 只标记 missing）不会触发，因为 listLocationProjects 仍包含缺失的项目。
- 修法：分两层修：
  1. 读取侧防御（必做）。在 decodeAssetRows 里识别解码失败：可以让 decodePath 返回带 unresolved 标记的结果，也可以在解码后用 path.isAbsolute 校验。对这类行跳过 allowMediaRoot，把 file_path 保留为原存储串或置空，inspection_status 按 missing 映射给前端，displayUrl 设为空或占位，保证这一行在列表里可见、可删除、可重新定位（relocateAsset）。queryAssets 第 355-356 行在调用 allowMediaRoot 之前，要先确认路径是绝对路径。inspectAsset 和 getAssetFilePath 遇到未解析的路径时，应直接标记为 missing，不去读文件。
  2. 源头处理（建议）。在 projects.trash、forgetExternal、index-scanner 移除项目时，同步把 assets 表里以 henji://project/<id>/ 开头的行改成 missing。也可以按产品语义删除这些行，或者把存储串改写为最后已知的绝对路径，避免留下无法解码的存储串。修复后加一个测试：项目上下文移除后调用 queryAssets，不抛错，正常素材照常返回，残留行显示为 missing。
- 测试缺口：electron/main/services/asset-library/index.scale.test.ts 把 db-locations 替换成 identityDatabaseLocations，同时 mock 掉 allowMediaRoot，测试数据也只有绝对路径，所以「存储串解码不了（unknown_project）时 queryAssets 的行为」没有测试覆盖。projects.trash 和 forgetExternal 的测试也都没检查 assets 表里的引用怎么处理。

### 缺陷 2：同一残留 henji://project 素材行使每次媒体回收扫描整体失败，候选永久保留

- 排查编号：`assets-1`
- 位置：`electron/main/services/media-recycle/providers.ts:52`；相关：`electron/main/services/media-recycle/runtime.ts`、`electron/main/services/media-recycle/collector.ts`、`electron/main/services/db-locations.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：用户把项目文件夹里的文件导入素材库后，assets.file_path 存成 'henji://project/<P>/…'。之后项目 P 因移到回收站（ProjectService.trash）、在列表里移除外部项目（forgetExternal）或索引扫描删掉不在范围内的记录而被移出 document_index_projects，素材行却还在。此后每次启动或退出时 runMediaRecycle 运行到 'assets' provider，collectSqlReferences → recordReferences → decodeReferenceValues 碰到 unknown_project 就抛出 'Unresolved stored media locations'。collectUnreferencedMedia 把整次扫描记为 failed（retained 里是 provider:assets），media_recycle_candidates 里的所有候选都不会被处理。generated/uploads/thumbnails/EditStates 里已经无人引用的文件永远不会删除，候选表只增不减，而且是永久性的：只要那条素材行还在，每次扫描都失败。同一根因也覆盖其他已登记的表：history.params/result_paths、presets、settings、各类任务 JSON 里只要有指向已移除项目的 henji://project 值，都会导致同样的整体失败。候选行自身的载荷（source='assets'/'history'）如果含这类值，runtime.ts 的 candidates() 迭代也会抛错。
- 修法：在回收侧把 'unknown_project' 视为“已解析的外部引用”，不让它中止扫描，同时保持 fail-closed 语义。理由：henji://project/<id>/ 只会编码项目根目录内的路径，而 managedMediaRoots（用户目录 generated/uploads、程序目录 thumbnails/EditStates）不在任何项目根目录下，所以这类引用不可能保护托管文件，跳过它不会误删。
  具体做法：在 providers.ts 的 decodeReferenceValues 中只对 reason 为 'invalid' 或 'no_container' 的项抛错；'unknown_project' 的项不计入引用、不抛错，并按 表/行 聚合后打一条 warn 日志（如 media_recycle.references.unknown_project，带 source 与 projectId，便于定位）。为保险起见，可额外校验：若某个已登记项目根目录与 managedMediaRoots 重叠（overlapsManagedMediaRoot），仍然 fail-closed。
  可选的根因侧补充：removeProject 或 trash 时把相关 assets 行解码成绝对路径后改写（或标记为缺失），避免残留无法解析的写法。注意 sweepProjects 对缺失的项目只标 missing、不移除，不受影响。
  补测试：在 collector/providers 层加一个用例，assets 行指向已移除项目时，无关的无人引用候选仍能被删除；同时保留现有的 'invalid' 值仍使扫描失败的断言。
- 测试缺口：electron/main/services/media-recycle/collector.test.ts 只测了 provider 抛错/超时会让扫描失败（这是期望行为），没有测试持久化记录里含 unknown_project 写法时 providers.ts 的 recordReferences/decodeReferenceValues 怎么处理。也没有任何测试覆盖“项目移出索引后，素材行残留 henji://project 引用”这条跨模块场景（projects.trash/forgetExternal 与 media-recycle 之间）。

### 缺陷 3：assetApplicationService.delete 删除成功后回读验证必然抛错：批量删除全部记为失败、助手 delete_asset 永远报错

- 排查编号：`assets-2`
- 位置：`src/features/assets/application/assetApplicationService.ts:114`；相关：`electron/main/services/asset-library/index.ts`、`src/features/assets/application/assetBatchOperations.ts`、`src/features/assets/application/registerAssetCapabilityHandlers.ts`、`src/features/assets/AssetLibrarySurface.tsx`、`electron/preload/index.ts`
- 严重度：高；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：素材库批量模式下勾选 N 个素材后点删除，调用路径是 AssetLibrarySurface:413 → deleteAssetsBatch → assetApplicationService.delete。助手调用 delete_asset 走的也是同一个 delete()。
  delete() 中主进程的 deleteAsset 会成功，数据库行确实已删除。随后 delete() 用 inspectAssets([id]) 回读验证，但主进程的 inspectAssets 对不存在的 id 会抛「资产不存在」，不会返回空数组，于是 delete() 必然 reject，带来两个后果：
  1. 批量删除的 N 条全部记入 failures，界面提示部分失败，勾选集合也不清空，而文件记录实际已经删掉。
  2. 助手的 delete_asset 每次都返回错误「资产不存在」，助手会误以为删除没有完成，可能重试或向用户报告失败。
  这里的根因是渲染层把 inspectAssets 当作「过滤掉不存在 id 的查询」来用，主进程的实际语义却是「逐个检查，缺一个就整体失败」，两边对接口行为的理解不一致（契约漂移）。渲染层单测 assetApplicationService.test.ts:49-55 用 mock 让 inspectAssets 直接 resolve []，正好把这个不一致掩盖了。
- 修法：在 assetApplicationService.delete 中改用不会因「不存在」而抛错的回读方式。下面两种做法任选其一：
  1. 推荐：新增一个轻量的按 id 判断存在性的查询，例如主进程 `assetExists(ids): boolean[]`，或者复用已有的 checkAssetPaths 思路，经 PAL（contracts / adapter / preload / ipc）暴露给渲染层，然后用 `verified = !exists` 判定。
  2. 最小改法：在 delete() 中把回读改成单条调用，并捕获「资产不存在」，捕获到即视为 verified=true；其他错误照常上抛。按错误文案匹配比较脆弱，最好让主进程抛出带 name 或 code 的结构化错误。
  不建议把主进程 inspectAssets 改成静默跳过缺失的 id，因为 index.inspection.test.ts:189、359 已经把「删除后 inspect 拒绝」作为契约断言下来。
  测试方面要做两处修改：
  - 把 assetApplicationService.test.ts:49-55 的 mock 改成与主进程一致：删除后回读那一步 reject('资产不存在')，或者 mock 新的存在性查询；同时断言 delete() 能 resolve，且 verified=true。
  - 补一条 deleteAssetsBatch 用例，断言全部成功时 failures 为空。
- 测试缺口：src/features/assets/application/assetApplicationService.test.ts:49-55「删除素材后回读索引，残留目标不得判为 verified」用 mockResolvedValueOnce([]) 模拟删除后的回读结果，与主进程「删除后 inspect 抛『资产不存在』」的真实行为不符（index.inspection.test.ts:189/359 对后者有断言）。assetBatchOperations 的删除路径和 delete_asset 能力处理器都没有用贴近真实行为的 mock 做过测试。

### 缺陷 4：导入预览图/视频封面直接写最终路径且不登记归属：半成品被永久当作缓存命中，且永不回收

- 排查编号：`assets-3`
- 位置：`electron/main/services/media-import/index.ts:228`；相关：`electron/main/services/media-import/probe.ts`、`electron/main/services/asset-library/thumbnailService.ts`、`electron/main/services/media-recycle/collector.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：三点可达性逐条核实如下。
  (1) 半成品被当成永久缓存（已复现）：prepareImage（index.ts:218-229）和 writeVideoPoster（probe.ts:68-90）都把输出直接写到按内容哈希命名的最终路径，判断“已生成”只看 access 是否成功。只要 sharp.toFile 或 ffmpeg 中途失败（磁盘满、解码异常、进程被杀、ffmpeg 留下 0 字节或残缺 jpg），目录里就会留下残缺文件。之后同一内容再导入（同一张大图或同一视频，包括 referenced 模式下 path、size、mtime 都没变的情况），会直接返回 cacheHit=true 和这张损坏的预览或封面，并写进画布节点的 previewImageUrl 或参数行的 previewUrl。重启也无法自愈，除非手动删除 Thumbnails 目录。
  (2) 永不回收（已复现）：生成的 image-<key>.jpg 和 video-<key>.jpg 位于受管根 Thumbnails 下，但从未调用 registerOwnedMedia。即使节点删除后它们进了回收候选，collector 也会因为 identity 为空而 retain('unowned') 并 forget 候选，文件会一直留在磁盘上。同目录的素材缩略图（thumbnailService.writeThumbnail）是先写临时文件再 rename，并调用 registerOwnedMedia(target, filePath)，两边做法不一致。
  (3) 并发同 key 写入：可以发生（withMediaHeavyTask 允许 2 个任务并行，同一内容被并发导入时两边都可能 access 未命中，然后各自写同一个路径），但危害比原描述小。两边写的是确定性的同样字节，最终内容通常一致。真正的风险是后开始的那一方以 O_TRUNC 打开文件时，先完成的那一方已经把路径交给了渲染层，渲染层可能读到暂时被截断的文件。这一条属于次要问题。
  定性修正：原 category 写的是 data-loss，不准确。用户原始素材不会丢失，实际问题是“派生预览损坏且永久缓存”加上“受管目录存储泄漏”。严重度维持 medium。
- 修法：让 index.ts 的 prepareImage 和 probe.ts 的 writeVideoPoster 统一采用 thumbnailService.writeThumbnail 的模式：
  1) 先输出到同目录的唯一临时文件（`${target}.${crypto.randomUUID()}.tmp`；ffmpeg 输出需要显式加 `-f image2` 或 `-f mjpeg`，因为扩展名是 .tmp，无法据此推断格式），成功后再 fs.rename 到 target，失败时在 finally 里 fs.rm(pending, {force:true})。这样最终路径上只会出现完整文件，access 命中就可以信任。
  2) rename 成功后调用 registerOwnedMedia(target, stored.fullPath)（视频封面传 sourcePath）。这样封面的 source_path 由原媒体保护，原媒体不再被引用时，回收器可以连带回收。注意 referenced 模式下源文件在受管根之外，canonicalPath 仍然可以作为 protector 使用。
  3) 用进程内 Map<targetPath, Promise> 对同一个目标路径的生成去重（类似 thumbnailJobs），避免并发重复写入。
  4) 可选：对已有缓存做一次简单校验（比如 size>0，或者用 sharp metadata 能读出来），用来清理旧版本已经留下的残缺文件；因为开发期不兼容旧数据，这一步也可以省略。
  同时在 electron/main/services/media-import/index.test.ts 补两条用例：toFile 写一半就失败后，下次导入必须重新生成；生成的预览必须调用 registerOwnedMedia(previewPath, fullPath)。
- 测试缺口：electron/main/services/media-import/index.test.ts 只覆盖了 audio 的 managed/referenced/bytes 导入和预热。sharp 被 mock 成空函数，writeVideoPoster 也被 mock 掉了，所以没有任何用例走到 prepareImage 的大图预览分支，也就测不到失败残留、缓存命中判定，以及预览/封面有没有调用 registerOwnedMedia。probe.ts 的 writeVideoPoster 没有单测。

### 缺陷 5：启动回收在窗口创建前同步全量扫描作品目录与所有文档，任一符号链接即整体失败

- 排查编号：`assets-4`
- 位置：`electron/main/services/media-recycle/providers.ts:91`；相关：`electron/main/index.ts`、`electron/main/services/media-recycle/runtime.ts`、`electron/main/services/media-recycle/file-scanner.ts`、`electron/main/services/media-recycle/lifecycle.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：1) 启动阻塞：用户删除过任意一条历史记录或资产（schema.ts 的 trigger 会写入 media_recycle_candidates，queue.enqueueMediaCandidates 也会写入）之后，下次启动时 app.whenReady 必须等 runMediaRecycle 完成才会 createWindow。其中 runtime.ts:59 的 collectDocumentReferences 没有超时，它会递归遍历整个用户根目录（包括 生成结果/上传素材/模型 下的全部文件，逐个 lstat），并把每个文档整份解析一遍。素材库越大，主窗口出现得越晚。JSON 解析虽然放在 Worker 里，不会卡住主线程事件循环，但 createWindow 被 await 推迟了。2) 符号链接导致永久失败：用户根下任意位置只要有一个符号链接或 junction（比如用户把某个子文件夹链接到别的盘），Worker 就会 throw，整次扫描 reject，runMediaRecycle 吞掉错误、只记 warn，候选保持不变。于是之后每次启动都要再付一次"扫描到链接为止"的阻塞代价，而回收一次也不会成功。不删除媒体这一点符合 fail-closed 的安全设计，并不是缺陷；真正的缺陷是：一个与文档无关的链接让整个回收功能永久失效，并且每次启动都要白白阻塞一次。
- 修法：1) 启动不要再阻塞窗口：把 startup 回收移到 createWindow 之后，在空闲时运行。"文档会话打开前完成普查"的语义改用 lifecycle 门控来保证，即在 startup 阶段让打开文档、外部服务开放这类操作等待或排队，而不是推迟窗口创建。同时给启动扫描加总超时：startup 用带超时的 AbortController，超时就保留候选，并把 runtime.ts:59 的扫描纳入同一套超时和取消。2) 缩小扫描根：用户根扫描时跳过 managedMediaRoots()（生成结果/上传素材/缩略图/EditStates）和模型目录，或者只扫描项目目录、外部位置和索引中的文档路径；document_index_documents 中已经落在其他根里的路径要去重。3) 符号链接按局部不可证明处理：Worker 遇到链接时不 throw，而是上报 {unprovable: target}。只有当 managed root 与链接目标存在重叠（或无法解析）时，才让扫描失败或保留候选；不能因为一个无关的链接放弃整轮回收。补测试：file-scanner 遇到无关符号链接时能完成扫描；startup 不会阻塞 createWindow 或会超时。
- 测试缺口：media-recycle 下没有 file-scanner 的测试，也没有任何符号链接用例（cache-deletion.test.ts 中的 junction 只测删除）。lifecycle.test.ts 和 collector.test.ts 都用 mock provider，既没覆盖 runtime.ts:59 不受 providerTimeoutMs 约束的文档扫描，也没覆盖 startup 在 createWindow 之前被 await 的顺序。

### 缺陷 6：导入层接受的 .pcm 音频在素材检查中必然判为 failed（导入与检查对无容器音频的契约不一致）

- 排查编号：`assets-6`
- 位置：`electron/main/services/asset-library/mediaInspection.ts:67`；相关：`electron/main/services/media-import/index.ts`、`electron/main/services/media-import/format.ts`、`src/features/assistant/conversation/assistantAttachments.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：两个问题，都已用测试复现。
  1. 裸 .pcm 音频检查必然失败：用户把 .pcm 拖进画布或生成区，导入层接受它（localMediaImport.ts 与 format.ts 支持 pcm；index.ts 在探测失败时让 pcm 的 durationSeconds 回退为 0）。随后在节点工具栏点"收录到素材库"，或把该音频节点拖进助手输入框，就会走 addMediaReferenceToLibrary → createAsset(mediaType='audio') → inspectAsset → inspectMedia。inspectMedia 的音频分支调用 readAudioDuration，ffprobe 对无容器 PCM 以 exit 1 退出。这里只有 reject，没有回退，于是资产 inspection_status 被写成 'failed'，素材卡一直显示检查失败。助手侧 importDroppedAssistantAttachment 会抛"附件源文件已经失效"；visual observation、剪辑引用等凡是要求 inspectionStatus==='ready' 的消费方也都会拒绝它。
  2. mime 回退为通用二进制：MIME_BY_EXTENSION 只有 16 个扩展名。导入层支持的 .avif、.m4v、.mkv、.aac、.opus、.pcm 等收录后，mime_type 一律落成 application/octet-stream，与导入层给出的 mime 不一致。
  严重度维持 low：pcm 是边缘格式，影响限于收录和附件，不会损坏数据。
- 修法：1. mime 改为共用导入层的格式表：在 mediaInspection.ts 中删掉自建的 MIME_BY_EXTENSION，改为从 electron/main/services/media-import/format.ts 导出的 EXTENSION_FORMATS，按 `path.extname(filePath).toLowerCase()` 取 mimeType。表里没有的扩展名仍回退 application/octet-stream。也可以复用 protocol.ts 已有的 mime 推断，二者择一，保持只有一个来源。
  2. 音频时长与导入层用同一条规则：音频分支对 pcm 的处理要与 media-import/index.ts:259-264 一致。可选做法：
     - `try { durationSeconds = await readAudioDuration(filePath) } catch (e) { if (ext !== '.pcm') throw e; durationSeconds = null }`；
     - 更好的做法是把"无容器格式无法探测时长"这条规则放进 format.ts 的格式描述（例如加一个 durationProbe:'optional' 字段），由导入层和检查层共同读取，不在两处各写一次 `extension === 'pcm'`。
  3. 另一条路是在导入层（localMediaImport.ts 与 format.ts）直接拒绝裸 PCM，让两层的契约一致。
  4. 补测试：在 asset-library/mediaInspection.test.ts 中增加两条用例：
     - ffprobe 失败时，.pcm 音频应 resolve，durationSeconds 为 null，mimeType 为 'audio/pcm'；非 pcm 音频仍应 reject。
     - .aac、.mkv、.avif 的 mimeType 应与 format.ts 一致。
- 测试缺口：electron/main/services/asset-library/mediaInspection.test.ts 只测 code 资产（有界读取、无效清单），音频分支和 MIME_BY_EXTENSION 映射都没有用例。media-import 的 pcm 回退也没有对应的跨层契约测试，无法发现导入层能收进来、检查层却不认的情况。
