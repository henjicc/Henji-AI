## 任务目标

作品目录里出现一份读不懂的文件时，扫描只跳过它而不是整轮失败；文档会话在冲突、移动、转正、收集素材期间不卡死也不丢修改；跨进程文件锁不会被长任务误接管。

## 当前情况

- 作品索引在 `electron/main/services/documents/index-scanner.ts`，只把 `DocumentFormatError` 当作“单个文件坏了”，`PersistenceError`（版本过新、外壳缺字段）和图片包头错误会让整轮扫描抛错。
- 文档会话在 `src/features/documents/documentSession.ts` 与 `documentSessionRegistry.ts`，提示框队列由 `DocumentSessionDialogs.tsx` 只渲染队首。
- 跨进程锁在 `electron/main/services/fs/file-lock.ts`，30 秒无更新即视为残留，持锁期间不刷新。
- 可复用：`documents.test-support` 的 `createTestEnvironment`、`index.native.test.ts`（原生 SQLite，需走原生验收器）、`fs/atomic-file.ts` 的原子写。

## 实施方案

先修两条高严重度（扫描整轮失败、起名对话框卡死），再修传输窗口与锁。扫描侧抽一个“文件内容不可读”判定函数供 `indexCandidate`、`otherCopyStillThere`、`scanProjects`、`collect` 共用；会话侧把冲突处理前移到起名之前，并引入“传输窗口”挂起自动保存。锁改为心跳 + 持有者令牌。

### 缺陷 1：一份读不懂的文档或项目说明会让整个作品索引扫描失败，且每次都失败

- 排查编号：`persist-0`
- 位置：`electron/main/services/documents/index-scanner.ts:313`；相关：`electron/main/services/documents/document-file.ts`、`electron/main/services/documents/workspace.ts`、`electron/main/services/documents/package-service.ts`、`electron/main/services/image-editor-v3/image-document/package-adapter.ts`、`src/core/documents/projectManifest.ts`
- 严重度：高；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：作品目录、项目或登记的外部文件夹里，只要出现下面任一文件：
  - 更高 kindVersion 或 envelopeVersion 的文档；
  - JSON 语法正确但外壳缺字段的文档；
  - version 更高或非数字的 .henji/project.json；
  - 截断或 0 字节的 .henjiimg 包；
  DocumentIndexScanner.scanOnce 就会整轮失败，并抛出“作品索引扫描未完成…请检查访问权限”。这些文件可能来自同步盘、新版本痕迹AI 写入，或项目包导入时原样带进来的读不懂文件。
  后果：
  - 之后每次 refresh 和 rebuild 都失败，新文档、新项目永远进不了索引。
  - repository.ts:595/635/646 和 projects.ts:306 的 refreshProjects 兜底，拿到的是扫描错误，而不是“找不到”。
  - importProject 在发布项目文件夹（package-service.ts:475）之后才调用 scanner.refresh()（:485）。这时失败会让导入报错，但因为 published 已赋值，项目不会被清理；用户重试就会再导入一份同名副本。
  - package-service.ts:178 注释写的“读不懂的文档…导入后由扫描如实报告”，与实际行为相反。
- 修法：1. 在 index-scanner.ts 的 indexCandidate（:312-313）和 otherCopyStillThere（:342）里，把 PersistenceError 和图片包头解析错误（ImageDocumentHeaderError、zip 打不开）也当作“单个文件不可读”：计入 report.invalid、记 warn 日志、返回 null 或 false。只有带系统错误码的 I/O 错误（EACCES、EIO、EPERM 等）才继续往上抛。建议抽一个 isUnreadableFileContent(error) 判定函数，供这几处共用。图片包适配器（package-adapter.ts 或 readImageDocumentPackageHeader）最好把 zip 打开失败统一包成 DocumentFormatError，免得扫描器去识别普通 Error。
  2. 在 scanProjects（:163）和 collect（:295）里，除了 ProjectManifestError，也把 PersistenceError 当作无效项目说明：跳过并计入 invalid。还可以在 workspace.readManifest 或 parseProjectManifest 内部把 PersistenceError 包成 ProjectManifestError（保留 cause 和 code），这样 projects.ts 等其他调用方也能统一处理。
  3. package-service.importProject：项目已发布后，scanner.refresh() 的失败不应再让导入报错。改为记 warn 日志，返回已发布的项目（可以用 describeProject 的结果，或附带“索引稍后刷新”的提示）。
  4. 补测试：在 index-scanner.test.ts 或 index.native.test.ts 里覆盖四种情况：kindVersion 过高、外壳缺字段、项目说明 version 过高、0 字节 .henjiimg。断言扫描正常完成、invalid 计数正确、正常文档照常入索引。
- 测试缺口：index.native.test.ts:231 只测了 JSON 语法损坏的文档（写入 '{'，抛 DocumentFormatError）会计入 invalid。没有测试覆盖版本过高、外壳缺字段（PersistenceError）、项目说明版本过高、损坏的图片包这几种情况下扫描是否还能继续。index-scanner.test.ts 只测了 EACCES、EIO 时整轮中止。

### 缺陷 2：草稿起名对话框提交时如果撞上版本冲突，界面永久卡死

- 排查编号：`persist-1`
- 位置：`src/features/documents/documentSessionRegistry.ts:216`；相关：`src/features/documents/documentSession.ts`、`src/features/documents/documentPromptStore.ts`、`src/features/documents/DocumentSessionDialogs.tsx`、`src/features/documents/DocumentSaveNameDialog.tsx`
- 严重度：高；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：前提：草稿会话处于 conflict 状态。有两种进入方式：
  1. 外部进程（例如无窗口的助手）改了这份草稿，自动保存撞上冲突，用户在冲突提示里选了“稍后”。
  2. 刚好在 submit 内的 flush 写入时撞上冲突。saveOnce 先排一个提示，flush 下一轮再去 await 同一个提示。
  之后用户按“保存”（registry.save），或在离开时选“保存”（registry.leave / leaveProject），起名对话框作为 queue[0] 弹出。用户填好名字点确定后，submit 调用 prepareTransfer，进而 flush，再进入 promptConflict，冲突提示被追加到 queue[1]。DocumentSessionDialogs 只渲染 queue[0]，冲突提示永远不可见；submit 一直不结束，起名对话框的取消和关闭在 submitting 状态下都无效。结果是这份文档没法保存、离开或关闭，save()、leave() 和 leaveProject() 返回的 Promise 也一直挂起。如果此时外层在等退出屏障，应用同样无法退出。leaveProject 的 submit（documentSessionRegistry.ts:263，对每个 session 调 prepareTransfer）有同样的问题。
- 修法：首选方案：在弹出起名对话框之前先处理冲突。具体是在 promptFinalize 调用 askSaveName 之前先执行 `await session.flush()`；leaveProject 在 askSaveName 之前对每个 session 先执行 flush。flush 里的 promptConflict 此时会排在队首，能正常显示。用户选“稍后”时 flush 会抛 DocumentSessionConflictError，save/leave 按“失败、修改保留”的原有约定往上抛。
  兜底方案：避免 submit 再弹出排队的提示，因为 submit 期间仍可能新撞上冲突。办法是给 flush 加一个不提示的变体（例如 `flush({ promptOnConflict: false })`，或者 prepareTransfer 遇到 status==='conflict' 时直接抛 DocumentSessionConflictError）。这样 DocumentSaveNameDialog 的 catch 能显示错误，并恢复 submitting=false，用户就可以取消。
  另一种做法是修改 documentPromptStore/DocumentSessionDialogs，允许 conflict 类型叠加渲染在当前 saveName 之上，或插到队首。
  修复后需要补测试：用 dialogDocumentSessionPrompter 加真实队列，复现“conflict 选稍后，然后 save，然后 submit”这条路径，断言 submit 能结束，或者冲突提示可见。leaveProject 也要覆盖这条路径。

### 缺陷 3：移动、转正、收集素材期间的编辑被 applyTransfer 的强制重新载入静默丢弃

- 排查编号：`persist-2`
- 位置：`src/features/documents/documentSession.ts:303`；相关：`src/features/documents/documentOperations.ts`、`src/features/documents/documentSessionRegistry.ts`、`electron/main/services/documents/repository.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：打开中的文档在执行 collectDocumentMedia，或者执行跨容器的 moveDocument 或 finalize 且复制了素材（主进程把 revision 加一）。在主进程复制期间，工具实例上发生的任何修改，无论来自用户编辑还是后台生成写入，都会在 applyTransfer 调用 reload() 时被磁盘内容覆盖，同时 savedSeq 被设成 changeSeq，状态显示为“已保存”，没有任何提示。分两种情况：(1) 修改发生在命令结束前 800ms 内，自动保存还没发出，修改直接消失，不出现任何提示；(2) 自动保存已经发出，在主进程排在收集之后，撞上 DocumentRevisionConflictError 并弹出冲突提示，但 reload 随即把会话重置为 saved。提示仍挂在屏幕上，用户选“覆盖”只会写回重载后的内容，选“重新载入”也拿不回修改。
- 修法：建议改法：在 DocumentSession 上提供“传输窗口”。(a) 在 prepareTransfer 和 flush 之后 suspend()，同时在 documentOperations 的 moveDocument、collectDocumentMedia、finalize 路径上用 try/finally 包住 IPC，结束后 resume()。这样传输期间的修改只标脏，不会发出自动保存，也就避免了必然的冲突和提示。(b) 改写 applyTransfer：revision 变化时如果会话不 dirty，照旧 reload；如果 dirty，不能直接 reload 丢弃修改，应读取新版本，把新的 meta 和 revision 作为 expectedRevision 的基准，再把内存内容按 result 的路径映射重算（需要主进程返回 mapping，或在主进程侧对传入内容做 rewriteContentPaths），然后重新保存。实在做不到时至少保持 dirty，并走冲突提示让用户选择，不能把 savedSeq 设成 changeSeq。(c) reload() 被 applyTransfer 调用时，不能在 status==='conflict' 且提示未决时把状态静默改成 saved。
  回归测试：在 documentOperations.test.ts 中加两例，用 gate 包住 collectDocumentMedia 和 moveDocument，并设置 saveGate 为同一个 gate。一例在 gate 期间 tool.edit 后立即放行；另一例推进 900ms 让自动保存先发出。两例都断言修改最终保留在工具实例或磁盘中，并且不会出现自相矛盾的冲突提示。
- 测试缺口：documentOperations.test.ts 的用例“移到项目前写完最后一次，移动后会话换到项目里的位置并重新载入”以及 videoEditService.test.ts 和 videoEditProjectDocuments.test.ts 的 collectMapping 用例，都只覆盖传输前已有的未保存修改会被 flush。没有一个用例在 move 或 collect 的 IPC 进行中修改工具实例，也没有用例检查 applyTransfer 在 dirty 或 conflict 状态下调用 reload 的行为。documentSession.test.ts 里没有直接测 applyTransfer 的用例。

### 缺陷 4：跨进程文档锁 30 秒即被当成残留接管，长时间的 move/collect 会被并发写入覆盖

- 排查编号：`persist-3`
- 位置：`electron/main/services/fs/file-lock.ts:51`；相关：`electron/main/services/documents/repository.ts`、`electron/main/services/documents/code-files.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：窗口进程对一份引用了大量或很大视频的剪辑/画布文档执行“移到项目”（move→relocate）或“收集素材”（collectMedia），并且媒体复制、哈希超过 30 秒。这期间同机运行的助手 CLI 进程（共用 documentStore/locks）对同一文档调用 save。它看到锁文件 mtime 已超过 30 秒，就当作残留删掉并自己拿锁。这时原文件还在原路径、revision 也没变，所以助手的 expectedRevision 校验能通过，它在原路径写入 revision+1。窗口进程随后用操作开头读到的旧 envelope，在目标处 writeNewDocumentFile，再 removeOriginal 删掉原路径，助手的保存就丢了（collectMedia 则会用旧内容覆盖写回）。窗口进程的 finally 还会无条件 rm(lockPath)，把助手持有的锁一起删掉，第三方随后可以直接拿锁，互斥彻底失效。图片编辑器的两个仓库（image-document-service.ts:603、image-editor-v3/document-repository.ts:499）和 code-files.ts:122 也共用这份 withFileLock，存在同源问题，只是它们当中长时间操作是否超过 30 秒还需要逐个确认。
- 修法：只改 electron/main/services/fs/file-lock.ts：(1) 拿锁后写入 pid 加随机 token，持锁期间用 setInterval（周期远小于 staleMs，例如 staleMs/3）对锁文件 utimes 做心跳，finally 里先清掉定时器；(2) 释放时先读锁文件，确认 token 是自己的再 rm，不是自己的就不删并记 warn；(3) 判定残留时，除了 mtime 超时，还可以用 process.kill(pid, 0) 判断写锁进程是否还在，进程仍在、心跳也新的锁不接管；(4) 接管残留锁时为避免两个等待者同时 rm 后重建，可以改用 rename 到临时名再删，或接管后重新校验 token。补测试：在 no-overwrite.test.ts 增加“持锁时长超过 staleMs 仍互斥”“释放不删除他人的锁”两例（可参考本次复现的写法，staleMs 设 100ms）。更彻底的做法是 relocate/collectMedia 把媒体复制放到锁外，最后短暂持锁核对 revision 再发布。不过这改动更大，可以作为后续优化。
- 测试缺口：electron/main/services/fs/no-overwrite.test.ts 的 describe('跨进程文件锁') 只测了两种情况：短时持锁串行，以及预置的旧 mtime 锁被接管。没有测“持有者持锁时间超过 staleMs，其他等待者不得接管”，也没有测“释放时只删除自己的锁”。repository 层也没有跨进程并发 save 与 move/collectMedia 的测试。

### 缺陷 5：跨进程文件锁的“陈旧接管”存在竞态且持锁期间不刷新 mtime：超过 30 秒的文档操作会被另一进程接管并发写入

- 排查编号：`ipc-4`
- 位置：`electron/main/services/fs/file-lock.ts:51`；相关：`electron/main/services/documents/repository.ts`、`electron/main/services/image-editor-v3/image-document/image-document-service.ts`、`electron/main/services/image-editor-v3/document-repository.ts`、`electron/main/services/documents/code-files.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：Reachable when one process holds the lock for more than 30s (staleMs) and another process (the main window, or the windowless assistant from assistant:cli) asks for the same documentId lock after that 30s mark. Examples of long holds: DocumentRepository.move, duplicate into another container, or collect_media copying many large media files. The second process sees an mtime older than 30s, deletes the lock that is still in use, and acquires it, so both processes write the same document and the same container directory at once. When the original holder finishes, its finally block also deletes the taker's lock file, so a third writer can get in without waiting. Separately, if several waiters judge the lock stale at the same moment, an rm-then-create race lets more than one of them believe they hold it. The trigger needs a single operation longer than 30s plus concurrent cross-process access, so it is rare in practice. Severity: low.
- 修法：Changes go only in electron/main/services/fs/file-lock.ts; callers stay as they are.
  1) Give each lock acquisition a token (pid + randomUUID) and write it into the lock file.
  2) While the lock is held, run a setInterval at an interval of about staleMs/3 that calls lock.utimes(now, now) on the FileHandle to keep the lock's mtime fresh. Clear the timer in finally.
  3) On release, read the lock file first and rm it only if its content still equals our own token. Otherwise our lock was already taken over, so log a warn and leave the file alone.
  4) Make stale takeover atomic: rename(lockPath, `${lockPath}.stale-${uuid}`) and then rm the renamed file. Only the waiter whose rename succeeds goes on to open('wx'). On ENOENT, just retry. Before renaming, stat again and compare mtime/ino so a lock someone else just recreated is not renamed away.
  Add regression tests to electron/main/services/fs/no-overwrite.test.ts, using a small staleMs: (a) an active holder whose hold time exceeds staleMs is not taken over (concurrency stays at 1); (b) a holder that was taken over does not delete the new owner's lock file on release.
- 测试缺口：The "跨进程文件锁" group in electron/main/services/fs/no-overwrite.test.ts only covers taking over a static leftover lock file whose mtime was pushed back by hand. It never tests an active holder whose hold time exceeds staleMs, never tests releasing without an ownership check, and never tests several waiters judging the lock stale at the same time.

### 缺陷 6：项目改名或转正与文档保存之间没有互斥，保存可能把旧项目文件夹重新建出来

- 排查编号：`persist-4`
- 位置：`electron/main/services/documents/projects.ts:319`；相关：`src/features/documents/documentOperations.ts`、`electron/main/services/fs/atomic-file.ts`、`electron/main/services/documents/repository.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：在 POSIX（macOS/Linux）上，项目 P 里有一份已打开的文档，它的保存请求（自动保存、画布后台生成触发的保存，或 collectMedia/写回）已经在主进程 DocumentRepository.save 里执行完 locate，拿到旧路径 P/doc。这时用户改项目名（ProjectService.rename），或草稿转正时又有新的保存插进来（ProjectService.finalize），relocate 用 moveDirectoryNoOverwrite 把 P 移到 Q，并对索引执行 rebaseDocuments。随后保存继续，writeBufferAtomically 的 recursive mkdir 重建 P，把最新内容写进 P/doc，保存报成功，还执行 catalog.upsertDocument，把索引里这份文档的位置改回 P/doc。结果：
  1. Q/doc 留着旧内容和旧 revision。
  2. P 是一个没有项目说明的文件夹，下次扫描会给它补写说明，成为一个新项目；里面的文档与 Q/doc 同 ID，会被换成新 ID。
  3. 会话 relocate 后按 ID 定位，可能得到 P/doc，也可能得到 Q/doc，用户在 Q 里看到的是旧版本。
  单元测试已稳定复现这一结果：旧文件夹被重建，新位置是 rev 0 的空内容。Windows 上目录有打开句柄时改名会失败，所以主要影响 POSIX。触发需要保存的 locate 到写盘之间与改名重叠，窗口很短，实际概率低。
- 修法：以下两层建议都做：
  1. 主进程兜底（必做）：DocumentRepository 的 save、collectMedia，以及 repository.ts:792 那处写回，在写盘前不要依赖 recursive mkdir 重建父目录。可以给 writeBufferAtomically 加一个选项，例如 createParent:false，文档仓库的已有文件写入传 false；父目录不存在时 fs.open 会报 ENOENT，转成 DocumentNotFoundError，由会话重新定位后重试。另外，写盘后应确认 file.path 仍等于 catalog 里该 ID 的当前路径，或者确认所在项目根目录的说明仍在，避免 upsertDocument 把索引改回旧路径。更彻底的做法是给 ProjectService.relocate 和 DocumentRepository.exclusive 加一把共享锁，比如项目路径级读写锁：文档写入持读锁，项目改名和转正持写锁。
  2. 渲染侧（建议）：DocumentOperations.renameProject 在调用 commands.renameProject 之前，对该项目下所有会话执行 prepareTransfer/flush，并暂停自动保存（suspend）；改名完成后执行 relocate，再恢复自动保存。leaveProject 的 finalize 路径同样要在 flush 之后暂停自动保存，直到 relocate 完成。
  建议补一条回归测试：在 projects.test.ts 里用上面的拦截方式（containerForPath 停住）让保存与 renameProject 交错，断言旧文件夹不存在、最新内容在新位置，并且索引路径指向新位置。
- 测试缺口：electron/main/services/documents/projects.test.ts 里“改名就是改文件夹名…”这条用例只串行地先保存、再改名，没有覆盖保存与项目改名、转正交错执行的情况。repository.test.ts 只测同一文档 ID 下的 exclusive 串行，不涉及跨 ProjectService 的互斥。src/features/documents 下的会话测试也没有覆盖 renameProject 期间自动保存插进来的情况。

### 缺陷 7：listDocuments 分页拼全量时中间有 await，并发保存会让文档从结果里漏掉

- 排查编号：`persist-5`
- 位置：`electron/main/services/documents/service.ts:81`；相关：`electron/main/services/documents/index-store.ts`、`src/features/documents/documentOperations.ts`
- 严重度：低；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：只在进程启动后封面缓存还没加载时出现，也就是本进程第一次调用 listDocumentsPage、listDocuments、getDocumentCover 或 saveDocumentCover 的那段时间；作品数要超过 DOCUMENT_PAGE_SIZE=100。第一次全量 listDocuments 读完第 1 页后，会在 covers.getMany 中逐个 readdir 封面目录（真实 I/O，让出事件循环）。如果这时另一路 IPC 保存（或索引扫描）更新了一份还没翻到的文档，它的 updated_at 变成最新，排到游标前面，后面的页都不会返回它，全量结果里就漏了这一条。findDocument 会报“找不到这份文档”，依赖完整列表的打开、移动、嵌入宿主等操作偶发失败。缓存加载好之后，循环里的 await 只让出微任务，不会再和别的 IPC 交错，所以实际窗口很窄，严重度维持 low。
- 修法：在 DocumentService.listDocuments 中，先同步调用 workspace.catalog.listDocuments(filter) 一次取到全部行（better-sqlite3 同步执行，中间不会让出），再对所有行调用一次 covers.getMany，然后映射成 DocumentSummary。可以把 listDocumentsPage 中行到摘要的映射抽成私有函数，供两处共用。或者在构造或首次使用前先 await covers.loadCache 预热，但这样不如前一种稳。另外建议 documentOperations.findDocument 改走按 ID 查询（如新增 getDocumentSummary(id)，或复用 catalog.getDocument），不要拉全表再 find，这样也能顺带消除 O(n) 开销。
- 测试缺口：electron/main/services/documents 下的测试（如 index-store.scale.test.ts、collect-documents.test.ts）只测了 catalog 的同步分页，或单次 listDocuments 的结果。没有测试在 DocumentService.listDocuments 翻页期间并发修改 updated_at，也没有覆盖封面缓存冷加载这个让出点。
