# 1.4 媒体处理落盘与大文件

## 任务状态

- 状态：待验证
- 所属阶段：第一阶段-构建与数据安全
- 前置任务：无
- 关联任务：3.1（生成预检调用压缩/裁剪）
- 是否可以并行：可以

## 任务目标

视频压缩、裁剪、导出占位、剪贴板读取这些主进程媒体操作做到：失败不留下会被当成缓存的半成品、可以取消、不把大文件整份塞进内存或 IPC、在非 NTFS 磁盘上也能导出。

## 当前情况

- `electron/main/services/video/ops.ts` 的 `compressVideoToFit`、`trimVideoSource` 直接写最终路径，`existsSync` 即视为缓存命中；同仓 `audio-edit/media.ts` 的 `prepareAudioEditAudio` 已是“临时文件 + rename”的正确写法，可照抄。
- `electron/main/services/system.ts` 的独占写依赖硬链接，exFAT/FAT32/网络共享不支持。
- `electron/main/services/clipboard.ts` 的 `readFiles` 把所有文件读成 base64 经 IPC 传输。
- `electron/main/ipc/video.test.ts` 整体 mock 了 `ops.ts`，压缩/裁剪逻辑没有任何单测。

## 实施方案

统一“原子落盘 + 在途去重 + 命中前校验”三件套；给生成预检链路透传取消信号；剪贴板改为返回路径或带上限的流式读取；导出占位在不支持硬链接时回退到 `O_EXCL` 打开。

## 缺陷明细

以下条目来自 2026-10-13 排查，位置与行号以当时 `main` 为准；开始前先用行号附近的代码片段重新定位。

### 缺陷 1：视频压缩/裁剪产物非原子落盘：ffmpeg 失败或被中断留下的残缺文件被当作缓存命中复用

- 排查编号：`mediamain-0`
- 位置：`electron/main/services/video/ops.ts:145`；相关：`src/core/services/generationRequestPreflight.ts`、`electron/main/ipc/video.ts`
- 严重度：高；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：生成提交（GenerationService L178-179）或裁剪弹窗确认（VideoTrimModal L178）触发 compressVideoToFit / trimVideoSource。ffmpeg 直接以 -y 写最终路径 `uploads/compressed-<digest>.mp4` / `uploads/trim-<digest><ext>`；muxer 写头失败、磁盘满、硬件编码器失败且重探测结论不变（encodeCompressedVideo L191 直接 throw）、应用退出/被杀等任一情况都会留下 0 字节或无 moov 的残缺文件且无人清理。本次调用方 catch 后回退原片，但 digest 只由源路径+mtime+参数（+kf1）决定，之后每次同源同参数提交都在 L93/L146 `fs.existsSync(outputPath)` 命中缓存，跳过 ffmpeg，把残缺文件路径替换进请求参数并上传给供应商；付费生成以损坏输入失败或产出垃圾，且用户没有任何自愈途径（除非改动源文件 mtime）。并发同 digest 调用（同一视频一次生成多个变体）两者都未命中 existsSync，两个 ffmpeg -y 同时写同一输出路径互相截断。
- 修法：在 electron/main/services/video/ops.ts 对 trimVideoSource 与 compressVideoToFit 两处统一改为原子落盘（与 audio-edit/media.ts prepareAudioEditAudio 同法）：
  1) ffmpeg 输出写到同目录临时文件 `${outputPath}.${crypto.randomUUID()}.tmp`（trim 需保留容器后缀以便 muxer 识别，可用 `trim-<digest>.<uuid>.tmp<sourceExt>` 或显式 `-f` 指定容器）；成功后 `fs.promises.rename(tmp, outputPath)`；`finally` 中 `fs.promises.rm(tmp, { force: true })`。encodeCompressedVideo 的重试路径也应各自写临时文件，throw 前不留产物。
  2) 命中缓存前校验：`stat.size > 0`（更稳妥用 ffprobe 读 duration），不合法则删除并重新编码。
  3) 用模块级 `Map<string /*outputPath*/, Promise<...>>` 做在途去重，同 digest 并发请求共享同一 Promise，完成后从 Map 删除。
  4) 补精确单元测试（mock node:child_process.execFile + 临时 uploads 目录）：首次失败不留最终命名产物、第二次重新编码、并发同 digest 只跑一次 ffmpeg。
- 测试缺口：electron/main/ipc/video.test.ts 把 '../services/video/ops' 整体 mock 掉（compressVideoToFit/trimVideoSource 均为 vi.fn()），ops.ts 的 compress/trim 逻辑没有任何单元测试；同目录 proxy.test.ts 对代理缓存有"损坏代理重算、残留临时文件清理"用例，但 ops.ts 的两个缓存路径没有对应覆盖。

### 缺陷 2：生成预检的视频压缩/裁剪 ffmpeg 不可取消：取消生成后编码进程继续跑满 CPU 直到结束

- 排查编号：`mediamain-2`
- 位置：`electron/main/services/video/ops.ts:165`；相关：`src/core/services/generationRequestPreflight.ts`、`src/core/services/GenerationService.ts`、`electron/main/ipc/video.ts`
- 严重度：低；核实方式：调用链追踪确认（未写复现测试）
- 现象：用户提交一个带大视频的生成：视频体积超过模型的 videoConstraints.maxSizeMB，或者设置了 uploadedVideoTrimStart/End。GenerationService.generate 在 L178 先 await compressFirstVideoIfNeeded，主进程启动 ffmpeg 重编码。CPU 路径是 libx264 preset medium，长视频要跑几分钟；如果硬件编码失败，还会重试再编一遍。
  编码期间用户取消，options.signal 被 abort，但这个信号既没传给预检，也没传过 IPC，主进程的 ffmpeg（以及之前的 ffprobe）会继续全速编码直到结束。遇到坏流或卡住的输入，因为没有 timeout，会一直挂着。等编码完成，GenerationService 在 L194 的 throwIfAborted 处才结束任务。
  用户反复取消再重试时，还有一个后果：第一次的 ffmpeg 正在直接写 outputPath（compressed-<digest>.mp4），第二次请求的 digest 相同，fs.existsSync(outputPath) 已经为 true，于是直接返回一个还没写完的半截 mp4 去上传。trim 路径（trim-<digest>.ext）同理。如果 ffmpeg 中途失败或被杀，残留文件也会被当成有效缓存一直复用。
  影响主要是 CPU 和电量浪费、进程叠加，加上半截文件被当缓存复用的连带风险。不会造成数据丢失。
- 修法：1) ops.ts：execFileAsync 增加 { signal?, timeout? } 参数，并传给 execFile；可以复用 media/shared 的 execFileAsyncBuffer 风格。readVideoInfo、trimVideoSource、compressVideoToFit、encodeCompressedVideo 都加可选的 signal，每次 await 后调用 signal?.throwIfAborted()。如果已经 abort，就不要再走硬件失败后换编码器重试那条路径。
  2) 同时把输出改成原子写：ffmpeg 先写到 `${outputPath}.${uuid}.part`，成功后再 fs.rename 成正式文件；失败或取消时 unlink 临时文件。这一步必须做：有了取消以后，被杀的 ffmpeg 会留下半截文件，而 existsSync 缓存命中会把它当成有效产物。同 digest 的并发请求可以用一个 in-flight Map 合并。
  3) ipc/video.ts：compress/trim 的 payload 增加可选 requestId，仿照 thumbnailRequests 的做法按 sender.id 管理 AbortController，sender destroyed 时一并 abort；再新增 'video:cancelCompress'，或者复用一个通用的 video 取消通道。preload、platform 合约和 commands/video.ts 同步增加 signal：abort 时调用取消 IPC。
  4) generationRequestPreflight.ts 的 compressFirstVideoIfNeeded / trimFirstVideoIfSelected 接收 signal。被取消时要把 AbortError 抛出去，不能按“压缩失败、用原文件继续”的分支吞掉。GenerationService L178-179 传入 options.signal。VideoTrimModal 关闭时也传一个 signal。
  5) 测试：在 electron/main/services/video/ 下新建 ops.test.ts，mock node:child_process 的 execFile，断言收到了 signal；abort 后 promise 被 reject，临时文件被清理，也没有生成正式缓存文件。
- 测试缺口：electron/main/ipc/video.test.ts 把 services/video/ops 整个 mock 掉了（L17），只测了缩略图的取消；ops.ts 本身没有单元测试。compressVideoToFit / trimVideoSource 的取消、超时和半截文件缓存行为，都没有任何测试覆盖。

### 缺陷 3：远程媒体 http(s) 源整段读入内存且无超时/大小上限

- 排查编号：`mediamain-3`
- 位置：`electron/main/services/media/shared.ts:48`；相关：`electron/main/services/video/ops.ts`、`electron/main/services/audio/ops.ts`
- 严重度：低；核实方式：逻辑成立但未复现（修前先确认）
- 现象：渲染层播放或预览远程 http(s) 视频时（VideoViewerModal 在没有 filePath 时用 videoUrl，CanvasVideoPlayer 的 readVideoInfo(src)），以及剪裁、压缩、缩略图、音频波形处理远程源时，主进程的 resolveLocalMediaPath 会把整个响应用 arrayBuffer() 读进主进程内存后再写到 Uploads 临时文件。为了拿一个 hasAudio 或时长，也要下载完整视频，并且每次都生成新的临时文件。数百 MB 到 GB 级的远程视频会让主进程内存出现约等于文件大小 2 倍的瞬时峰值，内存吃紧时主进程可能 OOM。除 generateVideoThumbnailBytes（IPC 路径）外，调用方都不传 signal；服务器完全挂起时 undici 默认约 300 秒超时，只有持续慢速吐数据的服务器才会让调用无限期挂住。原发现中「超过 Buffer 上限」和「服务器挂起时永久 pending」两点不成立。
- 修法：在 electron/main/services/media/shared.ts 的 downloadToTempFile 中：
  1) 改为流式落盘：`await pipeline(Readable.fromWeb(response.body), fs.createWriteStream(targetPath), { signal })`。
  2) 增加最大字节数上限：先检查 Content-Length，超出直接拒绝；传输过程中用 Transform 累计字节，超限就中止，并在 catch 里 rm 临时文件。原有的 rm 兜底逻辑保留。
  3) 合并调用方的 signal 和 AbortSignal.timeout（总时长上限），用 `AbortSignal.any([signal, AbortSignal.timeout(...)].filter(Boolean))`。
  4) 可选：readVideoInfo 这类只需探测元数据的场景，可以直接让 ffprobe 读 http(s) URL（或只下载开头一段），不再整段下载；或者按 URL 缓存已下载的临时文件，避免重复下载。
  测试补充在 electron/main/services/media/shared.test.ts：mock 一个 response.body 为 ReadableStream 的响应，断言流式写入；Content-Length 或实际字节超限时断言 reject 并调用 rm。
- 测试缺口：electron/main/services/media/shared.test.ts 只测了取消、写入失败清理和本地路径，没有覆盖大响应的流式写入、大小上限和下载超时。

### 缺陷 4：剪辑导出用 exclusive 写占位文件，底层依赖硬链接：导出到 exFAT/FAT32/网络共享会直接失败

- 排查编号：`ipc-2`
- 位置：`electron/main/services/system.ts:101`；相关：`electron/main/services/fs/atomic-file.ts`、`electron/main/services/fs/no-overwrite.ts`、`src/features/videoEdit/application/videoEditExport.ts`、`src/features/videoEdit/application/videoEditAutoSubtitles.ts`、`src/core/persistence/backup.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：用户在剪辑导出（或导出字幕、自动字幕、程序画面采集、代码素材、运动资源、工程备份）时，把目标路径选在不支持硬链接的卷上：exFAT/FAT32 的 U 盘或移动硬盘、部分 SMB/NFS 网络共享。主进程 writeFileBytes 的 exclusive 分支先写暂存文件，再调 fs.link 发布，这一步抛出 EPERM / ENOTSUP / EOPNOTSUPP / ENOSYS（Windows 上也可能映射成其他 errno）。导出在第一帧之前就整体失败，暂存文件被清理，用户只看到底层 errno 文本，不知道原因，也不知道怎么解决。在 NTFS/APFS/ext4 本地盘上不会出现。
- 修法：只改 electron/main/services/fs/atomic-file.ts 中 writeBufferAtomically 的 exclusive 分支：fs.link 抛出 EPERM/ENOTSUP/EOPNOTSUPP/ENOSYS/EINVAL（同盘情况下也可以加上 EISDIR，即 Windows 的 ERROR_INVALID_FUNCTION）时，回退为 `fs.open(targetPath, 'wx')` 独占创建占位（遇到 EEXIST 照常失败，保住不覆盖的语义），关闭句柄后用 replaceFileAtomically(stagedPath, targetPath) 把完整内容换上去；替换失败时删除自建的占位和暂存。这与 no-overwrite.ts 的 createFileExclusively 是同一套语义，也可以直接抽出共用，避免重复实现。这样 system.ts 的 writeFileBytes 和 ai-runtime/media-store.ts:140 都能修好。同步把 system.videoExport.test.ts 中「文件系统不支持排他发布时明确失败」改成：link 抛 ENOTSUP/EPERM 时排他写入成功且内容完整；目标已存在时仍然拒绝且不覆盖；回退路径失败时不留下占位和暂存。另外，因为确实存在“明确失败”的测试，修改前最好先和用户确认一下这个取舍的变更。
- 测试缺口：electron/main/services/system.videoExport.test.ts 的「文件系统不支持排他发布时明确失败，只清理暂存且不降级覆盖目标」mock 了 link 抛 ENOTSUP，但断言的是失败。它把“不支持硬链接的卷上导出失败”当作正确行为固化了下来，没有一个测试断言 exFAT/网络位置上可以不覆盖地成功写入。atomic-file.test.ts 也没有覆盖 exclusive 分支在 link 不支持时的回退。

### 缺陷 5：clipboard:readFiles 把剪贴板里所有文件整份读入内存再 base64 经 IPC 传给渲染层，无类型/大小限制

- 排查编号：`ipc-3`
- 位置：`electron/main/services/clipboard.ts:102`；相关：`electron/main/ipc/clipboard.ts`、`src/contexts/GlobalContextMenuProvider.tsx`、`src/commands/clipboard.ts`、`electron/preload/index.ts`
- 严重度：中；核实方式：已用最小测试复现（测试已删除，需按“修法”落为正式回归测试）
- 现象：在 Windows 资源管理器里复制一个大视频（或者一批大的原始素材），然后：(a) 在提示词输入框右键选“粘贴”，或者 (b) 在图片编辑器 / 图片标注工具里点“粘贴剪贴板图片”。主进程 readClipboardFiles 会对剪贴板里的每个路径调用 fs.readFile 读入全部字节，再 toString('base64')（比原文件大约 1.33 倍），然后经 IPC 结构化克隆送到渲染层。主进程和渲染进程的内存会暴涨好几 GB，UI 会卡住。文件超过 Buffer 或字符串上限时抛出的 RangeError 会被 catch 静默吞掉。即使剪贴板里有一张小图片，readClipboardImage 的文件回退分支也会先把所有非图片文件读完，才挑出第一张图片。补充发现（另一个缺陷，不影响本条结论）：GlobalContextMenuProvider 在 document 上分发 'global-paste-image'，而 useGlobalPasteImage 监听的是 window 上的 'globalPasteImage'。事件名和目标都对不上，所以右键粘贴文件读出来的 base64 根本没有消费方，等于把开销白白付了；而且拿到文件后会直接 return，粘贴看起来什么都没发生。
- 修法：1) readClipboardFiles 和 clipboard:readFiles 的 DTO 只返回 { path, mimeType, size }，不再返回 data。渲染层要内容时，按路径走已有的 media:importFromPath 或 henji-media:// 统一入口（见 docs/rules/media-url.md）。同时更新 preload 的 api-desktop.d.ts、src/platform/contracts/clipboard.ts、GlobalContextMenuProvider 和 useGlobalPasteImage。2) readClipboardImage 的文件回退分支不要复用 readClipboardFiles：先拿路径，用 inferMimeFromPath 按扩展名筛出 image/*，stat 后检查单文件上限（比如几十 MB，超出就返回 null 或记一条 warn 日志），只读第一张命中的图片。3) catch 里至少记 warn 日志（含路径数量和原因），不要静默吞掉。4) 在 clipboard.test.ts 补用例：FileNameW 同时包含视频和图片时，只读图片；超过上限的文件不读。5) 另外单独修 PASTE_IMAGE_EVENT 的事件名和分发目标不一致的问题（document 'global-paste-image' 对 window 'globalPasteImage'）。
- 测试缺口：electron/main/services/clipboard.test.ts 只测了 readClipboardImage 的位图分支和写入。它 mock 的 fs 没有 stat，readBuffer('FileNameW') 也恒为空，所以 readClipboardFiles 和 readClipboardImage 的文件回退分支（类型筛选、大小上限、只读第一张图片）都没有覆盖。GlobalContextMenuProvider 和 useGlobalPasteImage 之间的事件对接也没有测试。
