### 1.3 界面底座现状

已经扎实的部分：

- 按钮、选项、标签、导航、字段触发器都有统一组件。
- 正式代码中原生控件为 0。
- 颜色、圆角、阴影、层级、毛玻璃、时长任意值由 ESLint 与 `check:*` 硬拦。
- 调用点外观覆盖由规则 E 拦截。
- 组件样张页有“组件名出现过”的覆盖测试。

审计归纳出五类缺口：

1. **令牌值域不全**：间距、图标尺寸、行高、条带高度、面板与浮层尺寸、多行文本高度、弹窗内边距没有令牌，业务只能写任意值并登记豁免。
2. **同名尺寸不同高**：`UiButton md` 为 32，`UiIconButton md` 为 28，同一行默认组合必然不齐。
3. **缺组件**：加载态、行内错误、不可用原因、记录列表、查看器外壳没有共享实现，业务各自手写。
4. **门禁不在日常链路**：`verify:changed` 不跑界面门禁；`check:surface` 默认只告警；原生控件禁令没有 lint 规则；界面语法里的大部分规则没有检查。
5. **没有集中地**：样张页没有令牌、界面模式和规范，只截第一屏，只能用启动参数进入；规范文档之间口径分裂（选中态、分段项数、交付证据）。

## 二、最终目标

1. `electron:build` 恢复可用；已确认的 106 条缺陷全部修复，并且每条都有回归测试。
2. 有一个**设计系统中心页**，能集中查看全部组件（尺寸阶梯与状态矩阵）、全部设计令牌、常用界面模式与规范要点，可切换主题、可搜索、可整页截图审计。
3. 尺寸、间距、图标、行高、条带、面板、动效都只有一个来源。底座组件自身不越档，业务不需要写任意值。
4. 常见的“丑”都能在本地被自动发现：按钮大小不一、同一行不齐、间距随意、两个主按钮、标签在上的面板行、记录列表无分隔、禁用不说原因、动效时长不统一。
5. 界面规范只有一套说法，u7 巡检与界面重设计 5.8 的遗留都有结论。

## 三、总体思路

- **缺陷修复**：按领域聚合成任务，同一任务内按严重度从高到低处理。每条缺陷先把复现场景落成正式测试，再按“修法”做最小修复，并沿根因检查同源调用方（AGENTS.md 工作原则）。
- **界面底座**：先建设计系统中心页（4.1），让后续每一步都有地方对照和截图。然后由内向外推进：令牌（4.2、4.3）→ 动效（4.4）→ 组件（4.5、4.6）→ 性能（4.7）。每个任务都要在中心页补样本，并同步 skill。
- **门禁与文档**：门禁接入日常验证（5.1）可以提前做。规则增强（5.2）要等新令牌和新组件落地，否则规则无从判断。文档统一（5.3）放最后，一次收口。

## 五、全局开发约束

- 遵守 `AGENTS.md`。分支：默认在 `main` 工作，除非用户另有指定。每个任务独立提交，提交后立即推送。精确暂存，不用 `git add .`。
- 按领域读规则：持久化读 `docs/rules/persistence.md`，界面读 skill `henji-ui-surface` 与 `docs/rules/frontend-ui.md`，画布读 `docs/rules/canvas.md`，媒体读 `docs/rules/media-url.md`，主进程读 `docs/rules/electron-desktop.md`，助手读 `docs/rules/assistant-goal.md` 与 `assistant-status.md`，收尾读 `docs/rules/testing.md`。
- **行号会漂移**：缺陷条目的行号来自 2026-10-13 的代码。开始前用条目里的函数名或代码片段搜索定位。如果发现某条已被其他提交修好，在执行记录写明证据并跳过。
- **验证按 `testing.md` 判级**：精确测试 → 所属工程 tsc → `npm run verify:changed -- --level L2 <本任务文件...>`。原生 SQLite、FFmpeg、GPU 测试交给对应专项命令或原生验收器。不要因为“保险起见”跑全量。
- **界面任务**：改公共组件或令牌后，默认验收是中心页截图加 `src/core/theme` 测试（skill `references/review.md` 第 8 节）。截图需要 Windows 本机。
- **skill 两侧同步**：改 `.claude/skills/henji-ui-surface` 必须同步 `.codex/skills/henji-ui-surface`，并跑 `npm run check:skill-sync`。
- **助手相关改动**：按 `docs/rules/assistant-status.md` 第零节判断是否更新台账。涉及的任务是 2.6、3.3、3.4。
- **不扩大范围**：执行中发现新缺陷，记进当前任务的执行记录与总览“最近记录”，或在本计划新增任务。新任务编号接在当前阶段末尾，已有编号不重排。

## 六、风险与回退

- 每个任务独立提交，出问题可以单独回退。
- 改动面大的任务（4.2、4.3、5.1）建议拆成两到三次提交，每次都能独立通过门禁。
- 尺寸与令牌重命名是跨全仓的 API 变更，依靠 tsc 兜底，并在中心页加常用页面截图目视。开发期不保留兼容层。
- 持久化与锁的修复（1.2、1.3）属于 L2 高风险，必须跑原生测试。
- SDK 改动不发布。用户测试前，3.2 的状态保持“待验证”。

## 七、已驳回的发现（不要重复排查）

| 排查编号 | 原发现 | 驳回理由（摘要） |
|---|---|---|
| `react-5` | 音色克隆面板切换试听文件时直接删除旧文件 | 删除只是进入回收候选队列，实际删除只在启动或退出静止窗口，且会先检查引用 |
| `sdk-0` | APIMart 轮询把 MJ 的 FAILURE/CANCEL 当作处理中 | 统一查询接口按官方资料不返回 MJ 风格状态；如果日志里出现过，应改判 |
| `assets-5` | 集合删除撤销时用裸 INSERT 恢复成员 | 删除素材会推进修订号，撤销前的修订校验先行拒绝，路径不可达 |
| `canvas-7` | 后台生成登记后才 retain，被 UI 抢先会抛错 | 节点任务表同步写入，UI 抢先时会在 retain 前被拒，竞态不可达 |
| `camerastage-3` | 渲染任务入队前取消被吞掉 | 真实路径下结果不会写回；极端组合下只会白渲染一次 |
| `mediamain-4` | 帧导出写 stdin 无 error 监听 | 真实帧尺寸必然走带监听的 drain 路径；Node 22 实测不会成为未捕获异常 |
