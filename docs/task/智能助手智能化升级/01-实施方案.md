# 01 · 实施方案 —— 智能助手智能化升级

## 当前项目和相关功能现状

Henji-AI 当前基于 Electron + React + TypeScript。智能助手已经具备独立 utility process、AgentRunner、统一工具注册表与网关、审批模式、HostContextSnapshot、scope revision、记忆、用户指令、Artifact offload、日志关联和确定性跨工作区工作流。

- D:/VibeCode/Henji-AI/electron/main/services/agent-runtime/context/router.ts：意图路由；
- D:/VibeCode/Henji-AI/electron/main/services/agent-runtime/context/builder.ts：上下文组装；
- D:/VibeCode/Henji-AI/electron/main/services/agent-runtime/context/compaction.ts：当前上下文压缩；

## 当前实现方式

当前 Runner 基本流程是：

~~~text
读取宿主快照
  → 确定性规则或路由模型分类
  → 选择固定工具域
  → 每轮构建上下文
  → 单步模型调用
  → 顺序执行工具
  → 回注观察结果
  → 根据文本和工具结果判定结束
~~~

当前已经有较好的安全边界，但“路由一次确定、工具数量固定、失败后主要交给模型自行恢复、成功后没有统一验证”使 Agent 在复杂任务中表现不够稳定。

## 已确认的问题

1. 通用模型描述目录已建立，但描述内容目前基本为空，模型选择缺少定性依据。
2. 路由类型在 router.ts 中支持更多领域，但实际路由模型 schema 未覆盖工具箱、3D、分镜、图片编辑、素材和工作流等领域。
3. 每轮工具最多暴露 8 个，Runner 最多执行 4 个调用且全部串行，parallelTools 能力没有充分利用。
4. 工具错误已经带有恢复类型，但 Runner 尚未形成统一的刷新、等待、重试、换策略和询问用户流程。
5. 生成、画布和工作流没有统一的最终成功证据协议。
6. 当前压缩主要保留最近消息并生成短文本摘要，缺少计划、证据、未完成步骤和工具配对的状态重建。
7. 长期记忆主要依赖关键词 bigram 相关性，并在运行开始时一次性注入。
8. 模型层已产生 reasoningText/ReasoningDelta，但 Runner 和界面目前只显示普通文本增量。

## Claude Code 调研后的适配原则

只吸收适合 Henji-AI 的机制：

- 复用同一个执行内核，不建立第二套 Agent Loop；
- 将工具视为包含语义、权限、并发、输出、错误和进度的运行时协议；
- 使用分层 Prompt Runtime 和动态上下文边界；
- 压缩后重建当前工作状态，而不是简单截断历史；
- 将用户偏好、会话摘要和项目知识分层保存并渐进召回；
- 使用事件流记录执行事实，让界面消费计划、证据和下一步。

不直接照搬：

- 通用 Shell、任意文件系统和任意网络；
- 完整 MCP 生态和复杂 swarm/team；
- 面向代码仓库的全部 Skills；
- 原始隐藏思维链展示。

## 总体解决思路

### 1. 从一次性路由改为可修正的任务规划

路由只提供初始意图和候选领域，不再成为整个运行的硬锁。模型在探索工具结果、宿主快照和用户偏好后，可以补充或修正计划。计划步骤需要包含目标、前置条件、候选工具、成功证据和失败恢复方式。

### 2. 从工具名称改为工具语义协议

在现有 AgentToolDefinition 上逐步补充“适用场景、避免场景、前置条件、输出引用、成功验证和恢复策略”等描述。工具目录仍采用渐进式披露，但搜索结果要足以帮助模型判断下一步。

### 3. 从执行完成改为证据完成

每类写操作定义明确的完成证据。创建任务只代表提交成功；生成成功、画布变更、素材编辑和工作流完成都必须通过查询或结构化结果确认。

### 4. 从历史截断改为状态重建

上下文压缩时保留结构化任务状态、计划、最近证据、scope revision、相关记忆和活动工具。历史对话只保留有助于当前决策的部分。

### 5. 从单层记忆改为自然语言偏好加结构化状态

用户指令文件继续由用户直接编辑；长期记忆继续受确认和敏感信息策略约束；新增会话摘要和项目知识索引时，仍然只召回当前任务需要的少量内容。

## 阶段之间的关系

第一阶段先建立真实基线，避免凭感觉改 Agent。第二阶段解决直接压制判断力的路由、工具、验证和恢复问题。第三阶段处理长任务和跨会话的一致性。第四阶段把计划和证据转化为用户可理解的界面，并建立持续回归门槛。

## 兼容方式

- 保留现有 AgentRunner、AgentToolGateway、HostCommand/HostQuery 和 utility process 边界。
- 保留现有工具名称、输入输出 schema 和风险等级；新增字段优先向后兼容。
- 保留 user-instructions.md 的自然语言编辑方式。
- 保留 canonicalModelId 通用描述机制；供应商模型文件不重新承载通用描述。
- 已有确定性 Workflow 继续作为可靠执行器，不与通用计划重复实现。
- 未经真实数据确认，不自动改变默认批准模式、模型 Profile 或高风险操作策略。

## 风险控制和回退原则

- 每个阶段先补自动化回归，再做真实 Electron 手动测试。
- 发生未知副作用时不自动重放；运行进入 recovery_required，等待用户确认。
- 新的并行执行只允许在工具声明和 scope 校验都满足时启用。
- 新的记忆召回失败时退回空记忆，不阻塞主任务。
- 新的压缩或计划策略失败时保留现有短摘要路径作为回退。
- 任何路由优化都不能绕过工具网关、审批、数据分类和真实能力 schema。

## 全局开发约束

- 不在业务组件中直接调用模型或 Provider API。
- 不将模型特定判断写进通用 UI；优先扩展配置、schema 或 Agent 工具描述。
- 新增或改造网络、文件、长任务、状态流转和用户可见失败时接入现有日志系统。
- 不新增裸 any，不新增平行日志或平行权限通道。
- 所有用户可见的执行状态都来自结构化 AgentEvent，不从模型文本猜测。
- 用户偏好是高优先级自然语言上下文，但不能覆盖安全、审批、权限、真实运行状态和硬能力约束。

## 最终验收条件

1. 对生成、诊断、画布、工具箱、3D、分镜、图片编辑、素材和跨工作区工作流，Agent 能先理解任务，再选择工具并说明当前步骤。
2. 模型选择有可追溯的描述、标签、schema、用户偏好和供应商可用性依据。
3. 写操作有明确成功证据；失败后能按错误类型恢复、换策略或询问用户。
4. 长会话压缩后仍保留当前计划、关键证据和未完成事项；应用重载或 utility 异常不会重复未知副作用。
5. 用户能看到简洁的执行计划、工具状态、证据和下一步，不需要阅读原始日志或隐藏思维链。
6. 现有第七阶段手动测试清单全部纳入回归基线，新增智能性评测通过。
7. 真实 Provider、Electron 交互、日志、长稳、token、性能和安全验收结果均有记录；待确认项不能被标记为已完成。
