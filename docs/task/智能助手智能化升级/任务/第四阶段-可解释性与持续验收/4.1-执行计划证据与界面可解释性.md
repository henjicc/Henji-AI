## 任务目标

让用户能快速看懂助手正在做什么、为什么这样做、已经得到什么证据、下一步是什么以及是否需要批准。界面应使用结构化计划、工具状态、结果引用和错误恢复信息，不展示未经验证的原始思维链，也不把大段日志和模型增量直接堆给用户。

## 当前情况

- D:/VibeCode/Henji-AI/src/core/assistant/events.ts 已有 PlanUpdated、ToolRequested、ToolStarted、ToolCompleted、ToolFailed、ApprovalRequired、ContextCompacted 和最终结果等事件。
- D:/VibeCode/Henji-AI/src/features/assistant/conversation/agentRunReducer.ts 已将工具事件归并为活动状态，支持恢复时重新构建视图。
- D:/VibeCode/Henji-AI/src/features/assistant/conversation/AssistantConversation.tsx 已有折叠的计划摘要、工具活动卡、审批卡、Markdown 渲染和延迟渲染策略，但计划仍主要是单一摘要，缺少步骤状态、成功证据和恢复建议。
- D:/VibeCode/Henji-AI/src/features/assistant/conversation/RunStatusBar.tsx、ToolActivityCard.tsx、AssistantMarkdown.tsx 和 AssistantConversation.tsx 是当前执行状态、工具活动和最终答复的主要界面入口。
- 模型层可以产生 reasoningText/ReasoningDelta，但原始思维链不等同于执行事实；产品应优先显示短计划、工具原因、证据和下一步。

## 实施方案

1. 将 AgentEvent 中的计划扩展为可更新的步骤摘要，至少表达目标、当前步骤、已完成步骤、阻塞点、成功证据和下一步。
2. 统一工具活动卡的紧凑状态：默认显示工具名称、动作、状态和结果摘要；详细参数、引用和错误按需展开。
3. 将“已提交”“已完成”“已验证”三个状态区分开，生成、画布、素材和工作流必须根据 2.3 的证据协议展示真实状态。
4. 将错误恢复信息转为用户可执行的下一步，例如刷新、等待、批准、重试、换策略、补充信息或手动处理；不把内部堆栈直接展示为答复。
5. 保留 Markdown 的结构化渲染、代码、链接、列表和长文本性能；工具活动和计划块默认折叠，避免连续消息占满窗口。
6. 仅在产品设置和真实模型能力确认后考虑受限 reasoning 摘要；默认不渲染原始隐藏推理，不从模型思维文本推断工具事实。
7. 所有用户可见状态来自结构化 AgentEvent，不能通过解析普通模型文本猜测成功或失败。

## 执行步骤

1. 对照第七阶段手动测试清单和当前界面，记录计划、工具卡、审批卡、Markdown、错误和长会话的可读性问题。
2. 与 2.3、3.1 的计划和证据字段对齐 AgentEvent、agentRunReducer 和运行时恢复数据。
3. 调整计划展示组件，使步骤、状态、证据和下一步可折叠、可恢复且默认紧凑。
4. 调整工具活动卡、错误卡和最终答复的文案与状态映射，确保不会把提交成功误写成 Provider 已完成。
5. 检查 AssistantMarkdown、滚动、延迟渲染和悬浮窗口布局，避免长消息导致窗口拖动和尺寸调整卡顿。
6. 增加界面 reducer、事件回放、Markdown 和恢复状态测试，并把真实 Electron 鼠标操作留给用户按 4.2 清单验证。
