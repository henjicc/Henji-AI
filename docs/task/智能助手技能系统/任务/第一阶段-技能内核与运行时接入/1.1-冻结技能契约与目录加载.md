# 1.1 冻结技能契约与目录加载

- 关联任务：1.2（消费本任务的清单与正文读取）、2.1（安装时复用同一套校验）

## 任务目标

建立技能的唯一契约与加载入口：定义技能元数据结构、实现 frontmatter 解析、扫描内置与用户两个目录并聚合成一份去重后的技能清单，索引每个技能的 `references/` 引用文件，同时提供按名称读取正文、按路径读取引用文件的接口。本任务完成后，主进程可以准确回答"当前有哪些技能、每个技能的描述是什么、它有哪些引用文件、某个技能的正文或某个引用文件的内容是什么"，但还不接入助手运行时。

## 当前情况

- 项目中**没有任何技能相关实现**，这是全新模块。
- `resources/assistant-skills/` 下已有 3 个示例技能（`image-generation`、`3d-shot-composition`、`generation-troubleshooting`），是 2026-08-03 提前写的格式样例，可直接作为解析测试的真实夹具。
- 随包资源的解析范式已有两处可抄：`electron/main/services/ai-runtime/manifest.ts:59-64` 与 `progress.ts:353-355`，都是"先试 `cwd/resources/…`，再试 `process.resourcesPath/…` 与 `process.resourcesPath/resources/…`"。
- 数据根目录取值用 `getDataRootDir()`（`electron/main/services/image/path-utils.ts:38`），它会跟随用户在设置里改的自定义数据目录。
- 主进程文件服务的范式见 `electron/main/services/assistant/user-instructions.ts`：zod schema 放 `src/core/assistant/`，读写实现放 `electron/main/services/assistant/`，用 `createMainLogger` 记录 start/completed/failed。
- **依赖中没有 YAML 解析库**（`yaml`、`js-yaml`、`gray-matter` 均无），按重要记录 006 不引入，自己写解析器：`name` / `description` 严格校验，其余键宽容跳过。
- 外部标准技能的 frontmatter 常带 `allowed-tools`、`license`、`metadata` 等本项目不用的字段，`allowed-tools` 还常写成 YAML 列表。这些**必须能装上但绝不生效**（重要记录 008）。
- 标准技能用 `references/` 子目录做二级渐进披露，本期必须完整支持（重要记录 009）。`resources/assistant-skills/` 下现有的 3 个示例技能都没有 `references/`，写测试时需要自己造一个带引用文件的夹具。
- `electron-builder.yml` 的 `extraResources` 目前只列了 `model-manifest.json`、`progress-seeds.json`、`camera-stage`，需要加上 `assistant-skills`。

## 实施方案

契约放在 `src/core/assistant/skills.ts`（渲染层与主进程共用类型），加载实现放在 `electron/main/services/assistant/skills/`。

**frontmatter 解析分两档**：

- `name` 与 `description` 严格解析——必须是 `key: value` 标量（裸写或单双引号包裹），缺失、重复、超长、格式不符即判非法并报出行号。
- 其余任何键宽容跳过——无论标量、列表（`- item` 缩进行）还是缩进块，识别出边界后整段丢弃，**不存储、不返回、不进入任何输出**。这样外部标准技能带着 `allowed-tools` 也能装上，而这些字段在本项目里没有任何效果。

**references 支持**：扫描技能目录时同时索引 `references/` 下的 `.md` / `.txt`，作为 `referencePaths: string[]`（技能目录内的相对路径，如 `references/api.md`）放进元数据。读取引用文件时做三重校验：相对路径、拆段后无 `..` 与空段、`path.resolve` 后仍在该技能目录内。

扫描时内置目录与用户目录各扫一遍，同名以用户目录为准（**整个技能文件夹覆盖，不做文件级合并**），并在清单项上标 `source: 'builtin' | 'user'` 与 `overridesBuiltin`。解析失败的技能不进清单，但要以 `invalid` 条目形式返回，供 2.2 的界面显示错误原因——静默吞掉会让用户不知道自己的技能为什么没生效。

## 执行步骤

1. 新建 `src/core/assistant/skills.ts`，用 zod 定义并导出：
   - `ASSISTANT_SKILL_SCHEMA_VERSION = 'assistant-skill/v1'`
   - `assistantSkillNameSchema`：`^[a-z0-9]+(-[a-z0-9]+)*$`，1～64 字符
   - `assistantSkillReferencePathSchema`：`^references\/[A-Za-z0-9._-]+(\/[A-Za-z0-9._-]+)*\.(md|txt)$`，且不含 `..`
   - `assistantSkillMetadataSchema`：`{ name, description (1~200), source: 'builtin'|'user', overridesBuiltin: boolean, enabled: boolean, bodyBytes: number, referencePaths: string[], updatedAt: string }`
   - `assistantSkillDetailSchema`：`{ name, source, path: string | null, content: string, bytes: number }`（`path` 为 null 表示 `SKILL.md` 正文）
   - `assistantSkillManifestSchema`：`{ schemaVersion, skills: metadata[], invalid: { path, reason }[] }`
   - 常量：`ASSISTANT_SKILL_MAX_BODY_BYTES = 65_536`、`ASSISTANT_SKILL_MAX_COUNT = 100`、`ASSISTANT_SKILL_TEXT_EXTENSIONS = ['.md', '.txt']`、`ASSISTANT_SKILL_REFERENCE_DIR = 'references'`
2. 新建 `electron/main/services/assistant/skills/frontmatter.ts`，导出 `parseSkillFrontmatter(source: string): { name: string; description: string; body: string }`：
   - 文件必须以 `---` 开头，第二个 `---` 之前是 frontmatter
   - 逐行扫描：空行与 `#` 注释跳过；`name:` / `description:` 严格取标量值（裸写或单双引号），重复出现或值为空即报错
   - **其余任何 `key:` 一律跳过**，并连带跳过其后所有比它缩进更深的行以及紧随的 `- ` 列表行，直到下一个顶层键或 frontmatter 结束
   - 结束时缺 `name` 或缺 `description` 报错；所有错误必须携带行号
   - **返回值里不包含任何未知键**——解析器对外只暴露 `name`、`description`、`body`
3. 新建 `electron/main/services/assistant/skills/paths.ts`，导出：
   - `getBuiltinSkillsDir()`：按 manifest.ts 的三候选顺序解析 `resources/assistant-skills`
   - `getUserSkillsDir()`：`path.join(getDataRootDir(), 'assistant', 'skills')`
   - `resolveSkillFilePath(skillDir: string, relativePath: string): string`：校验相对路径、拆段无 `..` 与空段、扩展名在白名单、`path.resolve` 后仍以 `skillDir` 为前缀；任一不满足抛 `SKILL_PATH_REJECTED`
4. 新建 `electron/main/services/assistant/skills/registry.ts`，导出：
   - `listAssistantSkills(): Promise<AssistantSkillManifest>`——扫两个目录，解析每个 `<name>/SKILL.md`，校验 `name` 与文件夹名一致、正文不超限、总数不超限；递归索引 `references/` 下的白名单扩展名文件填入 `referencePaths`；用户技能整个文件夹覆盖同名内置；按 name 升序返回
   - `readAssistantSkill(name: string, relativePath?: string): Promise<AssistantSkillDetail>`——不传 `relativePath` 返回 `SKILL.md` 正文；传了则经 `resolveSkillFilePath` 校验后返回该引用文件内容。不存在抛 `SKILL_NOT_FOUND`，引用文件不存在抛 `SKILL_REFERENCE_NOT_FOUND`，被停用抛 `SKILL_DISABLED`
   - 目录不存在时按空清单处理，不创建目录、不报错
   - 用 `createMainLogger('main.assistant_skills')` 记录 `assistant_skill.scan.completed`（含 builtin/user/invalid/reference 计数），**不记录技能正文或引用文件内容**
5. 启用状态读取：从 SQLite `settings` 表读 key `assistant_disabled_skills`（JSON 字符串数组），缺失视为全部启用。写入在 2.1 实现，本任务只读。存储位置已定，见重要记录 007。
6. 在 `electron-builder.yml` 的 `extraResources` 增加 `resources/assistant-skills → resources/assistant-skills`。
7. 写单元测试 `electron/main/services/assistant/skills/registry.test.ts` 与 `frontmatter.test.ts`。

## 执行记录

### 2026-08-03 已完成

按计划实现，实际落地与计划的差异如下：

1. **多了一个 `state.ts`**。计划把"读停用名单"写在 `registry.ts` 里，实际拆成 `skills/state.ts` 的
   `readDisabledSkillNames()`。原因是 2.1 要在同一个 settings 键上加写入，读写放一个文件比分散在
   `registry.ts` 和 `install.ts` 两处更稳。2.1 的 `setAssistantSkillEnabled` 应写进这个文件。
2. **registry 导出可注入版本**。除计划的 `listAssistantSkills()` / `readAssistantSkill()` 外，另导出
   `scanAssistantSkills(dirs)` 与 `readAssistantSkillFrom(dirs, name, path?)`，参数是
   `SkillDirectorySet { builtinDir, userDir, disabledNames }`。前两个只是取真实目录后调用后两个。
   这样单元测试用临时目录即可，不必在 Node 环境里伪造 Electron 与 SQLite。
3. **错误类型收在 `src/core/assistant/skills.ts`**。新增 `AssistantSkillError`（带 `code` 与可选
   `line`）与 `isAssistantSkillError`，错误码 5 个：`SKILL_NOT_FOUND`、`SKILL_REFERENCE_NOT_FOUND`、
   `SKILL_DISABLED`、`SKILL_PATH_REJECTED`、`SKILL_FRONTMATTER_INVALID`。1.2 与 2.1 直接复用，不要
   各自再定义一套。注意渲染层 tsconfig 的 target 早于 ES2022，`Error` 构造函数没有 options 形参，
   `cause` 是手动挂上去的。
4. **多了 4 个常量**：`ASSISTANT_SKILL_MAX_REFERENCE_COUNT = 64`、
   `ASSISTANT_SKILL_MAX_REFERENCE_DEPTH = 8`、`ASSISTANT_SKILL_ENTRY_FILE`、
   `ASSISTANT_SKILL_DISABLED_SETTING_KEY`。前两个是防护：`referencePaths` 会随 `load_assistant_skill`
   的输出进模型上下文，一个塞了上万个引用文件的技能能直接撑爆一轮请求。
5. **`resolveSkillFilePath` 强制 `references/` 前缀**。计划只说"技能目录内的相对路径"，实现上第一段
   必须是 `references`，与 `assistantSkillReferencePathSchema` 对齐。技能正文只能通过不传 path 读取，
   不存在"用 path 读 SKILL.md"这条路。
6. **多了第六种非法情况**：文件夹存在但没有 `SKILL.md`，进 `invalid` 并给出"缺少 SKILL.md"。静默跳过
   会让用户拷错目录层级之后完全看不出问题在哪。
7. **引用文件名不符合 schema 的会被跳过**（含空格、中文等）。这类路径模型无法用来调用加载能力，
   收进 `referencePaths` 只会让模型拿到一个必然被拒绝的路径。
8. **符号链接在扫描阶段天然被排除**：`readdir({ withFileTypes: true })` 是 lstat 语义，指向目录的符号
   链接 `isDirectory()` 为 `false`；`references/` 递归里另有一次显式 `isSymbolicLink()` 跳过。
