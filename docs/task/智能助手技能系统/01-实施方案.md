# 实施方案

## 一、当前现状

### 1. 助手知识全部写死在系统提示词里

唯一来源是 `electron/main/services/agent-runtime/context/prompt-layers.ts` 的 `stableSystemPrompt`：**36 条、3796 字符**，每一轮请求原样发送。

按领域归类：

| 类别 | 条数 | 真正需要的场景 |
|---|---|---|
| 安全 / 权限 / 证据 / 答复格式 | 10 | 每次 |
| 上下文锚定、能力发现、错误恢复 | 5 | 每次 |
| 生成与模型选择 | 9 | 只有生成任务 |
| 导航与视觉观察 | 5 | 只有要看界面时 |
| 画布 | 2 | 只有画布任务 |
| 诊断与日志 | 2 | 只有排查问题 |
| 设置 / 记忆 / 产品概览 | 3 | 各自场景 |

**约 58% 是领域相关的**，却对所有请求无差别发送。而且每加一个领域，所有请求都变长一点——这个趋势不可持续。

### 2. 上下文分层机制已经具备

`prompt-layers.ts` + `layer-budget.ts` 已有完整的分层能力：

- `AgentContextLayer`：`id / source / trust / priority / required / maxTokens / content`
- `selectContextLayers(layers, tokenBudget)`：按 `required` 和 `priority` 排序，按预算截断或省略，输出 `AgentContextLayerReport`
- 层 ID 白名单在 `context/types.ts` 的 `AGENT_CONTEXT_LAYER_IDS`
- 每层被包进 `[CONTEXT_LAYER id=… trust=… source=…]` 标记

**已有条件注入的先例**：`model_catalog` 层在纯闲聊意图下整层不注入，生成意图下还会按媒体类型只塞对应模型。技能索引层可以直接沿用同一模式。

### 3. 工具侧早就按需

`discover_application_capabilities` 批量发现 + 每轮最多 8 个活动工具 + `addedToolNames` 增量激活。知识侧全量、工具侧按需，这个不对称是本任务要消除的。

**无 YAML 解析库**（`yaml` / `js-yaml` / `gray-matter` 均不在依赖）。

## 二、最终目标

- 常驻上下文从 3796 字符降到约 1500 字符（安全 + 通用流程）+ 约 250 字符技能索引。
- 领域知识按需加载：一个纯画布任务不再读到生成模型规则。
- 用户可以自己写技能、装技能，扩展助手行为，且不引入任何脚本执行面。
- 新增领域知识不再让所有请求变长。

## 三、总体思路

### 1. 格式：Anthropic Agent Skills 标准

```markdown
---
name: 图片生成
description: 什么时候用这个技能
---

正文（流程、对照表、常见错误）
```

- 一个技能 = 一个文件夹 + 一个 `SKILL.md`，加可选的 `references/` 子目录
- `name` 必填，≤64 字符，必须与文件夹名一致；**允许中文**，只拒绝会破坏文件夹名的字符（详见重要记录 012）
- `description` 必填，≤200 字符——这是**唯一常驻**的部分
- **其余 frontmatter 字段一律宽容跳过、永不解释**。外部标准技能常带的 `allowed-tools`、`license`、`metadata` 都能装上，但在本项目里没有任何效果（重要记录 006、008）

技能在本项目里的定位就是**一段按需加载的提示词**，不附带工具授权、脚本或任何其他功效。

选标准格式的原因见重要记录 001。

### 2. 加载：标准的两级渐进披露

- **常驻**：新增 `skills_index` 上下文层，列出所有已启用技能的 `name` + `description`
- **一级按需**：后端能力 `load_assistant_skill({ name, reason })` 返回 `SKILL.md` 正文 + 该技能的 `referencePaths`
- **二级按需**：同一能力带 `path: 'references/xxx.md'` 再读引用文件

两级都必须支持，否则外部标准技能装进来会出现"正文让模型去读 references/xxx.md，模型却读不到"的断链（重要记录 009）。用一个能力两种入参实现，不另建第二个工具。

这就是标准 Skills 的工作方式，也和项目里工具按需激活的节奏一致：工具进来了，说明书跟着进来。

### 3. 两个目录

| | 位置 | 可写 |
|---|---|---|
| 内置 | `resources/assistant-skills/<name>/SKILL.md` | 只读，随包发布 |
| 用户 | `getDataRootDir()/assistant/skills/<name>/SKILL.md` | 可增删改 |

用户目录挂在 `getDataRootDir()` 下（而不是 `getAppLocalDataDir()`），这样用户改数据目录时技能跟着走。同名时用户技能覆盖内置，界面上明确标注。

### 4. 安全模型

三条，见重要记录 002 / 003：

1. **只允许纯文本落盘**——非 `.md` / `.txt` 一律不安装，安装结果明确列出被丢弃的文件，不静默。
2. **技能是数据不是权限**——技能层 `trust` 标为 `untrusted_user`（内置为 `builtin`），系统提示词加硬规则声明技能不能改变权限、审批和安全边界。
3. **压缩包硬限额** + zip-slip / 符号链接 / 嵌套压缩包拒绝。

## 四、任务范围

- 技能契约（zod schema）、frontmatter 解析（严格 name/description + 未知键宽容跳过）、目录扫描、`references/` 索引与清单聚合
- `skills_index` 上下文层、`load_assistant_skill` 能力（正文 + 引用文件两级）、信任边界提示词
- 单文件 `.md` 与 `.zip` 安装、卸载、启用停用、IPC 与 platform 契约
- 设置面板技能管理分区
- 把 21 条领域规则沉淀为内置技能，`stableSystemPrompt` 瘦身

## 五、非任务范围

- 技能市场、在线下载、更新检查
- 技能内的脚本、命令、模板引擎执行
- `allowed-tools` —— **完全不支持**，与其他未知字段一样被跳过；技能不携带任何工具授权语义
- 技能多语言版本
- 技能自动匹配加载（由模型按 `skills_index` 显式调用 `load_assistant_skill`）
- 技能编辑器（本期只做安装/删除/启停，编辑靠外部编辑器改文件）

## 六、阶段划分与关系

```
第一阶段（内核 + 运行时）── 纯加法，不改现有行为
   1.1 契约与目录加载  →  1.2 运行时接入与信任边界
        │                        │
        ├────────────────────────┼──→ 第三阶段（3.1 提示词瘦身）唯一会改变助手行为的一步
        │
        └──→ 第二阶段（安装与管理）
                 2.1 安装卸载  →  2.2 设置分区界面
```

- 第二阶段只依赖 1.1 的契约与目录约定，**可与 1.2 并行**。
- 第三阶段依赖 1.2 的加载链路可用，且必须等用户完成既有实机验收（重要记录 005）。

## 七、兼容与回退

- **纯加法阶段无兼容问题**：1.1～2.2 不删除任何现有提示词内容，助手行为不变。
- **3.1 是唯一有回退需求的任务**：瘦身即"把规则从 `stableSystemPrompt` 移到内置技能"。回退方式是把对应条目移回数组，内置技能文件保留不影响。因此 3.1 必须单独提交，不与其他改动混提。
- **用户数据兼容**：技能目录初次运行时不存在属于正常情况，按空清单处理，不报错、不自动创建示例。
- **能力版本**：`load_assistant_skill` 是全新能力，版本从 1 开始，不涉及旧契约迁移。

## 八、风险控制

| 风险 | 控制方式 |
|---|---|
| 恶意技能声称"用户已授权" | 技能层标 `untrusted_user`，系统提示词硬规则拒绝技能提权；写入运行时测试 |
| 技能索引层撑爆上下文 | `description` ≤200 字符 + 技能总数上限 + 索引层独立 `maxTokens` 预算 |
| 索引层被字符截断导致半条描述 | 索引层按**整条技能**丢弃，不做字符截断 |
| zip 路径穿越 / 符号链接 / 压缩炸弹 | 复用 `validatePackagePath` 模式 + 单文件/总量/文件数三重限额 + 拒绝符号链接与嵌套压缩包 |
| frontmatter 解析引入 YAML 攻击面 | 不引依赖，只解析 `key: value` 严格子集，非法直接拒绝安装并报出行号 |
| 3.1 瘦身后模型遵循度下降 | 3.1 单独提交；瘦身前后各跑一次 `test:assistant-production`；用户实机复测代表性任务 |
| 路由/模型没想到去加载技能 | 索引层描述里明确"需要执行某领域操作前先加载对应技能"；3.1 的通用流程条目里保留一条引导 |

## 九、全局开发约束

- 遵守 `AGENTS.md` 与 `docs/rules/`：新增能力读 `assistant-capability.md` + skill `henji-application-capability`；新增设置分区读 skill `henji-ui-surface`；改主进程读 `electron-desktop.md`；收尾读 `testing.md`。
- 禁止在 `src/components/ui/primitives.tsx` 以外写原生表单元素；禁止硬编码颜色。
- 新文件优先 ≤400 行，>500 行禁止继续膨胀。
- 每个任务独立 Git 提交，提交信息用中文。
- 技能正文本身用中文书写（内置技能面向本应用用户）。

## 十、最终验收条件

- [ ] 内置与用户两个目录的技能都能被扫描、解析、去重（用户覆盖内置）并进入索引。
- [ ] 模型能通过 `load_assistant_skill` 拿到正文；未加载时上下文里只有名称与描述。
- [ ] 带 `references/` 的标准技能能完整安装并两级加载；非法引用路径被拒绝。
- [ ] frontmatter 带 `allowed-tools` 等未知字段的外部标准技能能正常安装，且这些字段不产生任何效果。
- [ ] 技能正文中的提权、免审批类语句不生效，有测试覆盖。
- [ ] 非文本文件在安装阶段被拒绝且明确报出，zip 穿越/符号链接/超限被拒绝。
- [ ] 设置面板可以列出、安装、删除、启停技能，内置项不可删除。
- [ ] `stableSystemPrompt` 条目数由 36 降到约 15，且安全相关条目一条不少。
- [ ] `npm run test`、双端 TypeScript、`npm run lint`、`npm run check:assistant-capabilities` 全部通过。
- [ ] `npm run electron:build` 与 `npm run electron:smoke` 通过，内置技能在打包产物中可被读取。
