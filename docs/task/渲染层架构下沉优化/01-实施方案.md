# 渲染层架构下沉优化 · 实施方案

## 当前情况

### 已经做对的部分

以下核心链路已正确通过 IPC 隔离，本次不涉及：

- **AI 生成主链路**：`GenerationService → aiRuntime → IPC → electron/main/services/ai-runtime/`
- **数据库**：所有 SQL 通过 `window.henjiNative.db` 走 IPC
- **文件系统**：通过 `window.henjiNative.fs` 访问，无裸 `fs` 调用
- **LLM 流式对话**：走 `llm:chatStream` IPC，主进程发起请求
- **密钥管理**：safeStorage + keystore，密钥存主进程

### 现有问题

#### 问题一：LLM 模型发现在渲染层发 HTTP 请求

- 文件：`src/services/llm/llmDiscoveryService.ts:76`
- 调用方：`src/components/Settings/sections/LlmSettingsSection.tsx:186`
- 现状：渲染层从 keystore 拿到 API key → 传给 `fetchOpenAiCompatibleModels` → 渲染层用 `nativeFetch` 发 GET /v1/models
- 问题：API key 在渲染进程内存中出现；无缓存；缺乏超时/重试控制
- 已有基础：`electron/main/services/llm/runtime.ts` 中有完整的 LLM 请求能力和 keystore 调用，`llm-runtime.ts` IPC handler 可扩展

#### 问题二：图片压缩在渲染层用 Canvas + Pica

- 文件：`src/utils/save/uploads.ts:324`（`ensureCompressedJpegBytesWithPica`）
- 调用方：`saveUploadImage()`，用于用户上传图片时的压缩
- 现状：在渲染线程创建 Canvas、用 Pica 高质量缩放、toBlob 输出，全程阻塞渲染
- 问题：4K 图片处理可能卡顿 UI 数秒；无进度反馈；内存峰值高
- 已有基础：`electron/main/services/image/ops.ts` 已有 sharp，有 `persistImageSource`、`prepareNodeImageSource` 等函数；`electron/main/ipc/image.ts` 已有完整 IPC 注册

#### 问题三：视频缩略图在渲染层用 HTML5 Video

- 文件：`src/utils/videoProcessing.ts:26`（`generateVideoThumbnail`）
- 调用方：`useVideoUpload.ts:89`、`useReeditContent.ts:67`
- 现状：创建隐藏 `<video>` 元素 → seek 到指定时间点 → Canvas 截帧，有 200ms 硬编码延迟，对某些编码格式不稳定
- 问题：比 ffmpeg 慢且不稳定；占用渲染线程
- 已有基础：`electron/main/services/video/ops.ts` 已有 ffmpeg 集成（`execFileAsync` 封装），`electron/main/ipc/video.ts` 已注册 `readVideoInfo`、`trimVideoSource`、`compressVideoToFit`

#### 问题四：AI 轮询任务状态不持久

- 文件：`electron/main/services/ai-runtime/task-registry.ts`
- 现状：只有内存中的 AbortController 映射，无 SQLite 持久化
- 问题：渲染层重载（崩溃/刷新）后，若主进程的轮询在此期间完成，结果无法传回；用户需要手动重新轮询
- 已有基础：`electron/main/services/db.ts` 已有 better-sqlite3 封装；`continuePollingTask.ts` 中 `serverTaskId` 已保存在任务记录里，用户可以手动触发重试

---

## 总体解决思路

每个问题的解决路径统一为：

1. **主进程新增服务函数**（`electron/main/services/`）
2. **注册 IPC handler**（`electron/main/ipc/`）
3. **扩展 preload bridge**（`electron/preload/api.ts` 类型 + `electron/preload/index.ts` 实现）
4. **渲染层调用方改为 IPC 调用**（`src/` 中的服务或工具函数）

---

## 阶段划分

### 第一阶段：安全修正（优先级最高）

**目标**：LLM 模型发现请求完全在主进程执行，API key 不再经过渲染层

任务 1.1 独立可并行启动。

### 第二阶段：媒体处理下沉

**目标**：图片压缩和视频缩略图在主进程用 sharp/ffmpeg 完成，渲染层只发 IPC 请求

任务 2.1 和 2.2 彼此独立，可以并行执行。

两个任务的输入处理策略一致：
- **用户从文件选择器或拖拽上传的文件**：通过 `webUtils.getPathForFile(file)` 拿到本地路径，传路径给主进程
- **无本地路径的 Blob**（如从画布生成的图片）：先写入临时文件再调用主进程，或保留现有渲染层处理作为后备

### 第三阶段：任务可靠性加固（可选）

**目标**：轮询结果短暂写入 SQLite，渲染层重载后可查询并恢复

复杂度较高，且当前用户可通过手动重试缓解，优先级低于前两阶段。

---

## 技术约束

- 主进程新增函数不超过 400 行（符合项目体积治理）
- 新增 IPC handler 走 `registerIpcHandler` 统一注册（见 `electron/main/ipc/registry.ts`）
- preload 扩展遵循 `contextIsolation: true`，不直接暴露 Node API
- 不新增 `any` 类型，新增导出函数补齐返回类型
