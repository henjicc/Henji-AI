## 机制设计

- 当前内容基线即现有版本：五种文档与多数文件为 v1，图片工作副本 v3、设置 v13、引导 v2、主题分享 v2、SQLite 账本 v18。没有重写剪辑/画布/图片等业务内容结构；缺少版本的库新增 version 外壳，组件说明头和 PNG/字幕记录新增版本字段。
- 文档类型以 descriptor.migrations 为单一链入口；其他 JSON 以 formatMigrations 为入口。键 N 严格代表 N→N+1，执行器先确认整链存在、隔离原输入、逐步运行、最终校验当前 schema。缺迁移、未来版本、迁移失败、结构不匹配、JSON 损坏与备份失败分别使用结构化错误。
- 文件存储升级前复用 no-overwrite/atomic-file 原语。小 JSON 使用实际解析的原字节/文本快照；归档流式复制，摘要寻址、校验已有备份内容、独占发布和 fsync，不覆盖历史备份。位置是原目录 .henji/backups，原件位于 .henji 时复用该目录的 backups。localStorage/SQLite 设置值先写独立备份键。备份失败不执行迁移。
- 读取升级只返回内存结果，原件首次明确保存时才改写。Zustand guarded storage 防止 hydration 的自动迁移写入；设置、主题、引导、默认模型、画布参数、创作库、导出预设、音色和媒体授权的失败记录不会在后续操作中被空值覆盖。
- SQLite 只复用原有 SCHEMA_MIGRATIONS 和事务运行器，登记记录 schema，不新增第二套账本或数据迁移。共享 schemaVersions 保证账本与登记表用同一版本来源。
- 代码目录本身是作者 .ts 源码：格式解释由版本引用的 apiVersion/languageVersion 及父剪辑或代码资产版本负责；组件作品 version 和新 schemaVersion 分开。未来只改变引用的持久 DTO、路径解释或哈希算法时，应同时升级所属文档/资产的格式，并迁移嵌套引用；语言语义改变还需升级实际语言/API。不能把组件作品发布号当格式号。
- t88/t89 以前同为 kindVersion=1 的内联 source 剪辑明确登记为开发期不支持；打开时识别为旧格式，不尝试恢复、迁移或静默转为文件引用。设置旧版本和过去没有样本的开发版本也显式记录豁免。仅复用已有主题 v1→v2，不新增旧开发数据迁移。
- 错误仍经现有文档/服务错误与提示路径传播，中英文文案在 errors.json；版本、字段和备份位置进入现有日志。没有新 UI、IPC、日志文件或助手工具。

## 门禁与样本

检查：npm run check:persistence-compat。显式登记：npm run persistence:baseline -- --dev-break <id> --reason "具体原因"；多个格式重复传 --dev-break。确无历史样本时额外 --waive-before，仅豁免当前版本之前，当前样本不能豁免。记录 UTC 时间、格式、版本、原因、前后指纹、豁免版本及支持下限；开发期完整删除功能另记 retired，发布后拒绝此方式。

正常升版本需完整迁移和 v1..vN 样本（接入时已有显式豁免保留），普通 baseline 更新不能绕过同版本结构变化。releasedCompatibility=true 后拒绝所有 dev-break，不因普通检查通过就允许破坏兼容。CI 直接运行相同门禁；脚本的 6 项精确单测接入既有 test:validation-tools。

黄金样本共 45 个：37 个 JSON（36 个当前格式及主题既有 v1），8 个正式归档/源码/PNG。剪辑覆盖代码文件引用及参数、效果、关键帧、字幕翻译、转场和全能调色。图片覆盖正式文档头、工作副本、图层包和 .henjiimg；项目包由正式 exporter 创建并通过真实 importer 打开，源码摘要和正式编译器校验均保留。JSON 与二进制作者脚本都拒绝覆盖已有样本，历史黄金样本应永久保留原字节。针对 Windows autocrlf 的精确测试曾失败，修正本任务尚未发布的源文件字节，并新增仅针对样本的 .gitattributes -text；未执行 Git 写操作。

## 成熟方案选型

- 已查证 Zod 官方 JSON Schema 文档：https://zod.dev/json-schema 。仓库现有 Zod 4.4.3 原生 z.toJSONSchema 支持输入/输出视图，直接使用，避免增加依赖。
- 对比 zod-to-json-schema 官方仓库：https://github.com/StefanTerdell/zod-to-json-schema 。该方案已弃用、主要面向 Zod 3，Zod 4 推荐原生方案，因此不采用。
- 指纹对结构稳定排序，required/enum 顺序归一化，联合分支与元组顺序保留，用现有 Node/WebCrypto SHA-256；不比较源码文本，不访问私有 Zod 内部结构，不静默跳过无法表示的 schema 类型。
- 归档、原子发布、SQLite 和 Zustand 都复用现有成熟实现，仅补契约适配。无新第三方依赖、锁文件变更或自研归档/数据库迁移器。
- 结构指纹无法证明任意 refine、动态 JSON 扩展、单位/算法语义或 SQLite DDL；这些仍须主动升版本、补关键字段断言/账本。已有技术预算保留，不新增素材/序列/文件夹数量上限；并修正授权保存既有 100 条截断为无数量截断。

- 只保护今后的机制，不恢复 t88/t89 以前开发项目；不读取不支持的旧设置、无版本库数组和配置。显式 devBreaks 是产品选择证据，总管理者应核对原因并保留历史。
