# t114 热播放单帧耗时波动

接 t113。真实 Electron 里 complex-to-simple 热播放已零掉帧，但单帧“求值 + 绘制”p95 在不同轮次间波动：t112 为 17–24ms，t113 三轮为 27.5 / 36.3 / 37.8ms，中位数稳定在约 12ms。尾部偶发长帧说明有与内容无关的开销，余量不足时（更复杂的内容、较弱的显卡）会变成掉帧。

## 要做

1. **先归因，再修。** 在真实 Electron（隔离资料目录，复用 `video-edit-code-performance` 巡检场景）对长帧（超过中位数 2 倍）逐帧拆分：Worker 内求值、绘制录制、GPU 提交到完成、帧回传（ImageBitmap/纹理转移）、主线程合成与呈现、等待调度的间隙。同时记录对应时刻的 GC（渲染进程与 Worker 的 `performance.measureUserAgentSpecificMemory` 不可用时用 Chromium trace 的 V8.GC 事件或 `--js-flags=--trace-gc`）、缓存淘汰、离屏会话/预热任务是否与播放并发。
2. 给出长帧的来源占比（例如“60% 与 Worker 内 minor GC 重合”）。证据不足时扩大样本，不凭猜测下结论。
3. **按根因修。** 可能的方向仅供参考，以实测为准：每帧临时对象（数组、闭包、包围盒、uniform 暂存）改为复用以减少 GC；预热、离屏会话等后台工作在节目播放时让路；GPU 提交与回读的同步等待改为流水线；缓存淘汰挪出帧内路径。
4. **验收**（同机、同场景、同口径，至少 5 轮）：
   - 给出改前改后每轮的中位数、p95、p99、最长帧和掉帧数。
   - 目标：p95 各轮均不超过 20ms，且轮间差异明显收窄；做不到时说明剩余长帧的来源和为什么不能在本任务内消除。
   - 像素不变，热播放与首轮播放均保持零掉帧，t113 的取帧数字不回退。

## 工作方式

独立 worktree，自己 `npm ci`（禁止 junction），只改不提交。允许启动隔离资料目录的 Electron（`npm run electron:bundle` 后用 ui:tour 的 `--profile temporary`），禁止使用或改动用户真实资料目录，禁止结束非本 worktree 的 Electron 进程，同时最多一个 Electron 测试实例。本机同时可能有其他 Electron 在跑，测量时记录系统负载，异常轮次重测。验证：对应测试、涉及时 GPU 测试、最终各跑一次两套 tsc、改动文件 eslint、`npm run check:main-imports`、`npm run check:dependency-graph`。

## 结果（2026-10-16 合并）

- 归因（前后各 900 个热播放样本，长帧 = 超过本轮中位数 2 倍）：长帧 152 → 95；与 Worker GC 重合 20% → 16%；GPU 完成后额外等待超过 10ms 的 7 → 0。剩余长帧主要是复杂画面前半段的内容求值与首次 GPU 完成等待；Worker 排队、帧回传、主线程通知、缓存清理都在 0.3ms 内，播放期间未见预热或离屏渲染并发。
- 修复：v3 渲染内部已等待队列完成，外层又挂一次完成回调，既多一次往返，又会把下一帧 CPU 工作记到上一帧，现已去掉；执行计划编译时分配统计槽位，减少每帧 Map 操作；新增默认关闭的逐帧分段取证。
- 五轮热播放：最长帧 38–49ms → 25–28ms，p99 轮间跨度 23.4 → 3.9ms，零掉帧，抽样帧零像素差，取帧准备 60ms 不回退。p95 为 21–24ms，**未达 20ms 目标**；改前改后系统负载不同，数字变化不全归因于代码。
- 继续压 p95 需要优化执行器或绘制批处理，不能靠删同步或改计时口径。
