## 一、巡检方法（本次结论的来源，可随时重跑）

项目已有 `scripts/lib/electronLaunch.cjs`，它支持两种启动方式，通过环境变量切换：

- 默认：spawn Electron + `chromium.connectOverCDP()`
- `HENJI_SMOKE_USE_ELECTRON_API=1`：`_electron.launch()` + `app.firstWindow()`

本次巡检使用 **Playwright Electron API**（`_electron.launch()`），因为它额外提供 `app.browserWindow(page)`，可以在主进程侧直接控制真实 `BrowserWindow`（`unmaximize()` / `setSize()` / `center()`），这是精确复现「默认尺寸」和「最小支持尺寸」的唯一可靠方式。

最小可用骨架：

```js
const { _electron: electron } = require('playwright')
const electronPath = require('electron')

const app = await electron.launch({
  executablePath: electronPath,
  args: [`--user-data-dir=${隔离目录}`, 'out/main/index.cjs'],
  cwd: 项目根目录,
  env: { ...process.env, ELECTRON_DISABLE_SECURITY_WARNINGS: 'true' },  // 必须删掉 ELECTRON_RUN_AS_NODE
})
const page = await app.firstWindow({ timeout: 40000 })
const win = await app.browserWindow(page)          // 真实 BrowserWindow 句柄
await page.waitForFunction(() => Boolean(window.henjiNative))  // 等 preload 桥就绪
await win.evaluate((bw) => { bw.unmaximize(); bw.setSize(1440, 900); bw.center() })
```

踩过的坑，重跑时直接避开：

1. **必须先 `unmaximize()` 再 `setSize()`**，否则窗口保持最大化，截出来永远是屏幕尺寸。
2. **必须等 `window.henjiNative`**，只等 `button` 选择器会在初始化中途截图。
3. **必须用隔离 userData**（`--user-data-dir` + 覆盖 `LOCALAPPDATA`/`APPDATA`），否则会读写用户真实数据库和密钥。
4. **`Escape` 关不掉 `UiModal`**（本次发现的缺陷之一）。在任务 1.1 修完之前，脚本里关闭弹窗要点真实关闭按钮或遮罩，不能靠 Esc，否则后续所有截图都会被残留的弹窗污染。
5. **窗口默认尺寸是 1200×800，最小是 960×640**（`electron/main/window.ts:26-29`），最小尺寸档要用 960×640。
6. `performance.now()` 在 Electron 里被粗化到 0.1ms，单次测量会得到 0；性能测量必须循环上百次取累计值。

固化这套脚本是任务 5.1。

### P4 性能（本次未复现，需继续定位）

用户报告：「生成页面存在动态进度条时，拖动智能助手窗口会出现明显延迟」。

**实测结果（1440×900 真实窗口，rAF 帧计时 + longtask observer）：**

| 场景 | 平均帧间隔 | p90 | p99 | >33ms 帧数 |
|---|---|---|---|---|
| 空历史 + 拖动助手 | 16.7ms | 16.7 | 24.1 | 0 |
| 30 张仿真任务卡（静态）+ 拖动 | 16.7ms | 16.8 | 17.2 | 0 |
| 30 张卡 + 进度条持续跑 width 过渡 + 拖动 | 16.7ms | 16.8 | 21.4 | 0 |
| 30 张卡 + 进度条改 transform + 拖动 | 16.7ms | 16.8 | 21.0 | 0 |

**已排除的怀疑方向：**

- ~~IPC 过于频繁~~：轮询默认间隔 3000ms（`electron/main/services/ai-runtime/progress.ts:272`），一个任务每 3 秒一次，不可能是瓶颈
- ~~状态放在过高层级~~：进度已经拆到 `generationTaskProgressStore` 独立 store，订阅面收敛到叶子 `TaskCard`
- ~~拖拽本身实现差~~：`useAssistantPanelInteraction` 已经是 rAF 批量 + 直接写 style，不走 React 状态
- ~~改 padding 导致整树重排~~：实测 200 次强制同步重排累计 5ms，单次 0.03ms
- ~~不可见工作区仍在更新~~：非激活 Tab 用 `hidden` 类隐藏，实测隐藏子树节点数为 0（懒加载未访问过的工作区根本没挂载）

**仍然成立的怀疑方向（任务 4.1 要验证的）：**

1. 仿真卡是纯 DOM，**没有真实 `TaskCard` 的 React 订阅、图片解码、媒体元素**。真实历史里每张卡有最多 4 个 `<img>`（`henji-media://` 协议）+ 视频元素，图片解码和光栅化的成本没有被覆盖到。
2. 真实生成中会同时有多个任务在轮询，每次进度更新触发一次 2800ms 的 width 过渡，多条叠加时的持续重排成本没有被覆盖到。
3. 本机 GPU/分辨率与用户实际环境不同（本次 dpr=1.5；用户是 3840×2160 @150%，逻辑 2560）。

**复现方式（已定，见 `重要记录.md` 记录 007）：** 挂载用户真实开发实例，不用隔离环境。

```bash

$env:HENJI_ELECTRON_REMOTE_DEBUGGING_PORT=9222; npm run electron:dev
```

`electron/main/index.ts:54-56` 已支持该环境变量。之后用 `chromium.connectOverCDP('http://127.0.0.1:9222')` 挂载。**生成由用户自己发起**（不花冤枉钱），我只做只读测量（滚动、拖拽、截图、量帧率），不做任何写操作。

## 四、总体解决思路

**顺序是有意的：先组件、再布局、再视觉、最后性能。**

理由：排在前面的每一步都会减少后面的工作量。比如 `UiEmpty` 收口（1.3）做完，2.x 的布局任务就不用再逐个处理空态；`Toggle` 改完（1.2），3.1 的选中态统一就少一类形态要处理。反过来先做视觉收敛，会在组件改动后重做一遍。

每个阶段的收敛策略：

- **第一阶段**：只改 `src/components/ui/` 下的公共组件本身 + 必要的调用点适配。判据是"改完之后，业务代码即使什么都不做也变好了"。
- **第二阶段**：改布局参照系与信息架构，不改视觉样式。判据是"截图里的遮挡、错位、密度失衡消失"。
- **第三阶段**：把令牌真正消费起来。这是量最大的一阶段，允许分批提交，但每批要能独立验证。
- **第四阶段**：先复现再改。**没有复现出来的性能问题不允许"顺手优化"**——上一轮 `content-visibility` 就是没有实测就上优化，最后造成滚动闪烁被回退。
- **第五阶段**：把方法固化，让后续任何 UI 改动都能低成本重跑巡检。

9. 同属性叠类 = 静默失效：两个工具类落在同一 CSS 属性上时，胜负看 Tailwind 产物顺序而非 className 顺序。优先写互斥三元。
10. 透明度修饰符只能用 Tailwind 刻度值（步进 5）；`bg-black/72` 这类不生成任何 CSS。
11. **布局定位不许藏在 CSS 里**（本次新增，见 `重要记录.md` 记录 008）：`position`/`top`/`left`/`right`/`bottom`/`z-index` 必须写在组件 className 上；样式表只做它文件名承诺的事；全局 CSS 变量只能放 `src/index.css`。例外要在 CSS 里就地写注释说明理由。

## 八、每个任务的标准检查动作

改动后按需执行，不要每次都跑 `electron:build`：

```bash
npm run lint
npm run check:colors
npm run check:surface:strict
npx tsc --noEmit
npm test
```

涉及 Electron 主进程时补：

```bash
npx tsc -p tsconfig.electron.json --noEmit
npm run electron:smoke
```

需要看真实渲染效果时（会重新构建，较慢）：

```bash
npm run electron:build && npm run check:ui-visual
```
