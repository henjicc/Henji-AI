### 图片高度问题（已实测确认）

`TaskCard` 对**非成功状态**已经预留了固定高度（`TaskCard.tsx:160-164` 注释写得很清楚）：

```ts
const RESULT_SLOT_CLASS = `h-64 rounded-lg ${UI_INSET_SURFACE_CLASS}`
// h-64 必须保留：结果区高度固定，生成过程中状态切换才不会让整条历史列表跳动。
```

但**成功态完全没有预留**：

```tsx
<img
  src={url}
  loading="lazy"
  decoding="async"
  className="w-full h-auto block cursor-grab ..."
/>
```

`h-auto` + `lazy` = 高度到解码完成才确定。后果是**两次跳动**：

1. 生成成功那一刻：从固定 `h-64` 切成自然高度
2. 往回滚时图片重新进入视口解码：从 0 撑到实际高度

第 2 条正是上一轮遗留、当时提了两个方案但没定的问题（上一轮修掉的 `content-visibility` 是第一个来源，这是第二个）。

### 上一轮的失败教训（必读）

`styleTokens.ts:91-104`：

> `content-visibility:auto` + `contain-intrinsic-size:auto 420px` 会造成明显的滚动闪烁，已移除。
> 原因：`contain-intrinsic-size` 是**固定**占位高度，而任务卡高度差异极大（排队态约 120px，多图结果可到 800px）。往回滚时占位高度被换成真实高度，视口上方内容尺寸突变，滚动锚定晚一帧补偿，表现就是"闪一下又跳回原位"。
> 结论：`content-visibility:auto` 只适合行高基本一致的长列表。高度差异大的列表要么老老实实虚拟化，要么什么都不做。

**这条教训直接决定技术选型：如果做虚拟化，必须用真正支持不定高的方案（`react-virtuoso`），不能再用任何基于固定估值的方案。**

## 实施方案

### 第一部分：图片高度预留（无条件做）

**已定方案：保持自然高度的视觉，用 `aspect-ratio` 预留空间。**

理由（已与用户确认）：固定槽位 + `object-contain` 会让竖图周围出现大片留白，观感反而变差。当前自然高度的观感是好的，要修的只是"高度到解码才确定"这一点。

```tsx
// 外层包一个按比例预留的盒子，img 填满它
<div style={{ aspectRatio: `${w} / ${h}` }}>
  <img className="w-full h-full block ..." />
</div>
```

**宽高比数据来源，按优先级：**

1. `GeneratorOptions.size`（`src/workspaces/GenerationWorkspace/types.ts:9`）——请求时的尺寸字符串。如果能解析出 `1024x1024` 这种形式就直接用。
2. 解析不出来时（比如「智能 / 1K」这类语义档位），在图片首次 `onLoad` 时读 `naturalWidth`/`naturalHeight` 并持久化到任务记录，第二次起就有了。
3. 两者都没有时（老数据）：不设 `aspect-ratio`，退回当前行为。**必须优雅降级**，不能让老历史记录显示异常。

同时处理"生成成功那一刻从 `h-64` 切自然高度"的跳动：成功后如果已知宽高比，让 `h-64` 的槽位直接过渡到目标比例，或者干脆在已知比例时让排队/生成态也用同样的比例槽位。

### 第二部分：长列表虚拟化（条件执行）

**先读任务 4.1 的执行记录再决定：**

- 4.1 定位到根因就是长列表渲染 → 必做
- 4.1 定位到别的根因 → 降级为预防性优化，要有明确收益数据才做
- 4.1 复现失败 → **标记为待定，不做**

如果做，用 `react-virtuoso`（原生支持不定高，项目已有使用参考）。需要特别处理：

1. 滚动位置保持：切 Tab 往返、新任务插入顶部时不跳
2. 筛选/搜索时的重建不闪
3. 与第一部分的 `aspect-ratio` 配合——有了确定的高度，Virtuoso 的测量会更稳

**不要做的**：不要再试 `content-visibility` / `contain-intrinsic-size`；不要自己手写虚拟化；不要在没有实测收益的情况下引入虚拟化（虚拟化本身有测量和 DOM 回收成本，条数少时可能更慢）。
