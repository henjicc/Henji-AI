## 当前情况

### 用户报告

> 生成页面存在动态进度条时，拖动智能助手窗口会出现明显延迟。

### 本次巡检的实测结果（未复现）

1440×900 真实 Electron 窗口，rAF 帧计时 + `PerformanceObserver('longtask')`，每场景连续拖动 70 步：

| 场景 | 平均帧间隔 | p90 | p99 | max | >33ms 帧数 |
|---|---|---|---|---|---|
| A 空历史 + 拖动助手 | 16.7ms | 16.7 | 24.1 | 24.1 | 0 |
| B 30 张仿真任务卡（静态）+ 拖动 | 16.7ms | 16.8 | 17.2 | 17.2 | 0 |
| C 30 张卡 + 进度条持续跑 width 过渡 + 拖动 | 16.7ms | 16.8 | 21.4 | 21.4 | 0 |
| D 30 张卡 + 进度条改 transform + 拖动 | 16.7ms | 16.8 | 21.0 | 21.0 | 0 |

**全部稳定 60fps，0 次掉帧，无 longtask。C/D 是对照实验——进度条改不改都不掉帧。**

### 已排除的怀疑方向（附证据）

| 怀疑 | 结论 | 证据 |
|---|---|---|
| IPC 过于频繁 | **排除** | 轮询默认间隔 3000ms（`electron/main/services/ai-runtime/progress.ts:272`），单任务每 3 秒一次事件 |
| 状态放在过高层级 | **排除** | 进度已拆到 `src/stores/generationTaskProgressStore.ts` 独立 store，订阅面收敛到叶子 `TaskCard`；该文件顶部注释明确记录了这次治理的动机就是本问题 |
| 拖拽实现本身低效 | **排除** | `useAssistantPanelInteraction.ts:282-305` 已是 rAF 批量 + 直接写 DOM style，不经过 React/Zustand |
| 改 padding 导致整树重排 | **排除** | 实测 200 次强制同步重排累计 5ms，单次 0.03ms（有卡/无卡一样） |
| 不可见工作区仍在更新 | **排除** | 非激活 Tab 用 `hidden` 隐藏；未访问过的工作区因懒加载根本没挂载，实测隐藏子树节点数为 0 |
| 阴影/模糊/透明增加渲染负担 | **部分排除** | 助手面板本身不用毛玻璃；拖动时未观察到合成开销异常 |

### 仍然成立的怀疑方向（本任务要验证的）

1. **真实 `TaskCard` 的成本没被覆盖**。仿真卡是纯 `<div>`，真实卡片有：最多 4 个 `<img src="henji-media://...">`（图片解码 + 光栅化）、视频任务的 `<video>`、React 订阅与子组件（`TaskActionIcons`/`TaskPrompt`/`MediaGrid`）。
2. **多任务并发进度**。真实生成可能同时有多个任务轮询，每次更新触发一次 2800ms 过渡，多条叠加的持续重排成本未覆盖。
3. **环境差异**。本次 dpr=1.5；用户是 3840×2160 @150%（逻辑 2560，dpr 1.5）。高分辨率下光栅化面积大得多。
4. **历史条数**。本次只到 30 条，上限默认 50、可设到 500。

## 实施方案

**挂载用户的真实开发实例测量，不用隔离环境，也不由我发起生成。**

`electron/main/index.ts:54-56` 已经支持通过环境变量开启远程调试端口：

```ts
const remoteDebuggingPort = process.env['HENJI_ELECTRON_REMOTE_DEBUGGING_PORT']
if (remoteDebuggingPort) {
  app.commandLine.appendSwitch('remote-debugging-port', remoteDebuggingPort)
}
```

所以流程是：

1. **用户**用带端口的方式启动自己的开发实例：
   ```bash
   $env:HENJI_ELECTRON_REMOTE_DEBUGGING_PORT=9222; npm run electron:dev
   ```
2. **我**用 `chromium.connectOverCDP('http://127.0.0.1:9222')` 挂上去
3. **用户**自己点生成（同时发 3-5 个）
4. **我**在生成过程中驱动拖拽并测量

这样做的好处：
- 真实历史记录（重 DOM）、真实 API Key、真实分辨率与缩放
- **生成由用户发起，不花冤枉钱，我也不会误点删除/清空**
- 我全程只读：滚动、拖拽、截图、量帧率

**明确不做**：不用 `isolateUserData: false` 直接跑构建产物读真实 profile——那样自动化会碰真实数据，风险不必要。

### 分三步，每步都可能提前得出结论

**第一步（不需要用户在场）**：先用隔离环境把条件推到极限——注入 200 条带真实本地图片的假历史 + 同时驱动 10 个任务的进度 + dpr 调到 2。如果这里就复现了，后面两步可以省。

**第二步（需要用户配合）**：按上面的 CDP 挂载流程，在用户真实环境复现。

**第三步（复现后）**：用 CDP Tracing 的 `Layout` / `UpdateLayoutTree` / `Paint` / `RasterTask` / `FunctionCall` 耗时分布定位到具体环节，针对性修复，同口径给出前后对比。

**可能的修复方向（复现后才决定，不要提前做）**：
- 长列表虚拟化（任务 4.2）
- 拖拽期间给工作区加 `pointer-events: none` 并暂停进度过渡
- 拖拽期间对工作区容器加 `contain: layout` 限制重排范围
- 图片 aspectRatio 预留避免解码后重排（这一条在任务 4.2 里本来就要做）

## 需要用户手动验证的点

执行到第二步时需要用户配合：

1. 用带调试端口的方式启动开发实例：
   ```bash
   $env:HENJI_ELECTRON_REMOTE_DEBUGGING_PORT=9222; npm run electron:dev
   ```
2. 我挂上去之后，你同时发起 3-5 个生成任务（挑便宜的模型就行）
3. 生成过程中（进度条在动时）打开智能助手，拖动它的左边缘调整宽度
4. **告诉我卡顿具体是哪一种**——这三种对应完全不同的根因：
   - 「拖动跟不上鼠标」→ 主线程被占，pointermove 处理不过来
   - 「进度条一跳一跳」→ 过渡被打断，是渲染管线的问题
   - 「整个界面僵住一下」→ 有 longtask，可能是同步 IPC 或大批量状态更新
5. 顺便确认一下你的显示设置：分辨率和缩放比例（右键桌面 → 显示设置）
