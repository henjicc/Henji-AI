## 记录 001：本次巡检采用 Playwright Electron API 而不是 CDP 连接

- 日期：2026-07-27
- 状态：已确定
- 背景：项目原有的 `scripts/lib/electronLaunch.cjs` 默认走 `spawn` + `chromium.connectOverCDP()`。本次需要精确复现「默认窗口尺寸」和「最小支持尺寸」两档，还需要在窗口最大化时先取消最大化。
- 最终决定：本次及后续 UI 巡检统一走 `_electron.launch()` + `app.firstWindow()`（启动器已支持，通过 `HENJI_SMOKE_USE_ELECTRON_API=1` 切换）。
- 选择原因：只有 Playwright Electron API 提供 `app.browserWindow(page)`，能拿到真实 `BrowserWindow` 句柄在主进程侧调 `unmaximize()` / `setSize()` / `center()`。纯 CDP 只能改渲染层视口，改不了真实窗口，测不出最小尺寸下的真实布局。
- 影响任务：5.1（脚本固化）、所有需要截图验证的任务

## 记录 002：性能问题未复现，不做无依据的优化

- 日期：2026-07-27
- 状态：已确定
- 背景：用户报告「生成页面存在动态进度条时，拖动智能助手窗口会出现明显延迟」。本次在真实窗口实测四种场景（空历史 / 30 张仿真卡 / 30 张卡+width 进度条 / 30 张卡+transform 进度条），全部稳定 60fps、0 次掉帧、无 longtask。同时排除了 IPC 频率（3s 轮询）、状态层级过高（已拆独立 store）、拖拽实现（已 rAF 批量 + 直接写 style）、padding 重排（单次 0.03ms）、不可见工作区更新（未挂载）五个方向。
- 最终决定：**在任务 4.1 复现成功之前，不做任何性能优化改动。** 任务 1.4 的 `ProgressBar` 改 `transform` 是"符合项目自己的动效规范"，不是"修复卡顿"，记录和提交信息里都不能写成性能修复。
- 选择原因：上一轮 `content-visibility` 优化就是在没有实测支撑的情况下上线的，结果造成滚动闪烁被完整回退（复盘见 `src/components/ui/styleTokens.ts:91-104`）。没有复现就没有验证修复是否有效的手段，改了也只是换一种猜。
- 影响任务：1.4、4.1、4.2

## 记录 003：`content-visibility` 方案已被否决，不再尝试

- 日期：2026-07-27（沿用上一轮结论）
- 状态：已确定
- 背景：上一轮 `UI设计系统统一` 中曾用 `content-visibility:auto` + `contain-intrinsic-size:auto 420px` 跳过生成历史中视口外卡片的布局，造成明显滚动闪烁后已移除。
- 最终决定：生成历史列表如果要做长列表优化，必须用真正的虚拟化（`react-virtuoso`，支持不定高），不得再使用 `content-visibility` 或任何基于固定高度估值的方案。
- 选择原因：`contain-intrinsic-size` 是固定占位高度，而任务卡高度从 120px（排队态）到 800px（多图结果）差异极大。往回滚时占位高度换成真实高度，视口上方内容尺寸突变，滚动锚定晚一帧补偿，表现就是"闪一下又跳回原位"。这是方案的固有缺陷，不是参数没调好。
- 影响任务：4.2

## 记录 005：去掉设置弹窗底部的「确定」按钮及整条底部区域

- 日期：2026-07-27
- 状态：已确定（用户拍板）
- 背景：设置项全部即时生效，底部的「确定」实际语义是「关闭」。它是一个 accent 实心按钮，独占一条约 110px 高的区域，在 960×640 窗口下弹窗几乎撑满屏幕的情况下尤其浪费。
- 最终决定：去掉「确定」按钮，并连带去掉整条底部容器。关闭路径保留三条：右上角 ×、Esc（任务 1.1 补齐）、点遮罩。
- 选择原因：一个语义是"关闭"的按钮不该用主动作的视觉权重；三条关闭路径已经足够；省下的 110px 直接改善小窗口下的压迫感。
- 前置条件：执行时必须确认没有任何设置项依赖"点确定才提交"。如果有，那个设置项本身要改成即时生效，**不能靠保留按钮兜底**。
- 影响任务：2.2

## 记录 006：模型显示与管理保留「开启=高亮」语义，只把高亮从整行收回到开关

- 日期：2026-07-27
- 状态：已确定（用户确认设计意图后修正方案）
- 背景：我最初把「设置 → 模型」整页实心蓝底判为"常态误用强调色"，建议改成中性表达。用户澄清这是有意设计：和「设置 → 界面」的布尔项同一思路，开启时高亮、文案「显示中」，关闭时不高亮、文案「已隐藏」。
- 最终决定：**保留这个语义映射**。要改的是高亮的**面积**——从整行（约 600×36）收回到开关控件本身（约 44×24）。文案保留「显示中 / 已隐藏」。
- 选择原因：语义映射本身是对的，问题出在同一个语义用了差 15 倍的视觉面积。整行填充读起来是"这一行被选中/很重要"，而不是"这个开关处于开态"；22 行全填时噪音盖过信息。收回到开关后，「设置 → 界面」和「设置 → 模型」才**真正成为同一套**——它们现在只是都用了蓝色，形态其实一个是按钮一个是整行填充。
- 影响任务：1.2（先把 Toggle 改成滑块）、3.2（复用同一个开关）

## 记录 008：样式表只做它名字承诺的事，布局定位不许藏在 CSS 里

- 日期：2026-07-27
- 状态：已确定
- 背景：任务 2.1 的根因是 `src/styles/scrollbar.css` 里的 `.app-scroll-container` 除了滚动条外观，还写了 `position: fixed; top: 40px; left/right/bottom: 0`。元素上的 className 是 `flex-1 overflow-y-auto p-4 app-scroll-container`，**完全看不出它是 `fixed`**，导致整个生成工作区脱离 `TabContainer` 的布局，助手侧栏打开时不避让。这个 bug 一直没被发现就是因为它藏在 CSS 里。
- 这是**第二次**遇到同一类错误：上一轮在 `storyboard.css`（工作区懒加载的样式表）里发现了全局主题变量 `:root[data-ui-radius]` / `:root[data-theme-tone]`，导致主题设置在用户打开画布之前完全不生效。
- 最终决定：确立通用规则——**样式表只做它文件名承诺的事**。具体地：
  - `scrollbar.css` 只管滚动条外观和滚动行为，不管定位
  - 任何 `position` / `top` / `left` / `right` / `bottom` / `z-index` 必须写在组件的 className 上，让读组件的人能看见
  - 全局 CSS 变量只能放 `src/index.css`（这条上一轮已确立，本次重申）
  - 例外必须在 CSS 文件里就地写注释说明理由
- 选择原因：布局藏在 CSS 里，读 JSX 的人和读 CSS 的人都看不到全貌，靠 grep 也搜不出来——本次是靠逐层量祖先链宽度才发现的。这类 bug 的发现成本远高于遵守规则的成本。
- 后续动作：本规则要写进 `.claude/skills/henji-ui-surface/SKILL.md` 和 `CLAUDE.md`（在任务 2.1 或 5.1 中一并完成）。
- 影响任务：2.1、5.1

## 记录 009：生成历史图片保持自然高度，用 aspect-ratio 预留空间

- 日期：2026-07-27
- 状态：已确定（用户表示"目前这样就挺好，视觉上好看"，代码方案由我定）
- 背景：`TaskCard.tsx:274-281` 的成功态图片是 `w-full h-auto` + `loading="lazy"`，完全没有预留高度。造成两次跳动：生成成功那一刻从固定 `h-64` 槽位切成自然高度；往回滚时图片重新解码从 0 撑开。上一轮曾提出"固定 `h-64` 槽位 + `object-contain`" vs "保持自然高度"两个方案未定。
- 最终决定：**保持自然高度的视觉不变**，用外层 `aspect-ratio` 盒子预留空间。宽高比来源按优先级：① 解析 `GeneratorOptions.size`；② 首次 `onLoad` 读 `naturalWidth/Height` 并持久化；③ 都没有则不设 `aspect-ratio`，优雅降级到当前行为。
- 选择原因：固定槽位 + `object-contain` 会让竖图周围出现大片留白，观感反而变差——用户明确说当前视觉是好的。要修的只是"高度到解码才确定"这一个技术点，不需要动视觉。这一项的验收前提就是**截图逐像素对比确认视觉零变化**。
- 影响任务：4.2
