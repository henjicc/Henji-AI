## 任务目标

治理装饰性 CSS 带来的合成与绘制开销：收敛 `backdrop-blur`、把 `transition-all` 改为具体属性、确认阴影仅用于浮层。这是性能收尾任务，同时也是视觉一致性收尾。

## 当前情况

### 实测基线（第二阶段开始前）

| 项 | 数量 | 问题 |
|---|---|---|
| `backdrop-blur` | 24 处 | 每处产生独立合成层，模糊需要读取背景纹理，在大面积或频繁重绘区域代价高 |
| `transition-all` | 16 处 | `all` 会把 `width`/`height`/`padding` 等触发布局的属性也纳入过渡，导致过渡期间反复重排 |
| `shadow-2xl` / `shadow-xl` | 18 处 | 大范围阴影绘制成本较高；按规范阴影应仅限浮层且统一为 `shadow-panel` |
| `will-change` / `contain` / `content-visibility` | 10 处 | 已有部分使用，需确认是否用在正确位置（`will-change` 滥用会常驻占用合成层） |

`backdrop-blur` 分布（≥2 处的文件）：

- `src/components/mediaViewer/ImageViewerModal.tsx`（3）
- `src/components/mediaViewer/VideoViewerModal.tsx`（2）
- `src/components/mediaViewer/ImageInfoPanel.tsx`（2）
- 另有 12 个文件各 1 处，含 `TaskCard`、`NotificationToast`、`ClearHistoryDialog`、`VideoNode`、`CanvasVideoPlayer`、`GroupNode`、`Canvas`、`AssetCard`、`UpdateDialog` 等

**注意**：第二阶段的迁移（尤其 2.2、2.3、2.4）会改动上述部分文件，`shadow-2xl` 与 `backdrop-blur` 的数量在第二阶段后会变化。**因此本任务必须在第二阶段完成后重新统计基线，不要用本文件记录的旧数字下结论。**

### 已知的合理用法（不要一律删除）

- 媒体查看器的背景模糊是**有意的视觉设计**（让 UI 浮在媒体之上），不应简单删除
- 画布节点上的 `backdrop-blur` 可能用于让节点内容在复杂背景上可读
- `AssistantMemoryPanel` 的 `content-visibility:auto` 是**正确的性能优化**，必须保留

**当前问题**：装饰性 CSS 没有使用规范，`transition-all` 属于明确应该修正的写法（几乎没有正当理由），`backdrop-blur` 缺少"什么场景值得用"的判断标准。

## 实施方案

按"明确该改的先改、需要判断的逐个判断、有意设计的保留"三档处理：

**第一档：`transition-all` → 具体属性（明确该改）**

`transition-all` 几乎没有正当用途。逐个改为实际需要过渡的属性：`transition-colors`、`transition-opacity`、`transition-transform`、`transition-shadow`，或 `transition-[width,height]` 这类显式列举。这是纯收益改动，无视觉变化（除非原本无意中依赖了某个属性的过渡，需逐个确认）。

**第二档：阴影收敛（规范收尾）**

按规范"阴影只有 `shadow-panel` 一档，且只有浮层能用"处理。非浮层的 `shadow-*` 删除；浮层的统一为 `shadow-panel`。`shadow-panel` 取值已刻意设为与 `shadow-2xl` 完全一致，所以浮层替换是像素等价的。

**第三档：`backdrop-blur` 逐个判断（需要设计判断）**

判断标准（写入 skill 作为长期规则）：

| 场景 | 结论 |
|---|---|
| 浮层覆盖在媒体/画布等复杂背景之上，模糊是为了保证可读性 | **保留** |
| 浮层覆盖在纯色/近纯色背景之上 | **改用不透明背景**，模糊无收益只有成本 |
| 高频重绘区域（进度条附近、动画元素、拖拽跟随层） | **移除** |
| 大面积（接近全屏）的模糊 | 评估是否可用降低透明度的纯色替代 |

## 执行步骤

1. **重新统计基线**（第二阶段已改动相关文件，旧数字不可用）：
   ```bash
   for p in 'backdrop-blur' 'transition-all' 'shadow-2xl' 'shadow-xl' 'will-change'; do echo -n "$p  "; grep -rEo "$p" src --include=*.tsx | wc -l; done
   grep -rn 'backdrop-blur' src --include=*.tsx
   grep -rn 'transition-all' src --include=*.tsx
   ```
   把新基线写入执行记录。
2. 逐个处理 `transition-all`：查看该元素实际会变化的属性，替换为具体属性。特别注意带 `transition-all duration-300` 的弹窗/面板容器——它们可能依赖 `transform` 与 `opacity` 的过渡。
3. 处理阴影：
   - 用 `grep` 找出所有 `shadow-` 使用位置
   - 判断该元素是否浮层（弹窗/侧栏/下拉/悬浮面板/画布节点）
   - 浮层 → `shadow-panel`；非浮层 → 删除
4. 逐个判断 `backdrop-blur`，按第三档标准分类处理，每个决策在执行记录中写一行理由。
5. 审查 `will-change` 使用：确认没有常驻的 `will-change`（应只在交互期间添加，或干脆不用）。若发现常驻滥用，移除。
6. 确认 `content-visibility` / `contain` 的现有用法保留且正确（`AssistantMemoryPanel` 必须保留）。
7. 把 `backdrop-blur` 与阴影的判断标准补进 skill `henji-ui-surface`（作为长期规则，不只是本次治理）。
8. 跑检查：`node scripts/check-surface-tokens.cjs`、`npx tsc -p tsconfig.json --noEmit`、`npm run lint`、`npm run check:colors`、`npx vitest run`。
9. 在执行记录中如实说明哪些改动是"纯收益无视觉变化"、哪些是"有意视觉变更需用户确认"。

## 需要用户手动验证的交互点

装饰改动直接影响观感，必须逐个界面确认：

1. 打开图片查看器 → 背景模糊/信息面板观感是否仍可接受
2. 打开视频查看器 → 控件条在深色与亮色视频上都清晰
3. 触发通知 Toast → 观感正常，文字清晰
4. 画布：节点、分组节点、视频节点 → 内容在画布背景上仍清晰可读
5. 资产库卡片 → 观感正常
6. 各弹窗打开/关闭动画 → 过渡仍流畅（验证 `transition-all` 替换未破坏动画）
7. 助手侧栏三种模式切换的过渡动画 → 仍流畅
8. 按钮/选项的 hover 过渡 → 仍有过渡，不生硬
9. 生成过程中（有进度条 + 动画）拖拽助手窗口 → 综合确认第三阶段整体收益
