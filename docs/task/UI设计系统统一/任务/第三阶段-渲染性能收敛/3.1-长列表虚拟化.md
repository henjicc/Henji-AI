# 3.1 长列表虚拟化

## 任务状态

- 状态：待开始
- 所属阶段：第三阶段-渲染性能收敛
- 前置任务：2.2（两者都改 `TaskCard`/`TaskList`，必须串行）

## 任务目标

给全量渲染的长列表接入虚拟化，减少 DOM 规模与父组件更新时的同步渲染成本。重点是生成历史任务列表——它每项都含图片/视频元素，是 DOM 最重的列表。

## 当前情况

### 现状

`react-virtuoso@^4.15.0` **已经是项目依赖**（`package.json:76`），但目前只用在一处：

- `src/features/logs/components/AssistantTraceList.tsx:1` — `import { Virtuoso } from 'react-virtuoso'`，可作为本项目的**实现参考范例**

未虚拟化的列表：

| 文件 | map 数量 | 单项内容 | 优先级 |
|---|---|---|---|
| `src/workspaces/GenerationWorkspace/components/TaskList.tsx` | 1 | `TaskCard`，含 `<img>`/`<video>`、多个按钮、拖拽 handler | **高** |
| `src/workspaces/GenerationWorkspace/components/MessageList.tsx` | 2 | 消息 + 附件 | 中 |
| `src/features/assets/components/AssetLibrarySidebar.tsx` | 2 | 资产卡片（含缩略图） | 中 |
| `src/features/canvas/params/ModelPickerList.tsx` | 5 | 模型选项 | 低（通常项数有限） |
| `src/features/assistant/history/AssistantRunHistory.tsx` | 1 | 运行历史条目 | 低 |

### 已完成的相关工作（不要重做）

前置提交 `eb74657` 已解决"进度更新导致整个工作区重渲染"的问题（进度抽到 `generationTaskProgressStore` 瞬态 store）。本任务解决的是**另一个**问题：即使不重渲染，列表本身的 DOM 规模也偏大，且父组件确实更新时（如筛选、新任务加入）需要 diff 全部子项。

### 相关性能上下文（来自审计，均为代码级确认事实）

- `TaskCard` 已用 `React.memo` 且比较函数只比 `task` 引用
- `AssistantMemoryPanel` 用了 `[content-visibility:auto]` + `[contain-intrinsic-size:auto_92px]`，是一种轻量替代方案，可作为不适合虚拟化场景的备选手段
- 生成工作区存在自动滚动到底部的逻辑（`useScrollBehavior`、`useAutoScrollOnResize`、`GenerationWorkspace.tsx` 中依赖 `tasks.length` 的滚动 effect），**虚拟化会与滚动控制逻辑冲突，这是本任务最大风险点**

**当前问题**：历史任务多时（用户可配置 `maxHistoryCount`）DOM 规模线性增长；每项含媒体元素，内存与解码开销可观。

## 实施方案

**只对确有收益且风险可控的列表做虚拟化，不为覆盖率而虚拟化。**

优先级与做法：

1. **`TaskList`（高优先级，本任务核心）**：改用 `Virtuoso`。最大难点是与现有滚动逻辑的整合——生成工作区有"新任务出现时自动滚到底部""窗口 resize 时保持位置"等行为，必须改为使用 Virtuoso 提供的 API（`followOutput`、`scrollToIndex`、`initialTopMostItemIndex`）而不是直接操作 `scrollTop`。
2. **`MessageList` / `AssetLibrarySidebar`（中优先级）**：评估实际项数量级。若通常在几十项以内，改用 `content-visibility:auto` 这种轻量方案即可，不必上虚拟化。**执行时先测量实际项数再决定**，并把结论写入记录。
3. **`ModelPickerList` / `AssistantRunHistory`（低优先级）**：本任务默认**不做**，只在记录中说明理由（项数有限、收益低于复杂度）。

**先测量、再决定**：本任务不允许"因为它是列表所以虚拟化"。每个列表都要先确认实际项数量级与 DOM 成本，再决定手段。

## 需要用户手动验证的交互点

虚拟化对滚动行为影响大，必须由用户实际操作验证：

1. 打开生成工作区，历史记录较多时上下快速滚动 → 流畅、无白屏、无跳动
2. 发起一次新生成 → 列表自动滚到底部，能看到新任务
3. 生成过程中滚动到列表中部 → 进度更新不会把视口强行拉走
4. 使用历史筛选（关键词/模型/时间）→ 列表正确刷新，滚动位置合理
5. 拖拽某个结果图片到画布 → 拖拽正常
6. 右键任务结果 → 菜单正常
7. 删除一个任务 → 列表正确更新，滚动位置不乱跳
8. 调整窗口大小 / 拖拽助手侧栏 resize → 列表布局与滚动位置正常
9. 切换到其他工作区再切回 → 滚动位置与内容正常

## 风险与回退

- **风险**：虚拟化与现有滚动控制冲突，可能出现滚动跳动、位置错乱、条目高度测量错误（任务卡高度可变，含图片，是虚拟化最难的场景）。
- **控制**：先梳理完所有滚动逻辑再动手；Virtuoso 对可变高度有内建支持，但需确认图片加载完成后的高度重算行为。
- **回退**：本任务单次独立提交。若出现难以收敛的滚动问题，整体 `git revert`，改用 `content-visibility:auto` 轻量方案（参考 `AssistantMemoryPanel` 的做法），并在记录中说明。
