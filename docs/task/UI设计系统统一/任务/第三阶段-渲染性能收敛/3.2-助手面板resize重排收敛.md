## 任务目标

收敛 docked（左/右停靠）模式下拖拽助手面板边缘 resize 时的整表重排开销。这是审计中定位到的**第二个独立卡顿源**，与已修复的进度条问题无关。

## 当前情况

### 已修复的部分（不要重做）

前置提交 `eb74657` 修复的是"生成进度更新导致整个工作区重渲染，与拖拽抢主线程"。那个问题的元凶是 `useTaskState.updateProgress` 用 `setTasks(prev.map(...))` 写进度，已改为独立瞬态 store。

### 本任务针对的是另一个问题

`src/features/assistant/hooks/useAssistantPanelInteraction.ts` 的拖拽实现本身**写得很好**，是审计中确认的良好范例：

- `pointermove` 只做 rAF 合并（`queueLayout` + `requestAnimationFrame(flush)`）
- 帧内直接写 DOM 样式，不触发任何 React / Zustand 状态更新
- 只在 `pointerup` 时通过 `commitLayout` 提交到 store

**但 `applyLiveResize`（约 `:192-205`）存在固有开销：**

```ts
const insets = getAssistantWorkspaceInsets(mode, next.size.width)
workspace.style.paddingLeft = `${insets.left}px`
workspace.style.paddingRight = `${insets.right}px`
```

docked 模式下每帧修改工作区的 `padding`，工作区宽度真的变了，因此**整个工作区子树需要重新布局**。当工作区内是未虚拟化的长任务列表（每项含图片/视频）时，每帧全量重排的代价很高。

注意：floating（浮动）模式下拖拽只写 `transform`（`applyDragPreview`），那是合成器操作，很便宜——**所以本任务只针对 docked 模式的 resize，不是所有拖拽**。

### 相关代码位置

- `src/features/assistant/hooks/useAssistantPanelInteraction.ts`：`applyLiveResize`、`startPointerInteraction`、`getAssistantWorkspaceInsets`
- `src/App.tsx:180-184`：`TabContainer` 接收 `insetLeft`/`insetRight`，来源是 `assistantSize.width`
- `src/features/assistant/AssistantSidebar.tsx`：resize 手柄定义（`onResizePointerDown`）
- `src/features/assistant/hooks/useAssistantPanelInteraction.test.ts`：已有测试，改动后必须保证通过
- `src/index.css`：`--assistant-layout-transition-duration` 变量在 resize 期间被设为 `0ms`

**当前问题**：resize 每帧触发工作区整子树重排，与 3.1（虚拟化）是互补关系——虚拟化减少需要重排的节点数，本任务减少重排的传播范围。

## 实施方案

**先测量、再优化。不要在没有确认瓶颈的情况下引入复杂机制。**

候选手段按"简单→复杂"排序，逐个评估：

1. **CSS containment**：给工作区容器加 `contain: layout`（或 `contain: layout style`）。这能把布局影响限制在容器内，阻止向上传播。风险低，是首选尝试。需确认不会破坏内部的 `position: fixed`/`sticky` 元素与浮层定位——`contain: layout` 会让容器成为包含块，可能影响内部绝对定位元素与 portal 之外的浮层。
2. **resize 期间降级**：拖拽 resize 进行中给工作区加一个标记类（如 `data-resizing="true"`），用 CSS 临时简化内部渲染（例如隐藏媒体缩略图、关闭过渡与阴影），`pointerup` 后恢复。视觉上会有轻微变化，需用户确认可接受。
3. **改变 inset 实现方式**：评估能否用 `transform` / `clip` 或让工作区固定宽度 + 平移，替代改 `padding`。风险较高，可能影响工作区内部布局与滚动，**只在前两条不够时考虑**。
4. **与 3.1 协同**：若 3.1 已完成虚拟化，需重新测量本任务的实际收益——虚拟化本身可能已把重排成本降到可接受，此时本任务可能只需做第 1 条甚至不做。

## 风险与回退

- **风险**：`contain: layout` 会让容器成为包含块，可能影响内部 `position: fixed` 元素定位。项目中 `UiModal` 已用 `createPortal` 挂 `document.body` 规避此类问题（其源码注释明确说明了原因），但其他非 portal 的浮层可能受影响。
- **控制**：改动后按验证清单第 8 项逐个检查浮层。
- **回退**：单次独立提交，出现浮层定位异常直接 `git revert`。

## 执行记录

### 2026-07-25

- **未改动任何代码**，本次只完成分析。原因见下。

#### 结论一：首选手段 `contain: layout` 被证据否决

工作区子树内有 **9 个文件**使用 `position: fixed`：`FloatingInputPanel`、`NotificationToast`、
画布的节点参数气泡 / 下载菜单 / 分镜导出设置 / 来图选择器、`ModelPickerList`、
资产库浮层与资产卡菜单。

`contain: layout` 会让工作区容器成为这些元素的**包含块**，它们相对视口的定位会全部失效。
因此手段 1 不可用（不是"有风险"，是确定会坏）。详见 `decisions.md` D-008。

#### 结论二：3.1 已经作用于本任务的根因

`applyLiveResize` 每帧改 `workspace.style.paddingLeft/Right`，工作区宽度真的变了，
所以整个子树要重新布局——而这个子树里最重的就是最多 500 张含图/视频的任务卡。

3.1 给任务卡加的 `content-visibility: auto` 会让浏览器**跳过视口外元素的布局**，
正好削掉这部分成本。所以本任务的主要开销大概率已经被 3.1 覆盖。

#### 结论三：剩余手段需要用户先测量

任务文件明确要求「不允许无测量直接优化」。剩下的两个手段都有代价：
- 手段 2（resize 期间降级渲染）：会带来可见的视觉变化，需用户接受
- 手段 3（改 inset 实现方式）：风险高，可能影响工作区布局与滚动

在没有真实测量数据的前提下动手，既违反任务约定，也可能是在优化一个已经不存在的问题。
