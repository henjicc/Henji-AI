# 1.3 自动化门禁与 CI 接入

## 任务状态

- 状态：已完成
- 所属阶段：第一阶段-令牌收口与自动化门禁
- 前置任务：1.1、1.2
- 关联任务：第二阶段全部任务（`check:surface` 转 strict 需等第二阶段清零）
- 是否可以并行：否，必须在 1.1 与 1.2 归零后执行

## 任务目标

把已经归零的视觉规则固化为**硬性 ESLint 规则**，并把 UI 规范检查接入构建/CI 链路，使后续 Agent 无法在不被发现的情况下引入违规写法。

## 当前情况

### 已有门禁机制

项目已在 `.eslintrc.json` 用 `no-restricted-syntax` + 正则选择器实现硬规则，机制**已验证有效**（用临时探针文件确认过规则会真实触发），且无需引入额外依赖：

```json
{
  "selector": "Literal[value=/text-\\[(?:9|10|11)px\\]/]",
  "message": "禁止内联 9/10/11px 字号，请使用已登记的 text-4xs / text-3xs / text-2xs。"
}
```

现有规则覆盖：十六进制颜色字面量、模板串中的十六进制颜色、`bg-[#xxx]` 形式、9/10/11px 内联字号。

### 已有脚本

| 脚本 | 命令 | 当前是否在构建链 |
|---|---|---|
| `scripts/check-color-tokens.cjs` | `npm run check:colors` | ✅ 在 `build`/`electron:build` 中 |
| `scripts/check-surface-tokens.cjs` | `npm run check:surface` | ❌ 未接入 |
| `scripts/check-model-i18n.cjs` | `npm run check:model-i18n` | ✅ 在 `build`/`electron:build` 中 |

`check-surface-tokens.cjs` 支持 `--strict`（`npm run check:surface:strict`，违规 exit 1）与两种豁免标记（行级 `ui-surface-allow`、文件级 `ui-surface-allow-file`）。

**当前问题**：`check:surface` 只能靠人主动跑，没有任何强制力；1.1/1.2 归零的成果没有规则保护，随时可能被下一次改动破坏。

**可复用**：`no-restricted-syntax` 机制、`check-surface-tokens.cjs` 的 `--strict` 与豁免机制。

## 实施方案

**核心原则：只对当前违规数已归零的模式加 `error`**，否则一加规则就破坏构建。

分三层建立门禁：

1. **ESLint 硬规则**（即时反馈、IDE 可见）：覆盖 1.1/1.2 归零的模式——任意圆角、任意阴影、任意 z-index、剩余内联字号。
2. **脚本检查**（结构性规则，ESLint 表达不了）：`check:surface` 负责表面层级与卡片嵌套；新增"弹窗绕过 `UiModal`"检查（手写 `fixed inset-0` + `bg-black/`）。
3. **构建链接入**：把 `check:surface` 加入 `build` 与 `electron:build`。是否用 strict 取决于第二阶段进度（见「分步策略」）。

### 分步策略

本任务先完成 ESLint 规则 + 脚本增强 + 以**非 strict**（告警）方式接入构建链。等第二阶段全部完成、`check:surface` 清零后，再由第二阶段最后一个任务或独立收尾把它切成 strict。这样门禁能立刻开始工作，又不会阻塞第二阶段的迁移过程。

## 执行步骤

1. 确认 1.1、1.2 的归零结果，逐个模式统计当前违规数，只对为 0 的模式加规则：
   ```bash
   for p in 'rounded-\[' 'shadow-\[' 'z-\[' 'text-\['; do echo -n "$p  "; grep -rEo "$p" src --include=*.tsx --include=*.ts | wc -l; done
   ```
2. 在 `.eslintrc.json` 的 `no-restricted-syntax` 中追加规则（每条都要同时加 `Literal` 与 `TemplateElement` 两个选择器，因为 className 常写在模板串里）：
   - 禁任意圆角：`rounded(-[a-z]+)?-\[`，但**必须放行** `rounded-[var(--node-radius)]`（正则需排除 `var(`）
   - 禁任意阴影：`shadow-\[`
   - 禁任意 z-index：`z-\[`
   - 禁剩余内联字号：`text-\[\d+px\]`（若 1.1 已全部归零）
3. 为确实需要例外的文件添加 `overrides`（参考现有 `src/core/theme/colorTokens.ts` 的 `no-restricted-syntax: off` 写法），而不是放宽全局规则。
4. **反向验证每条新规则真的会触发**：创建临时探针文件写入违规写法，跑 `npx eslint` 确认报错，然后删除探针：
   ```bash
   printf 'export const bad = "shadow-[0_0_0]"\n' > src/__lint_probe.tsx
   npx eslint src/__lint_probe.tsx --ext ts,tsx
   rm -f src/__lint_probe.tsx
   ```
   未经反向验证的规则不算完成（正则写错会静默不生效）。
5. 增强 `scripts/check-surface-tokens.cjs`，新增"弹窗绕过 `UiModal`"检查：业务组件（排除 `src/components/ui/`）中同时出现 `fixed inset-0` 与 `bg-black/` 且未 import `UiModal` 的文件即告警。当前已知 12 处，先以告警形式输出并打印基线数量供 2.3 跟踪。
6. 把 `check:surface` 以非 strict 形式加入 `package.json` 的 `build` 与 `electron:build` 脚本链（放在 `check:colors` 之后）。
7. 检查仓库是否存在 CI 配置（`.github/workflows/`）。若存在，把 `check:surface`、`check:colors`、`lint`、`tsc`、`vitest` 接入；若不存在，**不新建 CI**，改为在执行记录中说明"CI 待确认"并标记为待确认事项。
8. 更新 skill `henji-ui-surface` 的「完成前必跑」小节与 `CLAUDE.md` 的检查清单，保持与实际命令一致。
9. 跑全套验证：`npm run lint`、`npm run check:colors`、`npm run check:surface`、`npm run check:model-i18n`、`npx tsc -p tsconfig.json --noEmit`、`npx vitest run`。
