- 引用 `src-tauri` 目录 —— 已在 Tauri 清理中删除

### 执行中发现并修复的两个阻塞问题

1. **渲染层 `tsc` 存在存量错误**：`src/core/imageEdit/worker/webgpuRuntime.ts:21` 在 `import type { ... }` 内部又对两个成员写了 `type` 修饰符（TS2206）。这会让 `npx tsc -p tsconfig.json --noEmit` 与 `npm run build` **直接失败** —— 即 CI 不可能变绿。已修复（删除内层冗余 `type`）。
2. **`scripts/release.cjs` 硬编码分支**：第 381 行 `git push origin feat/electron-migration`，而当前分支已是 `main`，发布时会推错分支。已改为读取当前分支。

## 实施方案

拆成两个 job，职责分离：

- **`checks`（每次 push / PR）**：ubuntu-latest，跑生成产物 → 三个 check 脚本 → 双侧 ESLint → 双侧 tsc → vitest。快、无需凭据，是 UI 规范获得强制力的关键。
- **`build`（仅 `v*` 标签或手动触发）**：平台矩阵出安装包。

两个关键设计决策：

**平台矩阵按「构建机架构 = 目标架构」拆分**（`windows-latest` / `macos-13` x64 / `macos-latest` arm64）。原因：`better-sqlite3` 需要编译，`sharp` 依赖按宿主架构安装的 `@img/sharp-*` 可选包，跨架构交叉编译容易失败。旧 CI 用 universal binary 是 Tauri（Rust 交叉编译）的做法，Electron 侧不适用。

**由 electron-builder 自己发布（`--publish always`），而不是只上传安装包**。原因：项目使用 electron-updater，自动更新依赖 Release 中的 `latest.yml` / `latest-mac.yml`。只用 `action-gh-release` 上传安装包会漏掉这些元数据文件，静默破坏自动更新。配合 `max-parallel: 1` 串行发布，避免三个 job 并发抢占同一个 Release。

## 未能本地验证的部分（必须由用户实际触发确认）

以下环节依赖真实 GitHub Actions 环境，本地无法验证，**不做任何"应该没问题"的断言**：

1. `npm ci` 在干净环境下的依赖安装（尤其 `better-sqlite3` 编译、`sharp` 平台可选包）
2. electron-builder 在各 runner 上的原生模块 rebuild 与 asar 解包
3. Windows NSIS / MSI 与 macOS DMG 的实际产出
4. `--publish always` 向 GitHub Release 上传产物与 `latest.yml`
5. `macos-13` runner 的可用性（GitHub 已在逐步下线较旧的 macOS 镜像，若不可用需改用 `macos-14`）

**建议的验证方式**（按风险从低到高）：

1. 先用 **Actions → Run workflow（`workflow_dispatch`）** 手动触发一次。此时 `build` job 走 `--publish never` 分支，只产出 artifact **不会**创建任何 GitHub Release，可安全验证整条构建链。
2. 确认 artifact 里三个平台的安装包与 `latest*.yml` 都在。
3. 再考虑推一个真实标签验证发布链路。
