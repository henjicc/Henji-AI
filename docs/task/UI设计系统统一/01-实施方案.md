# UI 设计系统统一 - 实施方案

## 一、当前项目与相关功能现状

### 技术栈与落点

- 渲染层：React 18 + TypeScript + Tailwind CSS 3，构建走 Vite / electron-vite
- 颜色令牌三件套：`src/index.css`（CSS 变量）→ `tailwind.config.js`（语义色映射）→ `src/core/theme/colorTokens.ts`（TS 常量）
- 视觉令牌：`src/components/ui/styleTokens.ts`
- UI primitives：`src/components/ui/primitives.tsx`（项目唯一允许出现 `<button>/<input>/<select>/<textarea>` 的文件）
- 布局与状态组件：`src/components/ui/layout.tsx`、`src/components/ui/states.tsx`
- 统一导出口：`src/components/ui/index.ts`
- 规则文档：skill `.claude/skills/henji-ui-surface/SKILL.md`，约束摘要在 `CLAUDE.md`「UI Primitive 单点落地」

### 已有的检查手段

| 命令 | 作用 | 当前状态 |
|---|---|---|
| `npm run check:colors` | 拦十六进制颜色直写与 `bg-[#xxx]` | 通过 |
| `npm run check:surface` | 报手写卡片表面与同文件多层卡片，默认只告警 | 20 处 / 8 文件 |
| `npm run check:surface:strict` | 同上，违规即 exit 1 | 未接入门禁 |
| `npm run lint` | ESLint，已用 `no-restricted-syntax` 拦十六进制颜色与 9/10/11px 内联字号 | 通过 |
| `npx tsc -p tsconfig.json --noEmit` | 渲染层类型检查 | 仅存量 `webgpuRuntime.ts` 报错（与本任务无关） |
| `npx vitest run` | 单元测试 | 479 通过 / 11 跳过 |

## 二、当前实现方式

界面由业务组件直接消费 `@/components/ui` 的 `Ui*` 组件拼装，没有页面模板层。视觉数值一部分来自令牌，一部分直接写 Tailwind 类，历史上还有相当数量写成任意值（`text-[11px]`、`z-[9999]`、`rounded-[24px]`）。表面层级靠各组件自带的 `border + bg` 组合表达，没有统一的层级概念。

## 三、当前存在的问题

1. **表面令牌不可分拆**：`UI_PANEL_SURFACE_CLASS` / `UI_FIELD_SURFACE_CLASS` 把 `border` 与 `bg` 绑死，无法只要背景不要边框。
2. **容器词汇表缺一层**：改造前只有"卡片"（`UiPanel`）概念，缺少"分组"，Agent 想分组只能画卡片 → 卡片套卡片。已通过新增 `UiGroup` 等组件缓解，但**存量页面尚未迁移**。
3. **视觉数值未登记**：剩余 `rounded-[` 25 处、`z-[` 24 处、`shadow-[` 15 处、`border-[` 40 处、`text-[` 20 处。z-index 完全无序（`z-[2147483647]`、`z-[12000]`、`z-[9999]` 与 `z-50` 并存），是浮层遮挡 bug 的结构性隐患。
4. **弹窗实现分裂**：12 个弹窗绕过 `UiModal` 各自手写 `fixed inset-0` 遮罩与卡片外壳，外观与行为不一致。
5. **排版层级塌缩**：72% 字号决策集中在 `text-xs` 及更小，`text-base` 以上仅 32 处，导致只能靠边框背景区分内容，页面视觉重量偏大。
6. **性能隐患**：长列表（任务历史、消息、资产库、模型选择器）全量渲染，`react-virtuoso` 已在依赖中但只用于日志；docked 模式 resize 每帧写 `workspace.style.paddingLeft` 触发整表重排；`backdrop-blur` 24 处、`shadow-2xl/xl` 18 处、`transition-all` 16 处。

## 四、最终目标

1. 所有视觉数值来自登记令牌，Agent 无法轻易绕过添加新数值（有 ESLint / 脚本兜底）。
2. 普通内容分组默认不产生卡片；卡片嵌套不超过 1 层。
3. 页面视觉层级主要由排版、间距、结构建立，而非边框背景阴影。
4. 相同功能（弹窗、空/加载/错误状态、播放器、上传）在不同页面外观与交互一致。
5. `check:surface` 除已标注豁免项外清零，并进入 CI 门禁。
6. 已定位的渲染性能问题收敛，进度更新与窗口拖拽不再互相拖累。
7. 新 Agent 只读 skill + 任务文件即可正确产出符合体系的界面。

## 五、总体解决思路

**"先补表达能力，再立规矩，最后迁存量"**——这是本方案的核心判断。

审计结论是：过度卡片化的根因是工具箱里只有卡片这一把锤子，不是纪律问题。因此顺序必须是：
1. 先让"分组、内嵌、分隔"这些概念有官方写法与令牌（已在前置提交完成主体）
2. 再把剩余未登记数值收口，并让规则可自动检查（第一阶段）
3. 最后按新体系迁移存量页面（第二阶段）
4. 性能问题作为独立正交线推进（第三阶段）

## 六、技术方案与实施策略

### 令牌策略：三层架构

采用业界通行的三层令牌模型，落点复用项目已验证成功的颜色三件套模式，**不新建平行体系**：

| 层 | 内容 | 落点 |
|---|---|---|
| 原始层 | 颜色值、像素值 | `src/index.css` CSS 变量、`tailwind.config.js` |
| 语义层 | `bg-app`/`bg-panel`/`text-2xs`/`shadow-panel`/`z-modal` | `tailwind.config.js` |
| 组件层 | `UI_TEXT_*`/`UI_SECTION_STACK_CLASS`/`UI_PANEL_SURFACE_CLASS` | `src/components/ui/styleTokens.ts` |

`--ui-*` CSS 变量保留作为组件层，仅供无法用 Tailwind 类的纯 CSS 文件消费（当前唯一消费者是 `src/features/canvas/storyboard.css`），**不在其中新增**。

### 容器策略：五级词汇表

| 级 | 概念 | 组件 | 边框 | 背景 | 阴影 |
|---|---|---|---|---|---|
| 1 | Region | `UiRegion` | ❌ | ❌ | ❌ |
| 2 | Group | `UiGroup` | ❌ | ❌ | ❌ |
| 3 | Divided | `UiGroup divided` | 仅一条线 | ❌ | ❌ |
| 4 | Surface | `UiPanel variant="inset"` | ❌ | 更暗底 | ❌ |
| 5 | Card | `UiPanel` | ✅ | ✅ | ✅ |

卡片准入条件（四条全中才允许）：有独立交互或状态、可单独移动关闭拖拽、与兄弟元素是并列实体、脱离上下文仍可理解。

### 迁移策略：单点改动优先

优先寻找"改一个文件、多处受益"的杠杆点。Settings 试点已验证该策略有效：`SectionCard` 一处改动覆盖 15 个调用点。后续迁移同样优先改共享组件，其次才逐页面处理。

### 门禁策略：只对零违规模式加硬规则

ESLint 的 `no-restricted-syntax`（项目已验证有效的机制，无需新增依赖）**只对当前违规数已归零的模式**加 `error`，避免一加规则就破坏构建。存量违规先由 `check:surface` 告警跟踪，迁移清零后再转 strict。

## 八、阶段划分与阶段关系

- **第一阶段（1.1~1.3）令牌收口与自动化门禁**：把剩余任意值收进令牌，统一 z-index，建立可执行门禁。是第二阶段的前提。
- **第二阶段（2.1~2.5）页面去卡片化迁移**：按五级体系迁移存量页面。五个任务之间**互不依赖，可并行**，各自负责不同文件。
- **第三阶段（3.1~3.3）渲染性能收敛**：与第二阶段基本正交，可并行推进。例外：3.1 与 2.2 都改 `TaskCard`/`TaskList`，建议 3.1 排在 2.2 之后；3.3 需要在 2.1~2.5 之后做，因为迁移过程本身会减少装饰。

## 九、新旧实现兼容方式

- **组件 API 保持向后兼容**：像 `SectionCard` 这类被多处调用的组件，改内部实现但保留原有 props 签名，避免连带修改调用点。
- **保留过渡命名**：已改为零装饰分组的 `SectionCard` 保留原名以免动 15 个调用点，但在文件注释中写明"新代码请直接用 `UiGroup`"。
- **变体优先于新组件**：需要新表现时优先给现有组件加**有限枚举变体**（如 `UiPanel variant`、`UiGroup titleTone`），不开放任意 className 覆盖视觉，避免变体无限扩散。
- **像素等价优先**：纯登记性质的令牌迁移必须做到计算值不变（如 `text-2xs` 用字符串形式定义 fontSize，只产出 `font-size` 不带 `line-height`，与原 `text-[11px]` 完全一致）。有意的视觉变更必须单独说明并交用户确认。

## 十、数据与接口兼容要求

本任务不涉及数据库结构、IPC 接口、模型定义 schema、项目包格式的任何改动。唯一需要注意的兼容点：

- `src/stores/generationTaskProgressStore.ts` 是瞬态状态，**不进持久化、不进历史快照**。任务历史里的 `task.progress` 仅保留终态快照（成功时的 100）。
- 助手的任务状态查询（`registerVisibleGenerationTaskHandler`）读进度时必须优先读瞬态 store，回退 `task.progress`。这条链路被 `npm run assistant:cli -- --await-generation` 使用，改动进度存储时必须同步检查。

## 十一、风险控制方式

| 风险 | 控制方式 |
|---|---|
| 令牌迁移意外改变视觉 | 迁移前后对比生成的 CSS 计算值；纯登记迁移要求像素等价 |
| z-index 统一导致浮层遮挡错乱 | 逐个浮层梳理期望层序后再替换，不做批量正则替换；改完列出所有浮层供用户逐一验证 |
| 去卡片化后层级不清 | 每个迁移任务完成后交用户看实际界面；提供"加分隔线"作为备选方案 |
| 批量 sed 替换误伤 | 替换后必跑 `tsc` + `lint` + `vitest`，并检查 `git diff` 行数是否符合预期 |
| 门禁转 strict 破坏构建 | 只对零违规模式加硬规则；strict 在第二阶段清零后才接入 |
| 性能改动引入复杂度 | 优先缩小状态影响范围与减少无效更新，不为优化引入复杂架构 |

## 十二、回退与恢复原则

- 每个任务一次独立 Git 提交，便于按任务粒度 `git revert`。
- 令牌类改动（第一阶段）是加法为主，回退风险低。
- 页面迁移类改动（第二阶段）互相独立，单个页面回退不影响其他页面。
- 性能类改动（第三阶段）如引入虚拟化后出现滚动/定位异常，优先回退该单项而非整体。

## 十三、全局开发约束

1. 遵守 `CLAUDE.md` 全部既有约束，尤其：配置驱动、禁止跨层导入、原生标签只在 `primitives.tsx`、颜色只在三处改、新文件优先 ≤400 行。
2. 界面工作开始前先读 skill `henji-ui-surface`。
3. 不新增裸 `any`；新增/修改的导出函数补显式返回类型。
4. 涉及鼠标交互与视觉观感的验证交用户手动执行，写清操作步骤与验证点。
5. 每次改完告知用户是否需要重启 `npm run electron:dev`。
6. 不擅自重新编号已有任务；发现计划与实际不符先更新任务文件。
7. 性能结论必须有依据，禁止编造数据。
