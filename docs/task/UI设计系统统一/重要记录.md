## 记录 001：过度卡片化的根因判定为"表达能力缺失"而非"纪律缺失"

- 日期：2026-07-25
- 状态：已确定
- 背景：AI Agent 新建界面时反复出现"不该有背景边框的地方带壳""卡片套卡片""页面碎片化"。最初怀疑是 Agent 不遵守规范，考虑用更强的文档约束解决。审计后发现：
  - `styleTokens.ts` 的表面令牌（`UI_PANEL_SURFACE_CLASS`、`UI_FIELD_SURFACE_CLASS`）把 `border` 与 `bg` 绑死，无法只要背景不要边框
  - 容器词汇表里只有 `UiPanel`（卡片）一个概念，没有"分组"这一层，Agent 想把几个字段归成一组时没有任何官方写法，只能手写 `border + bg` 的 div
  - `UiIconButton` 默认 `showBorder=true`、`UiOptionButton` 提供 `variant="card"`、组件命名 `SectionCard`（分区=卡片）都在主动诱导画卡片
  - 页面示例本身就是坏范例：Settings 存在三层卡片嵌套（弹窗 `bg-panel` → `SectionCard` `bg-panel` → 内部行 `bg-surface-dark`），Agent 抄这个模板必然出错
  - 排版层级塌缩：72% 字号决策集中在 `text-xs` 及更小，没有字号层级就只能靠边框背景区分内容
- 最终决定：解决路径是**先补表达能力，再立规矩，最后迁存量**。优先新增零装饰容器（`UiGroup` 等）与登记令牌，而不是只写更严格的文档。
- 选择原因：Agent 不是不想克制，是工具箱里只有卡片这一把锤子。只加文档约束无法解决"没有替代写法"的问题。
- 影响任务：决定了整个计划的阶段顺序（第一阶段令牌 → 第二阶段迁移），以及 skill 的组织方式（五级容器词汇表 + 卡片准入条件，而非泛泛的"少用卡片"）。

## 记录 002：视觉数值采用登记制，且只对零违规模式加硬规则

- 日期：2026-07-25
- 状态：已确定
- 背景：审计发现 176 处 `text-[Npx]` 内联字号、24 处任意 z-index（含 `z-[2147483647]`）、25 处任意圆角、15 处任意阴影。需要建立约束，但一旦把 ESLint 规则设为 `error`，存量违规会立刻破坏构建。
  另外发现 `text-[11px]`（83 处）、`text-[10px]`（66 处）不是随手写——Tailwind 最小档 `text-xs` 是 12px，覆盖不了项目真实需求，是**令牌缺位导致的必然泄漏**。
- 最终决定：
  1. 缺失的档位先补进令牌（已注册 `text-4xs`=9px / `text-3xs`=10px / `text-2xs`=11px），再迁移存量
  2. 迁移必须**像素等价**：Tailwind `fontSize` 用字符串形式定义，只产出 `font-size` 不带 `line-height`，与原 `text-[11px]` 计算值完全一致（已 dump CSS 验证）
  3. ESLint 的 `no-restricted-syntax` **只对当前违规数已归零的模式**加 `error`
  4. 存量违规先由 `check:surface` 等脚本以告警形式跟踪，清零后再转 strict
  5. 每条新增 ESLint 规则必须用临时探针文件**反向验证真的会触发**（正则写错会静默不生效）
- 选择原因：既能立刻建立约束，又不破坏构建；像素等价保证令牌收口不夹带视觉变更，让"纯登记"和"有意改观感"两类改动可区分、可分别验收。
- 影响任务：1.1、1.2、1.3 的执行方式；`重要记录 004` 的 strict 切换时机。

## 记录 003：媒体查看器三个全屏 Modal 是否纳入 UiModal 统一范围

- 日期：2026-07-25
- 状态：已确定（2026-07-25 用户确认：豁免）
- 背景：项目 18 个 dialog/modal 中 12 个绕过 `UiModal` 手写遮罩与卡片外壳，2.3 要统一它们。但其中三个是全屏沉浸式媒体查看器：
  - `src/components/mediaViewer/ImageViewerModal.tsx`
  - `src/components/mediaViewer/VideoViewerModal.tsx`（553 行）
  - `src/components/mediaViewer/AudioViewerModal.tsx`
  
  `UiModal` 的语义是"居中的卡片式弹窗"（固定宽度、带标题栏、带 footer、`UiPanel` 外壳），与全屏沉浸式查看器（铺满视口、无卡片外壳、内容即主体）并不匹配。强行套用可能需要给 `UiModal` 加大量逃逸口，反而污染这个 primitive。
- 最终决定：**豁免**。保留独立实现，但加 `ui-surface-allow` 注释说明"全屏沉浸式查看器，非居中弹窗语义"，并在 skill 中写明这一例外类别，避免后续 Agent 误以为可以随意手写弹窗。
- 选择原因：primitive 应该保持语义单一。为一类语义不同的组件给 `UiModal` 加逃逸口，会让它变成"什么都能做"的万能组件，失去约束力。
- 影响任务：2.3（弹窗统一范围）、2.4（媒体查看器内部表面）、2.5（豁免清单）、1.3（"弹窗绕过 UiModal"检查的预期归零值 = 3 个豁免项）。

## 记录 004：check:surface 转 strict 的时机

- 日期：2026-07-25
- 状态：已确定（2026-07-25 用户确认：按倾向结论执行）
- 背景：`scripts/check-surface-tokens.cjs` 支持 `--strict`（违规 exit 1），但当前基线仍有 20 处违规 / 8 个文件。若立刻在构建链中启用 strict，`npm run electron:build` 会直接失败。
- 最终决定：
  1. 1.3 先以**非 strict**（告警）形式把 `check:surface` 接入 `build` 与 `electron:build`，让门禁立刻开始工作
  2. 等第二阶段（2.1~2.5）全部完成、`check:surface` 清零后，再切换为 strict
  3. 切换动作放在 2.5 之后作为收尾（2.5 的验收标准已包含"`check:surface:strict` exit code 为 0"）
- 选择原因：告警形式能立刻提供可见性且零阻塞风险；strict 需要等清零，否则会阻塞第二阶段自身的迁移工作。
- 影响任务：1.3、2.5。

## 记录 005：助手对话消息块是否保留容器

- 日期：2026-07-25
- 状态：已确定（2026-07-25 用户确认：按倾向方案执行）
- 背景：`AssistantConversation.tsx` 当前把用户消息渲染为 `ml-7 rounded-xl border bg-layer p-3`、助手消息渲染为 `mr-7 rounded-xl border bg-panel p-3`。问题有两个：
  1. 这些消息块位于 `bg-panel` 的侧栏卡片内部，构成卡片套卡片
  2. `bg-layer`(64) 比 `bg-panel`(23) **更亮**，违反"内层只能更暗"铁律
  
  同时注意 `ml-7`/`mr-7` 的左右缩进本身已经能区分用户与助手消息。
- 最终决定：用户消息保留 `variant="inset"` 底色（消息短、需要边界感），助手消息去掉容器只保留缩进（消息长、加框会让侧栏非常拥挤）。
- 选择原因：接近现代对话界面的通行做法，能显著减轻侧栏视觉重量；且用户/助手的区分不依赖边框，靠缩进与底色差异即可。
- 影响任务：2.1。此决策仅影响助手侧栏观感，不影响其他任务。

## 记录 006：画布节点是合法卡片，处理方式是豁免而非改造

- 日期：2026-07-25
- 状态：已确定
- 背景：`check:surface` 早期（规则收窄前）会命中大量画布节点文件（`ImageNode`、`VideoNode`、`GenerationNodeShell`、`StoryboardNode` 等），它们普遍使用 `rounded-[var(--node-radius)] border bg-surface-dark/xx`。曾考虑把它们也改造成非卡片形态。
- 最终决定：画布节点**符合卡片四条准入条件**（有独立交互与状态、可单独拖拽移动、与兄弟节点是并列实体、脱离上下文仍可理解），是合法卡片。处理方式是加**行级** `ui-surface-allow` 注释豁免，**不改动其样式**。
- 选择原因：画布节点就是 ComfyUI 式的节点卡片，这是该界面的既定视觉语言，改成无边框会破坏可用性（节点边界是连线与拖拽的视觉基础）。`--node-radius` 也是合法的组件层令牌。
- 影响任务：2.5（豁免标注）。同时确立了一条通用原则：**规则命中不等于违规，要先用卡片准入条件判断**。
- 补充约束：只允许行级豁免，禁止文件级 `ui-surface-allow-file`——否则该文件内将来真正的卡片套卡片也会被放行。

## 记录 007：GitHub Actions 工作流仍是 Tauri 时代产物，实际已失效

- 日期：2026-07-25（任务 1.3 执行中发现）
- 状态：**待确认**
- 背景：1.3 计划把 UI 规范检查接入 CI。检查 `.github/workflows/build.yml` 时发现它整份仍是 Tauri 时代的构建流程：
  - 引用 `src-tauri` 目录（已在 Tauri 清理中删除）
  - 调用 `npm run tauri:build:ci`、`npm run tauri:build:mac`（`package.json` 中均已不存在）
  - 安装 Rust 工具链、配置 `Swatinem/rust-cache` 的 `workspaces: src-tauri`
  - 产物路径指向 `src-tauri/target/release/bundle/msi` 与 `universal-apple-darwin`
  
  该工作流只在推 `v*` 标签或手动触发时运行，所以失效一直没被发现。一旦触发必然失败。
- 处理：本任务**未改动**该文件。改为把 `check:surface` 接入本地 `build` / `electron:build` 链路，满足实施方案"接入 CI **或**构建链路"的验收口径。不在一个已失效的工作流上叠加检查，否则会得到"已接入 CI"的假象。
- 选择原因：把 CI 从 Tauri 迁到 Electron 是独立的发布链路工作（涉及 electron-builder 产物路径、签名、Release 通道），范围和风险都超出"UI 设计系统统一"这个任务，应由用户单独决策。
- 影响任务：1.3 的 CI 部分标记为未达成（已在 `test-report.md` 说明）。
- 需要用户回答：是否要另开任务把 CI 迁到 Electron 构建链路（并在其中加入 `lint` / `tsc` / `check:*` / `vitest`）？还是暂时保持现状？
