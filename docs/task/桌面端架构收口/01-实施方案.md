# 桌面端架构收口实施方案

## 当前项目现状

Henji-AI 当前是 Electron + React + TypeScript 桌面应用。主生成链路已经迁到 Electron 后端能力：前端通过 `src/core/services/GenerationService.ts`、`src/commands/aiRuntime.ts`、`src/platform/*` 进入 `electron/main/services/ai-runtime/**`。LLM 流式请求走 `src/commands/llmRuntime.ts` 和 `electron/main/services/llm/**`。视频压缩和裁剪走 `src/commands/video.ts` 与 `electron/main/services/video/ops.ts`。图片主实现已在 `electron/main/services/image/ops.ts` 使用 Sharp。

仍需治理的地方集中在边界和兜底策略：`src/commands/image.ts` 仍有多处前端 canvas/data URL fallback；提示词优化附件在渲染层将文件和 blob 转成 data URL；`src/services/database/DatabaseService.ts`、`src/services/canvasProjects/CanvasProjectService.ts` 和 `src/commands/projectState.ts` 仍通过通用 `DbPlatform` 在渲染层持有 SQL；`electron/main/ipc/system.ts` 暴露通用文件、删除、网络能力；若干设置和模型扩展仍直接用 localStorage；`src/utils/falUpload.ts` 与 `src/core/providers/base/utils.ts` 是迁移后的遗留入口。第一阶段复核确认这些问题仍存在，后续 6 个任务继续成立。

## 第一阶段确认结论

- 桌面端生产路径：模型运行、LLM 请求、多媒体上传/转码、图像裁剪/拆分/合并/持久化、数据库事务、文件删除与网络下载上传等重型或安全敏感逻辑必须优先在 Electron 主进程执行。
- 裸 Vite 调试路径：允许保留 web-only fallback，用于界面调试和非桌面能力兼容，但必须通过运行时判断隔离，不能成为 Electron 生产路径的静默兜底。
- 测试脚本路径：允许 mock 平台能力或显式进入测试分支；测试兼容不能要求生产代码在主进程失败后自动回落到浏览器重活。
- 可留在渲染层：UI 状态、轻量预览、用户交互测量、展示 URL 组装、轻量图片/视频首帧预览可保留，但不应作为大文件长期持久化或后端协议适配主路径。
- 必须治理的高风险链路：Electron 图像命令失败后的 canvas/data URL fallback、提示词优化视频/图片附件 data URL、缩略图缓存文件再读成 data URL、渲染层 raw SQL、通用 `fs/http` 暴露过宽、localStorage 中的业务配置/敏感遗留入口。

## 当前存在的问题

- 桌面端主进程调用失败后，部分图像命令会静默回到渲染层执行，容易造成 UI 卡顿并掩盖主进程问题。
- 大媒体附件转 data URL 会造成内存膨胀、IPC 大包传输和日志/调试风险。
- 通用 `fs/http/db` 能力可被渲染层业务直接消费，长期会削弱领域边界。
- localStorage 同时承担轻量偏好、业务配置和迁移兼容，数据来源不够清晰。
- core 层存在反向依赖 UI 的历史结构，如 `src/core/panels/registerDefaultPanels.ts`。

## 最终目标

- Electron 桌面端下，重型媒体处理、上传、下载、数据库事务、模型发现和安全敏感逻辑优先在主进程执行。
- 渲染层保留 UI、交互、预览、轻量测量和用户状态展示，不负责执行模型供应商协议、不处理大文件字节流、不持有数据库 schema。
- fallback 策略清晰：桌面端主进程失败应暴露错误或进入明确降级路径，不应悄悄回退到高成本浏览器实现。
- 保留必要兼容，但迁移后的旧入口要标记、收敛或删除。

## 总体解决思路

先做边界清单和策略确认，再改高收益链路。优先级按风险排序：图像和大媒体处理高于数据接口治理，数据接口治理高于依赖和遗留入口清理。每个任务只处理一个职责面，避免一次性重构过大。

## 任务范围

- 图像命令和画布图像工具的主进程优先策略。
- 提示词优化中的图片、视频附件传递方式。
- 缩略图、预览图和媒体 metadata 中不必要的 data URL 返回。
- 数据库服务从通用 SQL IPC 向领域 IPC 的迁移计划和逐步落地。
- localStorage 使用分级治理。
- 遗留 provider/upload 工具和依赖的确认与清理。

## 非任务范围

- 不重做 Electron 迁移计划中已经完成的基础壳、preload、打包、更新、DPI、smoke 等工作。
- 不新增模型，不调整模型参数 schema，除非某个任务验证时发现必须配合字段迁移。
- 不处理 Windows/macOS 签名、公证、真实 GitHub Release 发布。
- 不进行画布交互人工验证，相关验证步骤交给用户执行。

## 阶段划分

第一阶段用于形成可执行基线：确认哪些 fallback 和通用能力可以保留，哪些必须治理。第二阶段处理最容易造成性能和内存问题的媒体链路。第三阶段处理数据库、存储和遗留入口，降低后续开发继续“网页化”的概率。

第二阶段中的 `2.1` 是 `2.3` 的前置，因为缩略图和媒体预处理要复用或对齐图像主进程能力。`2.2` 可在 `1.1` 后并行推进，不依赖 `2.1`。第三阶段可与第二阶段部分并行，但涉及全局接口和迁移时应避开同一文件的并发修改。

## 新旧实现兼容方式

- 兼容路径要显式标识运行环境：桌面端、裸 Vite 调试、测试脚本三类分开处理。
- 如果保留 web fallback，需要有日志或类型层面的约束，避免 Electron 生产路径静默命中。
- Electron 生产路径主进程能力失败时，默认抛出明确错误并保留函数名、输入来源类型和耗时日志；只有明确标记为轻量 UI 预览或 web-only 的路径可以执行浏览器 fallback。
- 图像裁剪、拆分、合并、持久化、保存目录、缩略图缓存和提示词优化附件处理不允许在 Electron 生产路径静默回到浏览器 data URL/canvas 重活。
- 数据迁移优先采用读旧写新或启动迁移，不直接删除用户已有 localStorage 数据。
- 旧接口若未立即删除，应改为抛出明确错误、标记废弃，或限制在测试/兼容层使用。

## 风险控制方式

- 大媒体链路先做小范围替换，并保留明确错误提示；如需临时回退开关，应只面向开发/测试环境，不作为生产默认行为。
- 数据服务改造时先新增领域 IPC，再逐步迁移调用方，最后收紧 raw SQL 暴露。
- 每个任务完成后运行与变更范围匹配的检查；涉及 Electron 主进程时至少运行 `npx tsc -p tsconfig.electron.json --noEmit` 和 Electron 侧 eslint。
- 涉及 UI 和画布交互时，提供用户手动验证步骤，不自行操作验证。

## 回退或恢复原则

- 单任务独立提交，出现问题优先回退对应提交。
- 对用户数据有影响的任务必须先确认迁移和回滚策略，不直接删除旧数据。
- 若主进程能力在某平台不可用，优先暴露明确错误和替代路径，不静默回到 UI 线程做重活。

## 全局开发约束

- 遵守项目 `AGENTS.md`：中文回复，代码改动后说明是否需要重启 `npm run electron:dev`。
- 新增或修改代码禁止引入裸 `any`，导出函数补显式返回类型。
- 不在业务 UI 新增原生控件，不直接引入 Electron、Node 或旧 Tauri API。
- 颜色、UI primitive、模型配置驱动、画布目录约束继续有效。

## 最终验收条件

- 高风险媒体链路不再在 Electron 生产路径静默使用浏览器 canvas/data URL 大对象 fallback。
- 提示词优化附件不再把大视频直接转 data URL 传入主进程。
- 数据库和通用系统能力有明确领域边界，新增业务不需要直接拼 SQL 或直接调用通用 `fs/http`。
- localStorage 使用有清单和迁移策略，密钥和业务配置不再走旧的前端存储入口。
- 计划总览、任务记录和重要决定与实际代码状态同步。
