### 2026-10-03 代码阶段（子 Agent，未提交）

#### 一、选型：取帧后端

| 方案 | 格式覆盖 | 实测性能 | 与预览播放的关系 | 缓存与改动面 | 结论 |
|---|---|---|---|---|---|
| 原生解码服务按时间点出帧（`frame_at`，1.3） | FFmpeg 9 全部格式 | 4K60 H.264 冷取 p50 277 ms、同 GOP 热取约 6 ms（1.3 表） | 同一服务进程、同一块显卡解码器；缩略图要与播放会话争用硬解与会话预算，需在服务内另做优先级调度 | 输出只有 D3D11 共享纹理，没有 CPU 读回与编码：要么改 Rust 协议加“读回 + 缩放 + 编码”命令（重建原生 release），要么在渲染进程 Worker 里读纹理、编码后再回传主进程落盘 | 不用 |
| FFmpeg 命令行（与原生服务同一份 9.0.2 构建）+ 磁盘缓存 | 同上（同一份库） | 4K60 每帧 31–319 ms（下表），命中 ≈ 0.15 ms/帧 | 独立子进程、软解、低于正常优先级；不碰原生服务与显卡解码会话 | 主进程已有 FFmpeg 定位、内容身份与原子写缓存，可复用 | **采用** |

结论：格式覆盖相同（同一份 FFmpeg），原生路径的速度优势只在首次生成，而它要么改原生协议、要么让渲染进程承担读回编码，并与播放争用同一解码器；缩略帧落盘后重开即命中，首次生成的速度不是瓶颈，隔离更重要。命令行方案在低优先级独立进程里运行，播放不受影响（Electron 验收第 5 节验证）。

#### 二、取帧与调度（`electron/main/services/video/filmstrip.ts`）

- 一个进程取同一素材、同一高度的多个时间点：每个时间点一路 `-threads 2 -ss <相对容器起点> -i`、一路 `-map i:v:0 -frames:v 1 -vf scale=w='max(2,trunc(H*dar/2)*2)':h=H:flags=area -c:v libwebp -quality 75`，直接写到缓存目录的临时文件再原子改名。按显示比例（含非方形像素）缩放，`area` 适合 4K → 几十像素的大倍率缩小。
- 时钟：请求是素材绝对时钟（与剪辑源时间同一时钟）；容器起点每个素材 ffprobe 一次后相减。不用 `-seek_timestamp 1`：实测 9.0.2 在起点 1.43 s 的 M2TS 上 3 s 之后的精确裁剪取不到帧。取到的是呈现时间不早于请求时间的第一帧；首格时间向下取整到微秒，正好落在入点那一帧。
- 直接定位解不出画面的帧（MPEG-TS 按字节定位落在非关键帧上，长 GOP H.264 TS 实测整段无输出）自动重试一次：输入侧定位到目标前 10 s，输出侧 `-ss` 解码丢弃到目标。
- 内存：每路输入常驻一套参考帧，实测（`-benchmark` maxrss）4K H.264 约 120 MB/路、4K HEVC 10 位与 ProRes 4444 约 210–230 MB/路，8 路同进程达 1.8 GB。因此每进程按 1800 万像素限制同时解码的输入（4K 2 路、1440p 4 路、1080p 8 路），超出的同批帧在同一槽位里顺序分进程；两个槽位合计 4K 不超过约 1 GB。
- 调度：相同帧共享一次生成；按“素材 + 高度”分组，攒 16 ms 成批（每批 ≤ 8 帧），组间轮转，一个长片段不会饿死其他素材；并发 2 个进程；进程以 `PRIORITY_BELOW_NORMAL` 运行、30 s 超时；排队中的帧无人等待即移除，整批都无人等待时结束进程，之后同一帧的新请求重新生成而不挂到被取消的进程上；应用退出时结束在跑的进程。
- 日志：`main.video.filmstrip` 的 `video.filmstrip.batch.started/completed`（debug，含帧数、重试数、耗时）、`batch.partial`/`batch.failed`（warn，含 FFmpeg stderr 前 1 KB）。

#### 三、缓存

- 键：`sha256(['filmstrip', 格式版本, 内容身份, 绝对时间µs, 高度档])`，文件 `userData/HenjiCache/Filmstrip/<键>.webp`。内容身份与 2.3 波形同一实现（`services/media/content-identity.ts`：真实路径 + dev + ino + 大小 + 纳秒级 mtime/ctime），请求时 1 s 内复用，生成后重新读取核对，文件在生成期间被改写则整批作废。
- 时间点按缩放量化：网格为 1/64 s × 2^k，k 取“不大于一格代表时长”的最大值，因此放大一级只新增一半的帧、缩小一级全部命中；同一素材的不同片段共享帧；每个片段第一格固定取入点那一帧。高度按设备像素分 32/48/64/96/128/192/256 七档。
- 磁盘上限 256 MB，超出按最久未用删到 80%，读命中刷新使用时间，残留临时文件 10 分钟后清理；目录扫描最多每 60 s 一次（文件多而小）。原 2.3 的波形磁盘缓存提为共用的 `services/media/content-disk-cache.ts`（扩展名参数化，新增 `locate`/`prepareTemporary`/`adopt` 与清理节流），波形行为不变。
- 渲染层（`services/videoFilmstrip/filmstripFrameService.ts`）：按“素材 + 修订 + 时间 + 高度”持有帧路径，解码（`Image.decode()`）完成才算就绪，换图不闪；就绪帧按“素材 + 高度”建有序索引，缩放后新时间点未到时显示同一素材最近的已有帧，不留白；在途 24、首格优先，无人显示即取消；失败只记一次日志、片段显示底色。

#### 六、性能

**取帧吞吐与命中**（`HENJI_FILMSTRIP_NATIVE=1 HENJI_FILMSTRIP_BENCH=1 npx vitest run electron/main/services/video/filmstrip.native.test.ts`，专业格式矩阵 3 s 样本，每个 12 帧铺满 3 s，64 px 高，本机 24 核）：

| 样本 | 首次 12 帧 | 每帧 | 新会话命中 12 帧 |
|---|---|---|---|
| H.264 8 位 4K60 MP4 | 2483 ms | 207 ms | 2.0 ms |
| HEVC Main10 4K60 MKV | 3829 ms | 319 ms | 1.8 ms |
| AV1 4K60 MP4 | 2414 ms | 201 ms | 1.8 ms |
| ProRes 422 HQ 4K60 | 890 ms | 74 ms | 2.0 ms |
| ProRes 4444 透明 | 1583 ms | 132 ms | 1.7 ms |
| DNxHR HQX 4K60 | 1371 ms | 114 ms | 1.9 ms |
| CineForm 4K60 | 2060 ms | 172 ms | 2.1 ms |
| MPEG-2 M2TS（起点 1.43 s） | 367 ms | 31 ms | 1.8 ms |

不限内存时（一进程 8 路）4K H.264 为 125 ms/帧、HEVC 10 位 187 ms/帧，但单进程峰值 0.95–1.8 GB；现取内存上限，4K 慢约 1.6 倍。命令行单帧（一进程一帧）为 290–630 ms，进程启动本身约 160 ms，成批后摊薄。

**时间线主线程耗时（改前/改后对照）**：jsdom 中直接渲染 HEAD 版与改后版 `VideoEditTimelineCanvas`（4 轨 500 片段、视口 48 个可见片段、改后 96 张缩略图已就绪），120 步横向滚动与 40 步缩放，每步 `act()` 墙钟（React 渲染 + 提交，不含浏览器布局与绘制；临时基准未入库，脚本在会话草稿目录）：

| | 改前 均值 / p95 / 最大 | 改后 均值 / p95 / 最大 |
|---|---|---|
| 滚动（两轮） | 3.89 / 5.89 / 9.67 ms；3.46 / 4.58 / 9.72 ms | 4.34 / 6.16 / 9.79 ms；4.24 / 6.33 / 9.84 ms |
| 缩放（两轮） | 4.88 / 8.68 / 10.82 ms；4.70 / 11.04 / 13.80 ms | 7.63 / 11.19 / 19.03 ms；7.12 / 10.55 / 20.40 ms |

滚动只多约 0.5–0.8 ms（可见范围取整后完全可见的片段不重绘；取整前为 +2 ms）；缩放每步多约 2.5 ms（每个可见片段重新铺格、换图片位置，属固有成本；jsdom 的 DOM 操作比 Chromium 慢，绝对值仅作对照）。真实 Electron 的帧间隔与长任务由新场景 `video-edit-filmstrip` 测量（见第八节）。
