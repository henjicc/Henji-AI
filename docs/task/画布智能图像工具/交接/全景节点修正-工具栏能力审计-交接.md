## 一眼结论

720° 全景节点的“生成”按钮声明和执行器均正确。异常的“更多”并不是全景节点自己的动作，而是图片能力工具条把节点端口的静态声明“将来会输出图片”误判成“当前已有或正在形成可继续处理的图片”。

全景生成节点本身不会持有本次生成结果：它会创建独立的 `exportImageNode` 结果节点。因此全景节点的 `getOutputs()` 为空是正常状态，并且不会因为左侧已经连入参考图而改变。当前工具条仍把九项图片能力全部收入“更多”，随后又因九项能力都要求真实图片而把它们全部标成不可用，最终形成用户看到的“有菜单、无动作”。

应只修改一个业务判断入口：

`src/features/canvas/ui/canvasImageCapabilityLayout.ts` 的 `resolveCanvasImageCapabilityActionsForSourceNode()`。

不要改全景节点、能力注册表、生成按钮声明或“更多”组件。

## 两套能力声明不能混淆

| 声明 | 所在位置 | 含义 | 720° 当前状态 |
|---|---|---|---|
| `capabilities.toolbarGenerate` | `domain/nodeRegistry.ts` | 选中当前节点时是否可执行这个节点自己的生成任务 | `true`，正确 |
| `executionKind` + 已注册 executor | 节点定义与节点组件 | “生成”按钮最终交给哪个画布执行器 | `standard-generation` + `GenerationNodeShell`，正确 |
| `media.role: 'generator'` | `domain/nodeRegistry.ts` | 当前节点是生成参数/输入宿主，不是素材或结果宿主 | 正确 |
| `ports.source.emits: 'image'` | `domain/nodeRegistry.ts` | 这个类型的输出端口在连线协议中是图片端口 | 正确，但只是静态端口类型 |
| `getOutputs(data)` | `domain/nodeRegistry.ts` | 当前节点此刻已有的真实、可被下游消费的媒体 | 为空，正确；结果在独立 `exportImageNode` |
| 九项图片能力动作 | `capabilities/builtInCapabilities.ts` + 工具条解析器 | 对选中节点已经物化的图片继续做全景、打光、高清等处理 | 全景生成节点不应出现 |

## 根因链路

1. `NodeActionToolbar.tsx` 对所有选中节点调用 `resolveCanvasImageCapabilityActionsForSourceNode(node)`。
2. 该函数先调用 `getNodeMediaOutputs()`。全景生成节点没有自身结果，得到 `[]`。
3. 函数又调用 `resolveNodeSourceMediaKind()`。全景节点端口声明 `emits: 'image'`，因此得到 `image`。
4. 当前筛选条件在真实输出为空时，仅凭 `declaredKind === 'image'` 就保留全部九项图片能力，没有区分 `media.role` 是 `source`、`generator` 还是 `result`。
5. 映射阶段发现九项能力都声明 `requireMaterializedMedia: true`，统一写入 `imageCapabilities.unavailable.sourceNotReady`。
6. `partitionCanvasImageCapabilities()` 只允许可执行项直显，因此直显区为空；全部九项进入溢出分组。
7. `CanvasImageCapabilityActions` 只看到溢出分组非空，于是渲染“更多”；菜单内九项全部 `aria-disabled=true`。
8. `NodeActionToolbar` 还因为动作数组非空渲染一条能力区分隔线，进一步强化了“这里应该有动作”的错误暗示。

左侧参考图是否已连接不影响上述结果：能力菜单处理的是“选中节点的输出媒体”，不是它的输入媒体。

## 唯一修复入口与建议语义

在 `resolveCanvasImageCapabilityActionsForSourceNode()` 中读取同一 `CanvasNodeDefinition` 的 `media.role`，把“没有真实输出时仍展示禁用能力”的发现态限制为素材或结果宿主：

1. 有匹配的真实 `getOutputs()`：按现有数量范围和能力发布状态返回动作，不受 `media.role` 限制。
2. 没有真实输出：
   - `media.role === 'source'`：保留现有空上传节点的“更多 + 未上传原因”。
   - `media.role === 'result'`：保留生成中结果占位节点的“更多 + 正在生成原因”。
   - `media.role === 'generator'`：返回空动作；该节点只有自身生成任务，不展示针对未来结果的派生能力。
   - 没有明确图片角色：维持不展示，避免仅凭端口推测产品语义。
3. 如果旧项目中的生成节点确实持有可由 `getOutputs()` 读出的历史图片，仍走第 1 条并允许继续处理，兼容旧数据。

建议实现形状是基于已有声明的通用判断，例如“`outputs.length === 0` 时只允许 `source/result` 进入待就绪发现态”。不得新增 `isPanoramaGenerationNode()`、节点类型数组、能力 ID 或模型 ID 分支。

### 明确不要修改

- 不要把 `panoramaGenNode.capabilities.toolbarGenerate` 改为 `false`；这会同时删除真正需要的“生成”按钮。
- 不要关闭 `image.panorama` 或其他图片能力；它们在真实图片结果节点上应继续可用。
- 不要在 `NodeActionToolbar.tsx` 写 `if (panorama)` 或维护特殊生成节点名单。
- 不要让 `CanvasImageCapabilityActions` 在“全部禁用”时一律返回空；空上传节点和生成中结果节点仍需要可恢复原因。
- 不要删除 `ports.source.emits` 或生成节点的 `getOutputs` 兼容读取；它们服务连接协议和旧数据，不应被工具条缺陷反向破坏。

## 旁支契约问题

`CanvasNodeCapabilities.toolbar` 的注释和 `canvas-node-builder` 都把它定义为“是否显示选中节点顶部工具条”，但 `SelectedNodeOverlay.tsx` 当前没有读取此字段，任何单选节点都会渲染 `NodeActionToolbar`。因此 `groupNode`、`storyboardSplitNode`、数值源和模型选择器等声明 `toolbar: false` 的节点实际上仍会出现基础工具条。

这不是 720° “更多”问题的根因，也不应与本次主修复混在同一补丁里。后续需要单独决定：

- 若字段语义仍有效，在 `SelectedNodeOverlay` 统一执行，并重新确认分组节点的“解散”入口；或
- 若所有节点都需要删除等基础工具条，删除/重命名这个失真的声明字段和对应文档。

在未完成上述产品语义核对前，不建议直接让 `toolbar: false` 生效，以免让分组节点失去唯一的解散按钮。

## 精确测试建议

### 纯逻辑：`canvasImageCapabilityLayout.test.ts`

新增表驱动回归，枚举所有图片生成宿主：`imageEdit`、`panoramaGen`、`relightGen`、`upscaleGen`、`portraitTextureGen`、`elementEditGen`、`storyboardGen`、`multiAngleGen`、`layerSeparationGen`。

- 使用各定义的默认数据或等价无结果数据，断言动作数组为 `[]`。
- 全景节点即使 `mediaInputs.image` 已有一张图，仍断言动作数组为 `[]`，证明输入媒体不会冒充选中节点输出。
- 空 `uploadNode` 继续断言九项动作均为 `sourceNotReady`，防止修复误删上传恢复提示。
- 生成中的 `exportImageNode` 继续断言九项禁用动作，证明 `result` 待就绪语义保留。
- 已完成 `exportImageNode` 断言九项能力按现有优先级可执行。
- 可选兼容用例：生成节点数据带旧版可读 `imageUrl` 时仍返回可执行动作。

### 组件：`CanvasImageCapabilityActions.test.tsx` / `NodeActionToolbar` 定向测试

- `actions=[]` 时无直达按钮、无“更多”。
- 选中全景生成节点时存在“生成”和“删除”，不存在 `data-image-capability-more="true"`，也不存在图片能力区分隔线。
- 选中空上传节点时仍存在“更多”，九项均可聚焦、禁用且展示恢复原因。
- 选中已完成全景结果节点时按窗口容量显示直达项和“更多”，避免把生成宿主修复误扩散到结果宿主。

### 正式 Electron：`canvas-panorama-toolbar`

现有场景只检查来源入口、相邻节点创建、选中和连线；它在创建后选中了全景节点，却没有核对选中工具条内容。应在现有场景的 `generatedNode` 选中断言后补：

- “生成”按钮可见。
- `[data-image-capability-more="true"]` 数量为 0。
- 图片能力分隔线数量为 0。
- “删除”仍可见。
- 不点击“生成”，继续保持零付费。

建议再用同一纯逻辑矩阵覆盖其余八个图片生成宿主，不需要为每种节点各建一套 Electron 场景。

### 声明一致性旁支测试

为 `SelectedNodeOverlay` 增加 `toolbar: false` 的契约测试前，必须先确定分组解散入口；该测试属于旁支任务，不应阻塞全景工具条主修复。
