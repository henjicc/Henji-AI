# 全景查看节点架构审计交接

- 日期：2026-08-29
- 审计范围：全景生成结果落点、节点注册、项目迁移、连线、复制、媒体输出、工具条与持久化兼容
- 工作性质：只读审计，未修改业务代码

## 一、结论

建议新增一等结果节点 `panoramaViewerNode`（中文名“全景查看”），并把 `panoramaGenNode` 的 `generation.resultNodeType` 从 `exportImageNode` 改为该节点。全景生成节点继续只负责生成；新节点负责节点内直接球面浏览、平面/全景切换、视口比例和当前视角截图。

旧项目中精确满足 `type === exportImageNode && data.resultKind === 'panorama'` 的节点，应在 `canvasStore` 载入归一化时原位迁移为 `panoramaViewerNode`。节点 ID、位置、尺寸、标题、媒体路径、生成状态、父组关系和所有边保持不变，因此无需创建替代节点或重连，撤销历史快照也能一起升级。`resultKind: 'panorama'` 仍建议保留为结果语义和下载 GPano 判定，不再承担组件路由职责。

该改动会推翻计划中的“全景首版不新增独立结果节点类型”决定。实施时必须同步更新 `00-任务总览.md`、`01-实施方案.md` 和 `重要记录.md`，将记录 002 标为“已废弃”，并新增一条独立全景查看节点的决定记录；记录 010 的项目内主真相应改为“`panoramaViewerNode + resultKind: panorama`”。

## 二、当前真实链路

### 1. 节点类型与结果语义

- `src/features/canvas/domain/canvasNodes.ts`
  - `CANVAS_NODE_TYPES.panoramaGen = 'panoramaGenNode'`。
  - 当前没有独立全景结果类型；全景结果是 `ExportImageNodeData.resultKind = 'panorama'`。
  - `resolveCanvasImageResultKind()` 把损坏值降级为普通图片。
  - `isExportImageNode()`、`nodeHasImage()` 仍把所有图片结果视为同一种节点。
- `src/features/canvas/domain/nodeDisplay.ts`
  - `exportImageNode` 根据 `resultKind` 解析默认标题；`panorama` 显示为“720°全景”。

### 2. 生成占位与完成提交

- `src/features/canvas/domain/nodeRegistry.ts`
  - `panoramaGenerationNodeDefinition.generation.resultNodeType` 当前是 `CANVAS_NODE_TYPES.exportImage`。
  - `exportImageNodeDefinition` 是图片结果的通用注册项，声明图片输出、下载和结果角色。
- `src/features/canvas/nodes/PanoramaGenerationNode.tsx`
  - 通过 `GenerationNodeShell` 传入 `resultNodeExtraData={{ resultKind: 'panorama' }}`。
- `src/features/canvas/nodes/shared/GenerationNodeShell.tsx`
  - 从注册表读取 `resultNodeType`，在模型调用前创建对应占位节点，再用统一完成契约提交结果。
  - 创建来源到占位节点的边时调用 `canvasStore.addEdge(sourceId, resultId)`。
- `src/features/canvas/application/generationOutputApplicationService.ts`
  - 通过传入的 `resultNodeType` 校验占位类型、查幂等提交、写入媒体补丁。
  - `createCompletedNodeData()` 对图片结果继续写 `resultKind`，因此新节点可以无修改复用单结果原子提交。
  - `getResultNodeMediaType()` 从“哪个生成节点声明了该结果类型”反查媒体类型；全景生成定义改指新类型后会自然得到 `image`。

结论：不需要改模型调用、媒体落盘或完成契约，只需把全景生成注册项的结果类型换成新节点，并让新节点注册为图片结果。

### 3. 当前渲染与查看

- `src/features/canvas/nodes/index.ts`
  - `exportImageNode` 统一渲染 `ImageNode`；新增类型必须注册新的组件映射。
- `src/features/canvas/nodes/ImageNode.tsx`
  - 通过 `type === exportImageNode` 和 `resultKind === panorama` 显示全景标识，并把双击路由到全景模态查看器。
  - 节点本体仍是平面 `<img>`，节点尺寸按源图 `aspectRatio` 约束；这正是无法在节点内表达“2:1 源图 + 16:9/4:3 视口”的根因。
- `src/features/canvas/ui/CanvasNodeImage.tsx`
  - 只负责双击打开查看器，适合普通图片，不适合作为节点内球面交互入口。
- `src/features/canvas/ui/specialInterfaces/panorama/PanoramaSphereCanvas.tsx`
  - 已有可复用的 R3F 球面渲染、拖拽、滚轮缩放、复位与资源释放。
- `src/features/canvas/ui/specialInterfaces/panorama/PanoramaViewerModal.tsx`
  - 已有平面/球面切换、原图下载、全屏、错误降级和懒加载资源。

结论：新节点不应复制 Three.js 资源创建逻辑；应复用并适度抽象 `PanoramaSphereCanvas`。节点内专属面板放入 `src/features/canvas/nodes/panoramaViewer/`，节点主文件只负责编排、端口、尺寸和数据更新。

## 三、建议的数据与注册契约

### 1. 新类型与数据

在 `src/features/canvas/domain/canvasNodes.ts` 增加：

```ts
panoramaViewer: 'panoramaViewerNode'

type PanoramaViewportAspectRatio = '21:9' | '16:9' | '3:2' | '4:3' | '1:1'
type PanoramaViewerDisplayMode = 'panorama' | 'flat'

interface PanoramaViewerNodeData extends NodeImageData {
  resultKind: 'panorama'
  displayMode: PanoramaViewerDisplayMode
  viewportAspectRatio: PanoramaViewportAspectRatio
}
```

建议默认 `displayMode: 'panorama'`、`viewportAspectRatio: '16:9'`。`aspectRatio` 继续描述原始等距柱状图，必须是实际媒体比例（正常为 `2:1`）；`viewportAspectRatio` 只描述节点内观察窗口，不能复用或覆盖 `aspectRatio`。

首版不建议把连续拖拽产生的 yaw、pitch、fov 每帧写进 Zustand：这会制造历史快照、项目保存和节点重渲染压力。相机姿态先保留在查看组件内；若产品后来明确要求“保存当前机位”，只在指针释放时以一个独立 `cameraView` 对象落盘，并使用单一 history group。

### 2. 注册表声明

在 `src/features/canvas/domain/nodeRegistry.ts` 增加独立定义，建议为：

- `visibleInMenu: false`：它是生成结果，不由节点菜单手工创建。
- `capabilities: { toolbar: true, promptInput: false, toolbarDownload: true }`：保留通用下载和删除；视口切换、比例和截图放节点内专属面板。
- `media: { kind: 'image', role: 'result' }`。
- `ports.source: { emits: 'image' }`，复用 `imageOutputsFromData`。
- `connectivity.sourceHandle: true`、`manualSource: true`，截图后的普通结果和后续图片能力都可从该节点继续连接。
- `connectivity.targetHandle: true`，保留生成来源到结果的溯源边。
- 不建议给这个溯源 target 声明 `ports.target.accepts`：当前 `canvasStore.addEdge()` 固定写 `targetHandle: 'target'`，它不是用户向查看器注入媒体的输入行。若声明图片输入，则按项目规则必须迁移为 `targetHandleMode: 'rows'`，但 `GenerationNodeShell` 创建的边仍会指向不存在的 `target`，造成悬空端口。首版应把该 target 明确定义为生成关系锚点，而不是媒体输入。

此处不要在通用组件中增加 `if (type === 'panoramaViewerNode')`。结果类型、输出、下载和连接能力均通过注册表声明；只有新节点自己的组件可以读取自身专属字段。

## 四、旧项目无损迁移

### 1. 迁移时机

迁移应落在 `src/stores/canvasStore.ts` 的 `normalizeNodes()`，因为这里同时覆盖：

- 项目打开和项目切换；
- 撤销/重做历史快照的归一化；
- 未知节点过滤、默认数据合并和瞬时状态恢复。

在读取节点定义和合并默认数据之前，先解析规范节点类型：

1. 原类型是 `exportImageNode`；
2. 原数据的 `resultKind` 精确等于 `panorama`；
3. 满足时将内存节点类型改为 `panoramaViewerNode`；否则维持原类型。

建议把纯判断提取到 `src/features/canvas/domain/nodeMigrations.ts`，例如 `resolveMigratedCanvasNodeType(type, data)`，并给它添加精确测试。不要按标题、图片比例或 GPano 元数据猜测：这些信息可能被用户修改或缺失，只有既有 `resultKind` 是项目内权威语义。

### 2. 需要保持的字段

迁移只改变 `type` 并补新节点默认数据，以下内容原样保留：

- `id`、`position`、`width`、`height`、`style`、`parentId`、`hidden`；
- `displayName`（包括用户自定义标题）；
- `imageUrl`、`previewImageUrl`、`aspectRatio`；
- `isGenerating`、`serverTaskId`、`serverTaskModelId`、`generationOutputCommitId`、`generationOutputDescriptor`；
- 与该 ID 连接的全部边。

特别注意正在轮询的旧全景占位：迁移后 `useCanvasResumePolling.ts` 会以新节点类型继续提交结果。要增加测试证明 `panoramaGenNode.generation.resultNodeType` 已指向新类型，且 `getResultNodeMediaType(panoramaViewerNode) === 'image'`，否则恢复提交会在结果媒体类型校验处失败。

### 3. 边与端口

`normalizeEdgesWithNodes()` 只要新定义仍声明 target/source handle，就会保留旧边。新节点 DOM 必须继续渲染 `id="target"` 和 `id="source"`，才能与历史边和 `GenerationNodeShell` 的自动边一致。

不要把新节点 target 直接迁移到 `mediaPortId('image')`，除非同时把 `canvasStore.addEdge()` 的自动生成边改为按注册表解析端口，并对所有结果节点做回归；这是更大的公共链路改造，不是本次必要条件。

### 已经声明化的部分

- `SelectedNodeOverlay.tsx` 会显示 `NodeActionToolbar`，当前没有实际读取 `definition.capabilities.toolbar`，所以新增节点只要被选中就会出现工具条。`toolbar` 字段目前更像契约信息，不能依赖它隐藏工具条。
- `useNodeDownload()` / `canvasMediaDownload.ts` 已按注册表工作。
- `canvasImageCapabilityLayout.ts` 已通过 `getNodeMediaOutputs()` 判断图片派生能力；新节点会自动获得全景、打光、多角度等图片能力入口。

### 仍有类型白名单的部分

- `NodeActionToolbar.tsx` 的复制图片和资产收集来源仅识别 `isUploadNode/isImageEditNode/isExportImageNode`。
- `tools/builtInTools.ts` 与 `NodeToolDialog.tsx` 的编辑、裁剪、宫格切分也只识别上述三类。

建议处理方式：

1. 复制和资产收集改为从当前节点定义的首个图片输出读取，复用 `getNodeMediaOutputs()`，避免为新节点继续加类型判断。

3. 节点内专属面板承载 `平面/全景`、`观察窗口比例`、`截图当前视角`；这些按钮不要再进入顶部工具条。
4. 如果用户仍认为顶部派生能力过多，应给 `CanvasNodeCapabilities` 增加声明式工具条策略（例如是否显示图片派生能力），由 `NodeActionToolbar` 读取；不要在工具条组件里按全景节点类型排除。

## 七、当前视角截图的结果语义

截图得到的是当前透视相机视口中的普通图片，不再是 2:1 等距柱状全景，因此必须创建普通 `exportImageNode`，`resultKind` 为 `image`，且不能写 GPano 元数据。

建议流程：

1. `PanoramaSphereCanvas` 对外暴露一次性捕获当前帧的受控接口，不让父组件直接操作 Three 内部对象。
2. 捕获尺寸按所选 `viewportAspectRatio` 生成 PNG；默认长边可控制在 1920 或 2048，避免按画布缩放后的 CSS 像素得到低清图。
3. 调用现有 `prepareNodeImage()` 或等价受管媒体入口落盘并生成缩略图，禁止把 `data:` URL 直接写进节点数据。
4. 使用现有相邻布局和普通 `exportImageNode` 创建结果，并连接 `panoramaViewerNode -> exportImageNode`。
5. 节点创建或连线失败时释放本次新建的受管原图和缩略图，遵循现有生成结果的媒体所有权原则。

截图如果只调用“另存为”而不落画布，会与用户所说“导出成一张图片”存在歧义。结合当前产品所有编辑结果都会回到画布继续使用的模式，推荐首版创建普通图片结果节点；原始 2:1 全景的文件下载继续保留在顶部通用下载入口。

## 九、关键风险与防护

1. **ReactFlow 拖节点与球面拖视角冲突**：球面交互根元素必须使用 `nodrag nowheel`，同时停止指针事件向节点拖拽层冒泡；target/source handle 和 resize handle 不能被遮挡。
2. **多 WebGL 上下文**：原计划明确避免每个全景节点常驻 WebGL。新需求改变了该前提，建议只有选中且达到内容 LOD 的全景节点挂载球面 Canvas；未选中或低倍率时显示静态预览。若要第一次按下就直接旋转，可在静态层 pointerdown 时选中节点并激活，但不要让所有不可见节点常驻 Three context。
3. **节点源图比例与视口比例混淆**：`aspectRatio` 只描述 2:1 原图，`viewportAspectRatio` 只描述观察窗口；下载、GPano、模型契约不得读取后者。
4. **截图资源所有权**：截图落盘成功但节点事务失败时必须释放本次创建文件，不能遗留孤儿媒体。
5. **旧任务续查**：迁移后的节点类型必须与新注册表结果类型一致，否则 `generationOutputApplicationService` 会把占位判断为不存在或媒体类型不匹配。
6. **画布性能结论**：节点 DOM 和 WebGL 热路径变化后必须运行 `npm run check:canvas-visual`；若涉及多节点平移性能，只能用 `npm run electron:pan-bench` 得出结论，不能以占位压力场景代替。

## 十、建议实施顺序

1. 新增类型、数据、注册表和默认标题，先让类型检查锁定所有遗漏的穷举映射。
2. 修改全景生成结果类型，并补生成/恢复契约测试。
3. 实现旧节点类型迁移，同时覆盖当前节点和历史快照。
4. 新建全景查看节点，先接静态预览、生成状态、端口和尺寸，再接共享球面 Canvas。
