# 3.2 实现打光节点与可视化编辑器交接

## 结论

- 手动打光固定 `fal-ai-ic-light-v2`，只把主光方向映射到官方 `initial_latent` 的 `None / Left / Right / Top / Bottom`。
- 亮度、色调、轮廓光和补充要求均编译为版本化提示词，界面显示“模型近似”，不承诺物理精确灯位。
- 智能打光固定现有 GPT Image 2 编辑模型家族，图像 1 始终是源图，图像 2 最多一张光照参考图；顺序不得改变。
- 节点输出是普通 `image`，不是新的展示结果类型。节点外编辑器通过内部白名单写回，不放宽助手可写 data schema。

## 主要入口

- `src/features/canvas/capabilities/relightPolicy.ts`：`RelightSettingsV1`、默认/规范化、两个提示词编译器、模式路由、最终请求排序。
- `src/features/canvas/nodes/RelightGenerationNode.tsx`：节点、源图行、生成执行器、进度与普通图片输出提交。
- `src/features/canvas/ui/specialInterfaces/RelightSpecialEditor.tsx`：节点外手动/智能编辑器，使用统一草稿宿主的确认、取消与放弃流程。
- `packages/ai-sdk/src/catalog/fal/ic-light-v2.model.ts`：Fal 端点、schema、固定请求参数、价格与输入限制。
- `packages/ai-sdk/docs/model-adaptation/IC-Light-v2/IC-Light-v2_Fal.md`：官方端点、OpenAPI、定价、商用与上游许可证记录。
- `src/features/canvas/domain/nodeMigrations.ts`：项目重开时恢复契约、路由、提示词和参考图。
- `src/features/canvas/application/specialEditorApplicationService.ts`、`canvasMutationService.ts`、`nodeControlRegistry.ts`：受控草稿原子写回与助手 schema 隔离。

## 数据与请求契约

`relightContractVersion` 必须为 `1`。未知版本不会静默降级。节点持久化主数据是 `relightSettings`，`modelId / params / prompt / promptDocument / promptTemplateVersion` 是可重建的路由结果。

- 手动模式：一张源图；`falIcLightV2InitialLatent` 映射五档方向；不发送光照参考图。
- 智能模式：一张源图加零或一张光照参考图；GPT Image 2 候选供应商顺序为 Fal、APIMart、KIE、Grsai。
- 当模式目标模型或密钥不可用时显式拒绝，不自动切换到另一模式。
- 源图连线与节点内上传互斥，生成前必须有且只有一张源图。

## 实现偏差与原因

`GenerationNodeShell` 的当前媒体合并语义是“有上游时忽略节点内联媒体”，无法表达“上游源图 + 编辑器光照参考图”。本任务因此实现专用节点执行器，但继续复用 `MediaInputRow`、`GenerationService`、`runCanvasGeneration`、进度 store 和 4.1 多结果提交内核。后续若为通用 shell 增加受控媒体合并扩展点，可再收回专用执行外壳。
