# 画布智能图像工具重要记录

## 记录 001：先以全景能力验证整体路线

- 日期：2026-08-29
- 状态：已确定
- 背景：目标能力较多，且同时涉及工具条、节点、模型限制、专用界面和多种结果形态；一次性铺开会放大架构错误。
- 最终决定：先完成最小共享基础，再交付全景生成和全景浏览；2.5 由用户确认后才开放后续阶段。
- 选择原因：全景同时覆盖工具条入口、相邻节点创建、固定模型语义、特殊结果类型和专用查看器，能够较完整验证路线，但比打光和图层分离的模型控制契约更清楚。
- 影响任务：1.1～2.5、全部第三至第五阶段任务。

## 记录 002：全景首版不新增独立结果节点类型

- 日期：2026-08-29
- 状态：已确定
- 背景：全景既是普通 2:1 图片文件，又需要球面浏览；用户提出是否应为浏览功能新增节点。
- 最终决定：保留全景生成功能节点；生成结果沿用 `exportImage`，新增全景结果语义和专用查看器。首版节点内只显示平面缩略图与全景标识。
- 选择原因：可直接复用图片端口、下载、复制、连接和持久化，避免新的节点类型只为改变双击行为。WebGL 查看器按需打开，避免画布常驻多个图形上下文。
- 影响任务：1.4、2.2、2.3、2.4、5.2。

## 记录 003：能力入口统一但交互界面允许专用化

- 日期：2026-08-29
- 状态：已确定
- 背景：Liblib 的全景使用普通生成面板，打光和多角度则有明显不同的图形化控制界面；现有项目节点布局也不同于传统大面板。
- 最终决定：统一能力声明、创建、运行、日志和结果契约；普通能力复用标准节点行，打光、多角度、元素编辑和图层分离在标准行之上使用节点外专用界面。
- 选择原因：既保持一致的数据与执行链路，也避免为了“统一外观”牺牲特殊能力的可用性。复杂界面不应持续撑高 ReactFlow 节点。
- 影响任务：1.1、1.2、1.4、3.2、3.5、4.4、4.6、5.1。

## 记录 004：模型限制必须声明化并经过能力基准

- 日期：2026-08-29
- 状态：已确定
- 背景：GPT Image 2 在多个供应商目录中已经存在，但 2:1、分辨率、参考图和渠道能力并不完全相同；“能生成图片”不能证明“能稳定生成无缝全景”。
- 最终决定：能力目录只允许展示已验证的规范模型家族与供应商组合；全景先完成固定样本基准和确认清单，再实施默认模型与参数。
- 选择原因：避免在 UI 中散落模型编号分支，也避免把未经验证的供应商入口暴露给用户。
- 影响任务：1.3、2.1、2.2、3.1、3.3、3.4、4.3、4.5。

## 记录 005：后续能力不强制共用同一模型

- 日期：2026-08-29
- 状态：已确定
- 背景：全景、打光、高清、多视图和图层分离的技术目标不同。统一成“都调用图片模型”会掩盖质量、确定性和输出结构差异。
- 最终决定：共享的是产品能力和节点执行契约，不强制共享模型。高清优先真实放大；打光优先验证专用重打光；多角度和图层分离分别验证结构化模型。
- 选择原因：功能名称应对应真实结果，不应以提示词重绘冒充高清放大或精确灯光控制。
- 影响任务：3.1～3.4、4.3～4.6。

## 记录 006：元素编辑等待现有蒙版派生媒体契约稳定

- 日期：2026-08-29
- 状态：已确定
- 背景：计划创建时，工作区存在 `DerivedMediaParamControl`、`ParamLabel` 与 `maskEditor` 等未提交并行改动。
- 最终决定：3.5 开始前重新扫描这些代码和最终提交，复用唯一蒙版导出与派生媒体入口；不在本计划中预先指定会与并行工作冲突的新实现。
- 选择原因：避免重复上传、重复蒙版格式或覆盖其他正在进行的工作。
- 影响任务：3.5、5.2。

## 记录 007：真实付费调用需要任务内再次授权

- 日期：2026-08-29
- 状态：已确定
- 背景：用户明确表示参考站额度有限，并要求尽量不要触发生成；项目供应商调用也可能产生真实费用。
- 最终决定：调研和界面检查默认不触发生成。2.1 先给出样本量、单价与预算，获得用户明确授权后才能执行真实付费基准。
- 选择原因：控制费用并确保测试目标、样本和判断标准已经准备好。
- 影响任务：2.1、2.4、3.1、3.3、3.4、4.3、4.5。
