# 画布智能图像工具重要记录

## 记录 001：先以全景能力验证整体路线

- 日期：2026-08-29
- 状态：已废弃
- 背景：目标能力较多，且同时涉及工具条、节点、模型限制、专用界面和多种结果形态；一次性铺开会放大架构错误。
- 最终决定：原决定为先完成最小共享基础，再交付全景生成和全景浏览；2.5 由用户确认后才开放后续阶段。2026-08-29 起其“人工确认闸门”部分被记录 009 取代，保留全景作为首个架构试点的历史背景。
- 选择原因：全景同时覆盖工具条入口、相邻节点创建、固定模型语义、特殊结果类型和专用查看器，能够较完整验证路线，但比打光和图层分离的模型控制契约更清楚。
- 影响任务：1.1～2.5、全部第三至第五阶段任务。

## 记录 002：全景首版不新增独立结果节点类型

- 日期：2026-08-29
- 状态：已确定
- 背景：全景既是普通 2:1 图片文件，又需要球面浏览；用户提出是否应为浏览功能新增节点。
- 最终决定：保留全景生成功能节点；生成结果沿用 `exportImage`，新增全景结果语义和专用查看器。首版节点内只显示平面缩略图与全景标识。
- 选择原因：可直接复用图片端口、下载、复制、连接和持久化，避免新的节点类型只为改变双击行为。WebGL 查看器按需打开，避免画布常驻多个图形上下文。
- 影响任务：1.4、2.2、2.3、2.4、5.2。

## 记录 003：能力入口统一但交互界面允许专用化

- 日期：2026-08-29
- 状态：已确定
- 背景：Liblib 的全景使用普通生成面板，打光和多角度则有明显不同的图形化控制界面；现有项目节点布局也不同于传统大面板。
- 最终决定：统一能力声明、创建、运行、日志和结果契约；普通能力复用标准节点行，打光、多角度、元素编辑和图层分离在标准行之上使用节点外专用界面。
- 选择原因：既保持一致的数据与执行链路，也避免为了“统一外观”牺牲特殊能力的可用性。复杂界面不应持续撑高 ReactFlow 节点。
- 影响任务：1.1、1.2、1.4、3.2、3.5、4.4、4.6、5.1。

## 记录 004：模型限制必须声明化并经过能力基准

- 日期：2026-08-29
- 状态：已确定
- 背景：GPT Image 2 在多个供应商目录中已经存在，但 2:1、分辨率、参考图和渠道能力并不完全相同；“能生成图片”不能证明“能稳定生成无缝全景”。2026-08-29 的静态调研进一步确认：Fal API 可通过自定义尺寸表达 2:1，但仓库当前共享比例 schema 尚未包含 2:1，真实全景质量也尚未验证。
- 最终决定：能力目录只展示符合规范模型家族和已确认供应商契约的组合；全景先完成固定样本基准和确认清单，再实施默认模型与参数。用户已在记录 009 确认首批组合；未付费的画质结论保持“待真实验证”，但不阻止实施。Fal 在补齐 2:1 schema 和精确请求构建测试前，不进入可执行组合。
- 选择原因：避免在 UI 中散落模型编号分支，也避免把未经验证的供应商入口暴露给用户。
- 影响任务：1.3、2.1、2.2、3.1、3.3、3.4、4.3、4.5。

## 记录 005：后续能力不强制共用同一模型

- 日期：2026-08-29
- 状态：已确定
- 背景：全景、打光、高清、多视图和图层分离的技术目标不同。统一成“都调用图片模型”会掩盖质量、确定性和输出结构差异。
- 最终决定：共享的是产品能力和节点执行契约，不强制共享模型。高清优先真实放大；打光优先验证专用重打光；多角度和图层分离分别验证结构化模型。
- 选择原因：功能名称应对应真实结果，不应以提示词重绘冒充高清放大或精确灯光控制。
- 影响任务：3.1～3.4、4.3～4.6。

## 记录 006：元素编辑等待现有蒙版派生媒体契约稳定

- 日期：2026-08-29
- 状态：已确定
- 背景：计划创建时，工作区存在 `DerivedMediaParamControl`、`ParamLabel` 与 `maskEditor` 等未提交并行改动。
- 最终决定：3.5 开始前重新扫描这些代码和最终提交，复用唯一蒙版导出与派生媒体入口；不在本计划中预先指定会与并行工作冲突的新实现。
- 选择原因：避免重复上传、重复蒙版格式或覆盖其他正在进行的工作。
- 影响任务：3.5、5.2。

## 记录 007：真实付费调用需要任务内再次授权

- 日期：2026-08-29
- 状态：已确定
- 背景：用户明确表示参考站额度有限，并要求尽量不要触发生成；项目供应商调用也可能产生真实费用。
- 最终决定：调研和界面检查默认不触发生成。2.1 先给出样本量、单价与预算，获得用户明确授权后才能执行真实付费基准。
- 选择原因：控制费用并确保测试目标、样本和判断标准已经准备好。
- 影响任务：2.1、2.4、3.1、3.3、3.4、4.3、4.5。

## 记录 008：能力声明与执行引用分离

- 日期：2026-08-29
- 状态：已确定
- 背景：九项能力需要提前形成统一目录，但全景等新能力尚未实现；若把“已登记”等同于“可执行”，工具条会提前暴露无效入口。
- 最终决定：能力目录分别保存产品语义、发布状态、默认功能开关和实现状态。只有 `implemented`、发布状态允许执行、功能开关开启且引用真实节点或本地工具的能力才能进入可执行查询。全景等新能力当前保持 `planned + draft`；既有宫格切分作为唯一 `available` 能力映射到现有本地工具。
- 选择原因：后续任务可以共享稳定编号和字段，不需要复制注册表；同时能在测试与开发期阻止未实现能力误开放和无效执行引用。
- 影响任务：1.2、1.3、1.4、2.1～2.4、全部第三至第五阶段能力任务。

## 记录 009：用户确认全景方案并授权连续完成全部任务

- 日期：2026-08-29
- 状态：已确定
- 背景：非付费调研已形成全景模型与参数确认清单；用户先确认该方案，随后将原“全景后暂停测试”指令更新为“自主连续完成全部任务”。
- 最终决定：全景采用规范模型 `gpt-image-2`；首批支持 APIMart EXT/官方、KIE、Grsai VIP，Fal 补齐 2:1 后加入；固定 2:1、单张、原生 2K，支持时默认 `medium`；最多 1 张参考图，按是否有图自动路由；产品名称暂用“720°全景”。团队获得对全部 22 项任务的连续实施、常规选型和测试决策授权；2.5 改为自动路线审查与证据归档，不再重复等待用户表态。
- 选择原因：用户希望所有功能完成后统一测试，并明确要求团队对可回退的实现与验证决策自主处理。保留证据归档点可防止架构偏差扩大，同时不把主观验收或未付费质量缺口变成实施阻塞。
- 付费边界：本记录不等于真实付费生成授权。本轮不运行任何会产生模型费用的基准请求；相关质量和稳定性结论必须标为“待真实验证”，但不阻止代码实现与后续阶段。
- 影响任务：1.3、2.2～2.5、全部第三至第五阶段任务。

## 记录 010：项目内全景语义与外部文件元数据分层

- 日期：2026-08-29
- 状态：已确定
- 背景：`exportImage` 全景结果既要在项目保存、重开和项目包导入后稳定进入球面查看器，也要让下载文件被支持 Photo Sphere 的外部工具识别；系统剪贴板和部分格式不能保证保留文件容器元数据。
- 最终决定：项目内唯一主真相为 `exportImage + resultKind: panorama`；下载时为严格 2:1 的 PNG/JPEG/WebP 无像素重编码写入最小 GPano XMP，作为外部兼容辅助。完整全景的裁剪尺寸等于完整尺寸、偏移为零；不支持格式、非 2:1 或非法 XMP 明确拒绝或返回状态，不伪造成功。剪贴板仍按系统位图语义处理，不用文件 XMP 反推项目语义。
- 选择原因：结果语义不依赖容易在复制、转码或第三方处理时丢失的 XMP；容器级写入又能保留原始编码像素，并让导出文件符合外部查看器的标准识别字段。
- 影响任务：1.4、2.2～2.5、5.2，以及所有复用图片结果下载或项目包链路的后续能力。
