# 画布智能图像工具实施方案

## 一、当前项目与相关功能现状

### 1. 画布与节点体系

- 画布基于 ReactFlow，节点类型、端口、菜单、生成能力和默认数据集中声明在 `src/features/canvas/domain/nodeRegistry.ts`。
- 标准图片生成节点由 `src/features/canvas/nodes/shared/GenerationNodeShell.tsx` 组合模型行、媒体输入行、参数行和生成动作；普通模型 schema 能被它自动读取。
- 生成链路已经收口到 `runCanvasGeneration`、`GenerationService`、渲染层命令、平台适配层、Electron 主进程和 `@henjicc/ai-sdk`，新能力不得在组件中直接请求供应商接口。
- 相邻节点放置和连线已有 `findNodePosition`、`useCanvasNodeMenu` 与 `canvasApplicationService` 可复用，不应为工具条另写一套几何和持久化逻辑。
- `GenerationNodeShell` 已通过统一完成契约提交单图、全景、图片组和图层栈；多结果持久化与画布写入分两阶段完成，成功后才移交受管媒体所有权。

### 2. 工具条与本地工具

- 单节点工具条位于 `src/features/canvas/ui/NodeActionToolbar.tsx`，已经负责生成、编辑、切分、复制、下载、删除等操作。
- 本地工具由 `src/features/canvas/tools/types.ts`、`registry.ts`、`builtInTools.ts` 和 `NodeToolDialog.tsx` 管理，目前主要是元素编辑和宫格切分。
- 现有工具插件偏向本地、确定性处理；模型驱动能力还需要独立的声明层，不能把提示词、模型限制和结果语义塞进本地工具执行器。

### 3. 结果节点与查看器

- 普通图片和全景继续使用 `exportImage`，全景由 `resultKind: panorama` 驱动专用查看器；多图使用 `assetGroup + image-group`，图层使用版本化 `LayerStackDocument`。
- `CanvasNodeImage.tsx` 双击后通过画布状态打开 `ImageViewerModal.tsx`；现有查看器只支持平面图片缩放、平移和列表导航，没有查看模式路由。
- 项目已经依赖 `three`、`@react-three/fiber`、`@react-three/drei`，无需新增全景渲染框架。
- `CameraStageNode.tsx` 与其懒加载专用对话框已经证明“节点保持轻量预览、复杂 Three 界面在节点外打开”的方式可行。
- 项目已有 `assetGroup` 节点和应用服务，可以承载多图结果，优先扩展而不是再造结果组。

### 4. 模型与参数现状

- GPT Image 2 已在 APIMart、KIE、Grsai、Fal 等目录中存在，但不同供应商的比例、分辨率、参考图和渠道约束不同。
- APIMart、KIE、Grsai 当前可表达 2:1；Fal 目录的通用比例候选暂未直接暴露 2:1，不能未经核查就列入全景首批供应商。
- 模型家族、供应商组合、固定参数和不可用原因已由能力策略与模型 schema 声明；界面仍通过标准模型行读取，不包含模型编号分支。
- 技术上的球形全景是等距柱状投影，覆盖水平 360°、垂直 180°，画面比例严格为 2:1。界面可沿用用户熟悉的“720°全景”名称，但提示词、验收和元数据必须按 360×180 球面定义执行。

### 5. 持久化与媒体处理

- 画布项目以节点、连线和视口快照持久化，节点新增可选数据字段时必须在 `nodeMigrations.ts` 中处理旧项目和损坏值。
- 本地媒体路径和展示地址由媒体命令与平台层统一解析；禁止把手动媒体网址输入框暴露给用户。
- 分镜 PNG 元数据仍使用自己的文本块；全景已建立独立 GPano/XMP 链路。项目内以 `exportImage + resultKind: panorama` 为主真相，下载时为严格 2:1 的 PNG/JPEG/WebP 无像素重编码写入最小 GPano，其他格式明确降级。

## 二、参考产品与开源调研结论

### 1. Liblib 参考界面

在不触发付费生成的前提下，实际检查了用户提供的画布：

- 图片选中工具条包含人像质感、全景、多角度、打光、九宫格、高清、元素编辑、图层分离和宫格切分。
- 全景入口会创建相邻生成节点，节点使用参考图、固定能力预设、模型、2:1、画质、分辨率和张数等参数；生成结果另有“进入全景预览”能力。
- 打光不是普通参数表：手动模式有灯位方向、亮度、颜色和轮廓光的图形界面；智能模式还提供提示词、参考光照图和风格预设。
- 多角度也使用专用图形界面，包含水平环绕、垂直俯仰、景别、预设视角和可选提示词。

这说明“工具条入口统一”不等于“节点内部界面统一”。应统一能力声明、创建、运行和输出，允许少数能力叠加专用编辑器。

## 三、建设前问题与当前解决状态

1. 九项能力已按窗口宽度分为少量直达项和单一“更多”菜单，基础操作之间只有一条分隔线，双尺寸 Electron 场景证明可达。
2. 模型能力、本地工具、功能节点、专用界面和结果语义统一由能力目录与注册表驱动，没有第二套工具条运行时。
3. 全景、打光、多角度、高清、人像、元素编辑和图层分离均有明确模型策略；提示词近似不会伪装为物理精确控制。
4. 结果契约已覆盖 `image`、`panorama`、`image-group` 和 `layer-stack`，并进入保存、重开、撤销、项目包与缺失媒体链路。
5. 多结果采用原子画布事务和受管媒体所有权移交；部分失败、项目切换和语义校验失败会回滚本次新建文件。
6. 打光和多角度使用节点外专用界面；高清、人像、九宫格复用标准节点；全景查看器与 3D 相机预览均按需渲染。
7. 元素编辑已复用唯一蒙版编辑和派生媒体入口。当前只剩 2.1、2.4 的真实付费全景质量证据，不是实现阻塞。

## 四、最终目标与总体方案

### 1. 四层结构

1. **能力入口层**：工具条根据选中节点和能力声明显示可用入口；常用能力直接展示，其余进入“更多”。
2. **功能节点层**：点击后立即在右侧安全位置创建并连接功能节点，保存输入引用、能力编号、模型语义、用户可见参数和隐藏提示词版本。
3. **专用界面层**：普通能力复用标准节点行；打光、多角度、元素编辑、图层等通过节点外浮层或沉浸式界面编辑，确认后回写节点数据。复杂界面不改变节点高度。
4. **结果语义层**：结果仍是可连接的画布媒体，但带有 `image`、`panorama`、`image-group`、`layer-stack` 等语义，决定双击查看和后续操作。

### 2. 拟建立的声明式能力契约

字段名称在 1.1 中最终确定，至少表达：

- 能力编号、名称、图标、分组和排序。
- 支持的源媒体类型、数量和入口可用条件。
- 功能节点类型及编辑器类型：标准、打光、多角度、蒙版、图层。
- 结果类型：单图、全景、图片组、图层栈。
- 允许的规范模型家族、供应商/渠道兼容条件和不可用原因。
- 隐藏提示词模板版本、固定语义参数、用户可见参数及其映射。
- 输出数量策略、后处理方式和失败恢复要求。

不得在 `NodeActionToolbar.tsx`、模型选择器或专用编辑器里写 `modelId === ...` 的产品分支。

### 3. 节点选择策略

| 能力 | 首选实现 | 结果形式 | 特殊界面 |
|---|---|---|---|
| 全景 | 标准生成外壳上的能力节点 | 带全景语义的图片结果节点 | 专用全景查看器 |
| 打光 | 特殊生成节点 | 普通图片 | 灯位/亮度/颜色编辑器 |
| 多角度 | 特殊生成节点 | 图片组 | 球形相机角度编辑器 |
| 九宫格 | 复用分镜生成能力 | 图片组或带网格元数据的图片 | 复用现有分镜交互 |
| 高清 | 标准处理节点 | 普通图片 | 无，标准参数行即可 |
| 人像质感 | 标准生成/编辑节点 | 普通图片 | 无或轻量预设 |
| 元素编辑 | 特殊生成节点 | 普通图片 | 复用统一蒙版编辑器 |
| 图层分离 | 特殊处理节点 | 图层栈 | 图层列表、可见性和合成预览 |
| 宫格切分 | 复用现有本地工具 | 多张图片/素材组 | 复用现有切分对话框 |

### 4. 全景首版的明确选择

- **需要功能节点**：保存参考图、提示词、固定 2:1、分辨率、模型家族和生成记录，保证可复现。
- **暂不新增独立结果节点类型**：沿用 `exportImage`，扩展 `resultKind: panorama`；这样图片端口、下载、复制和现有连线仍可复用。
- **必须有专用浏览**：双击全景结果后进入懒加载的球形查看器，至少支持拖动环视、滚轮缩放、复位、平面/球面切换、全屏和关闭。
- **节点内只显示平面缩略图和全景标识**：避免每个节点创建 WebGL 上下文，也避免拖动画布时与球面交互争抢事件。
- **升级条件**：只有在产品需要保存热点、默认镜头、自动导览或全景之间的跳转关系时，才把全景结果升级为独立一等节点类型。

### 5. 全景试点路线审查结果

2.5 已根据 2.1～2.4 的实际证据完成自动审查，决定为：**按当前架构继续后续阶段**。

- 已达标：声明式能力入口、原子相邻节点创建与连线、标准生成壳、固定模型/提示词/2:1 语义、`exportImage + resultKind: panorama`、惰性球面查看器、PNG/JPEG/WebP GPano、项目保存重开、下载和项目包往返。
- 已通过真实 Electron 验收：1440×900 与 960×640 的工具条和查看器场景均通过，结构化日志无错误或警告，11 项 DOM 审计零命中；程序化样本费用为 0。
- 待真实验证：模型输出的左右接缝、上下极点、地平线、主体重复、文字伪影、清晰度、提示遵从、渠道稳定性、实际耗时和费用。未付费证据不得写成通过或用于对外宣传。
- 5.2 已清零原全局欠账：助手附件只接受真实支持的三类媒体，`specialEditorController` 已建正式 StoreLedger，`maskEditor` 已按真实草稿/持久化边界进入盲区清单；完整类型、助手能力与 Electron 构建门禁均通过。
- 回退边界不变：真实画质若不达标，优先禁用具体供应商组合、暂停默认开放或更换模型；保留已验证的能力目录、节点编排、结果语义、查看器和文件兼容基础。

## 五、阶段关系与路线审查

```text
第一阶段：共享能力基础
          ↓
第二阶段：全景试点 → 2.5 自动审查与证据归档
          ↓ 根据证据自动继续或调整
第三阶段：单图能力扩展 ─┐
第四阶段：结构化输出能力 ├→ 第五阶段：整体收口
                         ┘
```

- 1.1 完成后，1.2、1.3、1.4 可在避免同文件冲突的前提下并行。
- 2.1 可与 1.2～1.4 并行调研；2.2 和 2.3 在各自前置满足后可并行实现。
- 用户已预先授权按当前架构连续完成全部任务。2.5 已完成团队自动路线审查与证据归档，结论是按当前架构继续；真实模型画质和渠道稳定性保持待验证但不构成后续实施门槛。
- 常规实现取舍、测试安排和可回退调整不再向用户索要确认。只有发现无法通过禁用能力、降级、更换方案或回退提交规避的致命技术问题时，才停止并请求用户处理。
- 2.5 不再是第三、第四阶段的人工前置闸门。第三、第四和第五阶段均已完成；2.1、2.4 只保留未来真实付费全景验证，不再影响代码任务状态。

## 六、兼容方式与数据要求

1. 现有 `imageEdit`、`exportImage`、`storyboardGen`、`assetGroup` 和本地工具继续可用，不以一次性迁移替换。
2. 新增节点数据必须有明确版本或稳定缺省值；`normalizeNodes` 和迁移逻辑需处理旧项目、缺失字段和非法字段。
3. 结果语义是附加信息，旧版不知道该字段时仍应把结果当普通图片显示；不得让旧项目无法加载。
4. 画布项目导入导出必须收集新增媒体引用；媒体持久化保存本地受管路径，渲染时通过统一展示地址解析。
5. 模型选择保存规范模型标识和必要的供应商选择，不保存只在界面有效的临时序号。
6. 隐藏提示词必须带版本，后续改模板不能静默改变历史节点的复现含义。
7. 多结果创建应作为一次图事务提交；部分失败时不得留下断裂素材组或无法辨认的孤儿节点。

## 七、风险控制与回退原则

| 风险 | 控制方式 | 回退原则 |
|---|---|---|
| GPT Image 2 不能稳定生成无缝球面 | 2.1 用固定样本和评分表先做基准，不把模型名写死在界面 | 保留能力骨架，暂停默认开放或更换已验证模型 |
| 专用界面过重导致画布卡顿 | 节点只渲染静态预览；Three、图层和灯光界面按需懒加载 | 关闭专用入口仍可按普通图片查看和下载 |
| 数值控件造成“精确控制”错觉 | 先定义模型能否接受结构化参数；提示词近似控制必须明确标注 | 降级为预设/文本控制，不伪造精确角度 |
| 工具条拥挤 | 直接入口限制为少量高频项，其余放入单一更多菜单 | 能力仍可从更多菜单或节点菜单进入 |
| 多输出中途失败 | 一次性图事务、明确重试与失败状态、保留原输入 | 删除未完成结果组，不影响源节点 |
| 与蒙版并行改动冲突 | 3.5 开始前重新扫描接口并复用唯一派生媒体入口 | 推迟元素编辑，不复制蒙版链路 |
| 供应商协议或价格变化 | 每个模型任务按官方资料重新核查并记录日期 | 禁用不兼容供应商组合，不在 UI 打补丁 |
| 付费或外部写入 | 默认只跑静态、模拟和本地测试；真实调用单独授权 | 未授权则保持待验证，不伪造结果 |

每个任务按可独立验证、可独立回滚的边界提交。回退优先禁用能力声明或撤销该任务独立提交，不删除用户项目和已有媒体。

## 八、全局开发约束

- 新建或改造画布节点时遵循 `canvas-node-builder`；界面层级、工具条、浮层和动效遵循 `henji-ui-surface`；模型/供应商工作遵循 `henji-model-adaptation` 的先调研、先确认、后实施流程。
- 画布热路径不得增加全量节点扫描、同步文件读写、常驻 WebGL 或大范围毛玻璃动画。
- 普通节点优先复用 `GenerationNodeShell`、`ModelInputRow`、`MediaInputRow` 和 `NodeParamRows`；特殊节点也应先使用标准行，再叠加专用面板。
- 不在业务组件直接调用模型 API，不在 UI 写模型特定分支，不新增媒体网址输入框，不绕过平台层。
- 新建共享 UI 原语前必须先证明现有原语无法复用，并在对应任务记录原因、替代方案和影响范围。用户已授权本计划内的常规实现决策，无需再次请求确认；仍不得为单一功能无必要地新建通用原语。
- 网络、文件、长耗时任务必须有开始、成功、失败和必要进度日志，日志进入现有统一系统。
- 涉及 VGPU 时若 API 或资源生命周期不确定，必须查官方资料；全景首版优先 Three/R3F，不引入不必要的 VGPU 依赖。
- 用户工作区可能有未提交改动。任务开始前必须检查状态，只提交当前任务文件，禁止覆盖他人改动。

## 九、验证策略

### 每个任务的最低验证

- 纯类型/注册表：相关单元测试、类型检查或专项检查。
- 节点与连线：节点工厂、注册表、相邻放置、端口兼容和项目往返测试。
- 模型 schema：官方资料快照、目录生成、模型国际化检查和对应 SDK 精确测试。
- 专用界面：组件测试加真实 Electron 场景；浏览器只能用于参考站调研，不能代替本项目验收。
- 媒体/元数据：主进程精确测试、导入导出往返、文件实际可读和错误日志。
- 画布性能：只在节点 DOM、热路径或大图加载变化时运行画布视觉/性能检查。

### 全景试点验收样本

至少覆盖：纯文本室内、纯文本室外、单张参考图、有人物的参考图、高细节场景。统一记录左右接缝、上下极点、地平线、主体重复、文字伪影、提示词遵从、等待时间和成本。本轮不执行真实付费基准；没有付费证据的质量结论必须标为“待真实验证”，但不阻止功能实现、模拟验证、本地样本验收和后续能力开发。

### 最终验收条件

- 工具条在不同节点宽度和缩放下可用，入口可发现但不挤占基础操作。
- 每个能力点击后都能创建正确的相邻功能节点并保持可复现参数。
- 全景生成结果能以平面图继续连接，并能进入真正的球面浏览模式。
- 打光、多角度、元素编辑和图层分离的专用界面与实际模型能力一致，不承诺无法执行的精度。
- 单图、多图、全景和图层结果能保存、关闭、重开、导入和导出。
- 原有图片生成、编辑、分镜、素材组、下载、复制和宫格切分无回归。
- 按 `docs/rules/testing.md` 完成相应检查，并在真实 Electron 环境检查实际截图、交互证据和日志。

以上实现与非付费条件已在 5.2 完成；真实供应商画质、渠道稳定性、耗时和费用不在无授权情况下冒充通过。

## 十一、后续任务执行流程

### 开始前

1. 阅读 `00-任务总览.md`、本实施方案和当前任务文件。
2. 必要时阅读前置任务执行记录与 `重要记录.md`。
3. 检查代码、依赖、官方资料和工作区状态是否变化；不一致先更新计划。
4. 将当前任务与总览状态改为“进行中”，只处理任务范围内内容。

### 执行中

1. 新依赖、风险、接口变化和范围变化及时写回任务文件。
2. 整体方案变化时更新本文件；跨任务决定写入 `重要记录.md`。
3. 不重编号既有任务，不顺便实施后续任务，不混入他人改动。

### 完成或阻塞

1. 完成任务文件内的专项验证并填写实际执行记录。
2. 验证通过标为“已完成”；功能完成但真实验证不足标为“待验证”。
3. 阻塞时写明原因、解除条件、影响任务和替代方案，并标为“已阻塞”。
4. 同步总览数量、阶段、当前任务和最近记录；检查后续依赖是否仍成立。
5. 代码任务按独立完成边界创建一次不混杂其他改动的 Git 提交。
