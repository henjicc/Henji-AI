# 3.1 确定打光模型与控制契约

- 所属阶段：第三阶段——单图能力扩展
- 前置任务：2.5

- 是否可以并行：可以；全景闸门通过后可与 3.3、3.4、4.1、4.3、4.5 并行调研

## 任务目标

确定打光能力到底使用专用重打光模型还是提示词编辑模型，以及亮度、颜色、主光方向、轮廓光、智能预设等控制能达到何种精度，形成 3.2 可直接实现且不夸大能力的输入输出契约。

## 当前情况

- Liblib 手动界面包含五级亮度、颜色、主光方向和九档轮廓光方向；智能界面包含提示词、参考光照图和八个风格预设。
- IC-Light 等项目表明重打光通常需要前景/背景或光照条件，不等于普通图片编辑模型能精确遵循灯位数值。
- 当前项目有标准图片编辑输入和参数 schema，但没有“灯位向量→供应商参数/提示词”的统一契约。
- 若先照参考图做控制盘，可能最终只能近似提示词控制，造成误导。

## 实施方案

按模型适配流程对候选供应商、专用模型和 GPT 图片编辑分别做资料与样本评估。把控制分为“结构化精确参数”“离散预设”“提示词近似”三档；只有模型证据支持时才在 UI 中呈现精确灯位。输出仍为普通图片。

## 执行步骤

1. 记录 Liblib 可见控制、预设和状态变化，不触发其付费生成。
2. 调查项目现有供应商目录与可接入模型，优先官方 API/模型卡，核对输入图、背景/蒙版、参数、价格、许可证和输出限制。
3. 定义固定人物、商品、室内样本与评价项：主体保持、光向、阴影、肤色、背景污染、边缘光和成本。
4. 提出最小付费矩阵并请求授权；按授权结果执行或将质量项标为待验证。
5. 明确手动控制与智能控制各字段的精度等级、默认值、互斥关系和降级文案。
6. 给出首选模型/供应商、备选与排除原因，形成节点数据、请求映射和结果契约。

## 涉及内容

本任务主要处理官方资料、候选模型目录、测试样本、确认清单和任务记录。发现 SDK 缺口时，遵循模型适配资料先行规则；不在本任务实现打光界面。
