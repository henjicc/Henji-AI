# 5.1 收口工具条信息架构与功能可用性

## 任务状态

- 状态：待开始
- 所属阶段：第五阶段——整体收口
- 前置任务：3.2、3.3、3.4、3.5、4.2、4.4、4.6
- 关联任务：1.2、5.2
- 是否可以并行：否；需要基于全部已实现能力的真实状态统一收口

## 任务目标

在所有目标能力已经有真实入口和成本信息后，最终确定工具条直接入口、更多菜单、分组、禁用说明、键盘操作和不同节点宽度下的布局，使功能可发现但不挤压画布基础操作。

## 当前情况

- 1.2 只建立通用入口和初始分组，不应在缺少真实能力前过度设计最终排序。
- 参考产品平铺多个功能文本，但本项目已有生成、编辑、复制、下载和删除等操作，布局密度不同。
- 不同能力有模型费用、输入限制、特殊界面和本地处理差异，需要一致但不过度打扰的状态表达。
- UI 规则要求横向条带数量受控、最多一个分隔、图标动作低层级、选中态不依赖鼠标悬浮。

## 实施方案

以实际使用路径和节点宽度测试确定最多 3～4 个直接能力，其余进入单一更多菜单。入口按“生成/变换、结构化输出、本地处理”分组，但菜单不做多层嵌套。模型或源媒体不满足时，根据可恢复性选择隐藏或禁用并解释。基础操作和危险操作保持现有层级。

## 执行步骤

1. 汇总每项能力的适用节点、使用频率假设、费用、特殊界面和不可用原因。
2. 用小/中/大节点、100%及常用缩放、中文/英文和窄窗口测试当前工具条。
3. 确定直接入口、更多菜单、分组、排序、标签长度、图标、分隔和危险操作位置。
4. 统一可用、禁用、实验、付费、本地、加载中和错误状态的视觉及辅助说明。
5. 补齐键盘导航、焦点管理、读屏名称、菜单关闭、工具提示和触控命中区域。
6. 检查工具条出现/消失不改变节点尺寸，不触发全画布重渲染，不与 ReactFlow 拖拽冲突。
7. 添加响应式、国际化、能力状态和真实 Electron 视觉审查场景；由执行者打开截图目视检查。
