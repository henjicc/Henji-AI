## 记录 003：离屏渲染技术选型

- 日期：2026-07-06
- 状态：已完成
- 背景：3.2 的两条实现路线（临时改现有 renderer 尺寸 vs 独立离屏 RenderTarget）在实现成本、视口副作用、渲染一致性上差异较大，需要小规模试验后决定。
- 小规模验证证据（2026-07-10）：`StageCaptureBridge` 当前只持有 R3F 的 `gl`，直接读取 `gl.domElement.toDataURL()`；`cameraStageVideo.ts` 随后把视口截图裁剪并缩放到目标分辨率。桥内可同时取得 R3F 的 `scene`、默认 `camera` 与 renderer。激活摄像机由 `StageViewportCamera` 设为默认相机，且已在逐帧 seek 后完成位置、FOV、lookAt 的播放期采样。
- 方案 A（临时改现有 renderer 尺寸）：可通过临时 `setPixelRatio(1)`、`setSize(width, height, false)`、调整默认相机画幅后手动 `render()` 并读取 canvas 实现。实现面较小，但 R3F 的 `size` 状态仍是视口尺寸；恢复时必须同时还原 pixel ratio、绘制缓冲尺寸、相机 aspect、render target 与投影矩阵。导出循环中的自动帧渲染可能读到中间状态，且 canvas 的可见画面会在导出期被拉伸/闪变，须额外遮罩和异常恢复保护。
- 方案 B（推荐：复用现有 renderer 的 `WebGLRenderTarget`，不新建第二 renderer）：在桥内以当前 `scene` 和逐帧已采样的默认相机克隆体渲染至目标尺寸 RenderTarget；克隆相机仅修改 `aspect = width / height` 并更新投影。读取 RGBA 像素、垂直翻转后编码 PNG bytes。视口 renderer 尺寸、R3F store 与可见画面均不变，导出构图直接等于相机画幅，可移除视频导出中的居中裁剪/上采样步骤。
- 方案 B 风险与控制：每个 1080p 帧至少约 8 MiB RGBA 读回缓冲，需复用 RenderTarget、像素数组与 2D 编码画布；需在 `finally` 恢复 renderer render target/clear 状态并 dispose target；RenderTarget texture color space 必须对齐 renderer 输出，读取像素须 Y 翻转。第二 renderer 不推荐：会新增 WebGL context 与资源初始化/上下文限制风险，且没有必要。
- 最终决定：用户于 2026-07-10 确认方案 B，复用当前 R3F renderer 的 `WebGLRenderTarget`，不创建第二 renderer。
- 实施结果：`StageCaptureFn` 新增目标尺寸异步捕获重载；每帧克隆当前默认透视相机，按目标宽高更新 aspect 后渲染到复用的 RenderTarget。RGBA 像素读回后垂直翻转、经复用 2D 画布编码为 PNG `Uint8Array`。视频导出直接传该 bytes，截图仍使用原 dataURL + 居中裁剪链路。
- 资源控制：RenderTarget texture colorSpace 对齐 renderer outputColorSpace；每帧 finally 恢复 renderer target、viewport、scissor、autoClear；一次视频导出的 finally 主动 dispose target，组件卸载也会兜底释放。
- 选择原因：用户已确认后实施，方案 B 保持视口稳定并消除视口截图上采样。
- 影响任务：3.2
