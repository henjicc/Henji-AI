# 1.1 三维渲染引擎接入验证

## 任务状态

- 状态：已完成
- 所属阶段：第一阶段-技术验证
- 前置任务：无
- 关联任务：1.2（可并行）
- 是否可以并行：是（与 1.2 并行）

## 任务目标

验证 three.js + `@react-three/fiber` + `@react-three/drei` 能在当前 Electron 42 + Vite 4 + electron-vite 技术栈、`contextIsolation: true`/`sandbox: true` 的安全配置下正常运行、正常打包，产出一个最小可跑通的三维场景（能看到基础几何体、能用 `OrbitControls` 环绕查看、能用 `TransformControls` 拖拽变换），确认技术路线可行后再进入第二阶段正式开发；如果验证不通过，须在本任务里记录具体障碍和备选方案。

## 当前情况

- `package.json` 中没有任何三维渲染相关依赖：无 `three`、`@react-three/fiber`、`@react-three/drei`、`@types/three` 等。
- 渲染层技术栈：React 18.2 + TypeScript 5 + Vite 4.4.5，桌面容器 Electron 42.5，用 `electron-vite` 构建。
- Electron 安全配置（见 CLAUDE.md）：`contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`，渲染层运行时代码统一走 `src/platform/*`、`src/commands/*` 访问桌面能力，业务 UI 禁止直接 import `ipcRenderer`/Node 内置模块。
- 现有画布模块用 `@xyflow/react`（2D 节点图），2D 图片编辑用 `konva`/`react-konva`，都不是三维渲染方案，项目里没有任何可复用的三维基础设施或 WebGL 使用先例。
- 工具箱 Tab 目前是纯占位组件 `src/workspaces/ToolboxPlaceholder.tsx`，由 `src/components/TabContainer.tsx` 懒加载挂载，是唯一现成的、不影响其他功能的验证挂载点。
- 现有回归检查基础设施可复用：`npm run electron:dev`（真实 Electron 窗口调试）、`npm run electron:build`/`npm run electron:pack`（构建与打包）、`npm run electron:smoke`（构建产物冒烟）、`npm run electron:dpi-check`（DPI/分辨率检查）。

## 实施方案

在不影响主链路的前提下，接入 three + `@react-three/fiber` + `@react-three/drei`，做一个最小 Demo 场景（地面网格 + 几个基础几何体 + `OrbitControls` + `TransformControls`），在真实 Electron 窗口里验证渲染是否正常、交互是否流畅；再走一次完整的 `electron:build`/`electron:pack` 流程，确认打包不报错并记录体积增量；同时确认是否需要为 WebGL 调整现有的 CSP/`webPreferences` 配置。验证过程中的代码只是技术验证，不追求代码质量或最终架构，验证通过后进入第二阶段时按正式方案重写，不强行保留验证期代码。

## 执行步骤

1. 安装依赖：`npm install three @react-three/fiber @react-three/drei` 以及 `@types/three`，检查安装后是否与现有 React 18.2/TypeScript 5 版本产生 peer dependency 冲突，记录冲突和解决方式。
2. 在 `src/features/cameraStage/`（验证阶段临时目录，最终命名见重要记录 005）下新建一个独立验证组件，渲染一个最小三维场景：地面网格 + 一个立方体 + 一个球体，接入 `OrbitControls`。
3. 选一个临时挂载点（建议直接临时替换 `ToolboxPlaceholder.tsx` 的内容做验证，验证完成后再决定是否保留改动或还原）能在 `npm run electron:dev` 里实际打开这个场景。
4. 接入 `TransformControls`，验证能否拖拽选中物体做移动/旋转/缩放。
5. 在真实 Electron 窗口（`npm run electron:dev`）里操作验证：渲染是否正常显示、鼠标交互（环绕/缩放/拖拽）是否流畅、有没有控制台报错（尤其是 CSP 相关报错）。
6. 跑一次 `npm run electron:build` 和 `npm run electron:pack`，检查构建/打包是否报错，对比新增依赖前后的产物体积差异。
7. 跑一次 `npm run electron:dpi-check`，确认三维画面在高 DPI/多显示器场景下没有明显异常（如模糊、尺寸错位）。
8. 把验证结论（技术路线可行 / 需要调整方案，以及具体原因）写入本文件的执行记录和 `重要记录.md`（如果结论会影响后续阶段方案）。

**DPI 验证（步骤 7）**

- `npm run electron:dpi-check` 的 6 组分辨率/缩放断言全部通过，脚本最终因"控制台零报错"门槛失败——但该报错是**与本次改动无关的存量环境问题**（见下方"已知环境问题"）。
- 另用针对性脚本在打包产物中切到工具箱 Tab 实测三维画布 DPI 表现：1.5x 下 canvas buffer 3840×2040 = CSS 2560×1360 × 1.5，模拟 2x 下 buffer 3840×2080 = CSS 1920×1040 × 2，像素缓冲正确跟随 devicePixelRatio，无模糊/错位风险。截图确认场景（网格/立方体/球体/覆盖 UI）渲染正常。

**已知环境问题（与本次改动无关，记录备查）**

- 本机 `electron:smoke` / `electron:dpi-check` 当前必然失败于"控制台零报错"断言：本机用户数据库中有一条历史记录引用 `E:\图片\截图快速保存\0_导出\VID_20260630_204459.mp4`，该路径在 `henji-media://` 协议的媒体根目录白名单之外，协议返回 403（`electron/main/protocol.ts` 的 `assertAllowedMediaPath`）。三维验证代码不加载任何媒体资源，且该失败在不打开工具箱 Tab 的冒烟路径上就会出现。后续可考虑单独立任务：渲染层在设置 `<video src>` 前用 `isPathWithinAllowedMediaRoots` 预检（协议文件注释里已有此设计意图）。

**验证结论**

- **技术路线可行。** three.js + R3F + drei 在 Electron 42 sandbox 环境下渲染、打包、DPI 全部无障碍，体积增量小且被懒加载完全隔离，无需调整任何安全配置。可以进入第二阶段正式开发。

### 2026-07-03 用户交互验证通过 + 追加发现一个重要坑（Claude）

- 用户在真实 `npm run electron:dev` 窗口手动验证：左键环绕、滚轮缩放、右键平移流畅无卡顿；点击立方体/球体后 gizmo 正常出现，移动/旋转/缩放三种模式切换均可正常拖拽变换；拖 gizmo 时不会误触发相机环绕，两套控制不冲突。**1.1 验收标准全部通过，任务状态标记为已完成。**
- 在 1.2 验证中额外发现一个对后续所有阶段都有约束力的问题：**打包态 Electron 用 `win.loadFile` 以 `file://` 协议加载 `out/renderer/index.html`（见 `electron/main/window.ts:48`），此时以 `/xxx` 开头的绝对路径静态资源引用会被解析到磁盘根目录（如 `file:///xxx`）而不是应用目录，导致资源 404。** 复现方式：把 Quaternius 验证用的 GLB 放进 `public/camera-stage-verify/` 并用绝对路径 `/camera-stage-verify/xxx.glb` 引用，开发态（vite dev server）能正常加载，但走完整的 `electron:build` 后在打包产物里用脚本实测会报 `ERR_FILE_NOT_FOUND`；改成相对路径 `./camera-stage-verify/xxx.glb` 后打包产物加载正常。
- **影响后续阶段的结论**：2.x/3.x 正式的三维模型/动作资源不应该走 `public/` 静态资源 + 绝对路径这条路，应该跟项目现有图片/视频资源一致，统一走 `henji-media://` 协议 + 主进程媒体根目录白名单机制（`electron/main/protocol.ts`）来读取，这样开发态/打包态路径解析行为一致，也符合"不新建一套独立资源加载方式"的项目约定。本文件验证代码使用相对路径只是validation 期的权宜写法，不代表 2.x 的正式方案。
