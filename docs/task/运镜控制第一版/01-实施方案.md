# 运镜控制 · 实施方案

## 当前项目和相关功能现状

- 桌面容器是 Electron 42 + electron-vite，渲染层是 React 18 + TypeScript + Vite 4，`contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`。
- `package.json` 中目前没有任何三维渲染相关依赖（无 `three`/`@react-three/fiber`/`@react-three/drei`/`@pixiv/three-vrm`/`Theatre.js` 等），画布模块用的是 `@xyflow/react`（2D 节点图），2D 图片编辑用 `konva`/`react-konva`，都不能复用为三维场景基础设施。
- 顶层有三个 Tab：`generation`（对话/生成，`src/workspaces/GenerationWorkspace.tsx`）、`nodes`（画布，`src/workspaces/CanvasWorkspace.tsx`）、`tools`（工具箱，`src/workspaces/ToolboxPlaceholder.tsx`），由 `src/components/TabContainer.tsx` 懒加载挂载。工具箱 Tab 目前是纯占位组件，只显示"开发中"文案，是一块完全空白、可以承接新功能的区域。
- 项目里已有一套成熟的"子项目持久化"参考实现——分镜生成对应的 `storyboard_projects` 表（`electron/main/services/db.ts:129-142`）+ `electron/main/services/storyboard-projects.ts` 服务层 + `electron/main/ipc/storyboard-projects.ts` IPC 注册 + `src/platform/contracts/storyboardProjects.ts` 平台契约 + `src/platform/adapters/electron/storyboardProjects.ts` adapter + `src/commands/storyboardProjects.ts` 前端命令桥，五层结构完整、可以照抄结构落地新的场景工程持久化。
- 画布里"分镜生成节点"（`StoryboardGenNode.tsx` + `src/features/canvas/nodes/storyboardGen/`）是目前唯一的"标准行组件 + 专属面板"节点案例，也是"节点内嵌自定义复杂交互面板"的现成参考（详见 `.claude/skills/canvas-node-builder/references/special-node-pattern.md`），但它是嵌在画布节点里的小面板，量级和一个完整三维场景编辑器不在一个数量级，本任务不套用这个模式，而是把"运镜控制"做成挂在工具箱 Tab 下的独立子应用。
- 全屏/大面板弹层已有先例，如 `src/components/Settings/components/SettingsDialog.tsx`，可作为"编辑器如何呈现"的界面参考。
- 图片资源统一走 `henji-media://` 协议 + `electron/main/services/ai-runtime/media-store.ts` 落盘管理，不应该另起一套图片存储方式；本地上传图/参考图统一走 `FileUploader`/`UiInput(type=file)`，导出的截图要能被这套机制识别复用。
- 项目已有本地 ffmpeg（`ffmpeg-static`/`ffprobe-static`）与 `electron/main/services/video/` 下的视频处理能力，是未来做"逐帧渲染 + ffmpeg 编码导出视频"（二期关键帧动画的落地方式）的现成基础，本次不使用，只作为后续任务的已知条件记录。

## 实测参考产品的功能现状（用于对齐一期范围）

用 chrome-cdp 实测 LibLib TV「3D导演台」得到的关键结论：

- 双视角模式：「导演视角」自由环绕摆场景，「机位视角」锁定某个相机对象、即最终取景预览。
- 场景对象三类：机位（相机）、角色、几何体/上传模型；角色是"单一基础骨骼 + 体型变体缩放"，不是真换模型；材质是纯色（十六进制颜色值），无贴图。
- 姿态控制是 FK 滑杆（前倾/转身/侧倾、躯干扭转、头部点头转头歪头、肩/肘/腕的前举/外展/扭转）+ 预设姿势库（站立/T型/行走/跑步/坐姿/蹲下/单膝跪/叉腰/鞠躬/格斗/踢球/招手/看手机等），不是通用 IK。
- 相机参数：位置 XYZ、注视目标（手动坐标或锁定某角色）、FOV，支持多机位。
- 几何体库：立方体/球体/圆柱体/环状体/圆锥/棱锥 + 本地上传。
- 输出是"相机截图"，直接变成节点画布上的一张图片，喂给后续 AI 生成节点；全程没有时间线/关键帧，这是它最大的短板，也是本项目计划做差异化的地方（但差异化能力留到二期）。

## 最终目标（本次任务范围内）

在工具箱 Tab 下提供一个可用的三维场景编辑器：能新建/保存/加载工程，能添加角色（体型变体+预设姿势+逐关节滑杆姿态调节）、道具/几何体、多个机位相机（位置/注视目标/FOV），场景纯色渲染，导演视角/机位视角可切换，机位画面能一键截图导出为本地图片，导出的图片能进入现有生成链路当参考图使用。

## 总体解决思路

- 渲染引擎：three.js，通过 `@react-three/fiber` + `@react-three/drei` 以 React 组件树方式接入，复用 drei 现成的 `OrbitControls`/`TransformControls`/`CameraHelper` 等，避免手撸 WebGL 底层代码。
- 姿态方案：FK 逐关节欧拉角滑杆 + 预设姿势 JSON 数据，不引入通用 IK 求解器（对照参考产品验证过这条路径够用）。
- 角色/道具资源：人形骨骼与基础动作/姿势来自 Mixamo（免费、骨骼标准统一、动作库量级最大），道具与几何体优先用 CC0 来源（Poly Pizza 原生 glTF、Quaternius、Kenney.nl），Mixamo 的 FBX 离线转换为 glTF/GLB 后随资源包分发，不在运行时做 FBX 解析。
- 工程持久化：完全照抄 `storyboard-projects` 的五层结构（SQLite 表 + 服务层 + IPC + platform 契约 + adapter + 前端 command），只是数据 schema 换成场景数据。
- 产品入口：作为工具箱 Tab 的第一个真实功能落地，替换 `ToolboxPlaceholder`；截图导出复用现有图片资源机制，不新建存储方式。
- 分阶段验证优先：三维引擎和免费资源管线都是项目里全新的技术领域，先各自独立验证可行性（第一阶段），确认没有打包体积、CSP、授权等硬性障碍后再投入正式编辑器开发（第二、三阶段），避免方向错了才发现。

## 技术方案

| 决策点 | 选型 | 说明 |
|---|---|---|
| 三维渲染 | three.js + @react-three/fiber + @react-three/drei | 与 React18+TS 技术栈契合度最高，drei 提供现成 gizmo/相机辅助组件 |
| 姿态控制 | FK 逐关节欧拉角滑杆 + 预设姿势数据 | 不引入 IK 求解器，参考产品验证过该方案足够 |
| 人形骨骼与基础姿势来源 | Mixamo | 免费、骨骼命名标准统一、未来动作库对接空间大 |
| 道具/几何体来源 | Poly Pizza / Quaternius / Kenney.nl（CC0 为主） | 原生或易得 glTF 格式，风格贴近"纯色低多边形"美术方向 |
| 资源格式 | glTF/GLB，离线转换后随资源包分发 | 不在运行时做 FBX 解析，减小运行时依赖 |
| 工程持久化 | 照抄 storyboard-projects 五层结构 | 项目内已验证成熟的模式，减少架构决策成本 |
| 动画引擎（二期预留，本次不实施） | Theatre.js core（仅动画引擎，不用其 Studio UI） | 见重要记录 001 |

## 任务范围

三维引擎接入与技术验证、免费角色/道具资源与转换管线验证、场景对象增删改、角色姿态系统（体型变体+预设姿势+逐关节滑杆）、多机位相机与双视角渲染、场景工程持久化、工具箱入口落地与截图导出接入现有生成链路。

## 非任务范围

关键帧/时间线动画、缓动曲线编辑器、逐帧渲染视频导出、自定义上传模型的动作自动重定向（需要人形骨骼映射规范如 VRM Humanoid/Mixamo 命名 + 运行时重定向逻辑，工作量大，留独立任务）、通用 IK 求解器、多人协作、云端同步、移动端适配。这些能力的技术方向已经过初步调研并记录在 `重要记录.md`，但本次任务不实施代码。

## 阶段划分与关系

1. **第一阶段-技术验证**：确认 three.js/R3F 在当前 Electron 技术栈下可行（1.1），确认免费资源到可用 glTF 的转换管线可行（1.2）。两者可并行，都是"能不能做"的验证，不是正式功能代码，允许验证过程中产出的临时代码在验证通过后重写。
2. **第二阶段-场景编辑器核心**：在第一阶段验证通过的基础上，做出真正的可交互编辑器——先有通用的对象数据模型和增删改能力（2.1），再分别接入角色姿态（2.2）和相机双视角（2.3），2.2/2.3 都依赖 2.1 的对象框架，彼此可并行。
3. **第三阶段-持久化与产品接入**：场景数据结构稳定后再定持久化 schema（3.1 依赖 2.1/2.2/2.3 全部完成），最后把编辑器接入工具箱 Tab、打通截图导出到生成链路的闭环（3.2）。

如果第一阶段验证发现方案不可行（例如打包体积暴涨、CSP 严重限制、Mixamo 资源授权有问题），须先更新本文件和 `重要记录.md` 里的技术选型结论，再决定是否调整第二、三阶段的方案，不要在方案已知不可行的情况下继续往下做。

## 新旧实现的兼容方式

完全新增能力，不改动现有生成链路（`GenerationService`/`aiRuntime`/画布节点体系）的任何现有代码，只在工具箱 Tab 下新增模块、新增数据库表、新增 IPC。已有的 `ToolboxPlaceholder.tsx` 在 3.2 完成后按情况废弃或保留，具体处理方式在 3.2 任务里确定并记录。

## 数据或接口兼容要求

导出的截图必须落地为标准本地图片文件（PNG），走 `henji-media://` 协议和现有媒体存储机制，保证能像本地上传图片一样被"生成"Tab 或画布节点的图片输入位置正常选中使用，不新建一套独立的图片来源/协议。

## 风险控制方式

- 三维渲染在 Electron sandbox/CSP 环境下的兼容性、打包体积增量，在 1.1 里提前验证，不要等到编辑器功能做完才发现打包/运行问题。
- 免费资源的授权条款、FBX→glTF 转换链路的可复现性，在 1.2 里提前验证并记录清楚每个资源来源的许可证类型，避免后续引入版权风险。
- 场景数据 schema 在 2.1-2.3 阶段可能反复调整，因此持久化（3.1）刻意排在场景编辑器核心功能之后，避免过早定死数据结构。

## 回退或恢复原则

本任务是全新增量能力，没有现有用户数据依赖，出现严重问题时可以整体移除 `src/features/cameraStage/`（或最终确定的模块目录）及对应的新增数据库表/IPC，不影响生成链路、画布、对话等现有主链路。新增数据库表全部使用 `CREATE TABLE IF NOT EXISTS`，不修改任何现有表结构。

## 全局开发约束

- 三维渲染逻辑必须留在渲染进程（依赖 DOM/WebGL）；资源转换（FBX→glTF）、工程持久化、未来的视频编码必须走 Electron 主进程或构建期脚本，遵循项目"前端负责界面展示与交互，后端负责文件系统/数据处理"的分工约束。
- UI 一律复用 `src/components/ui` 的 `Ui*` primitives 和 `styleTokens`，禁止新写原生 `<button>/<input>/<select>/<textarea>`，禁止颜色硬编码。
- 新文件优先 `<= 400` 行，`400~500` 可接受，超过需要有拆分计划。
- 新增/修改的导出函数需要显式返回类型，禁止新增裸 `any`。
- 模型定义、组件、Runtime/Provider 之间的跨层导入约束继续遵守 CLAUDE.md 现有规则。

## 最终验收条件

- 能在工具箱 Tab 新建三维场景工程，添加至少一个角色（可切换体型、可用预设姿势和滑杆调姿态）、若干几何体道具、至少两个机位相机（可调位置/注视目标/FOV）。
- 导演视角可自由环绕查看场景，机位视角能准确反映选中机位的真实取景画面，两者切换正常。
- 场景对象材质为纯色渲染，颜色可调。
- 机位截图能导出为本地 PNG，且这张图能在生成链路的图片输入位置正常被选中使用。
- 工程可保存、加载，关闭应用重开后数据不丢失。
- `npm run electron:smoke` 等现有回归检查无新增失败项。
