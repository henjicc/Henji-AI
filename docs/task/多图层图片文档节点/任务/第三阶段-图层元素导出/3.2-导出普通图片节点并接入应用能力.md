# 3.2 导出普通图片节点并接入应用能力

## 任务状态

- 状态：待开始
- 所属阶段：第三阶段——图层元素导出
- 前置任务：2.2、3.1
- 关联任务：4.2
- 是否可以并行：可以；2.2、3.1 均已完成，可与 4.1 并行，最终由 4.2 合并验收

## 任务目标

在完整图片编辑器中为当前受支持的单个图层、组或标注元素提供“一键导出到画布”动作。动作完成后创建普通图片节点、自动放置并从多图层文档节点连线；同时通过正式应用能力让智能助手可调用同一业务服务。

## 当前情况

- `ImageEditorV3` 已支持 `toolbarActions`，可以在现有命令栏动作区注入导出按钮，无需新增第二条工具栏。
- 画布 store 已有 `addDerivedExportNode` 和 `addEdge`，但 `NodeToolDialog` 当前在组件中依次调用，不能直接作为跨 UI/助手的正式事务。
- `src/features/canvas/application/canvasMutationService.ts`、`canvasBatchService.ts` 和 Canvas Application Capability 已提供受控节点创建、复制、删除和连线范式。
- 图片编辑 V3 的 reflection 已公开文档、图层、组、标注等稳定对象；跨域“渲染并创建节点”不是普通字段写入，需要算法型 `ApplicationCapabilityDefinition`。
- 普通导出图片节点可以保留受管 `imageUrl` 和尺寸，但不应复制源文档的 `imageEditSession`，否则会误变成第二个可写文档节点。
- 3.1 已实现 `createMultiLayerDocumentExportPort`，正式实现 `MultiLayerDocumentNodePort.materializeExportTarget` 与 `releaseExportRaster`。输入是节点 V3 会话及 `image_edit.layer` / `image_edit.group` / `image_mark.annotation` 稳定目标；输出包含受管 PNG 路径、预览路径、尺寸、比例、显示名称、透明信息、可补偿释放文件和诊断元数据。
- 2.2 已把 `MultiLayerDocumentEditorDialog.onCloseReady` 接到唯一 `saveMultiLayerDocumentAfterEditing`，并冻结打开时的项目和源节点上下文。文档节点的标准输出、下载和预览现在都以 CAS 成功后的最新 `imageUrl` 为准。
- `multiLayerDocumentNodeGenerationAdapter.ts` 已同时组装整图投影端口与 3.1 独立物化端口；`generationCanvasPort.createExportedImageNode` 仍是明确的未接入占位，3.2 应在同一组合根补齐，不另建 application 服务。
- `createMultiLayerDocumentProjectionCanvasPort` 展示了本项目同步比较项目/节点状态、一次写入 store、调用 `persistCanvasState`、失败补偿与清理候选日志的当前范式；独立导出需要复用相同事务边界，但成功结果必须是新的普通图片节点和连线。

## 实施方案

在图片编辑器现有命令栏动作区增加单一“导出到画布”动作。只有恰好选中一个受支持目标、文档已保存且当前节点/项目仍有效时启用；点击后显示进行中状态、防止重复提交，成功后保持编辑器打开，便于继续导出其他元素。

新增正式画布事务时，组装 1.2 的完整窄端口必须复用 `createMultiLayerDocumentExportPort`，且 UI/助手只调用既有 `MultiLayerDocumentNodeApplicationService.exportTarget`，不直接调用渲染适配器。业务服务会先物化独立 PNG，再通过画布窄端口创建普通 `exportImageNode`并连线；若画布事务未接管资源，它会调用 `releaseExportRaster` 释放 `ownedFilePaths`。

注册算法型 Application Capability，以稳定图片编辑对象引用和源画布节点引用作为输入，委托同一事务。能力要声明权限、影响范围、成功证据、可恢复错误和刷新范围；不要新增 HostCommand，也不要在助手 handler 中复制像素或节点创建逻辑。

## 执行步骤

1. 重新阅读助手目标、能力、状态规则和 `henji-application-capability`，核对现有图片编辑 reflection 与画布 mutation 能力的稳定引用格式。
2. 将 3.1 的当前选择适配为稳定导出目标；未保存 revision、多个选择和不支持类型必须禁用并给出明确原因。
3. 在 `ImageEditorV3` 现有 `toolbarActions` 注入导出动作和进行中/失败反馈，不新增工具栏、弹窗或通用按钮 primitive。
4. 实现 application 层原子事务：独立物化 → 准备普通图片数据 → 创建节点 → 建立连线；任一步失败执行精确补偿。
5. 确认导出节点是普通图片节点，不含源 `imageEditSession`、V1 图层栈或文档内部 ID；标题来自图层/元素用户名称。
6. 定义并注册正式 Application Capability，让 UI 和助手共用同一业务服务；补齐 live session、稳定引用、权限和成功证据。
7. 添加按钮启用规则、重复点击、物化失败、节点创建失败、连线失败、项目切换、助手调用和刷新可见性测试。
8. 按当前规则执行精确验证；若能力改变“通/不通”或欠账，更新 `docs/rules/assistant-status.md`，并记录是否需要在 4.2 做真实助手验证。

## 验收标准

- [ ] 恰好选中一个受支持目标时可一键导出，进行中不会重复创建。
- [ ] 成功后画布出现一个普通图片节点并从文档节点自动连线，编辑器和原文档保持不变。
- [ ] 导出节点显示、下载和下游连接均使用受管 PNG，且不含任何 V3 文档引用。
- [ ] 物化、节点创建或连线失败不会留下孤立节点或误改原文档。
- [ ] UI 和智能助手调用同一 application 服务，稳定引用、权限、成功证据和刷新范围完整。
- [ ] 正式界面不显示内部文档 ID、revision、资源引用或调试状态。
- [ ] 精确测试、助手能力覆盖检查和匹配验证通过；台账命中时已更新。
- [ ] 任务执行记录和总览已同步，4.2 已获得端到端场景所需稳定入口。
