# 5.1 接入多图层节点编辑器应用能力

## 任务状态

- 状态：已完成
- 所属阶段：第五阶段——助手稳定打开入口
- 前置任务：2.1、4.2
- 关联任务：3.2
- 是否可以并行：否；依赖已完成的完整编辑器路由和 V3 文档权威会话

## 任务目标

让智能助手通过稳定 `canvas.project` 与 `canvas.node` 引用，打开指定画布工程、定位指定节点，并且仅在节点是 editable-v3 多图层图片文档时打开该节点自己的完整编辑器。普通节点、旧 V1 和失效会话必须可自纠拒绝，不能误开工具箱独立图片编辑器。

## 当前情况

- 画布已有 `openCanvasProjectWithSummary`、`openApplicationSurface('workspace.canvas')` 和 `focusCanvasNode` 正式导航服务。
- `NodeToolDialogRouter` 已把 editable-v3 文档节点路由到 `MultiLayerDocumentEditorDialog`，`openMultiLayerDocumentForEditing` 可校验节点与权威 V3 会话。
- 助手原先只有工程打开和节点聚焦能力，没有打开节点专用编辑器的正式语义能力；通用 `openToolDialog` 是分镜拆分等多种工具共用的视图容器，有意 excluded，不能替代语义能力建账。
- 工具箱 `tool.image_edit` 是独立图片编辑入口，不代表画布节点的文档身份，不能作为本任务替代方案。

## 实施方案

新增严格 schema 的 R0 专用导航能力 `open_multi_layer_document_node_editor`。能力处理器只解析输入并委托正式 application service；服务按固定顺序打开工程、进入既有画布、聚焦节点、校验 editable-v3 与权威会话，再调用画布正式 `openToolDialog` action 并验证精确活动弹窗。

节点双击和“编辑”动作对 V3 节点复用同一服务。旧 V1 的迁移保持为 UI 兼容入口中的显式步骤，不进入 R0 导航能力。服务记录结构化开始、完成和失败日志，拒绝返回实际节点类型/状态与当前工程可用文档节点稳定引用。

## 执行步骤

1. 定义并注册 `open_multi_layer_document_node_editor`，约束稳定引用、权限、R0 风险、navigate Effect 和结构化结果。
2. 建立多图层节点编辑器 application service，串联工程打开、画布 Surface、节点聚焦、V3 校验、权威会话和正式弹窗 action。
3. 注册只委托该服务的能力处理器；保持 `openToolDialog` 通用视图容器 excluded，由专用能力覆盖多图层语义入口。
4. 让 `LayerStackResultNode` 的双击和编辑入口复用服务，同时保留 V1 显式迁移边界。
5. 补齐能力定义、注册发现、处理器委托、服务拒绝/幂等和 UI 共享入口测试。
6. 运行助手能力门禁、精确 Vitest、助手 harness、ESLint、渲染层 TypeScript 和差异检查。
