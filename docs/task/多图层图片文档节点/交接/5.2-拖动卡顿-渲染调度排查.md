# 5.2 拖动卡顿：渲染调度排查交接

## 结论

用户当前遇到的卡顿不是保存队列导致，而是多图层移动被明确排除在已有的低成本拖动反馈之外。

- 单底图满足条件时，移动过程只修改一个常驻 DOM 图片层的 `translate3d`，不发布 `PreviewOverride`，因此能逐帧跟手。
- 只要存在第二个可见内容图层，`resolveImageEditorRasterPasteboardLayerV3` 就返回 `null`，`directLayerFeedback` 随之为 `false`。
- 多图层移动随后在每个动画帧发布 transform preview，驱动文档投影、RenderPlan、视口瓦片读取/传输、共享 Worker 合成以及 Presentation Canvas 复制。调度会限制并发，却不会让像素生成变成低成本位移；旧草稿允许先显示、再追赶最新代，用户看到的就是明显落后于指针。

因此应修复的是“多层普通栅格文档缺少可移动的独立显示平面”，不应继续调整保存延迟，也不应只给 Worker 并发或节流参数打补丁。

## 根因证据

### 1. 已有快速路径只覆盖单个可见栅格层

- `src/features/imageEdit/v3/editor/rasterPasteboardV3.ts:12-33`：只有文档中恰好一个可见层，且该层为 resource raster、无 mask、无 brush tiles、opacity 为 1、normal blend 时才返回 pasteboard 图层。
- `src/features/imageEdit/v3/editor/ImageEditorPreviewV3.tsx:186-207`：该单层 pasteboard 与完整视口合成管线同时初始化。
- `src/features/imageEdit/v3/editor/ImageEditorPreviewV3.tsx:416-442`：pasteboard ready 后隐藏合成画面，直接显示源图 `<img>`。
- `src/features/imageEdit/v3/editor/useImageEditorLayerMoveGestureV3.ts:263-275`：只有 pasteboard 可用且目标为根级 raster、几何没有裁剪/旋转/镜像等条件时才启用 `directLayerFeedback`。
- `src/features/imageEdit/v3/editor/useImageEditorLayerMoveGestureV3.ts:336-346`：快速路径只写 `style.transform = translate3d(...)`，随后立即返回。

用户案例是 Seedream/KIE 分层结果，文档中存在多个可见 raster，必然在“恰好一个可见层”处退出快速路径。现有画布 Reality 夹具也正是两个可见、根级、normal、无 mask/tiles 的 raster：`scripts/lib/uiInspectionSceneCanvasEditing.cjs:170-206`。

### 2. 多图层路径每个 RAF 都进入完整合成链

- `src/features/imageEdit/v3/editor/useImageEditorLayerMoveGestureV3.ts:348-359`：没有快速路径时，每个动画帧调用 `controller.setTransformPreview(...)`。
- `src/features/imageEdit/v3/application/imageEditCommandBus.ts:126-140`：每次 `setPreview` 都重建 override snapshot 并通知订阅者。
- `src/features/imageEdit/v3/execution/useImageEditorViewportCompositeV3.ts:55-68`：snapshot 投影为新 document；document 或 override 引用变化都会增加 `renderGeneration`。
- `src/features/imageEdit/v3/execution/useImageEditorViewportCompositeV3.ts:81-100`：override 存在时以 draft quality 调用 RenderSession。
- `src/features/imageEdit/v3/execution/imageEditorRenderSessionV3.ts:121-157`：每一代 snapshot 都同步编译 RenderPlan、重算分析需求、warm source、present 并调度工作。
- `src/features/imageEdit/v3/execution/viewportCompositeClientV3.ts:167-199`、`:228-240`：草稿仍需取消/建立 job、准备文档、计划并读取多资源瓦片，后续还要传给 Worker 合成。

RAF 只把多次 pointermove 合并为“每帧最多一次重合成请求”，并没有提供“每帧一次低成本位移”。

### 3. latest-only 调度能限流，但不能保证跟手

- `src/features/imageEdit/v3/execution/imageEditorRenderSessionV3.ts:125-143`：draft→draft 且几何相同时走 `coalesceDraft`，不会取消当前在途草稿。
- `src/features/imageEdit/v3/execution/imageEditorRenderSessionV3.ts:266-273`：存在任意 `draft:` 任务时不会启动新草稿。
- 当前旧草稿结束后才由 `startTask(...).finally()` 再调度最新 snapshot（`:475-482`）。RenderSession 的既有测试也把“旧草稿可先呈现、完成后追赶最新代”当作预期行为。

这能避免任务爆炸，但连续拖动时显示帧天然落后于最新指针位置。不能把它当成逐帧交互反馈机制。

### 4. Presentation 仍有主线程像素复制成本

- `src/features/imageEdit/v3/execution/imageEditorPresentationSurfaceV3.ts:227-280`：每次可呈现结果都在主线程清 staging，绘制 fallback/target，再复制到 front 与 safety 两个 canvas。
- `src/features/imageEdit/v3/execution/imageEditorPresentationSurfaceV3.ts:291-339`：每个新的 result 会创建连续帧 canvas，把全部结果 tiles 经 atlas 再拼一次。

这些设计适合原子替换稳定帧，不适合拿来承担指针级的图层平移反馈。

### 5. 保存队列不是拖动中的瓶颈

- `setPreview` 只 emit；`ImageEditCommandBusV3.persistChange` 只在 dispatch/commit 后调用，见 `src/features/imageEdit/v3/application/imageEditCommandBus.ts:147-155`、`:220-227`。
- 画布宿主只在持久变更后设置 500ms 自动保存，见 `src/features/canvas/imageEditV3/CanvasEditToolEditorV3Host.tsx:287-310`。

因此拖动中没有每帧磁盘保存。鼠标松手时一次 commit、一次 revision 和延迟自动保存是正确行为，应保留。

## 建议修复

### 首选：把单图 pasteboard 扩展为“安全栅格图层显示栈”

为可安全直显的普通分层结果建立每层独立的常驻 `<img>`/presentation plane，复用现在单图 pasteboard 的屏幕像素位移逻辑：

1. 根据权威文档和资源描述构建显示栈，顺序必须复用渲染计划/图层树的既有顺序规则，不能在 UI 再发明一套层序。
2. 每个平面使用受管 `henji-media://image-editor-v3/...` 资源能力 URL，不暴露文件路径；资源媒体类型未知时不进入快速路径。
3. 拖动开始时保存目标平面 ref；pointermove 只更新该叶子平面的 `translate3d` 和参考线，不写 React 大状态、不发布 preview override。
4. 松手时只提交一次 `layer.update-common`；React 根据正式 transform 更新平面后清除手势残差，后台合成器再生成最终稳定帧。
5. 画布节点的实时保存语义不变：commit 后进入现有 500ms latest-only 保存队列。

首批安全范围应直接覆盖用户案例：

- 根级、扁平的多个 raster；
- `source.kind === 'resource'`；
- `blendMode === 'normal'`；
- `opacity === 1`；
- `mask === null`；
- `tiles` 为空；
- sRGB、8 bit、sRGB transfer、非 HDR；
- 无 crop、rotate、mirror；
- 资源描述有受支持的图片 media type。

Seedream/KIE 图层分离返回的普通透明 PNG/JPEG 元素应落入这一范围。透明 alpha 由图片自身承担，不妨碍平面合成。

### 复杂图层降级策略

以下任一情况出现时，整个显示栈继续使用现有 ROI/Worker 合成，不得用源图冒充最终像素：

- 非 normal blend、非 1 opacity；
- layer mask、稀疏 brush tiles；
- adjustment/effect 对层序或邻域像素有依赖；
- group/隔离组或嵌套父变换尚未被显示栈正确实现；
- crop、orientation、HDR/高位深/非 sRGB；
- 缺失或不可信的资源媒体类型。

降级时功能正确性优先，但应在后续设计中考虑“冻结下层合成 + 独立目标层 + 冻结上层合成”的三平面方案，避免复杂文档永远只能逐帧重合成。不要简单把目标源图叠到旧完整合成之上，否则旧位置会留下重影，层序、蒙版和混合也会错误。

## 现有测试缺口

### 单元测试把性能问题固化成了预期

`src/features/imageEdit/v3/editor/ImageEditorPreviewV3.test.tsx:462-530` 当前测试名称为“多内容图层移动按动画帧合并草稿更新且不叠加 CSS 位移”，并明确断言 `feedback` 为 `null`。它只证明：

- pointermove 被 RAF 合并；
- override 最终写入；
- 松手后只提交一次最终 transform。

它没有证明任何中间帧可见，更没有延迟门槛。修复后应改为：安全的多 raster 显示栈存在、100 次 pointermove 不产生 preview override、目标平面 transform 在每个 RAF 更新、pointercancel 清残差、pointerup 只提交一次 revision。

### 画布 Reality 有真实双层夹具，但没有执行移动

`scripts/lib/uiInspectionSceneCanvasEditing.cjs` 的 `canvas-multi-layer-document-editor` 已创建双 raster 文档并打开真实 Electron 编辑器，但场景只检查打开、导出、显隐、保存、预览更新和项目包往返，没有拖动任何图层。

建议直接扩展此场景，不另造重复场景：

1. 打开后选中“前景元素”，确认快速显示栈/目标反馈平面 ready。
2. 禁用吸附或按住 Control，按 8～12 个中间点连续拖动。
3. 每个点后等待一个 RAF，读取目标平面的 `getBoundingClientRect()` 或受控 transform；断言位移与指针累计差在 2 CSS px 内，且中间位置单调推进，不能只断言最终位置。
4. 每一步都断言 `data-document-revision` 未变化；鼠标松开后只增加 1。
5. 记录 pointer event 到下一次可见反馈的时延。确定性功能门槛建议先用“一个 RAF 内有位置反馈”；性能证据另记录 p95，目标对齐 `interactionMainThreadP95Ms = 16.7ms`，CI 若受调度噪声影响可把硬门槛设为不超过两个 RAF/50ms，但不能只检查最终 transform。
6. 松手后等待现有自动保存，重新加载权威文档并验证目标层 transform；关闭编辑器后节点预览仍按现有逻辑更新。
7. 同场景再加入一个复杂层配置，断言它没有误进入普通 raster 快速路径，最终像素与 revision 仍正确。

## 风险

- 图层顺序：必须确认 V3 文档数组顺序与 RenderPlan 的合成顺序，禁止凭 DOM 顺序猜测。
- 资源 URL：不要把主进程路径传到渲染层；应复用受管媒体协议并严格校验 media type。
- 旧帧重影：只有完整安全显示栈可替代现有 composite；不能在包含目标旧像素的 composite 上再叠一个移动源图。
- 提交闪跳：正式 document transform 生效前不能提前清除手势残差；应以目标平面已读取新 transform 或稳定合成代匹配为清理条件。
- 生命周期：平面切换、图片 load 失败、pointercancel、切工具、关闭编辑器时都要清理 transform/ref，且不得把瞬态状态持久化。
- 内存：多层 `<img>` 会增加解码表面占用，应限定快速路径层数/资源预算；超限立即回退 Worker 合成。

## 最小验收

- [ ] 用户同类的两个及以上普通分离 raster 图层进入低成本显示栈，拖动过程不发布 transform preview override。
- [ ] 连续拖动的每个中间点都有可见位移反馈，位置误差不超过 2 CSS px；不只验证松手后的最终位置。
- [ ] 拖动中 revision、历史和保存队列均不变化；松手只产生一个 revision 与一个历史单位。
- [ ] pointercancel、拖回原位、切换工具不产生持久修改，且没有残留 CSS transform。
- [ ] 松手后的稳定合成无重影、无层序错误，节点实时保存与关闭后预览更新保持原行为。
- [ ] mask、brush tiles、非 normal blend、effect/adjustment、group/crop/HDR 等复杂文档不误走普通 raster 快速路径。
- [ ] 扩展 `canvas-multi-layer-document-editor` Reality 场景，覆盖逐帧跟手、单次提交和持久化；精确单测覆盖资格判断与降级边界。
