# 5.2 多图层拖动卡顿热路径排查

## 结论

多图层文档移动卡顿的主因不是自动保存，也不是每次重新解码原文件，而是当前“直接位移”只覆盖单一可见栅格层。KIE 图层分离结果包含多个可见栅格层，必然退回 PreviewOverride 路径：每个动画帧发布一次变换预览，触发预览组件更新、瞬态文档投影、RenderPlan 编译、视口草稿调度以及 Worker 合成。即使源瓦片已经缓存，发送给 Worker 前仍会复制当前帧涉及的所有可见图层像素缓冲；图层越多，主线程内存复制和 Worker 合成越重。

拖动期间不会写文档历史或持久化。持久化只发生在 pointerup 最终提交之后。

## 热路径

| 阶段 | 当前行为 | 证据 |
|---|---|---|
| pointerdown | 记录手势、视口矩形和初始 transform。只有“存在单栅格反馈面、顶层栅格、无裁剪/方向变化、除目标外没有其他可见内容层”才进入直接 DOM 位移 | `src/features/imageEdit/v3/editor/useImageEditorLayerMoveGestureV3.ts:208`、`:239`、`:263`；`src/features/imageEdit/v3/editor/rasterPasteboardV3.ts:12`、`:22` |

## 可验证根因

现有测试已经把两条路径区分开：

- 单栅格测试断言连续 pointermove 不创建 PreviewOverride，只更新反馈元素的 CSS transform：`src/features/imageEdit/v3/editor/ImageEditorPreviewV3.test.tsx:391`、`:415`、`:422`。
- 多内容图层测试明确断言 rAF 后出现 transform PreviewOverride：`src/features/imageEdit/v3/editor/ImageEditorPreviewV3.test.tsx:462`、`:504`、`:511`、`:516`。

因此 KIE 多图层结果的卡顿是当前架构分支的确定结果，不依赖偶发网络、保存状态或图片首次加载。

## 建议的最小修复

### 实现边界

优先只覆盖 KIE 图层分离产生的“普通栅格堆栈”：顶层 `resource` 栅格、无 mask、无稀疏画笔 tiles、无裁剪和方向变换、sRGB 8-bit。复杂组、效果、调整层、特殊混合模式继续使用现有 Worker 预览降级，不能用源图冒充处理后的成品。

在该边界内，把现有单栅格 pasteboard 扩展成按图层顺序排列的瞬态栅格展示层：

1. 复用 `readImageEditorV3FastProxy` 和 `readImageEditorV3SourceMetadata`，按 `resourceRef` 预取每个普通栅格的代理和真实尺寸；缓存 object URL，并在卸载或资源变化时释放。
2. 复用 `rasterPasteboardV3.ts` 的 transform 换算和 `useImageEditorRasterPasteboardV3.ts` 的 ref/ready 生命周期，将单个反馈元素扩展为按 layerId 可寻址的栅格堆栈；不要另建第二套移动手势。
3. 拖动期间继续把坐标和 pending transform 保存在 `useImageEditorLayerMoveGestureV3` 的 ref 中，只对选中图层叶子元素写 `style.transform`，不调用 `setTransformPreview`，不更新文档 store，不调 Worker。
4. pointerup 只执行一次 `updateLayerCommon`；pointercancel 恢复元素样式且不写历史。提交后的直接栈保持到稳定合成帧接管，避免闪回旧位置。
5. 直接栈必须保持原图层顺序、透明度和资源像素尺寸；如果无法精确表达当前文档语义，必须在 pointerdown 前判为不适用并走原路径。

不要把 rAF 改成 10～15 fps 节流作为最终修复。节流只能减少任务风暴，仍然让视觉反馈等待全层 Worker 重合成，拖动不会真正跟手。

### 预计涉及位置

- `src/features/imageEdit/v3/editor/rasterPasteboardV3.ts`：提取普通栅格堆栈准入和 transform/尺寸计算。
- `src/features/imageEdit/v3/editor/useImageEditorRasterPasteboardV3.ts`：维护多资源代理、ready 状态、layerId → element ref。
- `src/features/imageEdit/v3/editor/ImageEditorRasterPasteboardV3.tsx`：按文档顺序渲染可直接呈现的栅格层。
- `src/features/imageEdit/v3/editor/useImageEditorLayerMoveGestureV3.ts`：把 direct feedback 从单一 ref 改为选中 layerId 对应的叶子 ref；保持一次提交语义。
- `src/features/imageEdit/v3/editor/ImageEditorPreviewV3.tsx`：直接栈与合成表面的无闪烁接管。

不需要修改 Canvas 自动保存、命令历史、文档持久化或 KIE 适配器。

## 测试与性能断言

### 精确单测

- 将 `ImageEditorPreviewV3.test.tsx` 的“多内容图层移动按动画帧合并草稿更新”改为普通多栅格快路径回归：连续 100 次 pointermove 后 PreviewOverride 始终为空，文档 revision 和 persistence 回调仍为 0，选中图层 DOM transform 等于最后坐标。
- pointerup 后只产生 1 个文档 revision、1 个历史单位和 1 次 persistence 通知；最终 transform 精确等于最后一次 pending transform。
- pointercancel、拖回原点和锁定层保持 0 次提交，并恢复瞬态 DOM transform。
- 至少覆盖三层顺序（下层／选中层／上层），截图或 DOM 顺序证明移动层没有被错误抬到最上面。
- 覆盖不满足准入条件的 mask、tiles、组或效果文档，断言仍走 PreviewOverride，防止错误扩大快路径。
- 覆盖代理加载失败和组件卸载，断言 object URL、异步请求和 refs 被清理。

性能回归不要使用机器相关的“总耗时小于 N ms”作为唯一门禁。优先使用确定性断言：N 次 pointermove 对 bus snapshot emit、RenderPlan 编译、Worker render 请求、源瓦片 buffer clone 的增量均为 0；pointerup 后这些计数只随一次稳定提交增长。

### Reality 场景

增加一个与生成结果同形状的 5 层透明 PNG fixture，在正式 Electron UI 场景中连续拖动约 2 秒：

- 拖动中截图确认选中层移动且上下层遮挡顺序正确，没有整图一起移动、双影或闪黑。
- pointermove 数量增加时，结构化 `image_editor_v3.viewport_composite.start`/Worker render 计数不随之线性增长；pointerup 后只出现最终稳定接管。
- 最终文档 revision 只增加 1，关闭并重新打开节点后位置保持。
- 场景同时检查 console error、pageerror 和结构化错误日志。

这是渲染热路径改动，完成实现后按 `docs/rules/testing.md` 选择 L2：精确测试、渲染层 TypeScript 检查，并运行缩小到该场景的正式 Electron Reality 验收。`electron:pan-bench` 测的是 ReactFlow 平移，不适合作为图片编辑器图层拖动的证据。

## 待确认

- KIE 当前实际返回的所有可见层是否始终为 `normal` 混合、无 mask/tiles；如果存在其他混合模式，第一版快路径应拒绝这些文档，而不是近似显示。
- 第一版直接栈使用 2048px fast proxy 作为拖动反馈时的清晰度是否可接受；若放大拖动仍需原分辨率，应复用视口金字塔瓦片而不是提高无界代理尺寸。
