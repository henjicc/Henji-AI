# 智能助手的终极目标与验收判据

> 读取时机：任何与智能助手相关的任务开始前。**先读这里，再读领域规则。**
>
> 本文件只写「要做成什么样」和「怎么算做到了」，**不写现状**。现状在 [assistant-status.md](assistant-status.md)，
> 那份会经常变；这份很少变。两者混在一起的话，规则会被台账的改动搅得没人信。

## 一、一句话目标

> **让智能助手成为这个软件的第二双手：人在界面上能做的每一件事，助手都能做，而且是走和人同一条路——同一个领域服务、同一份状态、同一个真相源，不是给助手另开一套。用户只需要说清楚要什么，剩下的选模型、调参数、跨工作区串流程、验证结果、失败了自己修，都由助手完成。**

这句话里有三个词是判据，不是修辞：

### 每一件事 —— 广度

人能做的助手都能做，差一件就是缺口，**不管有没有人报**。

更重要的是**缺口不能再生**：新增界面功能时助手同步接上的成本必须接近零。做不到这点，就是每加一个功能都欠一笔账，而账会比还账的速度长得快。这就是为什么登记要收敛成一处、覆盖门禁要遍历注册表而不是手挑场景。

### 同一条路 —— 唯一性

助手和界面必须调同一个领域服务、读写同一份状态。

一旦为助手开了旁路，它就会和界面漂移，然后变成两个真相源——而漂移**不会报错**，只会让两边慢慢给出不同的结果。所以「助手专用的某某实现」本身就是缺陷，不是权宜之计。

### 自己修 —— 闭环

助手撞墙时，错误信息必须带上运行时**已经知道**的事实：实体类型写错就列出该域注册了哪些、属性写错就列出这个实体有哪些、参数被静默丢弃就说清丢了哪些键、容量不够就给出上限。

只给一个错误码等于让模型继续猜，而它猜不中就是死循环。实测同一形状的缺陷在一个会话里出现过八次，代价从多烧一轮到整次运行报废不等（一次改设置：5 回合 3.8 万 token → 18 回合 25 万 token）。

## 二、做任务时拿这四句对照

| # | 问句 | 不通过的样子 |
|---|---|---|
| 1 | **人能做吗？助手能做吗？** | 界面上有的操作，助手没有对应路径 |
| 2 | **是不是同一条路？** | 为助手新开了入口、状态或判断逻辑 |
| 3 | **声明能走通吗？** | 注册齐全但经 Gateway 走不通——权限、revision、动态 availability、执行器，四关任缺其一 |
| 4 | **撞墙了模型能自己爬起来吗？** | 错误只有码，没有运行时已知的事实 |

**第 3 条是这个项目吃亏最多的一条。**「注册了但用不上」是一整类事故，不是几个孤立 bug，已经出现四种形状：域名没进工具契约（模型说不出）、域没有任何能力（说得出但目录是空的）、发现结果撞输出深度上限（连目录都拿不到）、并发基线发布不出来（拿得到目录但写不进去）。每一种都是"声明齐全、实际走不通"，而 `propertyCoverage` / `storeActionCoverage` 这类覆盖门禁**看不见它们**——那些守的是"声明与执行器一致"，不是"这条路经 Gateway 走得通"。

判断某个缺陷该由哪一层守、怎么验证，见 [testing.md](testing.md) 第四节「助手验证的三层分工」。

## 三、目标的边界

目标是「第二双手」，不是「第二套实现」，也不是「万能代理」。以下不在目标内，且这是**原则问题**，不是排期问题：

- **不为助手复制业务逻辑。** 助手接不上某个功能，正确的修法是把那个功能提升成可寻址的领域能力，而不是在助手侧写一份。
- **不为「设置某个值」「增删一条记录」这类动作手写专用 Agent 能力。** 注册实体属性后走通用动词（读/改/增删），专用能力只留给无法用属性写入表达的算法型操作。
- **不引入通用 Shell、任意文件系统、任意网络或不受控外部执行入口。** 助手的权限边界就是这个软件本身。
- **不把用户偏好改造成参数化面板。** 用户用自然语言说要什么，理解是助手的事。

暂缓而非否决的方向（会变，所以记在 [assistant-status.md](assistant-status.md) 而不是这里）：复杂多 Agent、技能市场、外部适配器。
